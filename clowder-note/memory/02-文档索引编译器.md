> 源码基线：`6868041ca`；重新整理日期：2026-09-13。本文只解决一个问题：项目中的 Markdown 如何进入记忆检索底座。示例是解释用的假数据，没有启动真实索引或数据库。

## 先给结论：它不是“搜索”，而是“搜索前的入库整理”

第一篇讲的是：

```text
聊天消息已经产生
    ↓
把消息写入 Redis
    ↓
把消息编译成 thread / passage 索引
```

第二篇讲的是另一种输入：磁盘上原本就存在的项目知识。

```text
项目 Markdown
    ↓
扫描和解析
    ↓
统一成 EvidenceItem
    ↓
写入 evidence_docs
    ↓
建立文档之间的 edges
```

所以第二篇的本质是：

> **把“人能读的项目文档”转换成“记忆系统能查、能关联、能回到原文的目录卡”。**

它不直接回答用户问题，也不负责最后把内容送进模型。第三、四、五篇的检索和排序，都建立在本篇产出的目录上。

## 1. 用图书馆理解它

假设项目中有四份文件：

```text
features/F042.md
  需求规格

decisions/ADR-007.md
  设计决策

plans/F042-plan.md
  上线计划

lessons-learned.md
  经验教训
```

图书馆不会把四份文件直接揉成一大段文字，而是先为它们建立目录卡：

```text
卡片 1：F042，类型 feature，标题“请求去重”，原文位置 features/F042.md
卡片 2：ADR-007，类型 decision，标题“采用稳定业务键”，原文位置 decisions/ADR-007.md
卡片 3：F042，类型 plan，标题“上线计划”，原文位置 plans/F042-plan.md
卡片 4：LL-001，类型 lesson，标题“重试必须幂等”，原文位置 lessons-learned.md
```

目录卡解决“在哪里、是什么、大概讲什么”；原始文件仍然解决“完整内容是什么”。

本篇的几个名词可以直接翻译成：

| 源码名词 | 先用什么中文理解 |
|---|---|
| Scanner | 文件发现和解析器 |
| ScannedEvidence | 刚解析出来的临时卡片 |
| EvidenceItem | 准备写入记忆库的标准卡片 |
| anchor | 卡片的稳定名字/主键 |
| sourceHash | 来源内容指纹 |
| edge | 两张卡之间的一条关系线 |
| `evidence_docs` | 卡片目录 |
| `edges` | 关系目录 |

## 2. 谁启动它？

API 启动时，工厂创建 `SqliteEvidenceStore` 和 `IndexBuilder`。随后启动流程调用：

```ts
await memoryServices.indexBuilder.rebuild();
```

也就是说，第二篇的主入口是：

```text
createMemoryServices()
    ↓
new IndexBuilder(...)
    ↓
indexBuilder.rebuild()
```

启动重建失败时，API 会记录 warning，而不是直接让整个服务启动失败。这代表“搜索索引失败不阻断 API 启动”，不代表索引已经成功。

源码：[memory factory](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/factory.ts#L128)、[启动时 rebuild](D:/AI/clower-1/clowder-ai/packages/api/src/index.ts#L926)。

## 3. 第一步：先决定用哪个 Scanner

Scanner 做的第一件事不是写数据库，而是回答：

> 当前这个目录应该用什么规则读取？

项目自己的 Cat Cafe 文档有固定目录约定，主要使用 `CatCafeScanner`；普通外部仓库可以走 `GenericRepoScanner`；collection 还可以通过 scanner resolver 选择其他扫描器。

不要把“四种 Scanner”理解成每次启动都会同时运行四个解析器。它们是可插拔实现，具体入口会根据项目根目录或 collection 配置选择。

本项目主要目录映射大致是：

```text
features     → feature
decisions    → decision
plans        → plan
lessons      → lesson
discussions  → discussion
research     → research
```

因此同一份内容放在 `features/` 和 `plans/` 中，默认可能得到不同的 kind。kind 不是装饰字段，它后面会参与冲突裁决、来源展示和搜索过滤。

源码：[Scanner选择](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L168)、[CatCafeScanner目录映射](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L1)。

## 4. 第二步：从 Markdown 提取一张临时卡片

以这份文件为例：

```markdown
---
feature_ids: [F042]
doc_kind: spec
topics: [retry, Retry]
---
# F042: 请求去重

重复请求只写入一次。

## Retry

策略见 [[ADR-007]]。
```

Scanner 大致提取：

```json
{
  "anchor": "F042",
  "kind": "feature",
  "title": "F042: 请求去重",
  "summary": "重复请求只写入一次。",
  "keywords": ["retry"],
  "sourcePath": "features/F042.md"
}
```

同时还保留：

```text
rawContent = 整个 Markdown 原文
provenance = 这条内容来自哪里、属于哪种来源层级
```

中间对象叫 `ScannedEvidence`：

```ts
export interface ScannedEvidence {
  item: Omit<EvidenceItem, 'sourceHash'>;
  provenance: Provenance;
  rawContent: string;
}
```

这里有一个关键点：`ScannedEvidence` 还不是最终落库对象，因为 `sourceHash` 要由 IndexBuilder 根据原始内容再计算。

源码：[ScannedEvidence契约](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/interfaces.ts#L58)。

## 5. summary 不是全文，也不是 LLM 总结

普通 Cat Cafe Markdown 的摘要提取逻辑很轻量：

1. 去掉 frontmatter；
2. 去掉标题；
3. 按空行分成段落；
4. 跳过标题、引用、表格和代码块开头的段落；
5. 取第一个合适的正文段落；
6. 超过约300字符就截断。

所以：

```text
summary = 适合搜索的短摘录
```

不是：

```text
summary = 模型读完整篇文档后生成的高质量总结
```

如果关键结论写在正文第七节，而第一段没有体现，文档级 summary 可能就没有这部分信息。后续是否能找到它，要看章节关键词、全文补充、passage 或原文读取。

源码：[extractSummary](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L434)。

## 6. 一个文件不一定只产生一张卡片

普通文档通常是一文件一条主要 EvidenceItem，但 `lessons-learned.md` 这类文件有特殊拆分逻辑。

例如：

```markdown
### LL-001: 重试必须幂等
响应丢失不等于写入失败。

### LL-002: 不要把超时当成写入失败
网络重试需要业务幂等。
```

可能得到：

```text
lessons-learned.md
    ↓
LL-001 卡片
LL-002 卡片
```

这解释了一个容易误解的现象：修改一个文件时，数据库里不一定只有一条记录需要考虑。逐条 lesson 的 `rawContent` 还可能是空字符串，导致它的 hash fallback 到标题；如果只改 lesson 正文、不改标题，普通 hash 路径可能无法发现这条拆分记录的变化。

这不是所有 Markdown 的通用行为，而是 Scanner 特殊拆分逻辑与 IndexBuilder hash 逻辑组合出来的边界。

源码：[lessons拆分](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L35)、[hash fallback](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L298)。

## 7. 第三步：anchor 是什么？为什么会冲突？

`anchor` 可以先理解成：

> 这张知识卡在整个记忆系统中的稳定名字。

例如：

```text
F042
ADR-007
LL-001
thread-<threadId>
session-<sessionId>
```

现在看两个文件：

```text
features/F042.md  → anchor=F042, kind=feature
plans/F042-plan.md → anchor=F042, kind=plan
```

同一个 anchor 出现两次，系统不能简单把两行都当作“F042 的唯一代表”，否则：

- 精确 anchor 查询会得到歧义；
- 关系边不知道连到哪一张卡；
- 后续 summary、向量和下钻可能对应不同来源。

IndexBuilder 使用 kind priority 参与裁决。简化理解：feature/decision 通常比 plan/discussion/research 更优先；低优先级条目不能在高优先级源文件仍存在时随意覆盖它。

注意：这是**类型优先级**，不是“谁的文本更正确”。它也不是搜索排名。源码：[kind priority与冲突保护](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L43)、[冲突判断](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L325)。

## 8. 第四步：sourceHash 决定是否需要重写

IndexBuilder 对扫描结果补上 hash：

```ts
const sourceHash = scanned.rawContent
  ? createHash('sha256')
      .update(scanned.rawContent)
      .digest('hex')
      .slice(0, 16)
  : existingOrTitleHash;
```

然后查询已有 anchor：

```ts
const existing = await this.store.getByAnchor(item.anchor);

if (existing?.sourceHash === item.sourceHash) {
  // provenance 不需要补齐时，跳过写入
  continue;
}
```

于是第二次启动时，如果文件没有变化：

```text
重新发现文件：是
重新读取和解析：是
sourceHash相同：是
重新写主表和embedding：通常跳过
```

所以 hash 节省的是落库和派生工作的重复成本，不是连文件都不读。

sourceHash 也不是文档身份。即使 hash 碰撞概率很低，它仍只是一个变更检测指纹，不应被描述成安全签名或版本历史。

如果索引规则本身变了怎么办？IndexBuilder 还保存 `indexing_version`。Scanner 逻辑升级后，即使原文没变，也可以触发 force rebuild。源码：[版本判断](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L252)、[hash与skip](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L291)。

## 9. 第五步：把卡片写进 evidence_docs

通过前面的检查后，IndexBuilder 才调用：

```ts
await this.store.upsert([item]);
```

这一步得到的是一条目录记录，例如：

```text
anchor      = ADR-007
kind        = decision
title       = ADR-007: 采用稳定业务键
summary     = 业务键由调用方生成
source_path = decisions/ADR-007.md
source_hash = 某个16位hex指纹
```

后续搜索可以先返回这张卡：

```text
anchor: ADR-007
sourcePath: decisions/ADR-007.md
snippet: 业务键由调用方生成
```

然后再通过 sourcePath 回到完整 Markdown。由此必须记住：

```text
写入 evidence_docs ≠ 把完整正文都放进目录卡
```

它主要是检索读模型，原文仍然是需要核查的来源。

## 10. 第六步：建立 edges——把“提到谁”变成关系线

文档里的关系来源主要有几类。

### A. frontmatter 关系

```yaml
related_features: [F042]
```

程序可以建立：

```text
ADR-007 --related_to--> F042
```

### B. WikiLink

```markdown
策略见 [[ADR-007]]
```

建立：

```text
F042 --wikilink--> ADR-007
```

### C. 文档相对链接

```markdown
查看 [决策](../decisions/ADR-007.md)
```

程序先把路径规范化，再通过“源路径→anchor”的映射找目标。

### D. 裸 Feature 引用

```text
历史替代项 F099
```

可能生成 feature_ref 关系。目标文档是否已经存在，要看具体抽取器和后续读取；关系本身不是把目标正文自动创建出来。

为什么要重建边前先删除旧边？

如果 A.md 原来引用 B，后来改成引用 C，只追加新边会留下错误的 A→B。全量重建先按 provenance 清理旧边，再根据当前扫描结果重建。

源码：[边清理与 frontmatter](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L344)、[边类型提取](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/edge-extractors.ts#L10)。

## 11. 全量 rebuild 与单文件 incrementalUpdate 的差别

这是第二篇最重要的工程边界之一。

### 全量 rebuild 掌握“当前世界是什么样”

```text
扫描全部输入
 → 得到全部 currentAnchors
 → 更新/跳过所有卡片
 → 重建相关 edges
 → 处理失效或过期对象
 → 可选生成向量
```

它能发现某个旧 anchor 已经不在当前扫描结果里，也能建立全局路径映射。

### incrementalUpdate 只知道“这几个路径发生变化”

```text
解析指定路径
 → 计算 hash
 → 更新相关卡片
```

它更快，但不天然知道：

- 哪个旧文件刚被删除；
- 全库中是否有同 anchor 的其他拥有者；
- 全局关系边是否需要完全重建；
- 其他 collection 是否也需要刷新。

因此不能说：

> incrementalUpdate 就是 rebuild 处理更少的文件。

更准确的是：

> **它们共享部分解析和落库能力，但掌握的信息范围不同，承担的正确性责任也不同。**

源码：[rebuild主流程](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L278)、[incrementalUpdate](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L606)。

## 12. 用一个完整状态变化收尾

初始状态：

```text
磁盘：features/F042.md、plans/F042-plan.md
数据库：没有F042
```

第一次 rebuild：

```text
扫描两个文件
 → 产生两个候选
 → feature优先级高于plan
 → evidence_docs中形成F042代表卡
```

此时 plan 不是一定被物理删除，而是不能覆盖当前高优先级拥有者；具体是否写入其他候选，要看当前 upsert/冲突路径。

接着修改 feature 文件中的正文：

```text
旧 rawContent → hash H1
新 rawContent → hash H2
H1 != H2
```

全量 rebuild 会重新处理卡片，并按当前扫描结果重建关系边。

如果只调用单文件 incrementalUpdate：

```text
只解析 F042 文件
 → 更新卡片和可能的派生索引
 → 不自动承担全库 edges 的重建责任
```

最后删除 feature 文件、保留 plan 文件时，全量扫描才能明确看到“旧拥有者消失、同 anchor 仍有 plan 候选”，再按规则让 plan 接管。单文件更新是否能正确处理删除和接管，要看它是否收到了删除语义，而不是只看文件修改接口。

## 13. 第二篇与后续章节的关系

```text
第02篇：文件 → evidence_docs + edges
第03篇：evidence_docs → FTS关键词候选
第04篇：evidence_docs/passages → 向量候选
第05篇：候选 → authority/消费/任务重排
第06篇：对话积压 → 抽象summary与候选
第07篇：旧session → bootstrap上下文
```

所以如果第二篇没有完成，后面会出现：

```text
没有统一anchor → 无法精确引用
没有sourcePath → 无法回读原文
没有sourceHash → 无法知道是否需要更新
没有edges → 无法沿关系导航
没有kind/status → 无法正确过滤和治理
```

## 14. 面试追问

**Q：这篇是不是在做RAG的chunking？**  
A：不完全是。它主要把项目文件编译成证据目录卡和关系边；普通文档摘要不是统一固定token分块。消息 passage 和向量召回是后续粒度。

**Q：Scanner发现一份文档后立刻写库吗？**  
A：先得到ScannedEvidence，再补sourceHash、做已有anchor比较和kind冲突判断，最后才upsert。

**Q：anchor和sourceHash有什么区别？**  
A：anchor标识对象，sourceHash检测来源内容变化。

**Q：为什么要保留原文路径？**  
A：目录卡只提供搜索入口；模型或工具需要通过sourcePath回读原文核查。

**Q：为什么不把所有关系都交给LLM抽取？**  
A：当前关系主要来自frontmatter、WikiLink、相对文档链接和Feature引用等确定性规则，结果可复现、可重建；LLM容易引入不稳定和幻觉。

**Q：全量和增量一样吗？**  
A：不一样。全量知道当前全部anchor，能做全局清理和关系重建；增量只处理局部输入，速度更快但全局责任更窄。

**Q：第二篇失败会导致整个服务不可用吗？**  
A：启动代码把rebuild失败作为非致命告警处理，但服务可能因此没有完整检索能力。这是“API可启动”和“记忆索引可用”两个不同状态。

## 最后只记住五个动作

```text
扫描文件
  ↓
解析字段
  ↓
生成统一卡片
  ↓
比较hash并写目录
  ↓
重建关系边
```

第二篇的核心不是某一个Scanner类，而是这个转换：

```text
人写的Markdown
    ↓
记忆系统认识的EvidenceItem
    ↓
evidence_docs + edges
```

把这条转换讲清楚，第三篇的关键词搜索、第四篇的向量搜索和第七篇的会话接续才有落脚点。
