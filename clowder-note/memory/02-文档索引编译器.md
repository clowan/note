## 1. 谁启动这次编译？先认清入口，再讨论算法

实际 API 启动先由 `createMemoryServices()` 初始化 store 并组装 `IndexBuilder`，随后启动流程等待 `indexBuilder.rebuild()`。构造器选出 scanner，并设置实际扫描根 `scanRoot`。

```text
createMemoryServices()
  → new IndexBuilder(store, docsRoot, ...)
  → detectScanner() 确定 scanner 与 scanRoot

API 启动调用 rebuild()
  → discover() 发现并解析文档
  → hash / 冲突裁决 / upsert
  → 重建文档关系边
  → 按配置处理 session、thread、message passage 等额外来源
  → 清理失效条目
  → 可选 embedding
  → 保存 indexing_version
```

本例没有那些额外来源，所以可以只看四份文件，不意味着生产方法中不存在它们。启动层会捕获重建异常并记录警告；这叫“索引失败不必终止启动”，不是“重建已经成功”。

源码：[工厂组装](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/factory.ts#L185)、[启动调用](D:/AI/clower-1/clowder-ai/packages/api/src/index.ts#L926)、[额外来源分支](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L418)。

## 2. 选择与发现：先决定按哪种仓库约定读文件

### 2.1 为什么本例有 package.json，却不选 Generic？

看主索引选择器的实际顺序：

```ts
if (existsSync(join(docsRoot, 'features')) || existsSync(join(docsRoot, 'decisions'))) {
  return { scanner: new CatCafeScanner(exclude), scanRoot: docsRoot };
}
if (hasProjectManifest(docsRoot)) {
  return { scanner: new GenericRepoScanner(), scanRoot: docsRoot };
}
const parentDir = resolve(docsRoot, '..');
if (parentDir !== resolve(docsRoot) && hasProjectManifest(parentDir)) {
  return { scanner: new GenericRepoScanner(), scanRoot: parentDir };
}
return { scanner: new CatCafeScanner(exclude), scanRoot: docsRoot };
```

源码：[detectScanner](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L169)。

这里的每个 `return` 都会结束选择：

| 条件，按顺序检查 | 本例中间值 | 下一步 |
|---|---|---|
| `/demo/docs/features` 是否存在 | true | 立即选 CatCafe |
| docsRoot 本身是否有项目清单 | 不再检查 | 不会改选 Generic |
| 父目录是否有项目清单 | 不再检查 | `/demo/package.json` 不影响本次结果 |
| 最终扫描根 | `/demo/docs` | `sourcePath` 相对它计算 |

如果没有前两个标准目录，选择器才会检查受支持的 `package.json`、`Cargo.toml`、`go.mod` 等清单；父目录命中时，会连扫描根一起提升。显式注入 scanner 则绕过探测，使用传入的 docsRoot。

**为什么这样做？** 可以把它理解为“具体仓库约定优先，通用约定兜底”。代价是：根目录不是纯粹的配置常量，后面的路径解析必须使用与 scanner 一致的根。探测的清单种类固定，探测本身是常量数量的存在性检查；真正的文件成本在下一步。

源码：[清单范围与构造器](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L152)。

### 2.2 为什么四份文件变成五个候选？

CatCafe 先调用 `splitLessonsLearned()`，再做普通文件扫描：

```ts
for (const item of splitLessonsLearned(projectRoot)) {
  results.push({
    item,
    provenance: { tier: 'authoritative', source: 'lessons-learned.md' },
    rawContent: '',
  });
}
```

普通扫描按标准目录、归档目录、顶层 Markdown、非标准目录补扫推进。本例每个标准目录只有一份文件，顺序可直接写出来：

| 扫描步骤 | 新增候选 | 候选总数 |
|---|---|---:|
| 特殊拆分 L | LL-001 | 1 |
| features | A | 2 |
| decisions | D | 3 |
| plans | P | 4 |
| 顶层 Markdown | 整篇 L | 5 |

所以“一文件一条目”在入口处就不是普遍规律。普通循环只使用发现结果的 `file.path` 去解析；发现阶段附带的 kind 不会直接作为最终类型写入。

源码：[两轮发现](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L37)、[目录顺序](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L149)。

递归分支的关键是：

```ts
if (depth > 10) return;
// 逐项检查时，节选：
const lst = lstatSync(fullPath);
if (lst.isSymbolicLink()) continue;
if (lst.isFile() && isIndexableSourceFile(entry)) {
  results.push({ path: fullPath, kind });
  discoveredPaths.add(fullPath);
} else if (lst.isDirectory()) {
  if (GENERATED_DOC_DIRS.has(entry)) continue;
  scanDir(fullPath, kind, depth + 1);
}
```

深度计数从 0 开始，超过 10 停止。递归遇到符号链接会跳过；但顶层 Markdown 分支用 `statSync`，不能推广成所有入口都执行同一链接检查。目录或文件不可读时，多数分支跳过它，后面清理阶段却可能把“没扫到”理解为“不存在”——两者的联系要留到第 11 节看。

`KIND_DIRS` 除 feature/decision/plan 外，还覆盖 discussion、research，以及多种 lesson 目录；fallback 排除 `.git`、`node_modules`、`mailbox` 等，生成目录 `exported-threads` 也被排除。LL 特殊拆分发生在普通 exclude 检查之前。

源码：[目录表](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L8)、[递归与补扫](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L125)。

**局部成本：** 设访问的文件/目录项数为 F、读取内容总长度为 B，常规遍历与读取成本约为 O(F+B)。`discover()` 返回一个数组并保留原文，不是读一份就立刻释放一份的流式实现。

## 3. Frontmatter 与 anchor：程序先问“这张卡是谁”

### 3.1 一行 feature_ids 如何变成数组？

提取器先找文件最前面的头部：

```ts
const match = content.match(/^---\n([\s\S]*?)\n---/);
if (!match?.[1]) return null;
```

- `^` 要求从文件开头开始。
- `\n` 是 LF，不等于任意换行约定。
- `[\s\S]*?` 跨行取最短匹配，直到关闭分隔符。
- 没有捕获到内容，就返回 null，不是抛出“YAML 语法错误”。

之后逐行执行的关键部分是：

```ts
const kv = line.match(/^(\w+):\s*(.+)$/);
if (!kv) continue;
const key = kv[1]!;
const rawVal = kv[2]!;
const arrMatch = rawVal.match(/^\[(.+)]$/);
if (arrMatch) {
  result[key] = arrMatch[1]?.split(',').map((s) => s.trim().replace(/^['"]|['"]$/g, ''));
} else {
  result[key] = rawVal.trim();
}
```

源码：[extractFrontmatter](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L367)。

把 A 的两行放进去：

| 表达式 | feature_ids 行 | topics 行 |
|---|---|---|
| `key` | `feature_ids` | `topics` |
| `rawVal` | `[F042]` | `[retry, Retry]` |
| `arrMatch[1]` | `F042` | `retry, Retry` |
| split、trim 后 | `["F042"]` | `["retry","Retry"]` |

注意，此时还没去重。这个解析器省去了完整 YAML 的复杂性，但只支持有限的单行键值和方括号数组；嵌套结构、缩进列表、块字符串不能按完整 YAML 来期待，普通标量也不统一去掉引号。

### 3.2 为什么 P 也会认领 F042？

编号提取是按字段优先级早返回：

```ts
const anchor = fm.anchor;
if (typeof anchor === 'string') return anchor;
const featureIds = fm.feature_ids;
if (Array.isArray(featureIds) && featureIds.length > 0) return featureIds[0] as string;
const decisionId = fm.decision_id;
if (typeof decisionId === 'string') return decisionId;
const planId = fm.plan_id;
if (typeof planId === 'string') return planId;
return null;
```

若返回 null，调用处用 `??` 回退到 `doc:相对路径去掉.md`。`??` 的意思是只在 null/undefined 时回退，不是“结果看起来不合理就换一个”。

| 候选 | 首个有效编号来源 | anchor |
|---|---|---|
| A | `feature_ids[0]` | F042 |
| D | `decision_id` | ADR-007 |
| P | `feature_ids[0]` | F042 |
| 整篇 L | 无 frontmatter | doc:lessons-learned |

这解释了冲突的来源：**编号来自元数据，不来自文件名，也不因 doc_kind=plan 自动变成独立计划编号。** 数组里写多个 feature ID，也只使用第一个当主键。

源码：[编号优先级](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L390)、[路径回退](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L84)。

kind 是另一条有顺序的判断链，节选如下：

```ts
if (docKind === 'decision' || filePath.includes('/decisions/')) return 'decision';
if (
  docKind === 'plan' ||
  filePath.includes('/plans/') ||
  filePath.includes('/phases/') ||
  filePath.includes('/guides/')
)
  return 'plan';
// lesson、discussion、research 分支省略
if (docKind === 'spec' || filePath.includes('/features/')) return 'feature';
return 'plan';
```

`||` 表示声明或路径任一命中即可；早返回说明前面分支有优先权。例如 spec 放进 plans 路径，也会先返回 plan，而不是把所有条件最后投票。对本例逐项代入：A 的 `spec`→feature，D→decision，P→plan；顶层 L 没有明确类型和匹配目录，回退 plan。status 在 frontmatter 是字符串时采用，否则 active；正文写“已完成”不会自动改变 status，类型断言也不等于运行时枚举校验。

**设计取舍：** 稳定 anchor 使文件改名后仍有机会表示同一知识对象，但允许多个文件认领同一个对象，所以必须有后面的冲突裁决。解析成本随头部长度增长；anchor 的几次字段判断是 O(1)。

源码：[kind 推断](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L402)、[status 赋值](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L89)。

## 4. 摘要与关键词：全文为什么不会全部进入搜索卡？

### 4.1 摘要是首段摘录，不是模型总结

以下是实际摘要函数的主体：

```ts
const afterTitle = content.replace(/^---[\s\S]*?---\s*/, '').replace(/^#.*$/m, '');
const paragraphs = afterTitle.split(/\n\n+/).filter((p) => {
  const t = p.trim();
  if (!t) return false;
  if (t.startsWith('#') || t.startsWith('>') || t.startsWith('|') || t.startsWith('```')) return false;
  return true;
});
const first = paragraphs[0];
if (!first) return null;
const trimmed = first.trim().replace(/\n/g, ' ');
return trimmed.length > 300 ? `${trimmed.slice(0, 297)}...` : trimmed;
```

源码：[extractSummary](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L439)。

逐步放入 A：

| 步骤 | 得到什么 | 为什么 |
|---|---|---|
| 第一轮 replace | 删除 frontmatter | 不把字段声明当摘要 |
| 第二轮 replace | 删除首个以 `#` 开头的行 | 实际正则未精确限定一级标题 |
| 空行分段 | 首个正文段为“重复请求只写入一次。” | 不是把全部段落连接起来 |
| filter | 排除空段、标题等段落 | 避免摘要主要由结构标记组成 |
| `paragraphs[0]` | 选中首段 | 后面的决策链接不是摘要 |
| 长度检查 | 原样保留 | 本段不足 300 |

标题另用 `^#\s+(.+)$` 匹配；未找到时 CatCafe 回退 anchor。摘要超长时保留 297 再补三个点，总长 300。这里的 length 是 JavaScript 字符串长度，不是 token 数或“300 个汉字”。这组正则也不是完整 Markdown AST：过滤某类段落，不代表正确理解了所有围栏和嵌套结构。

**为什么选首段？** 从实现可推导，它追求便宜、确定的目录卡，而不是每次扫描都调用模型。代价也直接可见：深藏在后半篇、未进入关键词的细节可能缺少检索入口。局部成本是对正文做几次遍历，常规约 O(B单篇)，摘要输出有界。

### 4.2 为什么 Retry 只保留一次，代码里的假标题不收？

围栏状态保存“字符种类+长度”，关闭条件是：

```ts
if (activeFence.char === char && length >= activeFence.length && suffix.trim() === '') {
  activeFence = null;
  continue;
}
```

只有不在围栏中，才尝试取标题：

```ts
if (activeFence != null) continue;
const heading = line.match(/^##+\s+(.+)$/)?.[1]?.trim();
if (!heading) continue;
if (heading.length > 80) continue;
keywords.push(heading);
```

| 读取行 | 围栏状态变化 | sectionKeywords |
|---|---|---|
| `## Retry` | 仍在围栏外 | `[Retry]` |
| `~~~text` | 进入 `~`、长度 3 的围栏 | 不变 |
| `## 示例中的假标题` | 仍在围栏内 | 不收这个标题 |
| `~~~` | 同字符、长度足够、后缀为空，退出 | `[Retry]` |

随后按“topics 在前、章节标题在后”合并：

```ts
for (const raw of [...primary, ...secondary]) {
  const value = raw.trim();
  if (!value) continue;
  const key = value.toLowerCase();
  if (seen.has(key)) continue;
  seen.add(key);
  merged.push(value);
}
```

| 本次 value | 查重 key | seen 原来有吗 | merged |
|---|---|---|---|
| retry | retry | 否 | `[retry]` |
| Retry，来自 topics | retry | 是 | `[retry]` |
| Retry，来自章节 | retry | 是 | `[retry]` |

算法按小写比较，但保留第一次出现的原始写法；不是把输出统一转换成小写。若标题超过 80 则跳过；围栏未关闭，后续标题会继续被当作围栏内容。遍历正文约 O(B单篇)，合并 K 个关键词约 O(关键词总长度)，seen 占 O(K)。

源码：[围栏与章节](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L453)、[合并去重](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L484)。

## 6. 指纹和编译版本：区分“文件变了”与“规则变了”

### 6.1 sourceHash 到底算了哪些文字？

```ts
const sourceHash = scanned.rawContent
  ? createHash('sha256').update(scanned.rawContent).digest('hex').slice(0, 16)
  : ((scanned.item as EvidenceItem).sourceHash ??
    createHash('sha256').update(scanned.item.title).digest('hex').slice(0, 16));
```

`update` 提供被散列的文本，`digest('hex')` 输出十六进制表示，`slice(0,16)` 只保留前 16 个十六进制字符，即 64 位指纹。它用于变化检测，不是绝不碰撞的身份或安全证明。真正的身份键仍是 anchor。

以下用 H(x) 代表这个表达式的结果，不编造散列常量：

| 候选 | rawContent 是否非空 | 实际被 hash 的内容 | 符号 |
|---|---|---|---|
| A / D / P / 整篇 L | 是 | 各自完整文件文本 | H(A0)、H(D)、H(P)、H(L0) |
| LL | 否，且没有自带 hash | `LL-001: 重试必须幂等` | H(LL标题) |

所以正文很长也要读完并 hash；300 字符只限制摘要，不限制 hash 输入。扫描、解析已经发生后才比较 hash，节省的是后续重复写入，不是免除本次扫描。主索引 hash 的常规成本约 O(B)。

源码：[hash 与 EvidenceItem 组装](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L298)。

### 6.2 为什么文件没变，也可能必须重写？

当前常量是 `INDEXING_VERSION=5`。重建读取 `embedding_meta.indexing_version`；缺失、不同或读取失败都视为版本变化。

```ts
const versionChanged = this.hasIndexingVersionChanged();
const effectiveForce = options?.force || versionChanged;
```

随后执行：

```ts
if (!effectiveForce) {
  const existing = await this.store.getByAnchor(item.anchor);
  if (existing?.sourceHash === item.sourceHash) {
    const needsProvenanceBackfill = !existing?.provenance?.tier && item.provenance?.tier;
    if (!needsProvenanceBackfill) {
      skipped++;
      continue;
    }
  }
}
```

| 条件 | effectiveForce | 能否走 hash 跳过 |
|---|---|---|
| 本例初建，版本键不存在 | true | 不能 |
| 已存 5，未 force，hash 一样且来源齐全 | false | 能 |
| 已存 5，hash 一样但旧记录缺 provenance | false | 不能，需要补字段 |
| 已存旧版本或显式 force | true | 不能 |

Builder 还在 hash 判断之前执行：

```ts
currentAnchors.add(item.anchor);
```

它记录的是“本轮看见了谁”，不是“本轮重写了谁”：

| 候选情况 | 是否写入 | 是否仍应在 currentAnchors |
|---|---|---|
| 原文未变，被 hash 跳过 | 否 | 是，不能误当成已删除 |
| P 被冲突保护跳过 | 否 | F042 仍在集合中，不重复增加 |
| CS-X 没有任何扫描候选 | 无此候选 | 不在；第 11 节将看到清理后果 |

如果只把成功 upsert 的编号放进集合，下次普通重建就可能把所有没变化的卡片当作陈旧记录删除。Set 的这一职责与 hash 去重不同。

`continue` 只跳过当前候选落库，不结束全量方法；后面的抽边仍会执行。force 也不取消下一节的 kind 冲突保护。版本最后保存，保存失败会让后续重建再次判为变化；这个键不是 SQLite schema 版本或模型版本，生产 session/thread 分支也未统一使用 effectiveForce。

**为什么需要第二种版本？** hash 反映“原料是否一样”，indexing_version 反映“提取规则是否一样”。比如刚增加章节关键词提取，即使文档没改，也要重做卡片。这是内容失效和编译规则失效的分工。

源码：[版本常量](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L41)、[版本读写](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L252)、[跳过判断](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L314)。

## 7. 冲突裁决与写入：为什么五个候选只留下四行？

### 7.1 用优先级选择 F042 的拥有者

源码给 kind 分配的优先级为：

```text
feature 4 > decision 3 > plan/discussion/research 2
          > session/lesson/thread 1 > pack-knowledge 0
```

实际保护分支：

```ts
const existingPriority = KIND_PRIORITY[existing.kind] ?? 0;
const newPriority = KIND_PRIORITY[item.kind] ?? 0;
const existingFileExists = existing.sourcePath ? existsSync(join(this.docsRoot, existing.sourcePath)) : false;
if (newPriority < existingPriority && existingFileExists) {
  skipped++;
  continue;
}
```

逐个代入，而不是只记“feature 优先”：

| 当前候选 | 库内旧拥有者 | 比较结果 | 主表动作 |
|---|---|---|---|
| LL | 没有 LL-001 | 不进入冲突分支 | 插入 LL |
| A | 没有 F042 | 不进入冲突分支 | 插入 A |
| D | 没有 ADR-007 | 不进入冲突分支 | 插入 D |
| P | F042 已由 A 占有 | `2 < 4 && true` | 跳过 P |
| 整篇 L | 没有 doc:lessons-learned | 不进入冲突分支 | 插入整篇 L |

`?? 0` 是未知 kind 的兜底值；`&& existingFileExists` 让已不存在的高优先级文件不能永久霸占编号。同级使用严格小于，所以没有按修改时间决胜的逻辑，遍历顺序可能影响结果。此处文件检查仍用 docsRoot；Generic 若提升过 scanRoot，两种根的语义可能不一致。

**设计取舍：** 用规格压住附属计划，避免搜索 F042 时标题随普通计划变动而漂移。但它是逐候选比较，不是先收齐所有候选再做稳定排序；优先级按 kind，和 provenance、authority 不是一回事。局部比较 O(1)，另外有一次查库与文件存在性检查。

### 7.2 upsert 不是“把新字段补到旧对象上”

主表的 SQL 原样如下：

```sql
INSERT OR REPLACE INTO evidence_docs
(anchor, kind, status, title, summary, keywords, source_path, source_hash,
 superseded_by, materialized_from, updated_at, pack_id, provenance_tier, provenance_source, generalizable,
 authority, activation, verified_at,
 source_ids, summary_of_anchor, compression_rationale,
 contradicts, invalid_at, review_cycle_days,
 world_id, scene_id, first_indexed_at)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
```

先不用背整张字段表。重要的是：

1. `anchor` 是主键；重复编号不会变成两张卡片。
2. 这是 `INSERT OR REPLACE`，不是第 01 篇 passage 的条件 `DO UPDATE`。
3. 问号按顺序绑定本次 item 的值，不会自动合并旧记录中的治理字段。
4. `first_indexed_at` 被显式查出并保留；这不是所有字段的默认待遇。

绑定值里有这些实际表达式：

```ts
item.activation ?? 'query',
item.verifiedAt ?? null,
item.sourceIds ? JSON.stringify(item.sourceIds) : null,
item.summaryOfAnchor ?? null,
```

| 输入 item 的字段 | 写入什么 | 容易误解的地方 |
|---|---|---|
| keywords 为数组 | JSON 字符串 | 主表不是数组列 |
| 没有 activation | query | 不会自动保留旧 backstop |
| 没有 sourceIds | NULL | 不会自动继承旧摘要来源关系 |
| 已有 first_indexed_at | 保留旧值 | 这是专门写出的保护逻辑 |

store 通过单写队列进入批次事务；Builder 每次 `upsert([item])` 传一项，不是整轮 rebuild 一个事务。字段序列化成本随字段长度增长；SQLite、FTS 和后置实体匹配成本另计。第 11 节会用具体状态说明“默认值重写”对 canonical summary 的影响。

源码：[upsert SQL 与绑定](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L1377)、[Builder 逐项提交](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L337)。

## 8. 抽边算法：把“提到了谁”编译成关系

### 8.1 为什么先删除一类旧边，而不是只加新边？

全量重建先按来源清理：

```sql
DELETE FROM edges WHERE relation IN ('related', 'related_to') AND provenance = 'frontmatter';
DELETE FROM edges WHERE provenance = 'content';
```

假设 A 删除了某个链接，如果只不断插入，旧关系会一直积累。当前实现选择“删除本轮负责的来源，再重算”。它不是清空所有关系：不符合这两条条件的边不会因此删除。代价是新边全部写好之前，有一个旧边已删、新边未齐的窗口。

| 原边 provenance | 本轮操作 |
|---|---|
| frontmatter 且 relation 为 related/related_to | 删除后重建 |
| content | 删除后重建 |
| 其他来源或 NULL | 不因这两句 SQL 自动清理 |

源码：[两类清理](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L344)。

### 8.3 WikiLink 与裸 Feature 编号不是同一种提取

WikiLink 先提取目标，再按小写排除自指和重复：

```ts

  const target = match[1]!.trim();
  const lower = target.toLowerCase();

裸 Feature 提取会先用空格遮住 WikiLink 和普通 Markdown 链接，再执行：

```ts

  const num = parseInt(match[1]!, 10);
  if (num > 999) continue;
  const fRef = `F${String(num).padStart(3, '0')}`;
  if (fRef === selfAnchor || seen.has(fRef)) continue;
  seen.add(fRef);
  edges.push({ fromAnchor: selfAnchor, toAnchor: fRef, relation: 'feature_ref', provenance: 'content' });
}
```

| 位置/输入 | 中间值 | 结果 |
|---|---|---|
| A 标题的 F042 | 42 → F042 | 与 selfAnchor 相同，跳过 |
| P 正文的 F099 | 99 → F099 | 输出 F042 → F099 |
| 整篇 L 的关联行 F042 | 42 → F042 | 源是 doc:lessons-learned，保留 |
| 另一个输入 F42 | 42 → F042 | 会规范为三位编号 |
| 另一个输入 F1000 | 1000 | 大于 999，跳过 |

遮住链接的目的，是避免同一个引用同时被当成“链接语法”和“裸编号”。但它没有统一遮住代码围栏，也没有检查 F099 目标是否存在。**别把正则命中解释成“已确认两个真实文档存在依赖”。**

## 11. 状态推演三：拥有者被删除，以及 canonical/backstop 的命运

这一节**回到 S1 独立演算**，不继承 A1 的正文修改。

### 11.1 删除 A 后，为什么不能简单把 F042 永久删掉？

因为 P 还在，也声明自己是 F042。增量算法因此采用“先删除，再寻找候选，再 upsert”。

删除定位的实际代码：

```ts
const relPath = relative(this.scanRoot, filePath);
const row = db.prepare('SELECT anchor FROM evidence_docs WHERE source_path = ?').get(relPath) as
  | { anchor: string }
  | undefined;
if (row) {
  await this.store.deleteByAnchor(row.anchor);
  this.embedDeps?.vectorStore.delete(row.anchor);
  deletedAnchors.push(row.anchor);
}
```

然后重新 discover，筛选 `s.item.anchor === anchor`。候选按下面的比较器排序：

```ts
candidates.sort((a, b) => (KIND_PRIORITY[b.kind] ?? 0) - (KIND_PRIORITY[a.kind] ?? 0));
const best = candidates[0]!;
if (!toUpsert.some((u) => u.parsed.anchor === anchor)) {
  toUpsert.push({ filePath: join(this.docsRoot, best.sourcePath!), parsed: best });
}
```

`b-a` 使高分靠前；`some` 表示本批已经有同号待写项时，不再用回补候选替换它。因此它不是对本批所有冲突做一次统一最优裁决。

| 阶段 | 中间状态 | docs 中的 F042 |
|---|---|---|
| 输入只有已不存在的 A 路径 | `toDelete=[A]`，`toUpsert=[]` | 仍为 A |
| 按 source_path 找旧记录 | row.anchor=F042 | 删除，暂时不存在 |
| 全量扫描剩余文件 | 同号候选只有 P | 仍不存在 |
| P 加入待写队列 | `toUpsert=[P]` | 仍不存在 |
| 第二轮 upsert | 旧拥有者已清除 | 变为 plan、H(P)、上线计划摘要 |

“先删除”就是为了让后来的低优先级候选有机会接管；如果先比较，P 会被仍在库里的 feature 挡住。

源码：[两轮处理与回补](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L622)。

### 11.2 卡片接管了，边也一起接管吗？

| 状态 | docs 行数 | F042 拥有者 | edges |
|---|---:|---|---|
| S1 | 4 | A，feature | e1～e5 |
| 删除 A 的增量完成 | 4 | P，plan | **仍是 e1～e5** |
| 再做全量 | 4 | P，plan | 只剩 e1、e4、e5 |

e2/e3 是 A 的链接，增量没有移除；全量从剩余文件重算才移除。`deleteByAnchor()` 本身只有主表 DELETE，没有统一清理所有入边和出边。上表是卡片重新占据同号后的陈旧边；如果没有候选接管，还可能留下指向已无卡片编号的边。

源码：[store 删除](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L1430)、[全量抽边](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L400)。

**这条算法的成本与边界：** 删除 D 个 anchor 会额外全量 discover；每个被删 anchor 再过滤 N 个候选，约 O(F+B+D×N)，还需候选排序和数据库查询。`source_path` 查询用 `.get()` 只取一行；L 那样一文件多 anchor，不会自动全部删除。解析 null 还可能来自不可读或被排除，不只来自真正删除；文件仍可解析但改了 anchor 时，增量也没有显式清掉旧 anchor。

这不是要求读者背四个缺陷，而是同一个设计选择的四个后果：**单文件返回“一个结果或 null”，表达不了零到多条记录、改名和失败原因之间的区别。**

### 12.2 哪个分支才会触发全库重新生成？

```ts
if (ctx.items.length === 0) return;
await ctx.embedding.reprobeIfNeeded();
if (!ctx.embedding.isReady()) return;

let toEmbed = ctx.items;
if (ctx.allDocsProvider) {
  const consistency = ctx.vectorStore.checkMetaConsistency(ctx.embedding.getModelInfo());
  if (!consistency.consistent) {
    ctx.vectorStore.clearAll();
    ctx.onVectorReset?.();
    toEmbed = ctx.allDocsProvider();
  }
}
```

先检查输入是否为空，再检查模型是否 ready，最后才检查元数据。把这个顺序代入不同场景：

| 输入与元数据 | 实际经过的分支 | toEmbed |
|---|---|---|
| 文档全部 hash 跳过，items 为空 | 第一行就 return | 不检查模型 |
| items 非空，但服务不 ready | 第三行 return | 不生成 |
| stored modelId=A，当前=B | 元数据不一致 | provider 返回的全部卡片 |
| modelId/dim 一样，只改 modelRev | 当前比较器认为一致 | 本批 items |
| 没有旧 modelId | 比较器认为“no prior meta”一致 | 本批 items |

比较器本身的实际条件是：

```ts
if (!meta.embedding_model_id) return { consistent: true, reason: 'no prior meta' };
if (meta.embedding_model_id !== current.modelId)
  return { consistent: false, reason: `model changed: ${meta.embedding_model_id} → ${current.modelId}` };
if (meta.embedding_dim !== String(current.dim))
  return { consistent: false, reason: `dim changed: ${meta.embedding_dim} → ${current.dim}` };
return { consistent: true, reason: 'ok' };
```

`String(current.dim)` 把运行时数字转成元数据表使用的字符串再比较；没有任何 modelRev 判断。因此保存了 revision，不等于使用了 revision 使向量失效。

主 Builder 的 provider 返回主表全部文档，且 reset 回调会清空 passage vectors；collection provider 只返回其前缀范围。所有批次完成后才写模型元数据。

维度变化也只能说明“需要另一套表示”：`ensureVectorTable()` 用 `CREATE ... IF NOT EXISTS`，没有把已有维度表迁移成新维度。不要把发现维度不一致，讲成已经完成 schema 迁移。

源码：[共享 helper](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/embed-utils.ts#L17)、[实际比较字段](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/VectorStore.ts#L32)、[向量表创建](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/schema.ts#L755)。

主增量直接调用：

```ts

  try {
    const [vec] = await this.embedDeps.embedding.embed([`${parsed.title} ${parsed.summary ?? ''}`]);

| 时间点 | 文档主表 | 文档向量 |
|---|---|---|
| 进入更新前 | 旧摘要 | 旧向量，若已有 |
| upsert 完成 | 新摘要 | 可能仍旧 |
| embed 成功并完成向量写入 | 新摘要 | 新向量 |
| embed 抛错 | 新摘要不回滚 | 没有在调用前主动删除的旧向量可能仍在 |

## 13. 一致性检查：用一个已验证的反例理解 COUNT 的边界

### 13.1 checkConsistency 实际证明了什么？

实现中的核心表达式就是：

```ts
const docCount = (db.prepare('SELECT count(*) AS c FROM evidence_docs').get() as { c: number }).c;
const ftsCount = (db.prepare('SELECT count(*) AS c FROM evidence_fts').get() as { c: number }).c;

返回对象把：

```ts

作为结论。它没有比较每个 anchor 的字段、边目标、向量，也没有执行 MATCH。数据库负责计算两次 COUNT；这个函数只做常量大小的结果比较，没有逐条完整性验证或修复动作。

### 13.3 串行写入也不是整个编译过程的原子提交

单写队列使一次入队工作按顺序执行；主 Builder 却在多次 await 之间依次完成：

```text
某些新卡片已经写入
  → 旧边被删除
  → 新边逐条写入
  → 失效卡片被删除
  → 远程 embedding
```

| 失败位置 | 可能留下的状态 |
|---|---|
| 扫描阶段跳过不可读文件 | currentAnchors 不完整，后续清理可能误判 |
| 删旧边后、插新边途中 | 部分新卡片与不完整新关系 |
| embedding 失败 | 文本主表已更新，向量覆盖不完整或仍旧 |

因此“写队列正常”“两张表 COUNT 相等”“业务仍能启动”是三个不同结论，都不等于整轮编译已经强一致。改进检查应包含实际 MATCH/倒排完整性、anchor 集、孤边和向量覆盖；这是拟改进方向，不是当前已执行的修复。

## 14. 换一种 Scanner，同样文件会不会得到同样目录卡？

主线已经讲通，现在再比较其他策略，不把四个类名堆在开头。以下是**不同入口下的对照推演**，不改变前面 S1/I1/R1 的定义。

### 14.1 Generic：按通用仓库约定取材，而非读取所有源码

它的 discover 主体按顺序调用：

```ts
this.scanAuthoritativeTopLevel(projectRoot, results, seen);
this.scanDocsDir(projectRoot, results, seen);
this.scanDerivedManifests(projectRoot, results, seen);
if (!options?.skipSoftClues) {
  this.scanSoftClues(projectRoot, results, seen);

```

| 输入位置 | provenance tier | 默认 kind |
|---|---|---|
| 根部 README/ARCHITECTURE/CONTRIBUTING/ADR 类 Markdown、docs/** | authoritative | plan |
| 根部受支持项目清单 | derived | research |
| CHANGELOG/HISTORY/RELEASE、issue templates | soft_clue | lesson |

这套策略把“来源层级”与“字段提取”分开，方便普通仓库接入，代价是不能自动继承 CatCafe 的全部含义。主 Builder 在根目录**直接子项**超过 200 时设置 skipSoftClues；不是整个仓库总文件数超过 200。扫描成本仍随访问项和文本增长。Generic Markdown 摘要直接截 300，不加省略号；有效 package.json 的描述和依赖名拼接没有同样的统一上限。

### 14.2 Flat/Structured 是 collection 入口的选择，不是主选择器的后两个分支

library rebuild 路由先取 manifest，再调用 `resolveCollectionScanner()`，最后创建 `CollectionIndexBuilder`。

把 collection.id 设为 mini、root 设为 `/demo/docs`：

| scannerLevel | 中间判断 | 选择 |
|---|---|---|
| 0 | 不探测 | Flat |
| 1 | 不探测 | Structured |
| auto，本例原样目录 | 无 SUMMARY.md；无 root/docs；根部仅 L 且无 frontmatter | Flat |
| auto，假设根部有 SUMMARY.md | 第一个条件命中 | Structured |

### 14.3 同一个 A，在 Flat 与 Structured 中怎样变化？

Flat 的编号表达式是：

```ts
const anchor = `${this.collectionId}:doc/${rel.replace(/\.md$/, '')}`;
```

Structured 先调用 Flat，再根据 frontmatter 覆盖：

```ts
const fmAnchor = extractAnchor(frontmatter);
if (fmAnchor) base.item.anchor = `${this.collectionId}:${fmAnchor}`;
const docKind = frontmatter.doc_kind;
if (typeof docKind === 'string' && FRONTMATTER_KIND_MAP[docKind]) {
  base.item.kind = FRONTMATTER_KIND_MAP[docKind]!;
}
```

| A 的字段 | Flat | Structured |
|---|---|---|
| anchor | mini:doc/features/F042 | mini:F042 |
| kind | research | spec 映射为 feature |
| scanner 的 provenance | derived | 有可解析 frontmatter，改为 authoritative |
| keywords | `[Retry]`，来自章节 | `[retry,Retry,ADR-007]` |
| title / summary / status | 请求去重标题 / 首段 / active | 本例相同 |

为什么 Structured keywords 还有 retry 与 Retry？它先保留 topics，再过滤已被 topics 覆盖的章节词和 WikiLink 目标，并不是 CatCafe 那个对整个序列去重的 merge。其新增关键词的核心顺序是：

```ts
const seen = new Set(topicStrs.map((t) => t.toLowerCase()));
const dedupSection = sectionKw.filter((k) => !seen.has(k.toLowerCase()));
for (const k of dedupSection) seen.add(k.toLowerCase());
const dedupWiki = wikiLinks.filter((l) => !seen.has(l.toLowerCase()));
const merged = [...topicStrs, ...dedupSection, ...dedupWiki];
```

| 中间值 | 本例结果 |
|---|---|
| topicStrs | `[retry,Retry]`，两项原样存在 |
| seen | `{retry}` |
| dedupSection | 空，Retry 已出现 |
| dedupWiki | `[ADR-007]` |

Structured 另接受 feature/spec、decision/adr、plan/design 等别名；没有 frontmatter 时仍保留 Flat 的基础结果，但可追加 WikiLink 关键词。WikiLink 在此是关键词，不意味着已经写入 edges。

两者遍历范围同样由 Flat 决定，递归 Markdown、深度保护、跳过目录与链接、处理 excludes；它们不调用 CatCafe 的逐条 LL 拆分器。SUMMARY.md 是选型信号，不是额外的目录链接遍历算法。Flat 围栏只是布尔翻转，不具备 CatCafe 同字符、长度、后缀配对的完整条件。局部成本仍是文本与关键词遍历，命名空间减少跨 collection 编号相撞，但不能消除同一 collection 内 A/P 共用编号。

源码：[Flat 解析](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/FlatScanner.ts#L85)、[Structured 增强与合并](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/StructuredScanner.ts#L21)、[Flat 围栏](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/FlatScanner.ts#L137)。

### 14.4 换 Builder，比换 Scanner 的影响还大

CollectionIndexBuilder 全量的跳过条件是：

```ts

## 15. 回到工程现场：输入约定和总成本怎么判断？

### 15.1 为什么开头特别约定 LF 与正斜杠？

不是为了绕开问题，而是先固定算法输入，再识别可移植性边界：

| 输入差异 | 对应源码条件 | 可能影响 |
|---|---|---|
| LF 改为 CRLF | frontmatter 正则要求开头 `---\n` | 编号与元数据可能走回退 |
| CRLF 段落 | 摘要按连续 `\n` 分段 | 段落选择不等同于 LF |
| Windows 反斜杠路径 | kind 使用 `'/features/'` 等字面包含判断 | 路径推断可能回退 |
| 只有标题或不可读文件 | summary 可返回 null，文件解析可返回 null | “无摘要”与“无候选”要分开 |

这是按表达式推导，不是本次运行 Scanner 得到的跨平台测试结果。不能从第 9 节的 LF 示例直接宣称当前 Windows 检出也得到同样编号。

还有一个长度例外：当前 CatCafe 会读取 SVG 的 title/desc/text/tspan 和部分标签文字，derived 摘要采用以下上限，而非 Markdown 的 300：

```ts
const summary = text.length > 3000 ? `${text.slice(0, 2997)}...` : text;
```

它索引的是抽出的文字，不是把图片像素做成向量。不同输入类型不能共用“全部只有 300 字符”的结论。

源码：[换行与路径处理](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L367)、[SVG 解析](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CatCafeScanner.ts#L223)。

### 15.2 不报虚构耗时，应该报哪些成本？

| 阶段 | 本篇已推导的成本来源 |
|---|---|
| 选择、发现、解析 | 固定探测 + F 个目录项 + B 长度文本 |
| hash 跳过 | 已付扫描成本，再逐候选查库；不是零工作 |
| 边生成 | N 条候选的路径 Map，全文扫描，E 条关系写入 |
| 全量清理 | 遍历 M 条主表记录，判定是否在 currentAnchors |
| 删除后回补 | 再次全量扫描，另有 D×N 候选过滤与排序 |
| embedding | K 条新卡片；模型重置可能扩大到 M 条 |

文档主干的常规 CPU 遍历可概括为 O(F+B+N+M+E)，但不能省略数据库、FTS、实体别名匹配与远程模型成本；扫描数组保留原文，空间至少要计 O(B+N)，另有主表列表等工作集。这里没有提供任何实测吞吐或耗时数字。

## 16. 面试时怎样从原理推到完整答案？

### 问一：这是不是一个普通的全文分块 RAG？

> 不是。本例四份文件先生成五个候选，再通过 anchor 冲突裁决留下四张卡。普通文档 FTS 只有标题与首段摘要，章节标题另作关键词；完整原文主要供 hash 和抽边使用。LL 是一个特定文件的逐条拆分，不是所有 Markdown 的通用 chunking。向量输入也只有标题加摘要，所以应该先确认信息是否进入这些字段，再讨论模型召回能力。

### 问二：为什么扫描器和构建器要分开？

> Scanner 决定去哪里读、如何从文本提取字段；Builder 决定哪些候选写入、谁占有编号、谁失效。这样 Generic 可以复用存储而不依赖 CatCafe 目录约定。但接口复用不保证算法等价：collection 用自己的 Builder，没有主索引的冲突与抽边流程。因此排错要先找实际入口，不能只看用了哪个 Scanner 类。

### 问三：hash 不变为什么还要全量重建？

> hash 检查原文是否变化，indexing_version 检查提取规则是否变化；两者不同。此外全量抽边不受单卡 hash 跳过控制。第 10 节增量已经写入 H(A1)，随后全量仍能移除旧 WikiLink、添加 F088 关系。全量的价值不只是多读几个文件，但读文件失败和治理清理边界也不会因“全量”两个字自动消失。

### 问四：增量到底便宜在哪里，又牺牲了什么？

> 无删除时只解析给定文件并更新卡片，不做全局边重建，因而扫描范围小；但不能承诺卡片、边和向量同时一致。有删除时还会全量扫描候选回补，复杂度出现 D×N。若要同时改善语义与成本，我会考虑让解析返回一文件多条证据及其出边，并维护 anchor 到候选的映射；这是拟设计，不是现有实现。

### 问五：既然源文档在 Git，为什么不能随便丢索引？

> 必须先分类库内记录。扫描卡片可以从文件再生成，CS canonical summary 却是数据库生成的治理结果。第 11 节中 CS-X 不在 currentAnchors，被普通清理删掉，原文又可能保持 backstop。安全的重建需要明确每类记录的所有权，并把内容字段和治理字段分开维护；不能只凭“这是索引库”判断全部可丢。

### 问六：换模型后是否一定重嵌入全部文档？

> 当前只有在 helper 收到非空 items、模型 ready、且 metadata 比较不一致时，才清空并重嵌入 provider 范围内的卡片。modelRev 没被比较，空批次提前返回，增量还绕过这个 helper。维度变化也不等于表结构已迁移，所以回答必须带触发前提，不能说只要改模型配置就全部完成。

### 问七：一致性检查 ok 还可能搜不到吗？你有什么证据？

> 可以。checkConsistency 只比较两次 COUNT。共享的内存 fixture 使用生产 SCHEMA_V1，故意不装同步触发器，插入 title=alpha 后报告 docCount=1、ftsCount=1，但 MATCH alpha=0。这直接否定“数量相同足以证明倒排可用”。它不证明真实库已损坏，也不等于所有重建路径的集成测试；排障还必须检查实际 MATCH、触发器及相关索引状态。

### 问八：单写队列是否解决了所有一致性问题？

> 没有。它串行的是一次入队工作，整个 rebuild 由多个提交阶段组成，远程 embedding 也不在这些同步事务里。失败可能留下新卡片配旧边，或者新文本配旧向量。要缩小这个窗口，可以考虑构建暂存结果后切换代次，并在扫描不完整时禁止破坏性清理；这属于后续方案，而不是已有的强一致保证。
