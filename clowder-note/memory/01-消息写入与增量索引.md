## 1. 第一站：消息先进入业务存储，不是直接进入向量库

### 1.2 Redis 到底保存了什么结构？

`RedisMessageStore.append()` 不只是写一个字符串。

它主要维护：

#### A. 消息详情 Hash

逻辑 key：

```text
msg:m101
```

其中保存：

```text
id
threadId
userId
catId
content
contentBlocks
toolEvents
metadata
mentions
timestamp
……
```

#### B. 时间线 Sorted Set

例如：

```text
msg:timeline
msg:user:<userId>
msg:thread:T42
msg:mentions:<catId>
```

Sorted Set 中：

```text
member = messageId
score  = timestamp
```

因此可以：

1. 先通过 thread 时间线获取一批消息 ID；
2. 再读取对应消息详情；
3. 按时间组装历史。

实际写入片段是：

```ts
const pipeline = this.redis.multi();

pipeline.hset(hashKey, {
  id,
  threadId,
  userId: msg.userId,
  catId: msg.catId ?? '',
  content: msg.content,
  // 其他字段省略
});

pipeline.zadd(MessageKeys.TIMELINE, String(score), id);
pipeline.zadd(MessageKeys.user(msg.userId), String(score), id);
pipeline.zadd(MessageKeys.thread(threadId), String(score), id);
```

这里使用的是 `redis.multi()`，变量虽然叫 `pipeline`，也不能仅凭变量名把它当成普通 pipeline。

源码：

- [`RedisMessageStore.append()`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/stores/redis/RedisMessageStore.ts#L77)
- [`消息 key 定义`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/stores/redis-keys/message-keys.ts#L6)

#### 面试官追问：为什么要 Hash 加 Sorted Set？

可以这样回答：

> 消息详情和访问路径分开。Hash 保存完整消息；Sorted Set 保存不同维度的有序消息 ID。这样按 thread 查历史不需要扫描全部消息，也不用在每条时间线里重复保存整个消息内容。

这里讲的是**访问结构**，不是记忆检索算法。全文和向量索引还在后面。

## 2. 记忆模块怎么感知“有新消息”？

### 2.1 不是每个 HTTP 路由都手动更新记忆索引

项目把通知挂在消息存储层。

启动时先建立一个回调占位：

```ts
let appendListener:
  ((msg: {
    id: string;
    threadId: string;
    timestamp: number;
    content: string;
  }) => void) | null = null;

const messageStore = createMessageStore(redis, {
  onAppend: (msg) => {
    appendListener?.(msg);
  },

```

等记忆服务初始化完成后，再接上真正的处理逻辑：

```ts
appendListener = (msg) => {
  if (msg.threadId) {
    ib.markThreadDirty(msg.threadId);
    ib.accumulateSummaryDelta(msg.threadId, msg.content);
```

- 存储创建时注入 `onAppend`；
- 通过闭包晚一点绑定实际 listener；
- 索引构建器通过读取函数访问业务存储。

这是**依赖注入加延迟装配**，不是神秘的事件总线。

### 2.2 `onAppend` 在写入之前还是之后执行？

源码顺序是：

```ts
await pipeline.exec();

// 业务消息写入之后，再发出索引更新通知
if (this.onAppend) {
  try {
    void Promise.resolve(this.onAppend(stored)).catch(() => {});
  } catch {
    /* best-effort */
  }
}

return stored;
```

因此，这条路径的核心顺序是：

```text
先完成消息存储调用
    ↓
再通知记忆索引
```

**不是先建好全文索引和向量，才能返回消息写入结果。**

源码：[`RedisMessageStore.ts:181`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/stores/redis/RedisMessageStore.ts#L181)。

#### 为什么同时有外层 `try/catch` 和 `.catch()`？

这是值得掌握的 JavaScript 细节。

表达式：

```ts
Promise.resolve(this.onAppend(stored))
```

会先执行：

```ts
this.onAppend(stored)
```

再把返回值交给 `Promise.resolve()`。

如果 `onAppend()` 在返回之前就同步抛错，后面的 Promise `.catch()` 接不到这个同步异常，所以需要外层 `try/catch`。

- 外层 `try/catch`：处理同步抛错；
- Promise `.catch()`：处理异步拒绝。

#### 由此得到什么保证？

可以说：

> 索引通知故障尽量不影响已完成的业务消息写入。

不能说：

> 只要消息写入成功，这条索引更新任务就被可靠持久化了。

因为这个通知是 best-effort，不是持久化队列。

## 3. Dirty Set 算法：为什么同一个 thread 来 100 条消息，只记一次？

实际实现只有一行：

```ts
markThreadDirty(threadId: string): void {
  this.dirtyThreads.add(threadId);
}
```

底层：

```ts
private dirtyThreads = new Set<string>();
```

假设连续发生：

```text
T42 收到 m101
T42 收到 m102
T42 收到 m103
T88 收到 m201
```

集合变化：

```text
{}
→ {T42}
→ {T42}
→ {T42}
→ {T42, T88}
```

它记录的是：

> 哪些 thread 需要重新检查？

不是：

> 每条消息对应一个索引任务。

源码：[`IndexBuilder.markThreadDirty()`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L823)。

### 3.1 这是不是 debounce？

源码注释中出现了 debounce，但从实现看，更准确的描述是：

> **固定周期刷新，加 Set 合并重复更新。**

因为定时器是固定的：

```ts
const DIRTY_THREAD_FLUSH_INTERVAL_MS = 30_000;

setInterval(async () => {
  await ib.flushDirtyThreads();
}, DIRTY_THREAD_FLUSH_INTERVAL_MS);
```

它不是传统意义上的：

```text
每来一条消息就重新计时，
直到最后一条消息之后安静 30 秒才执行。
```

这是面试中很好的区分：

- **Debounce**：不断推迟执行；
- **这里的实现**：按周期批处理，把同一 thread 的多次变化合并。

源码：[`定时刷新`](D:/AI/clower-1/clowder-ai/packages/api/src/index.ts#L949)。

---

### 3.2 为什么刷新开始时先清空 Set？

实际代码：

```ts
const dirtyIds = [...this.dirtyThreads];
this.dirtyThreads.clear();
```

然后才开始异步读取、处理。

考虑时间线：

```text
t0：集合是 {T42}
t1：取出快照 dirtyIds = [T42]
t2：清空集合
t3：开始处理 T42
t4：T42 又来一条新消息
t5：集合重新变成 {T42}
```

这样，处理期间的新变化可以留给下一轮。

如果等全部处理结束才清空集合，就可能把处理期间新加入的 dirty 标记一起清掉。

#### 但是，这个设计也有失败边界

源码接下来是：

```ts
try {
  threads = await this.threadListFn();
} catch {
  return 0;
}
```

如果：

```text
已经清空 dirty Set
    ↓
读取 thread 列表失败
    ↓
直接返回
```

当前快照没有被重新塞回集合。

因此不能说：

> 本轮失败，下一轮一定自动重试同一批 thread。

更准确的说法是：

> 当前采用 best-effort 增量刷新；后续新消息、启动重建等路径可以再次触发处理，但 Dirty Set 本身不提供可靠重试语义。

源码：[`flushDirtyThreads()` 开头](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L860)。

## 4. 第二条通知：待摘要计数和位图信号怎么累计？

`onAppend` 除了标记 dirty，还调用：

```ts
accumulateSummaryDelta(threadId, messageContent)
```

这个函数与索引刷新不同，它为**后续后台摘要任务**积累调度信息。

关键代码：

```ts
const tokenEstimate = Math.ceil(messageContent.length / 4);

let signalFlags = 0;
const lower = messageContent.toLowerCase();

if (/(?:决定|agreed|kd-|decided|confirmed)/i.test(lower)) {
  signalFlags |= SIGNAL_FLAGS.DECISION;
}

if (/(?:\.ts|\.js|\.tsx|pr\s*#|commit|merge|diff)/i.test(lower)) {
  signalFlags |= SIGNAL_FLAGS.CODE;
}

if (/(?:fix|bug|error|修复|报错)/i.test(lower)) {
  signalFlags |= SIGNAL_FLAGS.ERROR_FIX;
}
```

源码：[`accumulateSummaryDelta()`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L832)。

### 4.1 这里的“重要内容识别”是什么算法？

是正则启发式，不是 LLM 分类。

位定义是：

```text
DECISION  = 1 = 001
CODE      = 2 = 010
ERROR_FIX = 4 = 100
```

如果一条消息同时命中三类：

```text
001 | 010 | 100 = 111 = 7
```

按位 OR 的作用是：

> 已经出现过某类信号，就保留下来；后来的普通消息不会把它清掉。

数据库更新：

```sql
INSERT INTO summary_state (
  thread_id,
  pending_message_count,
  pending_token_count,
  pending_signal_flags,
  summary_type
)
VALUES (?, 1, ?, ?, 'concat')
ON CONFLICT(thread_id) DO UPDATE SET
  pending_message_count = pending_message_count + 1,
  pending_token_count = pending_token_count + ?,
  pending_signal_flags = pending_signal_flags | ?
```

三种累积逻辑不同：

| 字段 | 累积方式 |
|---|---|
| 消息数量 | 加一 |
| token 估计 | 相加 |
| 信号类型 | 按位 OR |

### 4.2 为什么不用精确 tokenizer？

这里用的是：

```ts
Math.ceil(messageContent.length / 4)
```

它只是决定“是否值得启动摘要”的一个便宜指标。

注意，**它和其他上下文预算位置使用的 `js-tiktoken` 不是同一种计数方式**。

因此面试时不能说：

> 整个记忆系统所有 token 数都由统一 tokenizer 精确计算。

当前代码中，不同位置有不同精度和成本的估算方式。

## 5. IndexBuilder 怎么读取消息？为什么不是直接依赖 Redis？

工厂装配时给它注入了读取函数：

这段转换非常重要。

它把业务层复杂消息转换成索引模块需要的最小快照。

例如：

```text

    ↓
索引快照中的 richBlocks
```

`IndexBuilder` 不需要知道消息是从 Redis、内存，还是其他实现读出来的。

源码：[`messageListFn 装配`](D:/AI/clower-1/clowder-ai/packages/api/src/index.ts#L793)。

### 5.1 为什么过滤 `origin === 'briefing'`？

briefing 是系统生成的上下文说明。

如果把它重新当原始讨论进行索引，可能出现：

```text
原始讨论
    ↓
生成 briefing
    ↓
briefing 又被索引
    ↓
下一次检索再次引用 briefing
```

这会增加重复和自我引用噪声。

所以过滤发生在**索引数据入口**，不是等搜索返回后再隐藏。

### 5.2 这里有没有通用多租户设计？

这一条装配中直接使用 `'default-user'`。

因此你应该描述为：

> 这是当前实例化的数据源装配方式。

不能单凭 `IndexBuilder` 有查询接口，就声称它已经具备完整的通用 SaaS 租户隔离。

## 7. 一条消息如何提取“可搜索文本”？

源码不是简单只用：

```ts
message.content
```

它还会提取富文本块中的文字。

实际算法：

```ts
const parts: string[] = [];
const seen = new Set<string>();

const push = (value: unknown): void => {
  if (typeof value !== 'string') return;

  const text = value.replace(/\s+/g, ' ').trim();
  if (!text) return;

  const key = text.toLowerCase();
  if (seen.has(key)) return;

  seen.add(key);
  parts.push(text);
};
```

然后：

```ts
push(message.content);

for (const block of message.contentBlocks ?? []) {
  collectBlockText(block, push);
}

for (const block of message.richBlocks ?? []) {
  collectBlockText(block, push);
}

return parts.join('\n');
```

源码：[`buildSearchableMessageContent()`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L90)。

### 7.1 算法逐步推演

假设同一条消息包含：

```text
content = "  重试需要   幂等键  "

某个 block.text = "重试需要 幂等键"

某个 block.caption = "响应丢失时不要重复写入"
```

执行结果：

#### 第一步：空白归一化

```text
"  重试需要   幂等键  "
→
"重试需要 幂等键"
```

#### 第二步：本条消息内去重

第二份同样内容被跳过。

#### 第三步：保留新的文字线索

最终：

```text
重试需要 幂等键
响应丢失时不要重复写入
```

### 7.2 它检查哪些字段？

包括：

```text
text
alt
caption
title
subtitle
label
description
body
bodyMarkdown
markdown
summary
```

并递归处理 `items`、`sections`。

因此：

- 图片的 alt/caption 可以进入文本索引；
- 但这不意味着这里把图片像素生成了多模态向量；
- 去重只发生在这一条消息的文本组合过程中；
- 这不是整个知识库的语义去重。

这个算法的目的，是避免“有价值的文字藏在富文本块里，纯 `content` 索引看不到”。

## 8. 变更指纹：什么时候跳过 Thread 条目的更新？

真实函数：

```ts
function computeThreadSourceHash(
  title: string,
  summary: string,
  keywords: string[],
): string {
  return createHash('sha256')
    .update(JSON.stringify({ title, summary, keywords }))
    .digest('hex')
    .slice(0, 16);
}
```

随后：

```ts
const existing = await this.store.getByAnchor(anchor);

if (existing?.sourceHash === sourceHash) {
  continue;
}
```

源码：[`computeThreadSourceHash()`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L72)、[`hash 比较`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L910)。

### 8.1 为什么不能只比较 thread 的最后活跃时间？

因为：

```text
时间变了
```

不一定意味着：

```text
搜索条目的有效内容变了
```

这里直接对索引使用的内容计算指纹。

内容不变，就不必重复写 thread 条目和生成对应向量。

### 8.2 这里有什么细微边界？

#### 第一，hash 不是整段完整聊天历史的 hash

只包含：

```text
title
被选取和截断后的 summary
keywords
```

因此：

> 某些消息变化没有影响这几个输入时，thread 条目 hash 可能不变。

#### 第二，keywords 数组顺序会影响 hash

```json
["cat-a", "cat-b"]
```

与：

```json
["cat-b", "cat-a"]
```

## 10. 核心算法：有变化才更新的 UPSERT

这段 SQL 是本篇最应该逐句吃透的部分：

```sql
INSERT INTO evidence_passages
(doc_anchor, passage_id, content, speaker, position, created_at)
VALUES (?, ?, ?, ?, ?, ?)

ON CONFLICT(doc_anchor, passage_id) DO UPDATE SET
  content = excluded.content,
  speaker = excluded.speaker,
  position = excluded.position,
  created_at = excluded.created_at

WHERE evidence_passages.content IS NOT excluded.content
   OR evidence_passages.speaker IS NOT excluded.speaker
   OR evidence_passages.position IS NOT excluded.position
   OR evidence_passages.created_at IS NOT excluded.created_at
```

源码：[`indexPassages()`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L1013)。

### 10.1 `ON CONFLICT` 处理的是什么冲突？

唯一键：

```text
(doc_anchor, passage_id)
```

因此，同一个 thread 下的同一条 message，再次索引不会多插一行。

例如：

```text
(thread-T42, msg-m101)
```

第一次来：

```text
INSERT
```

第二次来：

```text
发现同一个复合键
→ 进入 DO UPDATE 分支
```

---

### 10.2 `excluded` 是什么？

它表示：

> 这次原本准备插入的新数据。

可以把比较理解成：

```text
数据库里的旧 content
        对比
本次输入的新 content
```

它不是“被排除的历史记录”。

---

### 10.3 为什么最后还需要 `WHERE`？

如果没有这段条件，即使内容完全不变，也会执行更新。

有了它：

```text
所有字段相同
→ 不执行 UPDATE
→ changes = 0
```

这可以避免不必要的：

- 行更新；
- FTS 更新触发器；
- 后续向量失效。

注意用的是 `IS NOT`，而不是普通的 `!=`。

因为 `speaker`、`position` 等字段允许 NULL，需要处理“NULL 与非 NULL 不同”的情况，而不能被普通三值逻辑漏掉。

---

### 10.4 本轮实际验证结果

我直接从源码提取了这条 SQL，在内存 SQLite 中运行：

| 操作 | 实测结果 |
|---|---|
| 第一次插入 m101 | `changes = 1` |
| 完全相同的数据再次索引 | `changes = 0` |
| 同一消息内容发生变化 | `changes = 1`，行数仍为 1 |
| 只修改 `position` | `changes = 1` |
| 同样 passage ID 放在另一个 thread 下 | 可以插入另一行 |

最后一行说明：

> 去重范围是复合键，不是全局单独的 passage ID。

这比笼统说“我们用 UPSERT 防重复”具体得多。

## 11. 为什么重建时不删除“这次没读到”的旧 Passage？

`indexPassages()` 每个 thread 调用：

```ts

```

注意，这只是一次有限读取。

如果数据库中已经索引了：

```text

```

本次只读取到了其中一段：

```text
m3001 ... m5000
```

不能推导出：

```text
m1 ... m3000 已经被业务删除
```

“没有在这个读取窗口中出现”和“已经不存在”是两回事。

因此当前实现只更新本次返回的消息，并明确不因本次缺席而删除旧 passage。

源码注释也直接写了：

```text
never delete missing passages on rebuild
```

#### 本轮验证

内存表已经有：

```text

m102
```

下一次只重新索引 m102。

结果仍然保留两行，没有把 m101 删除。

#### 面试官追问：那真正删除的消息怎么办？

正确回答是：

> 这个索引刷新函数不能通过“本次没读到”判断删除。真正的删除同步需要明确的删除事件、墓碑或独立一致性清理机制。不能把窗口读取当作完整快照做全量差集删除。

这正是增量系统里常见的“局部视图不能推断全局不存在”。

### 12.1 为什么更新时先 `delete` 再插入？

假设内容从：

```text
alpha idempotency
```

变为：

```text
beta dedup
```

索引必须同时做到：

1. 不再把旧词 `alpha` 指向这条消息；
2. 把新词 `beta` 指向这条消息。

这里的 `'delete'` 是 FTS 的索引维护命令，不是在正文表里插入一条叫“delete”的消息。

```text
修改后搜索 beta：1 条
```

这验证的是**这条 passage 更新路径**。

不能据此扩展成：

> 所有 evidence 表的所有更新、替换、迁移路径都已经被本轮测试覆盖。

例如 thread 条目的 `upsert()` 底层使用 `INSERT OR REPLACE`，它和本篇这条 `ON CONFLICT ... DO UPDATE` 并不是同一条 SQL。文档条目的更新、rowid 和触发器关系会在对应篇章单独检查。

## 13. 正文变化后，旧向量怎么处理？

这是增量索引里很关键的一步。

SQL 执行后，源码立即检查：

```ts

```

源码：[`Passage 更新后的向量失效`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L1042)。

### 13.1 为什么不保留旧向量直到新向量生成成功？

因为旧向量对应旧内容。

如果：

```text
正文已经变为“不要采用方案 A”
```

但向量仍由旧正文：

```text
采用方案 A
```

生成，就出现了同一个条目的文本与语义表示不一致。

当前实现选择：

```text
正文变化
    ↓
使旧向量失效
    ↓
后续再补齐新向量
```

即使向量暂时缺失，文本和 FTS 路径仍然可用。

---

### 13.2 这里判断的是“内容变化”还是“整行变化”？

严格说，是：

```ts
result.changes > 0
```

而前面 SQL 的变化条件包括：

- content；
- speaker；
- position；
- created_at。

因此，**只修改 position 也会使向量失效**。

这点已经在本轮内存验证中确认：position-only update 的 `changes` 为 1。

这说明当前失效策略比较保守：

> 只要被索引行发生了这些变化，就重新考虑向量。

不能把它说成“精准地只在文本内容改变时才重新 embedding”。

如果后续要优化，可以把“影响向量输入的变化”与“纯元数据变化”区分，但那是改进方案，不是当前实现。

## 14. 缺失向量补齐算法：不是每次把所有文本重新 Embedding

`embedMissingPassages()` 的做法分成两个批量层次。

### 14.1 第一层：从数据库分批扫描

核心查询形态：

```sql

  id,
  doc_anchor AS docAnchor,
  passage_id AS passageId,
  content
FROM evidence_passages
WHERE id > ?
  AND doc_anchor IN (...)
ORDER BY id
LIMIT ?
```

扫描批大小是 **256**。

使用 `lastId` 作为游标：

```text
第一批读 id > 0
第二批读 id > 第一批最后一个 id
第三批继续
```

这不是：

```sql
LIMIT 256 OFFSET 很大的数字
```

而是按递增主键继续扫描。

### 14.2 第二层：只挑没有向量的 Passage

对读到的片段检查：

```sql

FROM passage_vectors

LIMIT 1
```

然后：

分开。

### 14.4 请求返回顺序为什么还要重新排序？

HTTP 返回后：

```ts
return body.data
  .sort((a, b) => a.index - b.index)
  .map((d) => {
    const arr = new Float32Array(targetDim);

    for (let i = 0; i < Math.min(d.embedding.length, targetDim); i++) {
      arr[i] = d.embedding[i]!;
    }

    return arr;
  });
```

程序依赖“输入第 i 条文本”和“输出第 i 个向量”一一对应。

所以它用响应中的 `index` 恢复顺序。

随后转换为固定配置维度的 `Float32Array`：

- 返回维度更长：按这里的代码只复制目标维度部分；
- 返回维度更短：剩余元素维持 Float32Array 默认的 0。

因此这段实现不是“维度不一致就严格报错”的验证器。

### 14.5 批次失败会怎样？

补齐算法：

```ts
try {
  await embedPassages(...);
  consecutiveErrors = 0;
} catch {
  consecutiveErrors++;

  if (consecutiveErrors >= 3) {
    return;
  }
}
```

含义：

1. 单批失败，不立刻终止整个扫描；
2. 连续三批失败，认为服务大概率不可用，停止本轮；
3. 成功一批后，连续失败计数归零；
4. 本轮失败的条目仍然没有向量，可以被后续扫描再次发现。

但要注意：

> “可以在后续扫描中被发现”不等于“这个函数自己建立了持久化重试任务”。

后续是否再扫描，还取决于后续 dirty 刷新、warmup 等触发路径。

## 15. 单写队列：它到底串行了什么？

Passage 的 SQL 批处理通过：

```ts
await this.store.runExclusive(() => tx(messages));
```

进入一个 Promise 队列。

实现是：

```ts
export class EvidenceWriteQueue {
  private tail: Promise<void> = Promise.resolve();

  enqueue<T>(fn: () => T | Promise<T>): Promise<T> {
    return new Promise<T>((resolve, reject) => {
      this.tail = this.tail.then(async () => {
        try {
          resolve(await fn());
        } catch (e) {
          reject(e);
        }
      });
    });
  }
}
```

源码：[`EvidenceWriteQueue`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/evidence-write-queue.ts)。

### 15.1 为什么 Node 单线程还需要这个队列？

因为：

```text
单线程执行 JavaScript
```

不等于：

```text
多个异步任务不会在 await 之间交错
```

例如：

```text
任务 A：读状态 → await → 写状态
任务 B：读状态 → await → 写状态
```

它们仍然可能交错。

队列提供的是：

> 进入这个队列的任务，按尾部 Promise 顺序执行。

---

### 15.2 一个任务失败，会不会把后面的队列“毒死”？

这份实现特意把：

```ts
reject(e)
```

作用在调用方拿到的 Promise 上。

内部链式回调捕获异常后没有重新抛出，所以内部 `tail` 可以继续完成，让后续任务接着运行。

否则，如果内部 tail 永远停在 rejected，而后续只写：

```ts
tail.then(nextTask)
```

下一批任务可能一直不执行。

这是一个很具体的异步队列实现细节。

---

### 15.3 它不保证什么？

不能把它说成：

- 多进程分布式锁；
- Redis 与 SQLite 的联合事务；
- 所有直接 `getDb()` 写入都自动进入的强制拦截器；
- 整条“写消息—生成向量”链路的原子性保证。

它是**某个 store 实例中的协作式写入串行化机制**。

本条 passage 写入批次中，正文 UPSERT、由此触发的 FTS 更新，以及代码中的旧向量删除发生在事务回调范围内；后续远程 embedding 请求则在外面执行，不需要把网络等待塞进这段同步数据库事务。

## 16. 把一次真实的算法变化串起来

现在用完整时间线总结本篇，不省略中间状态。

### 状态 A：新消息 m101 写入

```text
Redis:
  msg:m101 已存在
  thread 时间线中有 m101

Dirty Set:
  {T42}

SQLite:
  可能尚未有 m101 的 passage

模型向量:
  尚未生成
```

**此时消息存在，但不保证能通过记忆搜索找到。**

---

### 状态 B：定时刷新开始

```text
取出 dirty 快照 [T42]
清空 Dirty Set
读取 thread 和消息快照
```

先更新：

```text
evidence_docs:
  anchor = thread-T42
  summary = 有限长度的消息拼接
```

再更新：

```text
evidence_passages:
  doc_anchor = thread-T42
  passage_id = msg-m101
```

FTS 插入触发器使该片段进入全文索引。

---

### 状态 C：补齐向量

生成：

```text
passage_key = ["thread-T42","msg-m101"]
embedding   = 对应文本向量
```

写入 passage vector 表。

这时关键词和语义路径都具备了相应数据基础。

---

### 状态 D：m101 的内容被修改

条件 UPSERT 检测到变化：

```text
正文更新
FTS 删除旧词、加入新词
旧向量失效
```

暂时状态：

```text
新正文：有
新全文索引：有
新向量：可能还没有
```

这是允许出现的中间状态，不是全链路强一致。

---

### 状态 E：Embedding 失败

正文不会因为这次向量失败而被撤销。

当前状态可以是：

```text
关键词检索可用
语义召回暂时缺少该片段
```

以后补齐成功，再恢复语义侧覆盖。

这就是“向量是可再生成表示”在代码里的实际含义。

## 17. 这条算法的成本在哪里？

面试官问“增量更新是不是很便宜”，不能只回答“用了 hash 和 Set，所以很快”。

设：

- `T`：读取到的 thread 清单大小；
- `D`：本轮 dirty thread 数；
- `P`：扫描到的已有 passage 数；
- `K`：真正缺失的向量数。

当前实现至少存在这些成本：

| 阶段 | 成本来源 |
|---|---|
| 读取 thread 清单 | `threadListFn()` 读取清单，并建立 Map，不是只拿 D 个 thread |
| Thread 摘要刷新 | 每个 dirty thread 最多取 100 条消息并处理文字 |
| Passage 刷新 | 每个 dirty thread 最多取 2000 条消息，逐条执行 UPSERT 检查 |
| 缺失向量扫描 | 分批扫描相关 thread 已有 passage，并检查向量是否存在 |
| Embedding | 真正缺失的 K 条内容，以及变更后的 thread 级表示 |

因此：

> **增量的是“更新与生成工作”，不代表整个过程完全不扫描旧数据。**

尤其要区分：

```text
没有变化，所以没有重新调用 embedding
```

和：

```text
没有变化，所以什么 CPU、数据库工作都没做
```

后者不成立。

条件 UPSERT 即使最终 `changes=0`，查询和冲突检查仍然发生了。

这也给性能优化提供了具体方向：

- 是否能按消息变更游标读取，而不是反复读取大窗口；
- 是否能更直接查询缺失向量，减少逐条存在性检查；
- 是否区分纯元数据变化和文本变化；
- 是否给失败的 dirty 快照保留可靠重试状态。

这些是**从当前实现推导出的优化方向**，不是已经完成的功能。

## 18. 本篇可以直接用于面试的几个回答

#### 问：你们所谓“增量索引”，增量体现在哪里？

> 同一个 thread 的多次写入先通过 Dirty Set 合并。Thread 级条目比较 title、summary、keywords 的内容指纹；message 级 passage 使用复合唯一键与带差异条件的 UPSERT；向量侧使变化条目的旧向量失效，再只生成缺失向量。但数据库扫描本身仍有旧数据访问成本，不是纯追加式处理。

#### 问：消息写入成功，搜索就一定马上可见吗？

> 不一定。消息写入与索引刷新是分离的，存储层 listener 只做 best-effort 通知，随后周期刷新索引。30 秒是触发间隔，不是严格可见性 SLA。

#### 问：如何防止重复索引产生重复消息片段？

> passage 表使用 `(doc_anchor, passage_id)` 复合唯一键。重复输入走 `ON CONFLICT`，数据不变时 WHERE 条件阻止实际更新，`changes=0`。

#### 问：为什么正文改了，需要删旧向量？

> 向量是正文的派生表示，继续使用旧向量可能让语义匹配基于旧内容。当前实现优先失效，再异步补齐；向量缺失时保留正文和 FTS 能力。

#### 问：重建为什么不删除这次没看到的旧消息？

> 因为消息读取有限额，不是完整快照。未出现在本批数据里，不能证明业务记录已经被删除。

#### 问：你这次验证了什么？

> 使用源码中的 passage 建表语句、FTS 触发器和原样提取的 UPSERT SQL，在内存 SQLite 中验证了插入、无变化更新、文本更新、元数据更新、旧词移除、新词命中和旧行保留，共 14 个断言。没有把它扩展成真实 Redis、embedding 服务或整个应用端到端测试通过的结论。
