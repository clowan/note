## 1. 从工具调用到候选对象，哪些字段真的进入了存储？

工具是cat_cafe_retain_memory_callback。MCP侧调用callbackPost，API路由校验invocation身份与body，然后：

```ts
await deps.markerQueue.submit({
  content,
  source: `callback:${record.catId}:${record.invocationId}`,
  status: 'captured',

```

假设可信身份是cat-a/I42，输入content是“对可能重复送达的写入使用稳定业务键”。送给队列的source由服务端构造，不能通过body自称另一个cat就改变这条来源。

但这段route虽然允许tags/metadata入参，实际提交队列时没有把这些字段完整映射成keywords。不能根据工具schema允许tags就声称检索侧已按标签建立了索引。

返回status=ok表示候选提交这一步成功。它没有在此调用embedding，也没有立即写正式知识文档。

依据：[MCP写入入口](D:/AI/clower-1/clowder-ai/packages/mcp-server/src/tools/callback-memory-tools.ts#L48)、[retain route](D:/AI/clower-1/clowder-ai/packages/api/src/routes/callback-memory-routes.ts#L84)。

## 2. MarkerQueue怎样给候选身份并写成YAML？

submit生成randomUUID的前12个字符、createdAt，并保存content/source/status等字段。取一个有效形状的示意ID：a1b2c3d4-123。

写出的形式是：

```yaml
id: a1b2c3d4-123
status: captured
source: callback:cat-a:I42
created_at: 2026-09-12T00:00:00.000Z
content: |
  对可能重复送达的写入使用稳定业务键。
```

content的每一行都加两个空格。读端用配套的逐行解析器恢复字段和content块，不是支持任意YAML高级语法的完整对象反序列化器。

所以，格式边界是生产者和消费者共同定义的。把文件后缀叫yaml，不代表随意手工改成锚点、复杂嵌套结构，程序也能理解。

写入和transition前还验证marker ID只包含允许字符；transition使用传入ID而不是盲信文件内ID，避免篡改内容引导它去另一个路径。

依据：[submit](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/MarkerQueue.ts#L20)、[writeYaml/parseYaml](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/MarkerQueue.ts#L98)。

## 3. 保存两次相同结论，会发生什么？

这里没有先按content查重再复用ID，而是每次生成随机ID。因此正常情况下：

```text
第一次：M1，content=X
第二次：M2，content=X
```

两条都可能存在。随机ID解决记录身份分配，不解决业务去重；截短UUID也不是绝对无碰撞证明。

不要把“同一个文件不会被无意覆盖”和“同一个业务请求只处理一次”混在一起。后者需要稳定业务键、唯一约束或可靠去重记录。

源码写文件使用writeFileSync；这也不自动代表实现了临时文件+原子rename或完整崩溃恢复日志。

## 4. captured、normalized、approved是否构成强制流水线？

状态枚举包含captured、normalized、approved、rejected、needs_review、materialized、indexed。但是MarkerQueue.transition主要读文件、更新status及允许的patch字段、再写文件。

它不在这个底层函数里强制所有合法状态转换，也不因为状态叫normalized就调用一套文本语义归一化算法。

例如摘要自动候选的路径会依次调用transition到normalized和approved；那两步在这里主要是状态推进。不能把名字解释成“程序已经清洗、核验并证明了内容”。

各上层业务入口的检查和底层状态更新，必须分开阅读。

依据：[状态枚举](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/interfaces.ts#L21)、[transition](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/MarkerQueue.ts#L51)。

## 5. 正常批准轨迹：批准接口实际检查了什么？

用户批准M1，可能指定目标collection。路由按输入与manifest检查：目标存在、未归档、目标store可用；private/restricted来源需要明确目标collection；跨集合扩大可见性需要确认。

通过检查后，先把M1设为approved，然后尝试materialize。若有目标集合，就把root与CollectionIndexBuilder切换到目标集合，避免总写到当前项目。

这里至少有三个独立问题：

1. 谁可以调用该入口？身份与授权。
2. 这条知识能去哪个域？集合和可见性。
3. 里面是否包含不应公开的内容？内容审查与秘密扫描。

看到其中一项检查不能推导另外两项已经全面完成。Marker具备secretScanFingerprint等字段，也不等于这条generic approve路径必然执行了SecretScanner。

依据：[knowledge approve](D:/AI/clower-1/clowder-ai/packages/api/src/routes/knowledge-feed.ts#L83)。

## 6. materialize如何把对象变成一份真实文档？

实际服务先读取候选并要求status是approved，然后确定：

```ts
const kind = marker.targetKind ?? 'lesson';
const anchor = `${kind}-${markerId}`;
const root = options?.targetRoot ?? this.docsRoot;
```

本例没有targetKind，因此默认lesson，anchor为lesson-a1b2c3d4-123。文件包含frontmatter：anchor、doc_kind、materialized_from、created；有集合来源还会加source/target collection。

随后把marker.content写入正文。它不是让LLM“吸收进参数”，而是创建可供检索和读取的外部知识来源。

同名文件已存在会追加-2、-3等后缀，避免覆盖；默认不自动git commit。只有显式commit=true才尝试提交。

依据：[MaterializationService](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/MaterializationService.ts#L42)。

## 7. 写完文件后，状态如何变化？

继续执行：

```text
尝试 incrementalUpdate([outputPath])
  成功：reindexed=true
  异常：保留文件，reindexed=false
然后把marker设为materialized
返回markerId/outputPath/anchor/committed/reindexed
```

这里有一个容易忽略的事实：物化成功与索引成功是返回值中的不同信息。用户说“我已经保存了，为什么搜索看不到”，可以从reindexed字段与索引更新日志检查，而不是再次生成一份候选。

`indexed`在状态枚举中出现，不代表这个函数最后一定transition到indexed；当前这段最后设置的是materialized。

## 8. 失败轨迹：把每一步都当作可能中断

对M1逐阶段注入假设故障：

| 断点 | 候选状态 | Markdown | 搜索索引 | 合理理解 |
|---|---|---|---|---|
| 批准前失败 | captured | 无 | 无 | 尚未发布 |
| approved后写文件失败 | approved | 无/不完整 | 无 | 批准不等于落盘 |
| 文件成功，索引失败 | materialized可能已写 | 有 | 可能旧 | 需要重建/补索引 |
| 文件和索引成功，状态重写失败 | 可能仍approved | 有 | 可能有 | 不能只看状态判断未发生 |

这里是源码时序推演，不是本轮真实文件系统故障实验。YAML、Markdown、SQLite与git不在一个大事务中。

尤其第四种，若看到approved就再次物化，同名后缀可能创建第二份文件。防覆盖不等于幂等重放。要增强恢复，应记录阶段checkpoint或稳定输出身份，并区分“尚未写”与“写了但确认丢失”。

依据：[索引更新与状态收尾](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/MaterializationService.ts#L83)。

## 9. 为什么自动approved不能被描述为人工逐条审核？

第6篇模型候选会给confidence。当前解析器的explicit来源是模型输出标签中的感叹号。开关启用后，代码据此自动推进normalized、approved。


## 10. 知识越来越多，怎样发现重复？先别谈语义模型

DuplicateScanner默认读取lesson、decision、discussion，排除已经是canonical summary的条目。它使用title+summary，不读所有原文正文。

分词：小写，按非英数字/指定中文字符拆，去掉单字符token。连续中文短语可能仍是一整个token，不是中文语义分词。

然后计算词频TF、平滑IDF、TF-IDF稀疏向量，再两两计算余弦。这与第4篇外部embedding的神经网络向量完全是两套表示。

依据：[DuplicateScanner](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/f163-duplicate-scanner.ts#L26)。

## 11. 用三份资料手算TF-IDF，而不是只背公式

本轮真实内存fixture：

```text
A：alpha beta
B：alpha beta gamma delta
C：gamma delta
```

这些词是为了手算的代号。每个词都在三篇中的两篇出现，所以N=3、df=2：

```text
idf = ln((N+1)/(df+1)) + 1
    = ln(4/3) + 1
    ≈ 1.287682
```

每个词在各文档内只出现一次，TF=1。令w=1.287682，向量是：

```text
A = [w,w,0,0]
B = [w,w,w,w]
C = [0,0,w,w]
```

A与B的点积2w²，范数分别sqrt(2)w与2w：

```text
cos(A,B) = 2w² / (sqrt(2)w × 2w) = 1/sqrt(2) ≈ 0.7071
cos(B,C) ≈ 0.7071
cos(A,C) = 0
```

实际原始DuplicateScanner也输出相同连通簇与约0.7071的报告相似度。模型没有参与这次计算。

## 12. 从相似pair到簇：Union-Find究竟做什么？

默认threshold=0.6，因此保留两条边：A-B、B-C，不保留A-C。

初始化parent数组：

```text
[0,1,2]
```

union(A,B)把一个根连到另一个根；再union(B,C)。最终find得到相同根，三者归入同一组。find采用路径压缩，减少重复找根时的跳转。

关键结论：**同一簇只需要通过相似边连通，不要求簇内任意两篇都相似。** A与C的相似度是0，仍然因为B连接而同簇。这叫single-linkage的链式效应。

报告均值只对已经保存、达到阈值的pair平均，所以这里是(0.7071+0.7071)/2≈0.7071，不是把A-C=0也算进去后的0.4714。

suggestedTitle取簇内最长标题，本例是B。它只是合并建议，没有在scanner里自动删除A或C。

依据：[pair扫描与聚类结果](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/f163-duplicate-scanner.ts#L128)。

### 12.1 把 parent 数组真的写出来

Union-Find的两段核心代码：

```ts
while (parent[x] !== x) {
  parent[x] = parent[parent[x]];
  x = parent[x];
}
// union(a,b)：找到根ra/rb，若不同则parent[ra]=rb
```

按本例的边顺序：

| 操作 | parent数组 | 解释 |
|---|---|---|
| 初始化 | [0,1,2] | 每篇各自一组 |
| union(0,1) | [1,1,2] | A接到B的根 |
| union(1,2) | [1,2,2] | B的组再接到C |
| find(0) | 逐步压缩到根2 | A沿B也找到C |

分组时把所有相同root的下标放进Map，再去掉只有一个成员的组。孤立文档不是重复建议，因此不会被输出成“只有自己的一簇”。

这里的union没有按相似度再挑一个“最权威根文档”。根下标只是数据结构代表，不是知识保留对象；suggestedTitle又是单独按最长标题选的。若把Union-Find的root讲成最后保留的权威文档，就把结构算法与业务决策混淆了。
## 13. 为什么这个重复扫描不能声称无限扩展？

N篇资料要比较约N(N-1)/2对。Union-Find很快不代表整个算法很快，最重部分仍是两两相似度；文本变长还增加向量构造和点积成本。

把两两扫描变成近邻候选生成、先按主题/来源分组等，是可能的优化方向。但没有基准数据时，不能说当前N到了某个具体值就必然不可用，更不能把改进方案说成已经上线。

重复的语义判断也更复杂：标题摘要相似可能只是引用同一背景；某些互补文档不应该被一份摘要抹掉。因此产出“建议”比自动删除更容易审查。

## 14. ContradictionDetector真的在判断逻辑矛盾吗？

它先用incoming的title+summary搜索同kind最多10个候选，再对词频Map算余弦，留下similarity>0.3，reason为lexical_overlap。

注意两个区别：

1. 注释提到TF-IDF，但这份函数本体使用TF Map，没有重复扫描器那套IDF构造。
2. 它没有通过否定、条件或事实关系证明两段话矛盾。

本轮把incoming和候选都设置为完全相同的`retry request`。原函数仍返回约1的similarity、reason=lexical_overlap。这不是“完全相同的两句话逻辑上相互矛盾”，而是说明它只负责给出需要检查的重叠候选。

浮点结果可能是0.9999999999999998，因此验证使用容差，而不是把数学上的1当作所有浮点计算必须严格相等。

## 15. Canonical Summary怎样保留原始证据？

假设审核决定把A/B/C提炼成一份统一说明。createSummary接收sourceAnchors、title、summary、rationale。

先查给定sources是否存在，再拒绝source本身已经有summary_of_anchor的情况。目的之一是避免摘要再摘要的级联压缩。

事务中：

```text
插入CS-*条目：
  source_ids=[A,B,C]
  summary_of_anchor=某个组ID
  compression_rationale=为何合并
  authority=validated
  activation=query

更新A/B/C：activation=backstop
```

A/B/C没有被这个函数删除；新条目负责便宜入口，旧条目负责回查。validated在这里是程序赋的治理属性，不代表函数自己做了独立事实核验。

kind未指定时按sources中最多的类型选取，是计数规则，不是模型分类。

依据：[createSummary](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L1503)。

## 16. Backstop什么时候不出现在普通搜索里？

搜索代码根据压缩开关与includeBackstop决定是否追加activation过滤。不是把旧文档从世界上删除，而是让普通检索优先用整理后的入口，需要时显式回溯。

不过，也不能据此保证任何重建都保留治理状态。第2篇指出全量/增量重建有自己的源集合和清理逻辑；派生canonical与源文件重写之间的所有权需要明确，否则新扫描可能影响既有属性。

这里再次提醒：整个evidence.sqlite不只是可随便扔掉的全文索引缓存，还保存摘要、治理和评估数据。讨论重建算法不等于允许删除真实数据库。

依据：[backstop门控](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L185)。

## 17. 另外两套状态机为什么不能混成Marker的保证？

较早的MemoryGovernanceStore有明确转换表：draft→pending_review→published→archived，以及rollback。运行时创建的是内存Map实例。它不是MarkerQueue YAML文件的完整替代实现。

ProfileUpdate审批则有更细的恢复：per-target lock、claimForApproval、旧内容hash、writtenPath/provenancePath checkpoint，再finalizeApproval。

对比同一失败点：

```text
primer尚未写就失败 → 可以回退pending
primer已写、provenance失败 → 保留approving，后续从checkpoint恢复
```

如果把第二种也回滚成“什么都没写”，重入就可能重复执行已完成副作用。checkpoint的价值是区分“操作没发生”和“发生了但后续确认失败”。

这套服务的锁是进程级，也不能自动推广成多进程分布式锁。它展示一种不同恢复设计，而不是证明generic materialize已有同样机制。

依据：[旧治理状态机](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/stores/ports/MemoryGovernanceStore.ts#L1)、[Profile批准恢复](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/profile/approveProfileUpdate.ts#L1)。

本轮也直接执行旧治理状态转换函数：draft+submit_review得到pending_review，pending_review+approve得到published，而draft+approve抛异常。这验证的是旧状态表，不表示MarkerQueue.transition也执行了同样检查。

## 18. 本篇的验证与不能夸大的地方

实际运行：三篇TF-IDF重复扫描形成single-linkage簇；完全相同文本仍被潜在冲突函数返回。SQL采用内存数据库，潜在冲突的search依赖是只读fixture，没有修改真实知识文件。

## 19. 面试追问如何回答到代码？

**工具返回ok意味着什么？** captured候选提交完成，不是approved、Markdown、索引和模型消费全部完成。

**normalized是不是语义清洗？** 在这条自动推进路径里主要是状态变更，不能凭名字补出算法。

**随机ID和文件后缀能保证幂等吗？** 不能，它们分配身份、避免覆盖，不解决同业务请求重复处理。

**簇内每一对都达到0.6吗？** 不需要，single-linkage只要求连通；A-C=0的实际fixture仍成同簇。

**矛盾检测判断了真假吗？** 当前是TF余弦重叠候选，完全相同文本也会返回；判断真假与自动废止是更强的能力。

**压缩是不是删除原文？** createSummary把来源设为backstop，并保存source_ids；其他重建路径的相互影响仍需单独检查。

**怎么提高长期记忆可信度？** 从真实确认消息、精确引用、批准者身份、可见性、内容扫描和可恢复发布分别加约束；不能只把一个confidence字段写成explicit。
