## 本篇只解决一道题：找到了资料以后，怎样知道查全了没有、该读哪里？

用户问：

> “支付重试为什么必须幂等？项目里怎么决定的？通用方法怎么说？外部案例有没有反例？我以前是不是纠正过你？”

这不是一个关键词搜索就能完成的问题。它至少包含四种不同动作：

```text
决定去哪些库找
    ↓
各库返回候选 → 脱敏 → 合并排名
    ↓
选中一个对象 → 沿关系找依据 → 回读文件或原始消息
    ↓
区分：已经读过的证据、只发现的入口、没有覆盖的来源
```

profile 与 Event Memory 则回答另外两个问题：“开场应该记住用户什么偏好？”“用户哪条消息真的发生过纠偏？”它们不自动混入同一个 RRF 排名。

先不背八个类名。我们给这道题摆出一张小桌子，每走一步都检查桌上的数据如何变化。

## 1. 固定夹具：三本资料夹、六张证据卡、五条关系

### 1.1 三个 collection

| 简称 | collectionId | kind | sensitivity | status |
|---|---|---|---|---|
| 项目库 | `project:cat-cafe` | project | internal | active |
| 方法库 | `global:methods` | global | internal | active |
| 案例库 | `research:payments` | research | public，稍后改用 private 变体 | active |

前两个 ID 对应工厂的实际默认注册名。第三个是本篇模拟的外部库，不是已在你的机器上登记的库。public/private 是两份内存夹具，**没有修改实际 collection 配置**。

### 1.2 六张卡片的身份

后面的 P、L 等是阅读简称，不是新增字段；真实算法接收完整 anchor。

| 简称 | anchor | 所属库 | kind / title | updatedAt，均为 2026 年 UTC |
|---|---|---|---|---|
| P | `doc:retry` | 项目库 | plan / 支付重试方案 | 09-12 11:00 |
| L | `LL-042` | 项目库 | lesson / 幂等键教训 | 09-12 10:00 |
| T | `thread-t42` | 项目库 | thread / 为什么重复扣款 | 09-11 11:00 |
| G | `global:skill/retry` | 方法库 | plan / 通用重试方法 | 09-10 11:00 |
| X | `research:payments:doc/retry` | 案例库 | research / 支付重试案例 | 09-06 11:00 |
| Y | `research:payments:doc/rollback` | 案例库 | research / 退款补偿 | 09-04 11:00 |

还约定：P 的 keywords 为 `['稳定业务键']`，sourceIds 为 `['thread-t42']`；P 和 X 有文件 drillDown，G 没有。L 的 summary 是“重试应使用稳定业务键”。这些字段后面会真正参与算法，不能只把 title 当整条证据。

### 1.3 关系表也有存放位置

```text
P ──doc_link──── L ──related_to── T
│
├──related_to─── G
│
└──wikilink───── X ──doc_link──── Y
```

前四条关系存于项目 store，最后一条 X—Y 存于案例 store。`getRelated()` 对一条关系可从两端返回邻居，但同一条边不因此变成两条独立证据。

这个约定很重要：**节点在哪个库，与某条引用关系记录在哪个库，是两个问题。** 后面你会看到，候选评分和图展开处理这个问题的方式并不完全一样。

验证时，普通查询“重试”的库内排名固定为：

```text
项目 store → [P, L]
全局 store → [G]
案例 store → [X, Y]
```

这是为了单独验证协调层，不是声称真实 BM25 或向量模型一定给出这些名次。换成 Coverage 的查询时，我们会明确列出另一组固定输入。

## 2. 第一步之前：这三本资料夹怎样接进同一套服务？

### 2.1 Catalog 和 stores Map 各存什么？

可以把工厂装配理解为两张表：

```text
LibraryCatalog.collections：
  collectionId → manifest（根目录、类型、敏感级别、状态、策略）

stores：
  collectionId → 可以执行 search/getByAnchor 的 store 对象
```

最后的实际接线是：

```ts
const knowledgeResolver = new KnowledgeResolver({ projectStore: store, globalStore, catalog, stores });
```

因此，Catalog 有登记，不等于 stores Map 一定存在可用实现，更不等于索引已经完成。

工厂把主 store 注册为 `project:cat-cafe`；尝试创建全局 store，存在时注册为 `global:methods`；再读取外部 manifest，为非 archived 的外部库打开独立 SQLite，并设置 sourceRoot/sourceRef。来源：[`factory.ts`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/factory.ts#L208-L281)。

Catalog 本体只是内存 Map。外部登记信息由 `library/collections.json` 持久化，数据库另放在各 collection 对应目录中。别名也不是复制一份文档：重命名记录旧 ID 到新 ID 的映射，`get()` 最多追踪十次。来源：[`LibraryCatalog`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/LibraryCatalog.ts#L15-L62)、[`external-collections`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/external-collections.ts#L6-L46)。

### 2.2 为什么 G 能搜索，却没有文件回读提示？

看看全局技能条目的构造，关键字段是：

```ts
anchor: `global:skill/${entry.name}`,
kind: 'plan',
status: 'active',
title: fm?.name ?? entry.name,
summary: fm?.description ?? content.slice(0, 300),
updatedAt: statSync(skillPath).mtime.toISOString(),
```

它没有填 sourcePath。所以我们让 G 没有 drillDown，不是故意制造奇怪数据，而是在保留这个实际构造边界。

`GlobalIndexBuilder` 默认技能根为 `~/.claude/skills`，memory 根为 `~/.claude/projects`。它读取各技能的 `SKILL.md` 与根级 refs，再读各项目的 memory 子目录，不是扫描整台机器。memory 文件遍历里有一个不能漏掉的条件：

```ts
if (!file.endsWith('.md') || file === 'MEMORY.md') continue;
```

**读取 memory 子目录，不等于把 MEMORY.md 本身也编进索引。** 全局条目多为 title/summary 投影，而非整份文件常驻上下文。启动确实调用全局 rebuild，异常只记 warning。来源：[`全局发现算法`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/GlobalIndexBuilder.ts#L59-L119)、[`默认目录`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/factory.ts#L211-L225)、[`启动重建`](D:/AI/clower-1/clowder-ai/packages/api/src/index.ts#L939-L946)。

### 2.3 为什么 X 的 anchor 前面多了一段 collectionId？

外部资料通过 scanner 转换成 EvidenceItem。当前分派没有四套高级引擎：

```ts
if (level === 0) return new FlatScanner(manifest.id, manifest.exclude);
return new StructuredScanner(manifest.id, manifest.exclude);
```

auto 探测后选 0 或 1；配置类型虽允许 2、3，它们在这里仍走 StructuredScanner。

Flat 从 Markdown 相对路径构造：

```ts
const anchor = `${this.collectionId}:doc/${rel.replace(/\.md$/, '')}`;
```

于是案例库的 retry.md 变为 X，而不是与项目 P 共用一个裸 `retry`。StructuredScanner 即使读到 frontmatter 指定的 anchor，也会加 collection 前缀。这个身份约定正是后面跨库去重不误合并的基础。来源：[`scanner 分派`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/scanner-resolver.ts#L10-L48)、[`Flat anchor`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/FlatScanner.ts#L85-L113)、[`Structured anchor`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/StructuredScanner.ts#L22-L58)。

完整 rebuild 会先扫描秘密，命中则清理该 collection 索引并返回 blocked；正常时比较内容 hash/authority 再 upsert。单独的 incrementalUpdate 没有重复这套批量秘密检查，不能把完整重建的保证扩大到所有写入。外部项目启动也有真实桥接：Expedition 调用 `ensureProjectCollection()`，默认 private，再执行 scanner/builder；不是在用户说出路径后自动公开资料。来源：[`CollectionIndexBuilder`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/CollectionIndexBuilder.ts#L23-L125)、[`外部项目接线`](D:/AI/clower-1/clowder-ai/packages/api/src/index.ts#L874-L889)。

## 3. 轨迹一：同一句“重试”，为什么有时只得到项目资料？

### 3.1 先展开输入，不直接跳到最终结果

MCP 输入：

```json
{"query":"重试","scope":"docs","limit":5}
```

MCP handler 实际先做：

```ts
const { dimension = 'project' } = input;
const params = new URLSearchParams({ q: input.query });
// 中间设置其他参数
params.set('dimension', dimension);
```

因此进入 HTTP 的有效参数包含：

```text
q=重试
scope=docs
limit=5
dimension=project
```

而 resolver 自己的默认值是：

```ts
const limit = options?.limit ?? 10;
const dimension = options?.dimension ?? 'all';
```

两个 optional 参数并不意味着两个入口默认相同。我们实际执行 resolver 得到：

| 入口与选项 | 实际搜索对象 | 结果简称 |
|---|---|---|
| MCP 不传 dimension，handler 补 project | 主项目 store | P、L |
| 直接 resolver，不传 dimension | 旧项目 store + 全局 store | P、G、L |
| resolver 的 all，scope=threads | 主项目 store | T |

第三行来自 legacy 对 threads/sessions 的项目范围收缩。MCP 与 HTTP 的源码接线是静态核验，表中 resolver 输出经过夹具执行；本轮没有发真实 HTTP 请求。来源：[`MCP 默认`](D:/AI/clower-1/clowder-ai/packages/mcp-server/src/tools/evidence-tools.ts#L100-L138)、[`Resolver 默认与 legacy`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/KnowledgeResolver.ts#L39-L55)、[`legacy 目标选择`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/KnowledgeResolver.ts#L125-L187)。

### 3.2 现在明确要跨库：究竟选中了哪些 manifest？

改为 `dimension=library`。这次才进入 Catalog 的 N 库路由：

```ts
const manifests = this.catalog!.getRoutable(dimension, options?.collections);
```

Catalog 的关键过滤是：

```ts
private isRoutable(m: CollectionManifest): boolean {
  return m.status !== 'archived';
}

// library 分支
return active.filter((m) => m.sensitivity === 'public' || m.sensitivity === 'internal');
```

把三份 manifest 代进去：

```text
案例库为 public：
  [项目/internal, 方法/internal, 案例/public]
      → 三个都保留

案例库为 private：
  [项目/internal, 方法/internal, 案例/private]
      → [项目, 方法]
```

注意变量名 active 不代表只允许 `status=active`。真正共同排除的只有 archived；registered、stale、blocked 是否还有可搜内容，要继续看 store 与索引状态。来源：[`getRoutable`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/LibraryCatalog.ts#L107-L138)。

五个 dimension 放在这份数据上，区别就清楚了：

| dimension | 在本夹具里查谁 | 容易误解的点 |
|---|---|---|
| project | 项目 | 不是遍历所有 kind=project 的库 |
| global | 方法 | 可选的单个全局 store |
| all | 项目 + 方法 | 旧模式，带弃用警告，不自动加案例库 |
| library | 项目 + 方法 + public 案例 | private 案例被排除 |
| collection | 按显式 ID 名单解析 | 可选中 private，但不因此解锁正文 |

`scope=docs` 是**库内证据类别**；它与 dimension 是两个轴。Catalog 虽然也有按 kind 选 project/global 的辅助分支，KnowledgeResolver 的这些维度实际走 legacy，不可把两处同名概念机械等同。

### 3.3 显式名单怎样去重？

假设案例库是 private，进入 resolver 的名单如下。这里展示的是数组；MCP/HTTP 的 collections 是逗号分隔字符串，路由先 split、trim、去空项，再交给 resolver：

```text
collections = [
  project:cat-cafe,
  global:methods,
  research:payments,
  research:payments,
  research:missing
]
```

`getRoutable('collection')` 先 Set 去重输入 ID，再 get/解析别名，过滤不存在或 archived 的 manifest，最后按解析后的 m.id 再去重。

最终 eligible manifests 仍只有三个。第二次去重用于处理“旧别名和新名指向同一本资料夹”，不是文档内容去重。若没有提供 collections，结果是空，不会自动退回 library。

现在只是知道**将对谁发起查询**。还不能说读到了任何正文，更不能把用户自己写的 ID 当身份证明。

## 4. 轨迹一继续：从每库命中，到脱敏后的融合结果

### 4.1 扇出不是“先查完项目，再开始查全局”

真实代码摘录：

```ts
const settled = await Promise.allSettled(
  manifests.map(async (m) => {
    const store = this.stores.get(m.id);
    if (!store) return { manifest: m, items: [] as EvidenceItem[], noStore: true };
    const start = Date.now();
    const execution = await searchStoreWithMeta(store, query, { ...options, limit });
    return {
      manifest: m,
      items: execution.items,
      meta: execution.meta,
      durationMs: Date.now() - start,
      noStore: false,
    };
  }),
);
```

本例 limit=5 是发给**每一个 store**的上限，不是先给项目五个名额、剩下的再分给其他库。

当三库完成后，中间状态是：

```text
manifest 顺序：项目 → 方法 → 案例
per-store hits： [P,L]   [G]    [X,Y]
执行状态：       ok     ok      ok
```

Promise 完成先后不改变 allSettled 结果与输入位置的对应关系。接下来仍按这组顺序构造 groups。来源：[`N 库扇出与分组`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/KnowledgeResolver.ts#L57-L105)。

### 4.2 private 是删掉整个命中，还是改变返回形状？

先看 X 原本含有哪些字段：

```json
{
  "anchor":"research:payments:doc/retry",
  "kind":"research",
  "status":"active",
  "title":"支付重试案例",
  "summary":"同一订单只能生效一次",
  "sourcePath":"retry.md",
  "updatedAt":"2026-09-06T11:00:00.000Z",
  "drillDown":{"tool":"cat_cafe_read_file_slice"}
}
```

这里 drillDown 只展示 tool 字段；夹具中的完整值还含 params/hint。

public/internal 会保留原 item。private/restricted 则执行以下字段白名单：

```ts
return items.map((item) => ({
  anchor: item.anchor,
  kind: item.kind,
  status: item.status,
  title: `[redacted — ${collectionSensitivity} collection]`,
  updatedAt: item.updatedAt,
}));
```

实际得到：

```json
{
  "anchor":"research:payments:doc/retry",
  "kind":"research",
  "status":"active",
  "title":"[redacted — private collection]",
  "updatedAt":"2026-09-06T11:00:00.000Z"
}
```

**不是把 summary 清空后保留其余对象，而是重新构造只含五个字段的对象。** sourcePath、passages、drillDown 都不能搭便车留下。anchor 却仍是真实值，所以这不是完全隐藏元数据。

而且它发生在融合之前：`groups.items` 已经脱敏，随后 RRF 接收到的是这个版本。分组返回前另经 `redactGroupsForPersistence()`。来源：[`privacy-redactor`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/privacy-redactor.ts#L4-L17)、[`先脱敏后融合`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/KnowledgeResolver.ts#L83-L122)。

### 4.3 把 RRF 的 Map 一步一步填出来

核心循环没有比较 BM25 的原始数值：

```ts
const scoreMap = new Map<string, { item: EvidenceItem; score: number }>();
for (const group of groups) {
  for (let i = 0; i < group.items.length; i++) {
    const item = group.items[i]!;
    const score = 1 / (RRF_K + i);
    const existing = scoreMap.get(item.anchor);
    if (existing) {
      existing.score += score;
    } else {
      scoreMap.set(item.anchor, { item, score });
    }
  }
}
```

常量 RRF_K=60，i 从 0 开始。因此第一名是 1/60，不是 1/61。

| 处理到哪里 | Map 新增或更新 |
|---|---|
| 项目第一名 P | P → 1/60 |
| 项目第二名 L | L → 1/61 |
| 方法第一名 G | G → 1/60 |
| 案例第一名 X | X → 1/60 |
| 案例第二名 Y | Y → 1/61 |

Map 插入顺序此时是 `[P,L,G,X,Y]`。按 score 降序排序，等分保留本次插入先后，夹具结果变为：

```text
第一档：P、G、X，都是 1/60
第二档：L、Y，都是 1/61
limit=5 → [P,G,X,L,Y]
limit=3 → [P,G,X]
```

它解决的是“各库排名如何协调”，不是“哪篇材料一定正确”。临时 score 也没有作为新字段塞回 EvidenceItem。来源：[`rrfFusionN`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/KnowledgeResolver.ts#L285-L303)。

### 4.4 为什么要反复强调 anchor，而不是标题？

RRF 的 key 就是 `item.anchor`，**没有再套一层 collectionId**。

```text
P：doc:retry
X：research:payments:doc/retry
→ 两个 key，不能因为都讲 retry 就合并。
```

反过来，若一个新 adapter 错误地把 X 也命名成 `doc:retry`，它会给 P 累加分数，两库第一名相加变成 `1/60 + 1/60 = 1/30`，后来的 item 字段却不会替换第一份。标准外部 scanner 的前缀约定，是防这种错误的重要条件。

legacy 双库融合也是 anchor-only，并且先插项目，所以同 anchor 时项目字段胜出；两边都用相同的 `1/(60+i)`，没有额外乘一个“项目加权系数”。Map 解决身份去重，不自动解决语义近重复。来源：[`legacy RRF`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/KnowledgeResolver.ts#L249-L282)。

### 4.5 三个最终结果并排看，才能看懂 private 的意义

本轮实际验证：

| 请求 | eligible manifests | 最终结果 |
|---|---|---|
| library，案例 public | 项目、方法、案例 | P、G、X、L、Y |
| library，案例 private | 项目、方法 | P、G、L |
| collection 显式列三库，案例 private | 项目、方法、案例 | P、G、脱敏 X、L、脱敏 Y |

第三行中 X 仍会占用排名名额。这里不是“有权限才放进榜单”的统一认证系统，而是“明确选库后，按输出通道做脱敏”。

Resolver 返回 results、sources、query、meta、collectionGroups。sources 仍只表达 project/global；案例库需要看 collectionGroups，而不能因为 sources 没写 research 就认定没搜它。这里展示的是 Resolver 层顺序；HTTP 若开启 retrievalRerank 后处理，还可能继续改变排名。HTTP 层会把分组 items 改成 itemCount，并把 summary 映射为 snippet。其 confidence 根据最终名次生成，也不是刚才的 RRF 累计分。来源：[`Resolver 返回`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/KnowledgeResolver.ts#L107-L122)、[`HTTP 映射`](D:/AI/clower-1/clowder-ai/packages/api/src/routes/evidence.ts#L250-L285)、[`HTTP 分组`](D:/AI/clower-1/clowder-ai/packages/api/src/routes/evidence.ts#L332-L349)。

### 4.6 如果方法库失败，哪些状态仍然保留？

向模拟全局 store 注入异常后：

```text
groups：
  project:cat-cafe  status=ok     items=[P,L]
  global:methods   status=error  items=[]
  research:payments status=ok    items=[X,Y]

meta：{ degraded:true, degradeReason:"evidence_store_error" }
results：[P,X,L,Y]
```

另一个实验只移除案例库的 store 对象，保留 manifest：

```text
案例组 status=skipped，items=[]
其他搜索均健康时 meta.degraded 仍为 false
```

所以“没有结果”至少要区分：正常零命中、没有 store、执行异常。group 的状态不能被总 degraded 一个布尔值代替。

`allSettled` 避免一个 reject 抹掉其他完成结果，却没有逐库超时；如果某库一直不 settle，整体仍在等。legacy 又不对称：全局错误能降级，项目错误可向外抛。不要把某一分支的容错扩大到整个系统。

## 5. 轨迹二：已经拿到 P，怎样沿五条边找到原始讨论？

现在问题变成：“P 的根据是什么？”继续搜一遍关键词不如沿已有关系走。先给 `GraphQueryResolver` 精确 anchor：

```json
{"query":"doc:retry","depth":2}
```

它逐 store 调 `getByAnchor()`，本例只有项目库命中，且可见，因此返回 status=graph、queryKind=exact，并把 `resolvedCollectionId=project:cat-cafe` 交给图构建过程。多个可见精确命中会返回 candidates，不能擅自选一个；精确命中全不可见时返回 no_match，不再用模糊搜索泄露近似信息。来源：[`GraphQueryResolver.resolve`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/GraphQueryResolver.ts#L218-L263)。

### 5.1 先认识四个容器，各自防什么重复

```ts
const nodesMap = new Map<string, GraphNode>();
const edgeKeySet = new Set<string>();
const visited = new Set<string>();
let frontier = [anchor];
```

| 容器 | 装什么 | 在本例里的作用 |
|---|---|---|
| frontier | 这一层待处理 anchor 的数组 | 初始只有 P，随后变成 L/G/X |
| visited | 已处理的真实、归一化 anchor | L 回指 P 时不再次展开 P |
| nodesMap | canonical anchor → 输出节点 | 同一对象不产生多个节点对象 |
| edgeKeySet | 两端 anchor 加 relation | 同一条关系从反面读到时不重复绘制 |

frontier 不是 Set。同一节点可能被多条路径排入下一层，真正处理时再用 visited 跳过。别把“待处理”与“已经访问”当成同一种状态。

源码的层循环是：

```ts
for (let d = 0; d <= depth && frontier.length > 0; d++) {
  const nextFrontier: string[] = [];
  for (const currentAnchor of frontier) {
    if (visited.has(currentAnchor)) continue;
    visited.add(currentAnchor);
    // 解析 collection、归一 anchor、构造节点等步骤省略
  }
  frontier = nextFrontier;
}
```

这是分层 BFS 风格遍历，而不是递归让模型自由找链接。来源：[`容器与主循环`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/GraphResolver.ts#L116-L170)。

### 5.2 depth=2 时，每一层究竟发生了什么？

下面的内部状态按源码顺序展开；最终六节点、五边的结果已执行断言核对。

| 时刻 | frontier | 处理后的 visited | 新保留的边 | nextFrontier |
|---|---|---|---|---|
| d=0 前 | [P] | {} | 无 | [] |
| 处理 P | [P] | {P} | P—L、P—G、P—X | [L,G,X] |
| d=1，处理 L | [L,G,X] | {P,L} | L—T；反向 L—P 不重复加 | [T] |
| 再处理 G | 同上 | {P,L,G} | G—P 已有 | [T] |
| 再处理 X | 同上 | {P,L,G,X} | X—Y；X—P 已有 | [T,Y] |
| d=2 | [T,Y] | {P,L,G,X,T,Y} | 达到深度，不再扩边 | [] |

实际输出节点顺序为 `[P,L,G,X,T,Y]`，边就是夹具中的五条。

**为什么 G 所在 store 没存 P—G，仍然能从 G 找回 P？** GraphResolver 不是只查节点自己的 store：

```ts
for (const [, s] of this.stores) {
  // lookupAnchor 校验等步骤省略
  const related = await s.getRelated(lookupAnchor);
  // 遍历 related
}
```

因此能在项目 store 找到那条引用。身份解析先试 `${collectionId}:` 前缀，老式项目 anchor、全局技能 anchor 不一定符合这种完整前缀，还会通过逐 store 的 `getByAnchor()` 找归属。来源：[`归属解析`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/GraphResolver.ts#L72-L108)、[`跨库邻接查询`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/GraphResolver.ts#L234-L307)。

### 5.3 反向边和关系过滤：为什么 P 不会被无限绕回来？

边的实际 key：

```ts
const edgeKey = `${canonicalAnchor}→${relCanonicalAnchor}:${rel.relation}`;
const reverseKey = `${relCanonicalAnchor}→${canonicalAnchor}:${rel.relation}`;
if (!edgeKeySet.has(edgeKey) && !edgeKeySet.has(reverseKey)) {
  edgeKeySet.add(edgeKey);
  // 加入输出边
}
```

P→L:doc_link 与 L→P:doc_link 被视作同一条输出关系；若 relation 不同，则不是同一个 key。与此同时，visited 阻止重新处理已访问节点。一个控制边重复，一个控制节点展开，不能只用其中一个替代另一个。

把邻居排入下一层的实际代码是：

```ts
if (!visited.has(relCanonicalAnchor)) {
  nextFrontier.push(relCanonicalAnchor);
}
```

它只检查是否已访问，没有检查下一层数组是否已经排过队；所以 frontier 允许暂时重复，visited 在处理入口才兜住重复展开。

再请求 `relations=['doc_link']`，过滤发生在扩展下一层之前：

```ts
if (relationFilter && !relationFilter.has(rel.relation)) continue;
```

本轮结果只有 `[P,L]` 和一条边。P—G、P—X 根本不进入后续 frontier，L—T 同样被排除，不是先访问完六个节点再把不喜欢的线隐藏。来源：[`过滤与边 key`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/GraphResolver.ts#L242-L300)。

### 5.4 把案例库改成 private，再走相同的 P

默认没有 callerCollections。输出变为：

```text
nodes = [P, L, G, [redacted:1], T, [redacted:2]]
                    原 X                  原 Y
```

private 节点隐藏 collectionId/title/kind，anchor 换成不透明占位；边有独立敏感级别，未显式设置时取两端更严格者。本夹具中的 P—X、X—Y 被标记 redacted。对私有边，代码还要求 callerCollections 同时包含两端的 collection；只让 X 的节点可见，不自动让 P—X 的边可见。

但被遮盖的 X 仍可能展开到 Y，不能把 redacted 理解成“整个私有分支从未被遍历”。检索脱敏保留真实 anchor，图脱敏用占位；二者也不是同一输出规则。来源：[`节点和边脱敏`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/GraphResolver.ts#L195-L295)。

HTTP 图接口限制 localhost，depth 为 0—3，并明确不给客户端提供自填 callerCollections 的授权入口。类支持由可信调用方传入列表，不代表 HTTP 已实现按登录用户派生的 collection 权限。来源：[`图路由边界`](D:/AI/clower-1/clowder-ai/packages/api/src/routes/library.ts#L486-L548)。

### 5.5 图有上限，就能保证最多访问 50 个节点吗？

不能把常量当证明。代码设置每个展开节点的边数阈值 15、总节点阈值 50，但 50 的检查发生在扩边循环，不是每次插入节点之前的全局硬截断。已经排进 frontier 的节点，尤其最后一层，仍可能被加入结果。

`truncated` 是“发生了限制”的提示，不是严格访问量凭证。我们的小图没有触发阈值；没有执行大图压力测试，也没有把这次六节点验证夸成所有极端情况都已覆盖。

### 6.3 为什么返回了旧的 X，却没有更新的 L？

```ts
for (const [collId, items] of byCollection) {
  guaranteed.push(items[0]);
  selected.add(`${collId}\0${items[0].anchor}`);
}
```

本例可见库数=3，limit=3：

```text
先给项目一条 → P
先给方法一条 → G
先给案例一条 → X
剩余名额      → 0
最终按时间排序 → [P,G,X]
```

### 8.3 s2 为什么一个成功、一个失败，却没有任何文件正文？

```ts

## 9. 现在真的要读 X：逻辑 URI 怎样避免读到项目里的同名文件？

这不是一个互联网地址。store 通过 sourceRoot/sourceRef 生成它，意思是“案例库根目录下的 retry.md”，而不是“当前进程工作目录下的 retry.md”。

```

## 11. 轨迹六：同一次纠偏来两遍，Event Memory 怎样认出它？

现在回到 T 所代表的讨论：用户在 t42 的 m101 纠正了重复扣款处理。搜索文档只能找到“幂等”知识，Event Memory 要保存的是**这次发生过的事及其归属**。

### 11.1 先把事件写成明确的数据，不凭空补一个“顿悟”

夹具记录：

```json
{
  "type":"demo-brake",
  "trigger":"human_brake",
  "cat":"codex",
  "threadId":"t42",
  "messageId":"m101",
  "timestamp":100,
  "summary":"可能需要纠偏",
  "cognitiveTransition":null,
  "relatedHarness":null,
  "confidence":"mid"
}
```

demo-brake 是模拟命中词，不声称真实 detector 识别这个口令。100/200 是用于对比更新行为的测试数值，不是真实事件发生时间。

这十个业务字段之外，Store 再生成 eventId，并保存必填 ownerUserId。cognitiveTransition/relatedHarness 可为 null，但键不能省略；不确定就明确表示未知，而不是编造原因。[业务类型与 guard](D:/AI/clower-1/clowder-ai/packages/shared/src/types/event-memory.ts#L56-L101)、[字段验证](D:/AI/clower-1/clowder-ai/packages/shared/src/types/event-memory.ts#L137-L156)。

### 11.2 去重键里为什么既有 owner，也有 type？

建索引的真实 SQL：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_event_owner_coord_type
  ON event_memory(ownerUserId, threadId, messageId, type);
```

插入采用 INSERT OR IGNORE。把四元组写出来：

```text
Alice 的事件 → (alice, t42, m101, demo-brake)
Bob 的事件   → (bob,   t42, m101, demo-brake)
```

两者不是同一条事件。若 Alice 的同一条消息有不同 type，也不应全部压成一个。

本轮状态变化如下。E1/E2 是为了方便跟踪随机主键而使用的简称：

| 操作 | inserted | 事件身份 | Store 行数 |
|---|---:|---|---:|
| Alice 第一次写 mid | true | 新 E1 | 1 |
| Alice 完全相同地再写 | false | 仍 E1 | 1 |
| Alice 同坐标同 type，改成 high | false | 仍 E1，更新部分字段 | 1 |
| Bob 写相同坐标和 type | true | 新 E2 | 2 |
| owner 为空字符串 | 抛错 | 不创建“默认 owner”事件 | 2 |

unique 约束控制存储身份，返回的 inserted 告诉调用方这次是否新插入。来源：[`迁移与唯一键`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/EventMemoryStore.ts#L100-L144)、[`markEvent`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/EventMemoryStore.ts#L152-L222)。

### 11.3 为什么重复写还允许更新，而不是永远忽略？

历史回填可能先得到 mid，真实 live 事件后来明确为 high。源码只允许更高置信度升级：

```sql
UPDATE event_memory
   SET confidence = ?, trigger_type = ?, cat = ?, summary = ?, cognitiveTransition = ?, relatedHarness = ?
 WHERE ownerUserId = ? AND threadId = ? AND messageId = ? AND type = ?
   AND (CASE ? WHEN 'high' THEN 3 WHEN 'mid' THEN 2 ELSE 1 END)
     > (CASE confidence WHEN 'high' THEN 3 WHEN 'mid' THEN 2 ELSE 1 END)
```

把输入值代进去：

```text
旧 confidence=mid → 2
新 confidence=high → 3
3 > 2 成立 → 更新这些 SET 字段
```

不是大于等于。所以等置信度重试、较低置信度记录，不覆盖旧字段。

本轮 high 输入还把 timestamp 从 100 改成 200，但读取结果仍是 100：SQL 的 SET 没有 timestamp。eventId、坐标、type 也没换。准确承诺是“同身份事件可提升置信度与指定元数据”，不是“新记录整行替换”。

### 11.4 哪个真实写入者会构造 high？

`messages.ts` 的检测包装先要求真实 messageId 和 owner；从消息取有限摘要，再调用注入回调。`index.ts` 的实际 live writer 构造：

```ts
const record: EventMemoryRecord = {
  type: hit.word,
  trigger: 'human_brake',
  cat: catId ?? 'unknown',
  threadId,
  messageId,
  timestamp: Date.now(),
  summary: messageExcerpt ?? hit.word,
  cognitiveTransition: 'user_brake',
  relatedHarness: null,
  confidence: 'high',
};
```

这里 high 是该写入路径明确赋值，不是又调用模型评估了一次。trigger 的类型虽然支持五类信号，也不能据此宣布五套自动检测器全都上线。

更重要的调用顺序是：

```text
markEvent(record, ownerUserId)
  → 取得真实 eventId
  → appendMagicWordRefToEpisode({eventId,...})
```

完整事件是事实源，episode ref 是引用。对既有 E1 再走 live 回调，本轮记录到的 ref 仍指向 E1，没有凭重试创造第二条事实。来源：[`消息检测入口`](D:/AI/clower-1/clowder-ai/packages/api/src/routes/messages.ts#L207-L237)、[`真正的 live writer`](D:/AI/clower-1/clowder-ai/packages/api/src/index.ts#L1746-L1803)。

### 11.5 主事件写失败后：有死信，不代表已经自动恢复

本轮故意给真实 live 回调一个**未初始化的内存 EventMemoryStore**，让 markEvent 抛错。没有破坏实际数据库。

观察到的阶段结果：

```text
markEvent → 抛“EventMemoryStore not initialized”
eventId   → 没有取得
内存 dead-letter → 1 条，保留 alice 和完整 record
episode ref      → 0 条
错误日志         → 记录失败
回调             → 不把异常抛出阻断消息处理
```

原因是 catch 分支先 appendDeadLetter，然后 continue，根本不执行后面的 ref 写入。如果 ref 自己失败，事件已保存，不回滚主事件。

磁盘 Store 的死信位置是 `<dbPath>.outbox.jsonl`，每行含 record、ownerUserId、error、failedAt；`:memory:` 分支只进内存数组。本轮验证的是后者和失败分流，不是磁盘满、权限异常或断电恢复。

Store 只提供 append/listDeadLetter；核验的 live 接线中没有自动 drain/退避重放循环。死信写入本身还可能失败，代码会再记 error。因此正确说法是“留下可恢复材料”，而不是“已自动保证最终投递”。来源：[`失败后不写孤儿引用`](D:/AI/clower-1/clowder-ai/packages/api/src/index.ts#L1773-L1800)、[`死信实现`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/EventMemoryStore.ts#L289-L307)。

### 11.6 Alice 查询时为什么不会拿到 Bob 那一行？

按源码展开 owner=alice、threadId=t42 两个过滤条件时，动态 SQL 的有效形态为：

```sql
SELECT * FROM event_memory
WHERE ownerUserId = ? AND threadId = ?
ORDER BY timestamp DESC, rowid DESC
LIMIT ? OFFSET ?
```

参数是 `['alice','t42',limit,offset]`。本轮实际验证 owner 过滤只取到 Alice 的 E1；Carol 在同一坐标查询则为空。

```ts

```

客户端不能靠传别人的 owner 扩大该 HTTP 列表结果。但 Store 自身的 owner filter 是可选的，getEvent 甚至只按 eventId；可信内部调用者仍需负责范围。teleport 先查 owner 对应坐标是否有事件，广播却仍用 workspace:global，不能宣称实时推送已按租户彻底隔离。来源：[`Store 查询`](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/EventMemoryStore.ts#L225-L277)、[`路由强制 owner`](D:/AI/clower-1/clowder-ai/packages/api/src/routes/events.ts#L101-L125)、[`teleport 边界`](D:/AI/clower-1/clowder-ai/packages/api/src/routes/events.ts#L141-L166)。

## 13. 复杂度：六张卡的小例子，放大以后贵在哪里？

设 N 为选中的 store 数，k 为每库候选上限，U 为不同 anchor 数，V/E 为实际遍历到的节点/邻接关系数。

| 阶段 | 主要成本 | 不能从上限直接推出的结论 |
|---|---|---|
| Catalog 选择 | 遍历 manifest；别名最多十步 | 登记在目录不代表存在健康索引 |
| 联邦融合 | O(Nk) 聚合，O(U log U) 排序，O(Nk) 候选内存 | limit=5 不代表只向底层取五张卡 |
| 等待各库 | allSettled 等全部结束 | 某库 reject 可容错，不等于慢库可跳过 |
| Graph | BFS 外还有逐库查身份与邻接 | 简写 O(V+E) 会隐藏跨库探测成本 |
| Recent | 各库 SQL 加候选分组排序，池可达 Nk | LIMIT k 不证明数据库只检查 k 行 |
| Coverage | 两次初始查询，另随 keywords/thread refs 增加查询 | 最终最多 50 条，不限制所有前置工作 |
| Perspective | 按步骤累计耗时，open 逐项执行 | 有多个 step 不代表并行计划执行 |
| Event | 唯一索引检查、条件更新、过滤排序和分页 | 所有组合查询不都能宣称 O(log M) |

本例 Graph 的 P/L/G/X 四个节点要扩邻接，每个都扫三库；即便只有五条真实边，也有十二次邻接接口调用的结构性成本，另有归属查询。候选阶段却只读自己的 store，成本与信息完整性又不同。

N 库错误分组还用 `settled.indexOf(entry)` 找原位置，大量失败时有额外 O(N²) 查找成本。Event 默认 limit 未给时是 SQLite 的 -1，表示无界；OFFSET 分页也不能假装成主键游标。文件切片走流，耗时还取决于目标窗口前面的文本。

以上是源码推导，不是压测结果。若要改进，可考虑有界并发/超时、明确复合身份键、图身份缓存、真正的死信消费器；它们是改进方向，不能倒写成现有保证。

## 14. 面试追问：用刚才的状态回答，而不是再报一遍类名

### 问一：为什么默认搜索没有 X？是不是案例库坏了？

不一定。MCP 不传 dimension 时补 project，连案例 manifest 都没进入查询；直接 resolver 默认 all 也只查旧项目加全局。只有 library 且案例 public/internal，或显式 collection，才会进入案例 store。先查有效参数和 eligible manifests，再检查 group 是否 error/skipped，不要把选库错误当成召回率问题。

### 问二：你们 RRF 为什么能避免不同库的分数尺度不一致？

因为它用名次：本例每库第一名都贡献 1/60，而不是拿项目 BM25 的 8 分去和向量相似度 0.9 比。代价是这个分数只表达排名支持，不能代表权威、权限或正确性。相同 anchor 才会合并，若 adapter 没做好命名空间，RRF 也会把不同对象误当成一个。

### 问三：用了 visited，还为什么要 edgeKeySet？

visited 阻止已经处理的 P 再次展开；edgeKeySet 阻止 L 读到的 L—P 重复进入结果。两个集合控制不同对象，而且边 key 包含 relation。只有 visited 不能保证输出边不重；只有边去重也不能保证节点不重复处理。

### 问四：为什么 Recent 宁可返回旧 X，也不返回新 L？

因为这次 limit=3 且有三个可见库，先每库保底一张，结果 P/G/X。它优先让你看到多个来源，而不是只让最活跃的项目占满页面。若要严格看项目最新材料，应选合适的阅读入口，不能假定跨库 Recent 就是全局时间 top-k。

### 问五：Coverage 返回 gaps=[]，能不能说已经查全？

不能。这个数组当前是直接初始化为空，没有做完整性证明。我们只查项目 store 的 docs/threads，沿 P 的关键词找到 L，T 的重复命中被去重；G/X/Y 没因为 dimension=library 自动加入。还要看 convention graph unavailable 的降级，报告哪些来源没接、哪些正文没读。

### 问六：Perspective 已有 openedCount=1，还要读文件吗？

要。本例 P 的成功状态是 route_identified，content 只是 read_file_slice 的调用提示；G 失败，X 甚至未尝试，第二个 open 因 previousCandidates 已清空而没有候选。把计数说成全文阅读数量，会直接误报研究进度。

### 问七：300 字 capsule 超限，为什么不直接截断？

源码选择区分“没有画像”和“画像违反预算”：前者兼容返回空，后者明确抛错，避免静默丢掉用户偏好。计数是去空白后的 Unicode code point，primer 只给指针，不占这份正文预算。本轮验证了 300 成功、301 抛错，但没跑整个提示词注入系统。

### 问八：幂等事件为什么第二次还能改数据？

幂等首先约束身份和行数，不必意味着任何字段永远冻结。本例同 owner/线程/消息/type 仍是 E1，但 mid 可升级到 high；只改 SQL 指定的字段，timestamp 仍是 100。Bob 是另一个 owner，所以另建 E2。不能只说“我们有唯一键”，还要说明唯一键范围和冲突更新条件。

### 问九：有死信文件为什么还不能保证最终不丢？

首先死信写入也可能失败；其次留下一条 JSONL 不等于有人消费它。本轮真实 callback 的故障分支确实保存内存死信并停止写 ref，却没有自动重放循环。可靠恢复还需要消费、幂等重写、成功确认与清理机制，且不能把单条事件幂等扩展成所有下游副作用恰好一次。
