## 我们先把现场摆出来


## 1. 为什么“还没达到90%”也可能触发换班？

先看 shouldTakeAction 的输入：fillRatio、窗口大小、已用tokens、压缩次数和策略对象。

它先算：

```ts
const remaining = windowTokens - usedTokens;
if (remaining < turnBudget + safetyMargin) {
  // 按 compress/hybrid/handoff 分支决定动作
}
```

默认turnBudget=12000，safetyMargin=4000。演算窗口100000、已用85000：只剩15000，小于16000。即使action阈值是0.9，也可能先按预算不足处理。

这在保护“下一轮能否做完”，不是单纯在当前token比例上画一条红线。下一轮还会有工具结果和输出，等到100%再处理会太晚。

依据：[shouldTakeAction](D:/AI/clower-1/clowder-ai/packages/api/src/config/session-strategy.ts#L231)。

### 1.1 三种策略的动作并不相同

- handoff：到达条件后封存，换新session。
- compress：允许底层CLI压缩释放空间，不提前当作必须封存。
- hybrid：压缩次数尚未用完时允许压缩，次数耗尽后封存。

同样的剩余空间，策略不同，输出动作不同。默认阈值按provider区分，运行配置还可覆盖；不能把某只猫的0.85当全系统唯一规则。

## 3. 内存buffer与live文件是怎样同时增长的？

appendEvent先构造：

```ts
{
  eventNo: buf.length,
  timestamp: Date.now(),
  invocationId,
  event
}
```

先push到buffer，再排队追加events.live.jsonl。同一session的磁盘写入使用Promise链，避免同一个文件的这些追加互相打乱。

可以画成：

```text
buffer：[e0,e1,e2]
live：  [e0,e1]       ← e2 可能尚在队列里
```

这不是异常，异步磁盘复制本来可能落后。正常执行以buffer为主；live文件用于进程重启后恢复。追加失败会被捕获，所以它不是每个事件都等待fsync确认的零丢失日志。

依据：[append与磁盘队列](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/TranscriptWriter.ts#L130)。

## 4. 重启以后，flush如何把两份记录合起来？

假设重启前的事件before只在live文件，重启后的after同时在buffer和live：

```text
live   = [before, after]
buffer = [after]
```

flush先等当前排队写入结束，再读live。随后建立buffer指纹集合：

```ts
const bufKeys = new Set(
  buf.map((e) => `${e.timestamp}:${JSON.stringify(e.event)}`),
);
const diskOnly = liveEvents.filter(
  (e) => !bufKeys.has(`${e.timestamp}:${JSON.stringify(e.event)}`),
);
buf = [...diskOnly, ...buf];
```

执行中间值：

```text
bufKeys = {after的时间与内容指纹}
diskOnly = [before]
合并 = [before,after]
```

然后重新编号eventNo为0、1。重启后的buffer可能从0开始，不能直接把两份eventNo当全局唯一业务键相加。

本轮运行原始合并片段，实际得到两条记录，并保留I-old/I-new的invocationId。若两条事件时间和payload完全相同、但invocationId不同，当前指纹没有包含invocationId，会在这段比较中被当成重复；测试也展示了这一点。它是局部去重规则的边界，不是对真实日志已经发生丢失的断言。

依据：[flush合并](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/TranscriptWriter.ts#L255)。

## 5. 正式JSONL与偏移索引怎样生成？

flush会把合并后的事件包装为：

```text
v、t、threadId、catId、sessionId、cliSessionId、invocationId、eventNo、event
```

每隔默认100个事件记一个byteOffset。偏移增量使用：

```ts
Buffer.byteLength(line, 'utf-8') + 1
```

不是line.length。中文字符的UTF-8字节数与JavaScript字符串长度不同，用错单位会使后续按字节定位落进字符中间。

最后写events.jsonl、index.json；有封存时间时生成digest.extractive.json。全部正式写入之后再清理相应运行状态。这里是若干文件操作，不是一个文件系统多文件事务，不能把目录中看到一个文件当作全部阶段完成。

依据：[事件与index写入](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/TranscriptWriter.ts#L293)。

## 6. Reader真的按offset跳到第5000条了吗？

当前readEvents读取index，但打开流的代码仍是：

```ts
createReadStream(jsonlPath, 'utf-8')
```

循环从文件头逐行计数，跳过cursor之前的行，再收集limit条。没有把offsets用于createReadStream的start字节位置。

所以：

```text
逻辑上返回第5000条开始的一页：有
读取时直接seek到对应字节：当前这段代码没有
```

读index可获得eventCount，用于total/hasMore。没有index时total回退到当前扫描计数，不应未经验证把它解释成完整准确的全文件条数。

readInvocationEvents同样从头流式扫描，按invocationId筛选。流式是内存友好，不代表读取复杂度与位置无关。

这就是必须看消费者的原因：写出了稀疏索引，不等于它已在当前reader中实现随机访问优化。

依据：[readEvents](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/TranscriptReader.ts#L74)、[readInvocationEvents](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/TranscriptReader.ts#L253)。

## 7. requestSeal与finalize为什么分成两个阶段？

requestSeal主要检查状态并提出active→sealing；finalize负责慢整理：flush、digest、ThreadMemory、可选handoff，然后尝试sealed。

```text
S2 active
 → 请求封存
S2 sealing
 → 慢速整理
S2 sealed
```

区别是：生命周期转换要尽快推进，磁盘、模型和摘要不能全挤在一个小动作里。

但不能只看注释里的CAS。requestSeal先get后update；当前Redis update中有多次读写，不是这两个方法就能单独证明跨进程原子CAS。外层有没有互斥需要进一步追调度调用方。

依据：[SessionSealer](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/SessionSealer.ts#L113)、[Redis update](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/stores/redis/RedisSessionChainStore.ts#L219)。

## 8. 超时以后，“工作停止”和“停止等待”是同一回事吗？

finalize给doFinalize包装30秒超时。异常或超时后仍尝试终态转换，因为永久卡在sealing会影响后续工作。

这里要区分：withTimeout通过定时器让等待失败，不是传给doFinalize一个能中止所有底层操作的AbortSignal。原promise可能继续执行。

所以一种可能的时序是：

```text
t0：开始整理
t30：等待超时，记录失败并尝试sealed
t35：未被取消的底层操作才完成某个写入
```

这是根据Promise取消语义和源码控制流推导的边界，不是本轮真实封存实验。不能把“超时返回”讲成“之后绝不会再产生副作用”。

同理，sealed表示会话生命周期已推进，并不证明每份摘要都完整。新session可能暂时拿不到交接材料，需要回退。

依据：[finalize超时处理](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/SessionSealer.ts#L164)、[withTimeout](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/SessionSealer.ts#L517)。

## 10. 决策、问题和工件的规则抽取：同一句话可以落进两个集合

SessionSealer先把事件转成聊天文字，并从最新ThreadSummary取得conclusions/openQuestions，交给extractDecisionSignals。

它按中文标点/换行拆句，限制长度，用“决定、采用、使用”等模式抓决策，用“需要、待定、是否”等抓问题；正则另找ADR和Feature标识。已有summary结论优先放前面，再做子串包含去重和容量限制。

实际输入：

```text
是否使用 Redis 还需要确认。
决定采用稳定幂等键。
参考 ADR-020 和 F102。
```

summaryConclusions还提供`采用稳定幂等键`。原函数输出：

```text
decisions：采用稳定幂等键；是否使用 Redis 还需要确认
openQuestions：是否使用 Redis 还需要确认
artifacts：ADR-020；F102
```

为什么“是否使用”也在decisions里？因为两组正则独立，“使用”命中一组，“是否/需要”命中另一组。它不是互斥的语义分类器。

为什么更长的“决定采用稳定幂等键”没保留？因为summary里较早加入的短版本已与它存在包含关系，被去重了。优先级来自输入顺序，不是模型再次确认哪个版本更准确。

依据：[signals输入](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/SessionSealer.ts#L484)、[extractDecisionSignals](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/extractDecisionSignals.ts#L1)。

## 11. ThreadMemory怎样压成一份滚动交接便条？

第一步把新digest格式化成一行。文件操作优先级是create > edit > delete > read；同文件多个操作只选择最高优先级所属分组，每组显示有限数量。

因此本例文件ops=[read,edit]，显示在Modified分组，而不是同时列成Read与Modified。会话显示编号来自digest.seq+1，不是sessionsIncorporated。

第二步，把新行放到最前：

```text
新session摘要
OLD_RECENT
OLD_OLDEST
```

第三步，超过预算则从尾部逐行pop；只剩一行还太长，再用比例截断。这个算法保留近期材料，不是无限追加。

依据：[formatSessionLine与buildThreadMemory](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/buildThreadMemory.ts#L21)。

### 11.1 一次实际结构验证

```text
Session #2 (TIME, 1min): Modified: src/api.ts.

```

给它恰好容纳前两行的预算57，结果删掉OLD_OLDEST、保留新行和OLD_RECENT。sessionsIncorporated从7变8，但显示仍是Session #2，因为seq=1。

这里57不是实际模型token预算，也不能用于证明真实tokenizer一定同样裁剪；测试隔离的是“先放新行，再从旧端裁”的算法行为。

### 11.2 文件操作分组，逐句读 reduce 才能看出取舍

源码不是简单把每个工具名打印一遍，而是对同文件的ops选一个最高优先级：

```ts
const bestOp = file.ops.reduce((a, b) =>
  (OP_PRIORITY[a] ?? 99) <= (OP_PRIORITY[b] ?? 99) ? a : b,
);
```

优先级数字越小越重要：create=0、edit=1、delete=2、read=3。假设：

```text
a.ts：[read, edit]
b.ts：[read, create]
c.ts：[]
```

执行过程：a先拿read=3与edit=1比较，保留edit；b保留create；c在进入reduce前因空数组跳过。因此输出分组是Created包含b、Modified包含a，而不是四条工具操作。

再按固定OP_ORDER渲染，各组最多列10个文件，其余用more提示。这里牺牲完整工具顺序，换取短交接便条；如果要知道“先读后改还是先改后读”，必须回到Transcript。

未知操作在比较时使用99。它不会自动被理解成已知操作，也不会因为在groups里出现就必然被固定OP_ORDER渲染。对支持新的工具操作，应同时检查提取、归类、展示三个位置。

这就是为什么规则摘要不是原始日志的替代：它的压缩规则是明确、可读，但确实有信息损失的。

## 13. 保存便条的预算，和本次带进模型的预算不同

Sealer给ThreadMemory的构建预算是：

```text
max(1200, min(3000, floor(maxPromptTokens × 0.03)))
```

后面的bootstrap总预算却是2000。两者分别控制“存多大一份便条”和“这次交接包能装多少”。存下3000token的便条不保证下一次能把它完整带进2000token的包。

如果面试官问“不是保存了为什么模型没看到”，除了索引和检索，也要检查这层预算裁剪。依据：[构建预算](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/session/SessionSealer.ts#L399)。

## 14. S3 启动时，bootstrap先查谁的历史？

`buildSessionBootstrap(catId,threadId)`读取这只猫在这个thread的chain，选择sealed或sealing记录。没有则返回null；有则取最近旧session。

## 15. Bootstrap到底装了什么？哪些字段没在这条路径消费？

## 16. 预算不够时，交接包怎样一步步丢内容？

固定部分身份/工具优先保留；主动note先受预算限制并预留变长内容空间。剩下四块按优先级逐块去掉：recall→task→digest→ThreadMemory。

以下数字是假定estimateTokens已经给出的值，用于演算：

```text
总预算2000，固定部分450，剩余1550
ThreadMemory=1000，digest=500，task=200，recall=250
变量合计1950
```

步骤：

1. 1950>1550，删recall，剩1700；
2. 1700>1550，删task，剩1500；
3. 1500≤1550，保留ThreadMemory和digest。

如果ThreadMemory自身1700，即使其他变量都删掉仍超过1550，则这段ThreadMemory也被整体移除。当前这段不是动态摘取最重要几句话填满剩余空间。

token-counter使用gpt-4o编码器作为估算；与provider实际tokens、图片等开销并非完全同一度量。第6篇pending估计还使用字符/4，不能把这些数全部当精确账单。

本轮还提取原始预算丢弃片段，用字符计数桩复验了上述两种状态：普通例子保留1000长的ThreadMemory与500长的digest，oversize例子最终移除ThreadMemory。验证的是分支与丢弃顺序，仍然不是真实模型token预算。

## 17. 最后一跳：哪行代码让这些记忆真正影响模型？

## 18. 冷加入的猫走哪条补充路径？

ContextTransport保留近期消息，对被省略部分留下tombstone：时间、参与者、关键词、如何回查。它还用thread标题、当前用户消息和近期消息片段组成query，尝试有时限的hybrid recall。

它解决的是“这只猫现在该拿多少背景”，不等于另建一个数据库。不要把bootstrap、冷加入packet、当前历史窗口、底层CLI会话复用混成一个开关。

这也解释了为什么某只猫能在同thread接上工作，不一定是读了A的整个CLI session；它可能拿到共享消息、滚动记忆与检索入口。

依据：[cold recall](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/agents/routing/context-transport.ts#L429)。

## 19. 本篇的成本与故障边界

- flush要读取live、合并并序列化事件，成本随会话事件量增长；不是常数时间封存。
- 当前reader深页仍扫描前缀，流式减少内存，不消除I/O。
- 规则抽取是字符串和集合操作，但可能产生语义误判或重复归类。
- ThreadMemory预算限制文本长度，结构合并仍依赖输入质量和外部更新串行化。
- timeout只结束等待，不等于取消副作用。
- bootstrap返回成功不表示每一类资料都被保留；预算可以整段舍弃。

实际验证与静态推演要分开：本轮运行事件合并片段、signals原函数、带明确token/time桩的ThreadMemory主体；没有启动真正session/CLI或磁盘封存。报告中07开头的检查能复现这些中间值。

## 20. 面试追问的完整回答

**为什么剩余空间比比例更重要？** 下一轮还需要输出和工具结果空间，remaining<turnBudget+safetyMargin可以提前触发策略。

**为什么buffer和live不直接互相覆盖？** 一份可能保留重启前事件，另一份可能保留尚未落盘的新事件，需要合并而不是丢弃任意一侧。

**eventNo能作为跨重启永久ID吗？** 当前flush合并会重新编号，不应当作稳定业务主键。

**写出了offset为什么仍读得慢？** 当前reader没有使用offset seek，仍从头扫描；写结构和消费结构要分别检查。

**ThreadMemory为什么出现未确认问题？** 抽取是独立正则，使用/是否同句可同时命中决定和问题，不是互斥语义分类。

**已经存下记忆，为什么新session看不到？** 可能走不到这个bootstrap、字段未消费、资料未完成，或预算把整段丢掉；必须追到最终prompt。

**封存是跨进程CAS、超时就不再写吗？** 不能如此承诺，当前状态更新与Promise超时都需要按实际边界解释。
