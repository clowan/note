## 本篇先回答一个尖锐问题：什么叫“记忆有用”？

搜索返回5条，不能说明模型真的读了；模型读了，也不能说明读对了；读对资料，还不保证最终答案正确。

因此要分别观察：

```text
资料保存 → 索引命中 → Agent读取 → 答案/任务成功
```

F200这条链主要观察搜索之后的行为，不是自动给事实真值打分。我们拿一只猫cat-a、thread T42、invocation I1，追它从search_evidence到Read的全过程，最后亲手算consumedMRR。

## 1. 先准备最小事件轨迹

```text
t0：search_evidence("retry")，返回DOC-A、DOC-B
t1：Read("/work/docs/a.md")
```

最小期望是：如果这两件事属于同一只猫、同一次执行，且Read真的指向候选A，我们应该记录“A被消费过”。

注意这个“应该”仍然需要用代码定义。时间间隔多长算相关？别的猫读取算吗？只做了路径搜索算吗？失败的Read算吗？下面逐一看当前实现，而不是用自然语言猜。

## 2. 第一段数据变形：MCP输出如何变成评估可用字段？

搜索工具返回的不只是自然语言说明，还保留稳定的anchor/sourcePath/type行。例如：

```text
Found 3 result(s)
[high] A
  anchor: DOC-A
  type: lesson
[mid] B
  anchor: DOC-B
  type: lesson
  sourcePath: docs/b.md
```

这里故意让报告命中3条，却只提供2个可解析的anchor，用于观察边界。

`deriveResultSummary('search_evidence', content)`先将字符串或text数组变成统一文本，再通过`deriveSearchEvidence()`提取：

```text
resultCount=3
_f200Candidates=[DOC-A(rank0),DOC-B(rank1)]
```

本轮实际运行原函数得到的候选数是2，并没有为了凑resultCount凭空补第三个对象。

所以resultCount和candidates.length是两项观测：前者是工具报告的数量，后者是解析器成功恢复的可归因候选。把它们合并会掩盖协议解析丢失。

依据：[deriveResultSummary](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/tool-usage/derive-result-summary.ts#L19)。

## 3. 为什么sourcePath必须在本结果块里找？

解析器先收集每个anchor行的位置，再从当前anchor截到下一个anchor，分别查type/sourcePath。

如果用一个全局正则一路向下找，A没有sourcePath时，可能把B的路径误配给A。当前分块策略正是在防这种串位。

本轮输入如上一节，结果：

```text
DOC-A：没有sourcePath
DOC-B：sourcePath=docs/b.md
```

A没有路径，不等于可以借B的路径。这个小小的文本配对决定后面“读了哪个文档”的指标是否可信。

还有一个细节：rank从解析顺序生成，第一条下标0。这不是重新计算BM25，只是记录结果中位置。

依据：[block-scoped候选提取](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/tool-usage/derive-result-summary.ts#L66)。

## 4. 从工具结果到RecallEvent，中间还隔着哪些组件？

实际链路：

```text
MCP ToolResult
 → provider产生tool_result事件
 → deriveResultSummary补充结果字段
 → ToolEventLog记录/更新
 → 路由完成后读当前thread工具日志
 → 按catId和invocationId调用triggerRecallCorrelation
 → RecallEventCorrelator
 → recall_events与聚合指标
```

因此独立调用一次`evidenceStore.search()`，并不等于自动产生完整的“搜索→读取”评估记录。需要有工具执行和日志路径。

串行/并行路由都有对应hook；结束后关联是fire-and-forget，失败捕获，不阻塞主要回复。这选择了主任务可用性，但评估数据也因此不是强制同步成功的业务账。

依据：[路由收尾hook](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/agents/routing/route-serial.ts#L3654)、[triggerRecallCorrelation](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/recall-correlation-hook.ts#L10)。

## 5. Hook先丢掉哪些不适合关联的事件？

首先筛选当前invocation与cat。没有search_evidence、graph_resolve、list_recent，就没有本次召回可关联。

若memory事件显示有private hits，当前hook跳过该次关联。它是一项隐私边界，不能据此声称所有敏感query、路径和文本都被完备脱敏。

通过后，会补齐RawEvent字段、调用correlateWindow、加threadId和shadow信息、持久化，再刷新anchor统计、global CTR baseline及trajectory等。

这一顺序说明：后续重排读取的是由工具行为聚合的统计，不是模型直接在向量上做一次在线训练。

## 6. RawEvent与RecallEvent各保存什么？

RawEvent是一条工具观察：

```text
invocationId / sessionId / threadId / catId
toolName / timestamp / turnIndex / status / summary
```

RecallEvent则以一次记忆工具调用为中心，关联：query、mode、scope、candidates、consumed、reformulated、fellBackToGrep、abandoned、结果集归因信息等。

每个candidate还需要targetRef：doc、thread、session、invocation或passage。它回答的不是“这条资料显示叫什么”，而是“以后什么工具参数算读了它”。

例如：

```text
文档目标：sourcePath=docs/a.md
线程目标：threadId=T42
会话目标：sessionId=S2
调用目标：sessionId=S2 + invocationId=I42
```

没有正确targetRef，后续再精确的工具日志也无法正确归因。

依据：[RawEvent](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallEventCorrelator.ts#L28)、[targetRef推断](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallEventCorrelator.ts#L188)。

## 7. 关联窗口：先检查猫，再检查invocation

buildWindow向后扫描：

```ts
if (e.catId !== source.catId) continue;
if (e.invocationId !== source.invocationId) break;
sameCatCount++;
```

别的猫的事件跳过，不计入同猫工具距离；同一只猫已经换到下一次invocation，则停止。

本轮原始correlator验证：其他猫读取同一文件，不计入cat-a的消费；下一次invocation读取，也不归到当前这次搜索。

这保证的是该函数定义的关联范围，不是说跨会话绝不可能复用知识。跨会话复用存在，但不能随意算到这一条搜索事件上。

## 8. “20步、5分钟”的布尔关系必须逐字读

后面的条件：

```ts
const withinDistance = sameCatCount <= 20;
const withinWallClock = e.timestamp - source.timestamp <= 300000;
if (!withinDistance && !withinWallClock) break;
```

只有两项都超出才停止。所以：

| Read位置 | 距离是否合格 | 时间是否合格 | 当前函数是否可纳入 |
|---|---|---|---|
| 第21步，2分钟后 | 否 | 是 | 是 |
| 第3步，6分钟后 | 是 | 否 | 是 |
| 第21步，6分钟后 | 否 | 否 | 否 |

这三种情况都已调用原始correlator验证。不是“20步并且5分钟内”才有效。

从效果看，这样能容忍快速密集工具或少量但很慢的工具；代价是窗口比两个硬上限的交集更宽。是否合适要用实际任务评估，不必把它简单认定成bug，也不能说时间与步数都被严格独立封顶。

依据：[buildWindow](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallEventCorrelator.ts#L221)。

## 9. targetMatch怎么把一次Read配到A？

对Read，主要检查doc sourcePath或anchor是否出现在file_path中。对session reader检查sessionId；对invocation detail检查invocationId；get_thread_context要求thread类型目标且threadId相等。

例如：

```text
候选：doc, sourcePath=docs/a.md
读取：file_path=/work/docs/a.md
→ 匹配
```

这不是根据模型回答“我读过A”来判断，而是根据工具输入匹配，因而可以复核。

但它也不是严格文件身份验证。原函数对`/work/docs/a.md.bak`也可能因substring匹配而返回true。本轮已验证这个例子。

因此指标“消费了A”的可靠性依赖targetMatch规则，不能把字符串包含判断说成经过canonical path/inode证明。

依据：[targetMatch](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/recall-target-match.ts#L5)。

## 10. 失败的Read会不会被这层计为消费？

findConsumed主要检查允许的工具名和targetMatch，在这个层次没有额外要求wEvent.status必须成功。

我们向原始correlator提供一条路径匹配、但status='error'的Read事件，仍然得到consumed记录。

这不表示真实线上所有失败Read一定被统计：上游可能过滤或改变这类事件字段。它精确说明的是，**只把这样一条RawEvent交给当前correlator，它不会因error状态自动拒绝。**

因此消费指标是行为代理，不是“成功读到内容”的完美传感器。改进时可考虑成功状态与实际返回内容的约束，但要同步所有provider事件契约，不能只在一处猜状态。

## 11. 一个工具调用能消费多个候选吗？

findConsumed维护matched集合，避免同一anchor被重复统计。常规Read/Grep/graph等在匹配一个候选后会break；command_execution例外，因为一条shell命令可能读取多个文件。

实际fixture：

```text
候选：DOC-A→docs/a.md，DOC-B→docs/b.md
命令：cat /work/docs/a.md /work/docs/b.md
```

原始correlator记录两条consumed，分别保留其rank、method、consumingEventId和distance。

shell路径不是随便提取所有字符串。parseShellReadPaths识别特定只读命令与包装、分隔符，并对写操作等作限制。它不是完整shell解释器，不支持的合法读法仍可能漏判。

依据：[findConsumed](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallEventCorrelator.ts#L237)、[shell只读解析](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/parse-shell-read-paths.ts#L1)。

## 12. 一个真实的协议断点：thread anchor不自动变成thread target

这次我们把生产者和消费者接起来测试，而不手工提供正确targetRef。

MCP样式文本：

```text
Found 1 result(s)
[high] Thread
  anchor: thread-T42
  type: discussion
  sourcePath: threads/T42
```

先调用原始deriveResultSummary，再交给原始correlator，后续事件是get_thread_context(threadId=T42)。

得到：

```text
candidate.targetRef.kind = doc
sourcePath = threads/T42
consumed = []
```

为什么？这段search文本解析器主要抽anchor、rank、type、sourcePath，没有给candidate补threadId。inferTargetRef不会只因anchor以thread-开头就自动推断thread类型，最后回退doc；而get_thread_context匹配分支要求ref.kind是thread。

这是特定生产者/消费者组合的受控测试，不宣称所有记忆工具都如此。其他producer如果提供显式threadId，可以走不同分支。但它说明：**类型存在、工具也存在，不代表坐标在中间转换中没有丢失。**

该场景很适合面试中的“如何排查归因漏报”：先追字段在每一跳是否仍然存在，不要只调指标公式。

依据：[候选文本提取](D:/AI/clower-1/clowder-ai/packages/api/src/domains/cats/services/tool-usage/derive-result-summary.ts#L91)、[inferTargetRef](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallEventCorrelator.ts#L202)、[thread匹配](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/recall-target-match.ts#L44)。

## 13. 搜了两次才Read，功劳该算给谁？

轨迹：

```text
search(q1) → 返回A、B
search(q2) → 返回A、C
Read(A)
```

两个搜索都包含A。若直接给两次搜索都算一个完全清晰的正例，就会掩盖归因歧义。

correlator先预处理result-set bundle：连续记忆搜索、之间没有消费事件时共用一个bundle，并统计候选在该bundle出现几次。

本轮原始correlator结果：两次search拥有相同resultSetId，A均出现消费，但attributionClarity为ambiguous。

这里没有强行决定“A一定是第二次搜索带来的”。保留歧义比编造确定性更诚实，后续评估可以区分clean与ambiguous子集。

依据：[bundle构建](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallEventCorrelator.ts#L54)。

## 14. graph_resolve为什么同时关闭和新建bundle？

graph_resolve有双重身份：它可以消费之前找到的anchor，也可以产生新的记忆候选。

因此代码不是简单else-if二选一，而是：

```text
先按消费行为关闭旧bundle
再按memory工具创建自己的bundle
若它本身也是消费型，再关闭自己的bundle
```

实际fixture：

```text
search → graph_resolve → search
```

原函数生成三个不同bundle。这样第三次search不会被误挂在graph自身的结果集上。

这类细节体现了为什么一个普通“滑动时间窗口”不够：工具具有不同业务角色，关联边界要理解这些角色。

## 15. consumed、reformulated、abandoned怎么一起产生？

主循环为每次记忆工具建立窗口、找消费、检查改词与退回grep等行为，再计算：

```ts
const abandoned = consumed.length === 0 && !reformulated;
```

所以“没有Read但改词再搜”和“没有Read也没再搜”不是同一种结果。

每条consumed还带原候选rank、method、距离和具体工具事件标识，方便回到原始日志复查。它比一个只有总次数的计数器更可审计。

但不要把所有字段都当真实测量：当前correlator构造RecallEvent时把tokenCost初始化为0。这条生产路径没有在这里估算真实工具输出tokens；后面的token指标不能只因字段存在就被当成实际花费。

依据：[RecallEvent构造](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallEventCorrelator.ts#L101)。

## 16. 现在真正算一次MRR：分母不能偷偷换掉

我们让三个独立recall分别出现：

1. 读了第1名；
2. 候选前两名是X/Y，实际读了第3名A；
3. 没有消费任何候选。

原始correlator生成记录，persistBatch写进内存SQLite，再由原始RecallMetricsComputer.computeMetrics计算：

```text
consumedAt3 = 2 / 3 ≈ 0.6667
consumedMRR = (1 + 1/3 + 0) / 3 ≈ 0.4444
searchAbandonRate = 1 / 3
```

这组值已经实际运行验证。分母是全部3次，不是只在2次成功消费里平均。如果只对成功样本平均，会把没用上任何资料的失败搜索从分母里消掉。

这里仍是消费MRR，而不是人工标注“正确相关文档”的标准相关性MRR：某次Read可能不准确、文件可能过期、答案可能误读。指标名字里有MRR不能让真值自动出现。

依据：[computeCore](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallMetricsComputer.ts#L236)。

## 17. Shadow与live比较，为什么必须对齐样本？

假设总共100次搜索，只有40次保存了shadow排序，又只有其中20次有消费。若拿这20次的shadow均值和全部100次的live均值相比，差异同时混入了样本选择因素。

源码为shadow存在且有消费的子集另算liveOnShadowSubsetMRR。比较时应使用同一批样本与相同分母，再分析排序变化。

同样，改了query、索引版本、模型、候选池和重排开关之后得到两个数，也不能直接把全部提升归功于MMR。需要固定其他变量，或者明确实验是多项组合改动。

依据：[同子集指标说明](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/RecallMetricsComputer.ts#L21)。

## 18. 这些统计怎样重新影响下一次搜索？

hook持久化后刷新anchor近期曝光/消费、全局按kind的CTR基线，以及trajectory、已消费目标的edge traversal等。

第5篇的消费重排读取这些统计，再计算收缩先验、时间因子和候选排序。于是闭环是：

```text
检索候选 → 实际工具动作 → 可复核日志 → 统计 → 后续检索规则
```

不是每次都训练一个新的神经网络，也不是热门文档自然获得事实权威。曝光更高会更容易被读，这本身就可能形成反馈偏差；冷启动保护和constitutional规则也要结合真实评估，而不是把次数直接当真理。

## 19. 复杂度与数据量：窗口常量不等于整体成本固定

设N个工具事件、R次记忆查询、每次K个候选、有效窗口W。

- 每次召回都可能向后扫描窗口；最坏不能只按20个事件算，因为窗口是步数或时间条件的并集。
- findConsumed需要将读取事件与候选目标比较，粗略有R×W×K的匹配工作。
- shell读取的解析也有命令长度成本；多个候选可能重复检查同一命令。
- 路由hook先读thread工具日志，再筛本轮invocation，因此I/O也不完全只与本轮事件量相关。
- 聚合刷新访问近期历史，不能把统计计算看成永远O(1)的加一。

这些是应测的成本来源，不是本轮已证明的线上瓶颈。报告阶段耗时、事件量、候选量和匹配数量，才能解释扩容需要。

## 20. 将正确性保证分层列账

| 机制 | 它解决的事 | 它不自动保证 |
|---|---|---|
| 候选文本解析 | 从工具文本恢复坐标与名次 | 报告数量与成功解析数量一致 |
| 窗口 | 约束一次搜索与后续动作的范围 | 精确因果关系 |
| targetMatch | 用工具入参匹配候选 | 严格文件身份、读取成功、理解正确 |
| bundle | 标记重叠搜索的归因歧义 | 自动把功劳唯一分配给某次搜索 |
| persistBatch | 保存关联结果 | 源事件没有缺失、统计真值正确 |
| shadow指标 | 对照另一种排序 | 不同数据集可直接比较 |

第一篇的Dirty Set、摘要局部事务、Marker多文件写入也有各自边界，不能因为最后画出了闭环就宣称全系统强一致或零丢失。

## 22. 如果要在面试里给出“效果提升”，还缺哪些实验？

先建立固定小金标集，每条query写出正确的docAnchor/messageId和可接受替代证据。包含精确编号、同义、跨语言、旧决定、错thread转贴、无答案、私有资料等。

然后逐层比较：

1. 固定索引与query，比较lexical/semantic/hybrid；
2. 固定召回候选，比较重排off/shadow/on；
3. 看是否真正下钻正确资料；
4. 人工核查最终回答和任务完成情况；
5. 再记录p50/p95、token与模型调用量。

没有这个过程，最多说“实现了机制并做了局部正确性验证”，不能写“准确率提升30%”。检索相关性指标、消费指标和任务正确率应该分栏，防止一个代理指标替代全部目标。

## 23. 面试追问，用本篇轨迹回答

**为什么有sourcePath还要做parser测试？** 因为字段可能在文本配对或类型推断中错位、缺失，后续日志再完整也会归因错误。

**20步和5分钟是什么关系？** 当前同时超出才停止，三种边界例子已经由原函数验证。

**Read失败还能算消费吗？** 当前这一层仅看允许方法和目标匹配，没有独立成功状态过滤；受控error事件仍被匹配，线上影响还需看上游契约。

**为什么两次搜索都读到同一份资料还标ambiguous？** 同一bundle内候选重复，不能把后续Read唯一归给某一次搜索。

**graph_resolve为什么特殊？** 它既消费旧入口，又生产新入口，代码分别处理两种身份而非else-if。

**MRR分母为什么包含没读的搜索？** 否则失败样本被消失，指标会虚高；三次示例真实得到4/9。

**模型读过就等于记忆正确吗？** 不等于。保存、检索、读取、理解和任务结果必须逐层评估。

**目前真的证明了什么？** 原始算法在受控输入下的行为、一些局部SQL事务和失败分支；没有证明生产规模、完整多租户安全、所有provider日志一致性或线上提升。
