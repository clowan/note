## 本篇到底解决哪一个问题？

假设猫问：`F102 retry on cat`。数据库里有与 F102、重试和猫有关的资料。你需要能说清楚：程序先查什么？为何先找到 D，最后却可能让 B 排到前面？为什么某个词只出现在 keywords 里，FTS 搜不到、补召回却找到了？

我们不从 BM25 定义开始，而是把一组数据放在桌上，沿实际代码执行。主线是：

```text
工具入参 → HTTP 参数 → scope/limit 归一化
 → 整句 query 的精确 anchor 查询
 → 按严格程度生成并执行 FTS 查询
 → substring 补召回及覆盖度排序
 → entity mention 补召回
 → summary/raw 分流 → 后续模式和重排 → 返回材料
```

其中“FTS 得到的名次”只是中间结果，不能提前当成最终结果。源码：[工具入口](D:/AI/clower-1/clowder-ai/packages/mcp-server/src/tools/evidence-tools.ts#L100)、[Store 总入口](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L157)。

## 1. 准备四份能手工检查的资料

先放 A、B、C，稍后才加入 D：

| 代号/anchor | kind | title | summary | keywords |
|---|---|---|---|---|
| A / F102 | feature | F102 memory architecture | design evidence catalogue | retry |
| B / L-B | lesson | F102 retry protocol | on failure preserve idempotency | F102、retry |
| C / D-C | discussion | cat cooperation | short unrelated report | cat |
| D / P-D | plan | F102 retry cat adapter | on timeout use stable key | 空 |

默认假设均 active，未被 supersede，不在 archive。我们刻意保留英文，是为了能肉眼看见 token 与 substring 的差别；不是说明系统只支持英文。

先预测：B 有 F102、retry、on，但没有独立词 cat；D 四个词都有；A 的 retry 只在 keywords；C 的 cooperation 里包含子串 on，但它不是独立 token on。这几个差别会逐步影响结果。

本轮验证脚本创建 SQLite `:memory:`，运行生产 schema 和 FTS 同步触发器。它没有创建真实知识文件，也没有调用模型。可复跑文件：[memory-walkthrough-checks.mjs](D:/AI/clower-1/clowder-note/memory/verification/memory-walkthrough-checks.mjs)；输出：[results.json](D:/AI/clower-1/clowder-note/memory/verification/results.json)。

## 2. 第一次数据变形：工具对象变成查询参数

工具输入示意：

```json
{
  "query": "F102 retry on cat",
  "scope": "docs",
  "mode": "lexical",
  "depth": "summary",
  "limit": 5
}
```

handler 先给 dimension 补默认值 project，再组装 URLSearchParams。于是语义上得到：

```text
q=F102 retry on cat
scope=docs
mode=lexical
depth=summary
limit=5
dimension=project
```

为什么强调 dimension？因为它与 scope 不是同一层：dimension 选择哪几个知识库，scope 选择库中哪些资料类型。MCP 默认 project；若绕过 MCP 直接调用 KnowledgeResolver，默认可能是 all。不能把某个底层函数的默认值当作所有入口的默认行为。

另外，环境中的当前 thread 会作为 `currentThreadId` 提供跨 thread 提示。它不自动等价于传入 `threadId` 限制检索范围。如果调用者想“只搜 T42”，应追踪实际 threadId 参数是否传到 SQL。

依据：[MCP 参数构造](D:/AI/clower-1/clowder-ai/packages/mcp-server/src/tools/evidence-tools.ts#L116)、[API 有效 limit](D:/AI/clower-1/clowder-ai/packages/api/src/routes/evidence.ts#L164)。

### 2.1 同一个 limit 为什么出现 5 和 10？

API 默认 5，Store 独立调用默认 10。本例 API 已明确传 5，Store 不会再覆盖它。若 hybrid，词法候选池还会扩大：

```ts
const bm25Pool = options?.mode === 'hybrid'
  ? Math.min(Math.max(limit * 4, 20), 100)
  : limit;
```

本例 lexical 的池为 5；换 hybrid 后池为 20。20 是中间候选量，不是最终必须返回 20 条。这是将召回与最后展示分开。

## 3. 第二次数据变形：scope 被翻译成 SQL 条件

Store 内部计算 effectiveKind：threads→thread，sessions→session。对于 docs/memory，则不是 `kind='docs'`，而是排除 thread 与 session。还有默认排除 pack-knowledge，除非调用明确要求。

本例 docs 范围可理解成：

```sql
AND kind != 'session'
AND kind != 'thread'
AND kind != 'pack-knowledge'
```

如果加 `threadId='T42'`，代码会构造 threadAnchor=`thread-T42`，在相关路径追加 anchor 条件。参数组合不是都合理，例如同时限定只看 docs 又限定一个 thread anchor，可能自然得到空结果。

空结果首先应该检查“查询集合和过滤条件能否同时满足”，不要立刻调整 embedding 模型。

依据：[scope 归一化](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L167)。

## 4. 精确 anchor 查询用的是整句话，不是自动抽取 F102

实际起始 SQL：

```sql
SELECT * FROM evidence_docs WHERE anchor = ? COLLATE NOCASE
```

参数是 `trimmed`，也就是整个 `F102 retry on cat`。因此本例 exactRow 为空。程序不会在这一段先用正则把句中的 F102 拎出来再等值查。

如果 query 就是 `F102`，才会直接命中 A。后面的实体入口或 graph_resolve 是另外的对象识别路径，不能替精确 anchor 这一段“补脑”。

命中时：

```ts
results.push(rowToItem(exactRow));
seenAnchors.add(exactRow.anchor);
```

`results` 保存候选对象，`seenAnchors` 负责防止后续召回把同一 anchor 加第二次。集合去重只是“同一对象不重复”，不是“相似正文只保留一篇”，后者在别的算法中处理。

精确路径也追加 kind/status/thread 等条件，所以它不是能绕过资料范围的特权通道。

依据：[精确查询完整分支](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L195)。

## 5. Query builder：先分词，再决定放宽层级

函数的第一步：

```ts
const tokens = query.trim().split(/\s+/).filter(Boolean);
```

对本例得到：

```text
tokens = [F102, retry, on, cat]
```

注意，它按空白切，不是中文词法分析器。`回调重复消息` 在这一层是一个整体 token；`回调 重复 消息` 才是三个。

第二步把每个 token 包进 FTS 双引号短语，并转义内部双引号。这样用户输入的词尽量作为搜索文本处理，而不是意外被解释为 FTS 操作符。SQL 参数绑定与 FTS 语法转义各管一层，不能互相替代。

第三步：不超过三个 token 只生成严格查询；超过三个才构建后续放宽层。这里没有“只要空结果就必然改成 OR”的承诺。

依据：[fts-query-builder.ts](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/fts-query-builder.ts#L19)。

## 6. 强词、弱词怎样判定？中间层到底要求什么？

强词的判定是一组可读规则：某些 F/ADR/LL/KD 等编号形式、Phase 标识、包含 CJK 字符，或者长度至少四。它不是按照“真正有用”做语义打分。

因此本例：

| token | 原因 | 分类 |
|---|---|---|
| F102 | 编号模式 | 强 |
| retry | 长度≥4 | 强 |
| on | 短且不满足其他条件 | 弱 |
| cat | 三字符 | 弱 |

程序实际输出，已由原函数验证：

```text
第1层："F102" "retry" "on" "cat"
第2层："F102" AND "retry" AND ("on" OR "cat")
第3层："F102" OR "retry" OR "on" OR "cat"
```

第 2 层的含义是：两个强词都要有，弱词至少有一个。不是“强词都要有，弱词可全部没有”。括号前显式 AND 还避免了该处不合法的 FTS 拼接语法。

如果四个 token 全是强词，第二层没有“弱词组”可放宽，会省略；如果只有三个 token，即使你觉得它们很宽泛，也只生成第一层。这是源码分支，而不是搜索引擎自行决定的策略。

## 7. 把 A、B、C 放进 SQLite：每一层实际命中了谁？

暂时没有 D，真实查询结果如下：

| 层级 | A/F102 | B/L-B | C/D-C | 结果 |
|---|---|---|---|---|
| 全词 AND | 缺 retry/on/cat 的 FTS token | 缺 cat | 缺 F102/retry/on | 空 |
| 强词 AND + 弱词 OR | 不满足 retry | 满足 F102、retry、on | 不满足强词 | B |
| 全词 OR | 有 F102 | 有 F102/retry/on | 有 cat | B、C、A |

这是 `03-relaxation-before-D` 场景的内存 SQLite 输出。上表只讨论 FTS：A 的 keyword retry 不在这张 FTS 索引的列中，所以不能算它命中了 retry。

这里先解决“谁有资格被返回”，然后才考虑排序。若所有词都必须出现，大部分自然语言长句容易过窄；适度放宽用来恢复召回。代价是 OR 层可能包含只匹配一个普通词的材料。

## 8. 加入 D 后，为什么 FTS 不把 B 一起补回来？

现在加入 D，它同时有 F102、retry、on、cat。第一层命中 D。

真实循环的停止条件：

```ts
for (const ftsQuery of ftsQueries) {
  const rows = /* 执行这一级 SQL */;
  // 去重后加入 results
  if (rows.length > 0) break;
}
```

所以：

```text
第一层返回 [D]
→ rows.length=1 > 0
→ 停止
```

即使 limit=5，也不会为了补满五条继续执行第 2 层。也不是只有本层“新增的不重复候选”大于零才停止：代码判断的是原始 rows.length。

本轮验证同时单独执行了三个 query，确认：第一层只有 D，第二层有 D/B，第三层有四篇。但生产停止策略会选择第一层。**单独执行所有层是测试观察，不表示生产循环真的执行了后两层。**

这一步结束时，来自 FTS 的候选是 D；还不是最终完整词法结果，因为 substring 和 entity 尚未运行。

依据：[rows 非空即 break](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L317)。

## 9. BM25 在哪里？完整 ORDER BY 又是什么？

核心查询：

```sql
SELECT d.*, bm25(evidence_fts, 5.0, 1.0) AS rank
FROM evidence_fts f
JOIN evidence_docs d ON d.rowid = f.rowid
WHERE evidence_fts MATCH ?
```

FTS 索引 `title, summary` 两列，所以权重 5 和 1 分别对应标题和摘要。不是一个任意的“最终权威分”。rowid JOIN 则把索引命中还原成文档条目，取到 anchor、kind、来源和状态。

实际完整排序还包含前置条件：

```sql
ORDER BY
  (d.superseded_by IS NOT NULL),
  (d.source_path LIKE 'archive/%'),
  (CASE WHEN d.provenance_tier = 'authoritative' THEN 0
        WHEN d.provenance_tier IS NOT NULL THEN 1 ELSE 2 END),
  rank
LIMIT ?
```

它是多键的字典序排序，不是把四个值相加。先比是否 superseded，再比 archive 表达式，再比 provenance，最后才比较 rank。SQL 的 NULL 排序语义也不能凭日常“false/true”想当然处理；例如缺 source_path 与明确非 archive 的表达式值不完全一样。

因此“原始 BM25 更强就一定排前面”不成立。本轮简单四文档 query 用来观察匹配层级与 BM25，本段多键顺序由源码逐项核对，未把简化 fixture 说成完整路由回归测试。

实际 SQLite fixture 返回的 BM25 rank 有负数，排序使用升序。不要套另一个系统“越大越相关”的约定。

依据：[FTS SQL](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L248)、[完整 ORDER BY](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L311)。

## 10. 为什么 A 的 retry 还是可以被搜到？Substring 补召回

后续步骤把 query 小写、按空白拆词、去重，然后为每个词构造：

```sql
LOWER(title) LIKE ?
OR LOWER(COALESCE(summary, '')) LIKE ?
OR LOWER(COALESCE(keywords, '')) LIKE ?
```

参数是 `%word%`。同一个词可以从三个字段任意一个匹配；不同词组之间也是 OR。此路径才包含 keywords 字段。

A 的 keywords 是 `["retry"]`，因此能在此处进入候选。C 的 cooperation 包含 on，A 的 catalogue 包含 cat，也可能贡献 substring 匹配。

这就是词法补召回的两面：

- 可以补回 FTS token 边界下没命中的资料；
- 也可能引入“字面子串出现，但不是用户想要那个词”的噪声。

它没有凭空获得语义理解能力。前导 `%` 的 LIKE 也不能被描述为直接走 anchor 的精确查找。当前这段执行 `.all()`，SQL 本身没有 LIMIT；最后只展示 5 条不意味着只扫描和处理 5 条。

依据：[contains SQL](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L329)。

## 11. 补召回统计的是查询词覆盖，不是出现次数

对每一个 query word，程序检查：

```text
keywordHit：任意 keyword 包含 word？
titleHit：title 包含 word？
summaryHit：summary 包含 word？
```

然后各加一次。标题重复写十次 retry，`titleHits` 对 retry 仍只加一。

输出三项统计：

- keywordHits：有多少查询词在关键词集合里命中；
- titleHits：有多少查询词在标题中命中；
- textHits：有多少查询词在三个字段任一处命中。

比较顺序：keywordHits 优先，其次 titleHits，再其次 textHits。它不是 `3*关键词 + 2*标题 + 摘要` 这样的加权和。

依据：[compute 与 compare 函数](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/lexical-backfill.ts#L19)。

### 11.1 同一组四文档的真实中间结果

对 A/B/C/D 运行原始 `rankLexicalBackfillRows()`，得到：

| 条目 | keywordHits | titleHits | textHits |
|---|---:|---:|---:|
| A/F102 | 1 | 1 | 3 |
| B/L-B | 2 | 2 | 3 |
| C/D-C | 1 | 2 | 2 |
| D/P-D | 0 | 3 | 4 |

逐次比较：

1. B 的 keywordHits=2 最大，先于其他；
2. A/C 都是 1，比较 titleHits，C 的 2 大于 A 的 1；
3. D 虽然覆盖全部四词，但 keywordHits=0，排在最后。

结果：`B → C → A → D`。

所以 D 是严格 FTS 唯一命中，并不保证它在后续补召回覆盖度排序中仍第一。本例故意暴露这种阶段变化，让你在调试时会问“是哪一层把它排下去的”，而不是只看最后结果就归因 BM25。

这个顺序是原始补召回函数的实测，不是带所有 feature flags 的完整 API 最终名次。相关验证名称为 `03-four-doc-substring-ranking`。

## 12. 合并候选时，精确 anchor 与相似文档如何区分？

`seenAnchors` 只让同一条证据对象加入一次。先前 results=[D]，补召回来了 B/C/A/D，会加入前三个并跳过重复 D。之后比较器还可能调整整个 results 顺序。

对于 query 正好等于某个 anchor 的情况，补召回比较器接收 exactAnchor，会优先保留它。但如果 query 是完整句子，本例 exactRow 为空，没有这个保护。

补召回子集合自身同分时，还会考虑 superseded、archive、provenance、更新时间。注意：子集合的 tie-break 和总候选重新排序并不完全是同一个比较函数。不能把某处质量规则无条件推广成整个最终排序的保证。

依据：[contains 合并与重排](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L385)、[精确 anchor 保护](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/lexical-backfill.ts#L41)。

## 13. Entity 路径补的是什么？

如果 query 中出现一个注册过的猫名、Feature 或概念别名，EntityRegistry 可以提供额外线索。

归一化代码：

```ts
value.normalize('NFKC').trim().replace(/\s+/g, ' ').toLowerCase()
```

然后遍历别名，做匹配，按 entityId 去重。随后查询 mentions，把 entityId 还原到 docAnchor/passageId，再加入候选。

```text
输入中的名称 → 规范 entityId → 已记录的 mentions → 证据对象
```

这条路依赖已登记字典和 mention 索引，不是临时调用 LLM 做实体识别，也不是向量相似度的别名。别名不存在或匹配规则不覆盖，便不会凭空命中。

在调试某个 F102 查询时，应分别检查：整句 anchor 等值查询、FTS token、substring、entity registry。这四项都可能涉及 F102，但不是同一段代码。

依据：[别名归一化与 resolveQuery](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/EntityRegistry.ts#L64)、[entity 补召回接线](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L402)。

### 13.1 Entity 的边界匹配，为什么不同于 LIKE？

归一化之后，`compileAliasMatcher()` 又分两条路。别名含 CJK 字符时直接做字符串包含；其他别名先转义正则元字符，再要求左右边界不能继续接字母、数字、下划线、@ 或连字符。

核心形态：

```ts
if (hasCJK(aliasNorm)) return text => text.includes(aliasNorm);
// 非 CJK：转义别名，再检查前后不是身份/单词内部字符
const pattern = new RegExp(
  `(^|[^\\p{L}\\p{N}_@-])${escaped}(?=$|[^\\p{L}\\p{N}_@-])`,
  'u',
);
```

为什么要这层区别？第11节substring会让cat命中catalogue，但实体名称通常不应该这样扩散。原始函数的实际检查结果：

| 文本 | 别名 | Entity匹配 |
|---|---|---|
| cat cooperation | cat | true |
| catalogue | cat | false |
| F10 | F1 | false |
| 布偶猫 | 布偶 | true |

NFKC还会把全角`Ｆ１０`归一化成`f10`。因此“都叫关键词匹配”不表示每个模块使用同样边界。

别名里的正则符号会被转义，是为防止字典内容被当正则语法。它与SQL参数绑定、FTS短语转义分别属于三层文本协议。具体应用应检查自己的输入在哪一层被解释，不能做一次转义就认为所有下游都安全。

这个规则也有取舍：含CJK的混合别名走包含分支；其他别名把连字符/@当身份字符，可能拒绝某些你直觉希望算独立词的形式。应在别名字典测试中明确期望，而不是把匹配失败都归因模型。

依据：[compileAliasMatcher](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/EntityRegistry.ts#L585)。本轮场景`03-entity-boundaries-differ-from-substring`直接运行该源模块的导出函数。
## 14. 到哪里才决定 summary 还是 raw？

entity 之后，代码检查 depth：

```ts
if (options?.depth === 'raw') {
  const rawResult = await this.rawPassageSearch(...);
  return { items: this.enrichWithDrillDown(...), meta: rawResult.meta };
}
```

因此 raw 并不是所有 summary 处理结束后多附一段正文。它在后面的 authority/mode 主分支之前转入另一条路线。

Passage 词法检索使用 passage_fts 和 `created_at`，同样逐层放宽。scope 明确为 docs/sessions/memory 时，当前 raw 函数不会执行与 threads/all 相同的 message passage 搜索。

窗口读取还可按同一个 doc_anchor 的 position 范围查询相邻片段。position 由索引批次生成，不要未经验证就把它当成全历史永久稳定的消息序号。

## 15. 一个“检查通过但搜不到”的可复验反例

IndexBuilder.checkConsistency() 比较主表与外部内容 FTS 的 count。我们故意创建生产 SCHEMA_V1，但不安装同步触发器，然后插入一条正文含 alpha 的记录。

内存 SQLite 实际返回：

```text
evidence_docs 的 count = 1
evidence_fts 的 count  = 1
MATCH alpha 的 count  = 0
```

两个 count 相等，不代表倒排词项正确。这是因为外部内容 FTS 的普通内容查询与 MATCH 索引查询不能混为一种观察。

该损坏 fixture 演示检查的盲区，**不表示真实项目数据库已经发生同样损坏**。验证索引同步时还要做“新词能命中、改动后旧词消失、删除后不再命中”的行为检查。报告中可查 `02-10-count-equality-does-not-prove-fts-postings`。

依据：[checkConsistency](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L687)。

## 16. 复杂度：Top-5 为什么仍然可能很贵？

设查询词数 W、contains 命中行数 R、平均处理文本长度 L、别名字典大小 A。

- query 构造大体随输入长度增长；
- FTS 的成本依赖索引和候选分布，不由最终 limit 单独决定；
- contains 对多字段做子串条件，读取 R 行后还计算覆盖信号；
- 补召回统计至少要访问这些行与查询词，粗略可写为 O(R×W×L) 的字符串匹配工作；排序还有 O(R log R)；
- entity 分支有字典遍历和 mention 查询；
- hybrid 还会扩大候选池，后续另加向量与回表。

所以这里最值得测的是阶段耗时与各阶段候选量，而不是只记一个“整个搜索接口用了多少毫秒”。没有真实压测，不要声称以上某个分支已经是当前瓶颈；它们是从实现识别出的候选热点。

## 17. 故障时保留了什么？

FTS 某一级执行异常被捕获，循环可以尝试之后的 query；contains 异常会保留已有结果；其他层也有各自的回退。这提高可用性，也可能让“没有结果”与“某个搜索分支失效”在表面上相似。

因此排障顺序可以是：

```text
先确认原始内容存在
→ 确认是否被当前索引粒度收录
→ 确认 dimension/scope/thread 参数
→ 查看实际 query 列表和每层 rows
→ 检查 contains/entity 是否补回或改序
→ 最后再看向量与下游重排
```

这比一看到搜索差就改模型更可验证。

## 18. 本篇如何回答源码级追问？

**问：query 里有 F102，为什么没有直接精确命中？**  
答：精确分支对 trimmed 整句做等值查询，不负责从句中抽编号；实体、graph 或其他词法分支另外处理。

**问：放宽为什么只找到一条就停？**  
答：代码检查 rows.length>0，而不是 rows.length≥limit。策略优先使用较严格的非空层，不是自动填满 Top-K。

**问：关键词搜索就是 BM25 吗？**  
答：不是。精确 anchor、FTS 多键排序、substring 覆盖度、entity mention 共同构成词法候选，后续还可能重排。

**问：A 的 retry 在 keywords，为什么 FTS 没有命中它？**  
答：evidence_fts 只有 title 和 summary 两列，keywords 由其他过滤或补召回访问。

**问：为何覆盖全部词的 D 被排到 B 后？**  
答：补召回先比较 keywordHits，再比较标题和总覆盖，不是直接沿用 FTS 名次。本篇固定 fixture 已展示该中间变化。

**问：怎样验证全文索引真的同步了？**  
答：不能只比 count，要对已知词做 MATCH，检查增、改、删后的命中变化；当前已有故意缺触发器的内存反例。

**问：你真的运行了整个搜索 API 吗？**  
答：没有。本篇运行原始 query builder、补召回纯函数，以及生产 schema/触发器上的内存 SQLite 查询；未启动真实 API、Redis或向量模型。观察结论限定在这些范围。
