## 3. 第一站：authority 到底怎么把 D 从第四位移到第一位？

### 3.1 先解释这一行，而不是直接宣布“规范优先”

实际核心表达式：

```ts
score: (1 / (i + K)) * AUTHORITY_WEIGHTS[(item.authority as F163Authority) ?? 'observed']
```

拆开看：

- `i` 是当前数组的下标，从 0 开始，不是从 1 开始。
- `K=60`，所以第一条的基础值是 `1/60`，第二条是 `1/61`。
- 再乘 authority 对应的系数：constitutional 1.3、validated 1.2、candidate 1.1、observed 1.0。
- authority 缺失才用 observed；不是读取 BM25 的原始数值再乘权重。

对主场景逐篇计算：

| 输入位置 i | 文档 | 计算 | authority 分数 |
|---:|---|---|---:|
| 0 | A | 1.2/60 | 0.02000000 |
| 1 | B | 1.0/61 | 0.01639344 |
| 2 | C | 1.1/62 | 0.01774194 |
| 3 | D | 1.3/63 | 0.02063492 |
| 4 | E | 1.0/64 | 0.01562500 |
| 5 | F | 1.0/65 | 0.01538462 |

于是：

```text
之前：[A, B, C, D, E, F]
之后：[D, A, C, B, E, F]
```

**D 上升是因为 `1.3/63 > 1.2/60`，不是因为代码写了一条“constitutional 永远第一”。**

### 3.2 为什么分母要加 60？

如果直接用 `1/(i+1)`，第一条和第二条相差一倍，1.0～1.3 的权重很难让第二条反超。

加 60 后，相邻位置差距被压小，权威系数才有机会调整近邻顺序。这解释的是参数在公式中的作用，不是声称 60 已经被本章证明为最佳参数。

进入公式前还会检查：开关 off、结果少于两条、存在精确词法保护项，任何一个成立就直接返回。主场景 query 是单个非 CJK 词 `cache`，不启用那项词法保护；命名查询的情况留到第 10 节实际走一遍。

本次隔离验证确认：off、shadow 都保留 `[A,B,C,D,E,F]`，on 才写回 `[D,A,C,B,E,F]`。

## 4. 第二站先读统计：曝光和消费不是一回事

现在数组是：

```text
[D, A, C, B, E, F]
```

`enrichWithDrillDown` 会调用 `applyConsumptionRerank`。函数先按这些 anchor 批量读取统计，再读各 kind 的 baseline。它没有对每篇分别查询一次统计。

但这些数究竟表示什么？

统计刷新程序遍历 `recall_events`：

```text
某篇出现在一次搜索候选中 → 曝光加 1
该候选也在这次事件的 consumed 集合中 → 消费再加 1
```

因此 B 的 `n=30、c=20` 是 30 次曝光里有 20 次被记录为消费，不是“20 位用户确认它正确”。E 的最近 30 天消费为 0，也不能直接翻译成“内容是错的”。

真实 baseline 还有一个细节：它对同类各文档的 `c/n` 做等权平均，而不是先把全类的 c、n 分别相加再相除。比如两篇分别是 `1/1` 和 `0/100`，前者平均法得 0.5，后者总量法得 `1/101≈0.009901`。两种口径不能混用。

我们的统计桩已经直接提供 μ=0.2，接下来只研究排序函数怎么消费它。

## 5. 先只看 B：从 20/30 走到 prior=0.35，中间发生了什么？

### 5.1 第一步，不直接相信裸比例

B 的裸消费率：

```text
20/30 ≈ 0.666667
```

代码实际计算：

```ts
const shrunkCtr = (input.consumedCount30d + ALPHA_0)
  / (input.exposureCount30d + ALPHA_0 + BETA_0);
```

其中 `ALPHA_0=2`、`BETA_0=8`，所以：

```text
(20+2)/(30+2+8) = 22/40 = 0.55
```

可以把加 2、加 8 理解成：先放入“2 份成功、8 份未成功”的先验经验，再与观测合并。这对应 Beta(2,8) 收缩，先验中心是 `2/10=0.2`。

为什么需要它？看同一池里的 F：F 只有一次曝光，却刚好被消费了。裸比例是 100%，收缩后只有：

```text
(1+2)/(1+10) = 3/11 ≈ 0.272727
```

一次幸运的观测，不应自动战胜大量观测。这一步减少小样本比例的极端程度。

### 5.2 第二步，和“同类通常水平”比较

B 收缩后是 0.55，同类 baseline μ 是 0.2：

```text
0.55 - 0.2 = 0.35
```

这是**高于基线 0.35 个绝对比例单位**，不是“高出 35% 的相对比例”，也不是 `0.55/0.2`。

这里有两个不同的 0.2：

- 收缩中心来自固定常量 2 和 8；
- μ 来自同类统计，缺失时才默认 0.2。

本例恰好相等，不能误以为 Beta 先验会随 μ 自动改变。

### 5.3 第三步，历史消费越久，证据越弱

B 最后消费就在模拟当天，`d=0`。feature 的 T=90：

```text
消费时间系数 R = T/(T+d) = 90/(90+0) = 1
rawLift = (0.55-0.2)×1 = 0.35
```

这里用的是**最后消费时间**，还没有看文档 updatedAt。

### 5.4 第四步，通过分支门控才能把 rawLift 变成 prior

B 不在 14 天索引宽限期，不是规范豁免类型，曝光 30≥20，所以进入 full 分支：

```text
rawLift = 0.35
    ↓ full
prior = 0.35
```

这样 B 才拿到了后面能用于加分的 prior。前面算出了 rawLift，不代表一定原样使用。

## 6. 换看 C、D、E、F：为什么同一公式会走向不同结果？

### 6.1 C：算出了负值，但样本还不够惩罚

C 的 kind 是 plan，T=45；最近消费在 45 天前：

```text
shrunkCtr = (0+2)/(10+10) = 0.1
R = 45/(45+45) = 0.5
rawLift = (0.1-0.2)×0.5 = -0.05
```

它只有 10 次曝光，落在 `5≤n<20`：

```ts
prior: Math.max(0, rawLift)
```

`Math.max(0,-0.05)` 取两者较大值，所以 prior=0，branch=low-sample。

可以说“目前不使用这份负向信号”，不能说“C 已经被判定为高质量”。

### 6.2 F：100% 的裸比例，仍然不奖励

F 的 shrunkCtr 已算出 `3/11≈0.272727`；d=0，rawLift 约 0.072727。

但是 n=1<5，代码直接给 prior=0，branch=cold-start。**收缩之后还有曝光门槛，二者不是同一层保护。**

### 6.3 D：最先执行的其实是“入索引不足 14 天”

D 的 authority 是 constitutional，kind 是 lesson。直觉可能说：“那一定进入规范分支。”

先看函数最前面的实际代码：

```ts
if (input.firstIndexedAt > 0 && Date.now() - input.firstIndexedAt < GRACE_PERIOD_MS) {
  return { shrunkCtr: 0, meanCtrKind: 0, recencyFactor: 0, rawLift: 0, prior: 0, branch: 'cold-start' };
}
```

D 从 9 月 5 日入索引到模拟 9 月 12 日只有 7 天。因此直接返回，后面的规范判断根本没有执行。

这里诊断字段的 0 是提前返回的占位结果，**不能说 D 实际做了 `2/40` 计算后得到 0**。

### 6.4 E：样本足够，负向信号才真正进入排序

E 是 feature，n=50、c=0，最后消费在 90 天前：

```text
shrunkCtr = 2/60 = 1/30
R = 90/(90+90) = 1/2
rawLift = (1/30 - 1/5)×1/2 = -1/12 ≈ -0.08333333
```

E 进入 full 分支，所以 prior 就是这个负值。

六份资料汇总如下。注意 D 不是和 F 走了完全相同的执行过程，只是 branch 名字相同。

| 文档 | shrunkCtr | 消费时间系数 R | rawLift | branch | 最终 prior |
|---|---:|---:|---:|---|---:|
| A | 0.25 | 1 | 0.05 | full | 0.05 |
| B | 0.55 | 1 | 0.35 | full | 0.35 |
| C | 0.10 | 0.5 | -0.05 | low-sample | 0 |
| D | 0，提前返回 | 0，提前返回 | 0，提前返回 | cold-start | 0 |
| E | 0.03333333 | 0.5 | -0.08333333 | full | -0.08333333 |
| F | 0.27272727 | 1 | 0.07272727 | cold-start | 0 |

### 6.5 现在再总结分支顺序，才不容易背错

```text
入索引不足 14 天？是 → cold-start，直接返回 0
    否
authority=constitutional，或 kind=decision/lesson？是 → constitutional，负值钳为 0
    否
曝光 <5？ → cold-start，prior=0
曝光 <20？ → low-sample，负值钳为 0
其他 → full，允许正负 prior
```

恰好满 14 天不满足严格小于；`firstIndexedAt=0` 也不会获得时间宽限。正常 upsert 保留已有 anchor 的首次索引时间，不会因为普通覆盖写入自动重启 14 天。

validated+feature 不在规范豁免里；observed+decision 却在。名称、authority 与 activation 不能混为同一个开关。

## 7. 第三站：为什么已经算了消费时间，还要再算文档年龄？

B “今天被读过”和“今天更新过”是两件事。也完全可能存在一篇十年前写的文档，今天刚被读取。

源码因此有第二只时钟：

```ts
const ageDays = item.updatedAt
  ? (Date.now() - new Date(item.updatedAt).getTime()) / 86_400_000
  : 365;
```

这里把毫秒除以一天的毫秒数，得到**距 updatedAt 的天数**。不是距首次索引，也不是距最后消费。updatedAt 缺失时调用方使用 365 天。

`computeRecencyDecay` 再返回：

```ts
if (halfLife == null) return { factor: 1.0, halfLife: null };
return { factor: halfLife / (halfLife + ageDays), halfLife };
```

我们把这个文档年龄因子记作 V，避免和上一节的消费时间系数 R 混淆。

| 文档 | 文档年龄 age | T | V |
|---|---:|---:|---:|
| A | 90 | 90 | 90/180=0.5 |
| B | 0 | 90 | 90/90=1 |
| C | 45 | 45 | 45/90=0.5 |
| D | 7 | null | 1，不按年龄衰减 |
| E | 180 | 90 | 90/270=1/3 |
| F | 14 | 14 | 14/28=0.5 |

### 7.1 “半衰期”为什么不是指数函数？

当 age=T 时，`T/(T+age)=1/2`，因此 T 确实对应减半的年龄。

但 age=2T 时：

```text
当前分式：T/(T+2T)=1/3
指数衰减：2^(-2)=1/4
```

两者不同，不能只看到“半衰期”就擅自换成指数公式。

共享参数表还包括：adr/lesson/canon 为 null；feature/decision 为 90；plan/research/phase 为 45；discussion/reflection 为 21；thread/session 为 14；未知 kind 默认 45。

### 7.2 冷启动是不是就完全不改排名？

看 D：prior=0，但 V=1。看 F：prior=0，但 V=0.5。它们后面的年龄加分就不同。

因此只能说“冷启动禁用消费 prior”，不能说“冷启动禁用了整个重排”。另外，消费函数遇到“从未消费”时先返回 R=0.5，优先于 T=null；这也不等于文档年龄函数的 V=1。第 10 节会实际算到 D 的这种情况。

## 8. 把主场景的分数算完：B 怎样从第四位升到第一位？

此刻输入仍是 authority 输出：

```text
[D, A, C, B, E, F]
```

F200 **重新根据这个数组下标计位置分**，并不沿用前面的 authority 数值。

源码关键三项：

```ts
const positionalScore = 1 / (i + K);
const newScore = positionalScore + BETA * prior.prior + GAMMA * (decay.factor - 0.5);
```

`K=60、BETA=0.15、GAMMA=0.1`。可以把每篇的小账本写成：

```text
当前位置给的基础分
+ 消费先验贡献
+ 文档年龄贡献
```

### 8.1 为什么年龄项要减 0.5？

V=0.5 时，这一项为 0，是中性基准；V=1 时加 0.05；V 很小则减分。不是把整份文档分数乘一个衰减系数。

对 B，当前 i=3：

```text
位置：1/(3+60)           ≈ 0.01587302
消费：0.15×0.35           = 0.0525
年龄：0.1×(1-0.5)        = 0.05
总分                     ≈ 0.11837302
```

对 E，当前 i=4：

```text
位置：1/64               = 0.015625
消费：0.15×(-1/12)       = -0.0125
年龄：0.1×(1/3-1/2)      ≈ -0.01666667
总分                     ≈ -0.01354167
```

负分不是报错，也不是“负概率”；这只是用于彼此比较的排序量。

## 9. 第四站在路由：为什么 B 得分最高，HTTP 仍不把 B 放第一？

## 10. 轨迹二：明确点名 A，再让 D 跨过 14 天，会发生什么？

这一节仍用同六篇，但改变两个明确的测试条件：命名查询为 `缓存 失效`；召回边界提供的合成顺序为 `[E,C,D,B,A,F]`。仍按 summary/lexical 的排序调用顺序、limit=6 观察。**不测试这条 query 的真实 FTS 召回能力。**

### 10.1 为什么只有 A 被保护？

保护函数先把 query 转小写、按空白拆开并去重：

```text
缓存 失效 → [缓存, 失效]
```

然后检查：

```ts
if (!words.every((word) => haystack.includes(word))) return false;
return words.some((word) => title.includes(word) || keywords.includes(word));
```

`haystack` 是 title、summary、keywords 的拼接文本。

换成人话：每个词都得在这三处之一出现，而且至少一个词要出现在标题或关键词里。A 的标题同时含“缓存”和“失效”，其他五篇没有“失效”，所以保护集合只有 A。

这不是标题全等，也不要求两个词连续出现；anchor 和 passage 正文没有加入该判定。单个非 CJK 词不启动保护，含 CJK 的单词查询可以启动。这解释了上一条 cache 轨迹为什么没被保护短路。

### 10.2 authority 与 consumption 的做法不同

authority 只要发现有保护项，就跳过整轮权威重排：

```text
[E,C,D,B,A,F] → 不变
```

consumption 则把 A 抽出：

```text
protectedResults = [A]
rerankPool       = [E,C,D,B,F]
```

剩余池重新从 0 编号。因此 D 的“原位置”是这个池中的 2，不再直接使用完整输入数组下标的语义。

在模拟 9 月 12 日，D 仍是 cold-start，没有 pinned。算分后的剩余顺序是 `[B,D,C,F,E]`，再把 A 前置，得到 `[A,B,D,C,F,E]`。

### 10.3 现在只推进模拟时钟，不改文档身份

第二个时钟设为 **2026-09-19T00:00:00Z**。这是为测试边界使用的未来模拟日期，不是本文的整理日期。

文档字段、关键词、n/c 和 baseline 不变；按固定最后消费日期重新提供 dormancy，文档年龄也自然增加 7 天。

D 恰好满 14 天，不再满足 `<14 天`，于是终于执行后面的代码：

```text

从未消费，因此 R=0.5，先于 T=null 的判断
rawLift = (0.05-0.2)×0.5 = -0.075
constitutional 分支：prior=max(0,-0.075)=0
```

D 的 prior 仍为 0，但 **branch 从 cold-start 变成 constitutional**。这个字符串接下来会改变数组重建方式。

### 10.4 pinned 不是“得到无限大的分数”，而是固定槽位

源码用返回分支决定钉位：

```ts

```

再分别保存：

```ts

else movable.push(s);
```

在 `[E,C,D,B,F]` 中，新的账本如下；D 虽然有 newScore，却不参加 movable 的分数竞争。

| 文档 | 剩余池 i | prior | V | newScore | 去向 |
|---|---:|---:|---:|---:|---|

```text

V = 90/97 ≈ 0.92783505
```

| 模拟 9 月 12 日 | cold-start | A,B,D,C,F,E |

主轨迹一同理：对 Store 的 `[B,D,A,C,F,E]`，salience=off/shadow 都不替换；on 才变为 `[D,A,C,B,F,E]`。

所以回答“为什么 shadow 用户顺序仍变了”，第一件事是问清楚**哪一阶段 shadow，其他阶段是什么状态**。

salience 日志可记录 taskContext、before、after、scores；F200 shadow 先放在进程内关联记录中，按结果 anchor 查取。它们不是随机对照实验，更不能自动消除“前排更容易被读到”的曝光偏差。

## 13. 轨迹四：raw 找到了 F 的原文，为什么最后仍不是 F 第一？

仍回到主模拟时钟。初始候选 `[A,B,C,D,E,F]` 不变，只给 F 一条构造好的 passage，其他五篇没有：

```text
F.passages = [{ passageId: "msg-f1", threadId: "cache", messageId: "f1", ... }]
depth=raw，scope=all，limit=6
```

这次验证的是 `rankRawResults` 收到已回填 passage 后的排序，不是实际写入一条消息或运行 passage 检索。

`rankRawResults` 先比较有没有 passages：有的在前。两篇都有时比较第一次 passage 命中的顺序；都没有时保留原顺序。于是 F 先升到第一位。

但 raw 返回前仍会进入 enrich，只是没有传 targetLimit：

| 阶段 | 数组 | 发生了什么 |
|---|---|---|
| 给定父文档 | A,B,C,D,E,F | F 带一条 passage |
| rankRawResults | F,A,B,C,D,E | 原文命中优先 |
| authority | 不调用 | raw 已在其之前分流 |
| F200 | B,D,A,F,C,E | 按新的输入位置重新计分；无此处 MMR |
| 路由 salience | D,A,C,B,F,E | task 相关性最后排序 |

原文命中提高的是这个阶段的位置，不是后面所有算法都必须遵守的永久置顶规则。

raw 内部本身可以做 passage lexical、semantic、hybrid；显式 scope 不是 all/threads 时还会提前走基础文档排序。passage embedding 不可用或向量搜索失败时，有自己的词法回退和原因字段。因此不能把当前实现说成“raw 永远只有词法”，也不能说“raw 一定经过摘要侧 authority”。

源码：[raw 入口及 scope/模式](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L551)、[raw 排序函数](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L1049)、[raw 提前返回](D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L416)。

## 14. 看 explain 时，为什么“第一条 bm25Score=2”不一定是错误？

回到轨迹一。Store 输出 `[B,D,A,C,F,E]` 时，源码做了：

```ts
item.rankingFactors = { bm25Score: results.indexOf(item) + 1 };
```

逐字解释：在**当前结果数组**里找 item 的下标，再加 1。不是调用 SQLite 的 bm25 函数。

然后路由把数组排成 `[D,A,C,B,F,E]`，却没有重算这个字段：

| 路由最终位置 | 文档 | 保留下来的 bm25Score | 路由 confidence |
|---:|---|---:|---|
| 1 | D | 2 | high |
| 2 | A | 3 | high |
| 3 | C | 4 | mid |
| 4 | B | 1 | mid |
| 5 | F | 5 | mid |
| 6 | E | 6 | low |

这组错位在本次隔离验证中实际出现。它说明字段含义有限，不说明 D 的原始 BM25 真的等于 2。

还应记住：

- `consumptionPrior`、`mmrPenalty` 只在类型中预留，此处没有填值；不能编造完整贡献分解。
- `matchReason` 优先选 entity、anchor、title、summary、keyword，最后 content 兜底；它是一条命中线索，不是全部原因，也不是可靠的召回腿标签。
- confidence 是最终零基 index 映射：前两条 high，第 3～5 条 mid，之后 low；不是正确概率。
- `boostSource` 主要按 F163 开关归因，authority shadow 也可能有 authority_boost 标签；它不能证明实际发生了某次提分。

路由只接受 `explain=true/1`。没有开启时，不应期待 rankingFactors；开启也不意味着已完整记录 every stage 的输入、分支和分数。

## 16. 失败与成本：不要只说“有回退，所以可靠；候选少，所以很快”

### 16.1 给统计读取故意抛错，恢复的是哪条顺序？

对轨迹一，在 authority 已完成后让统计桩抛错：

```text
最初输入             A,B,C,D,E,F
authority 已完成      D,A,C,B,E,F
统计读取异常          ×
enrich 捕获后         D,A,C,B,E,F
```

本次实际确认保留的是 `[D,A,C,B,E,F]`，不是倒退到最初输入。随后解释注解仍能继续执行。

对应代码：

```ts
try {
  if (this.db) applyConsumptionRerank(results, this.db, targetLimit, query);
} catch {
  // 保留已有排序继续
}
```

authority 自身也有局部异常回退。局部失败未必会写成响应 degraded，因此“请求成功”不能证明每个排序阶段都执行成功。

### 16.2 缺统计和坏统计要分开

完全没有统计时，输入被补成 c=n=0、d=null；但年龄项仍在。本章六篇在这个桩下仍从 `[A,B,C,D,E,F]` 变为 `[B,D,A,C,F,E]`，所以不能拿“冷启动”推导任意输入都保序。

坏时间则不同：非法日期可以产生 NaN，分式函数也会返回 NaN，并不一定抛异常。try/catch 不是数据验证器。正常算法解释依赖 c、n 非负且 c≤n，时间合法、年龄非负、候选 anchor 唯一等输入条件。

### 16.3 MMR 的循环到底花在哪里？

设候选 n、要选 k、平均关键词规模 w。

本例六选二：第一轮遍历六篇，没有已选项；第二轮遍历五篇，各与 B 比一次。如果还要继续第三轮，每个剩余候选就要与两个已选项重新比较。

这份实现每轮重新计算全部已选相似度，每次 Jaccard 又新建 Set。所以一般上界是 **O(n·k²·w)**，不是把维护“最大相似度缓存”的优化版 O(n·k·w) 套过来。

authority、movable、salience 主要有 O(n log n) 排序；salience 还受任务引用数量、关键词和字符串长度影响。中间数组/Map 的本地空间通常随 n 增长。explain 中每篇都做一次 `indexOf`，位次查找部分还是 O(n²)。

HTTP limit 上限 20 有助于限制最终列表，但 hybrid 还会扩大候选池。这里只分析重排循环，不包括 FTS、向量召回、回表和日志成本，更没有据此声称多少毫秒。

### 16.4 消费更高，为什么仍然不能宣布“更真实”？

被排前的资料更容易被看见；经常用某类工具，也会改变哪些资料被记录消费。收缩缓解小样本极端值，不会自动消除这些选择偏差。

因此需要分开：

```text
被召回 ≠ 被读到 ≠ 被采用 ≠ 最后验证正确
```

规范豁免、精确词法保护、任务 salience 都说明系统没有只押注热门程度；但这些护栏本身也不是内容判真程序。真伪仍需返回原文、来源与可验证证据。

## 17. 面试时怎么把这些状态讲成一个连贯回答？

#### 问：你们是把所有排序分数线性加起来吗？

> 不是。authority 在词法侧按位置乘权重，hybrid 再融合各召回腿名次；F200 重建位置分，加消费 prior 和年龄项。路由 salience 最后独立稳定排序。raw 在 authority 调用前分流。我们的六篇示例每经过一站都有不同数组，不能用一个总公式代替调用顺序。

#### 问：贝叶斯收缩解决了什么，没解决什么？

> B 的 20/30 被收缩为 22/40，F 的 1/1 被收缩为 3/11，再与同类 baseline 比较。它减少小样本极端比例，后面还要过曝光和宽限门控；它不负责判真，也不消除曝光位置偏差。

#### 问：constitutional 是不是永远置顶？

> 不是。D 在前 14 天先返回 cold-start；满 14 天才进入规范分支。Store 根据返回 branch 将 D 固定在剩余池槽位，不是给无限分。词法前置、最终截断和路由 salience 还会影响完整结果位置。

#### 问：MMR 用向量吗，为什么有时不执行？

> 当前用关键词集合 Jaccard。六篇、limit=2 时，必须六篇都还在 movable 才过 3 倍门槛；D 进入 pinned 后只剩五篇就不执行。执行时先选 B，再因关键词冗余惩罚选 C，而不是纯相关分的第二名 D。

#### 问：shadow 对照怎么记录才有意义？

> shadow 模式保留旧 live，记录假设新序列；on 模式使用新 live，记录进入 F200 前的旧序列。后者可能已经是 RRF 或 passage 排序，不能统称纯 BM25。其他阶段 on 时仍可能继续改序。

#### 问：explain 能证明某篇为什么第一吗？

> 当前只能部分解释。bm25Score 实际写的是 Store 一基位置，路由改序后不重算；类型预留的 prior/MMR 贡献也没在这里填。因此 D 最终第一但字段为 2 是可复现的，不能按字段名臆造原始分数。

#### 问：这次验证和线上有效性差在哪里？

> 这次执行了源码中的函数与方法主体，使用固定六篇资料、模拟时钟、只读统计桩和给定 NN 名次，共 76 个断言。确认了计算和分支，不包含真实召回、数据库、网络或完整应用，更不是线上准确率、NDCG 或延迟提升的证明。
