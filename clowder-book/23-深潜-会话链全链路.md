## 0A. 零基础导读：thread、session、session chain 为什么不是一回事

> 会话章的难点不是 API 多，而是“同一段对话”在业务层和各 CLI Provider 中有不同身份。先分清对象，再看封板、续接和抗压缩。

### 0A.1 四个容易混淆的对象

| 对象 | 含义 |
|---|---|
| thread | 用户看到的长期对话容器 |
| invocation | 某一次具体执行 |
| provider session | Claude/Codex 等 CLI 自己的上下文会话 |
| session chain | 一个 thread/cat 因封板、失效或切换而产生的多段 session 关系 |

一个 thread 可以有很多 invocation；同一只猫也可能先用 session S1，封板后换 S2，但业务上仍属于同一协作链。

### 0A.2 为什么 session 不能永久复用

Provider session 会遇到：上下文过长、压缩后信息损失、CLI 文件丢失、工作目录变化、模型/账号切换、进程异常。继续 `--resume` 可能失败，甚至把任务恢复到错误工作区。

所以系统需要判断：可继续、正在封板、已封板、新建后继 session，而不是只保存一个 `sessionId` 字符串。

### 0A.3 会话状态机

```text
active → sealing → sealed
  │                    │
  └──── 创建 successor session ────→ active
```

- `active`：允许继续 resume。
- `sealing`：正在生成交接材料，避免多次同时封板。
- `sealed`：不再直接恢复，应使用后继 session。

状态机要回答：谁触发 sealing？失败是否回滚？并发两个 invocation 谁负责创建 successor？重复请求是否得到同一个结果？

### 0A.4 链表式关系如何理解

session chain 可以想成：

```text
S1 --successor--> S2 --successor--> S3
S2 --predecessor--> S1
```

每段保留自己的 Provider sessionId、状态、原因、时间和工作区指纹。链关系让系统既能找到当前 active 段，也能审计为什么从旧段切换。

### 0A.5 `SessionManager` 与持久化 Store 的边界

Manager 通常表达业务动作：取可恢复 session、更新映射、清理或切换；Store 负责具体内存/Redis 读写。接口分层的价值是业务规则不依赖 ioredis 语法，测试也可用内存实现。

读代码时区分：

```text
Manager：应该做什么
Store port：需要哪些数据能力
Redis/InMemory implementation：具体怎么存
```

### 0A.6 Mutex 为什么常按 sessionId 加

两个请求同时恢复同一 CLI session，可能同时写同一 transcript/session 文件，导致上下文互相覆盖。因此按 sessionId 串行化，而不是全局只允许一个调用：

```text
S1 的调用 A ─┐ 串行
S1 的调用 B ─┘
S2 的调用 C ─── 可并发
```

锁的粒度越大越安全但吞吐越低；按 session key 加锁是在正确性与并发度之间折中。

### 0A.7 工作区指纹为什么属于会话安全

同一个 Provider session 若原来在仓库 A 创建，却在仓库 B resume，模型可能带着旧路径、旧文件和旧任务记忆执行。指纹用于验证 session 与当前工作区是否匹配。

这不只是“体验问题”，也可能造成跨项目数据泄露或误修改，是明确的安全边界。匹配失败通常应新建 session，而不是盲目恢复。

### 0A.8 sealing 与普通 summary 的区别

普通 summary 是压缩历史文本；sealing 更像一次有契约的交接：保存当前任务、已完成事项、未解决风险、关键文件/真相源和下一段应继续做什么。它要让新 session 在不知道全部原文时仍能继续协作。

可以把 continuity capsule 理解为“从旧上下文编译出的恢复包”，不是新的真相源。原始 thread/存储仍是事实，capsule 是派生材料。

### 0A.9 hook、transcript 与运行时 session

CLI 可能把 session/transcript 存在自己的目录，服务端还维护业务映射。hook 用于在 Provider 生命周期关键点捕获信息或注入提示。阅读时要画清数据方向：

```text
API 业务 session record
↔ Provider CLI sessionId
↔ CLI transcript/session 文件
↔ hook 产生的状态或锚点
```

不要默认四者强一致；本章大量防御代码正是在处理它们可能短暂不一致。

### 0A.10 常见失败场景

1. Store 有 sessionId，但 CLI 文件已被删除。
2. 两个请求同时发现需要封板。
3. sealing 成功，但 successor 映射写入失败。
4. session 属于旧 worktree。
5. Provider 报“无法 resume”，系统需要新开而不是无限重试。
6. 进程在 `sealing` 状态崩溃，重启后如何恢复。
7. chain 出现环或 predecessor/successor 不对称。

### 0A.11 第一次源码陪读

```text
shared session 类型与状态枚举
→ SessionManager
→ session-chain store port 与 Redis/InMemory 实现
→ SessionMutex
→ session sealer / continuity capsule
→ runtime-session 目录
→ invokeSingleCat 中读取、验证、写回 session 的位置
→ Provider transcript/hook 适配
```

每一步记录：真相源是谁、缓存是谁、失败时新建还是终止。

### 0A.12 动手练习

先写一个内存版：`Map<threadId+catId, currentSessionId>`，再加入 chain record 和 `active/sealing/sealed`。用两个并发 Promise 同时 seal，观察没有锁时是否创建两个 successor。这个实验能直接理解为什么需要 mutex/CAS。

## 2. 核心数据结构

### 2.1 `SessionRecord`（`packages/shared/src/types/session.ts`）

这是整章的心脏。**逐字段解释「为什么存在」**：

| 字段 | 类型 | 为什么存在 |
|---|---|---|
| `id` | `readonly string` | 我们自己的 UUID。**不是** CLI 的 session id——因为 CLI 会换 id，我们的主键不能跟着换 |
| `cliSessionId` | `string`（可变） | CLI 自报的 id（`session_init` 事件带来）。ACP/bg 场景每轮都换，所以是可变字段 |
| `workingDirectory` | `string?` | 这个 CLI session 绑在哪个工作目录。跨目录 resume 会串上下文 |
| `workspaceFingerprint` | `string?` | 工作区稳定身份。判断「这个 CLI session 还能不能 resume」的依据 |
| `threadId` / `catId` / `userId` | `readonly` | 三元组身份。注释写明 session 按 threadId 隔离是「茶话会夺魂 bug fix #38」 |
| `seq` | `readonly number` | 链内序号，**0-based**。展示时 +1（`displaySeq`） |
| `status` | `'active'\|'sealing'\|'sealed'` | 三态。`sealing` 存在的理由：flush transcript 要时间，这段时间里不能再收新事件，也不能算已封好 |
| `contextHealth` | `ContextHealth?` | 最近一次 usedTokens/windowTokens/fillRatio/source 快照 |
| `lastUsage` | `SessionUsageSnapshot?` | 注释明写「persisted for frontend display after reload」——纯为刷新页面还能看到花了多少钱 |
| `messageCount` | `number` | unseal 时用来判断「这个 active session 是不是空的、能不能挤掉」 |
| `sealReason` | 联合类型 + `(string & {})` | `'threshold' \| 'manual' \| 'error' \| 'cat_initiated_handoff' \| (string & {})`。最后那个 `(string & {})` 是 TS 技巧：既保留字面量自动补全，又允许任意字符串（reaper 会写 `'reconcile_stuck'`、`'global_reaper'`） |
| `catHandoffNote` | `CatHandoffNote?` | F225：猫亲手写的五件套。注释强调是 **typed**，故意不塞进 `continuityCapsule: unknown` |
| `compressionCount` | `number?` | F33 hybrid 策略计数。只有 Claude 的 PreCompact hook 能维护它 |
| `continuityCapsule` | `unknown` | 故意是 `unknown`！读的时候必须过类型守卫（见 §4.7） |
| `consecutiveRestoreFailures` | `number?` | F118 AC-C6 熔断器。CLI session 被换掉时**继承**给新记录 |
| `chainKey` | `string?` | F198 Bug #3：bg carrier 的稳定会话锚 `bg:${threadId}:${catId}`。因为 bg daemon 每轮 `--bg --resume` 都 fork 一个新 sessionId UUID，`cliSessionId` 不是稳定身份 |
| `latestResumeSessionId` | `string?` | bg 专用：daemon 写的下一轮 resume 目标 |
| `createdAt` / `updatedAt` / `sealedAt` | number | `sealedAt` 是 nullable patch（见下） |

**`SessionRecordPatch` 的特殊设计**（`ports/SessionChainStore.ts`）：

```ts
export type SessionRecordPatch = Partial<Pick<SessionRecord, /* 13 个可变字段 */>> & {
  sealReason?: SessionRecord['sealReason'] | null;
  sealedAt?: number | null;
};
```

> **面试官追问：为什么 `sealReason`/`sealedAt` 要单独拎出来允许 `null`？**
> 「因为这两个字段需要支持『删除』语义，不只是『设置』。`reopenFailedExternalRegistrationSessionRecord()` 要把一条已封存记录改回 active，就必须把 sealReason/sealedAt 清掉——【源码】里全仓唯一写 `sealReason: null, sealedAt: null` 的就是它（`ExternalRuntimeSessionRegistration.ts`）。`Partial<T>` 里 `undefined` 的含义是『不改』，所以要表达『清空』只能引入 `null`。实现上两个 store 都用 `'sealReason' in patch` 判断键是否存在，再看值是 `null` 还是有值——内存版走 `delete record.sealReason`，Redis 版走 `HDEL`。」【源码】
> 补一句区分：`POST /unseal` **不**走这条清空路径——它是 `create()` 一条新的 active 记录（见 §4.1 状态机图），旧记录仍留在 sealed。

### 2.2 `ISessionChainStore` 完整 API（10 个方法）

| 方法 | 语义要点 |
|---|---|
| `create(input)` | seq 自增，status 固定 `active`，返回新记录 |
| `get(id)` | 按内部 id |
| `getActive(catId, threadId)` | 查 activeIndex，**并二次校验 `status === 'active'`**（索引可能脏） |
| `getChain(catId, threadId)` | 全链，按 seq 排序 |
| `getChainByThread(threadId)` | 跨猫全链，排序键 `catId` 再 `seq` |
| `update(id, patch)` | 部分更新 |
| `getByCliSessionId(cliSessionId)` | CLI id → 记录（hook route 全靠这个） |
| `getByChainKey(chainKey)` | **故意不过滤 status**。注释：「a sealed record must remain reachable so a concurrent done write during a seal edge keeps its state」 |
| `incrementCompressionCount(id)` | 原子自增，`status !== 'active'` 返回 `null` |
| `listSealingSessions()` | 全局 reaper 用 |

`CreateSessionInput` 里有个不显眼但关键的 `reuseExistingCliSession?: boolean`：置 true 时，若 `cliSessionId` 已被占用就直接返回已有记录（幂等），而不是造第二条。外部 runtime 注册路径用的就是它。

### 2.3 `ExtractiveDigestV1`（`TranscriptWriter.ts`）

```ts
export interface ExtractiveDigestV1 {
  v: 1;
  sessionId; threadId; catId; seq;
  time: { createdAt: number; sealedAt: number };
  sealReason?: string;
  invocations: Array<{ invocationId?: string; toolNames?: string[] }>;
  filesTouched: Array<{ path: string; ops: string[] }>;
  errors: Array<{ at: number; invocationId?: string; message: string }>;
  diagnostics?: { noise?: DigestNoiseSummary[] };
  recentMessages?: Array<{ role: 'assistant'; invocationId?: string; content: string }>;
  continuityCapsule?: CollaborationContinuityCapsuleV1;
}
```

**坑（值得当加分点说）**：`invocations` 字段类型看起来是「每个 invocation 一项」，但 `generateExtractiveDigest()` 实际只 push **一个** 元素：

```ts
invocations: [{ toolNames: [...toolNames] }],
```

即整个 session 的工具名去重后塞进单个 slot，`invocationId` 根本没填。所以 `SessionBootstrap.formatDigest()` 里的 `digest.invocations.flatMap(inv => inv.toolNames ?? [])` 实际上只是遍历一个元素。【源码】

`DigestNoiseSummary` 的字段：`kind`（三种）、`count`、`sample`、`invocationIds: string[]`、`firstAt`、`lastAt`、`outcome: 'recovered' | 'terminal'`。

### 2.4 `CollaborationContinuityCapsuleV1`

```ts
{
  v: 1; threadId; catId;
  invocationId?; parentInvocationId?;
  mode: 'independent' | 'serial' | 'parallel';
```

### 2.6 五个概念的 key 设计（这一节单独拎出来，因为面试最爱问）

任务点名要「把 Redis key 格式全列出来」。所有 key 都**不带前缀**写在代码里，前缀由 ioredis 的 `keyPrefix` 自动加，默认 `cat-cafe:`（`REDIS_KEY_PREFIX` 可改，见 `packages/shared/src/utils/redis.ts` 的 `getDefaultRedisConfig()`）。

#### 2.6.1 概念一：Thread（会话线）

- 存储：`ThreadKeys.detail(threadId)` 是一个 Hash。
- 与本篇相关的字段：`pendCont:{catId}:{userId}` —— 待续跑胶囊。
  - 注释写明两次修：`#813 P2` 改成 per-cat hash field（原子 HSET，避免 read-modify-write 竞态）；`Cloud Codex P1` 再加 userId 作用域，防共享 thread 里跨用户泄漏。
  - 消费用 Lua 原子读删：`local v = redis.call('hget',KEYS[1],ARGV[1]) if v then redis.call('hdel',KEYS[1],ARGV[1]) end return v`。
  - 内存版对应 `thread.pendingContinuation[`${catId}:${userId}`]`，消费后如果容器空了会 `delete thread.pendingContinuation`。

#### 2.6.2 概念二：Session Chain（会话链）

`stores/redis-keys/session-chain-keys.ts` 全文只有 5 条：

```
session:{id}                          Hash   —— SessionRecord 各字段
session-chain:{catId}:{threadId}      ZSet   —— 链，score = seq
session-active:{catId}:{threadId}     String —— 当前 active 的 record id
session-cli:{cliSessionId}            String —— CLI id → record id
session-by-chainkey:{chainKey}        String —— chainKey → record id（F198 bg）
```

内存版对应 5 个 Map：`records` / `chains`（`catId:threadId → id[]`）/ `activeIndex` / `cliIndex` / `chainKeyIndex`。复合键由私有方法 `catThreadKey(catId, threadId)` 生成，就是 `` `${catId}:${threadId}` ``。

#### 2.6.3 概念三：Active Slot（活跃槽位）

就是上面的 `session-active:{catId}:{threadId}`。**它是「一猫一线程只能有一个活跃 session」这条不变量的物理载体。**

三条读写规则（【源码】`RedisSessionChainStore.update()` + 内存版 `update()`）：
1. `patch.status === 'active'` → 无条件 `SET activeKey = id`（抢占）。
2. `patch.status` 是别的（sealing/sealed）→ **先读再删，且只在 `currentActive === id` 时删**。这叫 ownership check：不能替别人清槽位。
3. `getActive()` 读到 id 后还要 `get(id)` 再验 `status === 'active'`，索引脏了就返回 null。

#### 2.6.4 概念四：CLI Resume（CLI 续跑指针）

两套东西，别搞混：

**(a) SessionManager 管的 resume 指针**（`packages/shared/src/utils/redis.ts` 的 `SessionKeys`）：

```
sessions:{userId}:{catId}:{threadId}        String, TTL 86400s（1 天）
```

这条是「下次起 CLI 时 `--resume` 传哪个 id」。`SessionStore.setSessionId()` 默认 `ttlSeconds = 86400`。
同一个 `SessionKeys` 里还有几条相邻游标（不属本篇但一起列全，面试常连着问）：

```
delivery-cursor:{userId}:{catId}:{threadId}   String, TTL 604800s（7 天，#40）
mention-ack:{userId}:{catId}:{threadId}       String, TTL 604800s（#77，注释「same as delivery cursor」）
seen-cursor:{userId}:{catId}:{threadId}       String, TTL 604800s（F254，注释「same as other cursors」）
state:{catId}      tasks:{catId}      chat:messages
```

游标推进用 Lua `SET_IF_GREATER_LUA`：`local cur = redis.call('GET',KEYS[1]) if cur and ARGV[1] <= cur then return 0 end redis.call('SET',KEYS[1],ARGV[1],'EX',tonumber(ARGV[2])) return 1`——**单调 CAS，字典序比较**（因为 messageId 是可排序 id）。

**(b) SessionChainStore 管的反查索引**：`session-cli:{cliSessionId} → record id`。hook route 拿到 Claude Code 的 `session_id` 后就靠它找回我们的 SessionRecord。

> **面试官追问：为什么要两条？**
> 「方向不同、生命周期不同。`sessions:*` 是**正向**（我要起进程，给我 resume 目标），带 1 天 TTL，因为 CLI 那边的 session 本来就会过期。`session-cli:*` 是**反向**（外部 hook 报了个 cliSessionId，我要找回内部记录），必须持久（`DEFAULT_TTL_SECONDS = 0`），否则 hook 永远 404。另外 SessionManager 在没有 Redis 时会降级成一个 1000 条上限的内存 LRU Map，key 是 `${userId}:${catId}:${threadId}` ——写入前先 delete 再 set，让它移到 Map 尾部实现 LRU。」【源码】

#### 2.6.5 概念五：Connector Binding（外部 IM 绑定）

`infrastructure/connectors/connector-binding-keys.ts`：

```
connector-binding:{connectorId}:{externalChatId}   Hash   —— 绑定详情
connector-binding-rev:{threadId}                   Set    —— 反向索引，成员是「未加前缀」的 forward key
connector-binding-user:{connectorId}:{userId}      ZSet   —— score = createdAt
```

注意反向 Set 里存的是**不带 ioredis 前缀**的 key 字符串（`RedisConnectorThreadBindingStore.ts` 注释明写）。因为取出来还要当参数喂给普通命令，而普通命令会自动加前缀——存带前缀的就会双前缀。

#### 2.6.6 Runtime Session 侧车 key（`stores/redis-keys/runtime-session-keys.ts`，7 条）

```
runtime-session:{sessionId}                                     String JSON  —— 元数据本体
runtime-session:runtime:{runtime}:{runtimeSessionId}            String       —— → sessionId
runtime-session-active:{runtime}:{threadId}:{catId}             String       —— → 活跃 sessionId
runtime-session:lifecycle:{state}                               ZSet, score = lastObservedAt
```

#### 2.6.7 策略覆盖 key（`config/session-strategy-keys.ts`，1 条）

```
session-strategy:override:{catId}    String JSON  —— Partial<SessionStrategyConfig>
```

#### 2.6.8 SCAN 前缀陷阱（三处代码都写了同样的注释）

【源码】`RedisSessionChainStore.scanKeys()` / `session-strategy-overrides.ts` / `RedisRuntimeSessionStore` 头注释：

> ioredis 的 `keyPrefix` **会**自动加到普通命令和 `eval()` 的 `KEYS[]`，但**不会**加到 `SCAN MATCH` 的模式串上。

所以 scan 的正确写法是三步：
1. 手动拼 `matchPattern = keyPrefix + barePattern`；
2. scan 出来的 key **带前缀**；
3. 用之前必须 `k.slice(prefix.length)` 剥掉，否则后续 `get()` 会双前缀。

同理，Lua 脚本里**动态拼**的 key 也必须自己带前缀——Redis 服务端不知道 ioredis 的客户端选项。`RedisRuntimeSessionStore` 的 UPSERT_LUA 就是把 `keyPrefix` 当 `ARGV[2]` 传进去，脚本里到处 `ARGV[2] .. 'runtime-session:recent:' .. ...`。

### 2.7 从一条 `SessionRecord` 看懂“业务会话”和 CLI 会话的映射

一条记录不是只保存 `sessionId`：

```text
业务定位：threadId + catId（或稳定 chainKey）
CLI 定位：cliSessionId / latestResumeSessionId
生命周期：active / sealing / sealed
健康信息：token usage、fillRatio、compressionCount
继承关系：predecessor/successor、handoff note、continuity capsule
时间：createdAt、updatedAt、sealedAt
```

`chainKey` 的注释尤其值得读。普通 Provider 的 cliSessionId 可以稳定代表一段会话；bg carrier 每轮 resume 可能 fork 新 UUID，因此不能用最新 UUID 当整段对话身份。项目增加 `bg:${threadId}:${catId}` 作为稳定锚点，并另存 `latestResumeSessionId` 作为下一轮真正传给 CLI 的目标。这是“业务身份”和“运行时句柄”分离的典型案例。

`SessionRecordPatch = Partial<Pick<...>> & {...}` 可以拆开理解：`Pick` 从完整记录挑出允许修改的字段，`Partial` 再把它们都变成可选，因此 update 调用只提交变化部分；交叉类型 `&` 还能额外要求某些控制字段。这样比接受 `Partial<SessionRecord>` 安全，因为 `createdAt`、主键等不可变字段不会被任意覆盖。

`ContextHealth` 中 `fillRatio` 不能脱离 `source/usedFrom` 解读。精确 token、近似窗口和 bytes trajectory 的可信度不同，所以软提示还带 `fillConfidence`。这体现了一个重要设计原则：不要只保存一个百分比，还要保存这个百分比是怎样测出来的。否则上层会把近似值当硬阈值误封板。

`ExtractiveDigestV1` 与 `CollaborationContinuityCapsuleV1` 也不是同一种摘要：前者偏 transcript 中可机械提取的事实和索引；后者保存跨压缩/封板仍要继续执行的协作控制状态。后者若丢失，模型可能知道“讨论了什么”，却不知道“球在谁手里、下一步交给谁、哪些约束仍生效”。

进入 §3 时用三条线并行追踪：SessionRecord 状态怎样变、磁盘 transcript 写了什么、下一轮 bootstrap 最终注入了什么。只追其中一条，会误以为 `sealed` 写进 Redis 就等于交接已完整完成。

## 3. 主流程逐段拆解

按一次调用的真实执行顺序走：**开局绑定 → 事件累积 → 阈值判定 → 请求封存 → 收尾产出 → 下一轮引导**。

### 3.1 第一段：`session_init` 到来，绑定/新建 SessionRecord

**做什么**：CLI 子进程启动后吐的第一个事件带 `sessionId`。这时要 (a) 存 resume 指针 (b) 保证有一条 active SessionRecord。

**关键代码**（`agents/invocation/invoke-single-cat.ts`，搜 `'Session init: binding session'`）：

```ts
if (msg.type === 'session_init' && msg.sessionId) {
  log.info({ cliSessionId: msg.sessionId, threadId, catId, userId, invocationId },
           'Session init: binding session');
  try { await sessionManager.store(userId, catId, threadId, msg.sessionId); }
  catch { /* Redis write failure — session won't persist, but chain continues */ }
  // ... bg carrier 注册 ...
  if (isBgCarrier && bgChainKey && deps.sessionChainStore && sessionChainActive) { /* 分支 A */ }
  else if (deps.sessionChainStore && sessionChainActive) { /* 分支 B */ }
}
```

**分支 A：bg carrier（chainKey 路径）**

```ts
const bgRec = await deps.sessionChainStore.getByChainKey(bgChainKey);
if (bgRec && bgRec.status === 'active') {
  if (bgRec.cliSessionId !== msg.sessionId) {
    await deps.sessionChainStore.update(bgRec.id, {
      cliSessionId: msg.sessionId,
      ...(params.continuityCapsule ? { continuityCapsule: params.continuityCapsule } : {}),
      updatedAt: Date.now(),
    });
  } else if (params.continuityCapsule) { /* 只更新 capsule */ }
} else {
  const newRec = await deps.sessionChainStore.create({ cliSessionId: msg.sessionId, threadId, catId, userId, chainKey: bgChainKey });
  // ...
}
```

**为什么这么写**：注释写得很直白——「ACTIVE record → 就地更新 cliSessionId（NO seal+create —— that cascade is the multi-turn amnesia root cause）」。bg daemon 每轮 `--bg --resume` 都 fork 新 UUID，如果按分支 B 的逻辑「CLI id 变了 = 上下文丢了 = 封旧建新」，那每一轮都会封一次，猫就永远只记得一轮——这就是「多轮失忆」的根因。

**坑**：`getByChainKey()` 故意不过滤 status。所以这里必须**显式**判 `bgRec.status === 'active'`；已被外部（manual/threshold/reaper）封存的旧记录不能被复活，要走 create 新建，chainKey 索引重新指向新记录。

**分支 B：普通 CLI**

三种情形：
1. **有 active 且 cliSessionId 相同** → 只在有 capsule / workspace 绑定时 update。
2. **有 active 但 cliSessionId 变了，且 `msg.ephemeralSession === true`**（ACP 传输，每次 `newSession()`）→ 注释明写「This is normal — NOT a "session replaced" event」，只更新 id。
3. **有 active 且 id 变了，非 ephemeral** → **认定 resume 失败 / CLI 重启**，走完整封存：

```ts
const result = await deps.sessionSealer.requestSeal({ sessionId: existing.id, reason: sealReason });
sealAccepted = result.accepted;
if (sealAccepted) { /* 可能补写 antigravity_runtime_lifecycle 事件 */
  deps.sessionSealer.finalize({ sessionId: existing.id }).catch(() => {});
}
// ...
if (sealAccepted || !deps.sessionSealer) {
  const inheritedFailures = existing.consecutiveRestoreFailures ?? 0;
  const newRec = await deps.sessionChainStore.create({ cliSessionId: msg.sessionId, ...sessionWorkspaceBinding, threadId, catId, userId });
  if (inheritedFailures > 0) {
    await deps.sessionChainStore.update(newRec.id, { consecutiveRestoreFailures: inheritedFailures, ... });
  }
}
```

三个必须能复述的点：
- **不用 `update({status:'sealed'})` 而用 `requestSeal + finalize`**。注释：「not bare update(status:'sealed') which skips flush」——裸更新会跳过 transcript 落盘。
- **只有 sealAccepted 才建新记录**。注释：「Otherwise we'd have two active records — a dirty state.」
- **`consecutiveRestoreFailures` 要手动继承**，因为 `create()` 的入参里没这个字段（F118 D1）。这是熔断器：连续 resume 失败若干次就该换策略，计数不能因为换了条记录就清零。

### 3.2 第二段：每个事件写进 TranscriptWriter

**做什么**：`appendEvent()` 把事件塞进内存缓冲，同时 fire-and-forget 追加到磁盘。

```ts
appendEvent(session: TranscriptSessionInfo, event: Record<string, unknown>, invocationId?: string): void {
  let buf = this.buffers.get(session.sessionId);
  if (!buf) { buf = []; this.buffers.set(session.sessionId, buf); }
  const entry: BufferedEvent = {
    eventNo: buf.length,
    timestamp: Date.now(),
    ...(invocationId !== undefined ? { invocationId } : {}),
    event,
  };
  buf.push(entry);
  this.enqueueDiskAppend(session, entry);   // 崩溃恢复保险
}
```

`enqueueDiskAppend()` 的写法值得说：**每个 session 一条 Promise 链**，保证同一 session 的追加是串行的（不会交错写坏一行）：

```ts
const prev = this.diskWriteQueue.get(session.sessionId) ?? Promise.resolve();
const next = prev.then(async () => {
  const dir = this.sessionDir(session);
  await mkdir(dir, { recursive: true });
  const envelope = { v: 1, t: entry.timestamp, threadId, catId, sessionId, cliSessionId, invocationId, eventNo, event };
  await appendFile(join(dir, 'events.live.jsonl'), `${JSON.stringify(envelope)}\n`, 'utf-8');
}).catch(() => { /* Best-effort: buffer is the primary source */ });
this.diskWriteQueue.set(session.sessionId, next);
```

**为什么这么写**：注释——「buffer is the primary source during normal operation; disk copy only matters when the process restarts and buffer is lost」。正常路径读内存，`events.live.jsonl` 纯粹是进程崩了之后的保险。

**坑**：`.catch(() => {})` 吞掉磁盘错误，所以磁盘上可能**缺**某些内存里有的事件。这正是 flush 时要做「双向合并 + 内容去重」而不是「磁盘覆盖内存」的原因（见 §4.3）。

### 3.3 第三段：`done` 事件时的阈值判定

**做什么**：拿最新 usage 算 contextHealth，喂给 `shouldTakeAction()`，按返回的 5 种 action 分支。

```ts
switch (action.type) {
  case 'none': break;
  case 'warn': {
    queueContextHint(cKey, buildContextManagementHint({

      compressionCount: activeRecord?.compressionCount ?? 0,

  }
  case 'seal':
  case 'seal_after_compress': { /* 见下 */ }
  case 'allow_compress':
    outputs.push({ type: 'system_info', catId, content: JSON.stringify({
      type: 'strategy_allow_compress', catId, strategy: strategy.strategy,
      compressionCount: activeRecord?.compressionCount ?? 0, healthSnapshot: health }), timestamp: Date.now() });
    break;
}
```

`warn` 分支的注释是本篇最有信息量的一段之一：

> 「A system_info output would never reach the cat (routing feeds only `text` into previousResponses; ContextAssembler drops userId='system') — so we ride the prompt-injection channel (consumed at effectivePrompt assembly)。cKey matches the compressionKey used there: `${userId}:${catId}:${threadId}`。」

翻译：**`system_info` 是给人/前端看的，猫看不到**。要让猫知道「上下文快满了」，必须走 prompt 注入通道。这是云端 review 纠正过的一个真实错误。

### 3.4 第四段：`requestSeal()` —— CAS 那 20 行

```ts
async requestSeal(args: { sessionId: string; reason: SealReason }): Promise<SealResult> {
  const record = await this.store.get(args.sessionId);
  if (!record) return { accepted: false, status: 'sealed' };

  // CAS: only active sessions can be sealed
  // Snapshot status before mutation (memory store returns live reference)
  const currentStatus: SessionStatus = record.status;
  if (currentStatus !== 'active') return { accepted: false, status: currentStatus };

  const now = Date.now();
  const updated = await this.store.update(args.sessionId, { status: 'sealing', sealReason: args.reason, updatedAt: now });

  if (!updated || updated.status !== 'sealing') {
    // Race condition: another caller got there first
    return { accepted: false, status: updated?.status ?? 'sealed' };
  }
  log.info({ sessionId, catId, threadId, reason }, 'session seal requested');
  getEventAuditLog().append({ type: AuditEventTypes.SEAL_REQUESTED, threadId, data: {...} }).catch(() => {});
  return { accepted: true, status: 'sealing', sessionId: args.sessionId };
}
```

**四个必须讲清楚的细节**：

1. **`const currentStatus = record.status` 是拷贝快照，不是多余的行。** 注释明写「memory store returns live reference」——内存 store 的 `get()` 返回的是 Map 里那个对象本身，后面 `update()` 会原地改它。如果直接在 `update` 之后读 `record.status`，读到的是改后的值，判断就永远成立。这是**内存实现和 Redis 实现语义差异**逼出来的防御。
2. **双重检查**：进去前查一次 `!== 'active'`，`update` 回来再验一次 `=== 'sealing'`。
3. **幂等契约**：接口注释「Idempotent: returns accepted=false if already sealing/sealed」。记录不存在时返回 `{accepted:false, status:'sealed'}` —— 把「查无此人」当成「已经封好了」，让调用方不用区分两种失败。
4. **审计写入是 `.catch(() => {})`**：审计不能阻塞状态机。

**这个 CAS 是真 CAS 吗？**（可以主动抛出来当加分点）
不是硬件级 CAS。内存实现是单线程 Node，`get`→判断→`update` 之间没有 await 让出点吗？其实 `await this.store.get()` 有 await，Redis 实现下确实存在窗口。但 `update` 后的二次校验 + `getActive()` 读时再验 status 兜住了大部分。**真正做了原子保证的是 `incrementCompressionCount()`**（Lua 脚本），因为那条是高频并发路径（多个 hook 同时打）。

### 3.5 第五段：`finalize()` 的完整产出链

`finalize()` 本身是「壳」，真正干活的是私有的 `doFinalize()`，壳负责超时和终态：

```ts
async finalize(args: { sessionId: string }): Promise<void> {
  const record = await this.store.get(args.sessionId);
  if (!record) return;
  if (record.status !== 'sealing') return;          // 只处理 sealing
  const now = Date.now();

  let finalizeClean = false;
  try { finalizeClean = await withTimeout(this.doFinalize(record, now), FINALIZE_TIMEOUT_MS); }
  catch (err) { /* 写 SEAL_FINALIZE_FAILED 审计 */ }

  // Always attempt terminal transition — even if doFinalize failed/timed out.
  let sealWriteSucceeded = false;
  try {
    await this.store.update(args.sessionId, { status: 'sealed', sealedAt: now, updatedAt: now });
    sealWriteSucceeded = true;
    log.info({ ..., partial: !finalizeClean },
      finalizeClean ? 'session seal finalized' : 'session seal finalized (partial — transcript/digest may be missing)');
    if (finalizeClean) { /* 只有干净时才发 SEAL_FINALIZED */ }
  } catch (err) { /* 写 phase: 'terminal_update' 的失败审计 */ }

  if (sealWriteSucceeded && this.postSealHooks.length > 0) { /* 逐个 await，各自 try/catch */ }
}
```

**核心设计句（【源码】原注释，值得背下来）**：

> 「A sealed session with missing transcript is recoverable; a stuck sealing session is not.」

一条缺 transcript 的 sealed 记录还能救（重读 events.live.jsonl、人工 unseal）；一条卡在 sealing 的记录会**永远占着位子又不给用**——active 指针已清（不能再写），status 又不是 sealed（bootstrap 逻辑里 sealing 被当成可用，但 reaper 会一直盯着它）。所以**终态转换必须无条件尝试**。

`withTimeout` 的实现（文件底部）就是标准的 `Promise` + `setTimeout` 竞速，成功/失败两条路都 `clearTimeout`：

```ts
function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => reject(new Error(`finalize timed out after ${ms}ms`)), ms);
    promise.then((v) => { clearTimeout(timer); resolve(v); },
                 (e) => { clearTimeout(timer); reject(e); });
  });
}
```

**主体流程**：

**分支 1 — `compress`：永不封存，只记数**
```ts

                    ...(updated ? { continuity: compactContinuityFor(updated) } : {}) });
```

**分支 2 — `hybrid`：先自增再比**
```ts
const max = strategy.hybrid?.maxCompressions ?? 2;
const newCount = await sessionChainStore.incrementCompressionCount(record.id);
if (newCount == null) { reply.status(409); ... }
if (newCount <= max) { return reply.send({ action: 'compress_allowed', ..., maxCompressions: max, strategy: 'hybrid', ... }); }
// At or over max → 落到下面的封存路径
```
注释点名这是 **P1 fix**：「Atomic increment-then-check: avoids TOCTOU race on concurrent hook calls」。**先增后判，不是先判后增**——两个 hook 同时来，先读再写会都读到 1、都判「还没到上限」、最后计数只到 2；先增后判则一个拿到 2、一个拿到 3，第二个正确触发封存。

**分支 3 — `handoff`（或 hybrid 超限）：真封**
```ts
const sealReason = strategy.strategy === 'hybrid' ? 'max_compressions' : reason;
const sealResult = await sessionSealer.requestSeal({ sessionId: record.id, reason: sealReason });
if (!sealResult.accepted) { reply.status(409); return { error: 'Seal request not accepted (race condition)', sessionId, status: sealResult.status }; }
sessionSealer.finalize({ sessionId: record.id }).catch(() => {});   // fire-and-forget
return reply.send({ sessionId, threadId, catId, status: 'sealing' });
```
**hybrid 超限时用 `'max_compressions'` 覆盖 hook 传来的 reason** —— 让审计里能看出「不是阈值触发，是压缩次数用尽」。

**409 的三个来源**（面试常追）：① 进门时 `status !== 'active'`；② 原子自增返回 null（记录消失/状态漂移）；③ `requestSeal` 未被接受。

**`compactContinuityFor()` 的作用**：
```ts
function compactContinuityFor(record: SessionRecord) {
  const capsule = completeCapsuleForCompact(record.continuityCapsule, { createdAt: Date.now() });
  if (!capsule) return undefined;
  return { capsule, diagnostics: { source: 'active_session_route_state', boundary: 'compact_boundary',
           generated: true, threadId, catId, sessionId: record.id, compressionCount: record.compressionCount ?? 0 } };
}
```
把存在 SessionRecord 上的**半成品**胶囊补成成品（`continuationReason: 'compact_boundary'`），随响应回给 hook，让「压缩后」也能带上协作控制流状态。

### 3.12 源码执行复盘：从 `session_init` 到封板和下一任会话

会话链最容易被理解成“保存一个 sessionId”。真实实现复杂得多，因为它要解决：旧 CLI 会话何时停止使用、摘要何时生成、旧会话卡在 sealing 怎么恢复、下一任会话如何继承上下文。

#### 1. `session_init`：建立业务会话与运行时会话的绑定

Provider 发出 `session_init` 后，`invokeSingleCat()` 会把 CLI 给出的 runtime/session ID 写回业务侧 `SessionRecord`。此时至少要同时确认：

- 这是新 session 还是已有记录的 runtime 更新；
- catId、threadId、工作目录指纹是否匹配；
- 旧 runtime 是否发生异常切换；
- continuity capsule、route state 等是否需要一起保存。

所以 `session_init` 不是给前端看的普通消息，而是生命周期事件。测试 `invoke-single-cat.test.js` 覆盖“首次创建 SessionRecord”“已有 active 记录更新 cliSessionId”“ACP ephemeralSession 切换时不封旧会话”等分支。

#### 2. transcript 持续增长，但不会每条消息都封板

运行期间，TranscriptWriter 把可用于后续摘要和恢复的内容写入对应会话。系统根据上下文使用率、恢复失败次数、runtime 旋转、用户/错误原因等判断是否触发 seal。

这里必须区分：

- 达到阈值：说明“应该计划封板”；
- `requestSeal()` 成功：说明 active → sealing 的状态所有权已取得；
- `finalizeSeal()` 完成：说明摘要/记忆处理和终态写入结束；
- 新会话建立：说明 successor 已接棒。

不能把这四步写成一个布尔值，否则并发请求可能同时封同一会话。

#### 3. `requestSeal()` 是 CAS 风格的抢占

两次调用可能同时发现上下文超阈值：

```text
调用 X：读取 active
调用 Y：读取 active
调用 X：请求封板成功，状态变 sealing
调用 Y：再次请求时发现已 sealing，accepted=false
```

`accepted=false` 不一定是错误，可能代表另一个 worker 已经接手。`session-sealer.test.js` 验证 active 会话可进入 sealing，已经 sealing/sealed 的会话不会再次接受，且 active pointer 会被清除。

#### 4. `finalizeSeal()` 是可降级的长流程

finalize 可能读取 transcript、生成 extractive digest、提取 decision/signal、更新 ThreadMemory、写 sealedAt。这里有两个重要设计：

1. 摘要或 ThreadMemory 失败，不应让会话永远卡在 sealing；
2. 终态写入失败时，不能假装 hook 已成功完成。

`session-sealer-thread-memory.test.js` 验证 ThreadMemory 更新失败仍能 seal，动态 token cap 生效，decision 提取可写入 thread memory；`session-sealer.test.js` 验证 finalize 挂起或最终 update 抛错时仍有 force-seal/回收策略，而且 hook 只在终态写成功后触发。

#### 5. stuck sealing 的 reaper 是故障恢复，不是正常主流程

如果进程在 active → sealing 后崩溃，新进程看到的会话会一直是 sealing。`reconcileStuck()` 根据状态年龄找出卡住记录并 force-seal。测试覆盖：超过 maxAge 才处理、年轻 sealing 不动、active/sealed 不动、可跨多猫多线程回收。

这体现后端持久化状态机的一条原则：**每个中间态都要有超时或重入恢复办法。** 只设计 happy path 的状态机，一旦进程在中间崩溃就无法自愈。

#### 6. successor/bootstrap：新会话如何知道旧会话做过什么

新 CLI session 不能直接继承旧进程内存，因此项目把旧会话整理成受控的 continuity/bootstrap 内容：最新会话优先，祖先 ID 只做短上下文，旧摘要按 token budget 截断，并把历史摘要当作“不可信数据”引用，先放 injection guard 再放摘录。

`antigravity-continuity-bootstrap.test.js` 覆盖：控制块位于首次 effective prompt 之前、总预算默认不超过约 2k 估算 token、A→B→C 旋转顺序、旧摘要中的分隔符要转义、注入防护必须在摘录前。

#### 面试时用一句话串起来

**SessionRecord 是业务会话状态机，CLI sessionId 只是其中一个运行时字段；封板采用 active → sealing → sealed 的可恢复流程，通过 CAS/幂等避免重复封板，通过 reaper 修复中间态，再用受预算和注入防护约束的 continuity bootstrap 把必要上下文交给 successor。**

### 4.1 封存状态机全图

```
                       ┌─────────────────────────────────────────┐
                       │            (不存在)                      │
                       │   requestSeal → {accepted:false,        │
                       │                  status:'sealed'}       │
                       └─────────────────────────────────────────┘

   create()                requestSeal()               finalize()
      │                    CAS: status==='active'      status==='sealing'
      v                          │                          │
  ┌────────┐                     v                          v
  │ active │────────────────>┌─────────┐──────────────>┌────────┐
  └────────┘                 │ sealing │               │ sealed │
      ^                      └─────────┘               └────────┘
      │                          │  ^                       ^
      │  unseal（新建记录，       │  │ update 失败            │
      │  不是改回 active）        │  │ → 留在 sealing         │
      │                          │  └────────────────────────┘
      │                          │      reconcileStuck / reconcileAllStuck
      │                          │      条件: now - (updatedAt ?? createdAt) > maxAgeMs
      │                          │      sealReason ← 'reconcile_stuck' | 'global_reaper'
      │                          v
      └──── ExternalRuntimeSessionRegistration 的
            reopenFailedExternalRegistrationSessionRecord()
            仅当 sealReason === 'external_registration_failed'
            update({status:'active', sealReason:null, sealedAt:null})
```

**逐步骤 + 失败处理**：

| # | 步骤 | 成功 | 失败怎么办 |
|---|---|---|---|
| 1 | `store.get(id)` | 拿到记录 | 记录不存在 → 返回 `{accepted:false, status:'sealed'}`（当已封） |
| 2 | 快照 `currentStatus = record.status` | — | — |
| 3 | 判 `currentStatus !== 'active'` | 继续 | 返回 `{accepted:false, status: currentStatus}` |
| 4 | `update({status:'sealing', sealReason, updatedAt})` | — | 返回 null → `{accepted:false, status:'sealed'}` |
| 5 | 二次校验 `updated.status === 'sealing'` | 记 log + 审计 `SEAL_REQUESTED` | 竞态 → `{accepted:false, status: updated.status}` |
| 6 | `finalize()` 进门判 `status === 'sealing'` | 继续 | 直接 return（幂等，不报错） |
| 7 | `withTimeout(doFinalize, 30s)` | `clean=true` | 超时/抛错 → `clean=false` + 审计 `SEAL_FINALIZE_FAILED` |
| 8 | `update({status:'sealed', sealedAt, updatedAt})` | `sealWriteSucceeded=true` | 抛错 → 审计 `phase:'terminal_update'`，**记录留在 sealing**，等 reaper |
| 9 | 发 `SEAL_FINALIZED` 审计 | 仅当 `finalizeClean` | 不干净就只打 partial 日志，不发审计 |
| 10 | 逐个 `await hook(hookEvent)` | — | 每个 hook 独立 try/catch，只 `log.warn` |

**两个 reaper 的差异**：

| | `reconcileStuck(catId, threadId, maxAgeMs=5min)` | `reconcileAllStuck(maxAgeMs=5min)` |
|---|---|---|
| 扫描范围 | `store.getChain(catId, threadId)` 一条链 | `store.listSealingSessions()` 全库 |
| 触发时机 | per-invoke 懒扫描 | 启动时一次 + `setInterval` 5 分钟 |
| sealReason | `'reconcile_stuck'` | `'global_reaper'` |
| 二次校验 | 循环里判 `s.status === 'sealing'` | 先 `get(id)` 再判 `!s \|\| s.status !== 'sealing'` → continue |
| 审计事件 | `SEAL_FINALIZE_FAILED` + `phase:'reconcile_stuck'` | 同类型 + `phase:'global_reaper'` |
| 触发 postSealHook | ❌ 故意不触发 | ❌ 故意不触发 |

`reconcileAllStuck` 存在的理由（注释）：「catch orphaned sealing sessions that would never be visited by per-invoke lazy scanning」——一个线程如果之后再没人说话，懒扫描永远轮不到它。

`listSealingSessions()` 的 Redis 实现值得看一眼：`scanKeys('session:*')` 拿全部详情 key，然后**分批 50 条**走 pipeline `HMGET key id status`，只挑 `status === 'sealing'` 的 id。分批是为了不让 pipeline 无限膨胀。

### 4.2 `shouldTakeAction()` 决策表（`config/session-strategy.ts`）

输入：`(fillRatio, windowTokens, usedTokens, compressionCount, strategy)`。

```
turnBudget   = strategy.turnBudget   ?? 12_000
safetyMargin = strategy.safetyMargin ?? 4_000
remaining    = windowTokens - usedTokens
```

**第一层：预算是否耗尽（优先级最高，先于阈值判断）**

| 条件 | strategy | 返回 |
|---|---|---|
| `remaining < turnBudget + safetyMargin` | `compress` | `{type:'allow_compress'}` |
| 同上 | `hybrid` 且 `compressionCount < max` | `{type:'allow_compress'}` |
| 同上 | `hybrid` 且 `compressionCount >= max` | `{type:'seal', reason:'budget_exhausted'}` |
| 同上 | `handoff` | `{type:'seal', reason:'budget_exhausted'}` |

**第二层：低于 action 阈值**

| 条件 | 返回 |
|---|---|
| `fillRatio < thresholds.action` 且 `fillRatio >= thresholds.warn` | `{type:'warn'}` |
| `fillRatio < thresholds.warn` | `{type:'none'}` |

**第三层：达到/超过 action 阈值，按策略分叉**

| strategy | 返回 |
|---|---|
| `handoff` | `{type:'seal', reason:'threshold'}` |
| `compress` | `{type:'allow_compress'}` |
| `hybrid` 且 `compressionCount >= max` | `{type:'seal_after_compress', reason:'max_compressions'}` |
| `hybrid` 且 `compressionCount < max` | `{type:'allow_compress'}` |

`max = strategy.hybrid?.maxCompressions ?? 2`（三处都是这个默认值：`shouldTakeAction` 两处 + hook route 一处）。

**为什么「预算耗尽」要先判**：fillRatio 是比值，可能因为窗口大而看着不高；但「这一轮再塞 12000 token 就爆了」是绝对量问题。两个轴分开判，绝对量优先。

同文件还留了两个 `@deprecated` 的向后兼容函数：`getSealConfig(catName)`（转成 `ContextHealthConfig`）和 `shouldSeal(fillRatio, windowTokens, usedTokens, config)`（返回 boolean）。注释说明是「Kept for existing tests during migration」。

### 4.3 `flush()` 的合并 + 内容去重算法

**问题**：进程重启后，内存 buffer 空了，但 `events.live.jsonl` 有重启前的事件；重启后又新写了一些（同时也追加到了 live 文件，但追加是 best-effort 可能失败）。怎么合出一份完整、不重复、顺序正确的 events.jsonl？

**算法（编号步骤）**：

1. `buf = this.buffers.get(sessionId) ?? []`
2. `await this.drainPendingWrites(sessionId)` —— 等这个 session 的磁盘写队列排空，否则读到半截文件
3. `liveEvents = await this.readEventsFromLiveFile(sessionDir)` —— 逐行 JSON.parse，坏行跳过
4. 若 `liveEvents.length > 0`：
   a. 给 buffer 每条算指纹：`` `${e.timestamp}:${JSON.stringify(e.event)}` ``，塞进 `bufKeys: Set`
   b. `diskOnly = liveEvents.filter(e => !bufKeys.has(指纹(e)))` —— 磁盘独有的（= 重启前的）
   c. `buf = [...diskOnly, ...buf]` —— **磁盘的在前，内存的在后**
   d. 重编号：`for (let i=0;i<buf.length;i++) buf[i] = { ...buf[i], eventNo: i }`
   e. `this.buffers.set(sessionId, buf)` —— 写回，让后面的 `generateExtractiveDigest()` 能读到合并结果
5. `if (buf.length === 0) return;` —— 空就啥也不写（**不会创建空目录/空文件**）
6. `mkdir(sessionDir, {recursive:true})`
7. 遍历 buf 写 `events.jsonl`，同时按 `eventNo % indexStride === 0` 收集 offsets
8. 写 `index.json`
9. 若给了 `sealTimestamps` → `generateExtractiveDigest()` 写 `digest.extractive.json`
10. `this.buffers.delete(sessionId)` + `this.diskWriteQueue.delete(sessionId)`
11. `await unlink(join(sessionDir,'events.live.jsonl')).catch(() => {})`

**为什么是「合并」不是「磁盘覆盖内存」**（注释原文）：

> 「The buffer is authoritative for post-restart events — it may include events whose disk append silently failed (enqueueDiskAppend is best-effort, catch swallows errors). This also covers the zero-post-restart seal case: buffer is empty but events.live.jsonl has all pre-restart events.」

**指纹的选择**：`timestamp + JSON.stringify(event)`。不用 eventNo，因为重启后 eventNo 从 0 重新开始，会撞。**坑**：同一毫秒内两条完全相同的事件会被误判为重复而丢一条。【推断：实际概率极低，且丢一条重复事件无害，所以没有额外加序号】

**`capHandoffNoteToBudget()` 的收敛循环**（这是任务点名要的）：
```ts
function capHandoffNoteToBudget(section: string, maxTokens: number): string {
  if (!section || estimateTokens(section) <= maxTokens) return section;
  const suffix = `\n…[handoff note truncated to fit bootstrap budget]\n${HANDOFF_NOTE_MARKER_CLOSE}`;
  let body = section.endsWith(HANDOFF_NOTE_MARKER_CLOSE) ? section.slice(0, -HANDOFF_NOTE_MARKER_CLOSE.length) : section;
  while (body.length > 0 && estimateTokens(body + suffix) > maxTokens) {
    body = body.slice(0, Math.floor(body.length * 0.9));
  }
  return body.trimEnd() + suffix;
}
```
**四个可复述要点**：
1. 先摘掉尾部 close marker，最后再拼回去（保证截断后 marker 还在，围栏不破）。
2. **每次砍 10% 长度**（`* 0.9`），不是二分，也不是砍固定字符数。CJK 场景下字符数和 token 数比例不定，乘性衰减最省事。
3. 循环条件带 `body.length > 0` 防死循环（`Math.floor(1 * 0.9) === 0`，所以最终必然到 0 退出）。
4. `estimateTokens` 是**真 tokenizer**（`utils/token-counter.ts` 用 tiktoken 的 `encode()`），不是 `length/4` 估算——注释里强调「Token-accurate (CJK-safe) shrink」。

**为什么必须在这里截而不是靠后面 drop**（注释原文）：
> 「Because the note lives in baseTokens (no later section left to drop once remainingBudget is negative), truncate it HERE so identity + note + tools can never breach the hard cap.」
> 以及：「for CJK notes 600 chars ≈ ~900 tokens, so done+next+gotchas alone can exceed MAX_BOOTSTRAP_TOKENS」

三个字段各 600 字符 ≈ 2700 token > 2000 硬顶。per-field 的 `MAX_NOTE_FIELD_CHARS` 只管单字段，管不住总量，所以要再来一道聚合限额。

### 4.5 extractive digest 的噪声聚合算法

**目的**：一个 session 里 `context canceled` 可能刷屏几十条，不能让 errors 数组被它淹没。

**分类器**（`classifyDigestNoise(message)`，按顺序试）：

| 正则 | kind |
|---|---|
| `/context cancell?ed/i` | `context_canceled` |
| `/\bmcp\b/i` **且** `/refus\|status:\s*refused/i` | `mcp_refused` |
| `/cancell?ed step\|step .* cancell?ed\|user_cancel/i` | `canceled_step` |
| 都不匹配 | `null` → 当普通 error |

（`cancell?ed` 同时匹配美式 `canceled` 和英式 `cancelled`。）

**分组规则**（`recordDigestErrorOrNoise`）：
```ts
const latest = noiseGroups.at(-1);
const group = latest && latest.kind === kind && !latest.recovered
              && noiseGroupMatchesInvocation(latest, error.invocationId)
              ? latest : 新建;
if (group.count === 0) noiseGroups.push(group);
group.count += 1; group.lastAt = error.at; group.errors.push(error);
if (error.invocationId) group.invocationIds.add(error.invocationId);
```
只跟**最后一个** group 比（连续段聚合），三个条件全中才归并：同 kind、未标记 recovered、invocation 匹配。

`noiseGroupMatchesInvocation(group, invocationId)`：
- 无 invocationId → 要求 `group.invocationIds.size === 0`
- 有 → 要求 `size === 1 && has(invocationId)`

**恢复标记**（`markDigestNoiseRecovered`）：每当出现一条**可见的 assistant 文本**，就把所有满足 `!recovered && group.lastAt <= recoveredAt && noiseGroupCanRecoverFromInvocation(...)` 的 group 标成 recovered。
`noiseGroupCanRecoverFromInvocation`：`invocationIds.size === 0` 直接 true；否则要求 `invocationId !== undefined && invocationIds.has(invocationId)`。

**收尾**（`finalizeDigestNoise`）：
```
for each group:
  if group.count < 2:        errors.push(...group.errors)    // 太少，不算噪声，还原成普通 error
  else:
    outcome = group.recovered ? 'recovered' : 'terminal'
    summaries.push({kind,count,sample,invocationIds:[...],firstAt,lastAt,outcome})
    if outcome === 'terminal': errors.push(group.errors[0])  // 保留一条代表
errors.sort((l,r) => l.order - r.order)                      // 按原始 eventNo 恢复时序
```
最后 `digestErrors = errors.map(({order: _order, ...error}) => error)` 把内部排序键 `order` 剥掉。

**一句话总结**：**≥2 条同类连续噪声 → 折叠成一条 summary；恢复了就只留 summary，没恢复就额外保留第一条原始错误。**

### 4.6 `recentMessages` 的流式合并（coalesce）

流式输出会把一句话拆成很多 `text` 事件。digest 里不能存 200 条碎片。

```ts
const streamKey = evtType === 'text' && entry.invocationId !== undefined
  ? `${entry.invocationId}:${typeof evt.catId === 'string' ? evt.catId : session.catId}` : null;
const visibleText = extractVisibleAssistantText(evt, { trim: streamKey === null });
```
**注意 `trim` 参数**：流式片段 **不 trim**（`trim: false`），否则拼接时词间空格会被吃掉；非流式整条才 trim。

合并逻辑：
```ts
if (streamKey) {
  const existing = recentMessageByStream.get(streamKey);
  if (existing && recentMessages[recentMessages.length - 1] === existing) {   // 必须还是「最后一条」
    const content = normalizeVisibleText(coalesceVisibleText(existing.content, visibleText, evt.textMode), { trim: false });
    if (content) { existing.content = content.slice(0, 1200); moveToEnd(recentMessages, existing); }
    else { removeItem(recentMessages, existing); recentMessageByStream.delete(streamKey); }
  } else { /* 新建一条 push 进去，并登记到 recentMessageByStream */ }
} else { recentMessages.push({ role:'assistant', invocationId?, content: visibleText.slice(0,1200) }); }
```
`coalesceVisibleText(existing, next, textMode)`：`textMode === 'replace'` → 返回 `next`（整块替换语义）；否则 `existing + next`（追加）。

**`recentMessages[last] === existing` 这个身份比较**是关键：只有当这条消息**还在数组末尾**（中间没插入别的猫/别的 invocation 的消息）才继续追加，否则另起一条。这样交错流式不会串。

最终 `recentMessages: recentMessages.slice(-5)` —— 只留最后 5 条，每条 ≤1200 字符。

### 4.7 CollaborationContinuityCapsule 的两阶段构造

**阶段一（路由层，半成品）** —— `buildCapsuleFromRouteState(input)`：
- 固定写死 `ballState: 'in_progress'`、`continuationReason: 'threshold_seal'`
- **不填** `invocationId` / `createdAt` / `seal`
- 返回类型 `RouteStateContinuityCapsule = Omit<CollaborationContinuityCapsuleV1, 'invocationId'|'createdAt'|'seal'>`
- 所有可选字段用 `...(x ? {x} : {})` 展开——**exactOptionalPropertyTypes 友好**，不产生 `key: undefined`

**阶段二 A（封存点，成品）** —— `completeCapsuleForSeal(capsule, completion)`：
```ts

  ...(completion.invocationId ? { invocationId: completion.invocationId } : {}),
```

**阶段二 B（压缩边界，成品）** —— `completeCapsuleForCompact(capsule, completion)`：
```ts

```
**没有 `seal` 字段**——压缩不是封存。

| 检查项 | `isCollaborationContinuityCapsuleV1` | `isRouteStateContinuityCapsule` |
|---|---|---|
| `isRecord(value)`（对象且非数组） | ✔ | ✔ |

**精髓**：两个守卫**互斥**——半成品守卫显式要求那三个字段**不存在**。所以你不能把成品当半成品用（`completeCapsuleForCompact` 会拒绝一个已经完成过的胶囊），杜绝了「二次完成」污染。

### 4.10 Session Strategy 的六级查找

**优先级（`getSessionStrategyWithSource()`）**：

```
1. 测试覆盖 _testOverrides.get(catName)        → source: 'runtime_override'（直接返回，不做 provider 校验！）
2. 先算完整 fallback 链（下面 3~6）
3. runtime override（Redis）→ mergeStrategyConfig(fallback, override) → validateProviderCapability
4. 配置文件 getConfigSessionStrategy(catName)  → source: 'config_file'
5. STRATEGY_BY_BREED[breedId] ?? STRATEGY_BY_BREED[catName] → source: 'breed_code'
6. DEFAULT_STRATEGY_BY_PROVIDER[clientId]      → source: 'provider_default'
7. GLOBAL_DEFAULT_STRATEGY                      → source: 'global_default'
```

（源码头注释自己数的「六级」**已经包含测试覆盖**：`test override → runtime override → resolved cat config (breed) → STRATEGY_BY_BREED → provider default → global default`。而 `StrategySource` 联合类型只有 5 个值，因为测试覆盖复用 `'runtime_override'`。上面表里的第 2 步不是一层，只是实现顺序。）

**关键设计：runtime override 是「叠加」不是「替换」**
```ts
const fallback = resolveFallbackStrategy(catName);
const runtimeOverride = getRuntimeOverride(catName);
if (runtimeOverride) {
  const merged = mergeStrategyConfig(fallback.effective, runtimeOverride);
  return { effective: validateProviderCapability(merged, catName), source: 'runtime_override' };
}
```
注释：「Runtime override layers ON TOP of the resolved fallback, so partial runtime overrides preserve lower-layer values.」你在 UI 上只改了 `thresholds.action`，`thresholds.warn` 和 `turnBudget` 都保留。

**`mergeStrategyConfig()` 的嵌套合并**：
```ts
return {
  ...base, ...override,
  thresholds: { ...base.thresholds, ...override.thresholds },
  ...(override.handoff || base.handoff ? { handoff: { ...base.handoff, ...override.handoff } } : {}),
  ...(override.compress || base.compress ? { compress: { ...base.compress, ...override.compress } } : {}),
  ...(override.hybrid || base.hybrid ? { hybrid: { ...base.hybrid, ...override.hybrid } } : {}),
} as SessionStrategyConfig;
```
`thresholds` 无条件合并（必填），其余三个只在任一侧存在时才产出键（避免造出空对象）。

**provider 能力守卫**：
```ts
const HOOK_CAPABLE_PROVIDERS = new Set(['anthropic']);
```

`STRATEGY_BY_BREED` 目前**全是注释掉的示例**，实际是空对象。

**runtime override 的持久化**（`config/session-strategy-overrides.ts`）：
- 模块级两个变量：`let _redis: RedisClient | undefined` + `const _cache = new Map<string, Partial<SessionStrategyConfig>>()`
- `initRuntimeOverrides(redis)` 启动时调一次 → `hydrateFromRedis()`
- `setRuntimeOverride`：**写 Redis 成功后**才写 cache（注释 P1-3：「no cache split on Redis failure」）
- `deleteRuntimeOverride`：**Redis DEL 的返回值是存在性的真相源**，只有没 Redis 时才退回查 cache
- `getRuntimeOverride` / `getAllRuntimeOverrides`：纯读 cache，**同步**——这就是为什么整条 `getSessionStrategy()` 能保持同步

**`hydrateFromRedis()` 的两个讲究**：
```ts
const prefix = (_redis.options as { keyPrefix?: string }).keyPrefix ?? '';
const barePattern = SessionStrategyKeys.override('*');            // 'session-strategy:override:*'
const matchPattern = `${prefix}${barePattern}`;
const keyPrefix = `${prefix}session-strategy:override:`;
const tempCache = new Map(...);                                    // ① 先写临时 map
let cursor = '0';
do {
  const [nextCursor, keys] = await _redis.scan(cursor, 'MATCH', matchPattern, 'COUNT', 100);
  cursor = nextCursor;
  for (const key of keys) {
    const bareKey = prefix && key.startsWith(prefix) ? key.slice(prefix.length) : key;
    const raw = await _redis.get(bareKey);
    if (raw) { const catId = key.slice(keyPrefix.length); try { tempCache.set(catId, JSON.parse(raw)); } catch { log.warn({key}, 'invalid JSON in Redis key, skipping'); } }
  }
} while (cursor !== '0');
_cache.clear(); for (const [k,v] of tempCache) _cache.set(k,v);     // ② 原子换入
```
① **临时 map + 全成功才换入**：SCAN 中途失败的话 `_cache` 保持空（干净降级），而不是留一份「少了几条」的部分数据——后者会静默丢覆盖。
② **`_cache.clear()` 再灌**，不是 append：这样 Redis 里被删掉的 key 不会在内存里阴魂不散。
③ 注意 `catId` 是从**带前缀的 key** 上用**带前缀的 keyPrefix** 切的，而 `get()` 用的是**剥了前缀的 bareKey**——两条路径分别对应「scan 不自动加前缀」和「get 自动加前缀」。

### 4.11 猫主动接力：propose 的三重防刷 + approve 的 commit-point

**`proposeSessionHandoff(deps, input)` 五步**：

| 步 | 检查 | 失败返回 |
|---|---|---|
| 1 | `active = await sessionChainStore.getActive(sourceCatId, sourceThreadId)` | `{ok:false, reason:'no_active_session'}` |
| 2 | `store.listActiveBySession(active.id)` 非空？（≤1 pending\|approving） | `'already_pending'` |
| 3 | `recent = getMostRecentByCatThread(userId, catId, threadId)`；`Math.max(0, now()-recent.createdAt) < cooldownMs`（默认 5 分钟） | `'cooldown'` |
| 4 | `countRecentByCatThread(userId, catId, threadId, now()-hourlyWindowMs) >= hourlyLimit`（默认 1 小时 / 5 次） | `'hourly_limit'` |
| 5 | `store.create({...})` | `{ok:true, proposal}` |

**要点**：
- **session 是从 `getActive()` 查出来的，不信调用方传的**。注释：「so a cat can only propose handing off the session it is actually running in」。
- `Math.max(0, now() - recent.createdAt)` 里的 clamp 有注释解释：「the store's monotonic createdAt (P1-3) can sit a few ms ahead of wall-clock now() under same-ms bursts」——store 用了单调递增时间戳，可能略超前于 `Date.now()`，不 clamp 会算出负数从而绕过 cooldown。
- 为什么 cooldown 之外还要 hourly cap：注释「cooldown alone lets ~12 cards/hour slip through at the 5-min default」。

`buildHandoffProposalCardBlock(proposal)` 生成确认卡：`id: 'handoff-<proposalId>'`、`kind: 'card'`、`tone: 'info'`、fields 依次是「封印 session / 已完成 / 下一步 / worktree? / commits? / gotchas?」、actions 两个 `handoff:approve` 与 `handoff:reject`。

**`approveSessionHandoff(deps, proposalId)` 的 commit-point 模型**：

```
── Pre-commit（可以安全 expire，没有不可逆副作用）──
 step 1  claimed = await store.claimForApproval(proposalId)          // CAS pending→approving
         失败 → {ok:false, stage:'pre-commit', reason:'not_pending'}
 step 2  session = get(claimed.sourceSessionId); active = getActive(catId, threadId)
         stillActive = session?.status === 'active'
                    && active?.id === claimed.sourceSessionId
                    && session.userId === claimed.userId       ← 三条同时成立
         不成立 → markExpired + reason:'session_changed'
 step 3  update(sourceSessionId, { catHandoffNote: claimed.note })
         recordCheckpoint({ handoffNotePersistedAt: now() })

══ COMMIT POINT ══
 seal = await deps.requestSeal(sourceSessionId, 'cat_initiated_handoff')
 若 !seal.accepted → 仍属 pre-commit → markExpired + reason:'seal_rejected'
 若 accepted → recordCheckpoint({ sealedSessionId, sealAcceptedAt: now() })

── Post-commit（只 recover-forward，失败就 throw 让恢复流程接手）──
 cont = await deps.enqueueContinuation({ proposalId, sourceSessionId, threadId, catId, note })
 recordCheckpoint({ continuationEntryId: cont.entryId })
 finalized = await store.finalizeApproval(proposalId)
 return { ok:true, proposal: finalized ?? (await store.get(proposalId))! }
```

`ApproveResult` 的失败分支**只有 `stage:'pre-commit'`**——类型系统层面就表达了「过了 commit point 就不可能返回失败」。

**注意 step 3 的顺序**：note 先持久化，**再** requestSeal。注释叫「commit-point 反推 key (KD-9)」——因为 note 里带 `proposalId`，崩溃后可以从 session 侧反查出「这次封存是不是这个 proposal 干的」。

**崩溃恢复 `recoverStaleHandoffProposal()`**：

```
1. proposal = get(proposalId)；status !== 'approving' → {recovered:false, reason:'not_approving'}
2. if (!proposal.sealedSessionId)  // commit checkpoint 缺失 → 必须查 session 侧
     session = sessionChainStore.get(proposal.sourceSessionId)
     sealedByThisHandoff = !!session
                        && (session.status === 'sealing' || session.status === 'sealed')
                        && session.sealReason === 'cat_initiated_handoff'
                        && session.catHandoffNote?.proposalId === proposalId
     if (sealedByThisHandoff)  → 回填 checkpoint（handoffNotePersistedAt ?? now, sealedSessionId, sealAcceptedAt）
     else                      → markExpired → {recovered:true, outcome:'expired'}
3. if (sealedSessionId && status==='approving') → 重新 enqueueContinuation + recordCheckpoint
4. if (sealedSessionId && status==='approving') → finalizeApproval
5. return {recovered:true, outcome:'completed'}
```

**为什么必须查 session 侧**（注释原文，这是整段最精彩的部分）：
> 「The commit point (session-side `requestSeal` → sealing) and the proposal-side checkpoint (sealedSessionId) are two SEPARATE writes; a crash between them leaves an 'approving' proposal with handoffNotePersistedAt but no sealedSessionId. We CANNOT judge pre-commit from the proposal alone — must cross-check the session side.」

**四条判定同时成立**才算「确实是这次 handoff 封的」：session 存在、状态是 sealing/sealed、sealReason 是 `cat_initiated_handoff`、note 里的 proposalId 对得上。少任何一条都可能是别的原因封的，不能认。

重新 enqueue 为什么安全：注释「InvocationQueue itself is process-local; after a process crash the old entry id is only diagnostic. Re-enqueueing is safe because enqueueContinuation is keyed by proposalId and dedupes any still-active entry.」

**stale note 为什么不会泄漏**：即使 approve 失败、note 已经写在 session 上了，Bootstrap 那边的 B4 门（`sealReason === 'cat_initiated_handoff'`）会把它挡住——因为这条 session 最终不是因为 handoff 封的。

### 4.12 内存 SessionChainStore 的三级淘汰

`create()` 之后若 `records.size > 1000` 就 `evictOne()`，三轮扫描：

```
第一轮：找 status === 'sealed' 的         （最安全）
第二轮：找 status !== 'active' 的         （比如卡在 sealing）
第三轮：找 不在 activeIndex.values() 里的  （名义 active 但已被顶替）
都没有 → return false
```

`create()` 里对 `false` 的处理是**回滚新记录并抛错**：
```ts
const evicted = this.evictOne();
if (!evicted) {
  this.removeRecord(id);
  throw new Error(`SessionChainStore at capacity (1000): all records are truly active. ` +
                  'Cannot evict without data loss. Seal or remove existing sessions first.');
}
```
**宁可报错也不删活的**。

`removeRecord(id)` 清 4 处索引，其中两处带 **ownership 检查**：
```ts
this.cliIndex.delete(record.cliSessionId);
if (record.chainKey && this.chainKeyIndex.get(record.chainKey) === id) this.chainKeyIndex.delete(record.chainKey);
if (this.activeIndex.get(key) === id) this.activeIndex.delete(key);
const chain = this.chains.get(key); /* splice 掉，空了删 key */
this.records.delete(id);
```
chainKey 那条的注释（云端 review P1）：「After a sealed→fresh re-create, a newer active record owns the same chainKey, so evicting the old sealed one must not delete the live index」——同一个 chainKey 会被新记录接管，淘汰旧的不能顺手把新的索引删了。

### 4.13 `RuntimeSessionSealReaper` 到底做什么

**一句话**：Antigravity 这类 IDE runtime 没有「进程退出」这种明确终点，所以先把 runtime session 标成 `runtime_seal_pending`，再由这个 reaper **周期性地去 drain 它（等它静默），drain 干净了才封 SessionRecord**。

`runOnce()`：
```ts
const records = await this.runtimeSessionStore.listByLifecycleState('runtime_seal_pending');
const result = emptyRunResult(records.length);       // scanned = 数量
for (const record of records) addRunResult(result, await this.processRecord(record));
return result;   // { scanned, drained, sealed, pending, skippedMaxRetries, failed }
```

`processRecord()` 决策表：

| 条件 | 动作 | 计数 |
|---|---|---|
| `retryCount >= maxRetries`（默认 5） | 什么都不做，跳过 | `skippedMaxRetries=1` |
| drain 抛异常 | 转成 `{ok:false, drainResult:'skipped_runtime_unreachable', reason: err.message}` | 继续往下 |
| `drain.ok && drainResult === 'complete'` | `requestSessionSeal(sessionId, lifecycle.sealReason ?? 'runtime_error_reset')` → `markRuntimeSealed(state:'sealed')` | `sealed=1` |
| drain 不完整且是 `skipped_runtime_unreachable` | 先 `recordDrainFailure`（retryCount+1），再 `requestSessionSeal(sessionId,'runtime_disconnected')` → `markRuntimeSealed` | `sealed=1` |
| drain 不完整且是 `best_effort_quiet_window` | 只 `recordDrainFailure`，留在 pending 下轮再试 | `pending=1` |
| 上述过程抛异常 | `recordProcessingFailure`（retryCount+1，记 lastFailureReason），且外层 `.catch(()=>{})` | `failed=1` |

`toIncompleteDrain(drain)`：如果 drain 报 ok 但 drainResult 不是 `'complete'`，强制转成 `{ok:false, drainResult:'best_effort_quiet_window', reason:'runtime drain returned non-terminal <x>'}` —— **把「ok 但没干净」也当失败处理**。

`requestSessionSeal()` 的三态处理：
```ts
const seal = await this.sessionSealer.requestSeal({ sessionId, reason });
if (seal.accepted || seal.status === 'sealing') { await this.sessionSealer.finalize({ sessionId }); return; }
if (seal.status === 'sealed') return;                                  // 已封，幂等成功
throw new Error(`session seal request was not accepted; status=${seal.status}`);
```
**`accepted === false` 但 `status === 'sealing'` 也算成功并继续 finalize**——别人刚请求封存还没 finalize，我们帮它 finalize 完。

**定时器封装**（`startSerializedRuntimeSessionSealReaperInterval`）用了一个 `sweepInFlight` 闭包锁：
```ts
let sweepInFlight = false;
return setIntervalFn(() => {
  if (sweepInFlight) return;                    // 上一轮没跑完就跳过这一 tick
  sweepInFlight = true;
  void options.runtimeSessionSealReaper.runOnce()
    .then(r => options.onResult?.(r)).catch(e => options.onError?.(e))
    .finally(() => { sweepInFlight = false; });
}, options.intervalMs);
```
`index.ts` 里默认 30 秒一轮，`timer.unref()` 让它不阻止进程退出。

**`maxRetries` 的入参校验**也值得看一眼（防御性）：
```ts
this.maxRetries = Number.isSafeInteger(options.maxRetries) && (options.maxRetries ?? 0) > 0
  ? Math.floor(options.maxRetries as number) : DEFAULT_MAX_RETRIES;
```

### 4.14 外部 runtime 注册的并发控制与不可变断言

`ExternalRuntimeSessionRegistration.ts` 是 IDE 直连（Antigravity）自己来报到的入口，principal 必须是 `agent_key`。

**进程内互斥锁**（key = `` `${runtime}:${runtimeSessionId}` ``）：
```ts
const externalRuntimeRegistrationLocks = new Map<string, Promise<void>>();
async function withExternalRuntimeRegistrationLock<T>(runtime, runtimeSessionId, fn) {
  const key = `${runtime}:${runtimeSessionId}`;
  const previous = externalRuntimeRegistrationLocks.get(key) ?? Promise.resolve();
  let release: () => void;
  const current = new Promise<void>((resolve) => { release = resolve; });
  const next = previous.then(() => current, () => current);      // 前一个成功/失败都接上
  externalRuntimeRegistrationLocks.set(key, next);
  await previous.catch(() => undefined);
  try { return await fn(); }
  finally { release!(); if (externalRuntimeRegistrationLocks.get(key) === next) externalRuntimeRegistrationLocks.delete(key); }
}
```
经典的 Promise 链式互斥。`previous.then(()=>current, ()=>current)` 两个回调都返回 `current`，保证前一个 reject 也不断链。最后的 `get(key) === next` 是 ownership 检查，避免删掉后来者的锁。

**三条 immutable 断言**（同一个 runtimeSessionId 重复注册时）：

| 变了什么 | 错误码 | HTTP |
|---|---|---|
| catId | `external_runtime_cat_immutable` | 409 |
| userId | `external_runtime_user_immutable` | 409 |
| threadId / binding | `external_runtime_binding_immutable` | 409 |

**binding 两种模式**：
- `{mode:'orphan'}` → `threadStore.ensureExternalRuntimeAnchorThread(runtime, userId)` 拿一条锚点线程 → 存成 `{mode:'orphan_anchor', anchorThreadId}`
- `{mode:'thread', threadId}` → 校验 `canBindExternalRuntimeSessionToThread(thread, userId)`：`thread.createdBy === userId` **或** `thread.id === DEFAULT_THREAD_ID && thread.createdBy === 'system'`；不过 → `external_runtime_thread_forbidden` / 403
- `binding === undefined` → 默认 `{mode:'orphan'}`

**upsert 失败的补偿**（新建路径）：
```ts
try { await deps.runtimeSessionStore.upsert(metadata); }
catch (err) {
  await deps.sessionChainStore.update(sessionRecord.id, {
    status: 'sealed', sealReason: 'external_registration_failed', sealedAt: now });
  throw err;
}
```
侧车写失败 → 把刚建的 SessionRecord 封掉，别留孤儿 active。
下次重试时 `reopenFailedExternalRegistrationSessionRecord()` **只认这一个 sealReason** 才肯 reopen：
```ts
if (sessionRecord.status === 'active') return;
if (sessionRecord.sealReason !== 'external_registration_failed') throw new ...Error('external_runtime_session_record_inactive', 409);
const reopened = await sessionChainStore.update(sessionRecord.id, { status:'active', sealReason:null, sealedAt:null, updatedAt: now });
if (!reopened || reopened.status !== 'active') throw new Error('external_runtime_session_record_reopen_failed');
```

**`buildUpdatedMetadata()` 里的时间戳 CAS**：
```ts
const registrationIsCurrent = registration.lastObservedAt >= existing.lifecycle.lastObservedAt;
```
只有「这次上报不比已有的旧」才更新 state / externalRegistration / runtimeConversationId / 追加身份段。**乱序到达的旧上报不会覆盖新状态。** `startedAt` 取 `Math.min`，`lastObservedAt` 取 `Math.max`。

**`appendRuntimeIdentity()` 的时间段校验**（`RuntimeSessionMetadata.ts`）：
```ts
if (current) {
  if (nextEntry.from < current.from) throw new Error('identity segment starts before current segment');
```

### 4.15 agent-hooks 的同步机制

**四个同步目标**（`buildAgentHookTargets({projectRoot, targetRoot})`）：

| name | 源 | 目标路径 | contentKind | executable |
|---|---|---|---|---|
| `hooks/session-start` | `readUserHook(projectRoot,'session-start-recall.sh')` | `<targetRoot>/.claude/hooks/session-start-recall.sh` | text | ✔ |
| `hooks/session-stop` | `readUserHook(projectRoot,'session-stop-check.sh')` | `<targetRoot>/.claude/hooks/session-stop-check.sh` | text | ✔ |
| `codex-hooks` | `renderCodexHooksJson(targetRoot)` | `<targetRoot>/.codex/hooks.json` | **json** | — |
| `gemini-hooks` | `renderGeminiHooksJson(targetRoot)` | `<targetRoot>/.gemini/hooks.json` | **json** | — |

`readUserHook` 固定读 `<projectRoot>/.claude/hooks/user-level/<name>` —— **真相源是仓库里的 user-level 目录**（ADR-019 第 2 条）。

**Codex 与 Gemini 的唯一差异**：Stop 命令。
```ts
function bashCommand(scriptPath: string) { return `bash "${scriptPath.replace(/\\/g,'/')}"`; }
function codexStopCommand(scriptPath: string) { return `${bashCommand(scriptPath)} --codex-json`; }
```
Codex 的 Stop 多一个 `--codex-json` 参数，让脚本把提醒包成 `{"systemMessage": "..."}` 输出。**两份 JSON 都指向同一对 `.sh` 脚本**（`<targetRoot>/.claude/hooks/...`）——一份脚本三家共用。

**`canonicalize` + `canonicalJsonString`（JSON 语义比较）**：
```ts
function canonicalize(value: unknown): unknown {
  if (Array.isArray(value)) return value.map(canonicalize);
  if (value && typeof value === 'object')
    return Object.fromEntries(Object.entries(value).sort(([a],[b]) => a.localeCompare(b)).map(([k,v]) => [k, canonicalize(v)]));
  return value;
}
export function canonicalJsonString(content: string) { return JSON.stringify(canonicalize(JSON.parse(content))); }
```
**对象键递归排序，数组顺序保留**（数组顺序在 hooks 配置里是有语义的）。`contentMatches()` 据此分流：
```ts
if (target.contentKind !== 'json') return current === rendered;    // 文本：逐字节
return canonicalJsonString(current) === canonicalJsonString(rendered);   // JSON：语义
```
好处：用户用编辑器格式化过 `hooks.json`（改了缩进/键序）不会被误判成 drift。

`applySync(target, dryRun)`：dryRun 只打印；否则 `mkdirSync(dirname, {recursive:true})` → `writeFileSync` → `if (target.executable || targetPath.endsWith('.sh')) chmodSync(path, 0o755)`。

**`claude-settings.ts` 的 JSON 合并策略**（这是最需要小心的一个）：

它**不**整体覆盖 `settings.json`，只动自己管的那两条。

```ts
const MANAGED_HOOKS = { SessionStart: 'session-start-recall.sh', Stop: 'session-stop-check.sh' } as const;
const MANAGED_HOOK_NAMES = new Set(Object.values(MANAGED_HOOKS));
```

`syncClaudeSettings(targetRoot)` 五步：
```ts
const settings = readOptionalSettings(targetPath);                  // 不存在返回 {}
const hooksRoot = isJsonObject(settings.hooks) ? settings.hooks : {};
for (const eventName of ['SessionStart','Stop']) {
  const entries = withoutManagedHooks(eventEntries(settings, eventName), targetRoot);   // 先摘掉自己的旧条目
  const scriptPath = expectedClaudeCommand(targetRoot, eventName).replace(/\\/g,'/');
  entries.push({ hooks: [{ type:'command', command: `bash "${scriptPath}"` }] });       // 再加一条新的
  hooksRoot[eventName] = entries;
}
settings.hooks = hooksRoot;
await mkdir(dirname(targetPath), {recursive:true});
writeFileSync(targetPath, `${JSON.stringify(settings, null, 2)}\n`, 'utf-8');
```

`withoutManagedHooks(entries, targetRoot)` —— **只删自己的，用户的其他 hook 原样保留**，而且删空的 entry 会被整个丢掉：
```ts
return entries.flatMap((entry) => {
  if (!Array.isArray(entry.hooks)) return [entry];
  const hooks = entryHooks(entry).filter(h => !isManagedHookCommand(h.command, targetRoot));
  return hooks.length > 0 ? [{ ...entry, hooks }] : [];
});
```

**「是不是我管的命令」判定**（`isManagedHookCommand`）走一条归一化管线：
```
command 字符串
  → extractScriptPath():   /^bash\s+(.+)$/ 匹配就取捕获组，否则原样
  → stripWrappingShellQuotes(): 首尾同为 " 或 ' 就剥掉
  → 展开 home 前缀：$HOME/ | ${HOME}/ | ~/  →  join(targetRoot, 余下部分)
  → replace(/\\/g,'/')     反斜杠统一成正斜杠
  → 要求 normalized.startsWith(`${join(targetRoot,'.claude','hooks').replace(/\\/g,'/')}/`)
  → 且 basename ∈ MANAGED_HOOK_NAMES
```
**三种 home 写法 + 两种引号 + 两种路径分隔符全部归一** —— 这就是 README 里说的「手动复制 template 后 Hub 可能因路径规范化差异继续提示 stale，再 sync 一次即可」的来源。

**`claudeSettingsHealth()` 的四态判定**：

| 情形 | status | reason |
|---|---|---|
| 文件不存在 | `missing` | `'Claude settings.json does not exist'` |
| 两个事件都有正确命令 **且** 所有托管命令都有 `bash ` 前缀 | `configured` | `'configured'` |
| 两个事件都有正确命令但**缺 bash 前缀** | `stale` | `'...missing bash prefix for cross-platform support'` |
| 有托管命令但路径不对（`eventHasStaleManagedCommand`） | `stale` | `'has stale managed hook command entries'` |
| 都没有 | `missing` | `'missing managed SessionStart/Stop hook entries'` |
| JSON 解析失败 | `error` | 异常消息 |

`hasBashPrefix(command)` 就是 `/^bash\s/.test(command.trim())` —— Windows 上不写 `bash` 前缀，`.sh` 会被编辑器打开而不是执行（README 明写）。

**`health.ts` 的聚合与 diff**：
- `statusSeverity`: `error(5) > stale(4) > missing(3) > unsupported(2) > configured(1)`，`aggregateStatus` 取最严重的。
- `codex-hooks` 特判：`.codex/` 目录和文件都不存在 → `unsupported`（没装 Codex 不算 drift）。
- `buildTextDiff`: 逐行比，返回**第一处不同的行号**。
- `buildJsonDiff`: 用 `flattenJson()` 把两边拍平成 `路径 → JSON字符串` 的 Map（数组写成 `key[0].sub`），取差异键**最多 8 个**。
- `syncAgentHooks()` 末尾还有一道自检：codex 目标同步后若是 `configured`，会 `void canonicalJsonString(readFileSync(...))` 再解析一次，注释：「preserve a direct parse here so malformed output fails immediately after sync」。

### 4.16 `ClaudeThinkingRescue` 是什么（名字很怪，读完就懂）

**它跟本系统的 SessionRecord 一点关系都没有。** 它修的是 **Claude Code CLI 自己在 `~/.claude/projects/**/*.jsonl` 里存的本地 transcript**。

**问题**：Claude 的 extended thinking 块带一个 `signature` 字段用于服务端验签。第三方网关（或 CLI 内部生成的 thinking）可能产出**短的假签名**（注释举例 212 字节）。等你 `--resume` 这个 session 时，服务端验签失败，整个 session 就 resume 不回来了——**历史全废**。

**两种检测**（`scanTranscript` 逐行 JSON.parse）：

| 检测函数 | 判定 | `detectedBy` |
|---|---|---|
| `isThinkingSignatureApiErrorEntry(entry)` | `type==='assistant'` && `isApiErrorMessage===true` && `message.role==='assistant'` && content 数组里有 `{type:'text', text}` 且 `text` 匹配 `/Invalid [`'"]?signature[`'"]? in [`'"]?thinking[`'"]? block/i` | `'api_error_entry'`（优先） |
| `hasShortThinkingSignature(entry)` | `type==='assistant'` && `message.role==='assistant'` && content 数组里**存在**一项 `type==='thinking'` 且 `typeof signature==='string'` 且 `signature.length < 300` | `'short_signature'` |

`MIN_VALID_SIGNATURE_LENGTH = 300` 的依据（注释）：「Signatures from official Anthropic API are variable-length and typically > 400 bytes.」

**修复动作**（`stripPureThinkingAssistantTurns`）—— 只删「**纯 thinking**」的 assistant 轮次：
```ts
export function isPureThinkingAssistantTurn(entry: unknown): boolean {
  // type==='assistant' && message.role==='assistant' && Array.isArray(content) && content.length > 0
  // && content.every(item => item.type === 'thinking' && typeof item.signature === 'string')
}
```
**`every` 不是 `some`**：只有整条消息**全部**都是 thinking 块才删——如果里面还夹着 text 或 tool_use，删掉就丢内容了。

逐行处理时：空行原样保留；`JSON.parse` 失败的行**原样保留**（注释：「Keep malformed lines untouched; rescue only removes known-safe pure thinking turns」）；命中的行跳过并计数。

**备份**：`backupPathFor(sessionId, backupDir, now)` = `<backupDir>/<sessionId>.pre-strip-thinking-<unixSeconds>.jsonl`，默认 backupDir 是 `~/.claude/backups`，默认 rootDir 是 `~/.claude/projects`。顺序是 **mkdir → copyFile（备份）→ writeFile（覆写）**，先备份再改。

**三种单条结果**：`'missing'`（读不了，reason `'transcript_unreadable'`）/ `'clean'`（`removedCount === 0`，不备份不写）/ `'repaired'`。

**整体状态**：`rescuedCount > 0 ? (skippedCount > 0 ? 'partial' : 'ok') : 'noop'`。

`walkJsonlFiles(rootDir)` 是显式栈的迭代 DFS（不用递归），readdir 失败 `continue`，最后 `results.sort()` 保证确定性。

**HTTP 入口**（`routes/claude-rescue.ts`）：`GET /api/claude-rescue/sessions` 扫描并按 sessionId 字典序返回；`POST /api/claude-rescue/rescue` body 是 `{sessionIds: string[]}`，**先重新扫一遍**再按 sessionIds 过滤出 targets（不信任客户端传路径），一个都没匹配上就 400。两个端点都要 `resolveUserId(request)`，否则 401。

> **面试官追问：为什么这个东西放在 `session/` 目录下？**
> 「因为它服务的是同一个目标——**保住会话连续性**。SessionSealer 那条链是『我们自己的会话链』的连续性，ClaudeThinkingRescue 是『底层 CLI 会话』的连续性。CLI session resume 不回来，我们的 `--resume` 指针就是废的。这是 CLI 子进程方案必须承担的『下游 bug 我得自己修』的代价。」【推断，但源码里 `INVALID_THINKING_SIGNATURE_RE` 和 `--resume` 的注释支持这个说法】

### 4A. 会话链测试：不要只断言 `status === sealed`

#### 封板测试的分层断言

| 层 | 应检查什么 | 为什么 |
|---|---|---|
| 状态抢占 | active→sealing 只成功一次 | 防并发重复 finalize |
| 活跃指针 | request 后清除旧 active pointer | 新调用不能继续绑定旧会话 |
| 内容产物 | digest/capsule/thread memory 符合预算 | successor 需要可用上下文 |
| 终态 | sealing→sealed，写 `sealedAt/sealReason` | 可审计、可查询 |
| hook | 仅终态写成功后触发 | 防下游看到并不存在的 sealed |
| 恢复 | stuck sealing 超龄可 force-seal | 防中间态永久卡死 |

`session-sealer.test.js` 对上述状态、幂等、超时、reaper 和 hook 均有覆盖；`session-sealer-thread-memory.test.js` 则验证 ThreadMemory 失败不阻断 seal、决策/问题能累积、token cap 动态计算。

#### 竞态一：两个调用同时超过阈值

两个 worker 都可读取到“应封板”，但只有一个 `requestSeal()` accepted。输掉者应重新读取当前状态或直接继续新会话逻辑，不能把 accepted=false 当成必须报错。

#### 竞态二：finalize 生成摘要时进程崩溃

持久状态停在 sealing。重启后 `reconcileStuck()` 只处理超过 maxAge 的记录，避免把仍在正常 finalize 的会话误判为僵尸。测试要用可控时钟验证阈值前后，而不是 `sleep` 实际等待。

#### 竞态三：旧 runtime 突然切到新 runtime

需要判断是预期 rotation、自动 retry fragment、ephemeral session，还是异常冲突。不能看到新 ID 就简单覆盖，否则会失去旧会话封板原因，也可能把不同工作区的上下文串联。

`invoke-single-cat-resume-health.test.js` 验证连续恢复失败达到阈值后自动 seal，但 idle 很久本身不构成封板理由；这说明健康判断是行为驱动，不是粗暴按年龄淘汰。

#### Bootstrap 的安全测试

把旧 digest 写成包含类似系统指令、分隔符和超长文本的恶意内容，断言：

- injection guard 在摘录前；
- 历史内容被明确标成数据；
- 内嵌分隔符被转义；
- token budget 生效，最新会话优先；
- 祖先信息不会无限递归展开。

这些场景由 `antigravity-continuity-bootstrap.test.js` 覆盖。你的安全经验可以直接迁移到“持久化 Prompt Injection”测试。

#### 面试复述

> 封板不是一次 update，而是可恢复状态机。requestSeal 用原子状态转换取得所有权，finalize 生成摘要和线程记忆后写 sealed 终态，非关键增强失败可降级，但中间态必须由超时 reaper 修复。successor 通过受 token 预算和注入边界保护的 bootstrap 继承必要信息，而不是直接复用全部 transcript。

### 6.2 审计事件（`EventAuditLog`）

| 常量 | 值 | 何时写 | data 里有什么 |
|---|---|---|---|
| `SEAL_REQUESTED` | `'seal_requested'` | requestSeal 成功 | sessionId, catId, cliSessionId, reason, seq |
| `SEAL_FINALIZED` | `'seal_finalized'` | finalize **干净**完成 | sessionId, catId, cliSessionId, reason, seq, sealedAt |
| `SEAL_FINALIZE_FAILED` | `'seal_finalize_failed'` | ① doFinalize 抛错/超时 ② 终态写失败（`phase:'terminal_update'`）③ reaper 强封（`phase:'reconcile_stuck'` / `'global_reaper'`，带 `stuckDurationMs`） | 视 phase 而定 |

**注意 `SEAL_FINALIZE_FAILED` 一个类型承担四种含义**，靠 `data.phase` 区分。查问题时要看 phase：
- 没有 phase → doFinalize 本体失败（transcript/digest 可能缺）
- `phase: 'terminal_update'` → **最严重**，记录还卡在 sealing
- `phase: 'reconcile_stuck'` / `'global_reaper'` → 已被 reaper 救回来了，但说明之前有东西挂了

**「有 SEAL_REQUESTED 但没有 SEAL_FINALIZED」** = finalize 不干净或没跑完，是最典型的告警模式。

### 6.3 磁盘上的证据

```
data/transcripts/threads/<threadId>/<catId>/sessions/<sessionId>/
  events.jsonl              ← 正本；没有它说明 flush 从没成功
  events.live.jsonl         ← 还在？说明 flush 没跑完（或进程崩在中间）

  digest.extractive.json    ← 没有它说明 flush 时没传 sealTimestamps

```

**`events.live.jsonl` 还在 = 一个明确的故障信号**（正常 flush 最后一步会 unlink 它）。

`CliRawArchive` 的排查价值最大——它存的是**没经过任何解析的 CLI 原始 payload**，格式 `{"timestamp": 1750000000000, "payload": <原样>}` 每行一条。当你怀疑「是不是我们解析错了」，就对着这个文件看。`getPath(invocationId)` 给出今天的路径；目录用 `readyDirs: Set` + `initInFlight: Map` 做 mkdir 去重（同一目录并发 mkdir 只跑一次）。

### 6.5 两个 hook 脚本逐条检查项

两份脚本都遵循同一套骨架：读 stdin（hook 协议要求）→ 从 JSON 里 grep 出 `cwd` → `cd` 进去 → **不是 git 仓库就 `exit 0`** → 累积 `WARNINGS` 字符串 → 有内容才输出 → `exit 0`。

```bash
INPUT=$(cat)
CWD=$(echo "$INPUT" | grep -oE '"cwd"\s*:\s*"[^"]*"' | head -1 | sed 's/.*: *"//;s/"$//')
[ -z "$CWD" ] && CWD="$(pwd)"
cd "$CWD" 2>/dev/null || exit 0
git rev-parse --git-dir >/dev/null 2>&1 || exit 0
```
**用 grep+sed 而不是 jq 解析 JSON**——因为不能假设机器上装了 jq。**永远 `exit 0`**——hook 失败不能让 CLI 起不来。

**`session-start-recall.sh` 六项检查（开工前）**：

| # | 检查 | 命令 | 提示 |
|---|---|---|---|
| 1 | 共享文档有未提交改动 | `git diff --name-only -- docs/ cat-cafe-skills/ assets/system-prompts/ \| head -10` | 「记得 commit push（家规：共享文档改完立刻提交）」 |
| 2 | 有未 push 的 commit | `git log --oneline @{u}..HEAD \| head -5` | 「确认是否需要 push」 |

| 3 | 主仓库不在 main/master | `git branch --show-current` 非 main/master **且** `git rev-parse --git-dir` 不含 `.git/worktrees/` | 「铁律：主仓库禁止 checkout 到非 main 分支，改代码必须开 worktree」 |

## 7. 面试追问应对

### Q1「`active → sealing → sealed` 为什么要三态？两态不行吗？」

> 「不行，因为 finalize 是个**长操作**——要 flush JSONL、读回 digest、算 ThreadMemory、可能还要调一次 Haiku，代码里给了 30 秒超时。两态的话，从 `active` 直接改 `sealed` 有两个选择：改之前做 finalize，那这段时间 active 指针还在，新事件还会往这条 session 上写，flush 出来的内容不完整；改之后做 finalize，那外界已经看到 sealed 了，去读 digest 会读到 404。
> `sealing` 的语义是『active 指针已经清了（不再接新事件），但产出还没齐』。有了它，`requestSeal` 就能做成一个**快路径**：只改状态 + 清指针，几毫秒返回；`finalize` 是慢路径，fire-and-forget 异步跑。调用方拿到 `{accepted:true, status:'sealing'}` 就可以继续了。
> 代价是引入了『卡在 sealing』这个新故障态，所以配了两个 reaper 兜。」
> **加分点**：「SessionBootstrap 里 `sealedSessions` 的过滤条件是 `status === 'sealed' || status === 'sealing'`——sealing 的 digest 大概率已经可读了，等它转 sealed 会白丢一轮上下文。这是 R6 P1-2 补的。」

### Q2「`requestSeal` 里那行 `const currentStatus = record.status` 看着是废话，为什么留着？」

> 「不是废话，是**跨实现语义差异的防御**。内存版 `SessionChainStore.get()` 返回的是 Map 里那个对象**本身**，不是副本；紧接着 `update()` 会原地改这个对象的 `status`。所以如果我在 `update` 之后再读 `record.status`，读到的是改后的 `'sealing'`，那个『只有 active 才能封』的判断就永远成立了。Redis 版返回的是 `hydrate()` 出来的新对象，没这个问题——但接口两边都要正确。
> 源码注释就写着 `Snapshot status before mutation (memory store returns live reference)`。
> 这类 bug 特别阴——单测跑 Redis 版全过，跑内存版才炸。」【源码】

### Q3「hybrid 策略的 compressionCount，为什么非要用 Lua？普通 GET/INCR 不行？」

> 「因为这是**并发最高的一条写路径**——PreCompact hook 是 Claude Code 自己触发的，同一 session 可能几乎同时打进来两次。
> 如果写成『先 `get(id)` 拿到 compressionCount，判断 `< max`，然后 `update(count+1)`』，两个请求会都读到 1、都判『还没到上限 2』、都返回 allow_compress，最后计数只到 2——**多压了一次**。
> Lua 脚本 `INCR_COMPRESSION_LUA` 把三件事塞进一次 round-trip：`EXISTS` 检查、`HGET status` 必须是 active、`HINCRBY compressionCount 1`，返回新值（`-1` = 不存在，`-2` = 非 active）。
> 更关键的是 **route 层的用法是「先增后判」**：拿到新值 `newCount` 再跟 max 比。这样两个并发请求一个拿到 2、一个拿到 3，第二个正确触发封存。源码注释直接标了『Atomic increment-then-check: avoids TOCTOU race』。
> 内存版对应的 `incrementCompressionCount()` 也做了 `status !== 'active'` 返回 null 的同样契约——Node 单线程所以天然原子。」

### Q4「bootstrap 的 2000 token 预算，具体怎么分？」

> 「分成两类段落：**always-keep** 是 identity（会话身份）、handoffNote（猫亲手写的交接）、tools（MCP 工具说明）；**droppable** 是 threadMemory、recall、digest、taskSnapshot。
> 算法六步：
> 1. 先算 identity + tools 的 token 数；
> 2. note 的预算 = `max(0, 2000 - identity+tools - 400)`——那个 400 是 `HANDOFF_NOTE_VARIABLE_RESERVE_TOKENS`，**给可变段留的最低保障**，防止 note 把它们全饿死；
> 3. `capHandoffNoteToBudget()` 把 note 截到预算内；
> 4. `baseTokens` = identity + note + tools；
> 5. `remainingBudget = 2000 - baseTokens`；
> 6. 四个可变段的总量超了就按 **recall → task → digest → threadMemory** 顺序依次清空，每清一个重判一次。
> 丢弃顺序的含义：recall 是自动召回的、最容易再拿一次；threadMemory 是跨会话的滚动记忆、最不可替代，所以最后丢。」
> **加分点**：「这里有个非显然的坑，注释里写了：per-field 的 600 字符上限管不住总量——CJK 下 600 字符约 900 token，done+next+gotchas 三个字段单独就能超过 2000。而 note 属于 baseTokens，一旦它把 base 撑过硬顶，`remainingBudget` 变负数，后面**已经没有段可丢了**。所以必须在第 3 步先截。」

### Q5「`capHandoffNoteToBudget` 的收敛循环怎么写的？为什么是 0.9？」

> 「先把尾部的 `[/Cat Handoff Note]` 摘掉存成 body，准备一个 suffix = `\n…[handoff note truncated to fit bootstrap budget]\n[/Cat Handoff Note]`，然后：
> ```ts
> while (body.length > 0 && estimateTokens(body + suffix) > maxTokens) {
>   body = body.slice(0, Math.floor(body.length * 0.9));
> }
> return body.trimEnd() + suffix;
> ```
> 每次砍 10% 长度，**乘性衰减**。为什么不按字符数硬算：`estimateTokens` 走的是真 tokenizer（tiktoken），CJK 一个字可能 1~2 token，ASCII 四个字符约 1 token，字符数到 token 数没有稳定系数，所以只能试。乘性衰减最多几十轮就收敛，而且末尾 `Math.floor(1 * 0.9) === 0`，配合 `body.length > 0` 保证一定退出。
> 关键是**每轮都把 suffix 算进去**——不然截完再拼 suffix 又超了。而且 close marker 一定保留，围栏不能破。」

### Q6「finalize 产出链具体几步？某一步挂了会怎样？」

> 「四步，全部 best-effort，各自 try/catch，任何一步抛错只把局部变量 `clean` 置 false：
> 1. `transcriptWriter.flush()` → 写 `events.jsonl` + `index.json` + `digest.extractive.json`，最后 unlink `events.live.jsonl`；
> 2. 读回 extractive digest → 拿 ThreadMemory → 算动态 token 上限 `max(1200, min(3000, floor(maxPromptTokens * 0.03)))` → `extractSignals()` → `extractRecentArtifacts()` → `buildThreadMemory()` → 写回 ThreadStore；
> 3. `extractSignals()` 内部还有一层 try/catch，会去 SummaryStore 拿最新一条 ThreadSummary 的 conclusions/openQuestions，跟正则抽取的合并；
> 4. 如果 `bootstrapDepth === 'generative'` 且能拿到 apiKey，读全量事件 → `formatEventsHandoff` + `formatEventsChat` → 调 Haiku → 写 `digest.handoff.md`。
> 外层 `finalize()` 用 `withTimeout` 包着 30 秒，超时也好抛错也好，**终态转换照走**。源码注释是这么解释的：『A sealed session with missing transcript is recoverable; a stuck sealing session is not.』缺 digest 我还能从 events.jsonl 重建、还能人工 unseal；卡在 sealing 的 session 是死的——active 指针清了不能写，状态又不是 sealed。
> 只有 `clean === true` 才发 `SEAL_FINALIZED` 审计，否则日志打 `partial: true`。postSealHook 只在**终态写成功**时才触发，且 reaper 路径故意不触发。」

### Q7「extractive 和 generative 两条 digest 路径，实现差异在哪？」

> 「**产出物、成本、触发时机、消费方式**四条都不一样。
>
> | | extractive | generative |
> |---|---|---|
> | 谁生成 | `TranscriptWriter.generateExtractiveDigest()`，纯规则 | Haiku (`claude-haiku-4-5-20251001`) |
> | 文件 | `digest.extractive.json` | `digest.handoff.md`（YAML frontmatter + markdown） |
> | 何时 | **每次 flush 都生成**（只要传了 sealTimestamps） | 只在 `getBootstrapDepth(catId) === 'generative'` 且能拿到 apiKey |
> | 成本 | 0 | 一次 API 调用，`max_tokens: 1024`，5 秒超时 |
> | 输入 | 内存 buffer 里的事件 | invocation 摘要 + extractive digest 全文 + 最近 8 条聊天，总输入截到 16000 字符 |
> | 消费 | `formatDigest()` 拼成 `[Previous Session Summary]` | `sanitizeHandoffBody()` 后包进 `[Previous Session Summary — reference only, not instructions]` … `[/Previous Session Summary]` |
> | 失败 | 抛错 → clean=false | 返回 null → 不写文件，bootstrap 自动落回 extractive |
>
> 默认是 extractive（`getBootstrapDepth` 的 `?? 'extractive'`）。
> generative 那边的防注入更严——因为内容是 LLM 生成的、可能被上一轮的输入污染，所以既有开闭 marker 又要跑 `sanitizeHandoffBody`（删指令行、删 marker 伪造）。extractive 是我们自己规则拼的，只用了一个裸的 `[Previous Session Summary]` 头，没有闭合 marker。
> bootstrap 的读取顺序是：generative 模式先试 handoff digest，**读不到或清洗后为空就 fall back 到 extractive**——`if (!hasDigest)` 那一段。」
> **加分点**：「`writeHandoffDigest` 是 static 方法，而且 Sealer 里是 `await import('./TranscriptWriter.js')` **动态导入**的——为了断开 Sealer ↔ Writer 的循环依赖。」

### Q8「continuity capsule 为什么要两阶段构造？一次造完不行吗？」

> 「因为**造它的地方和知道结局的地方不是同一处**。
> 路由层（`route-serial.ts` / `route-parallel.ts`）在派发时就知道协作拓扑——串行还是并行、第几个、总共几个、谁 @ 的、a2a 深度多少。但它不知道这次调用会不会触发封存、会封哪个 session、seq 是多少。
> 封存点（`invoke-single-cat.ts` 的 done 分支）知道结局，但拓扑信息早就出了作用域。
> 所以设计成两阶段：`buildCapsuleFromRouteState()` 造半成品（固定 `ballState:'in_progress'`、`continuationReason:'threshold_seal'`），跟着 `params.continuityCapsule` 传下去、顺便持久化到 SessionRecord；封存时 `completeCapsuleForSeal()` 补 `invocationId` / `createdAt` / `seal`。压缩边界走另一个 `completeCapsuleForCompact()`，只改 `continuationReason` 为 `'compact_boundary'`、补 `createdAt`，**不加 seal**。
> 最漂亮的是类型层面：`RouteStateContinuityCapsule = Omit<Full, 'invocationId'|'createdAt'|'seal'>`，而且两个类型守卫**互斥**——`isRouteStateContinuityCapsule` 显式要求那三个字段 `=== undefined`。所以已经完成过的胶囊不可能被再 complete 一次。」

### Q9「`continuityCapsule` 在 SessionRecord 上是 `unknown` 类型，这不是偷懒吗？」

> 「是刻意的。这个字段会经过 Redis 序列化、hook route 往返、CLI 事件 JSON 解析好几道——任何一道都可能塞进来一个形状不对的东西。声明成 `unknown` 强制**每个读取点都必须过守卫**，编译器帮你把关。
> 对比一下 `catHandoffNote`：那个是 **typed** 的 `CatHandoffNote`，F225 的 KD-4 明确说了『typed，非 continuityCapsule:unknown』——因为 note 只在我们自己的 approve 事务里写，来源可控。
> 守卫的判定很细：`v === 1`、四个必填非空字符串/枚举、`a2aEnabled` 必须是 boolean（不是 truthy）、`chainIndex`/`chainTotal` 必须是**正整数**、`a2aDepth`/`maxA2ADepth` 必须是**非负整数**（0 合法）、`seal` 存在的话内部四个字段再验一遍。
> 还有一条容易漏的：`extractContinuityCapsuleFromAgentMessage` 里有 `msg.catId !== capsule.catId` 的**交叉校验**——防止 A 猫的消息里携带 B 猫的胶囊。」

### Q10「session strategy 的六级查找，runtime override 为什么不是直接替换？」

> 「因为 UI 上人通常只改一个值。查找顺序是：测试覆盖 → runtime override（Redis）→ 配置文件 → breed 代码覆盖 → provider 默认 → 全局默认。
> 实现上是**先把 3~6 层完整解析成 fallback，再把 runtime override 深合并上去**：
> ```ts
> const fallback = resolveFallbackStrategy(catName);
> const runtimeOverride = getRuntimeOverride(catName);
> if (runtimeOverride) return { effective: validateProviderCapability(mergeStrategyConfig(fallback.effective, runtimeOverride), catName), source: 'runtime_override' };
> ```
> `mergeStrategyConfig` 里 `thresholds` 是无条件展开合并的，所以你只覆盖 `{thresholds:{action:0.88}}`，`warn` 还是下层的值。`handoff`/`compress`/`hybrid` 三个嵌套对象只在任一侧存在时才产出键，避免造空对象。
> Redis key 是 `session-strategy:override:{catId}`（前缀 `cat-cafe:`）。
> 有个工程上的讲究：`getSessionStrategy()` 是**同步函数**（被 hook route 和 invoke 热路径调），但覆盖要持久化。解法是 Redis + 同步内存缓存：启动 `initRuntimeOverrides(redis)` 做一次 SCAN hydrate，之后写走 write-through（**Redis 成功才写 cache**），读只读 cache。
> hydrate 还有两个细节：用临时 Map 攒完再 `_cache.clear()` 原子换入——SCAN 中途失败就保持空缓存（干净降级）而不是留部分数据；以及 ioredis 的 `keyPrefix` 不作用于 SCAN MATCH，得手动拼、拿回来再剥。」

### Q11「猫主动接力的 approve 事务，commit point 划在哪？为什么？」

> 「划在 **`requestSeal` 返回 accepted** 那一刻。
> 之前是 pre-commit：CAS claim 提案（pending→approving）、校验 sourceSessionId 仍是同一 (user, thread, cat) 的 active session、把 note 持久化到 SessionRecord。这三步都可以安全地 `markExpired` 回滚——没有任何不可逆副作用。
> 之后是 post-commit：enqueue 续跑 + finalize 提案。**只能前滚**，失败就 throw 让恢复流程接手，绝不 rollback——rollback 会留下一个半封印的孤儿 session。
> 类型上直接表达了这件事：`ApproveResult` 的失败分支只有 `stage: 'pre-commit'`。
> 划在 requestSeal 是因为它**不可逆**：session 置 sealing、active 指针清空。这之后世界已经变了。
> 最难的是崩溃恢复。commit point（session 侧的 sealing）和 checkpoint（提案侧的 sealedSessionId）是**两次独立写**，中间崩了就出现『approving 状态、有 handoffNotePersistedAt、没有 sealedSessionId』这种从提案单侧无法判断的状态。所以 `recoverStaleHandoffProposal` 必须**反查 session 侧**，四条件同时成立才认定 commit 已过：session 存在、状态是 sealing 或 sealed、`sealReason === 'cat_initiated_handoff'`、`catHandoffNote.proposalId === proposalId`。认了就回填 checkpoint 前滚；不认就 expire，同时释放那个『≤1 pending』的名额。
> 顺带一提：note 是**先于** requestSeal 持久化的，注释叫『commit-point 反推 key』——就是为了让这个反查成立。」

### Q12「`ClaudeThinkingRescue` 这名字很怪，它到底救什么？」

> 「救的是 **Claude Code CLI 自己在 `~/.claude/projects/**/*.jsonl` 里的本地 transcript**，跟我们的 SessionRecord 没关系。
> 场景：extended thinking 块带 `signature` 做服务端验签。第三方网关或 CLI 内部生成的 thinking 可能带**短的假签名**（注释举例 212 字节，官方通常 > 400 字节）。等你 `--resume` 这个 session，服务端验签失败 → 整个会话再也 resume 不回来。
> 两种检测：① transcript 里已经有 `isApiErrorMessage: true` 且 text 匹配 `/Invalid signature in thinking block/i` 的条目（`detectedBy: 'api_error_entry'`）；② 主动扫，任一 thinking 块 `signature.length < 300`（`'short_signature'`）。第二种是**预防性**的——还没炸就先发现。
> 修复只删『**纯 thinking**』的 assistant 轮次：`content.every(item => item.type === 'thinking' && typeof item.signature === 'string')`。用 `every` 不是 `some`——只要里面还夹着 text 或 tool_use 就不删，否则会丢真实内容。JSON 解析失败的行原样保留。
> 改之前先 `copyFile` 到 `~/.claude/backups/<sessionId>.pre-strip-thinking-<unixSeconds>.jsonl`。
> 有 `dryRun` 选项、三种单条结果（`repaired`/`clean`/`missing`）、整体三态（`ok`/`partial`/`noop`）。HTTP 入口是 `GET /api/claude-rescue/sessions` 扫 + `POST /api/claude-rescue/rescue` 修，后者只收 sessionIds、**服务端重新扫描后自己解析路径**，不信任客户端传路径。
> 放在 `session/` 目录是因为服务同一目标：CLI session resume 不回来，我们的 resume 指针就是废的。这是 CLI 子进程方案的隐性成本——下游的 bug 得自己修。」

### Q13「`BoundSessionHistoryImporter` 干嘛的？」

> 「人工把一个已存在的 CLI session bind 到某只猫某条 thread 上时（`PATCH /api/threads/:threadId/sessions/:catId/bind`），前端气泡是空的——因为那些消息从来没进过我们的 MessageStore。这个函数把已封存 session 的 transcript 回灌进去。
> 流程：拿 chain 里所有 `status === 'sealed'` 的 → 逐个 `hasTranscript()` → `readAllEvents()` → 逐事件 `mapTranscriptEventToMessage()` → `messageStore.append()`。
> 可导入类型只有三种：`IMPORTABLE_TYPES = new Set(['assistant','text','user'])`，且必须能抽出文本内容。
> 幂等靠 `idempotencyKey: \`history-import:${session.id}:${evt.eventNo}\`` —— **事件级幂等**。注释很诚实地标了范围：『V1 dedup scope: only transcript-event idempotency. If the same logical content already entered messageStore via a different path (for example, live streaming), we intentionally do not attempt content-level dedup in this first slice.』——同一内容如果从直播流进来过，会重复。
> `catId` 的映射：`evtType === 'user' ? null : session.catId`（用户消息 catId 为 null）。
> 非 user 且有 invocationId 时会加 `extra.stream = { invocationId, turnInvocationId }` **两个都填成同一个值**——注释解释是为了跟前端『turn 优先』的气泡身份契约保持一致（F194 Phase Z9 KD-28）。
> 计数方式很朴素：导入前后各数一次 `messageStore.getByThread(threadId, 10000).length` 求差，`Math.max(0, ...)`。
> 四种 skip 原因：`history_import_unavailable`（依赖没注入）、`no_transcript_found`、`no_importable_messages`、`no_new_messages`；异常统一 `failed` + `import_failed`。」

### Q14「`RuntimeSessionSealReaper` 和 `SessionSealer` 里那两个 reaper 是一回事吗？」

> 「不是，管的是**两层不同的东西**。
> `SessionSealer.reconcileStuck` / `reconcileAllStuck` 管的是**我们自己的 SessionRecord** 卡在 `sealing` —— 就是 finalize 没跑完。判据是 `now - (updatedAt ?? createdAt) > 5 分钟`，动作是强制 `update({status:'sealed', sealReason:'reconcile_stuck'|'global_reaper'})`。
> `RuntimeSessionSealReaper` 管的是**外部 runtime 的会话**（目前只有 `antigravity-desktop`）。IDE 里跑的 agent 没有『进程退出』这种明确终点，所以先把侧车状态标成 `runtime_seal_pending`，reaper 周期性去 `drainRuntimeSession(record)` 等它静默，drain 结果 `'complete'` 才去封 SessionRecord。
> 它的决策表有五个分支：retryCount ≥ 5 跳过；drain complete → 封（reason 用 `lifecycle.sealReason ?? 'runtime_error_reset'`）；drain 报 unreachable → 也封，但 reason 换成 `'runtime_disconnected'`；drain 只到 `best_effort_quiet_window` → 记失败留 pending 下轮再试；抛异常 → 记 failed。
> 它调 `requestSeal` 的三态处理也有讲究：`accepted || status === 'sealing'` 都继续 finalize（帮别人收尾），`status === 'sealed'` 直接返回（幂等），其余 throw。
> 定时器用 `sweepInFlight` 闭包锁防重入，默认 30 秒一轮，`unref()` 不阻塞退出。」

### Q15「agent-hooks 同步为什么不能整个覆盖 settings.json？」

> 「因为 `~/.claude/settings.json` 是**用户的**文件——里面有他自己的权限配置、环境变量、其他 hook。我们只有权改 SessionStart 和 Stop 里我们自己那两条。
> `syncClaudeSettings()` 的做法是：读现有 settings（不存在就 `{}`）→ 对 SessionStart 和 Stop 各自 `withoutManagedHooks()` 摘掉自己的旧条目 → push 一条新的 `{hooks:[{type:'command', command: 'bash \"<path>\"'}]}` → 写回。`withoutManagedHooks` 是 `flatMap`：只过滤掉托管命令，过滤后 hooks 为空的 entry 整个丢掉，其他原样保留。
> 『是不是我管的』判定走一条归一化管线：剥 `bash ` 前缀 → 剥首尾引号 → 展开 `$HOME/`、`${HOME}/`、`~/` 三种写法 → 反斜杠统一成正斜杠 → 要求路径在 `<targetRoot>/.claude/hooks/` 下 → 且 basename 在 `MANAGED_HOOK_NAMES` 里。这么多归一化就是因为跨平台跨写法。
> JSON 比较用 `canonicalJsonString()`：递归排序对象键、**保留数组顺序**（数组在 hooks 配置里有语义），再 `JSON.stringify`。这样用户格式化过文件不会被误判 drift。文本目标（`.sh`）则是逐字节严格比。
> 健康检查还有个专门的 `stale` 分支叫『缺 bash 前缀』——Windows 上不写 `bash`，`.sh` 会被编辑器打开而不是执行。」

### Q16「flush 时那个内容指纹去重，为什么不用 eventNo？」

> 「因为 eventNo 是**进程内的计数器**，重启后从 0 重新开始，跟磁盘上的 eventNo 会撞。指纹用的是 `` `${e.timestamp}:${JSON.stringify(e.event)}` `` ——时间戳 + 事件内容。
> 合并方向也要说清楚：不是『磁盘覆盖内存』，是 `[...diskOnly, ...buf]`。因为磁盘追加是 best-effort（catch 吞异常），buffer 里可能有磁盘上没有的事件；反过来重启前的事件只在磁盘上。所以取『磁盘独有的』放前面，接内存的，然后**整体重编号** `eventNo: i`。
> 顺带一提这个合并还天然覆盖了一个 edge case：重启后一条事件都没有就直接 seal——buffer 空、磁盘满，合并后照样完整。注释里明确写了这一条。
> 已知的理论缺陷：**同一毫秒内两条完全相同的事件会被误判成重复丢一条**。我的判断是这在实践中概率极低，且丢一条重复事件无害，所以没加额外序号。」【推断：源码里没写这条权衡】

### 8.6 判定规则速记

- **能不能 seal**：`status === 'active'`，且 update 后 `=== 'sealing'`。
- **能不能 finalize**：`status === 'sealing'`（否则静默 return）。
- **reaper 强封**：`status === 'sealing'` 且 `now - (updatedAt ?? createdAt) > maxAgeMs`。
- **bootstrap 注入**：链上有 `sealed` 或 `sealing` 的 session（≥1 条）。
- **注入 handoff note**：`prevSession.sealReason === 'cat_initiated_handoff'` **且** `catHandoffNote` 存在。
- **走 generative digest**：`bootstrapDepth === 'generative'` 且 `resolveProfile()` 返回了 apiKey 且事件数 > 0。
- **hybrid 可用**：`clientId === 'anthropic'`。
- **noise 折叠**：同 kind、未 recovered、invocation 匹配的**连续**噪声，`count >= 2`。
- **recentMessages 合并**：同 `invocationId:catId` 且该条**仍在数组末尾**。
- **runtime active 抢占**：`lastObservedAt` 更大（或当前指针悬空）。
- **外部注册可 reopen**：`sealReason === 'external_registration_failed'`。
- **approve 已过 commit point**（崩溃恢复判定）：session 存在 ∧ 状态 ∈ {sealing, sealed} ∧ `sealReason === 'cat_initiated_handoff'` ∧ `catHandoffNote.proposalId === proposalId`。
- **托管 hook 命令**：归一化后路径在 `<targetRoot>/.claude/hooks/` 下 ∧ basename ∈ `{session-start-recall.sh, session-stop-check.sh}`。
- **thinking 轮次可删**：`type==='assistant'` ∧ `message.role==='assistant'` ∧ content 非空数组 ∧ **每一项**都是带 string signature 的 thinking。

### 8.7 六组「别搞混」

| A | B | 区别 |
|---|---|---|
| `SessionRecord.id` | `SessionRecord.cliSessionId` | 前者是我们的 UUID（不变），后者是 CLI 的（会换） |
| `sessions:{u}:{c}:{t}`（SessionManager） | `session-cli:{cliSessionId}`（ChainStore） | 前者正向找 resume 目标、1 天 TTL；后者反向找记录、永久 |
| `SessionSealer` 的 reaper | `RuntimeSessionSealReaper` | 前者救卡在 sealing 的 SessionRecord；后者驱动外部 runtime 从 pending 走到 sealed |
| `continuityCapsule`（unknown） | `catHandoffNote`（typed） | 前者外部来源多、必须过守卫；后者只在自家事务里写 |
| `seq`（0-based） | `displaySeq` / `seal.sessionSeq`（1-based） | 展示和 capsule 里都 +1 |
| extractive digest | handoff digest | 规则/免费/总生成 vs Haiku/收费/条件生成 |
