# 34 · Vibe Coding 指南：怎么把这样一个项目"喂"出来

> 这一篇回答你真正的问题：**我不需要手搓代码，但我不知道怎么指挥 AI 做出这种规模的东西。**
>
> 先说结论：**vibe 一个功能和 vibe 一个项目，难点完全不在一个地方。**
> 前者难在"把需求说清楚"，后者难在"**在几十次会话之间保持架构不漂移**"。
>
> 而且有个很讽刺的事实 —— 你 vibe 这个项目的过程，
> 本质上就是**手动扮演 Clowder 自己的角色**。它的每一个核心设计，
> 都对应 vibe coding 的一个具体痛点。这一篇最后会把这条线串起来。

---

## 1. 先搞清楚难在哪

### Vibe 一个功能（你大概率做过）

```
"帮我写一个 JWT 鉴权中间件，用 Fastify，token 从 header 取"
  → AI 一次给出 → 你测一下 → 改两处 → 完事
```

**难点是"把需求说清楚"。** 上下文够用，AI 一次能看全。

### Vibe 一个项目（你现在想做的）

```
第 1 天   AI 写了路由模块，用了 EventEmitter
第 3 天   新会话，AI 写调用模块，用了 AsyncGenerator —— 和路由对不上
第 5 天   新会话，AI 写记忆模块，自己发明了一套 store 接口 —— 和前面两套都不一样
第 8 天   你让它改路由，它把第 1 天的设计推翻重写了
第 12 天  三个模块各自能跑，串起来全是类型错误
```

**难点不是"AI 写不好代码"，是"AI 记不住你们上次商量好的东西"。**

### 核心矛盾

```
项目有结构（模块边界、数据契约、设计约束）
      ×
AI 的上下文装不下整个项目，而且每次新会话都从零开始
      ↓
结构必须由你持有，并且在每次会话开始时重新注入
```

**所以 vibe 一个项目的核心技能不是"写好 prompt"，
是"维护一份能反复注入的架构约束，并在每次产出后验收它有没有被违反"。**

**注意这句话** —— 它和 Clowder 的 L0 治理块、Skills、SOP 门禁解决的是**同一个问题**。
你会在 §9 看到完整的对应关系。

## 2. 你要先准备四份"喂养资产"

**不要一上来就让 AI 写代码。** 先花半天准备这四份东西，
后面每次会话开头都要贴一遍（或者放进项目的 `CLAUDE.md` / `AGENTS.md` 让 CLI 自动加载）。

### 资产一：愿景一页纸（≤ 300 字）

**作用**：防止 AI 把项目做成另一个东西。

**模板**：

```markdown
# 项目愿景

## 一句话
<产品是什么，给谁用，解决什么问题>

## 明确不做的三件事
1. <边界一>
2. <边界二>
3. <边界三>

## 成功长什么样
<一个能演示的场景，具体到用户点了什么、看到什么>
```

**为什么"明确不做的三件事"比"要做什么"更重要？**

因为 AI 天然倾向于**加功能**。你说"做一个多 Agent 协作平台"，
它会给你加用户系统、权限系统、计费系统、插件市场。

**参考 Clowder 的做法**：它的 `CONTRIBUTING.md` 里有三条
"Contributor Guardrails"，第一条就是"Cozy Café, not RPG ——
我们不做硬核 RPG 系统、技能树、XP 数值"。

**明确的否定边界比正面描述更能约束 AI。**

### 资产二：架构约束清单（≤ 15 条）

**作用**：这是你的"L0"—— 每次会话都要注入的硬约束。

**模板**：

```markdown
# 架构约束（每次改代码前必读）

## 技术选型（已定，不要重新讨论）
- 语言/运行时：<...>
- 框架：<...>
- 存储：<...>
- 包管理：<...>

## 模块边界（不许跨）
- <模块 A> 只能通过 <接口> 调用 <模块 B>
- <某某> 的真相源是 <某文件>，其他地方只能读不能写

## 数据契约（改动要同步）
- <核心类型> 定义在 <文件>，改它要同时改 <消费方清单>

## 硬规则
- 所有存储操作走接口，不直接调 <redis/sqlite> 客户端
- 所有对外的错误都要带 reason 字符串
- 不要引入新依赖，除非我明确同意
- 不要重写已有模块，除非我明确要求
```

**最后两条是重点。**

【推断，但我很确定】**AI 最常见的两个破坏性行为是：
① 顺手装个新库；② 觉得旧代码不好就重写了。**

这两条写进约束能挡掉八成。

### 资产三：模块契约表

**作用**：让每次会话只关心一个模块，但知道它的接口。

**模板**：

```markdown
# 模块契约

| 模块 | 职责 | 对外接口 | 依赖 | 状态 |
|------|------|---------|------|------|
| router | 决定叫醒哪个 Agent | `route(msg): AsyncIterable<Event>` | registry, invoker | ✅ 已实现 |
| invoker | 调起一次 Agent | `invoke(params): AsyncIterable<Event>` | provider | ✅ 已实现 |
| memory | 存取知识 | `search(q): Item[]` / `upsert(item)` | — | 🚧 进行中 |
| ... | | | | ⬜ 未开始 |
```

**这张表的价值**：新会话开始时，AI 看一眼就知道
"哪些已经有了、接口长什么样、我这次要动的是哪个"。

**关键是"对外接口"那一列要写具体的签名**，
不是"提供搜索功能"这种废话。

### 资产四：验收清单模板

**作用**：AI 说"做完了"的时候，你拿这个对。

```markdown
# 本次改动验收

- [ ] 能跑起来（给出启动命令和预期输出）
- [ ] 有测试，且我亲眼看到测试**先红后绿**
- [ ] 没有引入新依赖（或者引入了并说明了理由）
- [ ] 没有改动本次范围外的文件（给出 git diff --stat）
- [ ] 接口签名和模块契约表一致
- [ ] 类型检查通过
```

**"先红后绿"这条最重要** —— 见 §7。

## 3. 分阶段路线：七个里程碑

**核心原则：每个里程碑结束时都必须有一个能演示的东西。**

**不要按模块开发**（先写存储层、再写业务层、最后写接口）——
那样前三周你什么都看不到，而且 AI 会在没有反馈的情况下越跑越偏。

**要按"能演示的切片"开发。**

### 里程碑 1：能调起一个 Agent 并看到流式输出（2~3 天）

```
做完能演示：
  浏览器输入一句话 → 后端 spawn 一个 claude 子进程 →
  流式输出实时显示在页面上

砍掉：
  多 Agent、路由、记忆、身份、会话管理 —— 全部
  只有一个写死的 Agent
```

**为什么这个必须是第一个？**
因为它打通了整条链路（前端 → HTTP → WebSocket → 子进程 → 流式解析 → 推回前端）。
后面所有功能都是往这条链上挂东西。

**如果这一步卡住，后面全是空中楼阁。**

### 里程碑 2：身份注入（1 天）

```
做完能演示：
  Agent 知道自己叫什么、有什么性格，回复的语气明显不同
  换一个配置，行为立刻变

砍掉：
  队友名册、家规编译、动态段 —— 只做最简单的静态身份 + 一行身份锚
```

**这一步很便宜但效果立竿见影**，能给你信心继续。

### 里程碑 3：多 Agent + @ 路由（3~4 天）

```
做完能演示：
  @agent-a 说话 → A 回复
  A 的回复里写 @agent-b → B 被自动叫醒

砍掉：
  并行、群组 @、回退梯级 —— 只做"行首 @ 单目标"
  但护栏要有：深度上限、自调用过滤
```

**这一步开始就是"多 Agent"了。** 护栏必须在这一步就加 ——
因为一旦 Agent 能互相调用，跑飞就是烧钱。

### 里程碑 4：会话管理 + 抗压缩（3~4 天）

```
做完能演示：
  长对话跑到上下文快满 → 自动封存 → 新 session 起来 →
  Agent 还知道自己是谁、在做什么

砍掉：
  三档 session 策略、hook 集成 —— 只做"到阈值主动封存"
  digest 用最简单的规则抽取，不调 LLM
```

**这是价值密度最高的一步** —— 因为它解决的痛点最真实。

### 里程碑 5：记忆与检索（4~5 天）

```
做完能演示：
  Agent 能搜到之前讨论过的东西并引用

砍掉：
  14 层排序、向量检索、知识治理 ——
  只做 SQLite FTS5 全文检索 + 从文档目录扫描建索引
```

**向量检索先不做。** FTS5 对小规模足够，而且省掉 embedding 服务这个依赖。
等你真觉得搜不准了再加。

### 里程碑 6：跨模型互审（2~3 天）

```
做完能演示：
  Agent A 写完代码，系统自动选一个不同模型的 Agent B 来 review

砍掉：
  封板协议、Provenance Matrix —— 只做 reviewer 匹配 + 不能自审
```

**这一步是"团队感"的第一个体现**，演示效果很好。

### 里程碑 7：一套纪律（3~4 天）

```
做完能演示：
  Agent 在不同阶段会自动加载不同的方法论
  违反硬规则时被门禁拦下

砍掉：
  完整的 SOP 引擎 —— 只做"阶段提示注入 + 三五条 predicate 检查"
```

**总计约四到五周**（每天投入几小时的话）。

**这个规模足够写进简历，而且每一步都能演示。**

## 4. 每个阶段的 prompt 模板

**这一节是可以直接复制的。**

### 模板 A：开新阶段（每个里程碑第一次会话）

```
我在做一个多 Agent 协作平台。先读这三份文件建立上下文：
- docs/VISION.md（愿景，300 字）
- docs/ARCHITECTURE.md（架构约束，15 条）
- docs/MODULES.md（模块契约表）

读完先告诉我：
1. 用你自己的话复述这个项目要做什么（不超过 3 句）
2. 当前已实现的模块有哪些，接口是什么
3. 这次我们要做 <里程碑名>，你认为需要改动哪些文件

**先不要写代码。** 等我确认你的理解对了再开始。
```

**"先不要写代码"这句极其重要。**

【推断】AI 默认行为是立刻开始写。但如果它对项目的理解是错的，
写得越多返工越大。**让它先复述，是最便宜的对齐手段。**

### 模板 B：具体实现（确认理解之后）

```
现在实现 <具体功能>。

## 要求
<3~5 条，每条一句话，具体到可验证>

## 明确不做
<2~3 条边界>

## 接口约定
<给出你想要的函数签名，让它照着实现>

## 约束
- 不引入新依赖
- 不改动 <文件清单> 之外的文件
- 存储走 <某接口>，不直接调客户端

## 交付
1. 先写测试（我要看到它失败）
2. 再写实现
3. 给我 git diff --stat
```

**"接口约定"那段是关键。**

如果你不给签名，AI 会自己发明一个，
然后下次会话它又发明一个不一样的。
**你给签名 = 你在持有架构。**

### 模板 C：新会话继续（最常用的一个）

```
继续昨天的工作。

## 当前状态
- 已完成：<列表>
- 进行中：<这次要做的>
- 已知问题：<列表>

## 先做这三件事，做完再等我确认
1. 读 docs/ARCHITECTURE.md 和 docs/MODULES.md
2. 跑 <测试命令>，告诉我现在是什么状态
3. 读 <本次要改的文件>，告诉我它现在的结构

不要立刻改代码。
```

**这个模板解决的是"新会话从零开始"的问题。**
让它先自己把上下文读回来，比你贴一大堆代码更省 token 也更准。

### 模板 D：验收（AI 说做完之后）

```
按这个清单自查，逐条给我证据：

- [ ] 跑起来了吗？给我启动命令 + 实际输出（不要说"应该能跑"）
- [ ] 测试呢？给我测试命令 + 实际输出
- [ ] 测试是先红后绿的吗？如果你是先写实现后补测试，直说
- [ ] git diff --stat，我要看改了哪些文件
- [ ] 有没有引入新依赖？git diff package.json
- [ ] 接口签名和 docs/MODULES.md 一致吗？

**如果某一条没做到，直接说没做到，不要含糊过去。**
```

**最后那句要每次都加。**

【推断】模型有很强的"让对话看起来成功"的倾向。
明确给它一个"承认没做"的许可，能显著提高诚实度。

### 模板 E：改动已有模块（最危险的场景）

```
我要改 <模块>。

## 先回答，不要动代码
1. 这个模块现在的对外接口是什么？谁在调用它？
2. 我要的改动会不会影响调用方？
3. 有没有更小的改法？

## 硬约束
- **不要重写这个模块**。只做最小改动。
- 如果你认为需要重写，先说服我，说明为什么小改不行。
```

**"不要重写"这条必须写。**
AI 看到不合它口味的代码就想重构，这是 vibe 一个项目最大的破坏源。

## 5. AI 的七种典型失败模式

**这一节是你的"验收雷达"。** 认得出信号，才能及时拦。

### 失败一：偷偷换技术栈

**信号**：diff 里出现 `package.json` 变化；代码里出现你没听过的库。

**为什么会这样**：AI 训练数据里某个库更常见，它默认用那个。

**对策**：约束清单里写死"不引入新依赖，除非我明确同意"，
验收时必看 `git diff package.json`。

### 失败二：重写而不是改

**信号**：`git diff --stat` 显示某个文件 `+300 -280`。

**为什么会这样**：改一个不熟悉的实现比重写难，重写对 AI 更容易。

**对策**：模板 E 的"不要重写"约束 + 每次都看 diff stat。

### 失败三：接口漂移

**信号**：两个模块对接时类型对不上；同一个概念有两个名字。

**为什么会这样**：新会话不记得上次定的签名。

**对策**：模块契约表 + 每次会话开头让它读一遍 + 验收时对签名。

### 失败四：测试后写（然后必然通过）

**信号**：它给你的测试一次就绿；或者你问"测试先红了吗"它含糊。

**为什么会这样**：先写实现更顺手，测试是补的。

**为什么这个致命**：
**测试写在实现之后会立即通过 —— 你永远不知道它是否真的在测你要的东西。**

**对策**：要求它**贴出测试失败时的输出**。
这个要求很难造假（造假需要编一段合理的失败信息）。

### 失败五：过度设计

**信号**：你要一个功能，它给你一个框架；出现"为了将来扩展"这类措辞。

**为什么会这样**：训练数据里的"最佳实践"文章都在教抽象。

**对策**：需求里写"**只做当前需要的，不要为未来扩展做抽象**"。
以及：看到接口/抽象类/泛型时问一句"现在有几个实现？"——
**只有一个实现的抽象基本都是过度设计。**

### 失败六：静默降级

**信号**：功能"能跑"但效果不对；日志里有 catch 但没输出。

**为什么会这样**：AI 倾向于让代码"不崩"，于是到处 try/catch 吞掉错误。

**对策**：约束里写"**不要静默吞异常。要么向上抛，要么记录并明确降级**"。

**这条和 Clowder 的"降级必须可见"是同一件事**（见 §9）。

### 失败七：说"完成了"但没验证

**信号**：用"应该可以""理论上""通常会"这类词。

**对策**：模板 D 的逐条要证据 + 那句"没做到就直说"。

## 6. 一个反直觉的建议：给 AI 更少的上下文

**新手常犯的错**：把整个项目贴给 AI，以为上下文越多越好。

**实际效果**：

```
贴 5000 行代码
  → AI 的注意力被稀释
    → 它会"顾及"很多不相关的地方
      → 产出变保守、变啰嗦、开始加不必要的兼容代码
```

**正确做法**：

```
给它：
  ✅ 架构约束（15 条）
  ✅ 模块契约表（接口签名）
  ✅ 本次要改的那 1~3 个文件
  ✅ 直接调用方的接口

不给：
  ❌ 无关模块的实现
  ❌ 整个 src 目录
```

**判断标准：如果这段代码这次不会改、也不会被本次改动影响，就不要给。**

**而且这正是 Clowder 做的事** ——
它的 `ContextAssembler` 只给最近 20 条消息 / 2000 token，
`SessionBootstrap` 硬上限 2000 token，然后告诉 Agent
"想知道更多用工具查"。**给入口和指针，不给全量。**

## 7. 验收：怎么判断"做完了"是真的

**三个"不可造假"的验收手段**，按可靠性排序：

### 手段一：让它贴实际输出

```
❌ "测试通过了"
✅ 贴 pnpm test 的完整输出，包括通过数和耗时
```

**造假成本高** —— 要编一段格式正确的输出。

### 手段二：让它贴 `git diff --stat`

```
一眼看出：改了几个文件、每个文件加删多少行
超出预期范围立刻能发现
```

### 手段三：你自己跑一遍

**最可靠，而且只要一条命令。**

【推断】这是很多人跳过的一步 —— 觉得"AI 说跑通了应该没问题"。
**但你只要跑一次就能发现三成的问题。**

### 一个具体的验收节奏

```
每个里程碑结束时：
① 你自己从零跑一遍（git clone 到新目录 → install → build → start）
② 演示一遍核心场景（录个屏更好，将来面试能放）
③ 更新模块契约表
④ commit 一个带 tag 的版本
```

**第 ④ 步很重要** —— 有 tag 你才能在 AI 把东西改坏时回退。

**第 ② 步录屏在面试里价值很高** —— "我可以给你看个 demo"比什么都有说服力。

## 8. 上下文管理：你会遇到和这个项目一模一样的问题

**这一节有点元 —— 但它是真的。**

你 vibe 到第三周的时候会遇到这些：

| 你遇到的问题 | Clowder 的对应设计 |
|---|---|
| 新会话 AI 不知道项目是什么 | **静态身份注入**（每个新 session 注一次） |
| 聊长了 AI 忘了自己在做哪个模块 | **每轮身份锚**（15 token，每轮都注） |
| 上下文压缩后它忘了做到哪一步 | **连续性胶囊**（只存控制流状态） |
| 换会话时要重新交代进度 | **会话封存 + bootstrap digest** |
| AI 违反了之前定的架构约束 | **L0 治理块**（从 Markdown 编译，每次注入） |
| 不同任务需要不同的方法论 | **Skills 按需加载** |
| AI 跳过了该做的步骤（比如测试） | **SOP predicate 门禁** |
| AI 说完成了但没验证 | **"完成附证据"的家规 + quality-gate** |
| 你自己判断不了它写得对不对 | **跨模型互审**（让另一个模型审） |

**所以我建议你在 vibe 的过程中，直接借用它的手法：**

### 手法一：把架构约束写进 `CLAUDE.md`

Claude Code 会自动加载项目根的 `CLAUDE.md`。
**把你的 15 条架构约束放进去，等于每次会话自动注入 L0。**

### 手法二：写一份 `docs/PROGRESS.md` 当"交接摘要"

```markdown
# 当前进度（每次会话结束时更新）

## 已完成
- 里程碑 1：能调起 Agent（tag: v0.1）
- 里程碑 2：身份注入（tag: v0.2）

## 进行中
- 里程碑 3：@ 路由
  - ✅ 行首 @ 解析
  - 🚧 深度限制（正在做）
  - ⬜ 自调用过滤

## 已知问题
- WebSocket 重连后会丢一条消息（暂不修）

## 下一步
- 先修深度限制的 off-by-one
```

**每次新会话开头让 AI 读它。**
这就是手动版的 session bootstrap。

### 手法三：用另一个模型 review

```
让 Claude 写完 → 复制关键代码 → 给 GPT/Gemini：
"这段代码有什么问题？特别关注边界条件和错误处理。
 不要客气，我要的是找茬。"
```

**这就是手动版的跨模型互审。**
【推断】效果比让同一个模型自己 review 好得多 —— 原因见 [11 章](11-模块-跨模型互审.md)。

### 手法四：给自己定几条"predicate"

```markdown
# 我的门禁（每次 commit 前）
- [ ] 类型检查过了（tsc --noEmit）
- [ ] 测试全绿
- [ ] 没有新依赖
- [ ] PROGRESS.md 更新了
```

**手动版的 SOP 门禁。**

## 9. 元观察：Clowder 的每个设计都是 vibe coding 的一个答案

**这一节是本篇最有价值的部分，也是面试里的高分材料。**

把这个项目的核心设计和"人怎么指挥 AI 干活"对照一下：

```
痛点                          Clowder 的解法              你 vibe 时的对应做法
──────────────────────────────────────────────────────────────────────────
AI 不知道自己是谁              静态身份注入 + 每轮身份锚      CLAUDE.md + 每次会话复述
AI 忘了上次商量的架构          L0 从 Markdown 确定性编译      架构约束清单，每次贴
AI 上下文满了丢失进度          连续性胶囊 + 会话封存          PROGRESS.md + git tag
AI 不知道什么时候该用什么方法    Skills 按需加载 + manifest    针对不同任务的 prompt 模板
AI 跳过步骤                    SOP predicate + CI 门禁       你自己的 checklist
AI 说完成但没验证              "完成附证据" + quality-gate    要求贴实际输出
AI 自己审自己发现不了问题       跨模型互审 + 不能自审          换个模型 review
AI 跑偏了没人拦                Scope Guard + 最小杠杆         "明确不做"清单
AI 反复犯同类错误              Self-Evolution + 30 天验证     把踩过的坑写进约束清单
```

**这张表说明一件事：**

> **Clowder 本质上是"把人指挥 AI 的经验，固化成了系统"。**
>
> 它的每一个"看起来很重"的设计，都对应一个真实的、
> 任何用 AI 干活的人都会遇到的痛点。

**面试话术（这段很有杀伤力）**：

> "我研究这个项目最大的收获，不是学会了某个技术点，
> 是**看懂了它每个设计对应什么痛点**。
>
> 比如它有个'每轮注入 15 token 的身份锚'的设计，
> 一开始我觉得有点小题大做。
> 但我自己用 AI 做项目的时候就撞上了 —— 聊长了之后，
> 模型开始不记得项目是什么、不记得上次定的接口、
> 甚至把之前写好的模块推翻重写。
>
> 然后我回头看它那些设计，全都对上了：
> L0 治理块对应'架构约束要每次注入'、
> 连续性胶囊对应'上下文压缩后进度会丢'、
> 跨模型互审对应'同一个模型审不出自己的问题'、
> Scope Guard 对应'AI 会不断加功能跑偏'。
>
> **它本质上是把'人怎么指挥 AI 干活'的经验固化成了系统。**
>
> 我现在自己做东西也在用它的手法 ——
> 架构约束写进 `CLAUDE.md`、进度写进 `PROGRESS.md` 当交接摘要、
> 关键代码换个模型 review。这些都是从这个项目学来的。"

**这个回答的好处**：
- 诚实（没说是你设计的）
- 有深度（说明你理解了"为什么"而不只是"是什么"）
- 有实践（说明你真的用上了）
- **而且它把"我经验少"变成了优势** —— 你在讲一个真实的学习和应用过程

## 10. 一个务实的提醒：不要 vibe 出一个你解释不了的东西

**这是 vibe coding 最大的风险，而且和面试直接相关。**

```
AI 帮你写了 5000 行
  → 跑起来了，演示很好看
    → 面试官问"这块的错误处理怎么做的"
      → 你不知道，因为你没读过
```

**对策：每个里程碑结束时，花半小时读一遍 AI 写的代码。**

不需要读懂每一行，但要能回答三个问题：

```
① 这个模块的入口在哪？（哪个函数是外面调进来的）
② 数据从哪来、到哪去？
③ 出错了会怎样？
```

**能回答这三个，面试时就不会崩。**

**而且有个技巧**：让 AI 帮你读。

```
"给我讲一下你刚才写的 <模块>：
 1. 对外的入口函数是哪个
 2. 数据流是什么
 3. 有哪些错误路径，分别怎么处理
 用大白话，假设我三个月后才会再看这段代码"
```

**把它的回答存成 `docs/modules/<模块>.md`。**
这既是文档，也是你面试前的复习材料。

## 11. 本篇速查

### 四份喂养资产

| 资产 | 长度 | 作用 | 什么时候用 |
|---|---|---|---|
| 愿景一页纸 | ≤300 字 | 防跑偏 | 每次新会话 |
| 架构约束清单 | ≤15 条 | 你的 L0 | 每次新会话（放 CLAUDE.md 自动加载） |
| 模块契约表 | 一张表 | 防接口漂移 | 每次新会话 |
| 验收清单 | 6 条 | 防虚假完成 | 每次交付 |

### 七个里程碑

```
1. 调起一个 Agent + 流式输出   2~3 天   ← 打通全链路，最重要
2. 身份注入                    1 天     ← 便宜且效果明显
3. 多 Agent + @ 路由 + 护栏     3~4 天   ← 护栏必须同时做
4. 会话管理 + 抗压缩            3~4 天   ← 价值密度最高
5. 记忆与检索（FTS5，不上向量） 4~5 天
6. 跨模型互审                  2~3 天   ← 演示效果好
7. 一套纪律                    3~4 天
                        合计约 4~5 周
```

### 五个 prompt 模板

| 模板 | 场景 | 关键句 |
|---|---|---|
| A 开新阶段 | 里程碑第一次会话 | "**先不要写代码**，先复述你的理解" |
| B 具体实现 | 确认理解之后 | 给出**接口签名**让它照着实现 |
| C 新会话继续 | 最常用 | "先读文档 + 跑测试 + 读文件，**不要立刻改代码**" |
| D 验收 | 它说做完之后 | "**没做到就直说，不要含糊过去**" |
| E 改已有模块 | 最危险 | "**不要重写**。要重写先说服我" |

### 七种失败模式

| 失败 | 信号 | 对策 |
|---|---|---|
| 偷偷换技术栈 | `package.json` 变了 | 约束"不引入新依赖" |
| 重写而不是改 | diff `+300 -280` | 约束"不要重写" |
| 接口漂移 | 类型对不上 | 模块契约表 + 每次读 |
| 测试后写 | 一次就绿 | 要求贴**失败时**的输出 |
| 过度设计 | "为了将来扩展" | 问"现在有几个实现" |
| 静默降级 | 能跑但效果不对 | 约束"不要静默吞异常" |
| 假完成 | "应该可以""理论上" | 逐条要证据 |

### 四个直接借用 Clowder 的手法

```
① 架构约束 → CLAUDE.md（自动注入，等于 L0）
② PROGRESS.md → 手动版 session bootstrap
③ 换模型 review → 手动版跨模型互审
④ commit 前 checklist → 手动版 SOP 门禁
```
