# 03 · 模块：路由与编排

> 路由是整个系统的第一个决策点：**一条消息进来，叫醒谁、叫几只、按什么顺序、
> 什么时候必须停下来。**
>
> 最后那一句"什么时候必须停下来"是多 Agent 系统独有的 ——
> 单 Agent 不存在"两个 Agent 互相调用停不下来"这种问题。

---

## 0. 30 秒电梯版

> "路由层做三次判断：**目标集**（叫醒谁）、**意图**（讨论还是执行）、
> **策略**（并行还是串行）。
>
> 串行路径支持 Agent 之间接力 —— 一只 Agent 回复完，
> 系统扫它的文本，发现行首有 `@另一只`，就把那只追加到待办列表里。
> 并行路径**禁止**接力，因为并行 × 链式 = 组合爆炸。
>
> 最关键的设计是护栏：'该不该派下一只'这个判断被收口成了**一个纯函数**，
> 输入是只读快照，输出是结构化决策，不做任何副作用。
> 之前这套判断散在两个地方各写一遍，是一个 feature 改了七轮 review 才收敛的根因。"

---

## 1. 它解决什么问题

用户在一个多 Agent 的群聊里发消息，系统必须回答：

```
问题一：这条消息是给谁的？
   @opus 帮我看下          → 明确
   帮我看下                 → ？（没 @ 任何人）
   @all 大家讨论一下         → 所有人？
   @全体布偶猫              → 某个品种？
   @thread                  → 这个帖子的参与者？

问题二：多个目标的话，他们之间什么关系？
   @opus @codex 你们怎么看   → 各说各的（并行）
   @opus 做完让 @codex review → 接力（串行）

问题三：Agent 回复里又 @ 了别人，要不要继续？
   opus: "@codex 你看下"     → 要
   opus: "codex 之前说过…"    → 不要（只是提到）
   已经来回 8 次了            → 该停了
```

**问题三是这个模块最难的部分。**

---

## 2. 不做会怎样

### 场景 A：没有目标集回退逻辑

```
用户：@opus 帮我实现 F123
opus：（做完了，回复）
用户：辛苦了，那顺便把测试也补一下          ← 没有 @
系统：不知道给谁 → 报错 / 或者给默认 Agent
```

**用户体验直接崩** —— 正常聊天没人会每句话都 @ 一遍。

### 场景 B：没有护栏

真实的失控形态：

```
opus:  "@codex 这个方案你看下"
codex: "@opus 我觉得应该改成 X"
opus:  "@codex 但是 X 有个问题"
codex: "@opus 那可以试试 Y"
opus:  "@codex Y 也不行因为…"
...
```

每一轮都是一次完整的 Agent 调用 —— 几万 token 输入 + 工具调用 + 输出。
**跑一晚上能烧掉几百美元，而且它们真的会这样。**
LLM 天然倾向于礼貌回应，所以互相 @ 会自然形成闭环。

### 场景 C：并行还允许链式

```
用户 @ 了 3 只 Agent（并行）
  → 每只都 @ 出 2 只 → 6 个新调用
    → 每个又 @ 出 2 只 → 12 个
      → 深度 15 层…
```

指数爆炸。所以项目从架构上直接禁掉了这条路。

### 场景 D：Agent 之间的对话把用户饿死

```
用户发消息 → 进队列（因为目标 Agent 忙）
  Agent A 和 B 正在 A2A 接力
    → 每轮结束又追加下一只
      → 队列里的用户消息永远排不上
```

**用户发的消息比 Agent 之间的消息更重要**，但队列不知道这件事。
所以需要"公平性闸门"。

## 3. 怎么设计的

### 3.1 全景

```
用户消息
   │
   ├─ 判断一：目标集 ────────────────────────────┐
   │    ① 显式 @mention                          │
   │    ② 群组 @（@all / @全体{品种} / @thread）   │
   │    ③ 回退梯级（上一条用户消息的 @ → 最近回复者 │
   │                → 偏好 Agent → 默认 Agent）    │
   │                                              │
   ├─ 判断二：意图 ───────────────────────────────┤
   │    #ideate → 讨论   #execute → 执行           │
   │    无标签：≥2 只 → ideate，1 只 → execute      │
   │                                              │
   └─ 判断三：策略 ───────────────────────────────┘
        ideate + 多只 → routeParallel（并行，不许链式）
        execute 或单只 → routeSerial（串行，支持 A2A 链）
                            │
                            ▼
                    ┌───────────────┐
                    │ worklist      │  运行中可增长的数组
                    │ = [opus]      │
                    └───────┬───────┘
                            │ 执行 opus
                            ▼
                     解析回复文本
                            │  发现行首 @codex
                            ▼
                ┌───────────────────────┐
                │ resolveRoutingDecisions│  ← 六道护栏（纯函数）
                └───────────┬───────────┘
                            │ 通过
                            ▼
                    worklist = [opus, codex]
```

代码分布：

| 文件 | 行数 | 职责 |
|------|------|------|
| `AgentRouter.ts` | 1752 | 三次判断 + 目标集计算 |
| `route-serial.ts` | 3687 | 串行执行 + A2A 链 |
| `route-parallel.ts` | 1649 | 并行执行 + 流合并 |
| `routing-decision.ts` | ~200 | **护栏纯函数** |
| `IntentParser.ts` | ~75 | 意图解析 |
| `WorklistRegistry.ts` | 405 | worklist 注册与 streak 追踪 |

**注意 serial 是 parallel 的 2.2 倍长** —— 因为所有护栏都长在串行路径上。

### 3.2 判断一：目标集的三级瀑布

**① 显式 @**

见 [模块 04](04-模块-mention解析.md)，这里只说结论：
只认行首、最长匹配优先、单条最多 2 只。

**② 群组 @**

```
@all / @全体              → 所有可路由的 Agent
@全体布偶猫 / @all-ragdoll  → 该品种（模型家族）全部
@thread / @本帖 / @全体参与者 → 本帖参与过的 Agent
```

实现上有两个细节值得讲：

```ts
// Sort longest-first to avoid prefix collisions (@全体布偶猫 before @全体)
```

```ts
// substring collisions like @allison→@all or @threadsafe→@thread
```

**`@allison` 不能被当成 `@all`。** 这类边界处理在这份代码里到处都是 ——
因为路由错一次的代价是叫醒错的模型、烧真金白银。

**③ 回退梯级 —— 这段最值得在面试里讲**

没有 `@` 的时候要回看历史，找上一条**用户消息**的 `@`。
源码注释记录了三轮 review 的完整演进【源码】：

```ts
/**
 * F194 Phase Z5 AC-Z16: 无 @ fallback 回看最近 thread messages 找上一条 user message
 * 的 mentions。
 *
 * Spec 窗口 = N=5 USER messages OR 时间窗口 1h（防远古 mentions 主导 fallback）。
 *
 * 实现 = 以 USER message 为停止条件分页扫 thread messages（不是固定 thread message
 * 窗口）：cat-to-cat handoff / vision guard / cross-post 等 cat 消息不消耗 user count
 * 也不能挤掉远一点的 user mention。
 *
 * 砚砚 review 历程：
 *   R1 P1：原实现 `getByThread(threadId, 5)` 取最近 5 条 thread messages，user @ 后
 *     只要 5 条 cat/vision-guard 就把 user mention 挤出窗口 → Bug D 复活。
 *   R2 P1：R2 改成 `getByThread(threadId, 50)` + 反向数 N=5 user msgs + 1h cutoff，
 *     但仍然是单页 thread window — 51+ 条 cat 消息夹中间就退化回原 bug。
 *   R3 P1（当前）：改成分页 loop（getByThread 拉首页 → 不够再 getByThreadBefore
 *     拿历史页），停在 N=5 USER msgs / 1h cutoff / 没有更多消息。
 *     defensive 上限 = Z5_PAGE_SIZE * Z5_MAX_PAGES = 250 条 thread messages。
 */
const Z5_PAGE_SIZE = 50;
const Z5_USER_MESSAGE_COUNT_LIMIT = 5;
const Z5_TIME_WINDOW_MS = 60 * 60 * 1000; // 1h
```

**这段的教训，用大白话说是：**

> 在单 Agent 系统里，"最近 N 条消息"是个安全的窗口定义。
> 在多 Agent 系统里，**Agent 自己产生的消息会稀释这个窗口**——
> 你以为在看最近 5 条用户消息，实际看到的是 5 条 Agent 之间的交接记录。

修法是三层叠加：

```
① 计量单位从"thread 消息"换成"user 消息"   → 解决稀释
② 加时间闸门 1 小时                          → 防远古 @ 复活
③ 加页数上限 250 条                          → 防无限翻页
```

**面试里这段特别好用**，因为它是一个"看起来很简单的需求
（没 @ 就用上次的），实际要考虑三个维度"的例子。

### 3.3 判断二：意图解析

`IntentParser.ts` 出奇地短：

```ts
export function parseIntent(message: string, targetCatCount: number): IntentResult {
  let explicitIntent: Intent | null = null;
  const promptTags: string[] = [];

  for (const match of message.matchAll(/#(\w+)/gi)) {
    const tag = match[1]?.toLowerCase();
    if (INTENT_TAG_SET.has(tag)) explicitIntent = tag as Intent;
    else if (PROMPT_TAG_SET.has(tag)) promptTags.push(tag);
  }

  if (explicitIntent) return { intent: explicitIntent, explicit: true, promptTags };

  // Auto-infer: ≥2 cats → ideate, 1 cat → execute
  const intent: Intent = targetCatCount >= 2 ? 'ideate' : 'execute';
  return { intent, explicit: false, promptTags };
}
```

四条规则：

| 输入 | 结果 |
|------|------|
| 显式 `#ideate` | ideate |
| 显式 `#execute` | execute |
| ≥2 只且无标签 | **ideate**（并行独立思考） |
| 1 只且无标签 | **execute**（串行执行） |

另有 `#critique` 标签：**改变思维方式，不改路由**。

**"多只默认并行"这个默认值的理由**（面试要能讲）：

```
@opus @codex 这个方案你们怎么看？
  → 想要的是两个独立观点
  → 一旦串行，第二只会被第一只的答案锚定
  → 所以并行，两只互相看不见对方的回答
```

**并行的价值在于独立性。** 项目把它设成默认，就是在保护这个独立性。

### 3.4 判断三：两种执行策略

**routeParallel**

```
     用户消息
   ┌───┼───┬───────┐
   ▼   ▼   ▼       ▼
 opus codex gemini …    同时 spawn，各自独立上下文
   │   │   │       │
   └───┴───┴───────┘
        │
   mergeStreams()      流式合并，前端看到交错增量
```

`mergeStreams` 是个干净的小工具，值得单独提一句 ——
它是"带标签的 `Promise.race` 池"：

```ts
function arm(index: number): void {
  pending.set(index, it.next().then(
    (result) => ({ ok: true,  value: { index, result } }),
    (error)  => ({ ok: false, value: { index, error } }),
  ));
}
```

**为什么要打 `index` 标签？** 因为 `Promise.race` 只告诉你"谁先完成"，
不告诉你"是哪个流"。race 出来之后要重新 arm 对应的 iterator，必须知道是哪个。

**为什么 rejection 被 catch 成 `{ ok: false }`？**
让错误不冒泡到 race —— **一只 Agent 崩了不影响其他 Agent 继续输出。**

**routeSerial**

```
  worklist = [opus]
      │
   invoke opus ──► 回复文本
                    │
              parseA2AMentions()
                    │ 发现 "@codex 帮我 review"
                    ▼
          resolveRoutingDecisions()   ← 护栏
                    │ 通过
                    ▼
  worklist = [opus, codex]    动态增长
      │
   invoke codex ──► 继续检测…
```

**并行永不链式**，源码注释写死了：

```
 * A2A only triggers here in routeSerial; routeParallel never chains (MVP safety boundary).
```

`worklist` 除了文本 @ 能增长，MCP 回调（`callback-a2a-trigger`）也能触发追加目标：

```ts
// Worklist pattern: starts with targetCats, may grow via A2A mentions
// F27: Register worklist so callback A2A can push targets here
```

**但注意上面这条 `F27` 注释描述的是 legacy 路径。**
MCP 回调追加 A2A 目标现在**默认走 `InvocationQueue.enqueue`（agent 条目），
不是直接 push worklist** —— push worklist 只在队列依赖没接线时作为兜底。
不过两条路径**共享同一份 streak 状态**（都挂在 `WorklistRegistry` 上），
护栏语义是对齐的。完整的三代演进（F27 之前 spawn 独立调用 → F27 push worklist
→ F122B 入 queue）见 [模块 13](13-模块-MCP回调桥.md) §7 和 [模块 22](22-深潜-队列与并发控制.md)。

### 3.5 护栏：`resolveRoutingDecisions`

**这是本模块最值得讲的设计。**

先看它为什么要重构【源码】：

```ts
/**
 * F216 c1.2: routeSerial 决策层 — 纯函数统一路由 guard。
 *
 * routeSerial 历史上把"该不该派下一只猫"的 depth/dedup/streak/pendingTail 判断散在
 * inline-mention (route-serial.ts:1703-1797) 和 relay (route-serial.ts:1126-1150)
 * 两段里各写一遍，加任何决策都要多处同步改 → 笛卡尔积式炸 edge case
 * （F215 7 轮 review 的根因）。
 */
```

**"同一套判断写在两个地方，是 7 轮 review 才收敛的根因。"**
这句话面试里价值很高 —— 它是一个具体的、有数字的重复代码代价。

重构后的形态：

```ts
export function resolveRoutingDecisions(
  signal: RoutingSignal,   // 输入：三种触发形态之一
  ctx: RoutingContext,     // 输入：只读快照
): RoutingDecision[]       // 输出：结构化决策，零副作用
```

**输入的只读快照**（这张表就是六道护栏的清单）：

```ts
export interface RoutingContext {
  a2aCount: number;                 // 当前深度
  maxDepth: number;                 // 上限（默认 15）
  aborted: boolean;                 // 用户点了停止？
  queuedMessagesPending: boolean;   // 队列里有用户消息在等 → 公平性闸门
  pendingTail: readonly CatId[];    // worklist 未执行的尾巴 → 去重
  pendingOriginalTargets: readonly CatId[];  // 这些该回用户，不该被当 A2A
  hasActiveAgent: (cat: CatId) => boolean;   // 跨路径去重
  peekStreak: (target: CatId) => { wouldBlock: boolean; count: number };  // 乒乓预判
}
```

**输出的五种决策**：

```ts
export type RoutingDecision =
  | { action: 'enqueue_worklist'; cat: CatId }   // 放进 worklist，马上排
  | { action: 'defer_queue';      cat: CatId }   // 排到非-agent 消息之后
  | { action: 'mark_replyto';     cat: CatId }   // 只标 replyTo，不重复派
  | { action: 'skip'; cat: CatId; reason: 'depth' | 'dedup_active' | 'aborted' | 'queue_pending' }
  | { action: 'block_pingpong'; cat: CatId; pairCount: number };
```

**guard 链的顺序**：

```
abort → queue-pending → depth → dedup_active → pendingTail → streak → enqueue
```

**逐个用大白话讲清楚为什么需要：**

| 闸门 | 防什么 |
|------|--------|
| `aborted` | 用户点了停止，别再派新的 |
| `queue_pending` | 队列里有用户消息在等 → **公平性**，别让 A2A 链饿死用户 |
| `depth` | 链太长了，钱包护栏 |
| `dedup_active` | 这只 Agent 已经在队列里跑了，别重复派 |
| `pendingTail` | worklist 尾巴上已经有它了，别重复 |
| `streak` | 这两只已经来回 4 次了，硬切 |

### 3.6 一个设计洁癖：副作用不进纯函数

```ts
/**
 * **不做任何副作用** —— worklist.push / updateStreakOnPush(mutate) / span 创建 / yield
 * 都留在 routeSerial 执行层 apply decision 时做
 * （砚砚 GPT-5.5 OQ3：副作用不进决策函数，否则纯函数变上帝函数）。
 */
```

**"否则纯函数变上帝函数"** —— 这是从 review 里长出来的约束，不是教科书抄的。

好处很实在：**六道护栏的所有组合都能用单元测试穷举**，
不需要起 Redis、不需要 mock 进程。

### 3.7 深度预算怎么消费（一个隐蔽的 bug）

```ts
let depth = ctx.a2aCount;
for (const cat of signal.cats) {
  const decision = resolveInlineCat(cat, ctx, depth);
  if (decision === null) continue;
  decisions.push(decision);
  // enqueue 和 defer 都是真实的路由槽位，都消费预算
  // skip / mark_replyto / block_pingpong 不消费
  if (decision.action === 'enqueue_worklist' || decision.action === 'defer_queue') depth++;
}
```

注释点名了 bug 来源【源码】：

```
// 只计 enqueue_worklist 会让 batch resolve 无限 emit defer_queue 越过 maxDepth
// （砚砚 review PR#1991 P2）
```

**大白话**：`defer_queue` 也是一次真实的路由（只是延后执行），
如果不算它的深度，一批解析就能绕过深度上限，无限延后派发。

**这类"看起来能绕过去的漏洞"在多 Agent 系统里就是钱包漏洞。**

### 3.8 乒乓检测：先劝后拦

```
streak >= 2  →  软提醒：往 prompt 里注入警告
streak >= 4  →  硬阻断：yield a2a_pingpong_terminated
```

软提醒的内容【源码】：

```ts
/**
 * F167 L1: ping-pong streak warning.
 * When present (streak >= 2), inject a warning prompt reminding the cat
 * that they've been bouncing the same pair back and forth — consider
 * third-party input / wrap up / escalate to co-creator instead of another volley.
 */
pingPongWarning?: {
  pairedWith: CatId;   // 对面那只
  count: number;       // ≥2, <4
};
```

对应的 prompt 模板 `d5-ping-pong-warning.md`。

**"先劝后拦"这个顺序体现了整个项目的风格**：
优先给模型自己收手的机会，实在不行才由代码硬切。

**为什么不直接硬切？**
因为硬切会让对话在半途断掉，用户看到的是"系统终止了讨论"，
而软提醒能让 Agent 自己做个总结再交回给用户 —— 体验完全不同。

## 4. 为什么这么设计

逐个决策点讲取舍。

### 决策 A：为什么把护栏做成纯函数

**取舍**：多写一层抽象（signal + ctx + decision 三个类型），
换取可穷举测试 + 单点修改。

**证据**：注释明说是 "F215 7 轮 review 的根因"。
7 轮 review 的成本远高于多写 200 行抽象。

**面试可以补一个通用判据**【推断】：

> "什么时候该把判断逻辑提成纯函数？我的判据是：
> **这个判断有多少个输入维度，会被多少个地方调用。**
> 这里是 6 个维度 × 3 个调用点 = 18 种组合要保持一致 ——
> 手工同步必然出错。
> 如果是 2 个维度 1 个调用点，提抽象反而是过度设计。"

### 决策 B：为什么并行禁止链式

**取舍**：牺牲功能（并行讨论完不能自动交接），换成本可控。

**替代方案**【推断】：可以给并行也加深度限制，只是更严（比如深度 2）。
项目选了直接禁掉。

**我认为直接禁是对的**，理由：
并行本来就是"要独立观点"的场景，独立观点收集完应该由**用户**决定下一步，
而不是让 Agent 自己接力下去。所以这个限制和语义是一致的，不只是成本考虑。

### 决策 C：为什么"多只默认并行"

**取舍**：保护观点独立性（高频场景），代价是串行场景要用户显式写 `#execute`。

**这是我认为的一个缺陷**，见 §6。

### 决策 D：为什么公平性闸门只挡"非 agent"消息

```ts
/** F185 Phase B: non-agent fairness gate for text-scan A2A — user + connector block, agent does not. */
```

**大白话**：队列里有**用户**或**外部平台**（飞书/企微）的消息在等，
就不许展开新的 A2A 跳转；但队列里有 **Agent** 的消息在等，不挡。

**为什么这么分？** 因为如果 Agent 的消息也挡，
A2A 链会互相阻塞 —— A 排队等 B，B 排队等 A，死锁。

**这个区分很精细，面试里讲出来很有说服力。**

## 5. 否掉了哪些方案

### 方案一：A2A 走独立的分发通道，不进队列

**【ADR】ADR-018 明确记录了这个否决：**

> ### OQ-1: A2A handoff 入 queue + auto-execute ✅
>
> **决定**：A2A callback 产生的任务入 InvocationQueue，
> 但标记为 `auto-execute`，系统自动执行不需要用户批准。
>
> **效果**：
> - A2A 任务在 QueuePanel 可见（用户知道猫猫在干嘛）
> - 用户可以 steer 插队纠正方向（猫猫聊歪了能拉回来）
> - 用户发消息时，系统知道前面有 A2A 在排队，正确排序
>
> **放弃的方案**：保持 A2A 走独立 WorklistRegistry 分发。
> 理由：**不可见、不可控、两套分发平面维护成本高**。

**这条在面试里非常好用**，三个否决理由层次清晰：

| 理由 | 大白话 |
|------|--------|
| 不可见 | 用户不知道 Agent 在干什么，只能干等 |
| 不可控 | Agent 聊歪了没法插话纠正 |
| 两套平面维护成本高 | 用户消息一套、A2A 一套，排序/取消/暂停都要写两遍 |

**"可见性"这条尤其值得讲**：
多 Agent 系统一个很容易忽略的产品问题是 —— **Agent 之间聊起来之后，
用户就被排除在外了**。把 A2A 也放进用户能看见的队列里，
用户才有"我还在场"的感觉，才能 steer。

### 方案二：thread 级判忙（不是 slot 级）

**【ADR】同一份 ADR-018：**

> ### OQ-4: 保持 slot 级判忙 ✅
>
> **放弃的方案**：thread 级判忙（`has(threadId)`）。
> 理由：太粗，猫A忙时猫B也被锁，牺牲并行性。

对应代码里的注释【源码】：

```ts
/**
 * F108: ExecutionSlot(threadId, catId) 为并发执行的基本单元。
 * - 同一 catId 在同一 thread 仍保持单锁语义（新调用 abort 旧调用）
 * - 不同 catId 在同一 thread 可以并发执行
 */
```

### 方案三：句中 @ 也路由

见 [模块 04](04-模块-mention解析.md) §5。
【源码】项目文档明确写了"早期版本尝试过，带来误报和歧义"。

### 方案四：multi_mention 走独立通道

**【ADR】ADR-018 OQ-2：**

> **决定**：multi_mention 产生的子调用也入 InvocationQueue + auto-execute，
> 与 A2A handoff 一致。
>
> **理由**：multi_mention 本质是"一次 @ 多只猫"，
> 产生的每个子调用和 A2A handoff 语义相同。
> 统一入 queue 消除独立分发平面。

**"消除独立分发平面"是这三个 OQ 的共同主线** ——
方案一、二、四本质上是同一个决策的三个侧面：**一切派发走同一条路。**

## 6. 如果重新设计

【推断】以下全是我的方案。

### 6.1 意图判断改成"模型判断"

**现在的问题**（§4 决策 C 的代价）：

```
@opus 帮我实现，做完让 @codex review
  → 机械规则：2 只 Agent + 无标签 → ideate（并行）
  → 实际语义：串行
  → codex 会去 review 一个还不存在的实现
```

**我的方案**：

```
路由前先做一次极轻量的意图判断
  ├─ 走"轻活通路"（模块 02 §7.2 提的 API 直连）
  ├─ prompt：只给消息文本 + 目标列表，问"串行还是并行"
  └─ 成本：几百 token，几百毫秒
```

**为什么这个改动符合项目自己的原则？**
项目的核心原则是"机械层做路由，判断层留给模型"（见模块 04）。
串并判断本质上是**语义判断**，恰恰应该归模型。
项目在这一处用了机械规则，我认为是不一致的。

**代价**：多一次调用（延迟 + 成本），而且模型也可能判错。
**缓解**：保留显式标签作为覆盖手段，模型只在无标签时兜底。

### 6.2 护栏配置化，不是硬编码

现在深度、扇出、streak 阈值散在各处：

```ts
const MAX_A2A_MENTION_TARGETS = 2;                    // a2a-mentions.ts
Number(process.env.MAX_A2A_DEPTH) || 15               // a2a-mentions.ts
// streak 阈值 2 / 4                                   // 散在 route-serial + WorklistRegistry
```

**我会做成一张策略表**：

```ts
interface RoutingPolicy {
  maxFanoutPerMessage: number;      // 2
  maxChainDepth: number;            // 15
  pingpongWarnAt: number;           // 2
  pingpongBlockAt: number;          // 4
  fairnessBlockSources: readonly ('user' | 'connector' | 'agent')[];  // ['user','connector']
  parallelAllowsChaining: boolean;  // false
}
```

**收益**：
- 可以 per-thread / per-project 覆盖（有的项目愿意花更多 token 换深度）
- 可以做实验（A/B 不同的深度上限，看效果）
- 一处能看全所有护栏，新人不用翻五个文件

**代价**：多一层间接。而且现在的 `getMaxA2ADepth()` 每次现读 env 是为了热更新，
配置化要保留这个能力。

### 6.3 A2A 检测从"文本扫描"改成"结构化优先"

**现在的机制是扫回复文本找行首 `@`。** 这有个根本问题：
**Agent 的输出格式是它自己控制的，系统只能猜。**

代码里为此打了一堆补丁：

```ts
isZeroWidthChar()                    // LLM 会插入零宽字符
repairLineStartMentionWhitespace()   // "@ 布 偶 猫" 要先修复
while (line[cursor] === '*' || line[cursor] === '_') cursor++;   // 跳过 markdown 加粗
```

**项目其实已经有结构化通路了**（`F055 A2A MCP Structured Routing`，
ROADMAP 里还是 `spec` 状态），但默认还是文本扫描。

**我的方案**：反过来 —— **结构化优先，文本扫描降级为兜底**。

```
Agent 想交接给别人
  ├─ 优先：调 MCP 工具 handoff({ to: 'codex', reason: '...' })
  │        → 结构化，没有解析问题，能带 effect class（FYI/派活/协调）
  └─ 兜底：文本里写 @codex
           → 文本扫描（保留，因为不是所有 CLI 都可靠地调工具）
```

**为什么不能只要结构化？**
因为有些 Agent（比如纯文本输出的 Antigravity）调工具不可靠。
文本兜底必须保留。

**收益**：主路径不用再处理零宽字符、markdown 加粗、空白修复这些脏活。

### 6.4 我不会改的

| 我原本的想法 | 为什么放弃 |
|------------|-----------|
| 并行也允许链式（加严格深度限制） | 并行的语义就是"收集独立观点"，收完该由用户决定；自动接力和语义冲突 |
| 把 `route-serial.ts` 和 `route-parallel.ts` 合并 | 它们的差异是本质的（一个有 worklist 一个没有），合并会引入大量 `if (isSerial)` |
| 用状态机描述整个路由流程 | 试想过，但路由是"一次性决策链"不是"长生命周期状态"；球权那边才适合状态机 |

## 7. 和其他模块怎么咬合

### 上游（谁调用路由）

```
routes/messages.ts        用户发消息
routes/callback-a2a-trigger.ts   Agent 通过 MCP 触发交接
routes/callback-multi-mention-routes.ts   多方询问
QueueProcessor.executeEntry()    队列出队执行
infrastructure/connectors/*      飞书/企微/Telegram 消息
```

**五个入口都汇聚到 `AgentRouter`。**
这就是 ADR-018 那三个 OQ 的成果 —— 统一执行通道。

### 下游（路由调用谁）

```
AgentRouter
  ├─ IntentParser              解析意图
  ├─ resolveCatTarget          @handle → catId + 可用性
  ├─ SessionManager            拿/开 session
  ├─ route-serial / parallel
  │    ├─ SystemPromptBuilder  组装身份（模块 07）
  │    ├─ ContextAssembler     组装历史（模块 09）
  │    ├─ SessionBootstrap     上一段会话（模块 08）
  │    ├─ invokeSingleCat      真正调用（模块 05）
  │    ├─ parseA2AMentions     检测交接（模块 04）
  │    ├─ resolveRoutingDecisions  护栏
  │    └─ BallCustodyIngest    发球权事件（模块 10）
  └─ messageStore.append       落库
```

### 共享状态（谁和路由共用数据）

| 状态 | 谁写 | 谁读 |
|------|------|------|
| `worklist` | 路由（push）、MCP 回调（legacy 兜底才 push；默认改为入 queue） | 路由（遍历执行） |
| streak 计数 | `WorklistRegistry.updateStreakOnPush` | 护栏 `peekStreak`（只读预判） |
| `InvocationTracker` slots | 路由 start/complete | 路由判忙、队列判忙、取消 |
| `InvocationQueue` | routes 入队、路由 defer | `QueueProcessor` 出队 |
| thread 参与者活跃度 | 每次消息落库 | reviewer 匹配（模块 11）、`@` 消歧（模块 07） |

**`peekStreak` 这个命名值得注意**【源码】：

```ts
/** 只读 streak 预判（不 mutate；配对 peekStreakOnPush）。 */
peekStreak: (target: CatId) => { wouldBlock: boolean; count: number };
```

护栏是纯函数，不能改 streak。所以有一对方法：
`peekStreakOnPush`（预判，不改）和 `updateStreakOnPush`（真改）。
**决策时 peek，执行时 update。**

### 一条完整的咬合链

```
用户 @opus
  → 路由算出 [opus]
    → 模块 07 组装身份 prompt（含队友名册，让 opus 知道能 @ 谁）
      → 模块 05 spawn 子进程
        → opus 回复里写 "@codex review"
          → 模块 04 解析出 [codex]
            → 护栏放行
              → 模块 10 发球权事件：ball.handed(opus → codex)
                → 路由把 codex 加进 worklist
                  → 模块 07 为 codex 组装 prompt
                     （这次带 directMessageFrom=opus，
                       所以 codex 知道要回复给 opus 不是用户）
                    → 模块 11 的 canReview 判定 codex 能不能审 opus 的代码
```

**注意最后两步的因果**：
`directMessageFrom` 这个字段是路由传给 prompt 层的，
而 prompt 层用它决定注入哪个模板（`d2-direct-message.md`）。
**没有这个字段，codex 会以为在跟用户说话。**

## 8. 面试怎么讲

### 30 秒版

见 §0。

### 3 分钟版

> "路由做三次判断：目标集、意图、策略。
>
> **目标集**有三级瀑布：显式 @ → 群组 @ → 回退梯级。
> 回退这块有个坑值得讲：'没 @ 就用上一条用户消息的 @'听起来简单，
> 但 Agent 自己产生的消息会稀释窗口 ——
> 你以为在看最近 5 条用户消息，实际看到的是 5 条 Agent 交接记录。
> 他们改了三轮：从固定 5 条消息，到 50 条里数 5 条用户消息，
> 最后到分页扫直到数满 5 条用户消息，加 1 小时时间闸门和 250 条页数上限。
>
> **策略**分并行和串行。多只 Agent 默认并行，因为并行能保护观点独立性 ——
> 一旦串行第二只就被第一只锚定了。而且并行**禁止**链式接力，
> 因为并行 × 链式是组合爆炸。
>
> **最值得讲的是护栏。** '该不该派下一只 Agent'这个判断被收成了一个纯函数：
> 输入是六个维度的只读快照（是否中止、队列有没有用户消息在等、
> 当前深度、是否已在跑、worklist 尾巴有没有它、乒乓次数），
> 输出是五种结构化决策，**不做任何副作用**。
> 注释里写了原因：之前散在两个地方各写一遍，
> 是一个 feature 改了七轮 review 才收敛的根因。
> 还有句话我觉得挺好 —— '副作用不进决策函数，否则纯函数变上帝函数'。"

### 常见追问

**Q：怎么防止两个 Agent 无限互相调用？**

> "四层，从软到硬：
>
> 一，**扇出上限 2**：单条消息最多 @ 两只。
> 二，**深度上限 15**：链最长 15 跳。而且这个值是每次现读环境变量的，
> 注释写了 `read at call time for hot-reload`——链跑飞时能不重启就收紧。
> 三，**乒乓检测**：同一对 Agent 来回 ≥2 次，往 prompt 里注入警告
> '你们在来回弹球，考虑引入第三方 / 收尾 / 升级给人'；≥4 次直接硬切。
> 四，**公平性闸门**：队列里有用户消息在等时，不许展开新的 A2A 跳转。
>
> 我觉得第三层的设计最有意思 —— **先劝后拦**。
> 直接硬切用户看到的是'系统终止了讨论'，
> 软提醒能让 Agent 自己总结一下再交回来，体验完全不同。"

**Q：为什么 A2A 也要进队列？直接派发不是更快？**

> "他们的 ADR-018 明确否掉了直接派发，三个理由：
> 不可见、不可控、两套分发平面维护成本高。
>
> 我觉得'不可见'这条最重要。多 Agent 系统一个容易忽略的产品问题是 ——
> **Agent 之间聊起来之后用户就被排除在外了**，只能干等。
> 把 A2A 也放进用户能看见的队列，用户才有'我还在场'的感觉，
> 而且能插队 steer，Agent 聊歪了能拉回来。
>
> 代价是多一跳延迟，但换来的可观测性和可控性我觉得非常值。"

**Q：`route-serial.ts` 3687 行，你觉得该怎么拆？**

> "我会按'阶段'横切，而不是按'功能'纵切。
>
> 现在的结构是一个大 for 循环遍历 worklist，
> 循环体里混了：prompt 组装、调用、流式转发、A2A 检测、
> 落库、球权事件、遥测、错误处理。
>
> 我会抽成一个显式的 pipeline：
> `prepare → invoke → collect → detect → persist → advance`，
> 每一步一个函数，输入输出都是明确的数据结构。
> 护栏纯函数化已经证明了这条路可行 —— 那是 `detect` 那一步的成果。
>
> 但我要说清楚代价：**这种重构在有 3687 行历史包袱的文件上风险很高**，
> 因为里面每个防御分支都对应一个真实事故。
> 必须先把测试补到能覆盖那些 edge case，才能动。
> 所以我理解他们为什么还没拆 —— 他们有个 tech debt feature 在跟这件事。"

## 9. 本模块要点

| 要点 | 内容 |
|------|------|
| **三次判断** | 目标集 → 意图 → 策略 |
| **回退梯级的坑** | Agent 消息会稀释窗口；计量单位换成 user 消息 + 时间闸门 + 页数上限 |
| **多只默认并行** | 保护观点独立性；串行会锚定 |
| **并行禁止链式** | 组合爆炸；而且和"收集独立观点"的语义一致 |
| **护栏是纯函数** | 6 维只读快照 → 5 种决策，零副作用 |
| **7 轮 review 的根因** | 同一套判断散在两处各写一遍 |
| **defer 也算深度** | 否则一批解析能绕过上限 |
| **先劝后拦** | streak≥2 注入警告，≥4 硬切 |
| **公平性只挡非 agent** | 挡 agent 会造成 A2A 互相死锁 |
| **【ADR】三个 OQ 的主线** | 一切派发走同一条路，消除独立分发平面 |
| **我的改进** | 意图判断交给模型 / 护栏配置化 / 结构化交接优先 |
