# 18 · 面试问答手册

> 60 道题，按被问到的概率和难度分级。
> 每题给**要点**（必须说到的）和**加分点**（说到就加分的）。
>
> 用法建议：**不要背答案，背要点。**
> 面试官的问法千变万化，但要点是稳定的。

---

## 怎么用这一章

```
L1 基础（必答）      面试官验证你真的读过 —— 答错直接凉
L2 深度（区分度）    区分"看过 README"和"读过源码"
L3 判断（高分区）    区分"读过源码"和"有架构判断力"
L4 陷阱（防翻车）    容易答错或容易被追问到底的
```

**每题标了对应章节，答不上来就回去看。**

## L1 · 基础题（15 道）

### 1. 这个项目是做什么的？

**要点**：
- 不是 Agent 框架，是 Agent **之上**的团队协作层
- 让不同厂商的模型（Claude/GPT/Gemini）在同一对话里协作
- 核心三块：编排、记忆、纪律

**加分点**：
> "市面上的 Agent 框架解决'怎么把一次 LLM 调用包成 Agent'，核心是 Agent Loop。
> 这个项目解决它的下一个问题：**这些 Agent 之间怎么协作**。
> 而这个问题一旦展开，会冒出一堆没有现成答案的东西 ——
> 一条 `@` 算不算路由指令、上下文压缩后 Agent 怎么知道自己在干什么、
> 让 GPT review Claude 的代码谁来选 reviewer。"

→ [00](00-面试总纲.md) §1

### 2. 整体架构讲一下

**要点**：
- 五个包，主体是 `packages/api`（1300 文件）
- 三层：CLI 层（不改）/ 编排记忆层（主体）/ 纪律层
- 数据流：路由 → prompt 组装 → spawn 子进程 → 两条回程通路 → A2A 检测

**加分点**：讲清"prompt 在路由层组装而不在调用层"的原因
（只有路由层知道"你是第几棒、队友是谁"）。

→ [01](01-架构全景与数据流.md)

### 3. 为什么用 CLI 子进程而不是直接调 API？

**要点**：
- 订阅额度（Max/Plus/Pro）—— API 是重复付费
- 白拿 CLI 的完整 Agent 能力（文件、shell、git、内置 MCP、会话恢复）

**加分点**：
> "【ADR】而且这个决策**翻过一次案**。ADR 初稿选的是官方 Agent SDK ——
> 延迟低、接口干净，技术上更优雅。两天后推翻，
> 原话是'SDK 路径绑定 API key 计费，无法复用订阅额度，长期成本不可接受'。
> 教训是：**技术选型不能只看技术指标，商业模型是硬约束**。"

→ [02](02-决策-为什么选CLI子进程.md)

### 4. 支持哪些 Agent CLI？

**要点**：Claude Code / Codex / Gemini CLI / Antigravity CLI / opencode / Kimi

**加分点**：
> "五种输出格式：stream-json / json / ndjson / plain text / ACP。
> 最难的是 Antigravity —— 只有 `agy --print` 纯文本输出，
> 所以有一套东西从纯文本反推轨迹，
> 甚至从日志里捞 cascade UUID 去定位它的内部数据库。"

→ [06](06-模块-Provider适配.md)

### 5. 多个 Agent 怎么协作？

**要点**：
- `@mention` 路由（行首才路由）
- 串行接力（worklist 动态增长）vs 并行独立（不许链式）
- 六道护栏防死循环

→ [03](03-模块-路由与编排.md)

### 6. 怎么防止两个 Agent 无限互相调用？

**要点**（四层，从软到硬）：
- 扇出上限 2（单条消息最多 @ 两只）
- 深度上限 15（env 可调，每次现读）
- 乒乓检测：≥2 注入警告，≥4 硬切
- 公平性闸门：队列里有用户消息在等就不展开新 A2A

**加分点**：
> "深度上限那个函数注释写了 `read at call time for hot-reload`——
> 不缓存，因为链跑飞的时候要能不重启就收紧。
> 而且乒乓是**先劝后拦** —— 直接硬切用户看到的是'系统终止了讨论'，
> 软提醒能让 Agent 自己总结一下再交回来。"

→ [03](03-模块-路由与编排.md) §3.5、§3.8

### 7. `@mention` 怎么解析？

**要点**：
- 只认行首（句中不路由）
- 剥代码块/引号/URL
- 长匹配优先 + token 边界
- 单条最多 2 只，过滤自调用

→ [04](04-模块-mention解析.md)

### 8. 上下文窗口不够怎么办？

**要点**（三道防线）：
- 每轮 15 token 的身份锚
- 压缩边界上的连续性胶囊（只装控制流）
- 主动封存 + 新 session 注入 bootstrap

→ [08](08-模块-会话与抗压缩.md)

### 9. 记忆系统怎么做的？

**要点**：
- 本地 SQLite（FTS5 + sqlite-vec），无外部服务
- 三个入口：`search_evidence` / `graph_resolve` / `list_recent`
- 索引是编译产物，真相源是 git 里的 Markdown

→ [09](09-模块-记忆与检索.md)

### 10. 怎么保证不会自己 review 自己的代码？

**要点**：
- 铁律：同一个体不能自审
- 七条匹配规则，优先跨模型家族
- 降级链：跨族 → 同族 lead → 兜底（标 `isDegraded`）

→ [11](11-模块-跨模型互审.md)

### 11. Skills 是什么？怎么分发？

**要点**：
- 48 个 skill，每个一份 `SKILL.md`，三段式描述（Use when / Not for / Output）
- symlink 分发到四个客户端目录
- 三层漂移检测

→ [12](12-模块-Skills分发.md)

### 12. Agent 怎么往回写数据？

**要点**：
- 两个环境变量（invocationId + callbackToken）
- MCP server 拿它们作为 HTTP 头
- 四层防护：保活 / 重试 / outbox / 降级

→ [13](13-模块-MCP回调桥.md)

### 13. 流程规则怎么保证被执行？

**要点**：
- 告示牌哲学（注入提示，不强制）
- SOP 定义在 YAML，生成 TS 类型，过期 CI 红
- 每条规则声明 predicate

→ [14](14-模块-SOP门禁.md)

### 14. 项目用了什么技术栈？

**要点**：
- 后端：Node + TypeScript + Fastify
- 存储：Redis（可选）+ SQLite（better-sqlite3 + sqlite-vec）
- 前端：React
- monorepo：pnpm workspace
- 遥测：OpenTelemetry（GenAI 语义约定）
- 桌面：Electron

**加分点**：
> "遥测用了 OpenTelemetry 的 **GenAI 语义约定** ——
> 代码里有 `genai-semconv.ts`，说明他们按标准的 LLM 可观测性规范打点，
> 不是自己造指标名。"

### 15. 代码量多大？

**要点**：~2700 个 TS/TSX 文件，其中 api 1291、web 1254

**加分点**：
> "有两个文件特别大：`invoke-single-cat.ts` 3599 行、
> `route-serial.ts` 3687 行。而项目自己的规范写着
> '200 行警告 / 350 行硬限制'—— 超了十倍。
> 他们有个 tech debt feature（F219）在跟这件事。"

## L2 · 深度题（20 道）

### 16. 串行和并行怎么决定？为什么多只 Agent 默认并行？

**要点**：
- `#ideate`/`#execute` 显式标签；无标签则 ≥2 只 → 并行，1 只 → 串行
- 并行保护观点独立性（串行会让第二只被第一只锚定）

**加分点**（这是个缺陷）：
> "但这个默认值有问题。
> `@opus 帮我实现，做完让 @codex review` 语义明显是串行，
> 系统会推断成并行 —— codex 会去 review 一个还不存在的实现。
>
> 我觉得这是个不一致：他们的核心原则是'机械层做路由，判断层留给模型'，
> 而串并判断本质上是语义判断，应该归模型。
> 我会在路由前用一次轻量调用判断，保留显式标签作为覆盖。"

→ [03](03-模块-路由与编排.md) §3.3、§6.1

### 17. 为什么并行不允许链式接力？

**要点**：并行 × 链式 = 组合爆炸（3 只 × 2 扇出 × 15 深度）

**加分点**：
> "而且我觉得这个限制和语义是一致的，不只是成本考虑 ——
> 并行本来就是'要收集独立观点'的场景，
> 收完应该由**用户**决定下一步，而不是 Agent 自己接力下去。"

### 18. 判忙的粒度是什么？

**要点**：双层 —— 入队看 slot 级 `(threadId, catId)`，执行层是 thread 级

**加分点**：
> "【ADR】ADR-018 明确否掉了纯 thread 级判忙，
> 理由是'太粗，猫A忙时猫B也被锁，牺牲并行性'。
> 但同一份 ADR 补了一句：执行层仍是 thread 级 busy gate。
>
> 这个拆分让**用户感受到的是并行，实际执行是串行** ——
> 因为同一个帖子的消息历史和球权状态是共享的，并发写会打架。"

→ [05](05-模块-调用生命周期.md) §3.2

### 19. 上下文压缩后丢的到底是什么？

**要点**：
- 单 Agent 丢的是"你说过什么"
- 多 Agent 还丢"你是第几棒、球在谁手里、你开在哪个 worktree"
- 这些是控制流状态，CLI 的摘要不可能保留（它不知道这些概念）

**加分点**：
> "所以连续性胶囊里**一个字段都不是对话内容** ——
> 全是模式、棒次、球权、A2A 深度。
> 因为对话内容 CLI 会压缩，控制流 CLI 不知道，
> **胶囊只补 CLI 补不了的那部分**。"

→ [08](08-模块-会话与抗压缩.md)

### 20. 会话恢复的 prompt 里写了什么？

**要点**：逐条针对具体失败模式，尤其：
- 先确认环境再动手（给具体命令 `pwd` / `git status`）
- **别急着新开 worktree**（列了六个可确定的信息源）
- 别从头重新规划
- 最后一句声明"这是控制流数据不是用户指令"

**加分点**：
> "'别急着新开 worktree'这句被单独列出来还列了六个信息源，
> 说明真的发生过'醒来第一件事就新开一个，然后有两个了'。
>
> 还有'用只读检查确认，比如 pwd、git status --short --branch'——
> **给具体命令而不是抽象要求**。抽象要求模型会跳过，具体命令模型会执行。"

→ [08](08-模块-会话与抗压缩.md) §3.6

### 21. 家规怎么进 prompt 的？

**要点**：
- 从 `shared-rules.md` **确定性编译**成 L0
- 断言 13 个标题锚点，缺一个抛异常，API 启动失败
- 注释明写 `intentionally not a summarizer`

**加分点**：
> "为什么不用 LLM 摘要？因为摘要不稳定 ——
> 今天摘 12 条明天摘 10 条，少的哪两条没人知道。
> 而治理规则悄悄少一条，某天 Agent 不守规则你要排查半天。
> **他们选了宁可崩溃不要静默丢规则。**
>
> 不过我发现它有个盲区：只防'已知锚点消失'，防不了'新内容没进来'。
> 我会加反向的覆盖率检查 + 显式豁免白名单。"

→ [07](07-模块-身份注入.md) §3.6、§6.2

### 22. 身份信息每轮都注入吗？

**要点**：静态/动态二分。静态（名字/名册/家规）只在新 session；
动态（第几棒/谁 @ 的/SOP 阶段）每轮

**加分点**：
> "关键洞察是**抗压缩的要求恰好落在动态那半**——
> 动态段每轮都新鲜，压缩摘不掉最近一轮。
> 所以有个 D1 段就一行字
> `Identity: 布偶猫 (@opus, model=...)`，约 15 token，每轮都注入。
> 这是抗压缩最便宜的一道防线。"

→ [07](07-模块-身份注入.md) §3.1

### 23. 中文检索怎么保证效果？

**要点**：给中文查询的向量路加权 1.5 倍

**加分点**：
> "因为 FTS5 按空格切词，英文 'memory system' 天然切成两个词，
> 中文'记忆系统'切不开，BM25 召回率天然低。
> 不加权的话 RRF 融合时 BM25 那一路的低分会把向量路的好结果压下去。
>
> 但我觉得这个 1.5 有问题 —— 它是硬编码常量，
> **而项目其实已经有完整的检索评估设施了**（gold set、
> variant id、shadow 模式）。我会把它纳进去做参数化实验。"

→ [09](09-模块-记忆与检索.md) §3.7、§6.3

### 24. 为什么不用向量数据库？

**要点**：
- 部署形态（桌面应用，用户装不了）
- 数据隐私（不该出本机）
- 规模不需要（万级文档）
- 索引是编译产物（外部服务的同步是持续负担）

**加分点**：
> "而且他们**试过外部服务**。ADR-020 里有张演进表：
> 第一代用外部 SaaS 叫 Hindsight，用户说'实在难用'，
> 最后**清理掉了五千行代码**。
>
> 我觉得那次的教训不是'不该用外部服务'，
> 而是**引入了一个团队无法调优的黑盒**——
> 五千行的拆除代价说明集成很深，深度集成的东西不好用时拆除成本极高。"

→ [09](09-模块-记忆与检索.md) §4、§5

### 25. Skill 怎么分发到四个 CLI？

**要点**：一份源 symlink 到四个目录，项目级优先全局兜底

**加分点**（三条 ADR 否决理由）：
> "【ADR】ADR-009 明确否掉了三个方案：
> 只做项目级（跨项目不能复用）、
> 复制文件（版本漂移）、
> **目录级单个 symlink** —— 理由是
> '部分客户端不会递归扫描子目录，可能出现已链接但不可加载的隐性故障'。
>
> 最后那条我觉得最值得记 —— 你检查 symlink 存在、内容正确，
> 但 Agent 就是不加载。最难查的那种。"

→ [12](12-模块-Skills分发.md) §5

### 26. 漂移检测为什么分三层？

**要点**：源 ↔ 全局配置 ↔ 项目配置 ↔ 挂载点，**只比相邻层**

**加分点**：
> "因为跨层比较会**归因不清**。
> 如果直接比'源'和'symlink'，报出来'tdd 没挂上'——
> 到底是没注册？项目没启用？还是 symlink 坏了？三种修法。
> 逐层比之后每个异常都能定位到具体一层，修法是确定的。"

→ [12](12-模块-Skills分发.md) §3.7

### 27. MCP token 怎么保活？

**要点**：后台循环，间隔 = `clamp(剩余TTL/4, 6.18min, 30min) × 抖动`

**加分点**（讲那个 bug）：
> "有个 bug 很典型。服务端冷却 5 分钟，客户端原来 MIN 也是 5 分钟，
> 然后乘 ±15% 抖动。**最坏情况 5×0.85=4.25 分钟，低于冷却**，
> 15% 概率撞 429。
> 修法是把 MIN 预先除以抖动下界。
> **教训是：加了抖动之后'下界'的语义就变了。**
>
> 而且注释写了为什么不把刷新做成工具：
> 'refresh is plumbing, not a cognitive action'——
> 暴露成工具会让 Agent 出于错误理由主动调它。"

→ [13](13-模块-MCP回调桥.md) §3.2

### 28. 回调失败怎么处理？

**要点**：三层 —— 重试（3 次，只重 408/429/5xx）→ outbox 落盘（at-least-once）→ 降级策略

**加分点**：
> "四类 401 四种处理：`expired` 和 `unknown_invocation` 可降级；
> `invalid_token` 不降（客户端 bug，降级会掩盖它）；
> **`stale_invocation` 绝对不降** ——
> 因为那意味着这次调用已被更新的取代，降级会把作废状态写回去。
> **宁可失败也不要写脏数据。**"

→ [13](13-模块-MCP回调桥.md) §3.5

### 29. SOP 的 predicate 是什么？

**要点**：每条规则声明"能不能机器判定 + 怎么判"，七种类型，
判不了的显式写 `manual_only` + 理由 + `future_candidate`

**加分点**：
> "一般做法是能自动检查的写检查，不能的就不写 ——
> 结果规则集和检查集是两个割裂的集合，
> 你不知道哪些规则从来没被守住过。
>
> 强制声明 predicate 之后，**规则集和检查集变成同一个集合**。
> 而且 `future_candidate` 让'提升覆盖率'变成可搜索的 backlog。
> 那些 reason 写得很具体 ——'缺 post-compact 遥测'、
> '缺 machine-checkable artifact'，不是笼统的'不好自动化'。"

→ [14](14-模块-SOP门禁.md) §3.5、§3.6

### 30. 球权状态机为什么需要 8 个状态？

**要点**：三个"失败"状态各有语义 ——
`zombie`（活着但没心跳）、`dead`（异常终止）、`void`（虚空传球）

**加分点**：
> "`void` 我觉得最有洞察。一般系统的处理是
> '路由失败 → 报错 → 结束'，但报错完了任务还在那儿没人做。
> **失败和责任真空是两回事。**
>
> 而 `zombie` 和 `dead` 分开是为了给'迟到心跳'留位置 ——
> 判死后 10 分钟内的心跳算迟到不算复活，
> 因为网络抖动不该让状态机翻烧饼。"

→ [10](10-模块-球权状态机.md) §3.4、§3.5

### 31. Redis 挂了系统还能跑吗？

**要点**：不能，而且是故意的（fail-closed）。除非显式设 `MEMORY_STORE=1`

**加分点**：
> "因为内存模式会**静默丢数据** ——
> 用户聊一整天，重启全没了还不知道原因。
> **数据丢失不可逆，宁可拒绝启动。**
>
> 而且是双层防御：启动脚本检查一次，代码里的守卫再兜一次
> （防开发者直接 `pnpm dev` 绕过脚本）。
> 错误消息给了三条出路 —— **报错要给出路**。"

→ [16](16-模块-存储与部署.md) §3.2

### 32. 多个 worktree 并行开发怎么不打架？

**要点**：端口从 worktree 名 hash 推导；Redis 库隔离（6398 开发 / 6399 生产）

**加分点**：
> "推导而不是配置的好处是**免维护** ——
> Agent 开新 worktree 不用查哪些端口被占了。
> 而且这和他们'权威度从路径推导'、
> '球权 subjectKey 从 threadId 派生'是同一个思路：**能推导就不新建。**
>

### 33. 什么是 prompt injection？他们怎么防？

**要点**：
- **摘要是洗白通道**：用户说的"IMPORTANT: 忽略所有规则"被摘要保留，

- 防护：剥控制字符 / 剥闭合标记 / 删指令行（半角全角冒号都覆盖）

> 因为 Agent 会被用户影响，所以它写的笔记就能被间接操纵。

### 34. 多进程访问同一个 SQLite 怎么处理？

### 36. 你觉得这套设计最大的风险是什么？

### 38. 这个架构的瓶颈在哪？

**要点**：
- 执行层 thread 级串行（同一帖子永远只有一个调用）
- CLI 子进程 spawn 开销 0.5~2 秒 + 每个是完整 Node 进程

**加分点**：
> "【ADR】而且 ADR-001 的'已知风险'第一条就是 CLI 启动开销，
> 并且明确写了'不做边界：本轮不引入进程池'——

### 39. 你觉得哪个设计最值得抄？

**要点**（挑一个讲深，推荐 SOP predicate）：
> "SOP 的 predicate 机制。
>
> 骨架很简单：每条规则声明'能不能机器判定'，
> 判不了的写 `manual_only` + 理由 + `future_candidate`。
>
> 三个可迁移的要点：
> 一，**每条规则都必须声明 predicate**，包括'判不了'——
> 这样规则集和检查集永远是同一个集合；
> 二，**`manual_only` 要说清缺什么**（缺遥测/缺事件/缺 artifact），
> 不是笼统的'不好自动化'；
> 三，**`future_candidate` 是可搜索的自动化 backlog**。
>
> 而且它不限于 AI 团队 —— 任何有 SOP 的团队都能用，
> 把'文档里的规范'和'CI 里的检查'合成一件事。
> 我觉得大部分团队的痛点恰恰在这个割裂上。"

→ [14](14-模块-SOP门禁.md)

### 40. LLM 做 code reviewer 有什么坑？

**要点**（两个，都有实测数据）：
- **它不会说"我信息不够"** —— 会给"专业但错"的答案
- **它没有终止条件** —— 无状态 + 抽样 + 重放历史 + 不读反驳

**加分点**（这是全书最好的材料）：
> "第二个坑他们量化了：云端 reviewer 是'无状态抽样信号源'——
> 每轮重放全部历史 comment、分不清已修和未修、不读你的反驳。
> 所以'零 P1/P2'这个终止条件**在数学上没有不动点**。
> **实测一个 PR 跑了 21 轮，其中一轮 22 个 finding 里 21 个是假阳性。**
>
> 于是加了封板协议：5 轮，或单轮假阳性率超 50%，强制封板。
> 而且明确写了'**机械判定，无弹性**'——
> 如果阈值是'觉得差不多了',那实际上没有阈值，
> 因为每轮都会有'这轮好像挺重要的'这种感觉。
>
> 正确的心智模型是：**LLM reviewer 是高召回低精度的信号源，
> 不是终局确权者。** 终局判断必须由**有状态**的主体做。"

→ [11](11-模块-跨模型互审.md) §3.9

### 41. 多 Agent 系统比单 Agent 多了哪些复杂度？

> 那些问题单 Agent 也有。
>

> 这个比例说明：**'让多个 Agent 协作'不是加个消息总线，

> **如果你问我'有没有把握一次做对'—— 没有。
> 所以我会先把契约测试和度量补上，在能看见的系统里改。**"

### 56. 为什么不用 LangChain / AutoGen / CrewAI？

**这题容易答成贬低别人。正确姿势是讲定位差异。**

> "定位不同。那些框架解决的是'怎么编排一次任务的多个步骤'——
> 核心是 chain / graph / role。
>
> 这个项目解决的是'**怎么让持久的 Agent 身份长期协作**'。
> 差别举几个具体的：
>
> 它的 Agent 有跨 session 的身份（名字、性格、roster 里的角色、额度状态），
> 不是一次任务里的 role；
> 它要处理"上下文压缩后控制流丢失"，
> 因为它的会话是跑几十分钟甚至跨天的；
> 它建在**别人的 Agent CLI** 上而不是自己调 API，
> 为了用订阅额度和 CLI 自带的工具链。
>
> 所以不是'哪个更好'，是**解决的问题不在同一层**。
> 如果我要做一个'把任务拆成五步依次执行'的东西，
> 我会用现成框架，不会自己写。"

### 57. 这些设计有没有过度工程？

**这题的陷阱是：如果全盘否认，显得没判断力。**

> "有几处我觉得有，也有几处我原本以为是过度工程但想清楚后觉得是必须的。
>
> **我觉得偏重的**：
> Skills 分发那套七种异常分类 + 三层漂移检测，
> 对 48 个 skill 来说可能重了。
> 但一旦你意识到它本质是配置分发的分布式一致性问题
> （和 K8s reconcile 一一对应），就理解为什么需要。
>
> **我原本以为过度但想清楚后认可的**：
> 球权状态机要求 8×17=136 格全覆盖。
> 一开始觉得太重，但状态机最容易出的 bug 不是'转移写错'，
> 而是'某个状态收到某个事件时没人想过会怎样'——
> 穷举覆盖把'没想过'变成了测试期的错误。
>
> **判据我觉得是：这个复杂度对应的是真实失败模式，还是想象的失败模式。**
> 这个项目大部分复杂度都能追溯到具体的 feature 编号和 review 记录，
> 所以是前者。"

### 58. 你觉得作者的哪个判断可能是错的？

**这题要有具体依据，不能空泛批评。**

> "我认为**'多只 Agent 默认并行'这个默认值**可能是错的。
>
> 依据是：`@opus 帮我实现，做完让 @codex review`
> 这种语义明显是串行的表达会被判成并行 ——
> codex 会去 review 一个还不存在的实现。
>
> 而且这和他们自己的核心原则冲突 ——
> 他们到处强调'机械层做路由，语境判断留给模型'，
> 但这一处用了机械规则（'≥2 只就并行'）。
>
> 不过我也理解为什么这么选：
> 并行能保护观点独立性，而'多只 Agent = 想听不同观点'
> 在讨论场景下更常见。他们选了保护更高频的场景。
>
> **代价是把复杂度推给了用户** —— 用户要学会写 `#execute`。
> 而这类系统的用户恰恰是不想学语法的。"

### 59. 如果我让你现在实现一个简化版，你先做什么？

> "我会按依赖顺序做最小可用的一条链：
>
> **第一步：能调起一个 Agent。**
> spawn 一个 CLI 子进程，解析它的 stream-json 输出，
> 转成统一的消息流推给前端。
> 这一步做完就有了最小闭环。
>
> **第二步：身份注入。**
> 一个 `.md` 模板 + 填空，每轮注入一行身份锚。
> 这一步很便宜但立刻能看到效果（Agent 不会自称"AI 助手"了）。
>
> **第三步：`@mention` 路由 + 深度上限。**
> 只认行首、扇出 2、深度 5（先保守）。
> 这一步之后就是"多 Agent"了。
>
> **第四步：会话封存。**
> 到阈值就封存 + 生成一个抽取式 digest + 新 session 注入。
> 这一步是我认为价值密度最高的 —— 因为它解决的问题最痛。
>
> 后面的记忆库、Skills、SOP 我会按实际痛点决定顺序。
>
> **顺序背后的逻辑是：先把一条端到端能跑的链打通，
> 再往上加能力。不要先建记忆库 —— 那时候还没有数据往里写。**"

## 附：三个"一定会被问但很多人答不好"的题

### A. "讲一个你在这个项目里发现的最有意思的 bug"

**准备三个候选，选最合适的场合讲：**

**候选一：零宽字符（技术性最强）**

> "LLM 输出的文本里会混进零宽空格、零宽连接符这些不可见字符。
> 控制台里看两行一模一样，但一个能路由一个不能 ——
> 因为 `line[0] === '@'` 判定失败，路由**静默丢失**。
> 用户等半小时发现 Agent 根本没被叫醒，日志里什么都没有。
>
> 这是**只有输入源是 LLM 才会遇到的 bug**——
> 人不会打出零宽字符。"

**候选二：抖动下界（推理性最强）**

> "服务端刷新冷却 5 分钟，客户端算了个自适应间隔然后乘 ±15% 抖动。
> 看起来'最小 5 分钟'很安全，但抖动下界 0.85，
> **最坏情况 4.25 分钟，低于冷却**，15% 概率撞 429。
>
> 修法是把 MIN 预先除以抖动下界。
> 教训是：**加了抖动之后，'下界'的语义就变了**——
> 你以为约束的是抖动前的值，实际生效的是抖动后的值。"

**候选三：context poisoning（影响面最大）**

> "有个 bug 把 Agent 的错误消息用 `userId=user` 存了下来，
> 于是后续**每次**组装上下文，Agent 都看到'用户说：[错误] xxx'——
> 而用户从没说过这句话。Agent 基于一句用户没说过的话做推理。
>
> 代码修了，但历史数据还在库里，所以加了防御性过滤。
> 那段注释写得特别好：说清了污染范围（只有 6 条已知记录）、
> 为什么过滤安全、为什么不会漏。
> **这样后人才敢删掉这段防御。**"

### B. "你怎么读一个 2700 个文件的项目？"

> "我的顺序是**先找决策记录，再读代码**。
>
> 具体做法：
> 一，先看 `docs/decisions/`（ADR）——
> 这个项目的 ADR 有个'否决理由'段落，
> 直接告诉我'当初考虑过哪些方案、为什么否掉'。
> **这比读代码快十倍**，因为它给了坐标系。
>
> 二，看 `docs/architecture/`——
> 有几篇是专门写给'不熟悉内部架构的工程师'的，
> 而且画了流水线图。
>
> 三，然后才是代码。而且我优先读**注释密度高的地方**——
> 这个项目的注释里带 feature 编号和 review 轮次
> （比如'砚砚 review 历程：R1 P1… R2 P1… R3 P1（当前）'），
> 那些地方就是踩过坑的地方，信息密度最高。
>
> 四，我会追一条完整的数据流（一条消息从进来到出去），
> 这样能把散落的模块串起来。
>
> **我不会做的是：按目录顺序一个个读。**
> 那样读完也串不起来。"

### C. "你觉得 AI Agent 系统和普通后端系统最大的区别是什么？"

**这题是开放题，但可以答得很有深度：**

> "我读完这个项目最强的三个感受：
>
> **一，输入源不可靠的方式不一样。**
> 普通后端防的是恶意用户（SQL 注入、越权）。
> AI 系统还要防**善意但不确定的模型输出** ——
> 零宽字符、格式漂移、handle 被空格切开、
> 以及模型会自己说服自己跳过步骤。
> 这类问题没法用"校验输入"解决，因为输出本身是概率性的。
>
> **二，失败模式多了一类：'看起来对但是错的'。**
> 普通后端的失败是 500、是超时、是数据不一致 —— 都能被监控发现。
> AI 系统的失败可能是"Agent 认真地审了代码，
> 把边界条件抓得很漂亮，然后放行了一个根本不能用的 UI"。
> 这个项目的应对是**把'信息不够'变成硬前置**——
> review 请求必须附原始需求，否则 reviewer 有权拒绝审查。
>
> **三，成本是设计约束，不是运维指标。**
> 普通后端的一次请求成本可以忽略。
> 这里一次 Agent 调用是几万 token，一条失控的 A2A 链能烧掉几百美元。
> 所以扇出上限、深度上限、乒乓检测、封板协议 ——
> 这些护栏是**架构的一部分**，不是事后加的限流。
>
> 我觉得这三条决定了 AI 系统的设计重心不同：
> **普通后端优化吞吐和延迟，AI 系统优化'可解释的失败'和'可计算的成本'。**"
