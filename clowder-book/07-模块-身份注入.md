# 07 · 模块：身份注入与 L0

> 一次 LLM 调用是无状态的。但一只 Agent 要在成千上万次调用中**始终是同一只**——
> 有名字、有性格、有硬限制、知道队友是谁、记得团队家规。
>
> 这个模块回答：**这些信息怎么进 prompt，以及怎么在 token 预算内进。**
>
> 里面有一个我认为整个项目最硬核的设计：
> **家规不是用 LLM 摘要的，是用锚点断言"编译"出来的，缺一个锚点就启动崩溃。**

---

## 0. 30 秒电梯版

> "核心是**静态/动态二分**：不变的东西（名字、性格、队友名册、家规）
> 只在新 session 注入一次；会变的东西（你是第几棒、谁 @ 的你、
> 当前 SOP 阶段、乒乓警告）每一轮都注入。
>
> 而且 prompt 不写在代码里 —— 存在 `assets/prompt-templates/*.md`，
> 每段有编号（S1~S12 静态、D1~D20 动态），代码只负责填空。
> 有个开关能在生成的 prompt 里插入 `── [S5] 队友名册 ──` 这种分隔标记，
> 用来调试'这句话到底是哪段塞进来的'。
>
> 最硬核的是家规那块。家规原文是一份给人读的很长的 Markdown，
> prompt 里放不下。他们没用 LLM 摘要 —— 而是写了一个**确定性投影**：
> 断言 13 个必须存在的标题锚点，抽取 P1~P5 原理、W1~W8 世界观、
> ≥9 条 Magic Words，**缺一个就抛异常让 API 启动失败**。
> 注释里明说 `This is intentionally not a summarizer`。"

---

## 1. 它解决什么问题

### 问题一：Agent 怎么知道自己是谁

有三个显而易见的方案，全都不够用：

| 方案 | 问题 |
|------|------|
| 写进 CLI 的 `CLAUDE.md` | 只对 Claude Code 生效；改一次要同步四端；而且会被压缩摘掉 |
| 只在第一轮的 system prompt 里说 | 上下文压缩之后可能就没了 |
| 每轮全量重注入 | token 爆炸（名册 + 家规 + 工具索引 ≈ 几千 token × 每轮） |

### 问题二：Agent 怎么知道能 @ 谁

多 Agent 系统里，"能叫醒谁"这个信息必须在 prompt 里 ——
否则 Agent 不知道队友存在，永远不会交接。

而且这个信息很微妙：

```
队友有五只，但两只没额度  → 要不要列？（要，但标注不可用）
两只同名（都叫"布偶猫"）  → 怎么让 Agent 区分？
某只禁止写代码            → Agent 怎么知道不该派活给它？
某只当前跑的模型和默认不同  → 名册里显示哪个？
```

### 问题三：家规怎么进 prompt

团队家规（`shared-rules.md`）是一份给人读的长 Markdown：
第一性原理、世界观、决策漏斗、Magic Words、各种协议。

**prompt 里放不下全文，但每一条都不能丢。**

## 2. 不做会怎样

### 场景 A：不做每轮身份注入

```
第 1 轮  Agent 从静态身份知道自己是"布偶猫宪宪"
第 5 轮  上下文压缩，那段被摘要成了"助手介绍了自己"
第 6 轮  Agent 开始用"AI 助手"自称
第 7 轮  另一只 Agent @ 它，它以为在跟用户说话 → 回复给了用户
第 8 轮  git commit 签名写错
第 9 轮  跨模型互审判定失效（分不清谁是谁，同族分身可能自审）
```

**连锁反应**：身份丢 → A2A 错乱 → 互审失效。
**所以身份注入是 A2A 和互审这两个模块的前置条件。**

### 场景 B：名册里列了不能路由的 handle

```
prompt 说："你可以 @布偶猫"
但 registry 里只注册了 @opus-47
  → Agent 写了 "@布偶猫 帮我看下"
    → 解析器找不到这个 pattern
      → 路由丢失，静默失败
```

**prompt 和解析器必须用同一份真相源。**

### 场景 C：家规用 LLM 摘要

```
今天摘出来 12 条，明天摘出来 10 条
  → 少的那两条是哪两条？没人知道
    → 某天发现 Agent 不遵守某条规则
      → 排查半天，发现那条规则今天没被摘进去
```

**治理规则必须逐字稳定。摘要天然不稳定。**

## 3. 怎么设计的

### 3.1 静态 / 动态二分

```
┌─────────────────────────────────────────────────┐
│  静态身份 Static Identity                         │
│  S1~S12：名字 / 性格 / 硬限制 / 队友名册 / 家规 L0  │
│  ★ 只在【新 session】注入一次                      │
│  ★ resume 时不重复注入（省 token）                 │
├─────────────────────────────────────────────────┤
│  动态上下文 Invocation Context                    │
│  D1~D20：第几棒 / 谁 @ 的你 / SOP 阶段 /           │
│          乒乓警告 / 跨帖提示 / 引导状态             │
│  ★ 【每一轮】都注入                                │
└─────────────────────────────────────────────────┘
```

**核心洞察**：

> 不变的东西注入一次就够，会变的东西每轮都得重来。
> 而"抗压缩"的要求恰好落在动态那半 ——
> **因为它每轮都新鲜，压缩摘不掉最近一轮。**

### 3.2 prompt 是数据，不是代码

打开 `assets/prompt-templates/`：

```
静态段（S）
  s1-identity.md          s2-restrictions.md      s3-pack-masks.md
  s4-collaboration.md     s5-teammate-roster.md   s7-pack-workflows.md
  s8-cvo-reference.md     s9-governance-digest.md s10-pack-guardrails.md
  s11-pack-defaults.md    s12-world-driver.md

动态段（D）
  d1-identity-anchor.md   d2-direct-message.md    d3-same-breed-warning.md
  d4-cross-thread-reply.md d5-ping-pong-warning.md d6-teammates.md
  d7-mode-parallel.md / serial.md / solo.md
  d9-routing-feedback.md  d10-critique-tag.md     d11-skill-trigger.md
  d12-active-participant.md d13-routing-policy.md d14-sop-stage.md
  d15-voice-on.md / off.md d16-bootcamp.md        d17-guide-candidate.md
  d18-world-context.md    d19-constitutional-knowledge.md
  d20-signal-articles.md

L 层 / 其他
  l1-parallel-world.md ~ l7-collaboration-philosophy.md
  c1-mcp-callback.md      m1-dispatch-mission.md   n1-navigation.md
  handoff-decision-tree.md  a2a-ball-check.md     workflow-triggers.yaml
```

模板长这样（`s1-identity.md`）：

```markdown
<!-- @segment S1 — 身份声明 -->
<!-- Variables: NAME_LABEL, PROVIDER_LABEL, NICKNAME_ORIGIN, ROLE_DESCRIPTION, PERSONALITY -->

你是 {{NAME_LABEL}}，由 {{PROVIDER_LABEL}} 提供的 AI 猫猫。
{{NICKNAME_ORIGIN}}角色：{{ROLE_DESCRIPTION}}
性格：{{PERSONALITY}}
```

代码只负责填空：

```ts
const s1 = renderSegment('S1', {
  NAME_LABEL: nameLabel,
  PROVIDER_LABEL: providerLabel,
  NICKNAME_ORIGIN: nicknameOrigin,
  ROLE_DESCRIPTION: config.roleDescription,
  PERSONALITY: config.personality,
});
```

**三个好处（面试可以直接说）：**

1. 改 prompt 不用改 TypeScript、不用重新编译、不用发版
2. 每段有独立编号，能精确定位"这一句是谁注入的"
3. 可以做 prompt 的 git diff / 审计 / A/B 测试

### 3.3 段落标注：一个很实用的调试能力

```ts
// F237: segment annotation — preview inserts `── [SN] Name ──` markers
const mark = options?.annotateSegments
  ? (id: string, name: string) => { lines.push(`── [${id}] ${name} ──`); }
  : (): void => {};
```

开启之后生成的 prompt 长这样：

```
── [S1] 身份声明 ──
你是 布偶猫/宪宪（XianXian），由 Anthropic 提供的 AI 猫猫。
...
── [S2] 硬限制 ──
── [S5] 队友名册 ──
| 猫猫 | @mention · 当前模型 | 擅长 | 注意 |
...
```

**注意 `mark()` 在每个分支的两侧都调用了**：

```ts
if (config.restrictions && config.restrictions.length > 0) {
  mark('S2', '硬限制');
  // ...push content
} else {
  mark('S2', '硬限制');    // ← 即使没内容也标记
}
```

**为什么？** 这样看 preview 能分辨两种情况：
"S2 根本没渲染"（标记不在）vs "S2 渲染了但内容是空的"（标记在但下面没东西）。

**面试话术**：

> "prompt 组装涉及十几个条件分支，出问题时第一个要回答的是
> '这句话到底是哪段塞进来的'。他们做了个 `annotateSegments` 开关，
> 生成的 prompt 里插入 `── [S5] 队友名册 ──` 这种分隔标记。
>
> 而且标记在每个 if/else 的**两侧**都打 ——
> 这样能分辨'这段没渲染'和'渲染了但是空的'。
> 我觉得这个细节挺讲究的，说明他们真的用这个功能查过 bug。"

### 3.4 队友名册：一张四列表，每列都有讲究

`buildTeammateRoster` 产出：

```markdown
## 队友名册
| 猫猫 | @mention · 当前模型 | 擅长 | 注意 |
|------|---------|------|------|
| 缅因猫/砚砚 | @codex · gpt-5.5 | 审查严格，边界条件敏感 | … |
| 暹罗猫/烁烁 | @gemini · gemini-3 | 设计与视觉，发散思维 | 硬限制：禁止写代码 |
```

**第二列：句柄和模型必须"可见地"解耦**

```ts
// F167 Phase F (KD-21): surface resolved runtime model next to the @mention so
// sender's 认知真相 aligns with runtime catalog. Handle is identity constant;
// model is runtime-resolved metadata — the two must be visibly decoupled to
// prevent cargo-cult projection (e.g. "云端 codex bot" → 本地 @codex 快照).
```

**这个坑用大白话讲：**

> Agent 看到"codex"这个词，会本能地把**任何**叫 codex 的东西
> 都当成 `@codex` 这只队友 —— 包括 GitHub 上的云端 codex bot。
> 于是它会对着一个 CI 机器人喊"@codex 帮我 review"，然后等一个永远不来的回复。

解法是把"句柄"和"模型"并排显示，让它们**看起来就是两回事**：
`@codex · gpt-5.5`。句柄是身份常量，模型是运行时元数据。

还有个 P1 修复：

```ts
// P1 fix (cloud Codex review): resolve via getCatModel so env overrides show through,
// not the static template's defaultModel. Fall back to defaultModel only on error.
let resolvedModel: string;
try { resolvedModel = getCatModel(id); }
catch { resolvedModel = config.defaultModel ?? ''; }
```

**如果用静态模板里的 `defaultModel`，env 覆盖的模型不会反映在名册里** ——
Agent 看到 `gpt-5`，实际跑的是 `gpt-5.5`。

**"名册撒谎比名册缺失更糟"** —— 这句话可以当面试的总结。

**第三列：档案优先，配置兜底，而且告警条件很讲究**

```ts
// F208 KD-12: dossier l0RosterSummary → legacy teamStrengths → roleDescription
const dossierSummary = getDossierRosterSummary(id, projectRoot);

// KD-9: warn only for tracked cats (have dossier entry) missing l0RosterSummary.
// Runtime/custom cats with no dossier entry silently use config fallback.
if (!dossierSummary && hasDossierEntry(id, projectRoot)) {
  console.warn(`[F208 KD-9] cat "${id}" has dossier entry but missing l0RosterSummary — …`);
}
```

**只有"有档案但档案里缺这一项"才告警**；
完全没档案的运行时自定义 Agent 静默走兜底。

**这区分了"配置不完整"（该提醒）和"这类 Agent 本来就没档案"（不该刷屏）。**
—— 一个很小但很成熟的判断。

**第四列：硬限制取代了代码级的角色门禁**

```ts
// F167 Phase E (KD-20): surface hard restrictions alongside caution — data-driven
// replacement for the retired L3 role-gate. Sender sees e.g. "禁止写代码" so they
// self-regulate which cat to @ for which task; no harness-side regex.
```

**这是又一次"机械层 → 判断层"的迁移，而且是明确的"废弃"：**

```
原来（L3 role-gate，已废弃）：
  代码里判断"这只 Agent 不能写代码，拦下这次路由"

现在：
  把"禁止写代码"写进名册，让发起方自己看着办
  注释里明说 "no harness-side regex"
```

**面试怎么用这段**（这是个很好的例子）：

> "他们废掉了一个叫 L3 role-gate 的机制 ——
> 原来是代码里判断'这只 Agent 不能写代码，拦下路由'，
> 现在改成把'禁止写代码'写进队友名册，让发起方自己看着办。
> 注释里明确写了 `no harness-side regex`。
>
> 这和他们的 @mention 设计是同一个原则：**信息透明 + 模型判断，
> 而不是代码强拦**。
> 好处是没有 harness 侧的正则要维护，坏处是不保证。
> 但他们在整个项目里很一致地选了前者。"

**单元格长度限制**

```ts
const strengths = compactRosterCell(dossierSummary ?? config.teamStrengths ?? config.roleDescription, 52);
const cautionCell = compactRosterCell([...].join('；') || '—', 72);
```

52 和 72 个字符。**名册每个 session 都要注入，字数就是钱。**

### 3.5 同名消歧：三层防护

多 Agent 系统一个很实际的问题：两只 Agent 显示名相同
（都叫"布偶猫"，只是模型版本不同）。

**第一层：只用 registry 里真实存在的 handle**

```ts
function pickDisplayNameMention(config: CatConfig): string | null {
  // Do not synthesize @displayName unless the registry actually routes it.
  // Example: opus-47 shares displayName="布偶猫" but only registers @opus-47.
  return config.mentionPatterns.find((p) => p.toLowerCase() === expected) ?? null;
}
```

**不要合成 registry 里不存在的句柄** —— 否则 Agent 写的 @ 会路由失败。

**第二层：同名时只有默认变体能用短名**

```ts
const mention = group.length <= 1 || entry.config.isDefaultVariant
  ? pickDisplayNameOrVariantMention(entry.id, entry.config)
  : pickVariantMention(entry.id, entry.config);
```

**第三层：在 prompt 里明确提示**

```ts
dupHint = `同族多分身时：默认 \`@显示名\`，其它用**唯一句柄**（例如 \`${example}\`）。\n` +
          `同名队友并存时，请优先使用唯一句柄（例如 \`${example}\`）避免歧义。\n`;
```

**加上格式化标签也带变体标识：**

```ts
function formatHandleFreeLabel(catId: string, config: CatConfig | undefined): string {
  // F167 identity anti-spoofing: carry variantLabel when present to disambiguate
  // same-breed variants (e.g. "布偶猫 Opus 4.7(opus-47)" vs "布偶猫(opus)"),
  // preventing A2A handoff identity confusion.
  const variantPart = config.variantLabel ? ` ${config.variantLabel}` : '';
  return `${config.displayName}${variantPart}(${catId})`;
}
```

### 3.6 L0：从 Markdown 确定性编译出来的家规

**这是全模块最值得讲的设计。**

问题：家规原文在 `cat-cafe-skills/refs/shared-rules.md`，
是一份给人读的长 Markdown。prompt 里放不下全文。

**不能用 LLM 摘要** —— 摘要不稳定，而家规必须逐字稳定。

**答案：确定性投影 + fail closed**

```ts
/**
 * Deterministic projection from shared-rules.md into the compact always-on
 * governance L0 block. This is intentionally not a summarizer: required
 * headings/table anchors must exist, and missing anchors fail closed.
 */
export function compileGovernanceL0FromMarkdown(markdown: string): string {
  for (const anchor of [
    '## Rule 0',
    '### Push Back 协议',
    '## 第一性原理',
    '## 世界观',
    '## Magic Words',
    '## 10. @ 路由与球权',
    '## 14. 共享状态文件只在 main 改',
    '## 16. 实事求是',
    '### 46 hotfix 标签 + 跨猫升级 review',
    'fallback 层数检测协议',
    '创意-实现解耦协议',
    '## 0. 身份契约',
    '## 17. 决策漏斗',
  ]) {
    assertPresent(markdown, anchor);   // 缺一个就抛异常
  }

  const principles = extractNumberedHeadings(markdown, 'P', 5);   // P1~P5
  const worldviews = extractNumberedHeadings(markdown, 'W', 8);   // W1~W8
  const magicWords = extractMagicWords(markdown);                 // ≥9 行
  const identityContract = extractFirstParagraphAfterHeading(markdown, '## 0. 身份契约');
  // ...
}
```

**而且重复也报错：**

```ts
if (values.length === 0) throw new Error(`compileGovernanceL0: missing ${prefix} heading ${key}`);
if (values.length > 1)  throw new Error(`compileGovernanceL0: duplicate ${prefix} heading ${key}`);
```

**Magic Words 有数量下限：**

```ts
if (rows.length < 9) {
  throw new Error(`compileGovernanceL0: expected ≥9 Magic Words rows, found ${rows.length}`);
}
```

**这意味着：如果有人重构了 `shared-rules.md`、改了某个小节的标题，
API 会在启动时直接崩掉。**

**面试怎么讲这个设计（这是个高分点）：**

> "家规那块我觉得是整个项目最硬核的设计。
>
> 家规原文是一份给人读的长 Markdown，prompt 里放不下。
> 常规做法是用 LLM 摘要一下 —— 但他们没有。
> 注释里明确写了 `This is intentionally not a summarizer`。
>
> 他们写了一个**确定性投影**：断言 13 个必须存在的标题锚点，
> 抽取 P1~P5 第一性原理、W1~W8 世界观、至少 9 条 Magic Words、
> 身份契约的第一段……**任何一个锚点缺失就抛异常，API 启动失败。**
> 重复也报错，Magic Words 少于 9 条也报错。
>
> 为什么要这么硬？因为**摘要天然不稳定** ——
> 今天摘出 12 条，明天摘出 10 条，少的那两条是哪两条没人知道。
> 而治理规则如果悄悄少了一条，某天 Agent 不遵守某个规则，
> 你要排查半天才发现是那天摘丢了。
>
> **他们选择了'宁可崩溃，不要静默丢规则'。**
> 换个团队大概率会写成 warn 然后跳过 —— 那就是慢性病。"

### 3.7 编译产物长什么样

```
## 3. 家规（shared-rules.md）
Rule 0: 规则是边界不是全部。边界之内保留判断力；认为不适用时用证据说话。
Push Back 协议：证据 + 适用性论证 + 替代方案。
判断力三问：我现在在做什么 / 我的信息源可靠吗 / 方案感觉笨重？

### 第一性原理 P1-P5
- **P1** 面向终态，不绕路
- **P2** 共创伙伴，不是木头人
- **P3** 方向正确 > 执行速度
- **P4** 单一真相源
- **P5** 可验证才算完成

### 世界观 W1-W8
...

### 纪律
- 身份契约：{从 "## 0. 身份契约" 抽出的第一段}
- 用自己的身份签名 `[昵称/模型🐾]`，签名必须含模型型号；commit body 写 Why。
- 实事求是：结论必须基于多源证据；没查完就说还没查完。
- @ 是路由指令；收到 @ 后三选一：接 / 退 / 升。状态描述不是球权声明。
- 球权只有第一人称；唯一凭据是 @ 或 hold_ball 动作本身。
- 共享状态文件只在 main 改，改完立刻 git commit + git push。
- 跨 thread 阻塞依赖双写到可追溯状态；消息不是真相源。

### 质量覆盖
- Bug 先定位根因再修；不确定方向：停 → 搜 → 问 → 确认 → 再动手。
- "完成"附证据；Bug 先红后绿；scope 失控要记录并沉淀。
```

**四句话面试里可以拿出来单独讲：**

**① "Rule 0: 规则是边界不是全部。边界之内保留判断力。"**

作用是防止模型变成规则的奴隸。配 Push Back 协议兜底：
不同意可以顶，但要带证据 + 适用性论证 + 替代方案。

**② "SOP 流程推进不是决策，是执行。SOP 写了下一步就照做，不问。"**

防另一个极端：过度请示。
**这两条合起来才完整** —— 流程该走就走别问，但明显不适用时可以带证据顶回来。

**③ "@ 是路由指令；状态描述不是球权声明。"**

防这种情况：
```
布偶猫："我这边已经改完了，缅因猫应该可以开始 review 了"
      ↑ 这是状态描述，不是把球传出去
      ↑ 缅因猫不该因为看到自己被提到就开工
```

**④ "operator 升级必带 Decision Packet：给价值取舍题不给技术 A/B 题；缺 Packet = 打回"**

约束的是**升级的形式**。Agent 很容易把技术选型丢给人，
但人真正该决策的是价值取舍。

### 3.8 三层本地覆盖

```ts
function localPaths(basePath: string) {
  return {
    override: join(dir, `${stem}.local-override${ext}`),   // 完全替换
    local:    join(dir, `${stem}.local${ext}`),            // 追加
  };
}
```

```
shared-rules.local-override.md   存在 → 完全替换编译产物
shared-rules.local.md            存在 → 编译产物 + 本地追加
（都没有）                        → 纯编译产物
```

**开源项目要能让使用者改家规，但不能让他们改坏。**
`local` 追加是安全的，`local-override` 是给知道自己在干什么的人的逃生门。

### 3.9 动态段：每轮都要说的话

`buildInvocationContext(context: InvocationContext)` 的输入结构，
本身就是一份"这一轮 Agent 需要知道什么"的清单：

```ts
export interface InvocationContext {
  catId: CatId;
  mode: 'independent' | 'serial' | 'parallel';
  chainIndex?: number;  chainTotal?: number;      // 你是第几棒
  teammates: readonly CatId[];
  mcpAvailable: boolean;
  nativeL0Injected?: boolean;                     // ← 模块 06 的能力协商
  promptTags?: readonly string[];                 // #critique
  a2aEnabled?: boolean;
  directMessageFrom?: CatId;                      // 谁 @ 的你
  pingPongWarning?: { pairedWith: CatId; count: number };
  crossThreadReplyHint?: { sourceThreadId; senderCatId; effectClass? };
  mentionRoutingFeedback?: ThreadMentionRoutingFeedback;
  activeParticipants?: readonly ThreadParticipantActivity[];
  routingPolicy?: ThreadRoutingPolicyV1;
  sopStageHint?: { stage; suggestedSkill; featureId };   // ← 模块 14
  activeSignals?: readonly {...}[];
  voiceMode?: boolean;
  threadId?: string;
  bootcampState?: BootcampStateV1;
  guideCandidate?: {...};
  packBlocks?: CompiledPackBlocks | null;
  alwaysOnDocs?: readonly { anchor; title; summary }[];   // ← 模块 09
  worldContext?: WorldContextEnvelope;
  threadKind?: 'concierge';
  conciergeConfig?: ConciergeConfig;
}
```

**四个最值得讲的动态段：**

**D1 身份锚点 —— 最短也最重要**

```markdown
<!-- @segment D1 — Identity 锚点 -->
<!-- Condition: always injected -->

Identity: {{DISPLAY_NAME}}{{NICKNAME_PART}} (@{{CAT_ID}}, model={{RUNTIME_MODEL}})
```

**一行字，每一轮都注入，大约 15 个 token。**

**为什么？** 静态身份只在新 session 注入一次，
一旦上下文被压缩，S1 那段"你是布偶猫…"可能就没了。
D1 是那根永远新鲜的锚 ——
**它保证无论压缩多少次，最近一轮里一定有一句话说了你是谁。**

**这是抗上下文压缩的第一道防线，也是最便宜的一道。**

**D3 同族分身提醒**

```markdown
⚠️ 同族分身提醒：对方是 {{FROM_VARIANT}}（model={{FROM_MODEL}}），
你是 {{SELF_VARIANT}}（model={{SELF_MODEL}}）
——两个独立分身，不是你的旧版或新版。
```

触发条件：`directMessageFrom` 的 displayName 相同但 catId 不同。

**解决一个非常具体的认知混乱**：
布偶猫 Opus 4.7 收到布偶猫 Opus 4.8 的消息时，
会以为在跟"自己的另一个版本"说话，进而做出奇怪的推断
（"我升级过了？""这是我之前说的话？"）。

**这条直接服务于 [模块 11](11-模块-跨模型互审.md) 的互审**——
铁律是"必须跨族**或同族不同个体**"，
但前提是它们真的把对方当成"另一个人"。

**D4 跨帖回复必须结构化**

```ts
/**
 * F193 AC-B2: Cross-thread reply hint.
 * MUST be structured (not parsed from prompt text) — ContextAssembler
 * only renders slice(0,8) truncated thread + lacks senderCatId.
 */
crossThreadReplyHint?: {
  sourceThreadId: string;   // 完整的，不截断
  senderCatId: CatId;
  effectClass?: 'fyi' | 'coordinate' | 'investigate' | 'assign_work';
};
```

**注意 `MUST be structured`。**
上下文里渲染的 thread id 是截断到 8 位的（`slice(0, 8)`，见 [模块 09](09-模块-记忆与检索.md)），
Agent 拿它回不去源帖。

**`effectClass` 四类很妙** —— 告诉接收方"这条跨帖消息期待你做什么"：
`fyi`（就别开工）/ `coordinate` / `investigate` / `assign_work`（才是派活）。

**D14 SOP 阶段：告示牌哲学**

```ts
/**
 * F073 P4: SOP stage hint from Mission Hub workflow-sop.
 * Injected per-invocation so all cats (Claude/Codex/Gemini) see current stage.
 * 告示牌哲学：猫看了自己决定行动，不被系统推着走。
 */
```

**"告示牌哲学"是理解 [模块 14](14-模块-SOP门禁.md) 的钥匙。**

## 4. 为什么这么设计

### 决策 A：为什么不用 CLI 原生的配置文件（CLAUDE.md 等）

【ADR】ADR-017 有明确决策，而且是**禁止**级别的：

> **禁止** Cat Café 在运行时（dispatch/invocation 过程中）
> 自动修改各猫 home 目录下的配置文件。
>
> 系统提示词同步只通过显式脚本：`scripts/sync-system-prompts.ts --apply`。
>
> **Rationale**：
> 1. **侵入性**：改用户 home 目录文件影响所有使用该 agent 的场景，不只是 Cat Café
> 2. **竞态风险**：多个 Cat Café 实例/session 同时写同一文件可能互踩
> 3. **个人环境污染**：operator可能在原生配置中有自定义内容，runtime 覆写会丢失
> 4. **可审计性**：显式脚本有 commit 记录和 `--check` drift 检测，runtime 覆写无痕

**这四条理由值得背下来**，因为它们是通用的
——任何"往用户机器上写配置"的场景都适用。

**后果也写清楚了：**

> - 家规/身份变更后需手动跑 `scripts/sync-system-prompts.ts --apply`
> - **不支持原生配置的猫（OpenCode、Antigravity）继续靠 Cat Café 动态 prompt 注入**
> - CI 可集成 `--check` 模式检测漂移

**最后这条解释了为什么必须有动态注入这套东西**：
不是所有 CLI 都有原生配置文件。

### 决策 B：为什么静态只注入一次

**取舍**：省 token vs 抗压缩能力。

```
每轮全量注入   → 抗压缩最强，但每轮几千 token
只在新 session → 省 token，但压缩后会丢
折中（现在）   → 静态一次 + 动态每轮 15 token 的身份锚
```

**这个折中是我认为设计得最巧的地方**：
它认识到"抗压缩"不需要保住全部信息，只需要保住**身份**这个最关键的位。
其余信息可以在需要时通过工具查回来（[模块 09](09-模块-记忆与检索.md)）。

### 决策 C：为什么 L0 要 fail closed 而不是 warn

**取舍**：可用性 vs 正确性。

【推断】选 fail closed 的理由：

```
如果 warn 然后跳过：
  → 某天治理规则少了一条
  → 但系统照常运行
  → 几周后发现 Agent 不守某条规则
  → 排查：是模型不听话？是 prompt 写得不清楚？是规则没进 prompt？
  → 最难查的那种 bug

如果 fail closed：
  → 改坏了立刻启动失败
  → 一分钟就知道是自己刚才改的文档
```

**"把发现时机从几周提前到一分钟"** —— 这是 fail closed 的核心价值。

**这个 ADR 的参与者记录很有意思：**

> - Maine Coon/GPT-5.4（架构讨论 + **否决 runtime 覆写**）

**是另一个模型否掉了这个方案** —— 这本身就是跨模型互审的一个实例。

### 方案二：用 LLM 摘要家规

【源码】注释直接否掉了：

```

```

**"intentionally"这个词是关键** —— 不是没想到，是刻意不这么做。

### 方案三：L3 role-gate（代码级角色门禁）

【源码】明确标了"retired"：

```ts
// F167 Phase E (KD-20): surface hard restrictions alongside caution — data-driven
// replacement for the retired L3 role-gate.
```

**这是个真实的废弃**：从"代码拦"改成"信息透明 + 模型判断"。

### 方案四：把新 MCP 工具都加到 prompt 的工具清单里

**【ADR】ADR-037 是一份专门否掉这个做法的决策：**

> An older checklist treated `SystemPromptBuilder.MCP_TOOLS_SECTION` as the default
> place to announce every new MCP tool. That solved early discoverability gaps, but
> it also made prompt text grow and **turned a legacy prompt surface into a stale catalog**.
>
> **Decision**: New MCP tools must update the right cognitive entry point,
> but they **must not** be added to `SystemPromptBuilder.MCP_TOOLS_SECTION` by default.
>
> Use this priority order:
> 1. **MCP tool description** — the always-visible routing signal for the tool.
> 2. **Relevant skill refs or SOP docs** — scenario guidance, parameters, examples.
> 3. **Capability wakeup index or L0 quick index** — only for broad categories that
>    must survive context compression.
> 4. **`SystemPromptBuilder.MCP_TOOLS_SECTION`** — only when a legacy or fallback
>    prompt surface still depends on it.

**这份 ADR 的价值在于它定义了"认知入口"的优先级。**

大白话：**"加了个工具"不等于"Agent 会用它"。**
但解决办法不是往 prompt 里塞说明 —— 而是：

```
① 先改工具本身的 description（这是模型总能看到的）
② 再改相关 skill 文档（场景化指导）
③ 只有"必须扛住上下文压缩"的宽泛类别才进 L0 索引
④ prompt 工具清单只在遗留兼容时用
```

**Consequences 那段也很好：**

> Reviewers should ask: "Which cognitive entry point teaches agents to use this tool?"
> instead of "Was the tool appended to `MCP_TOOLS_SECTION`?"

**把 review 的问题从"有没有加到清单"改成"哪个认知入口教会了 Agent 用它"。**

**面试怎么用这段**：

> "他们有份专门的 ADR（037）否掉了'新工具都加到 prompt 清单里'这个做法。
> 理由是那让 prompt 不断膨胀，而且'把一个遗留的 prompt 界面变成了过期的目录'。
>
> 改成了四级优先的'认知入口'：
> 先改工具自己的 description（模型总能看到）、
> 再改相关 skill 文档、
> 只有必须扛住压缩的宽泛类别才进 L0、
> prompt 清单只做遗留兼容。
>
> 我觉得最好的是它改了 review 的提问方式 ——
> 从'有没有加到清单'变成'**哪个认知入口教会了 Agent 用这个工具**'。
> 这是把一个机械检查换成了一个真问题。"

## 6. 如果重新设计

【推断】以下全是我的方案。

### 6.1 给 prompt 段落加真正的预算账本

**现在的问题**：token 预算是分散的硬编码。

```
名册单元格   52 / 72 字符
对话历史     20 条 / 2000 token
bootstrap    2000 token 硬上限 + 400 token 保底
每条消息     1500 字符
```

**没有一个地方能回答"这次 prompt 一共花了多少，各段占比多少"。**

有个 `prompt-digest.ts` 和 F237 的 injection trace，
但那是可观测性，不是预算控制。

**我的方案**：

```ts
interface PromptBudget {
  total: number;                    // 比如上下文窗口的 25%
  allocations: {
    segment: string;                // 'S5' | 'D1' | 'history' | 'bootstrap'
    priority: 'must' | 'should' | 'nice';
    requested: number;
    granted: number;                // 实际给了多少
    truncated: boolean;
  }[];
}
```

**分配规则**：
```
① must 段先满足（D1 身份锚、L0 治理块）
② should 段按优先级分剩下的（名册、SOP 阶段）
③ nice 段有多少给多少（signal 文章、world context）
④ 超预算时从 nice 开始砍，并在 prompt 里标出"XX 段被省略"
```

**收益**：
- 能回答"这次为什么没注入队友名册"
- 能做实验："把历史预算从 2000 降到 1000，效果差多少"
- 上下文窗口变化时（换模型）自动适配，不用改一堆常量

**代价**：多一层间接；而且优先级排序需要真实数据支撑，一开始只能靠猜。

### 6.2 L0 编译加"覆盖率报告"

**现在的问题**：13 个锚点是硬编码的白名单。
如果 `shared-rules.md` 里**新增**了一节，编译器不会知道 ——
它只检查已知锚点存在，不检查有没有漏掉新内容。

```
有人在 shared-rules.md 加了 "## 18. 新的重要规则"
  → 13 个锚点都还在 → 编译通过
    → 但新规则没进 L0
      → 静默丢失（正是 fail-closed 想避免的问题）
```

**我的方案**：反向检查。

```ts
// 编译时同时产出覆盖率
interface L0CompileReport {
  compiled: string;
  coverage: {
    totalSections: number;         // shared-rules.md 有多少个 ## 小节
    projectedSections: number;     // 其中多少个进了 L0
    unprojected: string[];         // ★ 哪些没进
  };
}
```

然后加一条 CI 检查：**未投影的小节必须在一个显式的
`l0-exempt.yaml` 白名单里**，否则 CI 红。

**这样新增小节时必须做一个决定**：进 L0，还是显式豁免。
不能什么都不做就静默漏掉。

**为什么这个改进重要？**
因为它补上了 fail-closed 的一个盲区 ——
现在防的是"已知锚点消失"，防不了"新内容没进来"。
**两个方向都要防，才是真的 fail closed。**

### 6.3 身份锚从"一行文本"升级成"结构化 + 一行文本"

**现在的 D1 是纯文本**：

```
Identity: 布偶猫/宪宪 (@opus, model=claude-opus-5)
```

**问题**：如果 provider 支持原生 system 通道（`nativeL0Injection`），
这行文本走用户消息其实是浪费 —— 它应该走 system 角色（压缩免疫）。

**我的方案**：按 provider 能力分流。

```
provider 有原生 system 通道
  → 身份进 system 角色（一次，压缩免疫）
  → 用户消息里只放一个极短的确认位（比如 `[opus]`，3 token）

provider 没有
  → 保持现在的做法（每轮一行完整身份）
```

**收益**：有原生通道的 provider 每轮省 12 token。
按每天几千轮算，量不大但是免费的。

**更重要的收益**：`nativeL0Injection` 这个能力位现在只用来决定
"静态身份走哪条路"，我会把它扩展成完整的能力协商 ——
这和 [模块 06](06-模块-Provider适配.md) §6.1 的能力矩阵是一件事。

### 6.4 队友名册改成"按需查询"而不是全量注入

**现在的问题**：队友名册在每个新 session 全量注入。
Agent 有 5 只队友时是一张 5 行表；如果有 20 只呢？

**我的方案**：

```
静态注入：只放"你有 N 个队友，用 list_teammates() 查详情"
          + 最常协作的 3 个（按历史活跃度）

按需查询：list_teammates({ role?, available?, family? })
          → MCP 工具，Agent 需要时才查
```

**为什么这么改？**
因为名册的用途是"决定找谁"，而这个决定不是每轮都要做的。
大部分轮次 Agent 只是在干活，不需要知道全部队友。

**代价**：需要找人时多一次工具调用（几百毫秒）。
**但这符合项目自己的 ADR-037 精神** ——
"能力发现应该靠工具 description 和按需查询，不是靠 prompt 目录"。

**我认为这个方向和他们的 ADR-037 一致，只是他们还没把名册纳进来。**

### 6.5 我不会改的

| 我原本的想法 | 为什么放弃 |
|------------|-----------|
| 把 prompt 模板改成代码里的模板字符串 | 现在的 `.md` 文件能 git diff、能不重编译改、能审计，明显更好 |
| 用 LLM 压缩家规到更短 | 稳定性 > 简洁性；确定性投影是对的 |
| 去掉 D1 每轮注入（靠 system 通道） | 不是所有 provider 有原生通道；D1 是兜底 |
| 把 L0 做成运行时可编辑 | 治理规则应该走 git + review，不该运行时改（对应 CLAUDE.md 的"Config Immutability"铁律） |

```
  ├─ getCatModel(id)                  → env → registry → defaults
  ├─ getDossierRosterSummary()        → 档案文件
  ├─ loadCompiledGovernanceL0()       → cat-cafe-skills/refs/shared-rules.md
  ├─ getWorkflowTriggers()            → assets/prompt-templates/workflow-triggers.yaml
  ├─ getCoCreatorConfig()             → cat-template.json
  └─ packBlocks                       → PackStore（模块 —— pack 系统）

buildInvocationContext
  ├─ threadStore                      → 参与者活跃度、路由策略、mention 反馈
  ├─ workflowSopStore                 → SOP 阶段（模块 14）
  ├─ evidenceStore.queryAlwaysOn()    → always-on 文档（模块 09）
  ├─ guideSessionStore                → 引导状态
  └─ conciergeConfigStore             → 前台配置
```

**这张表说明身份注入是"最大的读者"** ——
它从八九个数据源拉数据拼一段文本。

### 三根最关键的跨模块线

**线一：mentionPatterns 是 prompt 和解析器的共享真相源**

```
catRegistry.mentionPatterns
   ├──→ 模块 04 的解析器（认哪些 handle）
   └──→ 本模块 S4/S5 段（告诉 Agent 能 @ 谁）
```

**必须一致，否则 prompt 教的 handle 路由不通。**
所以有 `pickDisplayNameMention` 那段"不合成不存在的句柄"的逻辑。

**线二：D1 身份锚是抗压缩的第一道防线**

```
本模块 D1（每轮 15 token）
   └──→ 模块 08 的三道防线之第一道
        （第二道是连续性胶囊，第三道是封存 + bootstrap）
```

**线三：D3 同族提醒是互审的前置条件**

```
本模块 D3（"两个独立分身，不是你的旧版"）
   └──→ 模块 11 的铁律"跨族或同族不同个体"
        └──→ 模块 14 的 predicate `reviewer_not_author`
```

**这三层如果第一层不成立（Agent 以为对方是自己的另一个版本），
后面两层的判定就失去意义。**

### 一个反向咬合：身份影响记忆写入

```
L0 里的"用自己的身份签名 [昵称/模型🐾]"
  → Agent 在 commit message / 文档里签名
    → 模块 09 的证据库记录了"这条知识是谁写的"
      → 模块 11 的互审能判断"这是不是你自己写的"
        → 模块 15 的 Self-Evolution 能统计"哪只 Agent 的哪类偏差多"
```

**签名规范这一条小规则，支撑了三个上层模块的可追溯性。**

## 8. 面试怎么讲

### 30 秒版

见 §0。

### 3 分钟版

> "核心是**静态/动态二分**。不变的东西 —— 名字、性格、硬限制、
> 队友名册、家规 —— 只在新 session 注入一次；
> 会变的东西 —— 你是第几棒、谁 @ 的你、当前 SOP 阶段、乒乓警告 ——
> 每一轮都注入。
>
> 关键洞察是：**抗压缩的要求恰好落在动态那半**，
> 因为动态段每轮都新鲜，压缩摘不掉最近一轮。
> 所以有个 D1 段，就一行字 ——
> `Identity: 布偶猫/宪宪 (@opus, model=...)`，大约 15 个 token，每轮都注入。
> 这是抗压缩的第一道防线，也是最便宜的一道。
>
> **prompt 不写在代码里**，存在 `assets/prompt-templates/` 下的 `.md` 文件，
> 每段有编号，代码只填空。好处是能 git diff、改了不用重编译、可以审计。
> 还有个 `annotateSegments` 开关能在生成的 prompt 里插入分隔标记，
> 用来调试'这句话是哪段塞进来的'。
>
> **最硬核的是家规那块。** 家规原文是一份给人读的长 Markdown，
> prompt 里放不下。常规做法是 LLM 摘要一下 —— 但他们没有，
> 注释里明确写了 `This is intentionally not a summarizer`。
> 他们写了个确定性投影：断言 13 个必须存在的标题锚点，
> 抽 P1~P5 原理、W1~W8 世界观、至少 9 条 Magic Words，
> **任何锚点缺失就抛异常，API 启动失败**。重复也报错。
>
> 为什么这么硬？因为摘要不稳定 —— 今天摘 12 条明天摘 10 条，
> 少的哪两条没人知道。而治理规则悄悄少一条，
> 某天 Agent 不守规则你要排查半天。
> **他们选了宁可崩溃不要静默丢规则。**"

### 常见追问

**Q：每轮注入这么多 token，成本怎么控制？**

> "分了三档预算。
>
> 静态段只在新 session 注入，resume 不重复 —— 这是最大的一笔省。
> 动态段每轮注入但很短，最关键的 D1 身份锚只有 15 token。
> 对话历史卡 20 条 / 2000 token，单条截断 1500 字符。
> 队友名册的单元格限长 52 和 72 字符 —— 因为名册每 session 都注入，字数就是钱。
>
> 但我觉得缺一个东西：**没有统一的预算账本**。
> 现在这些数字是分散的硬编码，没有一个地方能回答
> '这次 prompt 一共花了多少、各段占比多少、为什么某段没注入'。
>
> 我会做一个显式的预算分配器：段落标 must/should/nice 三档优先级，
> must 先满足，超预算从 nice 开始砍，并且在 prompt 里标出'XX 段被省略'。
> 这样换模型（上下文窗口变了）能自动适配，不用改一堆常量。"

**Q：为什么不直接用 CLAUDE.md 这类原生配置？**

> "他们有份专门的 ADR（017）**禁止**运行时覆写 Agent 的 home 目录配置，
> 四条理由我觉得都很通用：
>
> 一，侵入性 —— 改用户 home 目录会影响所有使用场景，不只是这个系统；
> 二，竞态 —— 多个实例同时写同一文件会互踩；
> 三，环境污染 —— 用户可能在原生配置里有自定义内容，覆写会丢；
> 四，可审计性 —— 显式脚本有 commit 记录和 `--check` 漂移检测，运行时覆写无痕。
>
> 所以同步只能通过显式脚本 `sync-system-prompts.ts --apply`。
> 而且 ADR 里明确写了后果：**不支持原生配置的 Agent
> （OpenCode、Antigravity）继续靠动态 prompt 注入**——
> 这就是为什么必须有这套东西，不是所有 CLI 都有配置文件。
>
> 有个细节挺有意思：这份 ADR 的参与者记录里写着
> 'Maine Coon/GPT-5.4（架构讨论 + 否决 runtime 覆写）'——
> **是另一个模型否掉了这个方案**。这本身就是跨模型互审的一个实例。"

**Q：L0 fail closed 会不会太激进？改个文档标题就崩了？**

> "我觉得是对的，而且我会做得更严。
>
> fail closed 的价值是**把发现时机从几周提前到一分钟**。
> 如果是 warn 然后跳过：某天治理规则少了一条，系统照常运行，
> 几周后发现 Agent 不守某条规则 —— 然后你要排查
> '是模型不听话？是 prompt 不清楚？还是规则根本没进 prompt？'
> 这是最难查的那种 bug。
>
> 不过我发现它有个盲区：**它只防'已知锚点消失'，防不了'新内容没进来'。**
> 如果有人在 `shared-rules.md` 加了 `## 18. 新的重要规则`，
> 13 个锚点都还在，编译通过 —— 但新规则没进 L0，静默丢失。
>
> 我会加反向检查：编译时同时统计覆盖率，
> 未投影的小节必须在一个显式的豁免白名单里，否则 CI 红。
> **这样新增小节时必须做个决定：进 L0 还是显式豁免，不能什么都不做。**
> 两个方向都防住，才是真的 fail closed。"

**Q：怎么让 Agent 知道有哪些工具可用？**

> "他们有份 ADR（037）专门讲这个，而且是**否掉**了'加到 prompt 清单里'这个做法。
> 理由是那让 prompt 不断膨胀，而且'把遗留的 prompt 界面变成了过期的目录'。
>
> 改成了四级优先的'认知入口'：
> 一，先改工具本身的 description —— 这是模型总能看到的路由信号；
> 二，改相关 skill 文档 —— 场景化指导、参数、副作用、坑；
> 三，只有必须扛住上下文压缩的宽泛类别才进 L0 索引；
> 四，prompt 工具清单只在遗留兼容时用。
>
> 我最喜欢的是它改了 review 的提问方式 ——
> 从'有没有加到清单'变成'哪个认知入口教会了 Agent 用这个工具'。
> 把机械检查换成了真问题。
>
> 顺着这个思路，我认为**队友名册也该按需查询**：
> 静态只放'你有 N 个队友 + 最常协作的 3 个'，
> 详情用 `list_teammates()` 工具查。
> 因为名册的用途是'决定找谁'，而这个决定不是每轮都要做的。"

## 9. 本模块要点

| 要点 | 内容 |
|------|------|
| **静态/动态二分** | 不变的注入一次，会变的每轮注入 |
| **抗压缩落在动态半边** | 动态段每轮新鲜，压缩摘不掉 |
| **D1 身份锚 15 token** | 抗压缩第一道防线，最便宜的一道 |
| **prompt 是数据** | `.md` 模板 + 段号 + `annotateSegments` 调试开关 |
| **标记打在 if/else 两侧** | 分辨"没渲染"和"渲染了但空" |
| **句柄 ≠ 模型** | 必须可见解耦，防把云端 bot 当成本地队友 |
| **名册撒谎比缺失更糟** | 必须用 `getCatModel` 而非静态 defaultModel |
| **告警条件讲究** | 只对"有档案但缺项"告警 |
| **L3 role-gate 已废弃** | 从代码强拦改成信息透明 + 模型判断 |
| **L0 是编译不是摘要** | `intentionally not a summarizer`，13 锚点 fail closed |
| **三层本地覆盖** | local 追加安全，local-override 是逃生门 |
| **【ADR-017】禁止覆写 home** | 侵入性/竞态/污染/不可审计 四条理由 |
| **【ADR-037】认知入口优先级** | 工具 description > skill 文档 > L0 索引 > prompt 清单 |
| **我的改进** | 统一预算账本 / L0 覆盖率反向检查 / 名册按需查询 |
