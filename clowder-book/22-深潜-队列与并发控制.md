# 22 · 深潜：队列、判忙与并发控制的完整实现

> 这一篇覆盖 `invocation/` 目录下的并发正确性核心：`InvocationQueue`(938 行) 存"谁在等"、`InvocationTracker`(518 行) 存"谁在跑"、`QueueProcessor`(1901 行) 把两者接起来并管理暂停/续跑/公平性，`getThreadLiveInvocations`(1122 行) 在三个存储之间做僵尸判定，三个对账器负责收尸。

```

**边界在哪（这是最容易被追问的点）**：

- `InvocationQueue` 里**没有任何** `await`、没有任何 socket、没有任何 tracker 引用。它是纯同步数据结构。好处：所有队列变更都在一个 JS tick 内完成，天然没有队列内部竞态。
- `InvocationTracker` 里也**没有** queue 引用。它只管 AbortController。
- 两者的桥只有 `QueueProcessor`。所以"槽位忙不忙"这个判断永远是 `processingSlots`（QueueProcessor 私有）**和** `invocationTracker.has()` 两个条件一起看 —— 因为它们覆盖的时间窗不同（§4.2）。
- `getThreadLiveInvocations` 是**只读**的，它自己不改状态；改状态的是 `reconcileZombies`。源码注释明确写了原因：`Read-side does NOT terminalize (砚砚 R1 P1-3); reconcile pathway decides failed vs succeeded`。【源码】

> **面试官追问：为什么"谁在跑"和"谁在等"要拆成两个类？**
> 「因为它们的键不一样、生命周期不一样。Tracker 的键是 `(threadId, catId)`，一只猫一个槽，用来做互斥和取消；Queue 的键是 `(threadId, userId)`，用来做用户隔离和 FIFO 公平。如果合成一个类，你就得同时用两个索引维护同一份数据，取消的时候要顺手改队列、入队的时候要顺手看槽位，很容易漏。拆开之后，桥只有 QueueProcessor 一个地方，所有跨两者的竞态都集中在那一个文件里审。」

## 2. 核心数据结构

### 2.1 `QueueEntry`（`InvocationQueue.ts`）

每个字段为什么存在 —— 这是本节重点：

| 字段 | 类型 | 为什么存在 |
|---|---|---|
| `id` | string | `randomUUID()`。所有跨用户操作（`removeProcessedAcrossUsers` / `markProcessingById`）都只认 id，因为它们不知道 userId |
| `threadId` / `userId` | string | 组成 scopeKey；`threadId` 冗余存在 entry 里，因为 `queueMatchesThread()` 要靠 entry 自己判断这个数组属于哪个 thread |
| `idempotencyKey` | string? | 请求级重放去重。同 key 的活跃条目直接返回旧条目而不是新建一行 |
| `content` | string | 提示词正文。合并（coalesce / batch）会往它上面追加 |
| `messageId` | string \| null | **可以为 null**：入队是容量守门（同步），写消息是异步的，所以先入队拿位置、再回填 messageId |
| `mergedMessageIds` | string[] | 合并进来的额外触发消息。投递/ack 要覆盖全部，不能只 ack 主消息 |
| `source` | `'user' \| 'connector' \| 'agent'` | 三条来源决定几乎所有分支：容量限制只管 user、公平性门只挡 non-agent、frustration 检测只对 user 开 |
| `targetCats` | string[] | `targetCats[0]` 是"主猫"，槽位判定全用它。多猫条目共享一个条目、一个 batch gate |
| `intent` | string | `'execute'` / `'ideate'`，批处理合并要求 intent 相同 |
| `status` | `'queued' \| 'processing'` | 注意：**没有终态**。执行完就从数组里删掉，不留 `done` |
| `createdAt` | number | 排序的最后一级 tiebreak（真正的 FIFO 依据） |
| `processingStartedAt` | number? | 只在转 processing 时写。所有"僵尸 processing"判定都用它，**不用 createdAt** |
| `autoExecute` | boolean | 是否不等用户点"继续"就自动跑。A2A / 续跑 / 连接器都是 true |
| `callerCatId` | string? | 哪只猫发起的。用于 A2A 合并的 caller 隔离（同一个 caller 的重复交接才可合并） |
| `senderMeta` | `{id,name?}`? | 群聊里的发送者身份，纯 UI 展示 + 流式占位符的 senderHint |
| `priority` | `'urgent' \| 'normal'` | 队内优先级 |
| `sourceCategory` | 见下 | 来源细分：`ci / review / conflict / scheduled / a2a / continuation / issue / freshness` |
| `continuationKey` | string? | 续跑条目的去重键（§4.5） |
| `position` | number? | 用户拖拽排序的显式位置。**只在同一 userId 内生效** |
| `suggestedSkill` | string? | 连接器触发时的技能提示，执行时变成 `promptTags: ['skill:xxx']` |
| `callerTraceContext` | CallerTraceContext? | OTel trace 串联 |
| `a2aTriggerMessageId` | string? | A2A 触发消息，用于流式回复挂到正确的消息上 |

### 2.2 `EnqueueResult`

```ts
export interface EnqueueResult {
  outcome: 'enqueued' | 'full';
  entry?: QueueEntry;
  queuePosition?: number;
  /** True when enqueue returned an existing active entry by idempotency key. */
  deduped?: boolean;
}
```

只有两个 outcome。`deduped: true` 时 outcome 仍然是 `'enqueued'` —— 调用方（`routes/messages.ts`）靠 `deduped` 决定"要不要再写一条用户消息"。【源码】

⚠️ 一个容易答错的细节：`queuePosition` 是**数组下标 +1**，不是 comparator 排序后的位置：

```ts
const position = q.findIndex((entry) => entry.id === existing.id);
return { ..., queuePosition: position >= 0 ? position + 1 : undefined, deduped: true };
// 新建路径：
q.push(entry);
return { outcome: 'enqueued', entry: { ...entry }, queuePosition: q.length };
```

而真正的出队顺序由 `compareEntries` 决定（§4.1）。所以 `queuePosition` 只是"你是第几个进来的"，不是"你是第几个跑"。【源码】

### 2.5 `InvocationTracker` 的 `ActiveInvocation`

```ts
interface ActiveInvocation {
  controller: AbortController;      // 这只猫自己的信号
  userId: string;                   // 跨用户取消的门禁
  catId: string;
  catIds: string[];                 // 整批的猫，用于取消广播
  startedAt: number;                // TTL 判定基准
  batchController?: AbortController;// 整个 invocation 的门（独立于任何 per-cat controller）
  state: 'active' | 'canceled';     // 墓碑标记
  cancelReason?: string;
}

export type SlotState = 'active' | 'canceled' | 'absent';
```

关键点：`controller` 和 `batchController` 是**两个独立的 AbortController**。取消一只猫只 abort 它自己的 `controller`；`cancelAll` 才 abort `batchController`。这是"取消一只猫不影响兄弟猫"的物理基础。【源码，`startAll()` 注释明写】

### 2.6 `QueueProcessor` 的六张表

```ts
private processingSlots      = new Map<string, number>();                    // slotKey → startedAt
private pausedSlots          = new Map<string, 'canceled' | 'failed'>();     // slotKey → 暂停原因
private pauseEpoch           = new Map<string, number>();                    // slotKey → 世代号
private suppressedAutoResume = new Map<string, number>();                    // slotKey → 打标时间
private entryCompleteHooks   = new Map<string, EntryCompleteHook>();         // entryId → 一次性回调
private continuationWindows  = new Map<string, number[]>();                  // `${tid}:${cat}` → 时间戳数组
```

**slotKey 的坑（很好的追问点）**：两个类用了**不同**的 key 格式。

```ts
// QueueProcessor
private static slotKey(threadId, catId) { return JSON.stringify([threadId, catId]); }
// InvocationTracker
private slotKey(threadId, catId) { return `${threadId}:${catId}`; }
```

QueueProcessor 用 JSON 数组，因为 threadId 里可能含 `:`，用冒号拼会歧义 —— 它还留了兼容解析：

```ts
private static parseSlotKey(key: string) {
  try { const parsed = JSON.parse(key); if (Array.isArray(parsed) && parsed.length === 2 ...) return {...}; }
  catch { /* Legacy in-memory keys from older code are not expected after restart. */ }
  const legacySep = key.indexOf(':');
  if (legacySep > 0) return { threadId: key.slice(0, legacySep), catId: key.slice(legacySep + 1) };
  return null;
}
```

【源码】Tracker 至今还用冒号拼且只做 `key.startsWith(prefix)` 前缀匹配 —— 这意味着如果 threadId 里含冒号，Tracker 的 thread 级遍历理论上会误匹配。【推断】实践中 threadId 是 UUID/短 id，所以没暴雷。

## 3. 主流程逐段拆解

### 3.1 入队：`InvocationQueue.enqueue()`

按执行顺序：

**① 算 scopeKey、取数组、算归一化优先级**

```ts
const key = this.scopeKey(input.threadId, input.userId);
const q = this.getOrCreate(key);
const priority = InvocationQueue.normalizedPriority(input);
const dedupeProcessing = input.dedupeProcessing ?? true;
```

`normalizedPriority` 干的事是"降权"：

```ts
private static normalizedPriority(input) {
  return input.source === 'agent' && input.sourceCategory !== 'continuation'
    ? 'normal'
    : (input.priority ?? 'normal');
}
```

含义：**agent 来源的条目一律不许 urgent，除了续跑**。为什么这么写？因为 A2A 是猫自己发起的，如果猫能给自己发 urgent，它就能无限插到用户前面。续跑是例外，因为续跑是"接着上次没干完的活"，必须优先，否则上下文更容易失效。【源码 + 推断（这个理由是我从代码形态反推的，注释只写了 F175）】

**② 幂等去重（可选）**

```ts
if (input.idempotencyKey) {
  const existing = q.find(e =>
    e.idempotencyKey === input.idempotencyKey &&
    (e.status === 'queued' || (dedupeProcessing && e.status === 'processing')));
  if (existing) {
    if (existing.status === 'queued') {
      const upgradedPriority = PRIORITY_RANK[priority] < PRIORITY_RANK[existing.priority];
      if (upgradedPriority) existing.priority = priority;
      if (input.suggestedSkill && (upgradedPriority || !existing.suggestedSkill)) existing.suggestedSkill = ...;
      if (input.sourceCategory && !existing.sourceCategory) existing.sourceCategory = ...;
    }
    return { outcome: 'enqueued', entry: { ...existing }, queuePosition: ..., deduped: true };
  }
}
```

三个细节值得复述：
- `dedupeProcessing` 默认 true，但连接器合流可以传 false —— 因为连接器要能"在已有条目正在跑时再排一条"。注释：`connector coalescing can opt out for in-flight entries`。
- 命中去重时**只升级不降级**优先级：`urgent` 请求命中一个 `normal` 的旧条目 → 旧条目升级；反之不动。
- `suggestedSkill` 的覆盖条件是 `upgradedPriority || !existing.suggestedSkill` —— 要么这次是升级（更权威），要么旧的本来没有。避免后来的低优先级请求把技能提示改掉。

**③ 容量检查（只管 user）**

```ts
if (input.source === 'user') {
  const userQueuedCount = q.filter(e => e.status === 'queued' && e.source === 'user').length;
  if (userQueuedCount >= MAX_QUEUE_DEPTH) return { outcome: 'full' };
}
```

三层限定：只数 `source === 'user'`、只数 `status === 'queued'`、只数**本 scope**（同一 thread 同一 user）。所以：
- agent / connector 条目永远不会被容量拒绝（否则 A2A 链会断在半路）；
- 正在跑的那条不占额度；
- 另一个用户塞满自己的队列不影响你。

【源码】而 `routes/messages.ts` 收到 `'full'` 时返回 **429 + `code: 'QUEUE_FULL'`，并且不写消息**（注释：`no ghost message`）。这个顺序很重要：入队是同步容量守门，通过后才异步写消息。

**④ 建条目 push**

`position: undefined` 显式初始化 —— 新条目不带显式位置，走 priority/createdAt 排序。

> **面试官追问：为什么容量检查放在幂等去重之后？**
> 「因为重放请求不该被容量拒绝。同一个 idempotencyKey 第二次进来，用户看到的应该是"你的请求还在队列里第 3 位"，不是 429。如果先查容量，队列满了的时候重试会直接 429，用户会以为自己的消息丢了。」

### 3.2 出队调度：三条路径

```
① onInvocationComplete(threadId, catId, status)   ← 系统级，一次调用结束后
② processNext(threadId, userId)                   ← 用户级，手动点"继续"
③ tryAutoExecute(threadId, opts)                  ← 入队后立刻扫，autoExecute 条目
```

它们最终都汇到三个私有方法之一：

| 私有方法 | 选条目的方式 | 用在哪 |
|---|---|---|
| `tryExecuteNextAcrossUsers(threadId, catId)` | `markProcessingAcrossUsers(threadId, busyCats)` 跨用户挑最高优先级 | ① 成功后 / 暂停自动恢复后 |
| `tryExecuteNextForUser(threadId, userId)` | `peekNextQueued` 先看 → 检槽 → `markProcessing` | ② |
| `tryAutoExecute` 自己的循环 | `listAutoExecute(threadId)` 全扫，按 createdAt 升序 | ③ |

**`tryExecuteNextAcrossUsers` 的 busyCats 回滚循环**（这段是并发正确性的精髓）：

```ts
const busyCats = new Set<string>();
for (;;) {
  const entry = this.deps.queue.markProcessingAcrossUsers(threadId, busyCats);
  if (!entry) return { started: false };
  const entryCat = entry.targetCats[0] ?? catId;
  const entrySk = QueueProcessor.slotKey(threadId, entryCat);
  if (this.processingSlots.has(entrySk) || this.deps.invocationTracker.has(threadId, entryCat)) {
    this.deps.queue.rollbackProcessing(threadId, entry.id);   // 撤销 markProcessing
    busyCats.add(entryCat);                                    // 下轮跳过这只猫
    continue;
  }
  this.processingSlots.set(entrySk, Date.now());
  void this.executeEntry(entry).then(...);
  return { started: true, entry };
}
```

为什么要"先标记再回滚"而不是"先检查再标记"？因为 `markProcessingAcrossUsers` 需要**跨所有用户**排序取最优，把这个逻辑搬到外面就得先拿全量快照，而快照和标记之间就有窗口。这里的做法是：标记是同步的（原子），发现槽忙就同步回滚，`busyCats` 保证不会无限循环。**注意 `rollbackProcessing(threadId, entryId)` 的签名不带 userId** —— 它遍历所有 scope 找这个 id，因为调用方此刻不知道条目属于谁。

**`tryExecuteNextForUser` 反过来 —— 先检查再标记**：

```ts
// F108 P1-3 fix: peek at next entry's target cat to check slot mutex BEFORE marking processing.
// This prevents entries from getting stuck as 'processing' when the slot is busy.
const nextEntry = this.deps.queue.peekNextQueued(threadId, userId);
if (!nextEntry) return { started: false };
```

注释直接写了这是个 fix：以前先 mark 后检查，槽忙时条目就永久卡在 `processing`（因为没有回滚）。【源码】

**`tryAutoExecute` 的并行分发**：

```ts
for (const entry of entries) {
  const entryCat = entry.targetCats[0] ?? 'unknown';
  const sk = QueueProcessor.slotKey(threadId, entryCat);
  if (this.processingSlots.has(sk)) continue;
  if (this.deps.invocationTracker.has(threadId, entryCat)) continue;
  if (!this.deps.queue.markProcessingById(threadId, entry.id)) continue;  // 快照后被消费了
  this.processingSlots.set(sk, Date.now());
  void this.executeEntry(entry).then(...);
  // Continue scanning — start all entries with free cat slots (parallel dispatch)
}
```

它**不 return**，继续扫 —— 多只猫可以同时起。`markProcessingById` 返回 false 的守卫注释写得很清楚：`may fail if entry was consumed between snapshot and now`。

三条路径的 `.then()` 收尾**完全一样**：

```ts
void this.executeEntry(entry).then(
  (status) => {
    this.processingSlots.delete(sk);                                   // ① 先释放槽
    this.onInvocationComplete(threadId, entryCat, status).catch(() => {}); // ② 再链下一条
    this.signalDeliveryBatchDone(threadId, status);
  },
  () => {
    this.processingSlots.delete(sk);
    this.onInvocationComplete(threadId, entryCat, 'failed').catch(() => {});
    this.signalDeliveryBatchDone(threadId, 'failed');
  },
);
```

顺序不能反。文件末尾有注释解释：
> Chain auto-dequeue is handled by tryExecuteNext* (calls onInvocationComplete **AFTER** releasing processingThreads mutex to avoid self-blocking).

【源码】如果先调 `onInvocationComplete` 再删槽，下一条同猫条目会看到槽还占着 → 不启动 → 队列停住。

**终态映射表**：

| 触发条件 | `finalStatus` | 记录状态 | onInvocationComplete 走哪个分支 |
|---|---|---|---|
| `create` 返回 `duplicate` | `succeeded` | 不动（另一条在跑） | 成功分支 |
| 预启动窗口被墓碑 | `canceled_by_user` | `canceled` | 成功分支（立即重启后继条目） |
| reborn 会话丢弃续跑条目 | `succeeded` | `succeeded` | 成功分支 |
| `batch.aborted && reason ∈ {user_cancel, cancel_all}` | `canceled_by_user` | `canceled` | 成功分支（+ cancel_all 打 suppress） |
| `batch.aborted && 其他 reason`（如 `preempted`） | `canceled` | `canceled` | 暂停分支 |
| 未 abort 但每只目标猫都是 canceled 墓碑 | `canceled_by_user` | `canceled` | 成功分支 |

⚠️ 最反直觉的一条：**墓碑自检返回 `canceled_by_user` 而不是 `canceled`**。源码注释解释了动机：

> Status: 'canceled_by_user' (not plain 'canceled') so onInvocationComplete takes the immediate-restart branch (tryAutoExecute) rather than the 10s pause branch. No suppressedAutoResume flag is set (only cancelAll sets it), so the suppress check is a no-op. Result: follow-up restarts immediately after slot release.

【源码】这是"借用状态语义换调度行为"的典型例子 —— 面试里说出这一条，比背整个流程更有说服力。

> **面试官追问：`create` 返回 duplicate 为什么算成功？**
> 「因为 duplicate 意味着同一个 idempotencyKey 已经有另一条 invocation 在跑或跑完了 —— 活已经有人干了。如果这里返回 failed，`onInvocationComplete` 会走暂停分支，把整个槽暂停 10 秒并给用户弹 `queue_paused`，用户会看到一个莫名的失败。返回 succeeded 则直接链下一条，用户完全无感。」

### 3.4 `onInvocationComplete()` 的处理链

```
onInvocationComplete(threadId, catId, status)
  sk = slotKey(threadId, catId)
  │
  ├─ status ∈ {succeeded, canceled_by_user}
  │    pausedSlots.delete(sk)
  │    suppressTs = suppressedAutoResume.get(sk)
  │    ├─ suppressTs 存在 且 已过 SUPPRESS_TTL_MS(60s) → delete（清陈旧标记）
  │    ├─ status === 'canceled_by_user' 且 suppressTs 新鲜
  │    │    → delete（单次消费）+ log「Auto-resume suppressed (cancelAll)」+ **return**
  │    └─ hasDispatchableQueuedForThread(threadId)
  │         → await tryExecuteNextAcrossUsers(threadId, catId)
  │         → await tryAutoExecute(threadId)
  │
  └─ status ∈ {failed, canceled}
       ├─ hasQueuedAutoContinuationForThreadCat(threadId, catId)
       │    → pausedSlots.delete(sk)
       │    → tryAutoExecute(threadId, {onlyContinuation:true, bypassNonAgentGate:true, onlyTargetCat:catId})
       │    → **return**（失败也要让续跑跑起来）
       ├─ !hasDispatchableQueuedForThread(threadId) → pausedSlots.delete(sk) + return（没队列就不暂停）
       └─ 真正暂停：
            epoch = (pauseEpoch.get(sk) ?? 0) + 1
            pauseEpoch.set(sk, epoch)
            pausedSlots.set(sk, status)
            await emitPausedToQueuedUsers(threadId, status)   ← 给每个有排队条目的用户发 queue_paused
            setTimeout(() => {
              if (pauseEpoch.get(sk) !== epoch) return;       ← 世代号校验
              pausedSlots.delete(sk)
              if (hasDispatchableQueuedForThread) void tryExecuteNextAcrossUsers(threadId, catId)
            }, PAUSE_RECOVERY_DELAY_MS /* 10s */)
```

三个关键 if 都值得单独说：

**(a) suppress 检查是"状态门控"的**，注释写了完整的竞态推演：

> Status-gated: ONLY consume on 'canceled_by_user', not 'succeeded'. Reason: if user does cancelAll → steer, the steer's new invocation may complete with 'succeeded' before the cancelled invocation's 'canceled_by_user' arrives. Without the status gate, 'succeeded' would consume the flag and the late 'canceled_by_user' would incorrectly auto-resume the queue.

【源码】这是本文件里最精细的一个竞态：cancelAll 打了标记 → 用户马上 steer → 新调用先成功 → 如果 succeeded 消费掉标记，那迟到的 canceled_by_user 就会触发自动续跑，用户点了"全部取消"结果队列自己跑起来了。

**(b) "没队列就不暂停"** —— 暂停只是为了管理排队条目。一个失败但队列为空的槽不需要进入 paused 状态，否则 `isPaused()` 的语义会被污染。注意 `isPaused()` 本身也是双条件：

```ts
isPaused(threadId, catId?) {
  if (catId) return this.pausedSlots.has(slotKey(threadId, catId)) && this.hasDispatchableQueuedForThread(threadId);
  ...
}
```

**(c) 续跑优先于暂停** —— failed 也要给续跑条目开路，而且是三个 opts 全开（`onlyContinuation` + `bypassNonAgentGate` + `onlyTargetCat`）。为什么？因为续跑本来就是"上一次没跑完/失败了"的产物，如果失败就暂停 10 秒，续跑链会被切碎。【推断，源码只有代码没有注释解释】

> **面试官追问：为什么 `pauseEpoch` 需要世代号？直接在 clearPause 里 clearTimeout 不行吗？**
> 「不行，因为 timer handle 没被存下来，而且更根本的问题是：同一个槽可以在 10 秒内暂停两次。假设第一次 failed 起了一个 10s timer，用户 5 秒时手动 processNext（内部调 clearPause），7 秒时又 failed 起了第二个 timer —— 第一个 timer 在 10 秒时触发，它会把第二次的暂停也清掉，第二次的 10 秒保护就没了。epoch 让每个 timer 只对自己那一代负责：`if (pauseEpoch.get(sk) !== epoch) return`。仓里有专门的红测 `queue-processor-pause-epoch.test.js`，断言 `clearPause must not reset epoch or old timers can collide with later pauses`。」

## 4. 关键算法与判定逻辑

### 4.1 出队排序：`compareEntries` 四级比较

```ts
private static compareEntries(a: QueueEntry, b: QueueEntry): number {
  const aPinned = isSystemPinnedQueueEntry(a);
  const bPinned = isSystemPinnedQueueEntry(b);
  if (aPinned && !bPinned) return -1;
  if (!aPinned && bPinned) return 1;

  if (a.userId === b.userId) {                        // ← 关键：position 只在同用户内比较
    const aHasPos = a.position !== undefined;
    const bHasPos = b.position !== undefined;
    if (aHasPos && !bHasPos) return -1;
    if (!aHasPos && bHasPos) return 1;
    if (aHasPos && bHasPos) return a.position! - b.position!;
  }
  const pDiff = (PRIORITY_RANK[a.priority] ?? 1) - (PRIORITY_RANK[b.priority] ?? 1);
  if (pDiff !== 0) return pDiff;
  return a.createdAt - b.createdAt;
}
```

可复述的四步：

1. **系统钉住优先**：`isSystemPinnedQueueEntry(e) === (e.source === 'agent' && e.sourceCategory === 'continuation')`，即续跑条目永远第一。
2. **同用户内比 position**：有显式 position 的排在没有的前面；都有则按数值。**跨用户不比 position**，注释明写原因：`Position is scoped to same-user entries to prevent cross-user queue-jumping in shared threads` —— 否则共享 thread 里你把自己拖到 position=-99 就能插到别人前面。
3. **比 priority**：`urgent(0) < normal(1)`。
4. **比 createdAt**：真正的 FIFO。

⚠️ 这个 comparator **不是全序**（跨用户时 position 被忽略，可能出现 A<B、B<C 但 A、C 不可比的情况）。`Array.prototype.sort` 对非全序 comparator 结果不保证稳定语义。【推断】实践中因为最终 tiebreak 是 createdAt（唯一性高），不会真的乱。

`isSystemPinnedQueueEntry` 还是三个"禁止操作"的门禁：`setPosition()` / `move()` / `promote()` 都会 `if (isSystemPinnedQueueEntry(e)) return false`；`routes/queue.ts` 的 steer 也会直接返 409 `ENTRY_POSITION_LOCKED`。【源码】

**`promote()` 的算法**（把条目提到最前）：

```ts
const minPos = q.reduce((min, e) => {
  if (e.status === 'queued' && e.position !== undefined && e.position < min) return e.position;
  return min;
}, 0);
entry.position = minPos - 1;
```

注意初始值是 `0`，所以第一次 promote 得到 `-1`，第二次 `-2`……position 会往负无穷走。没有重排/归一化。【源码】

**`move()` 的算法**（上下移一位）：先把 queued 条目按 comparator 排序，然后 `for (let i...) queued[i].position = i` **全量重编号**，再交换目标和邻居的 position。所以 move 是"归一化 + 交换"，promote 是"往负数走"，两者混用后 position 分布会很奇怪但排序结果正确。【源码】

**`collectUserBatch()` 的合并条件**：

```ts
const first = queued[0]!;
if (first.source !== 'user') return [{ ...first }];   // 非 user 一律单条
const batch = [{ ...first }];
const firstTargetsSorted = sorted(first.targetCats);
for (let i = 1; i < queued.length; i++) {
  const e = queued[i]!;
  if (e.source !== 'user' || e.intent !== first.intent || !arraysEqual(sorted(e.targetCats), firstTargetsSorted)) break;
  batch.push({ ...e });
}
```

三个条件全满足才合并：同 source(user) + 同 intent + targetCats 集合相等。**遇到第一个不匹配就 `break`**（不是 continue）—— 保证合并的是"相邻"消息，不会跨过一条别的消息去合并后面的。

### 4.2 判忙：五个层次

这是最容易被追问的地方 —— "你怎么知道一只猫忙不忙？"答案是**五个信号源，覆盖不同的时间窗**：

```
时间轴：
  t0 入队            t1 markProcessing   t2 startAll        t3 done/error   t4 completeAll
   │                   │                    │                  │              │
   ├── queue.status='queued' ──┤            │                  │              │
   │                   ├── queue.status='processing' ───────────────────────── ┤
   │                   ├── processingSlots.has(sk) ───────────────────────── ┤
   │                                        ├── tracker.has(tid,cat) ────────┤
   │                                        ├── record.status='running' ─────┤（跨进程）
   │                                        ├── draft.updatedAt 刷新 ───────┤（跨进程，心跳）
                        ↑
              「预启动窗口」：processingSlots 已占，tracker 还没占
              长度 = invocationRecordStore.create 的耗时（一次 Redis eval，无上界）
```

**"预启动窗口"是这个系统里最重要的一个概念**，源码里有一整段注释（`routes/queue.ts` 的 steer 分支）在讲它：

> its processingSlot may still be occupied by an executeEntry stuck in the PRE-START window (processingSlots.set runs before `await invocationRecordStore.create` + startAll — a window bounded by a Redis `eval`, NOT by any constant). Force-releasing that slot by age would double-start the cat once create returns.

【源码】所以：**只看 tracker 会漏（预启动窗口内 tracker 是空的），只看 processingSlots 会漏（直接 /api/messages 路径不走 QueueProcessor，不占 processingSlots）**。判忙必须两个都看。

五个层次的实际 API：

| API | 看什么 | 用在哪 |
|---|---|---|
| `invocationTracker.has(tid, cat)` | 槽位表，排除墓碑和过期 | 所有分发前的最后一道门 |
| `QueueProcessor.isCatBusy(tid, cat)` | `processingSlots`（带 TTL 判新鲜） **+** `queue.hasQueuedOrProcessingForCat` | `routes/messages.ts` 决定 immediate vs queue |
| `QueueProcessor.hasActiveExecution(tid)` | `tracker.has(tid)` **+** 新鲜的 processingSlots（先 sweep） | broadcast（无 @mention）判忙 |
| `QueueProcessor.isThreadBusy(tid)` | `hasDispatchableQueuedForThread` **+** 任意 processingSlot | F151 投递批次结束信号 |
| `getThreadLiveInvocations()` | record + tracker + draft 三方对账 | HTTP 读端（前端"正在回复中"） |

注意 `isCatBusy` 和 `hasActiveExecution` 的区别：

```ts
isCatBusy(threadId, catId) {
  const startedAt = this.processingSlots.get(slotKey(threadId, catId));
  if (startedAt !== undefined && Date.now() - startedAt < this.processingSlotTtlMs) return true;
  return this.deps.queue.hasQueuedOrProcessingForCat(threadId, catId);
}
hasActiveExecution(threadId) {
  if (this.deps.invocationTracker.has(threadId)) return true;
  this.sweepZombieSlots(threadId);
  // 只算新鲜的 processingSlots，不算 queued
  ...
}
```

`isCatBusy` **算 queued**（有人在等这只猫也算忙 → 新消息也去排队，保持顺序）；`hasActiveExecution` **不算 queued**，注释：`Active execution only; queued leftovers are not enough to keep new broadcasts in queue mode` —— 否则残留的 queued 条目会让整个 thread 永久处于队列模式。【源码】

### 4.3 四个"僵尸 processing"阈值判定

`InvocationQueue` 里有四个方法都在做"processing 条目还算不算数"的判定，规则统一：

```ts
const processingAge = now - (e.processingStartedAt ?? e.createdAt);
if (processingAge < STALE_PROCESSING_THRESHOLD_MS /* 600_000 */) return true;  // 算忙
// 否则 warn 一条 '[DIAG] ... ignoring stale processing entry (zombie defense)' 后 continue
```

（**只有 `hasActiveOrQueuedAgentForCat` / `hasPendingForCat` 打这条 warn**；`hasQueuedOrProcessingForCat` 和 `findInFlightAgentEntry` 里超阈值是静默跳过。【源码】）

⚠️ 用 `processingStartedAt` 而不是 `createdAt`，注释写了原因：

> An entry may sit queued for a long time before being picked up — using createdAt would falsely expire it the moment it starts processing. (P1 fix per codex review)

【源码】这是个真实修过的 bug：条目排队 20 分钟后开跑，用 createdAt 算的话它一开跑就"已经 20 分钟了"→ 立刻被当僵尸忽略 → A2A 路由认为这只猫空闲 → 双起。

而 **queued 条目的判定各处不同**，这是一张必须记住的对比表：

| 方法 | queued 是否有陈旧过期 | 为什么 |
|---|---|---|
| `hasQueuedForThread` | **有**（agent 除外，60s） | 只用于公平性/队列模式路由，老的交互消息不该永久锁死 thread |
| `hasDispatchableQueuedForThread` | **无** | 注释：`a queued entry is pending work until it is dispatched, canceled, or cleared` |
| `hasActiveOrQueuedAgentForCat` | **无**（queued 永远算） | queued agent 条目是合法待分发工作，`listAutoExecute` 迟早会捞它 |
| `hasPendingForCat` | **无** | 同上 |
| `hasQueuedOrProcessingForCat` | **无** | 同上 |
| `hasQueuedNonAgentForThread` | **无** | 公平性门要严 |

一句话记：**"能不能分发"用无过期版本，"路由决策/展示"用有过期版本。**

### 4.4 公平性三个方法：分别在什么场景用

| 方法 | 定义 | 场景 |
|---|---|---|
| `hasDispatchableQueuedForThread(tid)` | 任意 scope 有 `status==='queued'` | `onInvocationComplete` 决定要不要链下一条；`isPaused` 的第二个条件；`isThreadBusy` |
| `hasDispatchableNonAgentQueued(tid)` | 有 non-agent queued 条目**且它的目标猫的槽没被暂停** | `tryAutoExecute` 的入口门 —— agent 条目不能抢在用户消息前面 |
| `hasQueuedAutoContinuationForThreadCat(tid, cat)` | `listAutoExecute` 里有 `source==='agent' && sourceCategory==='continuation' && targetCats[0]===cat` | `onInvocationComplete` 失败分支的第一个 if —— 失败也要让这只猫的续跑跑起来 |

`hasDispatchableNonAgentQueued` 的实现有个精细之处：

```ts
private hasDispatchableNonAgentQueued(threadId: string): boolean {
  if (!this.deps.queue.hasQueuedNonAgentForThread?.(threadId)) return false;
  for (const userId of this.deps.queue.listUsersForThread(threadId)) {
    for (const entry of this.deps.queue.list(threadId, userId)) {
      if (entry.source === 'agent' || entry.status !== 'queued') continue;
      const cat = entry.targetCats[0];
      if (!cat || !this.pausedSlots.has(QueueProcessor.slotKey(threadId, cat))) return true;
    }
  }
  return false;
}
```

**关键：目标猫的槽处于 paused 时，这条 non-agent 条目不算"可分发"。** 为什么？因为一条卡在 paused 槽上的用户消息本来就跑不了，如果它还继续挡住 agent 条目，整个 thread 就死锁了 —— 用户消息等 paused 解除，agent 条目等用户消息，而 paused 解除靠 10s timer，timer 触发后又只调 `tryExecuteNextAcrossUsers`。【推断，注释没说但逻辑唯一解释】

`tryAutoExecute` 的三个 opts 就是给这个门开后门用的：

```ts
async tryAutoExecute(threadId, opts: {onlyContinuation?, bypassNonAgentGate?, onlyTargetCat?} = {}) {
  this.sweepZombieSlots(threadId);
  if (!opts.bypassNonAgentGate && this.hasDispatchableNonAgentQueued(threadId)) return;
  const entries = (this.deps.queue.listAutoExecute?.(threadId) ?? [])
    .filter(e => !opts.onlyContinuation || e.sourceCategory === 'continuation')
    .filter(e => !opts.onlyTargetCat || e.targetCats[0] === opts.onlyTargetCat)
    .sort((a, b) => a.createdAt - b.createdAt);   // ← 注意：这里是纯 FIFO，不用 compareEntries
```

⚠️ `tryAutoExecute` 用的是 **`createdAt` 纯 FIFO 排序**，不是 `compareEntries`。所以 autoExecute 路径不看 priority/position/pinned。【源码】这是个真实的不一致 —— 面试里被问"你觉得哪里可能有问题"，这是第二个可以说的点。

### 4.5 续跑限流：三层拦截

`enqueueContinuation()` 按顺序过六道关：

```
1. !capsule                                      → 'skipped_missing_capsule'
2. !isCollaborationContinuityCapsuleV1(capsule)  → 'skipped_invalid_capsule'
3. capsule.threadId !== threadId || capsule.catId !== catId  → 'skipped_invalid_capsule'（跨 thread 污染防护）
4. 一小时窗口内已有 5 次                            → 'skipped_rate_limited'
5. hasPendingForCat(tid, cat, {sources:['agent'], sourceCategories:['continuation'], continuationKey}) → 'skipped_existing_entry'
6. enqueue 返回 'full'                            → 'queue_full'
否则 → 'enqueued'（+ recent.push(now) + emitQueueUpdated 'continuation_enqueued'）
```

**限流实现是滑动窗口数组**：

```ts
const now = Date.now();
const key = `${threadId}:${catId}`;
const recent = (this.continuationWindows.get(key) ?? []).filter(t => now - t < CONTINUATION_WINDOW_MS);
if (recent.length >= MAX_CONTINUATIONS_PER_WINDOW) { this.setContinuationWindow(key, recent); return {outcome:'skipped_rate_limited'}; }
```

注意限流计算之后的每条 return 路径（rate_limited / existing_entry / queue_full / enqueued）都调了 `setContinuationWindow(key, recent)` —— **过滤后的数组要写回去**，否则过期时间戳永远留着，内存泄漏 + 限流越来越严。（前三道关在算 `recent` 之前就 return，自然没有写回动作。）`setContinuationWindow` 还会在空数组时 `delete` 掉整个 key（避免 Map 无限增长）：

```ts
private setContinuationWindow(key: string, recent: number[]): void {
  if (recent.length === 0) { this.continuationWindows.delete(key); return; }
  this.continuationWindows.set(key, recent);
}
```

**`continuationKey` 的构造**（去重的核心）：

```ts
private static continuationKey(capsule: CollaborationContinuityCapsuleV1): string {
  const seal = capsule.seal;
  const sealPart = seal ? `${seal.sessionId}:${seal.sessionSeq}` : `created:${capsule.createdAt}`;
  return `${capsule.threadId}:${capsule.catId}:${capsule.invocationId ?? 'unknown-invocation'}:${sealPart}`;
}
```

四段：thread + cat + invocationId + (sessionId:sessionSeq | created:createdAt)。有 seal 时用 `sessionId:sessionSeq` —— 这才是"同一次封存"的稳定身份；没 seal（比如 compact 边界产生的胶囊）退化成 createdAt。`sessionSeq` 让同一个 session 的第 N 次封存能区分开。【源码 + `CollaborationContinuityCapsule.ts` 的 `seal` 字段定义】

同一个 key 被 `hasPendingForCat(..., { continuationKey })` 用于精确去重 —— 注意它传的过滤条件是四件套：`excludeEntryId` + `sources:['agent']` + `sourceCategories:['continuation']` + `continuationKey`。少任何一个都会误判（比如不带 `sourceCategories` 就会被这只猫的 A2A 条目挡住）。

> **面试官追问：为什么续跑要限流 5 次/小时？**
> 「因为续跑是自动的、可以自我触发的：一次 invocation 产出 capsule → 入队一条续跑 → 续跑跑完又可能产出 capsule → 无限链。没有硬上限的话，一只猫可以自己把 CLI 配额烧光。1 小时窗口 + 5 次是"允许长任务分段做完，但不允许无限自转"的折中。而且限流键是 `${threadId}:${catId}`，粒度到猫，一只猫刷爆不影响别的猫。」

### 4.6 A2A 合并的两趟扫描：`findInFlightAgentEntry`

```ts
const matches = (e: QueueEntry): boolean => {
  if (!(e.source === 'agent' && e.sourceCategory === 'a2a' && e.targetCats.includes(catId))) return false;
  if (callerCatId === undefined) return true;                                    // caller 作用域未开启
  return e.callerCatId !== undefined && e.callerCatId === callerCatId;           // 严格双向匹配
};
// Pass 1: 优先找 queued（可原地合并）
for (...) if (matches(e) && e.status === 'queued') return { ...e };
// Pass 2: 退而找新鲜的 processing（调用方要 supersede）
for (...) { if (!matches(e) || e.status !== 'processing') continue;
            const age = now - (e.processingStartedAt ?? e.createdAt);
            if (age < STALE_PROCESSING_THRESHOLD_MS) return { ...e }; }
return null;
```

三层作用域收窄，每一层都是一次 review 修出来的（注释里带 review 出处）：

1. `sourceCategory === 'a2a'`（云端 codex R4 P1）：只看 `source==='agent'` 会匹配到续跑条目 → A2A 交接内容会被拼进续跑 prompt，两件不相干的事串味，而且真正的 A2A 路由被吞掉。
2. `callerCatId` 严格匹配（F216 c0 / 砚砚 GPT-5.5 P1）：只有**同一个 caller** 的重复交接才可合并。否则猫 A 排给目标的交接会被猫 B 后来的交接合并掉（"cross-caller 串味"）。严格性体现在"两边都必须有定义且相等"，注释里叫 `safe direction: prefer a fresh entry over a wrong merge`。
3. 两趟扫描的顺序（注释解释）：一只猫可能**同时**有一条在跑和一条排队的后继。第三次交接必须合进那条排队的后继，不能再生一条 —— 所以要先扫 queued。

【源码，三处注释都带 review 编号】

`coalesceContentIntoQueuedAgent()` 是同样三道门的**纵深防御**（defense-in-depth）副本：

```ts
if (!e || e.status !== 'queued') return false;
if (!(e.source === 'agent' && e.sourceCategory === 'a2a')) return false;
if (callerCatId !== undefined && !(e.callerCatId !== undefined && e.callerCatId === callerCatId)) return false;
e.content = `${e.content}\n\n${content}`;   // 空行分隔，让目标猫看成一条连贯消息
if (messageId && e.messageId !== messageId && !e.mergedMessageIds.includes(messageId)) e.mergedMessageIds.push(messageId);
```

**为什么同样的检查要写两遍？** 注释直说了：`findInFlightAgentEntry already caller-scopes, but guard here too so a stale/wrong entryId from a different caller can never splice content`。合并是不可逆的内容污染，值得双保险。【源码】

### 4.7 `invocation-state-machine` 转移表

```ts
const VALID_TRANSITIONS = new Map([
  ['queued',    new Set(['running', 'failed', 'canceled'])],
  ['running',   new Set(['succeeded', 'failed', 'canceled'])],
  ['failed',    new Set(['running', 'canceled'])],
  ['succeeded', new Set()],   // 终态
  ['canceled',  new Set()],   // 终态
]);
export const TERMINAL_STATES = new Set(['succeeded', 'canceled']);
```

矩阵形式（行=from，列=to，✓=合法）：

| from ↓ / to → | queued | running | succeeded | failed | canceled |
|---|---|---|---|---|---|
| queued | — | ✓ | — | ✓ | ✓ |
| running | — | — | ✓ | ✓ | ✓ |
| succeeded | — | — | — | — | — |
| failed | — | ✓ | — | — | ✓ |
| canceled | — | — | — | — | — |

关键性质：
- **`failed → running` 合法**（重试，CAS 保护的重新占位）；`succeeded → *` 和 `canceled → *` 全部非法。
- **自转移全部非法**（`running → running` 也不行，因为 running 的 allow-set 里没有 running）。这直接给了 `reconcileZombies` 幂等性：第二次调用时记录已是 `failed`，而 `failed → failed` 非法 → `update` 返 null → 变 no-op。
- `failed` 只有两条出路（running / canceled），**不能** `failed → succeeded`。

这张表**在两个地方实现了两遍**：TS 的 `isValidTransition()`（内存 store 用）和 `ATOMIC_UPDATE_LUA` 里的 Lua table（Redis store 用）：

```lua
local transitions = {
  queued   = {running=1, failed=1, canceled=1},
  running  = {succeeded=1, failed=1, canceled=1},
  failed   = {running=1, canceled=1},
  succeeded = {},
  canceled  = {}
}
```

【源码】两份必须手工同步 —— 这是个真实的一致性风险点。

### 4.8 `ATOMIC_UPDATE_LUA` 的返回码与 `-3` 重试

```
 1  = 成功
 0  = CAS 不匹配（expectedStatus 或 expectedUsageByCatAbsent 不满足）
-1  = 非法状态转移
-2  = 记录不存在
-3  = (threadId, userId) 漂移 —— KEYS[2] 是陈旧的，调用方要用新快照重试
```

`-3` 是为什么存在的？因为 running 索引的 key 是 `invoc:running:{threadId}:{userId}`，这个 key 是 **JS 侧**从记录快照算出来的（Lua 不能自己拼 KEYS）。如果 `reassignUserId()` 在快照和 EVAL 之间跑了，KEYS[2] 就指向了错误的 Set。Lua 里用 `ARGV[3]/ARGV[4]` 校验：

```lua
local currentThreadId = redis.call('HGET', KEYS[1], 'threadId')
local currentUserId = redis.call('HGET', KEYS[1], 'userId')
if currentThreadId ~= ARGV[3] or currentUserId ~= ARGV[4] then return -3 end
```

JS 侧 `MAX_RETRIES = 3` 的重试循环，`if (result === -3) continue;`。【源码】

**为什么索引维护要放进 Lua？**注释写得很直白：

> post-Lua best-effort SADD/SREM had a race where a process crash between status update and Set update would leave a record `running` but missing from the index, silently re-introducing split-brain. Atomic Lua eliminates that window.

【源码】

`LivenessEvent` 的字段是专门为诊断设计的，**每个字段都能单独回答一个问题**：

```ts
export interface LivenessEvent {
  kind: 'liveness_degraded' | 'liveness_pending' | 'record_zombie_detected';
  threadId, userId, invocationId, catId,
  source: LivenessSource | null,      // 走的哪条判定路径
  reason: LivenessReason | ZombieReason,
  recordStatus: 'running' | 'absent', // 记录侧
  recordUpdatedAt: number | null,
  trackerSlotPresent: boolean,        // tracker 侧（物理存在，不是"归我"）
  draftFresh: boolean | null,         // draft 侧
  draftAge: number | null,
}
```

⚠️ `trackerSlotPresent` 有一条被 review 专门修过的语义：它必须反映**物理存在**，不是分类结果。注释：

> degraded path also fires when tracker slot exists but is owned by another user (R3 P2-1 cross-user guard) — emitting `false` would let monitoring/alerting misclassify ownership-collision as tracker-loss.

【源码】所以看到 `degraded=true` + `trackerSlotPresent=true` 时，八成是**跨用户槽位撞车**，不是 tracker 丢了。

## 7. 面试追问应对

**Q1：`processingSlots` 和 `invocationTracker` 不是重复了吗？为什么要两把锁？**

> 「它们覆盖的时间窗不一样。`processingSlots` 在 `executeEntry` 开始前就 set，`invocationTracker` 要等 `startAll` 才占 —— 中间夹着一个 `await invocationRecordStore.create`，也就是一次 Redis EVAL，这个窗口没有上界。所以：
> - 只看 tracker → 预启动窗口内看起来空闲 → 同一只猫被起两次；
> - 只看 processingSlots → 直接 `/api/messages` 路径不经过 QueueProcessor，根本不占这张表 → 漏判。
> 所以三条调度路径都写 `if (processingSlots.has(sk)) continue; if (tracker.has(tid,cat)) continue;` 两条一起。
> 而且源码里有一段特别硬的注释，说这个窗口 `bounded by a Redis eval, NOT by any constant` —— 所以 steer 的时候**不能**按年龄强行释放槽，只能下墓碑让对方自己退出。」

**Q2：墓碑机制到底怎么写的？给我讲代码。**

> 「墓碑是 `ActiveInvocation.state: 'active' | 'canceled'`。`cancel()` 的关键三行是（中间隔着一条 `f211_reg6_invocation_abort` 观测日志，不是连着写的）：
> ```ts
> inv.controller.abort(abortReason);
> inv.state = 'canceled';
> inv.cancelReason = abortReason;
> ```
> **不删 Map 项**。然后同一个墓碑在四个读接口里呈现完全不同：
> - `has()` → `if (inv.state === 'canceled') return false`，墓碑=不忙；
> - `getController()` → **照样返回**那个已经 abort 的 controller，注释说 `that is the whole point of the tombstone`；
> - `getSlotState()` → 返回 `'canceled'`，让调用方能区分"被取消"和"从没跟踪过"；
> - `getActiveSlots()` → 跳过墓碑。
>
> 为什么必须留？两个场景：
> ① **预调用取消**：一只猫在路由层还没通过 `signalForCat` 拿到自己的 signal 时就被取消了。如果删了槽，`getController` 返 undefined，路由层退回到 batch gate 的 signal —— batch gate 没 abort，于是这只猫照样跑起来，用户的取消丢了。
> ② **终态聚合**：路由消费者在 abort 引发的 `done`/`error` 消息上会调 `completeSlot`，这**发生在** `resolveFinalStatus` 之前。如果 completeSlot 删掉墓碑，`getSlotState` 返 `'absent'`，`resolveFinalStatus` 就会算出 `'succeeded'` —— 明明用户取消了却记成成功。所以 `complete/completeSlot/completeAll` 三个都写了 `if (inv.state === 'canceled') return/continue`。
>
> 清除路径只有三条：start 家族覆盖（重新占位）、`trackExternalSlot` 显式替换、75 分钟 TTL。顺带一提，interface 上那句注释说 complete 家族也会清墓碑，是过期的 —— 代码里明确不清。」

（加分点：能指出注释和代码的不一致，说明真的读过。）

**Q3：`batchController` 和 per-cat controller 是什么关系？**

> 「`startAll(threadId, catIds, userId)` 里：为每只猫 `new AbortController()` 存进它自己的槽，另外**独立**建一个 `batchController` 存进每个槽的 `batchController` 字段，然后 **return `batchController`**。
> 所以返回值不是任何一只猫的 controller，而是"整个 invocation 的门"。
> （⚠️ 又一处文档滞后：`startAll` 自己的 JSDoc 还写着 `Returns the primaryCat's (catIds[0]) controller for execution signal.`，`getController` 的注释也说 `only RETURN primaryController`——**代码 return 的是 `batchController`**，以正文注释块里 `cancelAll aborts the batch controller` 那段为准。别照着 JSDoc 背。【源码】）
> - 单猫取消（`cancel`）→ 只 abort 那只猫的 `controller`，batch gate 不动；
> - `cancelAll` → abort 每只猫的 controller **并且**收集去重后 abort 所有 `batchController`；
> - `cancelInvocation(threadId, anchorCats)` → 只 abort anchor 猫和跟它共享同一个 batch gate 的槽，别的 batch 不动 —— 这样 force 抢占 @codex 不会误杀同 thread 里另一个 opus 侧分发。
>
> 这个设计让 `executeEntry` 的消费循环 `if (controller.signal.aborted) break` 只在**整批取消**时触发；单猫取消时兄弟猫继续流。而路由层拿每只猫的信号是通过 `signalForCat: (catId) => tracker.getController(tid, catId)?.signal`。
> `trackExternalSlot` 是这个模型的补充：A2A 目标传进来的 controller 其实是 batch gate，所以它**不能**存成 `slot.controller`（否则 `cancel(threadId, catB)` 就 abort 了整条 serial worklist），必须给这个槽新建自己的 controller、把传入的存成 `batchController`。」

**Q4：`tryStartThread` / `tryStartThreadAll` / `start` / `startAll` / `guardDelete` 有什么区别？**

> 一张表答：
>
> | 方法 | 抢占已有的同槽调用？ | thread 级忙就失败？ | 返回 | 用在哪 |
> |---|---|---|---|---|
> | `start` | **是**（`abort('preempted')`） | 否 | AbortController（deleting 时返回预 abort 的） | 单猫抢占式启动 |
> | `startAll` | **是**（每只猫都抢） | 否 | batchController | `QueueProcessor.executeEntry` |
> | `tryStartThread` | 否（**从不 abort**） | **是**（`this.has(threadId)`） | `AbortController \| null` | `ConnectorInvokeTrigger` |
> | `tryStartThreadAll` | 否 | **是** | `AbortController \| null` | `routes/messages.ts` 直发路径 |
> | `trackExternalSlot` | 否（但**替换墓碑**） | 否 | `boolean` | A2A worklist 目标 |
> | `guardDelete` | 否 | **是** | `{acquired, release}` | `routes/threads.ts` 删 thread |
>
> 「关键差异是三条轴：**要不要抢占**（start 家族抢，try 家族不抢）、**检查粒度**（try 家族查整个 thread `has(threadId)`，start 家族只管自己那个槽）、**deleting 时的行为**（start 返回预 abort 的 controller，try 返回 null）。
> `guardDelete` 特殊：它是同步的 check-and-set —— 一个 tick 内查完所有槽再 `deleting.add(threadId)`，中间不能有 await，否则删除和新调用会交叉。调用方必须在 finally 里 `release()`。deleting 期间 `start()` 返回**预先 abort 的 controller**（不是 null），这样调用方不用改代码路径，跑起来立刻自己中止。」

**Q6：`SUPPRESS_TTL_MS` 为什么是 60 秒？为什么需要 TTL？**

> 「需要 TTL 是因为 suppress 是"每槽一次性"的标记，但 cancelAll 会给**每只被取消的猫**都打一个：
> ```ts
> for (const catId of cancelledCatIds) { ...releaseSlot(...); suppressAutoResume(threadId, catId); }
> ```
> 多猫场景下，次要猫可能永远不会触发 `onInvocationComplete`（比如它的 executeEntry 早就退出了），标记就永久留在 Map 里。下次这只猫正常被单独取消时，那个陈旧标记会错误地抑制续跑 —— 用户点了单猫取消，队列却不动了。
> 60 秒是"一次取消的清理链最多多久跑完"的工程判断【推断】—— 源码只给了 TTL 的动机，没解释这个数值。我会答：它需要远大于"一次 cancel 的清理链耗时"（毫秒级）、远小于"用户下一次操作的间隔"（秒到分钟级），60s 在这两个尺度之间。
> 而且清理和判定是两段独立逻辑：先无条件清陈旧标记，再判是否命中：
> ```ts
> if (suppressTs !== undefined && Date.now() - suppressTs >= SUPPRESS_TTL_MS) this.suppressedAutoResume.delete(sk);
> if (status === 'canceled_by_user' && suppressTs !== undefined && Date.now() - suppressTs < SUPPRESS_TTL_MS) { ...delete(sk); return; }
> ```」

**Q7：steer immediate 是怎么实现的？为什么有两条完全不同的分支？**

> 「按 `invocationTracker.has(threadId, steerCatId)` 分两条：
>
> **分支 A（tracker 有槽 = 真的在跑）**：跨用户校验 → `tracker.cancel(..., 'preempted')` → 广播 cancel 消息（**只 scope 到 steerCatId**，因为 `cancelResult.catIds` 是整批，广播整批会清掉兄弟猫的 UI）→ `orchestrator.abortBySlot` → `clearPause` + `releaseSlot` → `promote` → `processNext`。
>
> **分支 B（tracker 没槽但 processingSlot 可能占着 = 预启动窗口）**：这里**不能** `releaseSlot`。原因源码写了：`create` 是一次无上界的 Redis EVAL，你按年龄强释放，等 create 返回后老的 executeEntry 照样继续跑，加上新起的那条 = 双起。
> 唯一安全的动作是**下墓碑**：`invocationQueue.findProcessingByCat(threadId, catId)` 找到那条 in-flight 条目（先做跨用户校验），`removeProcessedAcrossUsers(threadId, inflight.id)` 把它删掉。`executeEntry` 在 `startAll` 之后有个自检：
> ```ts
> if (!queue.list(threadId, userId).some(e => e.id === entry.id)) { ...; finalStatus = 'canceled_by_user'; return 'canceled_by_user'; }
> ```
> 它自己中止、自己释放槽，然后被 promote 的条目通过 `tryAutoExecute` 起来。返回 **202 + `code: 'PREEMPT_PENDING_PRESTART'`**（不是 200，因为是延迟生效）。
> 还有一个容易漏的收尾：被墓碑的条目的 executeEntry 是在 `markDelivered` 之前中止的，所以它的用户消息会永久停在 `deliveryStatus='queued'`（不可见、不进上下文）。steer 路径必须先收集 `[messageId, ...mergedMessageIds]`，然后 `markCanceled` + 发 `message_deleted`。」

**Q8：`getThreadLiveInvocations` 到底在判什么？为什么要 1122 行？**

> 「它要在**三个语义不等价的存储**之间对账，回答"这个 (thread, user) 现在有哪些调用真的活着"：
> - `InvocationTracker` = 进程内控制面（AbortController），**不是**生命周期真相源，进程重启就没了；
> - `InvocationRecord` = 跨进程真相源，但可能是僵尸（进程死了记录还是 running）；
> - `DraftStore` = 300 秒 TTL 的内容缓存，`draft.updatedAt` 是唯一真心跳（每个 stream chunk 都 touch）。
>
> 核心洞察一句话：**`record.updatedAt` 不是心跳**（只在状态转移时变），所以判活必须用 draft。
>
> 判定结果有 6 种 source × 6 种 reason，还有 2 种僵尸原因：
> - source: `record+tracker` / `record+draft` / `record-only` / `tracker+draft` / `parent+child+tracker` / `parent+child-draft`
> - reason: `tracker_present` / `record_running_with_fresh_draft` / `liveness_pending` / `tracker_active_missing_record` / `namespace_chain_active` / `namespace_chain_degraded`
> - zombie: `no_tracker_no_fresh_draft_age_exceeded` / `cat_slot_reused_no_self_draft`
> - 常量：`DEFAULT_FRESH_DRAFT_WINDOW_MS = 300_000`（= DraftStore TTL）、`DEFAULT_ZOMBIE_GRACE_MS = 600_000`（= 2×）。
>
> 1122 行主要花在两件事上：
> ① **槽位归属（single-injective mapping）**：一个 tracker 槽最多只能证明一个 invocation 活着。归属者 = 这只猫**最早锚定**的那个 draft（`slot.startedAt <= draft.createdAt`），预算在 `slotClaimedByDraft: Map<catId, DraftRecord>` 里。强路径（`record+tracker` / `tracker+draft`）只有槽主能用；弱路径（`slotAssocWithRecordSingle`）给没有自己 draft 的记录兜底，条件是"同猫只有一条 running 记录 + `record.createdAt <= slot.startedAt` + 没有别的 draft 占槽"。
> ② **namespace 桥（Phase Z）**：父 recordStore invocation ↔ 子 registry per-cat-turn 是两套 id 空间。桥靠 `getTurnInvocation(childId) → {parentInvocationId, threadId, userId, catId, createdAt}`（包 `InvocationRegistry.getRecord`）。还要做 per-parent 选子（registry latest 指针优先，退化到最新 createdAt）+ **跨 parent 同猫去重**（loser 只有在它所有猫都输了才算真僵尸，且 per-parent 去重）。
>
> 它识别的异常形态清单：无 tracker 无新鲜 draft 且超宽限（真僵尸）／有记录无 tracker 但 draft 新鲜（degraded 但活）／有记录无 tracker 无 draft 但在宽限内（`liveness_pending`）／tracker 活但记录丢了（恢复路径，`tracker+draft`）／记录非 running 或跨 thread/user（drop）／tracker 槽被别的用户持有（跨用户撞车 → 不算 healthy）／猫槽被另一个 parent 的新鲜 draft 抢了（`cat_slot_reused_no_self_draft`）／同猫多 parent 竞争（latest 指针裁决）／陈旧 draft 想抢槽主（预过滤掉）。」

**Q9：三个对账器怎么分工？**

> | | 触发时机 | 数据源 | 写成什么 | 粒度 |
> |---|---|---|---|---|
> | `sweepZombieSlots` | 每次 `tryAutoExecute` / `tryExecuteNext*` / `isThreadBusy` / `hasActiveExecution` 之前（同步、进程内） | `processingSlots` + `tracker.has` | 删掉进程内 slot（**不碰 Redis**） | per-slot |
> | `reconcileZombies` | 读端点返回响应**之后** fire-and-forget（`routes/queue.ts` / `routes/messages.ts`） | `getThreadLiveInvocations` 的 `zombies[]` | `failed(error='zombie_record_detected')` + 清 TaskProgress + 记 `invocation.died` | per-record |
> | `StartupReconciler` | 进程启动，且**在拿到 Redis namespace lease + 绑定 HTTP 端口之后** | `scanByStatus('running')` / `scanByStatus('queued')` | `failed(error='process_restart')` + 清 TaskProgress + 恢复消息可见性 + 给 thread 发系统通知 | 全库扫 |
>
> 「三层的关系是"越往下越慢、越权威"：sweepZombieSlots 是同步的进程内自愈（阈值 75min，且必须 `!tracker.has` 双确认）；reconcileZombies 是请求驱动的运行时收尸（阈值 600s，靠 draft 判活）；StartupReconciler 是重启后的全量兜底（queued 的阈值是 5min）。
> 三者都是幂等的，靠同一个东西保证：状态机 + CAS。`update({status:'failed', expectedStatus:'running'})`，第二次调用时记录已是 failed，而 `failed → failed` 在转移表里非法 → 返 null → no-op。」

**Q10：`reconcileZombies` 里 CAS 返 null 有三种情况，为什么要分？**

> 「因为一开始只分两种（"已终态"和"成功"），漏了第三种。三种是：
> ① `get()` 返 null/undefined → 记录不存在 → 计 `alreadyTerminal`，log `skipped (record missing)`；
> ② `status ∈ {succeeded, failed, canceled}` → 已终态 → 计 `alreadyTerminal`，**并且补做一次 `deleteSnapshot`**。为什么补？注释说：并发的另一路收尸可能已经把状态翻了但它的 deleteSnapshot 失败了；未来的僵尸扫描只看 running 记录，所以永远不会再碰这条 → 幻影进度条永久留着；
> ③ **记录还是 running/queued** → CAS 更新返回了 null 但记录仍活着 → 真实的瞬时失败 → 计 `errors + 1` + warn，下一轮重试。注释说这"可能是 CAS 漂移重试耗尽（Redis store 的 `-3` × 3 次），也可能是任何瞬时 store 故障"（原文 `could be CAS-drift retry exhaustion or any transient store failure`）。
> 不分第三种的后果注释写了：`Mis-classifying that as alreadyTerminal silently drops a real zombie`。」

**Q11：Redis 侧的 key 设计和 TTL 是怎么规划的？**

> 「两套。
>
> **鉴权（`RedisAuthInvocationBackend`）**，全部 bare key（ioredis `keyPrefix: 'cat-cafe:'` 自动加）：
> | key | 类型 | 内容 | TTL |
> |---|---|---|---|
> | `auth:inv:{invocationId}` | Hash | 记录字段 + `expiresAt` | `PEXPIREAT(expiresAt + 60000)` |
> | `auth:inv:{invocationId}:msgs` | Set | `clientMessageIds`（上限 1000，超了 SPOP） | 跟随记录 slide |
> | `auth:latest:{threadId}:{catId}` | String | 最新 invocationId | 跟随记录 slide（**且只在指针仍指向自己时**） |
> | `auth:refresh-cooldown:{invocationId}` | String | `'1'` | `SET ... PX cooldownMs NX` |
>
> 逻辑 TTL 是 2 小时（`DEFAULT_TTL_MS`），但物理 `PEXPIREAT` 一律加 **60 秒 grace**。这个 grace 是为了让 Lua 能区分 `'expired'`（key 还在但 `expiresAt` 已过）和 `'unknown_invocation'`（key 真没了）—— 两种 401 的归因完全不同。
> 三段 Lua：`VERIFY_LUA`（exists → token → expiry(过期就 DEL) → HSET 新 expiresAt → PEXPIREAT → HGETALL）、`VERIFY_LATEST_LUA`（同上 + 中间插 `GET latest ~= invocationId → 'stale_invocation'` + 同时 slide 指针）、`CREATE_LUA`（HSET + PEXPIREAT + SET latest + 再一次 PEXPIREAT）。
> ioredis 的坑注释在 `RedisAuthInvocationBackend.ts` 文件头，标了知识库编号（LL-016，正文在 `docs/public-lessons.md`）：`HSET/HGET/EVAL KEYS[]` 自动加前缀，`keys()/SCAN` **不加**。所以 `RedisInvocationRecordStore` 里 SCAN 要手动拼 `keyPrefix` 再 `stripPrefix`。
>
> **生命周期记录（`RedisInvocationRecordStore`，`invocation-keys.ts`）**：
> | key | 类型 | 备注 |
> |---|---|---|
> | `invoc:{id}` | Hash | `DEFAULT_TTL_SECONDS = 0` → **持久，不过期** |
> | `idemp:{threadId}:{userId}:{key}` | String | `EX 300`（5 分钟） |
> | `invoc:running:{threadId}:{userId}` | Set | running 索引，SADD/SREM **在 `ATOMIC_UPDATE_LUA` 内部**维护 |
>
> **TaskProgress**：`task-progress:{threadId}` 是一个 Hash，field = catId，value = JSON 快照。`createTaskProgressStore` 的 `DEFAULT_TTL_SECONDS = 0` → 默认持久（注释：`persistent — set >0 to enable expiry`）。所以收尸时必须显式 `hdel`，不能靠 TTL。」

**Q12：`SessionMutex` 和 `InvocationTracker` 都是锁，区别在哪？**

> 「维度完全不同：Tracker 锁 `(threadId, catId)` 槽位，SessionMutex 锁 `cliSessionId`。注释明写：`Does NOT modify InvocationTracker — that guards threadId:catId slots, this guards cliSessionId uniqueness`。
> 场景：同一个 CLI session 不能被两个请求同时 `resume`（会话文件会被写坏）。而同一个 cliSessionId 可能被不同 thread/cat 引用（会话继承、handoff），所以 tracker 的槽锁挡不住它。
> 实现是标准的 promise 队列：`held: Map<sessionId, {release}>` + `waiters: Map<sessionId, Waiter[]>`。三个细节：
> ① `release` 是**幂等**的（`let released = false; if (released) return;`）；
> ② 支持 `AbortSignal`：等待期间被 abort 会把自己从队列里 splice 掉再 reject，不会留幽灵 waiter；
> ③ `drainNext` 在队列空时 `waiters.delete(sessionId)`，避免 Map 无限增长。
> 策略上它是 **queue / fail-fast，不抢占**（注释：`Default strategy: queue / fail-fast (no preemption of healthy requests)`）—— 跟 `start()` 的抢占语义正好相反。」

**Q13（进阶）：`SessionContinuationCoordinator` 的 prepare/commit 决策优先级是什么？**

> 「`prepareInvocationContext`：
> 1. `resolveSessionStrategy` → `'reborn'` 就原样返回（跳过 consume）；
> 2. `consumePendingContinuation`（Redis 侧是 Lua 的 HGET+HDEL 原子消费，防并发双消费）；
> 3. 没有 pending → 原样；
> 4. 有 → 拼 `formatContinuationPrompt(capsule)` 到 content 前面，但先查 `content.startsWith(continuationPrompt)` 避免重复注入；
> 5. 返回 `consumedContinuation` 记账 token（含它自己的 threadId/catId/userId）。
>
> `commitInvocationOutcome` 的优先级（注释里列了 4 条）：
> 1. **produced 非空优先于 restore**（无论成功失败），因为失败过程中产生的最新状态不该被旧的覆盖；
> 2. 每个 capsule 存到**它自己携带的** `(threadId, catId)`，不是 commit input 的 —— 多猫场景下这是必须的；
> 3. 跨 thread 门：`capsule.threadId !== input.threadId` 就跳过（防幻觉 capsule 污染）；
> 4. per-cat 判 reborn（按 capsule 自己的 cat，不按整批），reborn 就跳过这一个；
> 5. `consumedSuperseded` 只有在**同 threadId + 同 catId** 被覆盖时才置 true —— 存了别的猫的 capsule 不算覆盖；
> 6. 非成功且没被覆盖且有 consumed → restore，用 **token 自己的 identity**。
>
> 这个类的 deps 类型里刻意**不含** InvocationTracker / processing slot / cancel / force-reset / releaseSlot，文件顶部注释说这是"结构上挡住 invocation-hang 那条轴揉进来 —— 以后谁想加 tracker/cancel，deps 类型就编译不过"。这是用类型系统钉架构边界的一个很好的例子。」

**Q14（进阶）：`MessageDeliveryService` 在并发里起什么作用？**

> 「它解决的是"回调消息什么时候广播给前端"这一个决策。规则：**入了队的消息必须等 QueueProcessor 的 `messages_delivered` 事件，不能立刻广播**（否则用户会看到消息两次，或者看到还没执行的消息像已执行）；但入队失败/零目标要 fail-open 立刻广播（否则消息永久隐身）。
> `resolveCallbackDeliveryDecision` 返回 `{shouldBroadcastNow, enqueued, enqueueAttempted, enqueueFailed}`，`shouldBroadcastNow = !messageStaysQueued`。三条 fail-open 路径都会调 `recoverQueuedMessage`（= `markDelivered(Date.now())`）：`!canEnqueueA2A`、`enqueued=0 且 coalesced=0`、`enqueueA2A` 抛错。
> 注意 `anyHandled` 的判定包含 `coalesced` —— F216 AC-D6：合并进已有条目也算"被处理了"，不能因为 `enqueued.length === 0` 就恢复广播。」
