# Clowder AI 深度拆解 · 面试向

> 这版笔记的目标只有一个：**让你能在面试里把这个项目讲透。**
>
> 不是讲"它有什么功能"，而是讲**每个模块为什么长这样、当初否掉了哪些方案、
> 为什么否、如果重来你会怎么改** —— 这才是面试官真正在听的东西。

---

## 先说一件重要的事：简历怎么写

这是个**别人的开源项目**（[zts212653/clowder-ai](https://github.com/zts212653/clowder-ai)）。
写简历时把它说成"我做的项目"是站不住的 —— 面试官一句"这个 commit 是你提的吗"就穿了，
而且这类翻车会直接毁掉整场面试的可信度。

三种站得住的写法，从轻到重：

| 写法 | 简历怎么描述 | 面试能撑多久 | 需要你额外做什么 |
|------|------------|------------|----------------|
| **A. 源码研究** | "深度研究开源多 Agent 编排框架 Clowder AI，产出 20 章架构拆解笔记，覆盖路由/会话/记忆/治理四大子系统" | 能撑住架构类追问，撑不住"你写的哪部分" | 就是这份笔记本身 |
| **B. 二次开发/贡献** | "为 Clowder AI 贡献 X 功能 / 修复 Y 类问题，PR #NNN 已合入" | 能撑住实现细节追问 | 真的提 PR，哪怕是小的 |
| **C. 借鉴架构自建** | "自研多模型 Agent 协作平台，参考 Clowder AI 的编排/抗压缩设计，实现了 A/B/C" | 最强，全都能讲 | 自己写一个精简版 |

**我的建议是 A + C 组合**：用这份笔记建立架构判断力，然后花两三周
写一个精简版（一个路由器 + 一套身份注入 + 一套会话封存就够了），
简历上写 C，面试里用 A 的深度回答"你为什么这么设计"。

> **精简版怎么做** → [31 章](31-动手-自己实现精简版.md)（七个里程碑 + 每个里程碑对应的简历写法）  
> **哪些话不能说** → [36 章](36-诚实定位与真实参与.md)（翻车话术清单，**建议开工前先读这章**）

这个组合的杀伤力在于：
面试官问"为什么用 CLI 子进程而不是直接调 API"，
你能答出"官方 SDK 只能用 API key 计费，用不了订阅额度，
这是 Clowder 从 SDK 方案翻案到子进程方案的原因，我也沿用了这个判断"——
**有出处、有取舍、有数据，这就是资深候选人的答法。**

如果你已经在用它干活了（用它跑过自己的项目、改过配置、踩过坑），
那 B 的门槛其实很低，提一个 PR 就能升级写法。

## 这个项目一句话是什么

> **Clowder AI 是一个"Agent 团队协作层"：
> 它不替代 Claude Code / Codex / Gemini 这些 Agent CLI，
> 而是架在它们之上，让不同厂商的模型能在同一个对话里互相叫醒、
> 互相审代码、共享同一份记忆、守同一套流程。**

面试时的展开顺序（三层，别一次全倒）：

```
第一层（一句话）  多模型 Agent 的团队协作层，不是 Agent 框架
第二层（三件事）  ① 编排：谁接活、串行还是并行、怎么防死循环
                 ② 记忆：跨 session 记得自己是谁、记得团队共识
                 ③ 纪律：跨模型互审、SOP 门禁、可机器判定的规则
第三层（一个点）  挑一个你最熟的模块深挖，比如抗上下文压缩
```

## 每个模块文件的固定结构

为了方便你背，所有模块文件都是同一个八段式：

```
0. 30 秒电梯版        ← 面试被问到这个模块，先说这段
1. 它解决什么问题      ← 场景化，不谈代码
2. 不做会怎样          ← 具体的故障画面
3. 怎么设计的          ← 大白话 + 图 + 关键代码
4. 为什么这么设计      ← 逐个决策点讲取舍
5. 否掉了哪些方案      ← 每条标注证据等级
6. 如果重新设计        ← 我的方案（面试高分区）
7. 和其他模块怎么咬合  ← 上游/下游/共享状态
8. 面试怎么讲          ← 30 秒 / 3 分钟 / 追问应对
```

## 证据等级标记

这份笔记里的判断分三档，我会明确标出来。**这一点对面试很关键** ——
你不能把我的推断当成项目的事实去讲，被追问出处会很尴尬。

| 标记 | 含义 | 面试里能怎么说 |
|------|------|-------------|
| **【ADR】** | 项目的架构决策记录里写明的 | "他们的 ADR-001 里明确记录了…" —— 可以当事实讲 |
| **【源码】** | 代码注释/实现里直接体现的 | "代码注释里写了原因是…" —— 可以当事实讲 |
| **【推断】** | 我根据代码形态反推的 | "我的理解是…" —— 必须说成自己的分析 |

比如：

> **否掉的方案 A：用官方 Agent SDK**
> 【ADR】ADR-001 初稿选的就是 SDK，2026-02-06 翻案。
> 原因：SDK 只能用 API key 计费，无法复用 Max/Plus/Pro 订阅额度，长期成本不可接受。

这条你可以直接当事实讲。而：

> **如果重新设计**：我会把 provider 适配层做成插件包…
> 【推断】

这条只能说"我会考虑…"。

## 三条学习路径

**路径一：只有一周，要能应付面试**

```
36 诚实定位（先读，知道边界在哪）
  → 00 面试总纲 → 01 架构全景 → 02 CLI 选型决策
    → 挑两个模块深读（推荐 08 抗压缩 + 11 跨模型互审）
      → 18 面试问答手册（背 20 道核心题）
        → 33 模拟面试实录（自测）
```

这条路径的赌注是：面试官不会把 15 个模块都问遍，
但一定会问"整体架构"和"你觉得最有意思的设计是什么"。
把架构 + 两个深挖点讲好，比 15 个都讲皮毛强得多。

**36 章放在最前面是故意的** —— 先知道哪些话会翻车，再去背内容。

**路径二：一个月，要能写进简历**

```
第 1 周：00-18 全部读完 + 17 章形成自己的观点
第 2 周：31 章开工，做到里程碑 3（能演示 @ 路由）
         遇到设计问题就查对应的深潜章（19-30）
第 3 周：做到里程碑 4-5，同时读 34 章优化 AI 协作方式
第 4 周：33 模拟面试 + 补上实现时踩到但笔记没提的坑
```

**边做边查深潜章**，比先读完再做效率高得多——
因为你卡在哪里，才知道该读哪一章。

**路径三：想真正学会多 Agent 系统设计**

模块层按依赖顺序：`02 → 06 → 05 → 03 → 04 → 10 → 07 → 08 → 09 → 13 → 12 → 11 → 14 → 15 → 16`

这个顺序是"从底往上"：先搞清怎么调起一个 Agent，
再往上盖编排、记忆、纪律。

**每读完一个模块章，接着读它对应的深潜章**：

| 模块章 | 对应深潜章 |
|---|---|
| 03 路由与编排 | 20（串行）+ 21（并行入口） |
| 05 调用生命周期 | 19（单次调用）+ 22（队列） |
| 06 Provider 适配 | 26（Provider 层） |
| 07 身份注入 | 25（prompt 组装） |
| 08 会话与抗压缩 | 23（会话链） |
| 09 记忆与检索 | 24（检索管线） |
| 13 MCP 回调桥 | 27（MCP 服务端） |

**路径四：想给这个项目提 PR**

```
00 → 01 → 02（建立全局观）
  → 35 二次开发手册（找到能下手的地方）
    → 对应模块章 + 深潜章（把那一块读透）

```

这条路径最短，因为你只需要读透**一个**模块。
提一个小 PR 就能把简历从写法 A 升级到写法 B。

## 一句提醒

这份笔记里有大量"某个 bug 修了三轮""某条规则是踩坑换来的"这类细节。
**面试里这些细节是你的护城河** —— 因为它们不可能从 README 里看出来，
只有真读过源码的人才知道。

比如你能说出：

> "他们的 A2A 深度限制是 15，单条消息扇出上限是 2。
> 这两个数字乘起来就是最坏情况的调用规模，本质上是钱包护栏。
> 而且深度限制是每次现读 env 的，注释里写了 `read at call time for hot-reload`——
> 因为链跑飞的时候要能不重启就收紧。"

这段话面试官一听就知道你不是看 README 混过来的。

**但有一条铁律**：这些细节要说成"我读源码发现的"，
不能说成"我当时是这么设计的"。差别就是过和不过。
细节全在 [36 章](36-诚实定位与真实参与.md)。
