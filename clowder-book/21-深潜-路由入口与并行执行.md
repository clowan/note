## 0. 先纠正一个命名（很重要，别在面试里说错）

任务书和 `AgentRouter.ts` 的文件头注释都提到 `execute()` / `executeWithContext()`：

```ts
/**
 * IMPORTANT: threadId 约束
 * 所有调用入口（execute, executeWithContext）必须传入正确的 threadId。
 * ...
 */
```

**这两个方法在当前代码里不存在。**【源码】实际的两个入口是：

| 注释里写的 | 实际方法 | 状态 |
|---|---|---|
| `execute` | `async *route(...)` | `@deprecated`，注释写明"Will be removed after S4 migration is complete" |
| `executeWithContext` | `async *routeExecution(...)` | 生产主路径（ADR-008 S1 解耦后的入口） |

我用 grep 全仓确认过：`executeWithContext` 只在这段注释里出现过一次，没有任何定义或调用点。

> **注意（别在面试里说过头）**：`route()` 不是"零生产调用方"。`packages/api/src/routes/messages.ts:1672` 还有一条 legacy 分支在调它，进入条件是 `else { // Fallback: no invocationRecordStore (legacy path, uses route()) }`——也就是没装 `invocationRecordStore` 时的兼容路径（代码里还留着 `TODO(F122 Phase B): Legacy path should be removed`）。正常生产装配下走的是 `routeExecution`。【源码】

> **面试官追问："你怎么发现这个注释是过时的？"**

### 1.3 边界在哪（三条硬边界）

1. **AgentRouter 不做"猫怎么跑"**。它只回答"派给谁 + 用哪种编排"。真正拉起子进程/流是 `invokeSingleCat`，AgentRouter 通过 `getStrategyDeps()` 把 30+ 个 store 打包成 `RouteStrategyDeps` 交给策略函数。
2. **用户 @ 与猫 @ 是两套解析器，不共用代码**。用户消息走 `AgentRouter.parseMentionsRaw`（行内任意位置都算），猫回复走 `a2a-mentions.ts` 的 `analyzeA2AMentions`（**只认行首**，且上限 `MAX_A2A_MENTION_TARGETS = 2`）。两边各自实现了 `TOKEN_BOUNDARY_RE` / `HANDLE_CONTINUATION_RE`——正则内容一样，但是两份独立常量。
3. **route-parallel 不写用户消息、不推进 InvocationRecord 状态**。它只负责"猫的产出落库 + 游标边界收集"，成功/失败的最终判定在 `messages.ts` 里。

> **面试官追问："为什么用户 @ 和猫 @ 不共用解析器？"**
> "因为语义不同。用户在句子中间写 `帮我问下 @codex`，是明确的路由意图；猫在回复里写 `刚才 @codex 提过` 只是引用，不该触发调用。所以猫这边收紧成'行首即路由'（`a2a-mentions.ts` 头部注释 F046 写明这条简化规则），行内的 @ 只走 `detectInlineActionMentions` 做写侧提示，不参与路由。共用一套解析器就没法在同一处同时满足这两种松紧度。"

## 2. 核心数据结构

### 2.1 `AgentRouterOptions`：38 个字段，只有 3 个必填

我数过：`AgentRouterOptions` 有 **38** 个字段，其中无 `?` 的必填只有 3 个；类上有 **39** 个 `private` 字段。【源码】

必填三件套：

```ts
export interface AgentRouterOptions {
  agentRegistry: AgentRegistry;   // 猫id → AgentService 实现
  registry: InvocationRegistry;   // 调用追踪
  messageStore: IMessageStore;    // 消息读写
  // ...其余 35 个全部可选
}
```

**关键不对称**：`agentRegistry` 传进来但**不作为字段保存**，构造函数里立刻被 `rebuildRuntimeCaches()` 摊平成 `this.services: Record<string, AgentService>`：

```ts
private rebuildRuntimeCaches(agentRegistry: AgentRegistry): void {
  this.services = {};
  for (const [catId, service] of agentRegistry.getAllEntries()) {
    this.services[catId] = service;
  }
  const allConfigs = catRegistry.getAllConfigs();
  const { speechMentionRe } = buildMentionData(allConfigs);
  this.speechMentionRe = speechMentionRe;
}
```

对外暴露 `refreshFromRegistry(agentRegistry)` 供运行时热更新（有测试 `refreshFromRegistry updates routable service set after runtime catalog changes`）。

### 2.2 39 个 private 字段的分组

| 组 | 字段 | 可选性 | 用途 |
|---|---|---|---|

**为什么这么多可选？** `getStrategyDeps()` 里全部用条件展开：

```ts
...(this.taskProgressStore ? { taskProgressStore: this.taskProgressStore } : {}),
```

这是 TypeScript `exactOptionalPropertyTypes` 下的标准写法——不能写 `taskProgressStore: undefined`，只能整个键不出现。所以 35 个可选依赖 = 35 行条件展开（`getStrategyDeps()` 里分布在 `invocationDeps` 和顶层两层）。

> **面试官追问："30 多个可选依赖不是典型的上帝类吗？你会怎么改？"**
> "会。现在 `getStrategyDeps()` 就是一个纯粹的搬运函数——把 39 个字段重新装配成 `RouteStrategyDeps` 里的 `invocationDeps` + 顶层两层结构，没有任何逻辑。我会把它反过来：让调用方直接构造 `RouteStrategyDeps` 注入 AgentRouter，AgentRouter 只保留自己真正用到的 4 个（`services`/`messageStore`/`threadStore`/`deliveryCursorStore`）。现在这 39 个里，AgentRouter 自己在方法体里真正读的只有 `messageStore`、`threadStore`、`services`、`deliveryCursorStore`、`frustrationIssueStore`、`socketManager`、`speechMentionRe` 这几个，其余全是穿透。不过我也理解现状：这是渐进式加功能的自然结果，每加一个 feature 就多一个可选依赖，没人愿意在加 feature 的 PR 里顺手做大重构。"

### 2.3 mention 解析用的三个结构

```ts
/** Parsed mention with position for ordering */
```

`position` 存在的唯一理由：`parseAllMentions` 要做"位置感知的并集"——`@gemini @thread` 和 `@thread @gemini` 派发顺序必须不同。没有 position 就只能按 Map 迭代序，那是不确定的。

### 2.4 `ThreadRoutingPolicyV1`（F042）

```ts
export type ThreadRoutingScope = 'review' | 'architecture';

export interface ThreadRoutingRule {
  preferCats?: CatId[];   // 优先排前面（可以注入原本不在候选集里的猫）
  avoidCats?: CatId[];    // 除非显式 @ 否则不路由
  reason?: string;        // 人类可读原因，如 "budget"
  expiresAt?: number;     // epoch ms；过期后整条规则被忽略
}

export interface ThreadRoutingPolicyV1 {
  v: 1;
  scopes?: Partial<Record<ThreadRoutingScope, ThreadRoutingRule>>;
}
```

类型定义处的注释把它和全局 roster 的区别写得很清楚：

```
 * NOTE: This is NOT global availability.
 * - Global roster `available=false` = technically unavailable/offline.
 * - Thread routingPolicy = temporary preferences (budget, focus, etc.).
```

**字段逐个解释"为什么存在"**：
- `v: 1` —— 版本号写死在类型里（不是 `number`），`applyThreadRoutingPolicy` 里 `policy.v !== 1` 直接放行，这样将来出 v2 时老代码会安全降级而不是误读。
- `scopes` 可选 —— 允许存一个空 policy 占位。
- `preferCats` 与 `avoidCats` 同时出现时，`prefer` 会先被 `avoid` 过滤：`prefer = preferList.map(String).filter(id => !avoid.has(id))`。**avoid 赢**。
- `expiresAt` —— 因为典型用法是"这个月 opus 额度用完了，review 别派给它"，是临时的；没有过期机制就会变成永久污染。判定条件是 `typeof rule.expiresAt === 'number' && rule.expiresAt > 0 && rule.expiresAt < Date.now()`，所以 `expiresAt: 0` 表示永不过期。

### 2.5 `ThreadParticipantActivity`

```ts
export interface ThreadParticipantActivity {
  catId: CatId;
  lastMessageAt: number;      // 这只猫在本 thread 最后一条消息的时间戳
  messageCount: number;       // 累计条数
  lastResponseHealthy?: boolean;  // #267: false = 上一次回复是 error
```

`lastResponseHealthy` 是可选三态，判定一律写成 `p.lastResponseHealthy !== false`——**`undefined` 视为健康**。这很关键：老数据没有这个字段，如果写成 `=== true` 会把所有历史参与者判成不健康，整个 fallback 梯级塌到默认猫。

## 3. 主流程逐段拆解

### 3.1 `resolveTargetsAndIntent()`：对外的目标解析总入口

```ts
async resolveTargetsAndIntent(
  message: string,
  threadId?: string,
  options?: { persist?: boolean },
): Promise<{ targetCats: CatId[]; intent: IntentResult; hasMentions: boolean; routing_warnings: CatRoutingError[] }> {
  const resolvedThreadId = threadId ?? DEFAULT_THREAD_ID;   // 'default'
  const allMentions = await this.parseAllMentions(message, resolvedThreadId);
  const hasMentions = allMentions.mentions.length > 0;
  const routing_warnings = allMentions.routing_warnings;
  const targetCats = options?.persist
    ? await this.resolveTargets(message, resolvedThreadId)
    : await this.peekTargets(message, resolvedThreadId);
  const intent = parseIntent(message, targetCats.length);
  return { targetCats, intent, hasMentions, routing_warnings };
}
```

**坑 1（性能）**：`parseAllMentions` 在这里调了一次拿 warnings，`resolveTargets`/`peekTargets` 内部**又调了一次**。也就是每次发消息，全量 mention 解析跑两遍（含一次 `threadStore.getParticipants` 的 IO）。【源码】做这个判断的依据是：`resolveTargets` 第一行就是 `const { mentions: mentionedCats } = await this.parseAllMentions(message, threadId);`。

**坑 2（语义）**：`persist: true` 与 `false` 的唯一区别是 `resolveTargets` 会在有显式 @ 时执行 `await this.threadStore.addParticipants(threadId, mentionedCats)`。两个函数从第二段开始的代码**逐字重复**（约 55 行），包括 `#ideate` 分支、concierge 分支、Z5 fallback、三级参与者 fallback。这是明摆着的复制粘贴。

> **面试官追问："为什么不合并 peekTargets 和 resolveTargets？"**
> "从代码看没有任何阻碍——两者差别只有一个 `addParticipants` 调用。合并写法就是 `resolveTargets(message, threadId, { persist })`，有 @ 时 `if (persist) await addParticipants(...)`。我猜没合并是因为它们分别在不同时期被加过分支（F229 concierge 那块两边的注释都写着 'see matching comment in peekTargets'，说明作者自己知道是双份），每次改都记得同步两边就先没动。这正是我在'如果重新设计'那篇里会先动的地方——现在 `if (this.threadStore)` 块里有 7 个 return 分支要双写（#ideate / concierge / Z5 / healthyReplier / fallbackParticipant / preferredCats[0] / default），漏一个就是线上路由不一致。"

### 3.2 `route()` vs `routeExecution()`：完整签名对照

```ts
// 老入口，@deprecated
async *route(
  userId: string,
  message: string,
  threadId?: string,
  contentBlocks?: readonly MessageContent[],
  uploadDir?: string,
  signal?: AbortSignal,

// 生产入口（ADR-008 S1）
async *routeExecution(
  userId: string,
  message: string,
  threadId: string,          // 必填
  userMessageId: string,     // 已存好的用户消息 ID
  targetCats: CatId[],       // 外部预解析
  intent: IntentResult,      // 外部预解析
  options?: { /* 18 个字段，见下 */ },
): AsyncIterable<AgentMessage>
```

`routeExecution` 的 `options` 全字段：`contentBlocks`、`uploadDir`、`signal`、`signalForCat`、`queueHasQueuedMessages`、`hasQueuedOrActiveAgentForCat`、`deferA2AEnqueue`、`invocationController`、`trackA2ASlot`、`completeA2ASlots`、`cursorBoundaries`、`persistenceContext`、`parentInvocationId`、`callerTraceContext`、`a2aTriggerMessageId`、`frustrationAutoIssueEligible`、`verdictPassWarningEnabled`、`freshnessReinvokeEnqueue`。

| 维度 | `route()` | `routeExecution()` |
|---|---|---|
| 目标解析 | 内部 `await this.resolveTargets(...)`（**带副作用**：写 participants） | 外部传入 |
| intent | 内部 `parseIntent(message, targetCats.length)` | 外部传入 |
| 用户消息 | 内部 `messageStore.append({userId, catId:null, content: message /* 原文含 tag */, mentions: targetCats, ...})` | 不写，只收 `userMessageId` |
| threadId | `threadId ?? DEFAULT_THREAD_ID` | 必填 |
| 局部变量名 | `legacyThinkingMode` | `thinkingMode` |
| 逐猫取消 | 无（只有共享 `signal`） | `signalForCat` |
| 游标 | 无 `cursorBoundaries` → 策略层走 legacy 立即 ack | 传 Map → 延迟 ack |
| 落库失败回传 | 无 `persistenceContext` | 有 |
| 跨路由 trace | 无 | `callerTraceContext` → `trace.setSpanContext(..., { isRemote: true })` 作为 span 的 parent context |
| span 属性 | 3 个 routing 属性 | 3 个 + `invocationId`（当 `parentInvocationId` 存在） |
| `finally` | 只 `routeSpan.end()` | 先把 `{ tracing: { traceId, spanId } }` 写回用户消息（`messageStore.updateExtra`），再 `end()` |
| 挫败检测门控 | 只看 `this.frustrationIssueStore` 是否存在 | 额外 `options?.frustrationAutoIssueEligible !== false` |

两者共享的核心两行完全一致：

```ts
const cleanMessage = stripIntentTags(message);
```

## 4. 关键算法与判定逻辑

### 4.1 显式 @ 的解析：`parseMentionsRaw()` 七步

```
输入 message
 ├─ 1. lowerMessage        = message.toLowerCase()
 ├─ 2. speechRouteMessage  = normalizeSpeechMentions(message).toLowerCase()
 ├─ 3. allPatterns         = 所有 config.mentionPatterns（小写）按长度降序
 ├─ 4. recordRouteLineMentions(lowerMessage, ...)      ← 行首路由语法
 ├─ 5. forEachUserMentionCandidate(lowerMessage, ...)  ← 全文任意位置
 │       ├─ 命中 pattern → recordResolvedMention
 │       ├─ 否则 hasDomainSuffixedMentionPatternAt → 静默 return
 │       └─ 否则 recordUnknownMentionWarning
 ├─ 6. if (speechRouteMessage !== lowerMessage)
 │       recordRouteLineMentions(speechRouteMessage, ...)  ← 语音别名只走行首语法
 └─ 7. mentions.sort((a, b) => a.position - b.position)
```

第 3 步的排序是**最长匹配优先**的全部实现：

```ts

```

配合 `findMentionPatternAt` 的"顺序遍历，第一个成功即返回"，就保证了 `@opus-45` 命中 `opus-45` 而不是 `opus`（测试：`line-start @opus-45 routes to opus-45 only, not both opus and opus-45`）。

第 6 步的注释解释了为什么语音别名要收紧：

```
// prose such as "look at codex docs" would become an implicit route.
```

**语音归一化正则怎么建的**（`buildMentionData`）：

### 4.2 `getRouteLineStart(line)`：一行是不是"路由行"

返回 `@` 在**行内**的下标，或 `null`。步骤：

```
1. cursor = 匹配 LINE_START_MENTION_PREFIX_RE 的长度
      /^[ \t]*(?:(?:>\s*)|(?:[-*+][ \t]+)|(?:\d+[.)][ \t]+))*/
      ↑ 缩进 + 引用 '>' + 无序列表 '- * +' + 有序列表 '1.' '1)'，可重复嵌套
2. 无限循环：
      跳空格/tab
      匹配 ROUTE_CONTROL_TAG_RE = /^#(?:ideate|execute|critique)\b/i
      命中 → cursor += tag.length，继续循环；否则 break
3. 跳空格/tab
4. 跳零宽字符          (isZeroWidthChar)
5. 跳任意个 '*' 或 '_'  (markdown 加粗/斜体)
6. 再跳零宽字符
7. return line[cursor] === '@' ? cursor : null
```

`ROUTE_CONTROL_TAG_RE` 是从 `IntentParser` 的常量动态拼出来的：

```ts
const ROUTE_CONTROL_TAG_RE = new RegExp(
  `^#(?:${ROUTE_CONTROL_TAGS.map((tag) => escapeRegExp(tag)).join('|')})\\b`, 'i',
);
```

而 `ROUTE_CONTROL_TAGS = [...INTENT_TAGS, ...PROMPT_TAGS] = ['ideate','execute','critique']`。所以新增一个 prompt tag，路由行语法自动跟着支持（有测试 `all IntentParser route-control tags allow line-start mention routing`）。

`isZeroWidthChar(code)` 的完整清单（#969）：

| 码点 | 名称 |
|---|---|
| `0x200b` | Zero Width Space |
| `0x200c` | Zero Width Non-Joiner |
| `0x200d` | Zero Width Joiner |
| `0xfeff` | Zero Width No-Break Space (BOM) |
| `0x00ad` | Soft Hyphen |
| `0x2060` | Word Joiner |

注释写明动机："Zero-width Unicode characters that LLMs may insert before mentions. These are invisible in consoles but break line-start `@` detection."

### 4.3 `forEachRouteLineMentionCandidate()`：逐行扫描

```ts
function forEachRouteLineMentionCandidate(message, visit) {
  let offset = 0;
  while (offset <= message.length) {
    const lineEnd = findLineEnd(message, offset);          // 扫到 \r 或 \n
    const line = message.slice(offset, lineEnd);
    forEachRouteCandidateInLine(line, offset, visit);
    const nextOffset = getNextLineOffset(message, lineEnd); // \r\n → +2，否则 +1
    if (nextOffset === null) break;
    offset = nextOffset;
  }
}
```

`getNextLineOffset` 显式处理 CRLF：`message[lineEnd] === '\r' && message[lineEnd + 1] === '\n' ? lineEnd + 2 : lineEnd + 1`。这不是可有可无的——有测试 `CRLF blockquote @mentions are inert user text`。

行内扫描：

```ts
function forEachRouteCandidateInLine(line, offset, visit) {
  const routeStart = getRouteLineStart(line);
  if (routeStart === null) return;          // 这一行不是路由行 → 整行放弃

  let candidate = routeStart;
  while (candidate >= 0) {
    if (candidate === routeStart || MENTION_TOKEN_BOUNDARY_RE.test(line[candidate - 1] ?? '')) {
      visit(line, offset, candidate);
    }
    candidate = line.indexOf('@', candidate + 1);
  }
}
```

**关键语义**：一旦这一行的开头是 `@`（即它是路由行），这一行里**所有**左边界合法的 `@` 都是候选。所以 `@opus @codex 帮忙看下` 一行能同时路由两只猫。但 `帮忙 @opus @codex` 这行 `getRouteLineStart` 返回 `null`，行首语法整行不参与——不过第 5 步的 `forEachUserMentionCandidate` 会兜住它（用户消息允许行内 @）。

### 4.4 span 剔除的完整规则

`buildMentionExclusionSpans(message)` 按顺序 push 五类区间：

| # | 规则 | 实现 |
|---|---|---|
| 1 | 围栏代码块 | `pushRegexSpans(message, /```[\s\S]*?```/g, spans)` |
| 2 | 行内代码 | `pushRegexSpans(message, /`[^`\n]+`/g, spans)` —— 注意 `[^`\n]+` 不跨行 |
| 3 | 引用行 | `pushRegexSpans(message, /^[ \t]*>[^\n]*/gm, spans)` —— `m` flag，**整行**剔除 |
| 4 | 成对引号 | `pushQuoteSpans`：`" "`、`“ ”`、`‘ ’`、`「 」`、`『 』` 五对 |
| 5 | 直角单引号 | `pushStraightSingleQuoteSpans`：`'` 的特殊处理 |

`pushQuoteSpans` 的循环：每一对独立从 `offset = 0` 扫，`indexOf(open, offset)` → `indexOf(close, start + open.length)`，找不到闭合就 `break`（该对结束，不做任何回退）。注意 `["','"]` 这对是 `['"', '"']`，开闭同字符，所以是"两两配对"。

`pushStraightSingleQuoteSpans` 单独存在是因为 `'` 会出现在 `don't` 这种词里：

```ts
function isStraightSingleQuoteOpener(message, pos) {
  const previous = message[pos - 1];
  if (previous === undefined) return true;
  return !ASCII_WORD_RE.test(previous);      // ASCII_WORD_RE = /[a-z0-9]/i
}
function isStraightSingleQuoteCloser(message, pos) {
  const next = message[pos + 1];
  if (next === undefined) return true;
  return !ASCII_WORD_RE.test(next);
}
```

开引号要求"前面不是字母数字"，闭引号要求"后面不是字母数字"。`don't` 里的 `'` 前是 `n`（字母）→ 不是 opener → 直接 `offset = start + 1` 跳过。有测试 `word apostrophes do not make real inline @mentions inert`。

判定函数是 `isInsideSpan(pos, spans)`：`spans.some(([start, end]) => pos >= start && pos < end)`——**左闭右开**，且是 `some()` 线性扫描（span 数量少，没做区间树）。

> **面试官追问："`>` 引用行既在 `LINE_START_MENTION_PREFIX_RE` 里被跳过、又在 span 里被整行剔除，不矛盾吗？"**
> "【推断】我认为 `LINE_START_MENTION_PREFIX_RE` 里的 `(?:>\s*)` 分支在当前代码路径下是死代码。理由：`recordRouteLineMentions` 和 `parseGroupMentions.findMatchPosition` 两条路径都先算 `buildMentionExclusionSpans`，而规则 3 会把 `^[ \t]*>[^\n]*` 整行加进剔除区间；候选位置一定落在这个区间内，`isInsideSpan` 直接返回 true。测试 `CRLF blockquote @mentions are inert user text, not routing targets` 也确认引用块里的 @ 不路由。所以那个分支是防御冗余——如果哪天有人改了 span 规则把引用行放出来，前缀正则还能兜住格式；但现在它不产生行为。这是我自己反推的，源码里没写。"

### 4.5 左右边界判定三件套

```ts
// 左边界（只用于 forEachUserMentionCandidate 的行内扫描）

  if (pos === 0) return true;
  const prev = message[pos - 1];
  if (!prev) return true;
  return !HANDLE_CONTINUATION_RE.test(prev) && !QUOTE_BEFORE_MENTION_RE.test(prev);

```
- `HANDLE_CONTINUATION_RE = /[a-z0-9_.-]/` → 挡住 `foo@opus`、邮箱 `a.b@opus`
- `QUOTE_BEFORE_MENTION_RE = /["'“”‘’]/` → 挡住紧跟引号的（与 span 剔除双保险）

```ts
// 右边界
function isMentionEndBoundary(message, end) {
  const next = message[end];
  if (!next) return true;
  if (next === '.') {
    const suffixStart = message[end + 1];
    if (suffixStart !== undefined && DOMAIN_SUFFIX_START_RE.test(suffixStart)) return false;
  }
  if (MENTION_TOKEN_BOUNDARY_RE.test(next)) return true;
  return !HANDLE_CONTINUATION_RE.test(next);

```
- `DOMAIN_SUFFIX_START_RE = /[\p{L}\p{N}]/u`（带 `u` flag 的 Unicode 属性）→ `@opus.com` 的 `.c` 命中 → 判定为域名，**不是** mention
- `@opus.` 句末的点后面没字符 → `suffixStart === undefined` → 继续走 boundary 检查 → 是 mention

`MENTION_TOKEN_BOUNDARY_RE` 完整字符集：

```
/[\s,.:;!?()[\]{}<>，。！？、：；（）【】《》「」『』〈〉]/
```

即：空白 + 英文标点 8 种 + 三种括号 + 尖括号 + 中文标点 6 种 + 中文括号 6 对。有测试 `CJK fullwidth brackets after a line-start mention count as token boundary (R3 P1 regression)`。

```ts
// URL 形状排除
function isUrlishMentionToken(message, pos) {
  const tokenStart = Math.max(
    message.lastIndexOf(' ', pos), message.lastIndexOf('\n', pos), message.lastIndexOf('\t', pos)
  ) + 1;
  const nextSpace = message.slice(pos).search(/\s/);
  const tokenEnd = nextSpace < 0 ? message.length : pos + nextSpace;
  const token = message.slice(tokenStart, tokenEnd);
  if (token.includes('://')) return true;
  if (token.toLowerCase().startsWith('www.')) return true;

```

`BARE_URL_PREFIX_BEFORE_MENTION_RE = /(?:^|[^a-z0-9_-])(?:[a-z0-9-]+\.)+[a-z0-9-]+(?:\/[^\s@]*)*\/$/i` —— 匹配"以 `域名/路径/` 结尾"的前缀，挡的是 `example.com/docs/@opus` 这种裸 URL 路径段。有测试 `bare URL path @tokens are inert user text`。

### 4.6 零宽容忍匹配：`matchMentionPatternEnd`

```ts
function matchMentionPatternEnd(message, pos, pattern) {
  let cursor = pos;
  for (let i = 0; i < pattern.length; i++) {
    while (cursor < message.length && isZeroWidthChar(message.charCodeAt(cursor))) cursor++;
    if (message[cursor] !== pattern[i]) return null;
    cursor++;
  }
  while (cursor < message.length && isZeroWidthChar(message.charCodeAt(cursor))) cursor++;
  return cursor;
}
```

**逐字符匹配，每个字符前都先跳零宽**。所以 `@o​pus` 也能命中 `@opus`。返回值是"pattern 结束后（且跳过尾部零宽）的下标"，交给 `isMentionEndBoundary` 判右边界。有测试 `zero-width characters inside line-start mention tokens still route (cloud P2 regression)`。

### 4.7 Markdown 包裹的配对消耗

```ts
function getOpeningRouteMarkdownMarkers(message, pos): MarkdownMentionMarkerRun | null {
  let cursor = pos - 1;
  while (cursor >= 0 && isZeroWidthChar(message.charCodeAt(cursor))) cursor--;
  const marker = message[cursor];
  if (marker !== '*' && marker !== '_') return null;
  let count = 0;
  while (cursor >= 0 && message[cursor] === marker) { count++; cursor--; }
  return { marker, count };
}

function skipClosingRouteMarkdownMarkers(message, end, openingMarkers): number {
  if (!openingMarkers) return end;
  let cursor = end;
  let remaining = openingMarkers.count;
  while (remaining > 0) {
    while (cursor < message.length && isZeroWidthChar(message.charCodeAt(cursor))) cursor++;
    if (message[cursor] !== openingMarkers.marker) return end;   // 配不上 → 退回原 end
    cursor++; remaining--;
  }
  while (cursor < message.length && isZeroWidthChar(message.charCodeAt(cursor))) cursor++;
  return cursor;
}
```

`recordRouteLineMentions` 把它作为 `normalizePatternEnd` 传进 `findMentionPatternAt`：

```ts
const openingMarkers = getOpeningRouteMarkdownMarkers(message, position);
const matched = findMentionPatternAt(message, position, patterns, (end) =>
  skipClosingRouteMarkdownMarkers(message, end, openingMarkers),

```

含义：`**@opus**` 的右边界应该在第二个 `**` 之后判，而不是在 `@opus` 后面看到 `*` 就判。**必须严格配对**（开了 2 个星就必须闭 2 个星），配不上就退回原 `end`。测试名：`markdown-wrapped line-start mentions ignore matching closing markers (cloud P2 regression)`。

### 4.8 `recordResolvedMention`：最早位置获胜

```ts
function recordResolvedMention(catId, position, seenCats, mentions, routingWarnings) {
  const key = catId as string;
  const resolved = resolveCatTarget(key);
  if ('error' in resolved) {
    if (!seenCats.has(key)) { seenCats.add(key); routingWarnings.push(resolved.error); }
    return;
  }
  if (!seenCats.has(key)) {
    seenCats.add(key); mentions.push({ catId, position }); return;
  }
  const existing = mentions.find((m) => String(m.catId) === key);
  if (existing && position < existing.position) existing.position = position;   // ← 最早位置获胜
}
```

第三个分支是 cloud P1 回归修复：同一只猫既有短别名又有长别名时（比如同时写了 `@opus` 和 `@布偶猫`），先被扫到的可能是后出现的那个，必须把 position 拉回最早。测试：`earliest position wins when same cat has short+long alias (cloud P1 regression)`。

`seenCats` 是**共享去重集**，同时容纳三种 key：
- 成功解析的 catId（如 `'opus'`）
- 解析失败的 catId
- 未知 handle 的 `@unknown:${handle}`（`recordUnknownMentionWarning` 里造的，命名空间隔离）

### 4.9 未知 handle 告警

```ts
function recordUnknownMentionWarning(message, position, seenCats, routingWarnings) {
  const handle = message.slice(position + 1).match(/^([a-z0-9_.-]+)/)?.[1];
  if (!handle) return;
  if (DOMAIN_LIKE_UNKNOWN_HANDLE_RE.test(handle)) return;    // /^[a-z0-9_-]+(?:\.[a-z0-9-]+)+$/i
  const key = `@unknown:${handle}`;
  const resolved = resolveCatTarget(handle);
  if ('error' in resolved && !seenCats.has(key)) { seenCats.add(key); routingWarnings.push(resolved.error); }
}
```

存在理由写在调用点注释里（codex review 6949db49）："an explicit @handle that matched NO registered cat is an unknown handle (e.g. @kimi). Without this, parseAllMentions returns empty mentions + empty warnings, so the caller silently falls back to the default cat with zero user feedback." —— 就是"@kimi 静默变成 opus"那个 bug。

注意 handle 正则只吃 `[a-z0-9_.-]`，**中文 handle 抓不到** → 不会产生未知告警。这是后面 `groupHandles` 只需要过滤 ASCII 的原因。

### 4.10 `resolveCatTarget()`：handle → catId 或结构化错误

```ts
export function resolveCatTarget(mentionOrId: string): { ok: CatId } | { error: CatRoutingError } {
  const input = (mentionOrId.startsWith('@') ? mentionOrId.slice(1) : mentionOrId).toLowerCase();
  const configs = catRegistry.getAllConfigs();
  let catId: string | undefined = catRegistry.has(input) ? input : undefined;
  if (!catId) {
    outer: for (const [id, cfg] of Object.entries(configs)) {
      for (const p of cfg.mentionPatterns) {
        if ((p.startsWith('@') ? p.slice(1) : p).toLowerCase() === input) { catId = id; break outer; }
      }
    }
  }
  if (!catId) return { error: { kind: 'cat_not_found', mention: mentionOrId, alternatives: buildAlts(null) } };
  // KD-9: two-step check — isCatAvailable not used (it returns true for not-in-roster)
  const entry = getRoster()[catId];
  if (entry && entry.available === false) {
    return { error: { kind: 'cat_disabled', catId, displayName: ..., alternatives: buildAlts(catId, entry.family) } };
  }
  return { ok: catId as CatId };
}
```

**KD-9 那条注释是重点**：这里**故意不用** `isCatAvailable()`，因为：

```ts
export function isCatAvailable(catId: string, config?: CatCafeConfig): boolean {
  const roster = getRoster(config);
  const entry = roster[catId];
  return entry?.available !== false;   // 不在 roster = 可用（向后兼容）
}
```

`isCatAvailable` 对"不在 roster 的猫"返回 `true`，无法区分"没配置"和"配置了 available:true"。而 `resolveCatTarget` 需要区分 `cat_not_found` 和 `cat_disabled` 两种错误——前者建议改 handle，后者建议换猫。所以它做两步：先查 `catRegistry`（存在性），再查 `getRoster()`（可用性）。

`buildAlts(excludeId, preferFamily)` 的排序是三级：


### 4.11 群组 mention：pattern 构造与排序

`parseGroupMentions(message, threadId)` 的完整构造顺序：

```
① 归一化：lowerMessage = normalizeSpeechMentions(message).toLowerCase()
     ↑ 注意：这里先做语音归一化，parseMentionsRaw 是分两份处理的
② excluded = buildMentionExclusionSpans(lowerMessage)
③ patterns 数组按此顺序 push：
     a) thread 域：'@全体参与者'、'@thread'、'@本帖'
          resolve = threadStore.getParticipants(threadId)
                    → filterRoutableCats → 非空则返回
                    → 否则 pickFallbackCat(new Set()) → [fallback] 或 []
     b) breed 域：遍历 catRegistry.getAllConfigs() 建 breedMap
          跳过 !config.breedId
          跳过 !Object.hasOwn(this.services, catId)      ← 没有 service 实现的不算
          displayName = config.breedDisplayName ?? config.displayName（第一只该 breed 的猫的）
          每个 breed 产出两条：`@全体${displayName}` 和 `@all-${breedId}`

     c) 全局：'@全体'、'@all'
          resolve = filterRoutableCats(Object.keys(this.services))
                    → 空则 pickFallbackCat(new Set())
④ patterns.sort((a, b) => b.pattern.length - a.pattern.length)   ← 长度降序
⑤ 顺序遍历，第一个 findMatchPosition(pattern) >= 0 的胜出
     → return { cats: await resolve(), matchPosition: pos }
⑥ 全都不命中 → return null
```

第 ④ 步的注释："Sort longest-first to avoid prefix collisions (@全体布偶猫 before @全体)"。如果不排序，`@全体布偶猫` 会被 `@全体` 先命中（`startsWith` 成立），然后边界检查看到 `布` 不是 boundary → 不命中，最终整条落空。排序后 `@全体布偶猫` 先试，直接命中。

**`findMatchPosition` 的实现与个体 mention 有一处关键差异**：

```ts
const findMatchPosition = (pattern: string): number => {
  const lowerPattern = pattern.toLowerCase();
  let found = -1;
  forEachRouteLineMentionCandidate(lowerMessage, (line, lineOffset, candidate) => {
    if (found >= 0) return;
    const candidatePosition = lineOffset + candidate;
    if (isInsideSpan(candidatePosition, excluded)) return;
    if (!line.startsWith(lowerPattern, candidate)) return;      // ← 用 startsWith，不是 matchMentionPatternEnd
    const end = candidate + lowerPattern.length;
    const charAfter = line[end];
    if (!charAfter || MENTION_TOKEN_BOUNDARY_RE.test(charAfter)) found = candidatePosition;
  });
  return found;
};
```

三点：
1. **群组 mention 不容忍零宽字符**——用的是 `line.startsWith(lowerPattern, candidate)` 而不是逐字符跳零宽的 `matchMentionPatternEnd`。所以 LLM 在 `@all` 中间插了一个零宽字符（`@a<ZWSP>ll`）时，群组展开**匹配不上**；而同样位置的零宽字符对个体 handle 无害，因为个体那条路径每比一个字符前都先跳零宽。【源码】
2. **群组 mention 只在路由行生效**（`forEachRouteLineMentionCandidate`），个体 mention 可以在行内任意位置。所以 `帮我问下 @all` 不会展开成全体。
3. 右边界判定只查 `MENTION_TOKEN_BOUNDARY_RE`，**没有** `isMentionEndBoundary` 那套域名后缀/handle 续接逻辑。所以 `@allx` 不命中（`x` 不是 boundary），`@all.` 命中（`.` 是 boundary）。测试覆盖：`@allison does NOT trigger @all`、`@threadsafe does NOT trigger @thread`、`@all-ragdollish does NOT trigger @all-ragdoll`、`@全体布偶猫咪 does NOT trigger @全体布偶猫`。

### 4.13 `filterRoutableCats` / `isRoutableCat` / `pickFallbackCat`

```ts
private isRoutableCat(catId: string | null | undefined): catId is CatId {
  return typeof catId === 'string' && Object.hasOwn(this.services, catId) && isCatAvailable(catId);
}

private filterRoutableCats(catIds: Iterable<string | null | undefined>): CatId[] {
  const filtered: CatId[] = [];
  const seen = new Set<string>();
  for (const catId of catIds) {
    if (!this.isRoutableCat(catId)) continue;
    if (seen.has(catId)) continue;
    seen.add(catId); filtered.push(catId);
  }
  return filtered;
}
```

**"可路由"的两个条件缺一不可**：
- `Object.hasOwn(this.services, catId)` —— 有 `AgentService` 实现。用 `Object.hasOwn` 而不是 `in` 或 `services[catId]`，是为了防原型链污染（`'toString' in services` 会是 true）。
- `isCatAvailable(catId)` —— roster 里没标 `available: false`。

`filterRoutableCats` 同时做**去重 + 保序**（`seen` Set + 顺序 push）。这是"同一只猫 @ 多次不重复派发"的实现（测试 `does not duplicate same cat when mentioned multiple times`）。

```ts
private pickFallbackCat(exclude: Set<string>): CatId | null {
  const def = getDefaultCatId() as string;
  if (!exclude.has(def) && this.isRoutableCat(def)) return def as CatId;
  for (const id of Object.keys(this.services).sort()) {
    if (!exclude.has(id) && this.isRoutableCat(id)) return id as CatId;
  }
  return null;
}
```

两级：默认猫 → `Object.keys(services).sort()` 字典序第一个可路由的。**`.sort()` 是确定性的关键**——注释就叫 "Pick a deterministic fallback cat"。没有 sort 的话结果取决于对象键插入顺序，不同启动次序会派给不同猫。

`getDefaultCatId()` 自己也有一条链：运行时覆盖 `_runtimeDefaultCatId` → 环境变量 `DEFAULT_CAT_ID` → 缓存 `_defaultCatId` → 配置里 `breeds[0]` 的 `defaultVariantId` 对应 variant 的 `catId ?? breed.catId` → 终极兜底（`catRegistry.getAllIds()[0]` → 原始 env 值 → `'__none__'` 哨兵 + `log.warn`）。**只有前两级过 `isKnownAvailableDefaultCat` 校验**（失败会 `log.warn` 并往下掉）；缓存值和 `breeds[0]` 这两级是直接返回、不做可用性校验的——真正兜住"默认猫不可用"的是 `pickFallbackCat` 那一层。【源码】

### 4.15 Z5 分页扫描：`findRecentUserMentionFallback()`

三个常量：

```ts
const Z5_PAGE_SIZE = 50;
const Z5_USER_MESSAGE_COUNT_LIMIT = 5;
const Z5_TIME_WINDOW_MS = 60 * 60 * 1000; // 1h
```

| 常量 | 值 | 作用 |
|---|---:|---|
| `Z5_PAGE_SIZE` | 50 | 每页拉多少条 thread message（不是 user message） |
| `Z5_USER_MESSAGE_COUNT_LIMIT` | 5 | 最多回看 5 条 **USER** 消息；第 6 条时 `return null` |
| `Z5_TIME_WINDOW_MS` | 3_600_000 | 1 小时。既做 user 消息 cutoff，也做 page 级 cutoff |

**完整算法**：

```
effectiveOrderTime(m) = (typeof m.deliveredAt === 'number' && m.deliveredAt > 0) ? m.deliveredAt : (m.timestamp ?? 0)
cutoffTimestamp = Date.now() - Z5_TIME_WINDOW_MS
userMessagesSeen = 0; cursorScore = undefined; cursorId = undefined

for (pageIdx = 0; ; pageIdx += 1):                        ← 无上限循环
  pageResult = pageIdx === 0
      ? messageStore.getByThread(threadId, 50)
      : messageStore.getByThreadBefore(threadId, cursorScore ?? 0, 50, cursorId)
  page = await Promise.resolve(pageResult)                ← 兼容同步 mock / async Redis
  if (!page || !Array.isArray(page) || page.length === 0) BREAK

  for (i = page.length - 1; i >= 0; i -= 1):              ← 页内反向扫（页是升序）
    m = page[i]
    userIdStr = typeof m.userId === 'string' ? m.userId : null
    isUserMessage = userIdStr != null && !SYSTEM_USER_IDS.has(userIdStr) && m.catId == null
    if (!isUserMessage) CONTINUE                          ← 猫消息/系统消息不消耗任何配额

    score = effectiveOrderTime(m)
    if (score > 0 && score < cutoffTimestamp) RETURN null  ← ① 时间窗口终止
    userMessagesSeen += 1
    if (userMessagesSeen > 5) RETURN null                  ← ② 数量终止

    mentions = Array.isArray(m.mentions) ? m.mentions : []
    if (mentions.length === 0) CONTINUE                    ← 没 @ 的 user 消息：继续往前找
    routable = filterRoutableCats(mentions)
    RETURN routable.length > 0 ? [routable[0]] : null      ← ③ 命中：只取第一个，单猫

  # 页内没找到 → 准备下一页游标
  oldest = page[0]                                         ← 升序 → page[0] 最旧
  if (typeof oldest.id !== 'string') BREAK
  oldestScore = effectiveOrderTime(oldest)
  if (oldestScore <= 0) BREAK
  if (oldestScore < cutoffTimestamp) RETURN null           ← ④ page 级 cutoff
  cursorScore = oldestScore; cursorId = oldest.id

RETURN null
```

**四个终止条件**：① user 消息早于 1h、② 看过 5 条 user 消息、③ 找到带 mention 的 user 消息、④ 整页最旧消息早于 1h。加上两个 `BREAK`（空页、游标数据异常）。

**为什么没有 page cap**（这是最容易被追问的点）。函数体里的 R10 注释：

```
// F194 Phase Z5 R10 (cloud Codex round-6 P2): 去掉固定 page cap，仅靠 spec stop conditions
//   (5 user msgs / 1h cutoff / no more history) 收敛。固定 page cap 在高流量 thread
//   (vision-guard / handoff > 250) 仍可能漏掉真正的 user @ → 退化回 participantsWithActivity。
//   1h cutoff 通过 effective score 时间维度天然 bound 扫描深度
```

但**文件顶部的注释还停留在 R3 时代**：

```
 *   R3 P1（当前）：改成分页 loop（getByThread 拉首页 → 不够再 getByThreadBefore
 *     拿历史页），停在 N=5 USER msgs / 1h cutoff / 没有更多消息。
 *     defensive 上限 = Z5_PAGE_SIZE * Z5_MAX_PAGES = 250 条 thread messages。
```

`Z5_MAX_PAGES` **这个常量在文件里根本不存在**（我 grep 过，只有三个 Z5_ 常量）。所以顶部注释里的"defensive 上限 250"是过时信息。测试 `AC-Z16 R10: 250+ non-user msgs do not cap fallback scan (cloud Codex round-6 P2)` 正是为了锁住"没有 250 上限"这件事。

**为什么游标必须用 `effectiveOrderTime` 而不是 `timestamp`**（R9，砚砚 R8 P1）：Redis 的 thread zset score 在 `markDelivered` 之后会被改成 `deliveredAt`，但 `msg.timestamp` 仍是发送时间。如果游标用 `timestamp`，会跳到一个更早的 send-time，导致跨页时**跳过**中间那些按 `deliveredAt` 排序的页面。测试 `AC-Z16 R9: cross-page cursor uses effective score (deliveredAt ?? timestamp)` 锁这个。

**为什么 cutoff 判定放在 `isUserMessage` 之后**（R8）：非 user 消息已经 `continue` 跳过了，所以 cutoff 不会被一条老的猫消息误触发 `return null`。测试 `AC-Z16 R8: 1h cutoff only applies to USER messages`。

**user message 的严格定义**（函数文档注释）：

```
 * user message 严格定义：`userId !== null && catId === null`。
 *   - cat-to-cat handoff (A2A) 有 catId → NOT a user message
 *   - vision guard cross-post 有 catId → NOT a user message
 *   - 系统消息 (userId === null && catId === null) → NOT a user message
```

实现里还多了一层 `!SYSTEM_USER_IDS.has(userIdStr)`（R5 → R6 演进）：

```ts
export const SYSTEM_USER_IDS: ReadonlySet<string> = new Set(['scheduler', 'system']);
```

R5 只排了 `'system'`，R6 改用 `visibility.ts` 的 `SYSTEM_USER_IDS`，把 `scheduler` 也带上，与 message store 的 `isSystemUserMessage` 同口径。两条测试分别锁：`AC-Z16 R5: system notices (userId="system") must NOT count` 和 `AC-Z16 R6: scheduler notices (userId="scheduler") must NOT count`。

**结果只取一只猫**：`return routable.length > 0 ? [routable[0]] : null`。函数注释解释："用户心智模型：'no @ = 继续刚才 @ 的猫里的一只'，不是'thread 里最近发言的猫'，也不是把上一轮 parallel mentions 全量延续成新一轮并发。" 测试 `@three cats then no-@ routes to one cat from last user-message mentions`。

**分页函数的实际语义**（`MessageStore.ts` 内存实现）：
- `getByThread(threadId, limit)` —— 从尾部反向收集 `limit` 条，最后 `.reverse()` → **升序返回**。跳过 `deletedAt` 和 `!isDelivered(msg)`。
- `getByThreadBefore(threadId, timestamp, limit, beforeId)` —— 同样反向收集 + reverse。游标比较用 `const effectiveTs = msg.deliveredAt ?? msg.timestamp`，`effectiveTs > timestamp` 跳过；`effectiveTs === timestamp` 时用 `msg.id >= beforeId` 跳过（**排除游标消息自身**，防同页无限循环，注释标 F232 P1）。

注意 Z5 调用时**不传 userId**，所以扫的是整个 thread 所有用户的消息。

> **面试官追问："这个循环真的不会无限转吗？"**
> "会终止，靠两条：一是 page 级 cutoff——`page[0]` 是当前页最旧的 effective score，页按 effective score 升序，所以只要 `page[0] < cutoff`，再往前只会更老，直接 `return null`；二是 `getByThreadBefore` 的游标是严格递减的（同 score 时用 id 严格小于），拉不到新数据就返回空页 break。最坏情况是 thread 里最近 1 小时有海量猫消息且一条 user 消息都没有——那时会一直翻到 `page[0] < cutoff` 为止，扫描深度由 1 小时的消息量决定。这是有意的取舍：R10 的评审认为'漏掉真正的 user @'比'多扫几页'更贵。"

### 4.16 `applyThreadRoutingPolicy()` 完整流程

```ts
private applyThreadRoutingPolicy(thread, message, candidates): CatId[] {
  const routableCandidates = this.filterRoutableCats(candidates);
  const scope = inferRoutingScope(message);
  if (!scope) { /* fallbackA */ }

  const policy = thread?.routingPolicy;
  if (!policy || policy.v !== 1 || !policy.scopes) { /* fallbackA */ }

  const rule = policy.scopes[scope];
  if (!rule) { /* fallbackA */ }
  if (typeof rule.expiresAt === 'number' && rule.expiresAt > 0 && rule.expiresAt < Date.now()) { /* fallbackA */ }

  const avoidList = Array.isArray(rule.avoidCats) ? rule.avoidCats : [];   // 防脏数据
  const preferList = Array.isArray(rule.preferCats) ? rule.preferCats : [];
  const avoid = new Set(avoidList.map((id) => String(id)));
  const prefer = preferList.map((id) => String(id)).filter((id) => !avoid.has(id));

  const filtered = routableCandidates.filter((id) => !avoid.has(id as string));
  const out: CatId[] = []; const seen = new Set<string>();
  for (const id of prefer) {            // ① prefer 先排（可注入原本不在候选集的猫）
    if (!this.isRoutableCat(id)) continue;
    if (seen.has(id)) continue;
    seen.add(id); out.push(id as CatId);
  }
  for (const id of filtered) {          // ② 再拼原候选（已去掉 avoid）
    const sid = id as string;
    if (seen.has(sid)) continue;
    seen.add(sid); out.push(id);
  }
  if (out.length > 0) return out;

  const fallback = this.pickFallbackCat(avoid);
  return fallback ? [fallback] : routableCandidates;   // ← 最后兜底：avoid 失效，保证不返回空
}
```

`fallbackA` 是重复了 4 次的同一段：

```ts
if (routableCandidates.length > 0) return routableCandidates;
const fallback = this.pickFallbackCat(new Set());
return fallback ? [fallback] : [];
```

**四条要点**：
1. `prefer` 可以**注入**原本不在候选集里的猫（只要 `isRoutableCat`）。测试 `routingPolicy(architecture) prefers opus even when participants would route elsewhere`。
2. `avoid` 与 `prefer` 冲突时 avoid 赢（`prefer` 先被 filter 掉）。
3. `Array.isArray` 双保险——注释写明 "Defensive guard: data might be malformed from external persistence"。测试 `routingPolicy tolerates malformed avoid/prefer lists without crashing`。
4. **最后一行的兜底会让 avoid 失效**：如果 avoid 干掉了所有候选、且 `pickFallbackCat(avoid)` 也返回 null（所有可路由猫都在 avoid 里），就原样返回 `routableCandidates`。宁可违反 avoid 也不返回空数组。

`inferRoutingScope(message)`：

```ts

  return 'review';
}
if (lower.includes('architecture') || lower.includes('tradeoff')
    || message.includes('架构') || message.includes('设计') || message.includes('方案')) {
  return 'architecture';
}
return null;
```

`\bpr\b` 的词边界是重点——测试 `routingPolicy(review) does not trigger on words containing "pr" like "prompt"` 专门锁它。函数注释：`Intentionally deterministic and conservative.`

**policy 怎么影响猫的 prompt**：`routingPolicy` 除了影响路由，还被 route-parallel/route-serial 读出来塞进 `buildInvocationContext({ routingPolicy })`，`SystemPromptBuilder` 的 `@segment D13` 会渲染成一行文字（`avoid @xx, prefer @yy (budget)`），且 `avoid`/`prefer` 各截前 3 个、`reason` 会 `.replace(/[\r\n]+/g, ' ')` 防注入换行。

`activeParticipants` 同理走 `@segment D12`，但只取**一只**：`.filter(p => p.catId !== context.catId).find(p => p.lastMessageAt > 0)`。

### 4.17 `parseIntent()` 与 `stripIntentTags()`

```ts
export const INTENT_TAGS = ['ideate', 'execute'] as const;
export const PROMPT_TAGS = ['critique'] as const;
export const ROUTE_CONTROL_TAGS = [...INTENT_TAGS, ...PROMPT_TAGS] as const;
const TAG_PATTERN = /#(\w+)/gi;

export function parseIntent(message: string, targetCatCount: number): IntentResult {
  let explicitIntent: Intent | null = null;
  const promptTags: string[] = [];
  for (const match of message.matchAll(TAG_PATTERN)) {
    const tag = match[1]?.toLowerCase();
    if (INTENT_TAG_SET.has(tag)) explicitIntent = tag as Intent;      // ← 后写的赢
    else if (PROMPT_TAG_SET.has(tag)) promptTags.push(tag);
  }
  if (explicitIntent) return { intent: explicitIntent, explicit: true, promptTags };
  const intent: Intent = targetCatCount >= 2 ? 'ideate' : 'execute';  // 自动推断
  return { intent, explicit: false, promptTags };
}
```

三个细节：
- `explicitIntent` 是**覆盖赋值**，`#ideate ... #execute` → 最后一个 `execute` 生效。
- `TAG_PATTERN = /#(\w+)/gi` 的 `\w` **不含中文**，也不含 `-`。
- `stripIntentTags` 只删已知 tag，未知 `#foo` 原样保留；删完做 `.replace(/\s{2,}/g, ' ').trim()` 收缩空白。

`strategy` 判定放在 AgentRouter 而非 IntentParser：`intent.intent === 'ideate' && targetCats.length > 1 ? 'parallel' : 'serial'`。所以"1 只猫 + #ideate"是 `ideate` intent 但 `serial` strategy——intent 会进 prompt（影响思维方式），strategy 只决定编排。

### 4.19 消费循环：三层结构

```
for await (const msg of mergeStreams(recoveredStreams, onError))     ← 外层
   ├─ 构造 effectiveMsgs[]（text 过 stripper / done 补 flush / 其他原样）
   ├─ for (const effectiveMsg of effectiveMsgs)                      ← 内层：累积 + yield
   └─ if (msg.type === 'done' && msg.catId) { ... }                  ← done 块：落库 + 收尾
```

**外层的 `effectiveMsgs` 变换**：

```ts
const effectiveMsgs: AgentMessage[] = [];
if (msg.type === 'text' && msg.content && msg.catId) {
  effectiveMsgs.push({ ...msg, content: getPayloadStripper(msg.catId).push(msg.content) });
} else if (msg.type === 'done' && msg.catId) {
  if (msg.metadata && !catMeta.has(msg.catId)) catMeta.set(msg.catId, msg.metadata);
  const flushedText = getPayloadStripper(msg.catId).flush();
  if (flushedText) effectiveMsgs.push({ type: 'text', catId: msg.catId, content: flushedText, timestamp: msg.timestamp });
} else {
  effectiveMsgs.push(msg);
}
```

`createLeakedToolCallStreamStripper()` 是**流式状态机**（per-cat，存在 `catPayloadStrippers` Map 里），`push()` 可能吞掉一部分内容（半个泄漏的 tool call payload 跨 chunk），`flush()` 在 done 时吐出残留。所以 `done` 消息本身**不会**进 `effectiveMsgs`（只有它 flush 出的 text 会进），`done` 的处理在外层第三块。

**内层累积清单**（顺序即代码顺序）：

| 触发 | 动作 |
|---|---|
| 首个 `system_info` 且 JSON `type === 'invocation_created'` | `catInvocationId.set(catId, parsed.invocationId)`；`catFlushTime.set(catId, Date.now())`；若 `deps.draftStore && !keepaliveStarted` → 启动**唯一一个**全局 keepalive `setInterval` |
| `text` + content | `catText.set(catId, accumulateTextAggregate(prev, content, msg.textMode))` |
| `system_info` | `isUserFacingSystemInfoContent` → `catSawUserFacingSystemInfo`；JSON parse 后：`thinking` → `catThinking`（`appendThinkingChunk`）、`rich_block` → `catStreamRichBlocks`（先过 `isValidRichBlock`）、`invocation_usage` → `routeTotalTokens += inputTokens + outputTokens` |
| `error` **且该猫 signal 已 aborted** | **`continue`** —— 整条丢弃，既不记录也不 yield |
| `error` | `catHadError.add`；若未 aborted 则 `catHadProviderError.add`；`catErrorText` 换行拼接；`catCliDiagnostics` 记第一条 |
| 任意（经 `toStoredToolEvent`） | 非 null → `catToolEvents` push |
| `tool_use` | `catToolNames` push；`toolUsageCounter.recordToolUse`（fire-forget）；`toolEventLog.append(...)`；`pendingToolResultsByCat` FIFO push `{toolName, toolUseId}`；`rawToolName === 'Skill'` → `skillLoadEventLog.append` |
| 有 metadata 且 `catMeta` 未记 | `catMeta.set` |
| `tool_result` | 推断 toolName → `deriveResultSummary` → `toolEventLog.updateSummary(threadId, matcher, summary)` |
| 任意（有 `catInvocationId`） | #80 draft flush 判定 |
| `text` 且 content 为空 | `continue`（不 yield） |
| 其余 | 盖 `invocationId` 章后 `yield` |

**取消误伤的两处修复**（F-parallel-cancel，cloud #4 2026-05-30）：

```ts
if (effectiveMsg.type === 'error' && effectiveMsg.catId &&
    (signalForCat?.(effectiveMsg.catId) ?? signal)?.aborted) {
  continue;
}
```

注释解释得很细：被取消的猫，`invokeSingleCat` 会把 abort 转成 `error + done`。这里必须**整条丢弃**——不记录（否则 done 块会把 user_cancel 当 error 落库），不 yield（否则 `messages.ts`/`QueueProcessor` 会当成 provider 失败广播）。而且判定用的是**这只猫自己的 signal**（`signalForCat?.(catId)`），不是共享 signal，"else canceling one concurrent cat mislabels a sibling's real error as cleanup"。

**yield 前的盖章**（F194 Phase Z9 R1 P1-1）：

```ts
const ownInvForYield = effectiveMsg.catId ? catInvocationId.get(effectiveMsg.catId) : undefined;
const stampedEffectiveMsg =
  ownInvForYield && !effectiveMsg.invocationId ? { ...effectiveMsg, invocationId: ownInvForYield } : effectiveMsg;
yield stampedEffectiveMsg;
```

CLI 的 text/done/tool 事件不带 `invocationId`，只有 `system_info=invocation_created` 带。不盖章的话下游广播器会 fallback 到 parent invocation，导致"同一只猫多轮对话在共享 parent 下塌成一个气泡"。

### 4.20 done 块：落库时序

**第 ③ 步的顺序是被 bug 逼出来的**（F194 Phase Z9 砚砚 R2 P1）：`ownInvId` 必须在 `catInvocationId.delete()` **之前**捕获，第 ⑫ 步的 `stampedDone` 用的就是这个局部变量。注释原文："Re-querying the map here returns undefined → done event yielded without invocationId → downstream broadcaster falls back to parent"。

**第 ⑤ 步的双 ID 语义**（#573 parallel variant）：

```ts
const persistedInvocationId = options.parentInvocationId ?? ownInvId;
// ...

  ...(persistedInvocationId ? {
    stream: { invocationId: persistedInvocationId, turnInvocationId: ownInvId ?? persistedInvocationId },
```

- `invocationId` = **parent 优先** —— 因为 `messages.ts` 的 socket 广播用 parent id 做"活气泡"身份，落库必须一致，否则刷新后 IDB 气泡和水合气泡对不上，产生重复气泡。
- `turnInvocationId` = **own 优先** —— F194 Z9 AC-Z25/KD-28，用来区分同一 parent 下同一只猫的多轮，防止塌成一个气泡。

| 分支 | 进入条件 | 落库内容 | 特殊动作 |
|---|---|---|---|
| **A 有文本** | `catText.get(catId)` 非空 | `content = storedContent`（sanitize + 抽 rich block 后），`extra.rich` = buffered + text + stream 三路 rich block 合并 | voice 合成（非 voiceMode）、投票拦截、concierge actions 注入 |
| **B 无文本无错误** | `!text && !catHadError.has(catId)` | 仅当 `shouldPersistNoTextMessage` 才落 `content: ''` | 可能 yield `silent_completion` |
| **C 有错误但有工具** | `!text && catHadError` 且 `catToolEvents.length > 0` | `content: ''` + `toolEvents` | 无 |

分支 B 的三个布尔：


设计意图（注释）："Purely empty turns should not create blank chat bubbles." —— 完全空的回合不落库、不建气泡，但会 yield 一条 `silent_completion` 的 `system_info`（含 `provider`/`model`/`invocationId`），"so the user sees *something* instead of a silent vanish (bugfix: silent-exit P1)"。

**所有三条分支共享的落库字段**：


### 4.21 #80 draft flush 的判定

常量：

```ts
const FLUSH_INTERVAL_MS = 2000;
const FLUSH_CHAR_DELTA = 2000;
const KEEPALIVE_INTERVAL_MS = 60_000;
```

per-cat 三个游标：`catFlushTime`、`catFlushLen`（已落盘的文本长度）、`catFlushToolLen`（已落盘的工具事件数）。

```ts
const neverFlushedCat = lastLen === 0 && lastToolLen === 0;

// 文本路径
if (effectiveMsg.type === 'text' && charDelta !== 0 &&
    (neverFlushedCat || isReplaceText || now - lastFlush >= FLUSH_INTERVAL_MS || charDelta >= FLUSH_CHAR_DELTA)) {
  upsert(...); 更新三个游标;
}
// 工具路径
else if ((effectiveMsg.type === 'tool_use' || effectiveMsg.type === 'tool_result') &&
         (neverFlushedCat || now - lastFlush >= FLUSH_INTERVAL_MS)) {
  if (curText.length > lastLen || curToolLen > lastToolLen) { upsert(...); 更新长度游标; }
  else { deps.draftStore.touch(userId, threadId, invId)?.catch?.(noop); }
  catFlushTime.set(catId, now);
```

### 4.23 `mergeStreams()` 完整算法

```ts
interface TaggedResult<T> { index: number; result: IteratorResult<T>; }
interface TaggedError { index: number; error: unknown; }
type TaggedOutcome<T> = { ok: true; value: TaggedResult<T> } | { ok: false; value: TaggedError };

export async function* mergeStreams<T>(
  streams: AsyncIterable<T>[],
  onError?: (index: number, error: unknown) => void,
): AsyncGenerator<T> {
  if (streams.length === 0) return;
  if (streams.length === 1) { yield* streams[0]!; return; }        // ← 短路

  const iterators = streams.map((s) => s[Symbol.asyncIterator]());
  const pending = new Map<number, Promise<TaggedOutcome<T>>>();

  function arm(index: number): void {
    const it = iterators[index];
    if (!it) return;
    pending.set(index, it.next().then(
      (result): TaggedOutcome<T> => ({ ok: true,  value: { index, result } }),
      (error):  TaggedOutcome<T> => ({ ok: false, value: { index, error  } }),
    ));
  }

  for (let i = 0; i < iterators.length; i++) arm(i);

  while (pending.size > 0) {
    const outcome = await Promise.race(pending.values());
    if (outcome.ok) {
      const { index, result } = outcome.value;
      if (result.done) { pending.delete(index); }                  // done → 移出池，不 re-arm
      else { yield result.value; arm(index); }                     // 有值 → 吐出 + 重新装填
    } else {
      const { index, error } = outcome.value;
      pending.delete(index);
      onError?.(index, error);                                     // 报错 → 移出池 + 回调
    }
  }
}
```

**逐步复述版（面试可以直接背）**：

1. 0 个流直接 return；1 个流 `yield*` 短路（不进池）。
2. 把每个 `AsyncIterable` 拿 `[Symbol.asyncIterator]()` 变成 iterator，存数组。
3. `pending: Map<index, Promise<TaggedOutcome>>` 是"竞速池"，key 是流下标。
4. `arm(index)`：调 `it.next()`，用 `.then(onFulfilled, onRejected)` **把两条路都转成 resolved 的 TaggedOutcome**。这是全函数最关键的一行——`Promise.race` 因此**永远不会 reject**。
5. 初始把所有 iterator 都 arm 一遍。
6. 主循环 `while (pending.size > 0)`：`await Promise.race(pending.values())`。
7. `ok && result.done` → `pending.delete(index)`，池缩小一格。
8. `ok && !done` → `yield result.value`，然后 `arm(index)` 重新装填**这一路**。
9. `!ok` → `pending.delete(index)` + `onError?.(index, error)`。
10. 池空 → generator 自然结束。

**四个必答的细节**：

- **为什么要 tagged**？`Promise.race` 只返回值，不告诉你是哪个 promise 赢的。所以在 `arm` 里就把 `index` 打进 payload。
- **为什么把 reject 转成 resolved**？如果让 `Promise.race` 直接 reject，整个 generator 会抛，其余 N-1 条流全部失联（且它们的 iterator 不会被 `return()` 清理）。转成 `{ok:false}` 后，报错的流只是被踢出池，其他流继续。
- **重复 race 已 settle 的 promise 有问题吗？** 没有。未被 yield 的那几路，它们的 promise 对象保持在 Map 里不变；`Promise.race` 对同一个已 settle 的 promise 反复调用是安全的，只是每轮都要重建一次 race——O(N) 的微开销，N 是并发猫数（个位数），可忽略。
- **背压深度是 1**。`arm` 已经调了 `it.next()`，所以每一路最多预取 1 个元素等在那里。消费者慢下来时，每路最多多跑一步。【推断】这是我从 `arm` 的调用时机反推的，源码没有直接写"背压"两个字。

**短路分支在生产不触发**：`routeParallel` 只在 `targetCats.length > 1` 时被调用（`strategy` 判定要求），所以 `streams.length === 1` 走不到。但它会影响单元测试——直接测 `mergeStreams([oneStream])` 时异常会**直接抛**而不是走 `onError`。

**`onError` 在生产几乎不会被调用**，因为上游已经包了一层：

```ts
async function* wrapStreamWithErrorRecovery(stream, catId) {
  try { yield* stream; }
  catch (err) {
    log.error({ catId, err }, 'Parallel stream iteration error — synthesizing error+done');
    yield { type: 'error', catId, content: ..., error: ..., timestamp: Date.now() };
    yield { type: 'done',  catId, timestamp: Date.now() };
  }
}
```

函数头注释写明为什么必须包这一层：

```
 * Wrap an agent stream so iteration-time errors yield synthetic error+done events
 * instead of propagating into mergeStreams (which silently drops errored streams).
 * Without this, @all can lose a cat's response with zero user-visible feedback.
```

**合成 `done` 是关键**——不合成的话 `completedCount` 永远达不到 `targetCats.length`，`isFinal` 出不来，前端一直转圈。所以 `onError` 的回调只是保险丝日志：`log.error({ streamIndex: idx, catId: targetCats[idx], err }, 'Parallel stream error (post-recovery)')`，注意 "post-recovery" 字样。

```
mergeStreams 的池演化（3 只猫）：

t0  pending = {0:P0, 1:P1, 2:P2}          全部 arm
t1  race → 1 赢，非 done  → yield v1 → arm(1)
    pending = {0:P0, 1:P1', 2:P2}
t2  race → 0 赢，非 done  → yield v0 → arm(0)
    pending = {0:P0', 1:P1', 2:P2}
t3  race → 2 赢，done     → delete(2)
    pending = {0:P0', 1:P1'}
...
tn  pending = {}  → while 退出 → generator return
```

### 4.25 DeliveryCursor：三套命名空间与 ADR-008

```ts
const MAX_CURSORS = 5000;
const FALLBACK_CATS: readonly CatId[] = [createCatId('opus'), createCatId('codex'), createCatId('gemini')];
function cursorKey(userId, catId, threadId) { return `${userId}:${catId}:${threadId}`; }
```

三个私有 Map，**完全独立**：

| Map | 语义 | 谁写 |
|---|---|---|
| `cursors` | delivery cursor：这只猫**收到过**的最后一条消息 ID | route-parallel/serial 的 done 块，或 `ackCollectedCursors` |
| `mentionAckCursors` | mention ack（#77）：已确认的 @ 消息 ID | mention 流程 |
| `seenCursors` | seen cursor（F254）：猫**实际读过**的消息 ID | MCP 工具 `list_recent`/`get_thread_context`/`get_message`、`post_message`；route-parallel 在准备阶段用 `inc.boundaryId` 播种 |

类注释明确写了隔离要求：`CRITICAL: pushing seenCursor MUST NOT affect deliveryCursor (AC-A9)`。

**单调性怎么保证**（三个 ack 方法结构完全一样）：

```ts
async ackCursor(userId, catId, threadId, deliveredToId): Promise<void> {
  const key = cursorKey(userId, catId, threadId);
  const memCursor = this.cursors.get(key);
  const effective = memCursor && memCursor > deliveredToId ? memCursor : deliveredToId;   // ① max(mem, 入参)

  if (this.sessionStore) {
    try {
      const advanced = await this.sessionStore.setDeliveryCursor(userId, catId, threadId, effective); // ② Lua CAS
      if (advanced) {
        this.upsertMap(this.cursors, key, effective);
      } else {
        try {
          const actual = await this.sessionStore.getDeliveryCursor(userId, catId, threadId);          // ③ 回读
          if (actual) this.upsertMap(this.cursors, key, actual);
        } catch { /* GET failed after CAS noop — memory stays unchanged (safe) */ }
      }
      return;
    } catch (err) { log.warn({ err }, 'setDeliveryCursor failed, fallback to in-memory cursor'); }
  }

  const current = this.cursors.get(key);        // ④ 内存兜底：读写之间无 await = 无竞态
  if (current && effective <= current) return;
  this.upsertMap(this.cursors, key, effective);
}
```

四个设计点：
- **① `max(内存, 入参)`** 防 Redis 恢复回退：Redis 挂过一段时间，内存游标更新，恢复后要把这个更高的值当地板灌回去。
- **② 原子 CAS**：`setDeliveryCursor` 是 Lua 脚本，单调检查 + 写入一个 round-trip。
- **③ CAS noop 时回读同步内存**，且**内层单独 try/catch** —— 注释写得很明确："if this GET fails, we must NOT fall through to the outer catch which would write `effective` (a lower value) into memory."
- **④ 内存兜底路径注释**："In-memory fallback: monotonic check then write (no await gap = safe)" —— Node 单线程，读写之间没有 await 就没有竞态窗口。

比较用的是**字符串比较** `memCursor > deliveredToId`。文件头注释交代了前提："IDs are lexicographically sortable (timestamp+seq prefix), so monotonic progression can be enforced with string comparison."

`getCursor` 返回 `max(redis, memory)`：

```ts
if (redisValue != null) return memValue && memValue > redisValue ? memValue : redisValue;
```

`upsertMap` 是 LRU 式驱逐：

```ts
private upsertMap(map: Map<string, string>, key: string, value: string): void {
  if (map.has(key)) map.delete(key);                    // 先删，让 key 移到 Map 尾部
  while (map.size >= MAX_CURSORS) {
    const oldest = map.keys().next().value;             // Map 保序 → 第一个是最老的
    if (oldest !== undefined) map.delete(oldest);
  }
  map.set(key, value);
}
```

利用 JS Map 的插入顺序特性做 LRU，上限 5000 条/每个 Map。

**游标怎么推进（route-parallel 侧）**：

```ts
  },
  parentCtx,                                                        // 第三个参数 = context
);
```

`isRemote: true` 是 F153 的跨路由 A2A 传播：一只猫 @ 了另一只猫，QueueProcessor 派发新 route 时把上游 span 的 `traceId`/`spanId` 带过来，新 route 的 span 就挂在同一条 trace 上。

状态处理（两个入口一致）：

```ts
try {
  if (strategy === 'parallel') yield* routeParallel(...); else yield* routeSerial(...);
  routeSpan.setStatus({ code: SpanStatusCode.OK });
} catch (err) {
  routeSpan.setStatus({ code: SpanStatusCode.ERROR, message: String(err) });
  throw err;                                 // 重新抛，不吞
} finally {
  /* routeExecution: 回写 tracing 到用户消息 */
  routeSpan.end();
}
```

**span 往下传**：`routeSpan` 塞进 `routeOptions`，route-parallel 在每猫 spawn 时传给 `invokeSingleCat`：

```ts
...(options.routeSpan ? { routeSpan: options.routeSpan } : {}),
```

于是每次 invocation 的 span 成为 route span 的子 span。

**聚合属性在 route-parallel 末尾打**：

```ts
if (options.routeSpan) {
  options.routeSpan.setAttribute(ROUTE_TOTAL_CATS_INVOKED, completedCount);
  options.routeSpan.setAttribute(ROUTE_TOTAL_TOKENS, routeTotalTokens);
  options.routeSpan.setAttribute(ROUTE_HAS_A2A_HANDOFF, false);
}
```

`routeTotalTokens` 的来源是消费循环里对 `system_info` 的解析：

```ts
if (parsed.type === 'invocation_usage' && parsed.usage) {
  routeTotalTokens += (parsed.usage.inputTokens ?? 0) + (parsed.usage.outputTokens ?? 0);
}
```

`ROUTE_TOTAL_CATS_INVOKED` 用的是 `completedCount`（**完成数**，不是派发数）。被取消跳过的猫不发 done，所以不计入。

## 7. 面试追问应对

### Q1：「用户发了一条没有 @ 的消息，你从头讲一遍是怎么决定派给谁的。」

> "入口是 `resolveTargetsAndIntent`，它默认走只读的 `peekTargets`（`persist: true` 时走 `resolveTargets`，两者唯一区别是后者会 `addParticipants`）。判定顺序是九级：
> ① `parseAllMentions` 有结果就直接返回，**不过 routing policy**；
> ② 没有 threadStore 就直接返回默认猫；
> ③ 消息里有 `#ideate` 且 `preferredCats` 里可路由的猫 >1 只 → 全量派发；
> ④ `thread.threadKind === 'concierge'` 且有 preferredCats → 值班猫；
> ⑤ `findRecentUserMentionFallback`——回看最近 5 条、1 小时内的 **user** 消息，找第一条带 mentions 的，取它的第一只可路由猫；
> ⑥ `participantsWithActivity` 里第一个 `messageCount > 0 && lastResponseHealthy !== false && isRoutableCat` 的；
> ⑦ 退而求其次：preferred 里的健康参与者，再退：任意健康参与者；
> ⑧ `preferredCats[0]`；
> ⑨ `getDefaultCatId()`。
> 除了第 ① ② 级，其余都会过 `applyThreadRoutingPolicy` 做 prefer/avoid 重排。"

**加分点**："第 ⑤ 级和第 ⑥ 级的先后是被一个真实 bug 逼出来的，注释里甚至留了产品负责人的原话——'明明 at 的最后一只猫是 47 or 55 但是召唤出来的却是 46'。原因是 vision guard 的 cross-post 消息带 catId，会更新 `participantsWithActivity`，把真正的用户意图挤掉。所以加了 Z5 这一级，严格只认 `userId != null && !SYSTEM_USER_IDS.has(userId) && catId == null` 的消息。"

### Q2：「Z5 那个分页扫描，循环有终止条件吗？三个常量各管什么？」

> "三个常量：`Z5_PAGE_SIZE = 50`（每页拉多少条 thread message）、`Z5_USER_MESSAGE_COUNT_LIMIT = 5`（最多回看几条 **user** 消息）、`Z5_TIME_WINDOW_MS = 1 小时`。
> 循环本身是 `for (let pageIdx = 0; ; pageIdx += 1)`，**没有页数上限**。终止靠四个 return 和两个 break：user 消息早于 1h → return null；看过第 6 条 user 消息 → return null；找到带 mentions 的 user 消息 → return `[routable[0]]`；整页最旧消息早于 1h → return null；空页 break；游标数据异常 break。
> 页数上限是 R10 那轮**主动删掉**的——固定 250 条在高流量 thread（vision-guard/handoff 刷屏）里仍然会漏掉真正的用户 @，退化回 participantsWithActivity。删掉后靠 R11 加的 page 级 cutoff 收敛。"

**加分点**："文件顶部的注释还写着 `defensive 上限 = Z5_PAGE_SIZE * Z5_MAX_PAGES = 250`，但 `Z5_MAX_PAGES` 这个常量已经不存在了——这是注释漂移。有个测试专门叫 `AC-Z16 R10: 250+ non-user msgs do not cap fallback scan`，锁的就是'没有 250 上限'。另外同一个文件里的 `collectAndDetectTextFrustration` 还保留着 `MAX_PAGES = 10`，两处分页策略不一致。"

### Q3：「`mergeStreams` 具体怎么实现的？为什么不用 `for await` 套一层？」

> "核心是 tagged `Promise.race` 池。每个 `AsyncIterable` 转成 iterator，`arm(index)` 调 `it.next()` 并用 `.then(onFulfilled, onRejected)` **把 resolve 和 reject 都转成 resolved 的 `{ok, value}`**，把 `index` 打进 payload，塞进 `pending: Map<number, Promise>`。主循环 `while (pending.size > 0)` 里 `await Promise.race(pending.values())`：拿到值就 `yield` 然后 re-arm 这一路；`done` 就 `pending.delete`；`{ok:false}` 就 delete + 调 `onError`。池空 generator 结束。
> 不能用嵌套 `for await`，因为那是**串行**的——外层 `for await` 会把第一条流吃完才轮到第二条，完全失去并发意义。也不能直接 `Promise.race` 原始 promise，因为 race 只给你值不给你来源，所以要 tag。"

**加分点**："把 reject 转成 resolved 是这段代码的灵魂。如果让 race 直接 reject，整个 generator 会抛，其余 N-1 条流全部失联、iterator 也不会被清理。转成 `{ok:false}` 后只是把出错那一路踢出池。不过实际生产里 `onError` 几乎不会触发，因为上游 `wrapStreamWithErrorRecovery` 已经把异常吞掉并合成了 `error + done` —— 合成 `done` 是关键，否则 `completedCount` 达不到 `targetCats.length`，`isFinal` 出不来，前端会一直转圈。日志文案里那个 'post-recovery' 就是这个意思：出现这条说明两层保护都没兜住。"

### Q4：「并行模式下猫能不能互相 @ 触发新调用？代码上怎么保证的？」

> "不能，有 8 道锁。代码层 5 道：
> ① `continuityCapsule` 里 `a2aEnabled: false` 硬编码；
> ② `route-parallel.ts` 全文没有 `WorklistRegistry`，`targetCats` 在函数入口固定、`Promise.all` 一次性建流，没有任何追加路径；
> ③ 最后一只猫 done 时确实会跑 `parseA2AMentions`，但只 `log.info({suppressedInParallel: true})`，不 enqueue；
> ④ 落库时 `mentions: []`，所以 `MessageStore.getMentionsFor()` / pending-mentions 流程看不到；
> ⑤ `routeSpan.setAttribute(ROUTE_HAS_A2A_HANDOFF, false)`。
> prompt 层 2 道：`d7-mode-parallel.md` 明写 'F167 L2: @句柄 在并行模式下无路由语义…不要互相 @'；`SystemPromptBuilder` 里 `shouldInjectA2ALongAnchors = context.mode !== 'parallel' && ...`，parallel 不注入 D8 球权锚点。
> 第 8 道是 `route-serial.ts` 的文件头注释——'A2A only triggers here in routeSerial; routeParallel never chains (MVP safety boundary)'。"

**加分点**："为什么不只靠 prompt？F167 那份 feature 文档 Phase A 的标题就叫'Harness 硬护栏'，副标题'三个运行时刹车，不依赖模型遵守 prompt'。失败模式很贵：3 只猫并行，每只回复里 @ 2 只，一轮就炸出 6 条链。而第 ③ 道锁保留日志不删——这样能统计模型违反 prompt 的频次，用来评估 prompt 效果。禁掉但可观测，比彻底静默好。"

### Q5：「说说 route-parallel 的落库时序。为什么所有猫的消息 timestamp 一样？」

> "落库全部发生在 done 块里，一只猫一次。顺序是：捕获 `ownInvId` → `catInvocationId.delete(catId)` → 消费 rich block buffer → 算 `persistedInvocationId = parentInvocationId ?? ownInvId` → 三选一分支落库 → 删 draft → `updateParticipantActivity` → 单独落错误消息 → 挫败检测 → 推进游标 → guide ack → yield done。
> timestamp 用的是 `invocationStartedAt`，在进入消费循环**之前** `Date.now()` 取一次，全批次共用。【推断】我理解是为了让同一轮并行的 N 条回复在时间轴上保持稳定顺序，不受各猫完成先后影响——否则前端每次刷新的排序可能不一样。源码里没写这条理由。"

**加分点**："`catInvocationId.delete` 的位置很讲究，它必须在 `ownInvId` 被捕获成局部变量**之后**、后续所有使用**之前**。删是为了让 keepalive 定时器不再 touch 已删的 draft（issue #83 P2，否则 HSET 会重建孤儿 Redis key）；捕获成局部变量是因为最后 yield done 时还要用它盖章（F194 Z9 砚砚 R2 P1，重新查 Map 会拿到 undefined，下游广播器 fallback 到 parent，气泡身份就错了）。"

### Q6：「`invocationId` 和 `turnInvocationId` 为什么要存两个？」

> "```ts
> const persistedInvocationId = options.parentInvocationId ?? ownInvId;
> extra.stream = { invocationId: persistedInvocationId, turnInvocationId: ownInvId ?? persistedInvocationId }
> ```
> `invocationId` 取 **parent 优先**，因为 `messages.ts` 的 socket 广播用 parent id 做活气泡身份；落库如果用 own id，刷新后水合出来的气泡 id 和实时气泡对不上，会出现重复气泡（#573 parallel variant）。
> `turnInvocationId` 取 **own 优先**，用来区分同一 parent 下同一只猫的多个回合；只有一个 id 的话多轮会塌成一个气泡（F194 Z9 AC-Z25 / KD-28）。
> 两个字段服务两个不同的相等性判断：一个是'属于哪次用户请求'，一个是'属于哪个回合'。"

### Q7：「群组 mention 和个体 mention 的解析有什么不一样？」

> "四点不一样：
> ① **作用域**：群组 mention 只在'路由行'生效（`forEachRouteLineMentionCandidate`），个体 mention 可以出现在行内任意位置（`forEachUserMentionCandidate`）。所以 `帮我问下 @all` 不会展开成全体，但 `帮我问下 @codex` 会路由到 codex。
> ② **零宽容忍**：个体走 `matchMentionPatternEnd`，逐字符匹配前都跳零宽；群组用的是 `line.startsWith(lowerPattern, candidate)`，**零宽字符会导致匹配失败**。
> ③ **右边界规则**：个体走 `isMentionEndBoundary`（含域名后缀、handle 续接判断）；群组只查 `MENTION_TOKEN_BOUNDARY_RE`。
> ④ **语音归一化时机**：`parseGroupMentions` 一进来就 `normalizeSpeechMentions(message).toLowerCase()`；`parseMentionsRaw` 是分两份处理的，原文走全量扫描、归一化后的只走行首语法。
> 优先级上，群组先解析、个体后解析，然后按位置做并集：`[before, ...group, ...after]`。"

**加分点**："pattern 的排序是关键。`patterns.sort((a,b) => b.pattern.length - a.pattern.length)` 保证 `@全体布偶猫` 在 `@全体` 之前。不排序的话 `@全体` 会先 `startsWith` 命中，然后边界检查看到 `布` 不是 boundary → 整条落空，用户以为写错了。同样的最长优先也用在个体 pattern 上，防 `@opus` 抢走 `@opus-45`。"

### Q8：「`DeliveryCursor` 是什么？和 ADR-008 什么关系？」

> "它是 `(userId, catId, threadId)` 三元组到'最后一条已投递消息 ID'的映射，key 就是 `${userId}:${catId}:${threadId}`。作用是增量上下文投递——每次调用只把游标之后的新消息拼进 prompt，而不是全量历史。ID 是 timestamp+seq 前缀的字典序单调串，所以单调性可以用**字符串比较**实现。
> ADR-008 的 S3 阶段规定'cursor 只在 succeeded 时推进，failed/canceled 不推进'。落地方式是 `RouteOptions.cursorBoundaries: Map<string,string>`：策略层在 done 时只 `upsertMaxBoundary` 收集边界，不真 ack；`messages.ts` 在把 InvocationRecord 标 succeeded **之前**调 `router.ackCollectedCursors()`。
> 如果调用方不传这个 Map，就退回 legacy 行为——done 时立即 `ackCursor`。"

**加分点**："实际实现比 ADR 文字更细。abort 分支也会 ack（注释标 F148 fix，'ack cursors for cats that completed before abort'），因为 parallel 下可能 2 只跑完 1 只被取消——已完成那 2 只的消息确实送出去了，不 ack 下次会重发。而 `persistenceContext.failed` 分支是真的不 ack。安全性由三层单调兜底：`max(内存, 入参)` + Redis Lua CAS + 内存路径的 `effective <= current` 早退。所以重复或乱序 ack 都不会让游标后退。
> 另外还有两套独立命名空间：`mentionAckCursors`（#77）和 `seenCursors`（F254，记录猫**实际读过**什么，由 MCP 工具写）。类注释明确写了 `CRITICAL: pushing seenCursor MUST NOT affect deliveryCursor (AC-A9)`。"

### Q9：「`ThreadRoutingPolicyV1` 怎么影响路由？prefer 和 avoid 冲突了听谁的？」

> "结构是 `{ v: 1, scopes?: Partial<Record<'review'|'architecture', ThreadRoutingRule>> }`，rule 有 `preferCats` / `avoidCats` / `reason` / `expiresAt`。
> 生效路径：`inferRoutingScope(message)` 先从消息文本推 scope（review 看 'review'/'lgtm'/'merge'/`\bpr\b`/'合入'/'帮我看看' 等，architecture 看 'architecture'/'tradeoff'/'架构'/'设计'/'方案'），推不出来就整条 policy 不生效。然后取 `policy.scopes[scope]`，检查 `expiresAt`，最后重排候选：先放 prefer 里可路由的（**可以注入原本不在候选集的猫**），再拼上过滤掉 avoid 的原候选。
> 冲突时 **avoid 赢**：`prefer = preferList.map(String).filter(id => !avoid.has(id))`。
> 有一个例外必须记住：**显式 @ 完全不过 policy**，有测试直接锁 `routingPolicy does not override explicit @mention`。"

**加分点**："最后一行兜底很有意思——如果 avoid 把所有候选都干掉、`pickFallbackCat(avoid)` 也返回 null，代码会 `return routableCandidates`，也就是**宁可违反 avoid 也不返回空数组**。设计取向很明确：没人回复比派错猫更糟。
> 还有 `policy.v !== 1` 直接放行的写法，是给未来 v2 留的安全降级；`Array.isArray` 双保险是防外部持久化写脏数据，注释写明 'data might be malformed from external persistence'。
> 另外 policy 不只影响路由，还会通过 `buildInvocationContext({routingPolicy})` 进到 prompt 的 D13 段，渲染成一行 `avoid @x, prefer @y (budget)`——各截前 3 个，`reason` 还会 `.replace(/[\r\n]+/g, ' ')` 防换行注入。"

### Q10：「取消一只猫，怎么保证不误伤同批的其他猫？」

> "靠 `RouteOptions.signalForCat: (catId) => AbortSignal | undefined`。`messages.ts` 传的是 `(catId) => invocationTracker?.getController?.(threadId, catId)?.signal`——每只猫一个独立 controller。
> route-parallel 里三处都用 `signalForCat?.(catId) ?? signal`：
> ① spawn 前的前置检查 `if (catSignal?.aborted) return 空 generator`——已经被取消的猫直接不 invoke，否则 `invokeSingleCat` 会把 aborted iterator 转成 error+done，把 user_cancel 广播成 provider 错误；
> ② 消费循环里 `if (error && 该猫 signal.aborted) continue`——abort 之后产生的 error 整条丢弃，不记不吐；
> ③ `catHadProviderError` 的判定：`if (!(signalForCat?.(catId) ?? signal)?.aborted) catHadProviderError.add(catId)`——只有 abort **之前**的错误才算真 provider 失败。
> 第 ③ 点会一路传到 `updateParticipantActivity(threadId, catId, !catHadProviderError.has(catId))`，也就是被取消的猫**不会**被标成不健康，下次无 @ 时还能被 fallback 选中。"

**加分点**："注释里特别说明了为什么不能用共享 signal 判断：'judge abort with THIS cat's own signal, not the shared one — else canceling one concurrent cat mislabels a sibling's real error as cleanup'。也就是说如果用共享 signal，取消 A 猫的瞬间 B 猫真的报错了，B 的错误会被当成清理噪音丢掉，用户什么都看不到。
> 还有一点：批次门（batch gate）**故意不因单猫取消而 abort**，所以消费循环里没有 `controller.signal.aborted` 的 break——这是和 route-serial 的 `if (catSignal?.aborted) break` 的对称设计，注释里明说了。"

### Q11：「`route()` 和 `routeExecution()` 到底差在哪？为什么要拆？」

> "拆的原因是 ADR-008 S1：'用户消息写入和猫调用执行彻底解耦'。老流程 `POST /api/messages` 里写消息和调猫耦合在一个后台任务里，失败了没法单独重试。新流程是：Lua 原子创建 InvocationRecord + 幂等 key → 写用户消息 → 回填 `userMessageId` → 返回 202 → 后台执行。重试端点只需要重新执行第 ⑤ 步，不会重复写用户消息。
> 所以 `routeExecution` 不写消息，只收 `userMessageId` + 已解析的 `targetCats` + `intent`。它多出来的能力全是解耦带来的：`cursorBoundaries`（延迟 ack）、`persistenceContext`（跨 generator 回传落库失败）、`signalForCat`（逐猫取消）、`callerTraceContext`（跨路由 trace 传播）、finally 里把 `{traceId, spanId}` 回写到用户消息。
> `route()` 标了 `@deprecated`，注释写 'Will be removed after S4 migration is complete'，S4 就是重试端点。"

**加分点**："顺带说一个坑：文件头注释里写的入口名是 `execute` 和 `executeWithContext`，这两个方法**根本不存在**，全仓 grep 只命中注释自己。真实入口是 `route` 和 `routeExecution`。这类注释漂移在这两个文件里不止一处。"

### Q12：「这段代码你觉得最脏的地方在哪？」

> "三处。
> 第一，`peekTargets` 和 `resolveTargets` 有大约 55 行**逐字重复**的代码，唯一差别是有 mention 时 `resolveTargets` 会 `addParticipants`。作者自己知道——F229 那块的注释写着 'Placed BEFORE findRecentUserMentionFallback — see matching comment in peekTargets'，等于承认在双写。现在有 7 个 return 分支要同步改，漏一个就是只读试算和真实派发不一致。
> 第二，`resolveTargetsAndIntent` 里 `parseAllMentions` 被调了两次（一次拿 warnings，一次在 `peek/resolveTargets` 内部），每次发消息全量 mention 解析跑两遍，还带一次 `getParticipants` 的 IO。
> 第三，目标解析走了 9 级 fallback 中的哪一级**完全没有日志**。线上出'派错猫'只能靠 span 的 `target_cats` 反推。我会加一行结构化 log，把 `tier`（1~9）和关键输入（mentions/preferredCats/lastReplier）打出来。"

**加分点**："另外 `route-parallel.ts` 1649 行、单个函数就占了 1550 行，远超仓库自己 CLAUDE.md 写的 '200 行警告 / 350 行硬上限'。它和 `route-serial.ts` 之间还有大量镜像逻辑（tool_result FIFO、draft flush、落库三分支、错误消息落库、挫败检测），注释里到处是'mirrors serial route's XXX'。这是我会优先抽公共层的地方——不过要小心，两边的细节差异（isLastCat、a2aEnabled、mentions 是否为空）是有意的，不能一刀切。"
