# 01 · 架构全景与数据流

> 这一篇回答面试里最常见也最难答好的一题：**"整体架构讲一下"。**
>
> 讲架构最忌讳报菜名（"有路由模块、有记忆模块、有 Skills 模块……"）。
> 正确的讲法是**跟着一条消息走一遍** —— 每经过一个模块，
> 说清它做了什么、为什么必须在这个位置、如果没有它下游会出什么问题。
>
> 讲完这条链，模块之间的咬合关系就自然出来了。

## 2. 一条消息的完整旅程

现在跟着一条真实的消息走。假设用户在 Console 里输入：

```
@opus 帮我实现一下 F123，做完让 @codex review
```

### 阶段 0 · 前端到后端

```
浏览器 Console
   │  POST /api/messages   （消息内容 + threadId）
   │  同时 WebSocket 订阅这个 thread 的推送
   ▼
routes/messages.ts
```

前端**不等 HTTP 响应拿结果** —— HTTP 只负责"我提交了"，
实际的流式输出走 WebSocket。这是必须的，因为一次 Agent 调用可能跑几十分钟。

### 阶段 1 · 入队还是直接执行？

这是很多人会漏掉的一步，但它是并发正确性的关键。

```ts
// routes/messages.ts（简化）
const tryResult = opts.invocationTracker.tryStartThreadAll(threadId, targetCats, userId);
if (!tryResult.ok) {
  // 目标 Agent 正忙 → 进队列
  const enqueueResult = opts.invocationQueue.enqueue({ ... });
  return { queued: true, queuePosition: enqueueResult.queuePosition };
}
// 空闲 → 直接执行
```

**判忙的粒度是"slot 级"，不是"thread 级"。**

什么意思？`slot = (threadId, catId)`。也就是：

```
opus 正在忙          →  再发给 opus 的消息进队列
                      →  但发给 codex 的消息可以立刻执行
```

【ADR】这是 ADR-018 明确决策的（OQ-4）：

> **决定**：Connector 和用户消息的判忙维持 slot 级（`has(threadId, catId)`），
> 不改为 thread 级。
>
> **效果**：猫A 在忙时，发给猫B 的消息直接执行（by the way 场景）；
> 用户可以同时和多只猫交互，只要目标猫空闲。
>
> **放弃的方案**：thread 级判忙（`has(threadId)`）。
> 理由：太粗，猫A忙时猫B也被锁，牺牲并行性。

但同一个 ADR 里紧接着有个补丁：

> **安全保障**：`tryStartThread()` 在执行层面仍是 thread 级 busy gate
> （同一 thread 不会并发两个 invocation），slot 级只影响入队决策。

**读懂这两句话的关系很重要**，它是一个双层设计：

```
入队决策层：slot 级   →  宽松，让"顺便问问另一只猫"能立刻走
执行层：   thread 级 →  严格，同一个帖子里不会真的并发两个调用
```

为什么执行层要严格？因为同一个 thread 的消息历史、球权状态是共享的，
两个调用并发写会打架。

**面试可以这么讲**：
"它的判忙做了两层。入队看 slot 级（每个 Agent 独立），
所以你可以在 A 忙的时候顺手问 B；但执行层是 thread 级串行的，
因为同一个帖子的状态是共享的。这个拆分让'并行感'和'状态一致性'能同时拿到。"

### 阶段 2 · 路由：算出叫醒谁、怎么叫

```
routes/messages.ts
   ▼
AgentRouter.execute()
```

路由做三次判断（详见 [模块 03](03-模块-路由与编排.md)）：

```
判断一：目标集
   显式 @ → [opus, codex]（发现两个）

判断二：意图
   没有 #ideate / #execute 标签
   → 但这里有个坑：两只猫默认会推断成 ideate（并行）
   → 实际这条消息语义是串行（"做完让 codex review"）
   → 用户需要显式写 #execute，或者只 @opus 让它自己 @codex

判断三：策略
   ideate + 多猫 → routeParallel（并行，互相看不见）
   execute 或单猫 → routeSerial（串行接力，且只有它支持 A2A 链）
```

**这里就有一个面试可以讲的设计缺陷**（见 §5）。

假设走了 `routeSerial`，`worklist = [opus, codex]`。

### 阶段 3 · 组装 prompt

```
AgentRouter → route-serial.ts
   ▼
   ├─ SystemPromptBuilder.buildStaticIdentity(opus)     ← 只在新 session
   ├─ SystemPromptBuilder.buildInvocationContext(...)   ← 每轮
   ├─ ContextAssembler.assembleContext(messages)        ← 最近 20 条 / 2000 token
   └─ SessionBootstrap.buildSessionBootstrap(...)       ← 如果是 session #2+
```

最终喂给 CLI 的 prompt 结构大致是（详见 [模块 07](07-模块-身份注入.md)）：

```
┌─ 静态身份（只在新 session）─────────────────┐
│ S1 你是布偶猫/宪宪，由 Anthropic 提供…       │
│ S2 硬限制：…                                │
│ S5 队友名册（表格：@handle · 模型 · 擅长 · 注意）│
│ S9 治理摘要 L0（从 shared-rules.md 编译）     │
└────────────────────────────────────────────┘
┌─ Session Bootstrap（session #2+）───────────┐
│ [Previous Session Summary — reference only] │
│ 上一段会话干了什么 / 任务快照 / 怎么查更多    │
└────────────────────────────────────────────┘
┌─ 动态上下文（每轮）────────────────────────┐
│ D1 Identity: 布偶猫/宪宪 (@opus, model=…)   │  ← 抗压缩身份锚
│ D7 当前模式：你是第 1/2 只被召唤的猫          │
│ D14 SOP 阶段：impl，建议 skill: writing-plans│
└────────────────────────────────────────────┘
┌─ 对话历史 ────────────────────────────────┐
│ [对话历史 - 最近 12 条]                     │
│ [14:32 co-creator] …                       │
│ [/对话历史]                                 │
└────────────────────────────────────────────┘
┌─ 用户这条消息 ─────────────────────────────┐
│ @opus 帮我实现一下 F123，做完让 @codex review │
└────────────────────────────────────────────┘
```

**这里有个关键的架构边界**，面试可以讲：

`invoke-single-cat.ts` 的文件头明确写了：

```
 * 不处理: system prompt 构建（由调用方负责 prepend）、
 *         消息存储（由调用方在 yield 后累积并存储）。
```

**为什么 prompt 组装在路由层，不在调用层？**

因为 prompt 里有"你是第 1/2 棒""队友是 codex""前面那只猫说了什么"——
**只有路由层知道这些**。如果放在调用层，就得把整个路由状态传下去，
那才是真正的上帝函数。

### 阶段 4 · 调用：spawn 子进程

```
route-serial.ts
   ▼
invokeSingleCat(deps, params)     ← async generator，边跑边吐
   │
   ├─ ① cloud-only 短路？（有些 Agent 跑在浏览器里，不 spawn）
   ├─ ② 解析账号凭据
   ├─ ③ 解析 session（新开还是 --resume）
   ├─ ④ 解析工作目录（项目根 / worktree / bootcamp）
   ├─ ⑤ 注入环境变量 ★
   ├─ ⑥ 写 MCP 配置
   ├─ ⑦ spawn 子进程
   ├─ ⑧ 解析事件流 → yield AgentMessage
   └─ ⑨ 终态 + 审计 + 遥测
```

**第 ⑤ 步是全系统最关键的一根线**：

```
CAT_CAFE_INVOCATION_ID = <这次调用的 id>
CAT_CAFE_CALLBACK_TOKEN = <这次调用的 token>
```

这两个环境变量传给子进程，子进程再传给它拉起的 MCP server，
MCP server 拿它们作为凭据往 API 回写数据。

**这就是"回程通路"的钥匙**（详见 [模块 13](13-模块-MCP回调桥.md)）。

同时还注入 git 身份：每只 Agent 用自己的名字提交代码，
`git log` 里能看出哪个功能是谁写的。

### 阶段 5 · 两条回程通路

```
        ┌──────────────────────────┐
        │  claude 子进程            │
        └────┬────────────────┬────┘
             │ stdout          │ MCP stdio
             │ （流）           ▼
             │          ┌──────────────┐
             │          │ mcp-server   │  另一个子进程
             │          │ cat_cafe_*   │
             │          └──────┬───────┘
             │                 │ HTTP + invocationId/token
             ▼                 ▼
      event parser      routes/callback-*.ts
             │                 │
             └────────┬────────┘
                      ▼
              AgentMessage 流
```

**这两条路性质完全不同，这是面试可以展开的一个点：**

| | stdout 通路 | MCP 回调通路 |
|---|---|---|
| 传什么 | 增量文本、工具调用事件 | 结构化写操作（发富文本、申请权限、标球权） |
| 谁发起 | CLI 自动 | Agent 主动调工具 |
| 可靠性 | 父子进程管道，进程活着就通 | HTTP，会超时/鉴权过期/失败 |
| 失败处理 | 进程死了整轮就结束 | 重试 3 次 → outbox 落盘 → 降级策略 |

**为什么不统一成一条？**
【推断】stdout 是 CLI 的既有行为，改不了；
MCP 是标准协议，也不该改。所以只能两条并存。
代价是要处理"两条路的状态不一致"——比如 MCP 回调已经写了消息，
但 stdout 那边进程崩了。

### 阶段 6 · A2A 检测：可能再来一轮

```
opus 的回复文本完整结束
   ▼
parseA2AMentions(storedContent, 'opus')
   │  发现行首有 "@codex 帮我 review"
   ▼
resolveRoutingDecisions(signal, ctx)   ← 六道护栏
   │  abort? queue-pending? depth? dedup? pendingTail? streak?
   │  全部通过
   ▼
worklist.push('codex')     ← 运行中动态增长
   ▼
回到阶段 3，为 codex 组装 prompt
```

**注意 `worklist` 是可增长的数组**，这是 `routeSerial` 的核心数据结构。
`routeParallel` 永远不做这一步 —— 源码注释写死了：

```
 * A2A only triggers here in routeSerial; routeParallel never chains (MVP safety boundary).
```

**为什么并行不许链式？** 3 只猫并行，每只又 @ 出 2 只，一轮就是 6 个新调用，
深度 15 层的话就是烧钱机器。所以从架构上直接禁掉。

### 阶段 7 · 落库 + 推送

```
messageStore.append(...)          落库
   ▼
SocketManager → WebSocket        推给前端
   ▼
球权状态机 ingest 事件            更新"任务现在归谁"
   ▼
如果到了 session 阈值 → SessionSealer.requestSeal()
```

## 3. 模块咬合关系：四张"依赖切片"

上面是时间顺序。但面试官可能问"这些模块之间是什么关系"，
这时候需要换成**结构视角**。我把它切成四张图。

### 切片一：谁产生 prompt

```
                    ┌─────────────────────┐
                    │  最终喂给 CLI 的     │
                    │  一大段文本           │
                    └──────────┬──────────┘
                               │ 由谁拼出来
        ┌──────────────┬───────┴───────┬──────────────┐
        ▼              ▼               ▼              ▼
┌──────────────┐┌────────────┐┌──────────────┐┌────────────┐
│SystemPrompt  ││Context     ││Session       ││McpPrompt   │
│Builder       ││Assembler   ││Bootstrap     ││Injector    │
│（身份+L0+名册）││（对话历史）  ││（上一段会话） ││（工具说明） │
└──────┬───────┘└─────┬──────┘└──────┬───────┘└─────┬──────┘
       │ 读             │ 读            │ 读            │ 读
       ▼               ▼              ▼              ▼
┌──────────────┐┌────────────┐┌──────────────┐┌────────────┐
```

**这张图的价值在于回答"记忆系统怎么进 prompt 的"** ——
不是一股脑塞进去，而是四个组件各管一段，各有自己的 token 预算。

### 切片二：谁在管并发

多 Agent 系统的并发点比想象的多。这是面试的加分区：

```
┌────────────────────────────────────────────────────────────┐
│ 并发点 1：同一 thread 多个调用                                │
│   InvocationTracker.tryStartThread()   thread 级 busy gate  │
│   → 执行层串行                                               │
├────────────────────────────────────────────────────────────┤
│ 并发点 2：同一 Agent 多个 session                             │
│   SessionMutex + Active Slot                                │
│   → 每只 Agent 每个 thread 最多 1 个 active session          │
├────────────────────────────────────────────────────────────┤
│ 并发点 3：队列公平性                                          │
│   QueueProcessor 的 fairness gate                           │
│   → 用户消息不能被无限的 A2A 链饿死                            │
├────────────────────────────────────────────────────────────┤
│ 并发点 4：压缩次数计数                                        │
│   incrementCompressionCount() 原子自增                       │
│   → 防两个 hook 同时打进来导致 TOCTOU 少算                     │
├────────────────────────────────────────────────────────────┤
│ 并发点 5：SOP 阶段推进                                        │
│   WorkflowSopStore 乐观并发（版本号 + VersionConflictError）  │
├────────────────────────────────────────────────────────────┤
│ 并发点 6：配置文件读写                                        │
│   withCapabilityLock()                                      │
├────────────────────────────────────────────────────────────┤
│ 并发点 7：多进程访问同一 SQLite                                │
│   WAL 模式 + busy_timeout 5s                                │
├────────────────────────────────────────────────────────────┤
│ 并发点 8：多个 worktree 抢端口                                │
│   check-worktree-port-offset.mjs（CI 门禁）                  │
└────────────────────────────────────────────────────────────┘
```

**面试话术**：

> "多 Agent 系统的并发点比单 Agent 多一个数量级。
> 我数了下这个项目至少处理了八处：thread 级 busy gate、session 互斥、
> 队列公平性、压缩计数的原子自增、SOP 的乐观并发、配置文件锁、
> SQLite 的 WAL、甚至多个 worktree 抢 dev server 端口都有 CI 门禁。
>
> 最有意思的是队列公平性 —— 因为 Agent 之间会互相调用，
> 如果不做限制，一条 A2A 链能把用户的新消息饿死。
> 所以护栏里专门有个 `queuedMessagesPending` 的闸门：
> 队列里有用户消息在等的时候，不允许再展开新的 A2A 跳转。"

### 切片三：谁在管"钱"

Token 就是钱。这个项目的成本控制点：

```
入口侧（少喂）
  ├─ 对话历史：20 条 / 2000 token，单条截断 1500 字符
  ├─ bootstrap：硬上限 2000 token
  ├─ 静态身份只在新 session 注入，resume 不重复
  ├─ 队友名册单元格限长 52 / 72 字符
  └─ Skills 按需加载（不是全塞进 prompt）

出口侧（少调）
  ├─ 单条消息扇出 ≤ 2
  ├─ A2A 链深度 ≤ 15
  ├─ 乒乓检测：≥2 警告，≥4 硬切
  ├─ 并行路径禁止链式
  ├─ reviewer 必须"有额度"（注释写着"40 美刀教训"）
  └─ 云端 review 封板：5 轮上限

观测侧（知道花了多少）
  └─ tokenUsage / llmCallDuration / catInvocationCount 等 10 个遥测指标
```

**"40 美刀教训"这个注释值得在面试里提一句** ——
它说明这个项目的成本意识不是理论上的，是被账单教育过的。

### 切片四：谁在管"错"

```
错误分三类，各有各的处理层
┌──────────────────────────────────────────────────────────┐
│ 瞬时错误（重试能好）                                        │
│   callback-retry: 3 次 [1s, 2s, 4s]，只重试 408/429/5xx    │
│   每次带 10s AbortSignal（否则半开 TCP 会永久挂起）          │
├──────────────────────────────────────────────────────────┤
│ 永久错误（重试没用，要降级）                                 │
│   degradation.ts: 只在 401 + 可降级原因时降级                │
│   expired / unknown_invocation → 可降级                    │
│   invalid_token → 不降（客户端 bug，降了会掩盖）              │
│   stale_invocation → 绝不降（会把作废状态写回去）             │
├──────────────────────────────────────────────────────────┤
│ 投递失败（暂时发不出去）                                     │
│   callback-outbox: 落盘 JSON + rename 原子写 + 最多 10 次   │
│   语义是 at-least-once → 所以服务端要幂等（idempotencyKey）  │
├──────────────────────────────────────────────────────────┤
│ 进程级失败（Agent 卡死/崩了）                                │
│   球权状态机：zombie / dead / void 三种状态                  │
│   reconcileZombies + StartupReconciler                     │
│   迟到心跳 10 分钟宽限，防网络抖动翻烧饼                       │
├──────────────────────────────────────────────────────────┤
│ 会话级失败（封存卡住）                                       │
│   reconcileStuck（懒扫描）+ reconcileAllStuck（全局收割）    │
└──────────────────────────────────────────────────────────┘
```

**这张图是面试的高分区**，因为它显示你不只看了 happy path。

## 4. 五个"如果没有它会怎样"

模块之间的咬合，最好的证明方式是**抽掉一个看会塌什么**。

### 抽掉身份注入（模块 07）

```
第 1 轮：Agent 从 CLAUDE.md 知道自己是"布偶猫"
第 5 轮：上下文压缩，CLAUDE.md 那段被摘要掉了
第 6 轮：Agent 不知道自己叫什么，开始用"AI 助手"自称
第 7 轮：另一只猫 @ 它，它以为在跟用户说话，回复给了用户
第 8 轮：签名写错，git commit 用了错的作者
```

**连锁反应**：身份丢了 → A2A 交接错乱 → 跨模型互审的
"不能自审"判定失效（因为分不清谁是谁）。

**所以身份注入是 A2A 和互审的前置条件。**

### 抽掉连续性胶囊（模块 08）

```
Agent 正在 worktree/f123 上干活，第 3/4 棒
  ── 压缩 ──
Agent 醒来，只看到"讨论了一个功能实现"
  → 在 main 上直接改代码（违反铁律）
  → 或者新开一个 worktree（现在有两个了）
  → 或者重新规划整个任务（丢掉已完成的工作）
  → 或者回复给用户而不是回复给 @ 它的那只猫
```

**连锁反应**：控制流丢了 → 串行链断掉 → 球权状态机收到不匹配的事件
→ 任务进入 zombie。

### 抽掉护栏（模块 03 的 `resolveRoutingDecisions`）

```
opus: "@codex 你看下"
codex: "@opus 我觉得应该这样"
opus: "@codex 但是…"
codex: "@opus 不过…"
… 无限循环，每轮烧掉几万 token
```

**连锁反应**：账单爆炸。这不是假设 —— 深度限制、乒乓检测、
公平性闸门这三层护栏都是事后补上的（有 feature 编号和 review 记录）。

### 抽掉证据库（模块 09）

```
昨天讨论出来的决策 → 只存在 CLI 的会话历史里 → 换 session 就没了
  → Agent 重新讨论一遍同一个问题
  → 或者做出和昨天相反的决策
  → 而且没人知道昨天讨论过
```

**连锁反应**：Self-Evolution 的"同类错误 ≥2 次"判定失效
（因为查不到第一次）；跨模型互审失去"原始需求可引用"的能力。

### 抽掉 MCP 回调桥（模块 13）

```
Antigravity CLI（纯文本输出）
  → 没法发富文本消息
  → 没法申请权限
  → 没法标记球权
  → 只能靠父进程解析它的纯文本，反推它想干什么
```

**连锁反应**：非 Claude 的 Agent 退化成"只会说话不会做事"，
多模型的意义就没了。

## 5. 三个我认为的架构缺陷

面试里能主动说出项目的问题，比只夸好话强得多。这三个我有具体依据。

### 缺陷一：意图推断和真实语义会打架

【推断】

`IntentParser` 的规则是"≥2 只猫且无显式标签 → ideate（并行）"。

但用户写的：

```
@opus 帮我实现，做完让 @codex review
```

**语义明显是串行**，系统却会推断成并行 —— 两只猫同时收到同一条消息，
opus 去实现，codex 也去 review（review 什么？还没实现呢）。

**为什么这个默认值还是对的？**
因为"多猫 = 想听不同观点"在讨论场景下更常见，而并行能保护观点独立性。
项目选择了保护更高频的场景。

**但代价是**：用户必须学会写 `#execute`。
这是把复杂度推给了用户 —— 而这类系统的用户恰恰是不想学语法的。

**我会怎么改**：让模型来判断。路由前先用一次便宜的模型调用
（或者直接让第一只被 @ 的 Agent 判断）决定串并 ——
这和项目自己的"机械层 vs 判断层"原则是一致的，
只不过他们在这一处选了机械规则。

### 缺陷二：`invoke-single-cat.ts` 3599 行是个真问题

【源码】项目规范写着 `File size: 200 lines warning / 350 hard limit`，
这个文件超了十倍。项目自己有 `F219-tech-debt-architecture-evolution` 在跟。

**为什么会这样**（四个原因叠加）：

1. 六种 provider 的差异必须在某处收敛
2. 每个可选依赖都要 fail-open（大量 `readonly xxx?:` + 判空）
3. 遥测密度极高（10 个指标 + span + 审计）
4. 每个 review 发现的 edge case 都留下了防御分支

**我会怎么改**：见 [17 章](17-如果重新设计.md)。核心思路是
把"provider 差异"从条件分支改成策略对象 ——
现在的形态是一个函数里 if/else 处理六种 CLI，
应该是六个类各自实现同一个接口，公共流程只写一遍。

### 缺陷三：两条回程通路的状态一致性没有统一收口

【推断】

MCP 回调写数据和 stdout 解析出的消息，是两条独立的写入路径。
它们之间没有事务。所以理论上存在：

```
Agent 通过 MCP 发了一条富文本消息（已落库）
  → 然后 stdout 那边进程崩了
  → 这一轮的终态是 error，但消息已经在库里了
```

代码里能看到应对痕迹（`ensureTerminalStatus.ts`、
`cleanupStreamingOnFailure`），但那是打补丁，不是设计上的统一。

**我会怎么改**：把两条通路都收敛成"事件写入同一个 append-only 日志"，
然后从日志投影出消息和状态。这样一致性问题变成了"投影是否幂等"，
比现在的"两条路互相补偿"好推理。

## 6. 面试怎讲这一篇

### 30 秒版

> "五个包，主体是 `packages/api`，1300 个文件，DDD 分了 22 个 domain，
> 核心就一个 `domains/cats/services`。
> 数据流是：路由算出叫醒谁 → 四个组件各拼一段 prompt →
> spawn CLI 子进程 → 两条回程通路（stdout 流 + MCP 回调）→
> 检测有没有 @ 下一只 Agent → 可能再来一轮。
> 里面最有设计感的是护栏和抗压缩那两块。"

### 3 分钟版

按 §2 的七个阶段讲，每个阶段一句话，重点停在三处：

1. **阶段 1 的双层判忙**（slot 级入队 + thread 级执行）—— 显示你懂并发
2. **阶段 3 的架构边界**（prompt 在路由层组装）—— 显示你懂职责划分
3. **阶段 6 的护栏**（六道闸门 + 并行禁链）—— 显示你懂成本控制

### 常见追问

**Q：为什么不用消息队列（Kafka/RabbitMQ）做编排？**

> "它其实有队列（`InvocationQueue`），但是进程内的 + Redis 持久化，
> 没上外部 MQ。我理解的原因是：
> 一，这是个本地优先的桌面应用，Redis 都是可选的（有内存模式），
> 上 Kafka 会让安装门槛爆炸；
> 二，它的队列语义很特殊 —— 需要 slot 级判忙、需要用户插队 steer、
> 需要公平性闸门防 A2A 饿死用户消息，这些用通用 MQ 表达不如自己写清楚。
>
> 但如果做多租户 SaaS 版，我觉得必须换 —— 现在的队列是单进程状态，
> 横向扩展不了。"

**Q：如果 API 进程重启了，正在跑的调用怎么办？**

> "有专门的模块。`RedisAuthInvocationBackend` 的注释写着
> `Restart-resilient: API process exit / deploy / crash no longer drops active…`，
> 说明 invocation 记录是持久化的。
> 启动时有 `StartupReconciler` 和 `reconcileZombies` 做对账，
> 把重启前遗留的 active 调用清理成终态。
> 球权状态机那边也有对应的 `zombie` 状态。
>
> 不过子进程本身是活不过重启的 —— 父进程死了子进程会被回收，
> 所以恢复的是'状态一致性'，不是'继续跑'。
> 真要继续跑得靠会话恢复（`--resume` + 连续性胶囊）重新调一次。"

**Q：这个架构能撑多少并发？**

> "单机、单进程、本地优先，它没往这个方向设计。
> 瓶颈在两处：
> 一是执行层 thread 级串行，同一个帖子永远只有一个调用在跑；
> 二是 CLI 子进程本身，每次 spawn 有 0.5~2 秒开销，
> 而且每个子进程是一个完整的 Node 进程 + 模型客户端，内存不便宜。
>
> ADR-001 的'已知风险'里第一条就是 CLI 启动开销，
> 并且明确写了'不做边界：本轮不引入进程池'。
> 所以进程池是他们知道但故意没做的事。"

**这个答法的价值**：它显示你不但知道瓶颈，还知道**项目自己知道**
——而且能引用出处。
