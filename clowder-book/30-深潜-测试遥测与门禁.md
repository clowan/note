## 2. 核心数据结构

### 2.1 `TraceSpanDTO`（`telemetry/local-trace-store.ts`）

内存里存的**不是** OTel SDK 的 span 对象，而是投影后的纯数据 DTO。

```ts
export interface TraceSpanDTO {
  traceId: string;        // OTel trace ID，随机 hex，不是 PII，原样存
  spanId: string;
  parentSpanId?: string;  // 有它才能重建树
  name: string;           // 'cat_cafe.invocation' / 'cat_cafe.tool_use Bash' ...
  kind: number;           // SpanKind 数值
  startTimeMs: number;
  endTimeMs: number;
  durationMs: number;     // 冗余存，省得前端每次减
  status: { code: number; message?: string };
  attributes: Record<string, unknown>;  // 已脱敏快照（一层展开拷贝）
  events: ReadonlyArray<{ name: string; timeMs: number; attributes?: Record<string, unknown> }>;
  storedAt: number;       // 存进 buffer 的时刻，用于按龄淘汰（不是 span 的时间）
}
```

**为什么每个字段存在**：
- `storedAt` 和 `startTimeMs` 分开：淘汰按"什么时候进的缓冲"，不按"span 什么时候发生的"。hydrate 从 Redis 灌回来的 span 用消息的 `timestamp` 当 `storedAt`，这样 24h 的窗口对历史数据同样成立。
- `attributes` 要拷贝一份（`{ ...span.attributes }`，见 `local-trace-exporter.ts` 的 `spanToDTO()`）：因为 `RedactingSpanProcessor` 是**原地 mutate** span.attributes 的，不拷贝会拿到共享引用。**注意**：源码注释写的是 "deep-copied from span"，但实现是对象展开，只拷了一层——嵌套对象值仍是共享引用【源码，`spanToDTO()`；注释与实现的措辞落差，这是个可以主动指出的小瑕疵】。
- `parentSpanId` 从 `span.parentSpanContext?.spanId` 读【源码，`spanToDTO()`】——OTel 2.x 的 API，不是老的 `span.parentSpanId`。

### 2.2 `StepSummary`（`telemetry/step-summary.ts`）

这是"一轮对话走了几步"的描述性摘要。

```ts
export interface StepSummary {
  traceId: string;
  routeSpanId?: string;
  agent_loop_count: number | null;      // 长度：think→act→observe 循环数
  tool_call_count: number | null;       // MCP 子 span 数 + 基础工具计数器
  a2a_dispatch_count: number | null;    // mention_dispatch span 数
  duration_ms: number;                  // 总是有值
  token_total: number;
  error_count: number;
  is_restored: boolean;                 // 层级已丢（冷启动 hydrate 出来的）
  width_avg_tools_per_loop: number | null;  // 宽度 = tool/loop
  agent_loop_partial: boolean;          // 有的 invocation 有 loop 计数、有的没有
}
```

**三个 `| null` 字段是这个结构最值得讲的设计**【源码，文件头注释】：注释里写 "UI must render `—` for null, not `0`(AC-I4 / AC-I7 non-degradation)"。也就是说，**"不知道"和"是 0"必须在类型层面区分开**。为什么？因为不同 Provider 的流协议不一样，有的能识别出 LLM 调用边界（就调 `recordAgentLoop()`），有的识别不出（就永远不调）。如果把"识别不出"渲染成 0，用户会以为这只猫一步都没走。

`agent_loop_partial` 更细一层：混合 Provider 场景下，有的 invocation 报了、有的没报，这时候 `agent_loop_count` 是个**低估值**，宽度 `width_avg_tools_per_loop` 会被算成偏大——所以代码里 `width` 的条件包含 `!agentLoopPartial`【源码】。

> **面试官追问："为什么不直接默认 0？"**
> 我会说：这是可观测性系统里最容易犯的错——把 missing 折叠成 zero。这个项目在类型上用 `number | null` 强制区分，并且在注释里把"UI 必须渲染破折号"写成验收条件。因为多 Agent 系统里 Provider 是异构的，某个 Provider 的流里根本没有"一次 LLM 调用结束"这个事件，你只能诚实地说不知道。折叠成 0 会让运维看着一堆 0 去查根本不存在的故障。

### 2.4 `ToolEvent` 判别联合（`tool-usage/event-log-types.ts`）

```ts
export type ToolStatus = 'success' | 'low_hit' | 'no_match' | 'error';

export interface BaseToolEvent {
  invocationId: string; sessionId: string; threadId: string; catId: string;
  toolName: string; timestamp: number; turnIndex: number; status: ToolStatus;
}

export type ToolEvent =
  | (BaseToolEvent & { toolName: 'search_evidence'; summary: SearchEvidenceSummary })
  | (BaseToolEvent & { toolName: 'graph_resolve';   summary: GraphResolveSummary })
  | (BaseToolEvent & { toolName: 'list_recent';     summary: ListRecentSummary })
  | (BaseToolEvent & { summary: GenericSummary });
```

`turnIndex` 存在的理由：文件头注释说这个日志要算 `grep_after_search_rate` / `candidate_selection_distribution` / `list_recent_adoption_rate` / nudge 有效性——**全是序列指标**，必须保留顺序。而现有的两套设施都做不到【源码，注释直接对比】：
- `ToolUsageCounter`：按 `(date, catId, category, toolName)` 聚合，丢了序列
- `TranscriptWriter`：把 toolNames 塞进 `Set` 去重，也丢了序列

`GraphResolveSummary.rankedCandidateAnchors` 的注释很讲究：**"selectedCandidateIndex can be reconstructed by finding selectedAnchor's position in rankedCandidateAnchors — don't just record candidateCount"**【源码】。即：光记数量没用，要记完整的排序候选集，才能反推"猫选了第几个"。

## 3. 主流程逐段拆解

### 3.1 遥测初始化（`telemetry/init.ts` 的 `initTelemetry()`）

**Step 0：整体开关**
```ts
if (process.env.OTEL_SDK_DISABLED === 'true') {
  log.info('OTel SDK disabled (OTEL_SDK_DISABLED=true)');
  return { shutdown: async () => {}, traceStore: null, getMetricsText: null, metricsSnapshotStore: null };
}
```
返回的是一个"全 null 的句柄"而不是抛异常——下游 `telemetry.ts` 路由看到 `traceStore === null` 会返回 503。

**Step 1：debug 模式默认拒绝**
```ts
export function shouldEnableDebugMode(requested: boolean): boolean {
  if (!requested) return false;
  const env = process.env.NODE_ENV;
  if (env === 'development' || env === 'test') return true;
  return process.env.TELEMETRY_DEBUG_FORCE === 'true';
}
```
为什么这么写：`TELEMETRY_DEBUG=true` 会把**未脱敏**的 span 打到 console。而 `start-dev.sh --profile=production` 启动时 `NODE_ENV` 是**没设置的**（注释明确写了 "including unset NODE_ENV from profile-driven startup"【源码】），所以"unset 也要拦"，必须显式 `TELEMETRY_DEBUG_FORCE=true` 才放行。这是 default-deny。

**Step 2：HMAC salt 启动期校验**
```ts
try { validateSalt(); } catch (err) {
  log.error({ err }, 'OTel SDK disabled: HMAC salt validation failed');
  return { shutdown: async () => {}, traceStore: null, ... };
}
```
注释里的原话：**"telemetry should never be a crash source"**【源码】。缺 salt 就静默关掉遥测，服务继续跑。

**Step 3：span processor 链的顺序**（这一段是整个文件最重要的）

```ts
// ORDERING MATTERS: debug exporter must come BEFORE RedactingSpanProcessor.
const spanProcessors = [];
if (cfg.debugMode) spanProcessors.push(new SimpleSpanProcessor(new ConsoleSpanExporter()));
if (cfg.otlpEnabled) {
  spanProcessors.push(new RedactingSpanProcessor(new BatchSpanProcessor(new OTLPTraceExporter())));
} else {
  // KD-13 fix: 没有 OTLP 也必须跑脱敏，否则 LocalTraceExporter 会看到原始 attributes
  const noopInner = { onStart(){}, onEnd(){}, shutdown: ()=>Promise.resolve(), forceFlush: ()=>Promise.resolve() };
  spanProcessors.push(new RedactingSpanProcessor(noopInner));
}
const localExporter = new LocalTraceExporter();
spanProcessors.push(new SimpleSpanProcessor(localExporter));   // 必须最后
```

链条是：`Console(未脱敏) → Redacting(原地改) → LocalTraceExporter(看到已脱敏)`。

**坑在哪**：`RedactingSpanProcessor.onEnd()` 是**原地 mutate** `span.attributes`（`Object.assign((span as any).attributes ?? {}, redacted)`）。这意味着：
1. 排在它前面的 exporter 看到原始值 → 所以 debug console 要放最前；
2. 排在它后面的 exporter 看到脱敏值 → 所以 LocalTraceExporter 放最后；
3. **OTLP 关掉时，链里就没有 RedactingSpanProcessor 了**，LocalTraceStore 会存原始 prompt / invocationId → 这就是注释里的 KD-13 bug。修法是插一个包着 noop 内层处理器的 Redacting，纯粹为了触发 mutate 副作用。

> **面试官追问："用副作用来达成脱敏，不脆吗？"**
> 我会承认脆，并且指出代码作者自己也知道——`local-trace-exporter.ts` 的文件头把三层顺序画成了 ASCII 注释，`init.ts` 里写了大写的 "ORDERING MATTERS"。更干净的做法是让 LocalTraceExporter 自己调一次纯函数 `redactAttributes()`，而不是依赖上游处理器的 mutate 时序。代价是同一批属性脱敏两遍（HMAC 会重复算），但换来的是顺序无关。我会说这是一个 knowingly-taken 的技术债，标记方式是注释而不是类型。

**Step 4：warmup counters**
```ts
sdk.start();
import('./instruments.js').then(({ warmupCounters }) => warmupCounters());
```
`warmupCounters()` 对 30 个低频 counter 做 `.add(0)`。注释【源码】："Pre-touch counters that may never fire in normal operation so they appear in Prometheus output (eval can distinguish 0 from absent)."

为什么用动态 `import()` 而不是顶部静态 import：`instruments.ts` 里那个 `lazy()` Proxy 的注释解释了——**静态导入会让 instruments 模块在 `initTelemetry()` 之前被加载，instrument 就绑到 NoopMeterProvider 上了**【源码，`instruments.ts` 顶部注释提到 AntigravityAgentService 的静态 import 链】。

**Step 5：30 秒快照定时器**
```ts
const SNAPSHOT_INTERVAL_MS = 30_000;
const snapshotTimer = setInterval(async () => {
  const { resourceMetrics } = await prometheusExporter.collect();
  const text = metricsSerializer.serialize(resourceMetrics);
  snapshotStore.add({ timestamp: Date.now(), metrics: parsePrometheusText(text) });
}, SNAPSHOT_INTERVAL_MS);
snapshotTimer.unref();   // 不阻止进程退出
```

### 3.2 一次调用的 span 生成时序

```

  │     attributes: cat_cafe.routing.target_cats / .intent / .strategy

     立即 end()，返回它的 spanContext 作为新 route 的 caller ctx
```

**几个"为什么这么写"**：

1. **`llm_call` span 是回溯创建的**（`startTime = now - durationApiMs`），因为代码只有在 CLI 吐出 `done` 事件带 usage 时才知道这次调用花了多久。函数注释直接写了 "startTime is approximate"【源码】。

2. **基础工具不建 span**（Bash/Read/Write）：`recordToolUseSpan()` 里 `if (!isMcpToolName(toolName))` 就走计数器分支。注释【源码】："to avoid flooding the trace tree"。计数器状态存在模块级 `WeakMap<Span, number>` 里，key 是 span 对象本身——span 被 GC 时自动清理。

3. **`ToolSpanTracker` 的基础工具分支要委托给 `recordToolUseSpan`**，不能自己维护计数：
```ts
if (!isMcpToolName(toolName)) {
  recordToolUseSpan(this.invocationSpan, this.catId, toolName, toolInput);
  return undefined;
}
```
注释【源码】说明了原因："prevents undercount during the partial-wiring migration window when some msg path goes through tracker and some through legacy"——迁移期两条路径并存，必须共用同一个 WeakMap。

4. **`mention_dispatch` span 立即 end()**：它只是个"接力棒"，用来把 caller 的 trace 上下文变成一个可被新 route 引用的 spanId。

### 3.3 `RedactingSpanProcessor.onEnd()` 的脱敏四级

```ts
function redactValue(key: string, value: unknown): unknown {
  if (isClassA(key)) return '[REDACTED]';
  if (isClassB(key) && typeof value === 'string') {
    const hash = createHash('sha256').update(value).digest('hex').slice(0, 16);
    return `[hash:${hash} len:${value.length}]`;
  }
  if (isClassC(key) && typeof value === 'string') return pseudonymizeId(value);
  return value;  // Class D: pass through
}
```

| 级别 | 判定 | 处理 | key 清单【源码】 |
|---|---|---|---|
| A 凭证 | `CLASS_A_KEYS.has(lower)` 或 `lower.endsWith('_token')` 或 `endsWith('_api_key')` | `'[REDACTED]'` | authorization, cookie, set-cookie, x-api-key, token, apikey, api_key, secret, password, credential, credentials, callbacktoken |
| B 业务内容 | 精确匹配小写 | `[hash:<sha256前16> len:<长度>]` | prompt, message.content, thinking, toolinput, tool_result, command, aggregated_output, mcp.arguments, rich_block.image |
| C 系统标识 | 精确匹配小写 | HMAC-SHA256 前 32 hex | userid, threadid, invocationid, sessionid, messageid, rawarchivepath |
| D 其他 | 兜底 | 原样 | agent.id, gen_ai.*, tool.name … |

**F192 Phase D 的补丁**【源码，注释】：早期版本只脱敏 `span.attributes`，不管 `span.events[].attributes`。而 per-fire sample evidence 会把原始 `messageId`/`invocationId`/`threadId` 打在 span event 上，导致这些原始 ID 通过 `/api/telemetry/traces` 泄漏。修复就是在 `onEnd()` 里多加一段遍历 events 的循环。

> **面试官追问："Class B 为什么是 hash+len 而不是直接删掉？"**
> 我会说：因为要保留"两次调用是不是同一个 prompt"的可比性和"prompt 有多长"的量纲。删掉就没法回答"是不是同一个 prompt 反复重试"。hash 取前 16 hex（64 bit）对这个用途够了。而 Class C 用 HMAC 而不是裸 hash，是因为 threadId/invocationId 这种 ID 空间小、可枚举，裸 hash 能被彩虹表反查，加 salt 才行。salt 从 `TELEMETRY_HMAC_SALT` 读，dev/test 用固定值 `'dev-only-insecure-salt'`。

### 3.5 `pre-merge-gate-guard.mjs` 的系统压力预检

这个脚本被 gate Step 0 调用，做三件事【源码】：

1. **singleflight 锁**：`--lock-dir` 下写 `metadata.json` 记 holder pid，用 `process.kill(pid, 0)` 判活。
2. **fseventsd RSS 检查**（macOS）：`ps -axo pid=,ppid=,rss=,command=`，找 `fseventsd` 进程，RSS > `DEFAULT_FSEVENTSD_RSS_MAX_KB = 4 * 1024 * 1024`（4 GB）就阻塞 gate，并打印 `pnpm process:doctor` / `pnpm process:cleanup` 的引导。
3. **Redis 孤儿端口检查**：`lsof -nP -iTCP -sTCP:LISTEN` 过滤 `^redis`，端口在 `[6300, 65535]` 且不在 `ALLOWED_LOCAL_REDIS_PORTS = {6379, 6099, 6398, 6399, 6401}` 里的算孤儿。

`PROTECTED_REDIS_PORTS = new Set([6099, 6398, 6399, 6401])` 的注释是一段事故记录【源码】：
> "6401 must be protected too — flagging it as a killable orphan led to it being murdered alongside 6399 (CAFE-INCIDENT-20260527)."

还有一段"把硬阻塞降级成软警告"的注释，解释并发 gate 为什么不再互斥：
> "gates run in parallel safely — no shared writable state (git objects immutable, pnpm store writes are atomic hard-links, node_modules/dist/.next are per-worktree) … The old hard-block was incident-era over-defense."

而所有外部命令都可以用环境变量注入 fixture 来测：`CAT_CAFE_GATE_GUARD_PS_FIXTURE` / `_LSOF_FIXTURE` / `_REDIS_CONFIG_FIXTURE`【源码，`readFixtureOrCommand()`】——这就是 `check:pre-merge-gate` 能在 CI 里跑的原因。

```ts
function lazy<T extends object>(factory: () => T): T {
  let inst: T | undefined;
  return new Proxy({} as T, {
    get(_, prop) {
      if (!inst) inst = factory();
      return (inst as Record<string|symbol, unknown>)[prop];
    },
  });
}
```
每个 instrument 都包一层 Proxy，第一次访问属性（`.add` / `.record`）时才真正 `meter().createXxx()`。`meter()` 本身也是懒的（`_meter` 缓存）。

### 4.5 `derive-result-summary.ts` 的埋点解析算法

这是"从工具的**文本输出**里反向抽结构化埋点"的例子——因为 MCP 工具返回的是给猫看的文本，不是 JSON。

```
deriveResultSummary(normalizedToolName, content):
  1. text = extractText(content)
       string → 原样
       array  → 逐项取 c.text（或 c 本身是 string），join('\n')
       其他   → ''
  2. switch(normalizedToolName):
       'search_evidence' → withGenericErrorFallback(deriveSearchEvidence(text), text)
       'graph_resolve'   → withGenericErrorFallback(deriveGraphResolve(text), text)
       'list_recent'     → withGenericErrorFallback(deriveListRecent(text), text)
       default           → deriveGenericError(text) ?? {}
  3. withGenericErrorFallback: 专用解析出空对象时，退回通用错误识别
```

`GENERIC_ERROR_PATTERN`【源码】：
```
/^(?:error:|callback failed|callback request failed|refused:|access denied:|.*\bfailed\b|.*\berror\b|.*\brejected\b)/i
```

`deriveSearchEvidence()` 抽的东西：
- `Found\s+(\d+)\s+result` → `resultCount`；`No results found` → `resultCount=0, topScore=null`
- 文本含 `'🧭 Memory navigation'` → `nudgeEmitted=true`，否则（且已知 resultCount）→ `false`
- `\[(high|mid|low)\]` 第一次命中 → `topConfidence`
- **块作用域候选抽取**（F200）：先 `[...text.matchAll(/^\s+anchor:\s+(\S+)/gm)]` 拿到所有 anchor 及其 index，然后用相邻 index 切出 block，在 block 内再匹配 `type:` / `sourcePath:`。注释解释了为什么必须块作用域【源码】：全局正则会在某些结果块缺 `sourcePath` 时"漂移"到下一块的值。
- 含 `📎 Related directions` → 从这一节往后抽 `^\s+-\s+(\S+):` 作为 `expansionHintAnchors`（F256）

`deriveGraphResolve()` 的 anchor 正则改过一次【源码注释】：从 `[A-Za-z][\w.-]+` 拓宽到 `[\w.:/-]+`，理由是多段 anchor（`world:lexander:dragon`、`docs/decisions/019`）会被截断，而 FM-2 的选择链接依赖对 `centerAnchor` 的精确字符串匹配。

### 4.6 工具名规范化（三个函数的分工）

这是个容易在面试里被追问"重复了吧"的地方，实际三个函数职责不同：

| 函数 | 文件 | 输入→输出 | 用途 |
|---|---|---|---|
| `classifyTool(name, input)` | `tool-usage/classify.ts` | → `{category: 'native'\|'mcp'\|'skill', toolName, mcpServer?}` | ToolUsageCounter 的 Redis key 分类 |
| `isMcpToolName(name)` | `tool-usage/classify.ts` | → boolean | span-helpers 决定要不要建子 span |
| `normalizeMcpToolName(raw)` | `tool-usage/normalize-mcp-tool-name.ts` | → 裸工具名 | ToolEventLog 聚合时对齐 `search_evidence` 等 |

`classifyTool` 的判定顺序：
1. `toolName === 'Skill'` → skill，真名从 `toolInput.skill` 取，取不到用 `'unknown'`
2. `startsWith('mcp__')` → 剥 5 字符，找 `'__'`，前半是 server（Claude Code 格式）
3. `startsWith('mcp:')` → 剥 4 字符，找 `'/'`，前半是 server（Codex 格式）
4. 其余 → native

`isMcpToolName` **故意比 `classifyTool` 宽**，多认两个前缀：
```ts
return toolName.startsWith('mcp__') || toolName.startsWith('mcp:')
    || toolName.startsWith('cat_cafe_') || toolName.startsWith('signal_');
```
注释【源码】："This is intentionally wider than `classifyTool()` for span-emission purposes. `classifyTool()` returns `native` for bare prefixes, which is a F150 design choice; this helper does not change F150 behavior."

修复的是一个具体 bug（KD-40）：老的本地 `isMcpTool` 只认 `cat_cafe_`/`mcp__`/`signal_`，**漏了 Codex 的 `mcp:` 前缀**，导致 Codex 猫的 MCP 工具调用不生成 span。

`normalizeMcpToolName` 是两段剥皮：先剥传输前缀（`mcp__`/`mcp:`），再剥服务器前缀（`cat_cafe_`）。所以 `mcp__cat-cafe__cat_cafe_search_evidence` → `search_evidence`。空输入返回 `'unknown'`。

### 4.7 `computeStepSummary()` 的子树聚合

```
1. 确定 route span：
   给了 routeSpanId → 直接用
   没给 → 找所有 name==='cat_cafe.route' 的 span，
          筛出 parentSpanId 不存在于本 trace 的（不是"不在 route span 集合里"），
          按 startTimeMs 升序取第一个
   注释【源码】：A2A 链里子 route 的父是 mention_dispatch 不是父 route

2. collectSubtree(spans, rootSpanId)：
   先建 byParent: Map<parentSpanId, children[]>
   BFS 从 root 展开，结果含 root 自身

3. isRestored = 活 invocation span 数 === 0 且 restored span 数 > 0

4. agent_loop_count（isRestored 时保持 null）：
   withAttr = 活 invocation 里 typeof attributes['agent_loop.count'] === 'number' 的
   withoutAttr = 其余
   withAttr.length > 0 → sum(withAttr)，且 agentLoopPartial = withoutAttr.length > 0
   withAttr.length === 0 → 保持 null

5. tool_call_count = (name 以 'cat_cafe.tool_use ' 开头的 span 数)
                   + sum(活 invocation 的 attributes['tool.basic_call_count'])
   —— 双轨（KD-35）

6. a2a_dispatch_count = 子树内 name==='cat_cafe.mention_dispatch' 的数量

7. duration_ms = routeSpan.durationMs ?? (max(endTimeMs) - min(startTimeMs))
8. token_total = routeSpan.attributes['route.total_tokens'] ?? 0
9. error_count = status.code === 2 的 span 数（SPAN_STATUS_ERROR = 2）

            ? tool / loop : null
```

第 5 步的双轨很关键：MCP 工具是**真 span**（能数 span 数），基础工具是**属性计数器**（不建 span），所以总数必须两边相加。

### 4.8 检索评估三件套

**（a）`f163-eval-utils.ts` — NDCG@k / MRR**

```ts
export function computeNDCG(ranked: string[], relevance: Record<string, number>, k = 10): number {
  const dcg = computeDCG(ranked.slice(0, k), relevance);
  const idealOrder = Object.entries(relevance).sort(([,a],[,b]) => b-a).map(([anchor]) => anchor);
  const idcg = computeDCG(idealOrder.slice(0, k), relevance);
  if (idcg === 0) return 0;
  return dcg / idcg;
}
function computeDCG(ranked, relevance) {
  let dcg = 0;
  for (let i = 0; i < ranked.length; i++) {
    const rel = relevance[ranked[i]] ?? 0;
    dcg += (2 ** rel - 1) / Math.log2(i + 2);   // i+2 因为 log2(1)=0
  }
  return dcg;
}
export function computeMRR(ranked: string[], relevantAnchors: string[]): number {
  const relevant = new Set(relevantAnchors);
  for (let i = 0; i < ranked.length; i++) if (relevant.has(ranked[i])) return 1 / (i + 1);
  return 0;
}
```
用的是**指数增益** DCG（`2^rel - 1`），不是线性。

**（d）`QueryReplayCompare`（`domains/memory/QueryReplayCompare.ts`）**

比的是"同一个查询，当时的结果 vs 现在的结果"——回归检测。

```
replay(captureId, resolver):
  1. SELECT * FROM f163_logs WHERE id = ? AND log_type = 'search'
     没有 → throw `Capture ${captureId} not found`
  2. payload = JSON.parse(row.payload)
     校验 topKPerCollection 存在、是对象、非空 → 否则 throw "Unsupported capture format"
     校验每个 entry 都有 anchors 数组 → 否则 throw
  3. result = await resolver.resolve(query, {scope, dimension, collections, limit})
  4. allCollectionIds = Object.keys(topKPerCollection) ∪ replayGroups 的 collectionId
  5. 每个 collection 算：
       overlap  = capturedAnchors ∩ replayedSet
       added    = replayedAnchors − capturedSet
       removed  = capturedAnchors − replayedSet
  6. 全局 Jaccard = |capturedSet ∩ replayedSet| / |capturedSet ∪ replayedSet|
     union 为空时定义为 1（两边都空 = 完全一致）
```

**三者的分工**：`f163-eval-utils` 评**排序质量**（NDCG/MRR，需要人工标注的相关度分级），`RecallFixtureRunner` 评**能不能召回**（recall@k，只需要期望 anchor 的 glob），`QueryReplayCompare` 评**改动有没有让结果漂**（Jaccard，不需要任何人工标注）。第三个是最便宜的——不需要 gold label，只需要历史快照。

### 4.9 harness-eval：用 Agent 评估 Agent

`packages/api/src/infrastructure/harness-eval/` 有 2727 行（顶层 .ts）+ 8 个子目录（`a2a/` `anchor-first/` `capability-wakeup/` `domain/` `friction/` `hub/` `manual-trigger/` `memory/` `publish-verdict/` `sop/` `task-outcome/`）。测试 95 个文件。

**核心思路**：不是写断言来判定 Agent 行为对不对，而是——
1. 把遥测（traces + metrics + metrics history + trace store stats）抓下来，
2. 用**确定性代码**算出一个 `RuntimeEvalSnapshot`（`f167-eval.ts`），
3. 把 snapshot 交给一只"eval 猫"，让它写 `VerdictHandoffPacket`，
4. 猫通过 `cat_cafe_publish_verdict` MCP 工具发布裁决，工具校验 schema、建分支、开 PR。

**7 个 eval domain**【源码，`eval-cat-invocation.ts` 的 `DOMAIN_INSTRUCTIONS`】：`eval:a2a`、`eval:memory`、`eval:sop`、`eval:capability-wakeup`、`eval:task-outcome`、`eval:friction`、`eval:qc`、`eval:anchor-first`（实际 8 个 key）。

**counter 会重置但 trace 不会** → 用 trace 窗口当分母算 counter 速率会系统性低估。而且 raw snapshot YAML 里字段名是 snake_case（`counter_window`），bundle JSON 里是 camelCase（`counterWindow`），instruction 里两个都写了。

**`VerdictHandoffPacket` 的 13 个字段**【源码，`PUBLISH_VERDICT_PACKET_INSTRUCTIONS`】：
`id`（slug）/ `domainId` / `createdAt` / `phenomenon` / `harnessUnderEval` / `evidencePacket` / `dailyTrend` / `rootCauseHypothesis` / `verdict` / `ownerAsk` / `acceptanceReevalPlan` / `counterarguments` / `governance`(可选，`delete_sunset` 时必填 `cvoAcceptRequired: true`)。

`verdict` 是**分类值**：`fix` / `build` / `keep_observe` / `delete_sunset`——注释里明确写了 "(NOT a score)"。

schema 上的两个硬约束（说明作者被这两个坑过）：
- `evidencePacket.sampleTraceRefs` 必须非空，"even on no-finding packets — pass at least one metadata-only ref"
- `dailyTrend.current` / `baseline` / `threshold` 是 **Zod `record(number)`**，即"值是数字的对象"。裸数字（`current: 9`）、字符串（`"3/10"`）、null、嵌套对象都会被拒。正确写法：`current: { verdictWithoutPass: 9 }`

> **面试官追问："让 LLM 当评估者，怎么防止它瞎编？"**
> 我会说这个项目用了四招：
> ① **证据必须是 ref 不是叙述**——`evidencePacket` 四个字段全是 refs（snapshotRefs / attributionRefs / metricRefs / sampleTraceRefs），指向已提交的产物文件；
> ② **强制反方**——`counterarguments` 是必填的非空数组，逼它写"另一种解释"；
> ③ **裁决是分类不是打分**——四选一，不给"7.5 分"这种可以糊弄的输出空间；
> ④ **schema 在提交时校验**——`cat_cafe_publish_verdict` MCP 工具会拒掉形状不对的包，而不是发布后再发现。
> 但我也会承认最后的归因（root cause 的 7 分类：harness_misfit / tool_gap / environment_drift / vision_gap / translation_gap / execution_gap / taste_gap）仍然是 LLM 的主观判断，instruction 里只能写"do not fabricate attribution — if the evidence is thin, lower your confidence or say so"。

### 6.1 五个诊断 HTTP 端点（`packages/api/src/routes/telemetry.ts`）

### 6.5 怎么复现一个问题

```
现象：某只猫的某轮回复很慢 / 出错了

  3. 看 cli_session span 的 status.message（"exit code N"）和 cli.pid

  5. computeStepSummary() 给出 duration_ms / token_total / error_count

  7. 要审计时间线 → data/audit-logs/audit-<date>.ndjson，grep cat_invoked / cat_responded / cat_error
  8. 要本地日志 → data/logs/api/api.log（Pino JSON，按 module 字段过滤）
  9. 系统层面 → GET /api/telemetry/metrics（Prometheus 文本）
```

**冷启动后 trace 丢失怎么办**：`hydrateTraceStoreFromRedis()` 会扫最近 `MAX_SCAN = 500` 条消息（`zrevrangebyscore(MessageKeys.TIMELINE, '+inf', cutoff, 'LIMIT', 0, 500)`），重建 `cat_cafe.invocation.restored` 标记 span 和真时长的 `cat_cafe.tool_use` 子 span。但**层级信息会丢**——`computeStepSummary` 检测到 `is_restored=true` 就把三个 count 都返回 null。

## 7. 面试追问应对

### Q1：你们怎么测多 Agent 系统里的 CLI 子进程？

> 不真起进程，用**依赖注入 + 假 ChildProcess**。`spawnCli(options, { spawnFn })` 的第二个参数是可注入的 spawn 函数（`packages/api/test/telemetry/otel-tracing-runtime.test.js`）。测试里的 `createMockProcess()` 用 `PassThrough` 流当 stdout/stderr，用 `EventEmitter` 当事件源，并且**重写了 emit**：
> ```js
> emitter.emit = (event, ...args) => {
>   const emitted = originalEmit(event, ...args);
>   if (event === 'exit') process.nextTick(() => originalEmit('close', ...args));
>   return emitted;
> };
> ```
> 这一句是精髓——真实 Node 里 `exit` 之后才会有 `close`，mock 必须复现这个顺序，否则等 `close` 的代码会挂死。
>
> 另外还有 `packages/api/test/helpers/fake-cli-path.js` 的 `ensureFakeCliOnPath(command)`：在临时目录写一个 `#!/bin/sh\nexit 0\n` 脚本，`chmod 0o755`，然后 prepend 到 `process.env.PATH`。这是给"只需要 `which claude` 能找到"的场景用的。opencode 那条分支还专门伪造了 `opencode run --help` 的输出文本，因为代码会解析它来探测 `--auto` 参数是否可用。
>
> **加分点**：这两个 helper 都有缓存（`installed` Map / 模块级 memo），避免测试之间反复建临时目录。

### Q2：怎么测 span 的父子关系是对的？

> 用 OTel 官方的 `InMemorySpanExporter`。`otel-tracing-runtime.test.js` 顶部：
> ```js
> const exporter = new InMemorySpanExporter();
> const provider = new NodeTracerProvider({ spanProcessors: [new SimpleSpanProcessor(exporter)] });
> provider.register();
> ```
> 然后每个用例 `exporter.reset()` → 手动建父 span → 跑被测代码 → `exporter.getFinishedSpans()` → `spans.find(s => s.name === 'cat_cafe.cli_session')` → 断言 `cliSpan.parentSpanContext.spanId === parentSpan.spanContext().spanId`。
>
> 这套测试的 6 个用例覆盖了：父子关系、属性齐全（`cli.command` / `cli.arg_count` / `cli.pid` / `invocationId` / `sessionId`）、干净退出 status=OK、非零退出 status=ERROR 且 message 含 "exit code 1"、**没有 parentSpan 时不产生 span**、以及一个很有意思的**属性命名反向断言**：
> ```js
> assert.ok(!attrKeys.includes('cat_cafe.invocation_id'), 'Must not use dotted cat_cafe.invocation_id');
> assert.ok(attrKeys.includes('invocationId'), 'Must use camelCase invocationId');
> ```
> 为什么要断言"不能用带点的 key"？因为 `redactor.ts` 的 Class C 判定是 `CLASS_C_KEYS.has(key.toLowerCase())`，清单里是 `'invocationid'`。写成 `cat_cafe.invocation_id` 就**匹配不上，不会被脱敏**。所以这条断言守的是"命名必须是 redactor-safe 的"。

### Q3：怎么测并发/竞态？

> `packages/api/test/concurrent-fault-drill.test.js`（307 行）是最典型的，4 个场景 × 2 个层级（内存 store + 真 Redis）：
> - **S1 CAS 竞态**：`Promise.all([store.update(id, {status:'running', expectedStatus:'queued'}), store.update(id, {status:'canceled', expectedStatus:'queued'})])`，断言 `winners.length === 1 && losers.length === 1`（输家返回 `null`）。
> - **S2 更新 vs 删除**：删除立即发起，更新 `await new Promise(r => setTimeout(r, 0))` 后再发，断言最终 `threadStore.get(id) === null`（**删除赢了就不能被复活**）。
> - **S3 ack vs append**：投递游标不能跳过也不能重复消息。
> - **S4 幂等键竞态**：同一个 idempotencyKey 并发 create。
>
> 关键手法是**用 `setTimeout(0)` 精确控制交错点**，而不是靠随机。这样测试是确定性的。
>
> Redis 层的用例用 `redis-test-helpers.js` 的 `assertRedisIsolationOrThrow()` / `redisIsolationSkipReason()` / `cleanupPrefixedRedisKeys()`——没设 `REDIS_URL` 就跳过，设了但指向受保护端口就抛错。48 个测试文件用这套 helper。
>
> 另外还有一批专门的竞态测试：`preflight-race.test.js` / `preflight-race-integration.test.js` / `connector-router-hub-thread-race.test.js` / `proposal-concurrency.test.js` / `messages-parallel-slot-release.test.js` / `parallel-cancel-signal-isolation.test.js` / `route-parallel-result-merge-fifo.test.js`。

### Q4：路由护栏怎么测？

> `packages/api/test/agent-router.test.js` 有 3779 行，100 个 test/describe 块。手法是**把 AgentRouter 的所有依赖全 mock 掉**：
> - `createMockRegistry()`：`create()` 返回自增的 `inv-N` / `tok-N`，`verify()` 恒返回 `{ok:false, reason:'unknown_invocation'}`
> - `createMockMessageStore()`：一个数组 + 十来个查询方法
>
> 最能说明"他们真懂"的是 mock messageStore 的一段注释【源码】：
> ```js
> // Redis 模型: thread sorted set 的 score = deliveredAt ?? timestamp（markDelivered 后 score 重打）。
> // mock 也用 effective score 排序/过滤，让 R9 cross-page cursor bug 可复现。
> const score = (m) => m.deliveredAt ?? m.timestamp;
> ```
> 也就是说，**mock 刻意复现了真实 Redis 的 score 语义**（投递后 score 会被重打），目的是让一个真实发生过的跨页游标 bug 能在 mock 层被复现。这是 mock 设计的高阶用法——mock 不是"随便返回点数据"，而是"精确模拟真实存储的排序语义"。
>
> describe 分组直接对应护栏规则：`F078: Default to last replier`（没 @ 人时默认给上一个回复者）、`F078: Group mentions`（群组 mention 展开）、`#58: preferredCats candidate scope (not dispatch list)`（preferredCats 是候选范围不是派发列表——这个区分本身就是一条护栏）、`F229: Concierge thread routing (duty-cat always takes priority)`。

### Q5：为什么有测试去 grep 源码文本？这不是很脆吗？

> 确实脆，但它守的是**跨文件的时序约定**，这类约定没法用类型或运行时断言表达。
>
> `packages/api/test/telemetry/observability-coverage.test.js` 就直接 `readFileSync(resolve(__dirname, '../../src/utils/cli-spawn.ts'))` 然后：
> ```js
> assert.ok(source.includes('registerLivenessProbe(options.invocationId'), ...);
> assert.ok(source.includes('unregisterLivenessProbe(options.invocationId)'), ...);
> ```
> 以及最能说明问题的这条：
> ```js
> assert.ok(source.includes('hadError || wasAbortedWithoutError'),
>   'Pane registry condition must include wasAbortedWithoutError to prevent abort→done inconsistency');
> ```
> 守的是"三套观察系统在 abort 时必须一致"——审计日志要发 `generator_returned_without_completion`、OTel 要发 `invocation_aborted`、面板要标 crashed 而不是 done。这三件事分散在一个大文件的不同分支里，跑一次真实的 abort 场景成本很高。
>
> 全仓库这类测试大概 16 个文件（读 `src/` 文本的），其中 11 个用了 `source.includes(`。**占比很小（<1%）**，是有节制的用法。
>
> 更有意思的一类是 `harness-eval/merge-gate-provenance-contract.test.js`——它 grep 的不是代码，是**Markdown 技能文档**：
> ```js
> const mergeGate = read('cat-cafe-skills/merge-gate/SKILL.md');
> assert.ok(mergeGate.includes('Review Provenance Matrix'), ...);
> assert.ok(mergeGate.includes('headChangeCause = cloud-finding'), ...);
> assert.ok(mergeGate.includes('禁止为了 cloud P1/P2 修复 @ 本地旧 reviewer'), ...);
> ```
> 甚至有**反向断言**：
> ```js
> assert.ok(!prSignals.includes('Review 处理完: "已按 receive-review 模式处理 PR #42 ..."'),
>   'old source-blind reviewer notification template must not return');
> ```
> 这是"给 Agent 看的提示词也是被测代码"这个理念的落地——因为在这个系统里，SKILL.md 就是 Agent 的行为规范，改坏了和改坏代码一样严重。

### Q6：metric 基数怎么控？为什么不靠 code review？

> 靠 code review 会漏，所以做成了 SDK 层的硬约束。`metric-allowlist.ts` 的 `createMetricAllowlistViews()` 返回一个 View：
> ```ts
> { instrumentName: 'cat_cafe.*', attributesProcessors: [createAllowListAttributesProcessor(allowedKeys)] }
> ```
> 传给 `NodeSDK({ views })`。效果是：**不在 17 个 key 白名单里的属性会被 SDK 静默丢弃**——不聚合、不导出。所以就算有人写 `tokenUsage.add(n, { threadId })`，`threadId` 也进不了 Prometheus。
>
> 文件头注释写得很直白：`"This prevents anyone from accidentally adding high-cardinality attributes (threadId, invocationId, etc.) to metrics."`
>
> 第二道防线是 `model-normalizer.ts`：`defaultModel` 在配置里是自由字符串，直接当 label 会爆炸。`normalizeModel()` 用一个有序的 `MODEL_BUCKETS` 数组做 `includes` 匹配，11 个桶（claude-opus / claude-sonnet / claude-haiku / gpt-4o / gpt-4 / gpt-5 / o3 / o4 / gemini-2.5 / gemini-2.0 / qwen），未知归 `'other'`。
>
> **加分点**：注意顺序——`gpt-4o` 排在 `gpt-4` 前面，因为是 `includes` 不是精确匹配，`gpt-4` 会误吞 `gpt-4o`。这是有序数组而不是 Map/Set 的原因。

### Q7：`pnpm gate` 和 CI 有什么关系？为什么本地跑的比 CI 全？

> 这是这个项目最反直觉的地方：**本地 gate 比 CI 严格得多**。
>
> - CI（`ci.yml`）4 个 job：`lint`（= `pnpm check`）、`build`（shared/api/web 三个 build）、`test`（只跑 `test:public`）、`dir-size`。
> - 本地 `pnpm gate` 8 个阶段：脏工作区检查 + worktree 位置守卫 + 系统压力预检 + rebase 到最新 origin/main + frozen-lockfile 安装 + biome 版本校验 + 全量 build + **全包 tsc --noEmit（含测试文件）** + 全量 test（或 public）+ web lint + `pnpm check` + dirty-worktree 台账。
>
> CI 里没有的关键项：**rebase 到最新 main 再跑**（CI 跑的是 merge commit 但不保证 base 最新）、**tsc --noEmit 覆盖测试文件**（Next.js build 跳过 `__tests__/`，接口改了但 mock 没同步会静默过关，见脚本注释）、**全量测试**（CI 只跑 public 子集）。
>
> 为什么这么设计？我的理解是【推断】：这是个多 Agent 并行开发的仓库（多个 worktree、多只猫同时改代码），本地 gate 是"合流前的最后一道自检"，而 CI 是"公开仓库的对外承诺"。两者服务的对象不同。
>
> `write-gate-last-run.sh` 会写一个时间戳哨兵，注释说是给 pre-push 的 "Layer 4" 用的（`check-gate-freshness.sh`）——但那个脚本在这份仓库里我没找到，可能只在源仓库里有【推断】。

### Q8：`test:public` 是什么？为什么要维护一个排除清单？

> 这是开源同步带来的产物。仓库有两种形态：源仓库（有 `.claude/settings.json` 等治理产物）和公开同步产物（没有）。有些测试依赖只在源仓库存在的文件，在公开仓库里跑必然红。
>
> 解法不是"随便 skip"，而是一个**带 TTL 和 owner 的排除注册表**：`packages/api/config/public-test-exclusions.json`，41 条 entry【源码计数】，每条 7 个必填字段：`id` / `match`（正则字符串） / `category` / `reason` / `owner` / `introducedBy`（commit SHA） / `expiresOn`。
>
> `category` 的四个值就是分类学：`source_only`（依赖源仓库产物）、`private_fixture`（依赖私有 fixture）、`flaky_or_perf`（不稳或太重）、`product_regression`（**真实产品回归，正在跟踪**）。最后一类只有一条 —— `capabilities-route`，reason 写着 "must be tracked as a real product regression"。这个分类的存在意义是：**不允许把真 bug 伪装成环境问题**。
>
> `resolve-public-test-files.mjs` 的校验极其严格（见 §5 表格）：日期格式必须严格 `YYYY-MM-DD`（拒 `2026-6-23`、`never`、`2026/06/23`）、必须是有效日历日（拒 `2026-13-99`，因为 `new Date()` 会滚动）、过期即 throw、匹配不到任何文件即 throw、id 重复即 throw、正则编译失败即 throw。
>
> 而 `run-public-tests.sh` 用 shell 层兜住最后一个坑：如果解析器非零退出或返回空集，就 `exit 1` 而不是让 `node --test` 拿着空参数去遍历整棵树。注释里写了这是 codex review #2326 P1 —— 因为 `$(...)` 命令替换会吞掉退出码。
>
> **加分点**：`expiresOn` 目前大部分是 `2026-07-31`，而今天是 2026-07-26 —— **五天后这些排除项会集体过期，gate 会全红**。这是设计意图（强制定期复核），但也是个即将到来的运维事件。

### Q9：`check:followup-tails` 是干嘛的？这也算门禁？

> 这是我见过最不寻常的门禁：它扫 `git log --format=%s origin/main..HEAD` 的 commit 标题和 PR body，**发现"留尾巴"关键词就拒绝合并**。
>
> `BLOCKED_PATTERNS` 中英混合，包括 `follow-up` / `deferred` / `next phase` / `next PR` / `stub` / `will address later` / `TD` / `out of scope`，以及中文的 `MVP先上` / `留个尾巴` / `先这样` / `下次一定` / `回头(再|补|做|处理)` / `以后再` / `后续(优化|完善|补充|处理|再)` / `迭代再补`。
>
> 它守的是一条治理规则：**不允许把没做完的验收条件伪装成"后续跟进"**。
>
> 但纯正则会误伤，所以有两层豁免：
> - `EXEMPT_PREFIXES`：`^Merge`（merge 提交常带分支名如 `fix/foo-followup`）、`^docs(F\d+): add feature spec|spec follow-up|...`、`\[red\]`（TDD 红阶段提交，"stub" 是失败测试的占位符）
> - `SEMANTIC_EXEMPTIONS`：区分**编程术语**和**拖延用词**。比如 `deferred catch-up` / `deferred load` / `deferred init`（异步/惰性执行），`deferred≠resolved`（代码概念对比），`stub snowball/py_rust/fastembed`（Python 模块兼容垫片），`create X stub` / `stub X for Y`。
>
> 注释里的原话最能说明意图【源码】：`"conflate 'we wrote a stub to defer rust compilation' (implementation noun) with 'stubbed out, will do later' (procrastination verb)"`。
>
> **面试话术**：我会说这体现了一个判断——在 Agent 参与开发的项目里，最大的质量风险不是代码写错，是"看起来做完了但其实没做完"。因为 Agent 特别擅长写出一份很有说服力的"已完成"报告。所以门禁要拦的是**叙述层的谎**，不只是代码层的错。

### Q10：遥测数据丢了怎么办？为什么要 hydrate？

> LocalTraceStore 是纯内存的（`TraceSpanDTO[]` 数组），进程重启就没了。但 span 的关键指针（`traceId` / `spanId` / `parentSpanId`）在写消息时被持久化进了 Redis 的 `extra.tracing` 和 `toolEvents[].tracing`。
>
> `hydrateTraceStoreFromRedis()` 做的是**指针级恢复**：
> 1. `zrevrangebyscore(MessageKeys.TIMELINE, '+inf', cutoff, 'LIMIT', 0, 500)` 拿最近 500 条消息 ID
> 2. pipeline `hmget(detail(id), 'extra','timestamp','catId','metadata','toolEvents')`
> 3. 有 `extra.tracing` → 造一个 `cat_cafe.invocation.restored` 的 DTO，起始时间用 `ts - metadata.usage.durationMs`
> 4. 有 `toolEvents` → 调 `synthesizeToolSpansFromEvents()`，把 `tool_use` 和 `tool_result` 按 `toolUseId` 配对，造**真时长**的 `cat_cafe.tool_use {name}` span
>
> **诚实性边界（KD-41）**：配对要求四件套齐全（`type==='tool_result'` + `toolUseId` + `tracing` + `status`），并且 `endTimeMs > startTimeMs`。任何一项缺失就跳过，不造假 span。注释原话：`"Missing status falls back to legacy invocation.restored on the parent, not a fake UNSET tool span (KD-41 honesty: don't materialize what we don't actually know)"`。
>
> 而 `status: 'unknown'` 是**允许**的，映射到 OTel UNSET(0) —— 因为"调用方主动表达了歧义"和"我们不知道"是两回事。
>
> 恢复后的 trace 层级是丢的（invocation 变成扁平的 restored 标记），所以 `computeStepSummary()` 检测到 `is_restored` 就把三个 count 返回 null，UI 渲染 `—`。

### Q11：`eval:*` 那套"猫评估猫"怎么防止自欺？

> 见 §4.9 的四招（ref 而非叙述、强制反方、分类而非打分、提交时 schema 校验）。这里补三个更细的：
>
> ① **分母显式建模**。`c2.exit_checked` / `c2.void_hold_checked` 这两个 counter 存在的唯一目的就是当分母。注释里记了事故：没有分母时 attribution 会"fabricating 100%"，导致 2026-05-29 的过度升级。
>
> ② **摩擦 vs 激活的归类是产品决策**。`c1.hold_zombie_count` 归 `frictionCounts`（要报警），`c1.hold_replacement_count` 归 `activationCounts`（正常行为）。同一个物理事件（前一个 hold 被取消），按 `bucketWakeDelay()` 的桶分到两个语义完全不同的账上。改错了就会重现历史误报。
>
> ③ **`telemetryGaps` 是一等公民**。snapshot 里显式列出"这个指标我没数据，原因是 `no_counter` / `span_not_persisted` / `ttl_expired`…"，而不是给 0。eval 猫的 instruction 里也反复出现 "flag as telemetry gap"。
>
> **加分点/软肋**：`eval:anchor-first` 的 instruction 里有个双信号判定，第二个信号叫 **blindness**——"预览让猫做出了错误判断，但 token 账面上看不出来"。它的检测方式是**跨域引用**：去读 `eval:task-outcome` 的最新裁决，看 anchor 上线后任务成功率有没有变差。这本质上是相关性推断，instruction 里也承认 "F236 does NOT write to eval:task-outcome; cross-reference only"。我会说这是这套体系最薄的一环——它在用一个 LLM 的主观判断去关联两个域的时序数据。

### Q12：这个项目的质量保障哪一层最弱？

> 我会按"投入 vs 覆盖"给出这个排序：
>
> **强的三层**：
> 1. **单元/集成测试量**：api 1491 个文件约 18875 个用例，覆盖到 memory(176) / harness-eval(95) / telemetry(19) / acp(13) 等每个子域，1281 个文件是对 `dist/` 的真实导入（不是 mock 整个模块）。
> 2. **一致性门禁**：15 项 `check:*` 守的是"文档 ↔ 代码 ↔ 生成物 ↔ 环境变量"的四方一致，而且每一项都有自己的自测（`.test.mjs`）。
> 3. **脱敏/基数的强制层**：不是靠约定，是靠 OTel View + SpanProcessor 在 SDK 层拦。
>
> **弱的五层**：
> 1. **没有浏览器 e2e**。web 有 555 个组件测试，全是 jsdom + vitest，没有真实浏览器、没有真实后端。"用户点了发送，消息真的到了猫那里"这条链路没有自动化验证。
> 2. **`packages/shared` 有 17 个测试文件没人跑**。shared 的 `test` 脚本是 `vitest run`，而 `vitest.config.js` 的 `include` 只列了 6 个文件（注释说"Most shared tests use node:test and run separately via `node --test`"）——但仓库里没有任何脚本执行那个 `node --test`。这 17 个文件（`client-routing` / `connector-definitions` / `meeting` / `normalize-cat-id` / `world-types` 等）是死代码。
> 3. **11 个 `check:*` 定义了但没接入任何流程**，其中 `check:deps`（依赖环检测）和 `check:lockfile` 是有实际价值的；`check:video-new` 更严重——它指向的 `test/scripts/video-new-project.test.mjs` **在仓库里根本不存在**，跑它一定失败，但因为没人跑所以没人发现。
> 4. **测试排除清单集体在 2026-07-31 过期**。41 条 exclusion 绝大多数是同一天，到期后 `test:public` 会一次性红一大片。TTL 机制本身是对的，但同批到期意味着复核压力也是同批到来。
> 5. **`node --test --test-concurrency=1`**（public 套件）。全部串行，1491 个文件的全量测试在 gate 里是最慢的一步。`--test-timeout=60000`（api 的 test 脚本）意味着单个卡死的测试要等一分钟才被判失败。
>
> 还有一个不算"弱"但值得说的：**门禁高度依赖 macOS/Linux 特有的命令**（`ps -axo` / `lsof` / `comm` / `mktemp -d`）。Windows 上 `pnpm gate` 基本跑不了，只有 `windows-smoke.yml` 那两个测试（`cli-spawn-win.test.js` + `process-liveness-probe.test.js`）在 Windows CI 上跑。
