# 19 · 深潜：invoke-single-cat 的 3599 行——一次调用到底做了多少件事

> 这一篇只讲一个文件：`packages/api/src/domains/cats/services/agents/invocation/invoke-single-cat.ts`（3599 行，`invokeSingleCat` 一个 async generator 占了 2900 多行），以及它所在的 `invocation/` 目录（27 个文件、11123 行）。

```ts
export type AgentMessageType =
  | 'session_init'     // CLI 报出它的 sessionId
  | 'text'             // 模型输出正文
  | 'tool_use'         // 调工具
  | 'tool_result'      // 工具结果

  | 'status'           // F198 C：daemon 瞬时进度——只更新头像 tooltip，不成气泡
  | 'agent_loop';      // F153 I：纯遥测标记，永不可见
```

**这 12 个类型的分层是本章最该背下来的东西**，因为它决定了三个独立的判定：

| 类型 | 重置调用超时? | 算 `attemptHasContentOutput`? | 算 `attemptHasSubstantiveOutput`? |
|---|---|---|---|
| `text` / `tool_use` / `tool_result` | ✅ | ✅ | ✅ |
| `system_info` | ✅ | ❌ | ❌ |
| `provider_signal` / `liveness_signal` / `status` | ❌ | ❌ | ❌ |
| `error` / `done` / `session_init` | ✅ | ❌ | ❌ |
| `agent_loop` | ✅ | ❌ | ❌（且永不 push 到 outputs） |

后两列决定"能不能自愈重试"（见 §4.3）；第一列防的是"续命"——【源码】3061-3065 注释原话：

> F149: provider_signal / liveness_signal must NOT reset timeout — prevents "续命"
> F198 Phase C P2-1: status (daemon detail progress) also must NOT reset timeout — a daemon sending frequent status updates must not evade the 30-min kill deadline.

这是个真实攻击面思维：**如果心跳信号能重置超时，那一个只发心跳不干活的子进程就永远杀不掉。** 我（安全背景）在面试里会主动把这一条拎出来讲——它本质是"keep-alive 不得延长 deadline"，和 13 章 MCP 桥的 keep-alive 设计是同一套判断。

### 3.2 ③④ invocationId、callbackToken 与两层超时（769-815）

```ts
const { invocationId, callbackToken } = await registry.create(
  userId, catId, threadId, params.parentInvocationId, params.a2aTriggerMessageId,

```

这一对就是 13 章 MCP 回调桥的**身份凭据**：子进程拿着它们回调 API 才能证明"我是这次调用"。`parentInvocationId` 和 `a2aTriggerMessageId` 是链路血缘（谁触发的我）。

紧接着的 triggerType 派生是个漂亮的三元链：

```ts
const triggerType = params.a2aTriggerMessageId ? 'mention'
                  : params.parentInvocationId ? 'routing'
                  : 'default';
```
【源码】778

**两层超时的关系是本节重点**：

```ts
const INVOCATION_TIMEOUT_MULTIPLIER = 2;
const cliTimeoutMs = resolveCliTimeoutMs(undefined);
const invocationTimeoutMs =
  (cliTimeoutMs > 0 ? cliTimeoutMs : DEFAULT_CLI_TIMEOUT_MS) * INVOCATION_TIMEOUT_MULTIPLIER;
```
【源码】784-787

- **内层**：CLI 超时（Provider 层管，NDJSON 流空闲判定）
- **外层**：调用级硬超时 = 内层 × 2

为什么要 ×2 而不是相等？注释写了：`Must be > CLI_TIMEOUT_MS to avoid racing the inner timeout.`——两个超时如果同时到，你不知道错误消息会是哪一个，诊断信息会丢。**外层留出一倍余量，保证"内层先报，外层兜底"的顺序是确定的。**

还有一个边界：`CLI_TIMEOUT_MS=0` 是"禁用 CLI 超时"的开关，但调用级超时**不允许被禁用**——回退到 `DEFAULT_CLI_TIMEOUT_MS`（30 分钟）。**「可以关掉内层，但绝不能没有天花板」**。

超时用的是 `setTimeout` + `unref()`，而且是**可重置**的：

```ts
const resetInvocationTimeout = (): void => {
  if (invocationTimer) clearTimeout(invocationTimer);
  invocationTimer = setTimeout(() => {
    log.error({...}, 'Invocation hard timeout fired');
    invocationAc.abort(new Error('invocation_timeout'));
  }, invocationTimeoutMs);
  invocationTimer.unref();
};
```
【源码】790-797

`unref()` 的意思是"这个定时器不阻止 Node 进程退出"。忘了写它的话，进程关不掉。

然后是信号合并：

```ts
const signal: AbortSignal | undefined = callerSignal
  ? AbortSignal.any([callerSignal, invocationAc.signal])
  : invocationAc.signal;
```
【源码】801-803

注释：`Merge caller signal (user cancel) with invocation timeout — neither loses semantics.` `AbortSignal.any` 是 Node 20+ 的 API，用它比手写 `addEventListener` 转发要干净得多——**而且 abort reason 会保留原始那个**，所以下游能区分"用户取消"和"超时"。

### 3.4 ⑦ session 解析的四道处理（1025-1157）

这一段是全函数最容易讲出深度的地方。目标只有一个：**决定这次 CLI 要不要带 `--resume <sessionId>`，带哪个。**

**第一道：读，但允许失败**

```ts
let sessionId: string | undefined;
try {
  sessionId = await preflightRace(sessionManager.get(userId, catId, threadId), 'sessionManager.get', signal);
} catch (err) {
  log.warn({...}, 'Session get failed (timeout or Redis), proceeding without');
}
```
【源码】1025-1031

`preflightRace` 是 `invoke-helpers.ts` 里的纯函数（后面 §4.1 细讲）。这里的判断是：**Redis 读失败不该让整次调用失败，退化成"新会话"就行**——丢上下文是可恢复的，卡死不是。

**第二道：封板短路（R8 P1）**

```
// R8 P1: Read-side short-circuit — if sessionChainStore has sealed/sealing sessions
// but NO active session, the previous session was sealed. Discard the persisted CLI
// sessionId to prevent --resume into a sealed session. This eliminates the race
// window between fire-and-forget delete and next get().
```
【源码】1033-1045

这里有三条叠加的修复注释（R8 P1 / R11 P1-1 / F33-fix），拼出来的完整判断是：

- `sessionManager` 里的值**可能是脏的**（session_init 更新了 chain 记录但没回写 sessionManager）→ **active 记录里的 cliSessionId 才是权威值**（R11 P1-1）
- 链非空但没有 active → 上一个被封板了 → 丢掉 sessionId（R8 P1）
- **即使 `sessionManager` 返回空也要查链**——因为 PATCH bind 端点只写 chain 不写 sessionManager（F33-fix）

最后的兜底注释是全函数里我最喜欢的一句：

> If we can't verify chain state, it's safer to start fresh than risk `--resume` into a sealed session. **Lost resume is recoverable; sealed-session corruption is not.**
> 【源码】1124-1128

**这句话是可以直接搬进面试的取舍模板**：两个失败模式比大小，选可恢复的那个。

**第三道：reborn 策略（#836）**

```ts
let isReborn = false;
try {
  isReborn = threadStore.isRebornSession
    ? await preflightRace(..., 'isRebornSession', signal)
    : false;
} catch (rebornErr) {
  log.warn({...}, '#836: isRebornSession lookup failed pre-invoke, defaulting to non-reborn');
}
if (isReborn) { sessionId = undefined; }
```
【源码】1189-1207

有的 thread 配成"每轮都开新会话"。注意注释：`Optional chaining: test mocks may omit isRebornSession (absent = false)` + 独立 try/catch，理由是 `a transient Redis failure must not skip workspace resolution below`——**如果这个 try 包大了，Redis 抖一下会顺带跳过后面的工作区解析。** 这种"try 块边界要按补偿语义划，不按代码相邻性划"的细节，是真读过代码才说得出来的。

**第四道：SessionMutex（F118）**

```ts
const mutexKey = isBgCarrier && bgChainKey ? bgChainKey : sessionId;
if (mutexKey) {
  try {
    sessionMutexRelease = await sessionMutex.acquire(mutexKey, signal);
  } catch (err) {
    if (signal?.aborted) { /* yield done, didComplete = true, return */ }
    throw err;
  }

```
【源码】1136-1157

模块级单例 `const sessionMutex = new SessionMutex();`（181 行），**按 sessionId 粒度串行化**。为什么需要：两个请求同时 `--resume` 同一个 CLI 会话，CLI 那边的 JSONL rollout 会写坏。

`bg carrier` 的特殊处理值得单独记（F198 Bug #3）：bg 守护进程**每轮 `--bg --resume` 都会 fork 出新 UUID**，所以 sessionId 是滚动的，拿它做 mutex key 等于没锁。解法是派生一个稳定锚点：

```ts

const bgChainKey = isBgCarrier ? `bg:${threadId}:${catId}` : undefined;
```
【源码】766-767

**"排队时被取消"不是错误**——干净退出并且置 `didComplete = true`，这样 finally 里的兜底审计不会误报成 error（见 §3.9）。

### 3.5 ⑧ workingDirectory 与三道 preflight（1159-1404）

**workingDirectory 的四条来源**（优先级从上到下）【源码】1208-1244：

### 3.7 ⑩ effectivePrompt 的四层 prepend（1873-1926）

先算"要不要注入静态身份"：

```ts
  lastStaticIdentityRevision !== registryRevision;
```

【源码】1873-1885

**四个 OR 条件的含义**：

第 4 条是个很细的正确性考虑：热改配置后，一个正在 resume 的会话里那只猫**还活在旧身份里**。用一个单调 revision 号比对就解决了。

> Injection method: prepend to prompt string (universal, all CLIs).
> **`--append-system-prompt` proved unreliable (cats didn't receive content).**
> Codex/Gemini AgentServices also prepend if `options.systemPrompt` is set, so we intentionally do NOT pass systemPrompt in options to avoid double injection.
> 【源码】1869-1872

**"官方参数试过，不可靠，退回字符串拼接"** + **"下游也会拼，所以这里故意不传 options.systemPrompt 防重复"**。第二句是那种只有踩过才知道的坑。

然后是**四层 prepend，顺序固定**【源码】1896-1926：

```
[contextHintPrefix]     ← F225 上下文管理软提示（上一轮排队的）

[missionPrefix]         ← F070 外部项目任务上下文

```

两处注释都在强调**同一件事**：

```

```
```

// (independent of injectSystemPrompt).
```

【源码】1903-1919

**为什么不把 staging 折进 staticIdentity？** 注释直接给了 review 记录：`Cloud R2 P1 #2237 L1099: folding into staticIdentity would let resumed session-chain turns drop staging`。折进去 = resume 时被一起跳过 = 契约破了。

### 3.8 ⑪ processMessage：消息处理管线（2037-2921）

`processMessage(msg) → AgentMessage[]` 是个**一进多出**的纯度较高的函数（有 IO，但没有控制流副作用）。输入一条 provider 消息，输出零到多条要 yield 的消息。

外面套了一层 generator 适配：

```ts

  for (const out of await processMessage(sourceMsg)) { ... yield out; }
};
```
【源码】2923-2925

主流程里所有 yield 都走这个包装，**唯一入口**保证了每条消息都被同样处理（任务进度持久化、invocationId 附加）。

**四个主要分支：**

**(a) `error` → 只记状态，不拦截**（2378-2381）

```ts

```

**(b) `session_init` → 绑定会话**（2383-2445）

普通猫走 `getActive()`，bg carrier 走 `getByChainKey()`。bg 分支的注释解释了一个真实的记忆丢失 bug：

> bg: look up the conversation by its stable chainKey. ACTIVE record → just update cliSessionId to the current daemon shortId (**NO seal+create — that cascade is the multi-turn amnesia root cause**). Missing (first round) OR externally sealed → create a fresh record carrying the chainKey; the index re-points to it and the sealed record is NOT revived.
> 【源码】2407-2413

**"multi-turn amnesia root cause"**：bg 每轮换 UUID，原来的逻辑看到"sessionId 变了"就封板+建新记录，于是每轮都是新会话，猫每轮都失忆。修法是识别出"这是同一个对话的 UUID 轮换"而不是"换了会话"。

ACP 也有类似的特判：

```ts

  // ACP transport: sessionId is per-invocation (newSession() each time).
  // This is normal — NOT a "session replaced" event. Just update the tracked ID.
```
【源码】2450-2452

**同一个现象（sessionId 变了）在三种载体下有三种含义**：普通 CLI = 会话被换了（要封板）；bg = UUID 轮换（不动）；ACP = 每次调用都新建（不动）。所以协议层加了 `ephemeralSession` 布尔位让 Provider 自己声明语义，而不是让上层猜。**这是"让知道的人说，不让不知道的人猜"的接口设计。**

**(c) `done` → 结算**（2620-2810）

- 审计类型按 `hadStreamError` 二选一：`CAT_ERROR` / `CAT_RESPONDED`（2624）
- `messageCount` 自增，注释说明了它为什么关键：

> This counter is critical for unseal safety: **empty sessions (0 messages) can be displaced, but sessions with user-visible output must not be silently sealed or folded away** before a final done event arrives.
> 【源码】2643-2646

- 用 `userVisibleOutputCountedSessionIds` 这个 Set 做**同轮去重**——流中途已经数过就不再数（2655、2676）
- push `invocation_metrics` 给前端状态面板（2691-2702）
- F070 执行摘要回流（2704-2721）

**(d) usage / context_health → 封板判定**（2057+）

这段被抽成了闭包 `processUsageAndContextHealth(msg, { deferSealForMidStream })`，注释记录了它为什么被抽出来：

> clowder#915 (cloud P1): F8/F24 usage + context_health block extracted so it can run from BOTH the `done` branch AND the `agent_loop` branch (NEW — **opencode's step_finish event carries mid-stream token usage via agent_loop**). Before this extraction, the agent_loop's early-return at L2322 **silently dropped usage → no context_health → no seal → no handoff → opencode CLI hung at context limit.**
> 【源码】2040-2046

**这是一条完整的因果链 bug**：一个 early-return 吃掉了 usage → 一路传导到"CLI 在上下文上限处挂死"。面试里讲"你排查过最长的因果链"，这个例子有五跳。

而 `deferSealForMidStream` 这个参数本身是第二个修复：

> R4 cloud P1 #3 (defer seal): when a mid-stream agent_loop crosses the seal threshold, we capture the seal intent here instead of firing requestSeal inline. The actual seal is executed at the `done` event boundary, **so post-seal text/tool events in the SAME opencode invocation (tool-loop tail) still find an active SessionRecord via getActive() and write to transcript normally.**
> 【源码】1998-2006

**中途封板会让同一次调用尾部的事件找不到会话记录**，所以改成"记下意图，到 done 边界再执行"。这是个很典型的**"副作用要在事务边界执行，不能在流中间执行"**的判断。

### 3.9 ⑫ 重试循环与六类错误抑制（3033-3452）

外层是个最多两次的 for 循环：

```ts
const maxAttempts = 2;
let allowSessionRetry = Boolean(sessionId);
let allowTransientRetry = true;
for (let attempt = 0; attempt < maxAttempts; attempt++) {
  const options: AgentServiceOptions = { ...(sessionId ? { sessionId } : {}), ...baseOptions };
  // 六个 suppressed* 变量
  const serviceIter = service.invoke(effectivePrompt, options)[Symbol.asyncIterator]();
  for (;;) {
    const iterResult = await abortableNext(serviceIter, signal);
    if (iterResult.done) break;
    // ...
  }
}
```
【源码】3031-3057

自愈策略的三条原始注释（后来长到六类）：

```
// Self-heal policy (at most one retry total):
// 1) stale --resume session: "No conversation found with session ID ..."
// 2) poisoned --resume session: "prompt token count ... exceeds the limit ..."
// 3) transient CLI bootstrap exit: "CLI 异常退出 (code: 1, signal: none)"
```
【源码】2986-2989

**为什么不用 `for await`：**

```ts
// F089: Use abortableNext instead of `for await` so the invocation timeout
// can break out even when the service generator is stuck on an unresolvable await.
```
【源码】3054-3055

`for await` 会阻塞在 `gen.next()` 上，**没有任何办法打断**。所以手写了：

```ts
function abortableNext<T>(iter: AsyncIterator<T>, signal: AbortSignal): Promise<IteratorResult<T>> {
  if (signal.aborted) return Promise.reject(signal.reason ?? new Error('aborted'));
  return new Promise<IteratorResult<T>>((resolve, reject) => {
    const onAbort = (): void => reject(signal.reason ?? new Error('aborted'));
    signal.addEventListener('abort', onAbort, { once: true });
    iter.next().then(
      (result) => { signal.removeEventListener('abort', onAbort); resolve(result); },
      (err) => { signal.removeEventListener('abort', onAbort); reject(err); },
    );
  });
}
```
【源码】188-205

**注意两个分支都 `removeEventListener`** —— 不摘监听器的话，一次长会话下来 signal 上挂几千个回调，内存泄漏。这是个很好的"看细节功底"的点。

**六类错误抑制表**（这是本章第二个必背表）：

| # | 判定函数 | 触发条件（额外门槛） | 处理 |
|---|---|---|---|
| 1 | `isMissingClaudeSessionError` / `isSessionNotFoundDiagnostic` | `allowSessionRetry` | 丢 session 重试 |
| 2 | `isPromptTokenLimitExceededError` | `allowSessionRetry` **且无内容输出** | 丢 session 重试 |
| 3 | `isContextWindowOverflowError` | 同上 | 丢 session 重试 |
| 4 | `isTransientCliExitCode1` / `isTransientAcpPromptFailure` | `allowTransientRetry` 且无内容输出 | **原样重试**（保留 session） |
| 5 | `isCliTimeoutError` | `allowSessionRetry` 且有 sessionId 且**无实质输出** | 丢 session 重试（#774） |
| 6 | `isMalformedToolCallError` | 无内容输出 | **封板** + 无 session 重试（F215） |

**"无内容输出"这个门槛为什么关键**，第 6 类的注释说得最透：

> P1 7th fix: only suppress malformed error (and retry) when NO content was emitted yet. ... Without this guard, a multi-step run that used a tool then ended with a malformed turn **would re-run the original prompt from scratch — duplicating tool actions.**
> 【源码】3142-3145

**重试 = 重放。如果上一次已经动过手（写过文件、发过请求），重放就是重复副作用。** 所以"已经有内容输出"必须禁止重试。这条判断是所有带副作用的重试逻辑的通用原则，面试里非常好用。

而第 5 类用的是 `attemptHasSubstantiveOutput` 而不是 `attemptHasContentOutput`，因为 `timeout_diagnostics`（system_info）不该阻止重试（3108-3111）。**两个近似的布尔量，差别只在 system_info 算不算**——这种精度是被 bug 逼出来的，注释里那条 F215 hotfix 记录了原因：

> Bug: system_info from rate_limit_event precedes malformed turn → sets attemptHasContentOutput=true → malformed suppress guard fails → seal/fresh-retry/46接力 all skipped → **bare malformed error leaks to user.**
> 【源码】3264-3270

**抑制的机制**（这是最巧的一段）：

```ts
if (allowSessionRetry && msg.type === 'error' && isMissingClaudeSessionError(msg.error)) {
  suppressedMissingSessionError = msg;
  continue;          // ← 不 yield，先扣下
}
// ...
if (suppressedMissingSessionError || ...) {
  if (msg.type === 'done') {
    shouldRetryWithoutSession = Boolean(...);
    break;           // ← 等到 done 才决定要不要重试
  }
  // done 之前又来了别的消息 → 说明流还在继续 → 把扣下的错误放行
  if (suppressedMissingSessionError) { yield ...; suppressedMissingSessionError = undefined; }
}
```
【源码】3073-3246

**逻辑是："先扣下错误，等到 `done` 事件才判断这是不是终局错误。如果 done 之前流又活了，说明不是终局，把扣下的错误放行。"** 这个模式很值得记——**流式协议里，"是不是最终错误"只有在流结束时才知道。**

**重试前的六件事**【源码】3320-3349：

```ts
await sessionManager.delete(userId, catId, threadId);         // 1 删 session
// 2 consecutiveRestoreFailures++（F118 AC-C6）
sessionId = undefined;                                        // 3
delete baseOptions.cliSessionId;                              // 4 防诊断误归因
if (params.systemPrompt && !baseOptions.systemPrompt) {        // 5 补回身份注入
  baseOptions.systemPrompt = params.systemPrompt;
}

```

第 5 条注释：`F-BLOAT P1: self-heal drops session → retry is now a fresh session. Must re-inject systemPrompt since baseOptions may have omitted it when the original attempt was a resume.` **自愈把 resume 降级成新会话，所以 §3.7 那套注入判定的结论失效了，得补。** 这种"状态变了、之前算好的决策要重算"的 bug 最难发现。

**兜底：Opus 4.8 炸毛卡片（F215 AC-C3）**

两次都 malformed 之后，吐三条消息 + 一条合成的 done【源码】3394-3450：

1. 用户可见 `text` 卡片（中文人话解释 + 折叠技术细节 + 明确"不是猫咖的问题"，附 Anthropic issue #49747）
2. 内部路由信号 `malformed_toolcall_relay_46` —— route-serial 消费它，把 opus-4.6 推进 worklist
3. 显式 `error`（AC-D1：`Explicit final error (not silent empty return)`）
4. **合成 `done`** —— 注释：`provider's done was consumed by the suppression path (continue). Without this, route-serial's doneMsg stays null and direct consumers never receive the terminal signal.`

## 4. 关键算法与判定逻辑

### 4.1 `preflightRace`：给所有前置 IO 加天花板

【源码】invoke-helpers.ts:139-184

```ts
export const PREFLIGHT_TIMEOUT_MS = Number(process.env.CAT_CAFE_PREFLIGHT_TIMEOUT_MS) || 30_000;

export async function preflightRace<T>(promise: Promise<T>, label: string, signal?: AbortSignal): Promise<T> {
  if (signal?.aborted) throw signal.reason;
  let timer: ReturnType<typeof setTimeout> | null = null;
  const cleanup = (): void => { if (timer) clearTimeout(timer); };
  const timeoutPromise = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`preflight_timeout: ${label}`)), PREFLIGHT_TIMEOUT_MS);
    // Keep the process alive until the preflight guard actually fires.
    // Unref'ing this timer lets Node exit early when the raced promise never settles.
  });
  const parts: Promise<T | never>[] = [promise, timeoutPromise];
  if (signal) {
    parts.push(new Promise<never>((_, reject) => {
      signal.addEventListener('abort', () => reject(signal.reason), { once: true });
    }));
  }
  return Promise.race(parts).finally(cleanup);
}
```

存在理由的注释写得极清楚：

> Without this guard, a hung Redis/store operation blocks the generator indefinitely — **the finally block never runs, InvocationTracker never clears, and the thread is permanently "busy."**
> 【源码】invoke-helpers.ts:130-133

**"thread 永久 busy"是这个系统里最难受的故障态**：用户看到猫在转圈，但什么都不会发生，也没法取消。根因是 generator 卡在一个不会 settle 的 await 上，`finally` 永远不执行。

两个细节：

1. **`label` 参数**：错误消息是 `preflight_timeout: sessionManager.get`，直接指出卡在哪一步。调用点有四处（`sessionManager.get` / `threadStore.get` / `isRebornSession` / 会话链查询）。
2. **这里的 timer 故意不 unref**（和 §3.2 的调用超时相反！）。注释解释了：`Keep the process alive until the preflight guard actually fires. Unref'ing this timer lets Node exit early when the raced promise never settles.` —— **如果 unref 了，Node 会在"被 race 的 promise 永不 settle"时提前退出，守卫就白设了。** 同一个 API 在两个地方要相反的用法，这种对比是很好的面试素材。

`Promise.race` 的三方参与者：原 promise / 超时 / abort。注意 **原 promise 不会被取消**（注释：`The original promise is NOT cancelled (no way to do so generically)`）——它还在后台跑，只是没人等它了。**这是 JS 里 race 的固有限制，诚实地写在注释里而不是假装解决了。**

**(a) Gemini 的收窄**

**(c) 上下文溢出不算瞬时错误**

```ts

  // writes the same user turn into the rollout JSONL again (see bug-report
  // 2026-04-19-codex-transient-retry-context-overflow).
```

**这三条是我在面试里会主动讲的一组**，因为它们指向同一个抽象结论：**错误分类的正确性 = 正则的精度。分类错了不是"没修好"，是"往错误的方向自愈"，比不自愈更糟。**

**(d) 跨层诊断：`isSessionNotFoundDiagnostic`**


### 4.5 `getOpenCodeKnownModels`：进程级缓存 + 静默失败

【源码】116-147

```ts
let _openCodeKnownModels: Set<string> | null = null;

export function getOpenCodeKnownModels(): Set<string> {
  if (_openCodeKnownModels !== null) return _openCodeKnownModels;
  try {
    const opencodePath = resolveCliCommand('opencode');
    if (!opencodePath) { _openCodeKnownModels = new Set(); return _openCodeKnownModels; }
    const stdout = execFileSync(opencodePath, ['models'], {
      encoding: 'utf-8', timeout: 5000, stdio: ['ignore', 'pipe', 'ignore'],
    });
    _openCodeKnownModels = new Set(stdout.trim().split('\n').map((line) => line.trim()).filter(Boolean));
  } catch {
    _openCodeKnownModels = new Set();
  }
  return _openCodeKnownModels;
}
```

四个细节：`null` 表示未初始化 / 空 Set 表示"查过了但没有"（**区分"没查"和"查了是空"**）；`timeout: 5000`；`stdio: ['ignore','pipe','ignore']` 吞掉 stderr；catch 里也赋空 Set（**失败也算查过，不重试**）。

**这是"用子进程当配置源"的最小实现。** 值得注意的是它同步阻塞（`execFileSync`）——在 Node 服务里同步调子进程是要挨骂的，但因为有缓存所以只在进程内第一次调用时发生一次，5 秒上限。**这是"明知不优雅但影响可界定"的实用主义取舍**，比起改成异步要传染一整条调用链，这里选了简单。面试里这样讲比装作没看见强。

## 5. 边界情况与防御性代码清单

| 边界 | 代码 | 处理 |
|---|---|---|
| Redis 读 session 超时 / 挂 | `preflightRace(..., 'sessionManager.get', signal)` catch | 退化成新会话，不中断 |
| Redis 写 session 失败 | `sessionManager.store(...)` catch | 只打 warn，会话链继续 |
| session 排队时用户取消 | `sessionMutex.acquire(mutexKey, signal)` catch + `signal?.aborted` | 干净退出，`didComplete=true`，不算 error |
| 工作区路径无效（永久） | `validateProjectPathDetailed` 返回 `ok:false, reason:'invalid'` | 报错文案含"怎么修"，不重试 |
| 工作区路径 IO 错误（瞬时） | 同上，`reason:'io_error'` | 报错文案含"请重试" |
| 游戏 thread 虚拟 projectPath | `projectPath.startsWith('games/')` | 跳过工作区解析 |
| bootcamp 工作区解析失败 | `resolveBootcampWorkspaceRoot().ok === false` | 记 `bootcampWorkspaceError`，后续流程处理 |
| 代理服务器不在线 | `tcpProbe('127.0.0.1', proxyPortNum)` 返回 false | 降级直连，warn |
| OpenCode 配置目录清理失败 | `rm(openCodeRuntimeConfigDir)` catch | 打 warn，不中断 |
| `finally` 里 `sessionMutexRelease` 为 undefined | `?.()` 调用 | 幂等，安全 |
| generator 被 `.return()` 掐断 | `!didWriteAudit && !hadError && !didComplete` | 兜底 CAT_ERROR 审计 |
| Opus 4.8 malformed 两次都失败 | retry 耗尽 + `suppressedMalformedError` | 吐卡片 + 路由信号 + 合成 done |
| 云猫（ChatGPT Pro）没有 CLI | `provider === 'openai-chatgpt-pro'` | fire-and-forget 桥，直接 yield done |
| bg carrier UUID 轮换 | `isBgCarrier && bgChainKey` 分支 | 用 `chainKey` 而非 `sessionId` 做一切键 |
| 重试前身份未注入 | `params.systemPrompt && !baseOptions.systemPrompt` | 补回 `systemPrompt` |
| ToolSpan 没有 tool_result | `finally: toolSpanTracker.endAllOrphans('aborted')` | 防止 span 永不结束 |
| 任务进度状态降级（完成后 abort） | `finalizedTaskProgressStatus === 'completed' && status === 'interrupted'` | return，拒绝降级 |
| preflight 超时后原 promise 继续跑 | （无操作）注释：`The original promise is NOT cancelled` | 副作用不可撤，接受这个限制 |

**三个"知道做不到但诚实承认"的地方**（反而是面试亮点）：

1. **`preflightRace` 不能取消原 promise**——JS 无通用 cancel 机制，注释里说清楚了。
2. **`_needsReinjection` 是进程内内存**——多实例部署时补注会丢，项目现在是单机所以接受。
3. **`getOpenCodeKnownModels` 同步阻塞**——只发生一次，影响可界定，没改成异步。

| `CAT_RESPONDED` | 流里收到 `done` 且 `!hadStreamError` |
| `CAT_ERROR` | ① catch 块（`hadError=true`）/ ② `done` + `hadStreamError` / ③ finally 兜底 |

**注意 `CAT_ERROR` 有三个来源** —— 事后看事件流时，`didWriteAudit` 防止 ①③ 重复写，但 ②（流里报错但还能走到 done）走的是 processMessage 里的分支，和 ① 路径不重叠。

### 6.3 遥测 Instruments（OTel）

| Instrument | 类型 | 触发 |
|---|---|---|
| `catInvocationCount` | Counter | 调用创建时，按 `triggerType`（mention/routing/default）分 |
| `activeInvocations` | UpDownCounter | try 入口 +1，finally -1 |
| `invocationDuration` | Histogram | finally，秒 |
| `invocationCompleted` | Counter | finally，按 `status`（ok/error）|
| `catResponseDuration` | Histogram | finally，秒 |
| `threadDuration` | Histogram | finally，从 `thread.createdAt` 算，有值才记 |
| `llmCallDuration` | Histogram | processMessage 里，从 `done.metadata.durationMs` 读 |
| `tokenUsage` | Counter | processMessage 里，`input_tokens` + `output_tokens` 分开记 |
| `sessionRounds` | Histogram | 每次 `messageCount` 自增时 |
| `geminiContextFallback` | Counter | Gemini 的 context window fallback 路径 |

**`invocationDuration` 和 `llmCallDuration` 的差**：前者含所有 preflight；后者只含"provider 实际跑了多久"（从 provider 的 `done.metadata.durationMs` 读）。两者相减 ≈ 本文讲的这一切"前置工作"的开销。

## 7. 面试追问应对

**Q: 最复杂的一段代码是哪里？怎么理解它？**

A: `invoke-single-cat.ts` 的 `invokeSingleCat`，3599 行，一个 generator 函数。它是全项目所有"跟真实世界打交道的脏活"的汇聚点，按照我的理解分成 12 个阶段：云猫短路、invocationId 注册、两层超时合并、session 四道解析（Redis 读 + 封板检查 + reborn + mutex）、三道 preflight（工作区 / 共享态 / 治理）、账号凭据注入、effectivePrompt 四层 prepend、消息处理管线、两次重试 + 六类错误抑制、catch 审计、finally 八项补偿。每一段都能单独说出"它为什么这么复杂、它防的是哪种真实故障"。

**Q: generator 被 `.return()` 掐断怎么处理？**

A: `finally` 块用三个标志位的组合识别这条路：`!didWriteAudit && !hadError && !didComplete`。正常完成置 `didComplete`，catch 里报错置 `hadError + didWriteAudit`，干净退出（排队时取消）也置 `didComplete`——三个都不置就是被掐了，写兜底审计 `generator_returned_without_completion`。这是全函数里我认为最精妙的一处，因为它把"一个 generator 的三条出口"用三个布尔量完整覆盖了。

**Q: 为什么要用 `abortableNext` 而不是 `for await`？**

A: `for await` 会永久阻塞在 `gen.next()` 上，没有任何办法打断。`abortableNext` 把 `gen.next()` 和 AbortSignal 赛跑，信号先到就 reject，并且在两个分支都 `removeEventListener`——不摘监听器的话长会话会挂几千个回调，内存泄漏。这是 JS 里"如何取消正在等待的 async iterator"的一个完整答案。

**Q: 重试逻辑的核心判断是什么？**

A: 关键门槛是 `attemptHasContentOutput` 和 `attemptHasSubstantiveOutput`——有内容输出时不允许重试，因为重试 = 重放 prompt，会重复副作用。六类错误对这个门槛的依赖各不相同：session 类的三个都要求无内容输出；malformed 也是；只有瞬时 CLI 退出允许有 system_info 存在（不算"内容"）。用两个布尔量区分"真正的内容"和"系统信号"，这个区分是被 F215 hotfix 逼出来的。

**Q: session 解析为什么这么复杂？**

A: 四道处理里面，我认为最有价值的一条判断原则是注释里那句：*"Lost resume is recoverable; sealed-session corruption is not."* 两个失败模式比大小，选可恢复的。Redis 读不到、chain 对不上、reborn 策略——每一道都是在解决"resume 进错会话比不 resume 更糟"这个问题。mutex 那道是解决"两个请求同时 resume 同一个 CLI 会话会写坏 rollout JSONL"——这个不加锁的话是必现的并发 bug，不是概率问题。

**Q: 你说子进程会超时，那超时怎么设计的？**

A: 两层。内层是 CLI 超时（Provider 管，NDJSON 流空闲判定），外层是调用级硬超时 = 内层 × 2。两层分开是为了保证"内层先报错、外层兜底"的顺序是确定的。有三类消息不重置外层超时：`provider_signal`、`liveness_signal`、`status`——不重置的原因是防止"只发心跳不干活"的子进程续命。硬超时用的 `AbortSignal.any([callerSignal, invocationAc.signal])` 合并了用户取消和超时两个信号，两个都能打断，而且 reason 保留，下游能区分。

**Q: effectivePrompt 怎么组装的？**

A: 四层 prepend + 一个尾部 append。每一层都有独立的注入条件，最重要的是要区分"只在新会话注入"（staticIdentity）和"每轮必注入"（staging / contextHint / missionPrefix）——前者在 resume 时跳过，后者不能跳过。两类"每轮必注"还要独立于 `injectSystemPrompt` 判定，因为 `injectSystemPrompt=false`（resume 跳过身份）时它们仍然需要在场。这个区分是被 ADR-038 的"每轮注入生效"契约和 F225 的"压缩后补提示"两个需求共同逼出来的。

**Q: 这里有什么安全隐患？**（我的安全背景）

A: 我看到三处值得关注：①callbackEnv 把 `CAT_CAFE_CALLBACK_TOKEN` 传给子进程——这是设计需要，但 token 的有效期和轮换机制要看 `InvocationRegistry`，如果 token 不过期且可重放就有问题；②账号凭据（API key）通过 `callbackEnv` 传环境变量——子进程可以通过 `/proc/self/environ` 或日志泄露，`maskEnv` 这个函数在 debug 日志里会遮掉值（3024），但只有 debug 级才走，生产 info 日志里呢？③ `workingDirectory` 用了 `validateProjectPathDetailed` 验证，防的是路径遍历，但允许的 root 范围够严格吗？这些是我实际研究后的怀疑，不一定是真洞，需要进一步看。
