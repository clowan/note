## 0A. 零后端基础补课：先把 `invokeSingleCat` 翻译成人话

> 这一部分是旧版集中导读。它没有按正文小节解释，第一次阅读可跳过；本轮真正的白话解释从第 1 节开始，并放在每个原小节内部。

### 0A.1 这不是“调用模型的函数”，而是一次调用的总协调器

对本项目来说，一次 Agent 调用并不是 `prompt → answer` 两步，而是：

```text
选中的猫 + prompt + thread
  → 注册 invocation，拿调用 ID 和回调凭证
  → 找到或创建 CLI session
  → 确定工作目录和账号
  → 准备环境变量、MCP 与超时
  → 启动 Provider/CLI 子进程
  → 一条条转发输出
  → 正常、失败或取消后统一收尾
```

所以 `invokeSingleCat` 更准确的定位是**调用生命周期协调器**。它不决定叫谁（第 20/21 章），也不负责最终保存完整回复（route 层负责）；它负责把“已经决定调用某只猫”安全地变成一串可消费的 `AgentMessage`。

### 0A.2 五个必须先懂的概念

1. **生命周期**：对象从创建、运行到终止的全部状态。调用至少有 running、succeeded、failed、canceled，不写明确终态就可能让 UI、队列和监控永远认为它还活着。
2. **依赖注入**：registry、sessionManager、store 由外部传入，而不是函数内部临时 `new`。这样测试可传内存实现，业务流程也不会绑死 Redis。
3. **异步 IO**：`await` 表示等待外部 IO 时让事件循环处理别的请求，不等于这一行自动开了新线程。
4. **流式输出**：异步生成器会多次 `yield`，不是最后只 `return` 一个字符串。
5. **补偿式收尾**：一旦创建 timer、注册运行记录或启动子进程，成功、报错、取消都必须清理，因此 `finally` 是正确性的组成部分。

### 0A.3 把函数签名逐个符号读懂

```ts
export async function* invokeSingleCat(
  deps: InvocationDeps,
  params: InvocationParams,
): AsyncIterable<AgentMessage> {
  // ...
}
```

| 语法 | 人话 |
|---|---|
| `export` | 其他模块可以 import |
| `async` | 内部可以 `await` IO |
| `function*` | 可以多次 `yield` |
| `async function*` | 异步地分批产出结果 |
| `deps: InvocationDeps` | 长期依赖的对象形状 |
| `params: InvocationParams` | 这一次调用自己的参数 |
| `AsyncIterable<AgentMessage>` | 调用方用 `for await` 消费很多条消息 |

调用方的样子大致是：

```ts
for await (const msg of invokeSingleCat(deps, params)) {
  // 实时处理 metadata、正文、工具事件、错误和 done
}
```

`yield` 的含义是“先把这一条交出去，函数稍后还能继续执行”。这就是页面能实时看到输出的语法基础。

常见解构：

```ts
const { registry, sessionManager } = deps;
const { catId, prompt, threadId } = params;
```

等价于逐个写 `const registry = deps.registry`。`foo?: Store` 表示依赖可能不存在，使用前要判断；`Store | null` 表示值明确可能为 `null`。`readonly` 只限制字段重新赋值，不代表外部数据库不可变化。

### 0A.4 `deps` 和 `params` 为什么分开

- `deps` 是 router 实例长期复用的能力，如 registry、sessionManager、各种 store。
- `params` 是单次请求变化的值，如 catId、prompt、userId、threadId、signal。

混在一个对象里也能运行，但难以看出哪些是基础设施、哪些是请求数据。面试可说：这种拆分有利于测试和职责识别；但 optional deps 太多会导致主流程遍布 `if (deps.xxx)`，是渐进接线能力与复杂度之间的取舍。

### 0A.5 三种 ID 一定要分清

| ID | 回答的问题 | 生命周期 |
|---|---|---|
| `threadId` | 属于哪段对话？ | 可跨很多次调用 |
| `sessionId` | 某个 CLI 是否恢复之前的模型上下文？ | 可跨调用，但会失效或封板 |
| `invocationId` | 当前这一次执行是谁？ | 单次调用 |

不要把 session 当 thread：一个 thread 可以经历多个 CLI session；也不要把 invocation 当 session：重试或重新调用会产生新的 invocation，但可能继续同一 session。

### 0A.6 为什么先 `yield` 元数据，再吐正文

先暴露 invocationId 属于“先建立控制面，再传数据面”：

- 前端能把 chunk 归到正确调用；
- 用户点击取消时知道取消谁；
- MCP callback 能携带对应身份；
- 日志、trace、审计可用同一 ID 串联。

正文、thinking、tool event 属于数据面；ID、token、状态和取消能力属于控制面。控制面晚到，会导致取消和追踪出现时间窗口。

### 0A.7 取消为什么不是“不要等这个 Promise 了”

Promise 没有通用强杀能力。项目用 `AbortController/AbortSignal` 逐层传递取消意图：

```ts
const controller = new AbortController();
controller.abort('user-cancel');
```

但发出 abort 不等于子进程已经停止。阅读取消链要追四件事：

1. signal 在哪里创建；
2. 是否传到 `invokeSingleCat` 和 Provider；
3. Provider 是否监听并终止 CLI；
4. 谁写 canceled 终态、释放 timer 和运行记录。

这与安全测试里的竞态测试非常接近：重点测注册前后、spawn 前后、最后一个 chunk 前后、重复取消。

### 0A.8 `try/catch/finally` 各负责什么

```ts
try {
  // 正常主流程
} catch (error) {
  // 把失败分类、转换成可观测结果
} finally {
  // 成功、失败、取消、消费者提前停止都会执行的清理
}
```

错误可分三层：

| 层 | 示例 | 常见策略 |
|---|---|---|
| 前置错误 | 目录不存在、账号不可用 | 不 spawn，尽早失败 |
| 运行错误 | CLI 崩溃、超时、流中断 | 分类后重试、降级或失败 |
| 收尾错误 | 记状态或清理失败 | 记录，但不要覆盖原始错误 |

看到 `catch {}` 或 best-effort 时，要判断吞掉的是辅助能力失败还是核心调用失败。前者可能是有意 fail-open，后者通常会造成假成功。

### 0A.9 一条真实请求的慢动作

假设用户在 thread `T1` 里让 `@codex` 审查代码：

1. route 已解析出 codex，并把完整 prompt 传入。
2. `invokeSingleCat` 注册本次调用并尽早产出 metadata。
3. 根据 cat、thread 和工作区决定恢复旧 session 还是新建。
4. 做工作目录、账号、凭据和 MCP preflight。
5. 调用统一 `AgentService.invoke()`；从这里进入第 26 章 Provider。
6. Provider 启动 CLI，持续产生统一 `AgentMessage`。
7. 本函数过滤、补充和审计消息后继续 `yield`。
8. route 层累积正文、落消息；正文里的 A2A 交给第 20 章。
9. 无论正常、异常或取消，都进入收尾逻辑。

### 0.1 一个比喻：invokeSingleCat 像"餐厅后厨的出餐流程"

**这一小节只帮助你确定函数的角色，不解释实现细节。** route 层已经决定任务交给谁，`invokeSingleCat` 负责把这一次执行从准备带到结束。读完后只需回答：它为什么不是一个简单的 `prompt -> answer` 函数？答案是中间还要处理身份、会话、目录、凭据、流式事件、取消和清理。

前台（route 层，20 章）决定"这道菜派给哪个厨师"。
`invokeSingleCat` 是**后厨的出餐流程**：菜（任务）已经派到手了，
它负责把这道菜真正做出来、一口一口端出去。中间要做的事：

```
① 先看这单是不是"外卖代做"（云猫）—— 是的话不用自己开火，转给外部
② 领一个取餐号（invocationId）+ 一张限时餐券（callbackToken）
③ 找到该用哪个灶台（session：新开还是接着上次没做完的）
④ 确认在哪个操作台干活（工作目录：主仓库？还是某个隔离的 worktree？）
⑤ 备料 + 插电（注入环境变量、账号凭据、MCP 配置）
⑥ 点火，启动厨师（spawn CLI 子进程）
⑦ 厨师一边做，一边把半成品端出来（流式 yield 消息）
⑧ 每端出一道，检查一下（消息处理管线：过滤、加工、落库交给前台）
⑨ 做完了报个数（终态：成功/失败/被取消）
```

**关键点：它是"边做边端"的（async generator），不是"全做完再一次性端上桌"。**
所以你在页面上能看到猫的回复一个字一个字冒出来 —— 这就是"边做边端"。

而且**这道菜可以中途被叫停**（用户点了取消）。厨师做到一半被喊停，
灶台要关火、料要收好、账要记清 —— 这就是代码里那一大坨 `finally` 补偿逻辑存在的原因。

### 1.1 invocation/ 目录全景（行数为实测）

**先说人话：这张目录表不是让你背文件名，而是在告诉你“一个调用不是一个文件完成的”。**

用户看到的只是“点发送，Agent 开始回复”，后端却要分工处理：`invoke-single-cat.ts` 负责总协调，`InvocationQueue` 负责等待顺序，`InvocationTracker` 记录谁正在运行，`SessionMutex` 防止同一个旧会话被两次同时续跑，`ensureTerminalStatus` 防止调用没有最终状态。就像安全测试平台里，请求执行、任务排队、状态查询和超时回收不会全写在一个类里。

读下面的目录时只分三组即可：

| 增强功能 | transcript、continuity、task progress 等 | 现在只把它们当可插拔配件 |

### 1.2 一句话职责

**先说人话：这一节是在给函数划责任边界。** 一个大函数最容易被讲成“什么都负责”，但面试官真正想听的是它负责什么、明确不负责什么。

```text

invokeSingleCat 做：准备运行环境 + 调 Provider + 转发事件 + 失败收尾
下游继续做：累积正文 + 保存聊天消息 + 决定是否再叫下一个 Agent
```

这样划分以后，出问题时也更容易定位：叫错 Agent 查 route；CLI 起不来查 invocation/Provider；回复已经出来但历史里没有查 route 的存储逻辑。

**代码阅读提示：**文件头里的 `处理:` 和 `不处理:` 比 3599 行实现更重要。先抓边界，再看细节。`prepend` 在这里就是“把一段文字加到 prompt 前面”。

**面试掌握线：**用三句话说清“输入、职责、输出”，不要声称这个函数还负责完整 prompt 构建或最终消息落库。

### 1.3 调用者与被调用者

**先说人话：这张图只表达一条调用链，箭头可以读成“上一层叫下一层干活”。**

- `route-serial/parallel` 是调度员：决定现在轮到哪只 Agent。
- `invokeSingleCat` 是现场负责人：把这一次任务安全执行完。
- `AgentService` 是统一插座：上层只调用 `invoke()`，不用懂每家 CLI 的参数格式。
- Claude/Codex 等具体实现才决定如何启动和读取各自 CLI。

需要纠正一个容易说错的点：`service.invoke()` **不等于这一行必然直接执行 `spawn`**。它进入统一 Provider 接口，具体实现可能用普通子进程、PTY、后台载体或 ACP。准确说法是“它把调用交给 Provider，Provider 再按自己的载体启动或连接 CLI”。

**面试掌握线：**能画出 `route -> invokeSingleCat -> AgentService -> 具体 CLI/载体`，并解释统一接口隔离了各家差异。无需背所有 Provider 类名。

```
        │  invokeSingleCat(deps, params)
        ▼
invoke-single-cat.ts  ← 本篇
        │  service.invoke(effectivePrompt, options)
        ▼
ClaudeAgentService / CodexAgentService / ...  ← 26 章的 Provider 层
        │  spawn(cli, args, { env })
```

`invokeSingleCat` 站在**编排层和 Provider 层的接缝上**。它上面不知道 CLI 长什么样，下面不知道 A2A 链长什么样。

## 2. 核心数据结构

### 2.1 `InvocationDeps`：4 个必需依赖 + 20 个可选依赖

**先说人话：`InvocationDeps` 是这个函数的“工具箱清单”。** 函数不会自己临时创建 Redis、会话管理器和审计组件，而是由外面把已经准备好的对象传进来。这叫依赖注入。它最实际的价值不是术语好听，而是测试时可以传假的内存对象，不必真的启动 Redis 和 CLI。

先把 TypeScript 语法拆开：

```ts
readonly sessionManager: SessionManager;
readonly taskProgressStore?: TaskProgressStore;
```

- `字段名: 类型`：这个字段应该放什么对象。
- `readonly`：函数拿到对象后不能把这个字段重新指向别的对象；不代表数据库内容不能改。
- `?`：这个字段可以不传。使用前通常会看到 `if (deps.taskProgressStore)` 或 `deps.xxx?.method()`。
- 没有 `?` 的四个基础字段是主流程必需品，缺少时程序连基本调用都组织不起来。

为什么会增长到 24 个槽位？不是一次设计就想出了这些依赖，而是项目不断加会话封存、任务进度、Guide、Concierge 等功能后，都接到了这条主干。这也是代码变难的原因：每多一个可选能力，函数里就多一组“存在时怎么做、失败时是否继续”的分支。这个数字会继续随版本变化，不值得背。

这里还要分清两种失败策略：

- **fail-open（失败后继续）**：例如任务进度写失败，主回答仍可继续，只记日志。
- **fail-close（失败后停止）**：例如凭据缺失或工作目录不安全，继续执行可能泄露数据或改错项目，所以必须拦下。

**面试掌握线：**不用背字段数量。记住“4 个基础依赖 + 多个可选增强”，并能说出依赖注入利于测试、可选依赖利于渐进上线，但会让主函数分支膨胀。

### 2.2 `InvocationParams`：一次调用的入参

**先说人话：`InvocationParams` 是这一次任务的“派工单”，和上面的长期工具箱不是一回事。**

一次派工最少要回答：叫谁（`catId`）、通过哪个适配器执行（`service`）、给它什么完整指令（`prompt`）、属于哪个用户和会话线（`userId/threadId`）、它是不是当前链条最后一个 Agent（`isLastCat`）。其他字段是图片、取消信号、父调用、追踪信息等补充信息。

几个语法按下面读即可：

| 写法 | 人话 |
|---|---|
| `signal?: AbortSignal` | 可能带一个“请停止”的信号 |
| `readonly contentBlocks?: readonly MessageContent[]` | 可能带一组图片等内容；本函数不应替换数组 |
| `Span` | 一段可追踪的运行区间，用来串日志和耗时 |
| `{ current?: Span }` | 一个小盒子，函数内部可把创建的 span 放进去交给调用方 |

最容易混淆的是 `prompt` 与 `mentionContent`：前者已经混入系统身份、历史和协作规则，是给 Agent 执行的完整版；后者保留最初的 @ 文本，是给云端桥传递原始意图的。不能拿完整版冒充用户原话，否则云端 Agent 会看到错误的来源和上下文。

### 2.3 `AgentMessage`：12 种消息类型

**先说人话：Provider 返回的不是一个最终字符串，而是一串“事件”。** 类似抓包时一个请求会经历建连、数据包、错误和关闭，Agent 调用也会先报告 session、再陆续给正文和工具事件，最后给 `done`。

不要硬背 12 个名字，先分成四类：

| 类别 | 包含 | 页面/后端怎么用 |
|---|---|---|
| 用户内容 | `text`、`tool_use`、`tool_result` | 形成可见回复或工具过程，也意味着可能已有副作用 |
| 生命周期 | `session_init`、`done`、`error` | 建立会话、结束或报告失败 |
| 状态信号 | `system_info`、`status`、`provider_signal`、`liveness_signal` | 给提示、进度和存活信息，不一定是正文 |
| 协作/遥测 | `a2a_handoff`、`agent_loop` | 交接或内部统计 |

这一分类为什么影响重试？如果已经出现 `tool_use`，Agent 可能写过文件或发过请求；此时从头重试可能重复操作。如果只收到“还活着”的状态信号，通常还没有真实产出，某些失败仍可以安全重试。

英文注释的中文意思是：`provider_signal`、`liveness_signal` 和 `status` **不能靠频繁发送来刷新硬超时**。否则一个实际卡死、只会发心跳的进程可以永远逃过 30 分钟上限。这里的 `daemon` 指后台常驻进程，`tooltip` 指鼠标悬停提示。

**面试掌握线：**不背 12 种逐项行为。能说出“内容事件、生命周期事件、状态信号”三大类，以及“心跳不能续命、已有副作用不能盲目重试”即可。

### 2.4 把三个类型真正装进一次调用：字段是怎样一层层被使用的

**先说人话：前面三种类型合起来就是“工具箱 + 派工单 -> 事件流”。**

```text
InvocationDeps   长期工具箱：会话、存储、审计等能力
InvocationParams 本次派工单：谁、做什么、在哪个 thread、能否取消
AgentMessage     执行过程中不断送回来的事件
```

读这里的示例对象时，不要试图记住字段。你只需要沿一条数据追踪：`params.threadId` 被用来找旧 session，`params.signal` 被传给等待和 Provider，`params.prompt` 最终交给 `service.invoke()`；Provider 吐出的 `AgentMessage` 再由 route 层消费。

**面试掌握线：**看到一个字段能回答“它来自哪里、在哪一步被用、影响什么结果”。这比背接口定义更有价值。


只看接口时，`InvocationParams` 很像一张很长的参数表。更有效的读法是构造一个接近真实运行的对象：

```ts
const params: InvocationParams = {
  catId: 'codex',
  service: codexService,
  prompt: finalPrompt,
  userId: 'user-1',
  threadId: 'thread-42',
  isLastCat: true,
  signal: requestAbortController.signal,
  systemPrompt: staticIdentity,
  parentInvocationId: 'inv-parent',
};
```

这里的 `service` 不是模型名称，而是已经创建好的 Provider 适配器；所以主函数只调用 `service.invoke()`，不需要知道它最终运行 `codex`、`claude` 还是其他 CLI。`prompt` 注释强调它已经由 route 层完成动态上下文和 chain context 的组装，说明本函数收到的不是用户原话，而是“可直接执行的成品 prompt”。`mentionContent` 则恰好相反，它要保留原始意图；当前源码注释明确说这两个 cloud bridge 字段未完整接线，因此缺失时选择抑制云端派发，而不是拿成品 prompt 冒充用户原话。这是典型的 fail-close：宁可不发，也不把错误语义发送给远端。

`isLastCat` 也不是装饰字段。串行路由中，当前猫后面可能还有 worklist 项；“这是链上最后一只猫”会影响提示、收尾或最终答复语义。`parentInvocationId` 用来把本次执行挂回父调用/队列链，`routeSpan` 与 `invocationSpanRef` 则是可观测性上下文：前者把 span 串成父子关系，后者让调用方拿到本函数内部创建的 span。

`AgentMessage` 要按 `type` 阅读，而不是假定每条都有 `content`：

```ts
if (msg.type === 'session_init') use(msg.sessionId);
if (msg.type === 'text') appendOrReplace(msg.content, msg.textMode);
if (msg.type === 'status') updateAvatarTooltip();
if (msg.type === 'done') finishInvocation();
```

`content?`、`sessionId?` 的问号表示字段只在特定消息类型有意义。当前接口没有被写成十二个完全分离的联合对象，所以编译器不能自动保证“text 一定有 content”；消费者仍需按 type 做防御检查。`textMode: 'append' | 'replace'` 也很关键：大多数 Provider 发增量后缀，用 append；有些 Provider 会发修正后的完整快照，此时必须 replace，否则 UI 会重复文本。

最后把 `deps` 和 `params` 放在一起看：`params` 描述“这一次要做什么”，`deps` 提供“完成它需要哪些能力”。当 `deps.sessionChainStore` 不存在时，session chain 增强可以 fail-open；但 `registry`、`sessionManager`、`apiUrl` 是主流程基础，不能当作可有可无。读后面的每个 `if (deps.xxx)` 时，都应追问：这是增强功能失败，还是会破坏调用身份/凭据/目录的核心失败？两者的错误策略不能相同。

### 3.1 第一关：先问"这只猫要不要本地开火"（① 云猫短路，677-758）

**这一节只解决一个问题：目标 Agent 是在本机运行，还是在外部 ChatGPT 会话里运行？** 如果是后者，本地没有对应 CLI 可启动，就不能继续走普通流程，而要通知云端桥后直接结束本地调用。

把代码按三步读：先从 `catRegistry` 查配置；再判断 `provider === 'openai-chatgpt-pro'`；命中后尝试通知 bridge，随后 `yield done` 并 `return`。这里的 `return` 很重要，它表示后面的 session、工作目录、凭据和本地 Provider 全部跳过。`fire-and-forget` 的中文意思是“发起后不等待结果”，因此云端失败不会把当前生成器一直卡住。

英文长注释的核心中文翻译是：**桥接时必须发送未经系统加工的原始 @ 文本，并说明是谁 @ 的；这两个字段没接好时宁可不派发，也不能把混入系统提示的 prompt 当成用户原话发给云端。** 这属于 fail-close，因为发错内容和错误归因比暂时不发更危险。

**不做会怎样：**系统会尝试在本机启动一个根本不存在的 CLI，或者把错误上下文交给云端 Agent。

**面试掌握线：**知道这是“云端载体的提前分流”即可。F247、PR-B/PR-C、五字段 delta 都是版本演进证据，不用背。


第一个分支不是业务逻辑，是**一整类猫根本不走这个函数**：


### 3.2 领身份牌 + 设两层超时（③④ invocationId / callbackToken，769-815）

**这一节做两件事：先给本次运行建立可追踪身份，再给它设置最长运行时间。** 身份解决“这是谁的回调和日志”，超时解决“它一直不结束怎么办”。

`invocationId` 可以理解为本次执行的流水号；`callbackToken` 是只有这次执行应该持有的临时通行证。它们不是同一个东西：ID 用于定位，token 用于证明请求确实来自这次调用。`parentInvocationId` 和 `a2aTriggerMessageId` 则记录“是谁触发了我”，用于把 A2A 链串起来。

两层超时可以类比安全测试中的两道超时：Provider 内层先判断 CLI 自己是否卡住；invocation 外层是最终兜底。外层设得更长，是为了让内层先产生更具体的诊断，而不是两个计时器同时触发造成结果随机。`AbortSignal.any` 的意思是“用户取消”和“系统超时”任何一个先发生，都通知下游停止。

`unref()` 不需要会写，只要知道它让这个定时器本身不阻止 Node 进程正常退出。发出 abort 也不等于子进程已经被成功杀掉，后面还要靠 Provider 响应 signal、`abortableNext` 退出等待和 `finally` 清理资源。

**面试掌握线：**讲清 `invocationId` 与 token 的区别、内外两层超时的顺序、取消信号必须传到下游。倍数和具体分钟数作为源码事实查表即可。


```ts
const { invocationId, callbackToken } = await registry.create(
  userId, catId, threadId, params.parentInvocationId, params.a2aTriggerMessageId,
);
```

这一对就是 13 章 MCP 回调桥的**身份凭据**：子进程拿着它们回调 API 才能证明"我是这次调用"。`parentInvocationId` 和 `a2aTriggerMessageId` 是链路血缘（谁触发的我）。

紧接着的 triggerType 派生是个漂亮的三元链：

```ts

                  : params.parentInvocationId ? 'routing'
                  : 'default';
```
【源码】778

**两层超时的关系是本节重点**：

```ts
const INVOCATION_TIMEOUT_MULTIPLIER = 2;
const cliTimeoutMs = resolveCliTimeoutMs(undefined);
const invocationTimeoutMs =
  (cliTimeoutMs > 0 ? cliTimeoutMs : DEFAULT_CLI_TIMEOUT_MS) * INVOCATION_TIMEOUT_MULTIPLIER;
```
【源码】784-787

- **内层**：CLI 超时（Provider 层管，NDJSON 流空闲判定）
- **外层**：调用级硬超时 = 内层 × 2

为什么要 ×2 而不是相等？注释写了：`Must be > CLI_TIMEOUT_MS to avoid racing the inner timeout.`——两个超时如果同时到，你不知道错误消息会是哪一个，诊断信息会丢。**外层留出一倍余量，保证"内层先报，外层兜底"的顺序是确定的。**

还有一个边界：`CLI_TIMEOUT_MS=0` 是"禁用 CLI 超时"的开关，但调用级超时**不允许被禁用**——回退到 `DEFAULT_CLI_TIMEOUT_MS`（30 分钟）。**「可以关掉内层，但绝不能没有天花板」**。

超时用的是 `setTimeout` + `unref()`，而且是**可重置**的：

```ts

  if (invocationTimer) clearTimeout(invocationTimer);
  invocationTimer = setTimeout(() => {
    log.error({...}, 'Invocation hard timeout fired');
    invocationAc.abort(new Error('invocation_timeout'));
  }, invocationTimeoutMs);
  invocationTimer.unref();
};
```
【源码】790-797

`unref()` 的意思是"这个定时器不阻止 Node 进程退出"。忘了写它的话，进程关不掉。

然后是信号合并：

```ts

  ? AbortSignal.any([callerSignal, invocationAc.signal])
  : invocationAc.signal;
```
【源码】801-803

注释：`Merge caller signal (user cancel) with invocation timeout — neither loses semantics.` `AbortSignal.any` 是 Node 20+ 的 API，用它比手写 `addEventListener` 转发要干净得多——**而且 abort reason 会保留原始那个**，所以下游能区分"用户取消"和"超时"。

### 3.3 第一口"端出去"的不是内容，是取餐号（⑤ 先 yield 元数据，810-815）

**这一节的核心是：正文还没来，先把本次调用 ID 交给上层。** 上层只有先拿到 ID，后续的文本、富内容、取消操作和日志才能明确归到这次调用。

`yield` 可以读成“先交出这一条，但函数还没结束”。这里交出的是 `system_info`，其内容是 `invocation_created + invocationId`。旧实现去全局状态里猜“最新 ID”，并发或抢占时旧调用 A 可能拿到新调用 B 的数据；现在把确切 ID 随事件传出去，消除了这种猜测。

英文注释的中文意思是：**不要再调用 `getLatestId()` 猜当前调用，因为发生抢占时，旧调用可能偷走新调用缓冲区里的富内容；创建后立即把 ID 显式交给调用方。**

**面试掌握线：**能概括为“用显式 ID 传递替代读取易变的全局最新值，修复并发归属问题”。不用了解 `RichBlockBuffer` 的全部实现。


```ts
yield {
  type: 'system_info' as const,
  catId,
  content: JSON.stringify({ type: 'invocation_created', invocationId }),
  timestamp: Date.now(),
};
```

注释解释了为什么必须在这儿吐：

> F22 R2 P1-1: Expose invocationId to caller (route-serial/parallel) so they can use it for `RichBlockBuffer.consume()` instead of `getLatestId()` which is **wrong under preemption** — old invocation A would steal new invocation B's blocks.
> 【源码】807-809

**这是一个真实并发 bug 的修复痕迹**：原来上层用"最新的 invocationId"去取富块缓冲，在抢占场景下会拿错。修法不是加锁，而是**把 id 主动推给消费者**。面试里这类"从隐式全局状态改成显式传参"的修复很好聊。

### 3.4 找灶台：新开一个，还是接着上次没做完的（⑦ session 解析，1025-1157）

**这一节只做一个决定：这次要续接旧 CLI 上下文，还是开一个干净的新会话。** `sessionId` 存在不代表一定能用，因为旧记录可能已经封存、属于不同工作区，或者正被另一个请求使用。

按以下四关理解原文即可：

1. 先尝试读取旧 session；Redis 读失败时可以开新会话继续。
2. 检查会话链是否已封存；已封存就不能再 resume。
3. 检查 thread 是否配置为 reborn；若是，每轮都强制新建。
4. 真要 resume 时按 session 加互斥锁，防止两个请求同时写坏同一个 CLI 会话。

原英文注释逐句翻成人话：**如果会话链里有已封存或正在封存的记录，却没有活跃记录，说明旧会话已经结束。即使另一个异步删除动作还没来得及清掉旧 `sessionId`，读取侧也要主动丢弃它，从而堵住这段竞态时间窗。** `race window` 就是两个并发动作先后顺序不固定、可能短暂读到旧数据的窗口。

这里最值得记的英文判断是 `Lost resume is recoverable; sealed-session corruption is not.`，中文是：**少续接一次，最多损失一些上下文，还能补救；续接到已经封存的错误会话，可能污染会话链，后果更难恢复。** 所以不确定时选择新会话。

`SessionMutex` 不用深入实现。把它理解为同一 session 的单人卫生间钥匙：拿到钥匙的人执行 resume，其他人等待；按不同 session 加锁，不会让全系统所有 Agent 都排成一队。

**面试掌握线：**四关能说清即可。重点是“恢复旧上下文不是默认安全的”和“锁的粒度是 session，不是整个服务”。bg carrier 的 chainKey 是特殊载体细节，能看懂无需主动讲。


这一段是全函数最容易讲出深度的地方。目标只有一个：**决定这次 CLI 要不要带 `--resume <sessionId>`，带哪个。**

**第一道：读，但允许失败**

```ts

try {
  sessionId = await preflightRace(sessionManager.get(userId, catId, threadId), 'sessionManager.get', signal);
} catch (err) {
  log.warn({...}, 'Session get failed (timeout or Redis), proceeding without');

```

`preflightRace` 是 `invoke-helpers.ts` 里的纯函数（后面 §4.1 细讲）。这里的判断是：**Redis 读失败不该让整次调用失败，退化成"新会话"就行**——丢上下文是可恢复的，卡死不是。

**第二道：封板短路（R8 P1）**

### 3.5 确认操作台，别在错的目录里干活（⑧ 工作目录 + 三道 preflight，1159-1404）

**这一节是在 Agent 动文件前确认“它到底应该在哪个项目目录工作”。** 对代码 Agent 来说，工作目录不是普通配置：选错目录可能读取别人的代码、修改错误仓库，甚至绕过项目治理规则。

`workingDirectory` 的来源虽多，主线只有两步：先从 thread 绑定或训练营配置解析真实目录，再执行前置检查。`preflight` 可翻成“起飞前检查”，即在昂贵且有副作用的 Provider 调用之前，先验证条件是否满足。

三层门禁不要背编号，只记力度：本地聊天调用中的部分 Git 状态问题只警告，避免每次共享状态稍有滞后就让聊天不可用；真正可能让 Agent 在未经治理的外部项目中工作时则硬阻断。`warn-only` 是“提示但继续”，`hard block` 是“不满足就不执行”。

`done` 携带 `errorCode` 表示流程已经明确结束，但结束原因是可识别的业务失败。这样 route 和前端不必解析中文错误文案，就能决定是否展示修复操作或允许重试。

**不做会怎样：**轻则 CLI 报“目录不存在”，重则 Agent 在错误仓库修改或提交文件。

**面试掌握线：**讲清工作目录是安全边界、检查分为告警和硬阻断、错误码比解析文案可靠。四种路径来源和所有 feature 编号不必背。


**workingDirectory 的四条来源**（优先级从上到下）【源码】1208-1244：

| Provider 要求工作区（OpenCode）但都没有 | 报错文案："Bind the thread to a project workspace before spawning OpenCode." |

游戏 thread 用 `games/werewolf` 这种虚拟 projectPath 只做分类，**如果不特判会触发 F070 治理门禁去检查一个不存在的目录**——这是个典型的"两个功能各自合理、交叉处出 bug"的例子。

### 3.6 备料插电：账号、凭据、环境变量（⑨ 账号解析与凭据注入，1406-1870）

### 3.7 上桌前的最后一撮调料（⑩ prompt 的四层 prepend，1873-1926）

**这一节不是重新构建整份 prompt，而是在真正调用前补上几段有不同生命周期的控制信息。** `prepend` 就是加在前面，`append` 就是加在后面。

最关键的区分只有两个：

- 静态身份通常只需在新 session 注入；续接旧 session 时模型上下文里已经有了，重复塞会浪费 token。
- staging、上下文提示和任务信息要求每轮生效，不能因为本轮是 resume 就漏掉。

英文注释的中文意思是：**曾尝试使用 CLI 官方的 `--append-system-prompt`，但实际存在 Agent 收不到内容的情况，因此改用所有 CLI 都能理解的字符串前置拼接；同时不再把同一份 systemPrompt 交给下游 Provider，避免上下两层各拼一次。**

配置 revision 改变或检测到上下文压缩时，即使是 resume 也要重新注入身份。原因很直观：旧会话记着旧身份，或身份已经被压缩摘要丢掉。

**面试掌握线：**不背四层的 feature 名。要能说明 prompt 中不同片段有“只在新会话”和“每轮都要”的生命周期，resume 不能简单理解成全部跳过注入。


先算"要不要注入静态身份"：

**四个 OR 条件的含义**：

2. `!isResume` —— 新会话，必须注入
3. `forceReinjection` —— **检测到上下文压缩了**（8 章那套），身份被压掉了要补

### 3.8 边做边端：每条消息怎么加工再交出去（⑪ 消息处理管线，2037-2921）

**这一节是消息流水线：Provider 每送来一条事件，系统先加工，再交给上层。** `processMessage(msg) -> AgentMessage[]` 表示“一条输入可能变成零条、一条或多条输出”，例如一个 `done` 除了原终态，还可能产生 usage 和 context health 信息。

只抓四种处理：`error` 记住本轮有错；`session_init` 保存 CLI 新给的 sessionId；正文和工具事件标记已经有真实产出；`done` 完成审计、用量、会话轮次和上下文健康结算。

bg 和 ACP 的长注释是在说明：**sessionId 变化不总等于换了一段业务会话。** 普通 CLI 的变化可能需要封存旧记录；后台载体可能每轮换临时 UUID；ACP 甚至每次调用都创建临时 session。上层不能看见 ID 变了就一律封存，应由 Provider 通过 `ephemeralSession` 等字段说明语义。

`one input, many outputs` 的设计也意味着消费者必须按事件类型处理，不能假设“Provider 给一条，页面就原样显示一条”。

**面试掌握线：**讲清 `session_init`、内容事件、`done` 三类即可；usage、OpenCode 中途事件和各种载体特判作为进阶材料查阅。


`processMessage(msg) → AgentMessage[]` 是个**一进多出**的纯度较高的函数（有 IO，但没有控制流副作用）。输入一条 provider 消息，输出零到多条要 yield 的消息。

外面套了一层 generator 适配：

```ts

  for (const out of await processMessage(sourceMsg)) { ... yield out; }
};
```
【源码】2923-2925

主流程里所有 yield 都走这个包装，**唯一入口**保证了每条消息都被同样处理（任务进度持久化、invocationId 附加）。

**四个主要分支：**

**(a) `error` → 只记状态，不拦截**（2378-2381）

### 3.9 厨师中途崩了，要不要重做（⑫ 重试循环 + 六类错误抑制，3033-3452）

**这一节的总原则只有一句：重试等于把原任务再执行一遍，所以只有能证明没有产生实质副作用时才重试。**

两个布尔量可以这样理解：

- `attemptHasContentOutput`：已经出现正文或工具活动，说明用户看到了结果或系统可能动过手。
- `attemptHasSubstantiveOutput`：是否有真正的模型产出；单纯诊断信息不算。

“抑制错误”不是吞错，而是**暂时扣住**。流式 Provider 有时先发一条 error，后面还会恢复并继续发消息；系统先不展示，等 `done` 到来再判断它是不是最终失败。如果 error 后又来了正常消息，就把扣住的错误按协议处理，不能假装没发生。

英文注释 `Self-heal policy (at most one retry total)` 的中文是：**自愈最多只再试一次。** `Without this guard ... duplicating tool actions` 的中文是：**若没有“尚未产出内容”这道门，Agent 已经调用过工具后再次从头执行 prompt，会重复写文件、重复发请求等操作。**

`malformed tool call` 是模型生成了无法解析的工具调用。第一次且没有实质输出时，可以换干净 session 再试；已经有内容时不能谎称“系统正在恢复”，因为代码根本不会重试。原注释称旧文案为 `a lie`，中文就是“这是假话”，修复后改成如实告诉用户最后一步未完成。

**面试掌握线：**掌握“最多一次、已有副作用不重试、错误先暂扣到流终态再判断”三点。六类正则和 Opus 专用接力卡片不必背，除非你把错误恢复选作个人深挖方向。


外层是个最多两次的 for 循环：

【源码】2986-2989

**为什么不用 `for await`：**

```ts
// F089：使用 abortableNext 而不是普通 for await；即使 Provider 生成器卡在
// 一个永远不返回的 await 上，调用超时也能打断等待。
```

`for await` 会阻塞在 `gen.next()` 上，**没有任何办法打断**。所以手写了：

```ts
function abortableNext<T>(iter: AsyncIterator<T>, signal: AbortSignal): Promise<IteratorResult<T>> {
  if (signal.aborted) return Promise.reject(signal.reason ?? new Error('aborted'));
  return new Promise<IteratorResult<T>>((resolve, reject) => {
    const onAbort = (): void => reject(signal.reason ?? new Error('aborted'));
    signal.addEventListener('abort', onAbort, { once: true });
    iter.next().then(
      (result) => { signal.removeEventListener('abort', onAbort); resolve(result); },
      (err) => { signal.removeEventListener('abort', onAbort); reject(err); },
    );
  });
}
```
【源码】188-205

**注意两个分支都 `removeEventListener`** —— 不摘监听器的话，一次长会话下来 signal 上挂几千个回调，内存泄漏。这是个很好的"看细节功底"的点。

**六类错误抑制表**（这是本章第二个必背表）：

| # | 判定函数 | 触发条件（额外门槛） | 处理 |
|---|---|---|---|
| 1 | `isMissingClaudeSessionError` / `isSessionNotFoundDiagnostic` | `allowSessionRetry` | 丢 session 重试 |
| 2 | `isPromptTokenLimitExceededError` | `allowSessionRetry` **且无内容输出** | 丢 session 重试 |
| 3 | `isContextWindowOverflowError` | 同上 | 丢 session 重试 |
| 4 | `isTransientCliExitCode1` / `isTransientAcpPromptFailure` | `allowTransientRetry` 且无内容输出 | **原样重试**（保留 session） |

**"无内容输出"这个门槛为什么关键**，第 6 类的注释说得最透：

> 源码注释中文意：只有本轮尚未输出任何内容时，才能暂扣 malformed 错误并重试。否则一个已经调用过工具、最后一步格式错误的多步任务会从头重放原 prompt，造成工具动作重复执行。
> 【源码】3142-3145

**重试 = 重放。如果上一次已经动过手（写过文件、发过请求），重放就是重复副作用。** 所以"已经有内容输出"必须禁止重试。这条判断是所有带副作用的重试逻辑的通用原则，面试里非常好用。

而第 5 类用的是 `attemptHasSubstantiveOutput` 而不是 `attemptHasContentOutput`，因为 `timeout_diagnostics`（system_info）不该阻止重试（3108-3111）。**两个近似的布尔量，差别只在 system_info 算不算**——这种精度是被 bug 逼出来的，注释里那条 F215 hotfix 记录了原因：

> 源码注释中文意：限流事件产生的 `system_info` 可能先于 malformed 错误到达。如果把这种系统信息误算成实质内容，malformed 的暂扣条件会失败，封存、干净重试和接力都会被跳过，最后把未经处理的底层错误直接暴露给用户。

### 3.10 不管怎么收场，都要关火记账（catch 与 finally 两条补偿路径，3474-3598）

**这一节区分“报告失败”和“无论如何都要清理”。** `catch` 处理被抛出的异常，生成 error/done 并写错误审计；`finally` 不管成功、失败、取消还是调用方提前停止读取都会运行，负责释放资源和结束追踪。

三个标志位用人话读：

| 变量 | 问的问题 |
|---|---|
| `hadError` | 执行过程中是否确认发生错误？ |
| `didWriteAudit` | 最终审计是否已经有人写过？ |
| `didComplete` | 是否到达了代码认可的正常或干净终点？ |

三者都为否，说明没有正常结束、没有明确抛错、也没人写终态，最典型就是消费者对 generator 调了 `.return()` 或客户端中途断开。因此 `finally` 补一条 `generator_returned_without_completion`，防止后台永远留下“还在运行”的假象。

英文注释 `drain any open tool spans whose tool_result never arrived` 的中文是：**某些工具调用已经开始记录耗时，但取消或异常导致结果事件永远不来；收尾时要把这些孤儿 span 统一结束。** `idempotent` 是“重复执行也不会造成额外破坏”，所以释放函数即使没拿到锁也应安全。

**面试掌握线：**能解释 catch 与 finally 的区别，并用正常、异常、提前 return 三条路径说明为什么 finally 是正确性逻辑而非卫生代码。八项清理动作不用逐条背。


**catch 做四件事**：span 置错 → 写 `CAT_ERROR` 审计 → `yield error` → `yield done`（带 tracing）。关键是置了两个标志位：`hadError = true; didWriteAudit = true;`。

**finally 做八件事**【源码】3515-3597：

```
1. toolSpanTracker.endAllOrphans('aborted')   ← 收尾没等到 tool_result 的 span
2. clearTimeout(invocationTimer)
3. sessionMutexRelease?.()                    ← 幂等，没拿到锁也安全
4. rm(openCodeRuntimeConfigDir)               ← 删临时配置目录
5. 兜底审计（三标志位判定）
6. finalizeTaskProgress()
7. 遥测：invocationDuration / activeInvocations−1 / invocationCompleted / catResponseDuration / threadDuration
8. agentPaneRegistry 标记 + span.end()
```

**第 5 项是全函数最精妙的一处**：

```ts
if (!didWriteAudit && !hadError && !didComplete) {
  auditLog.append({ type: AuditEventTypes.CAT_ERROR, data: { error: 'generator_returned_without_completion' } });
}
```
【源码】3536-3553

**三个布尔量的组合正好识别出"generator 被 `.return()` 强行掐断"这一路**：没写审计、没报错、也没正常完成 = 有人在外面把迭代器关了（客户端断连、AbortController）。注释标了 issue 号 `#99`。

`didComplete` 的三个赋值点是这个判定的完整性保证：
- 3473：正常走完
- 1152：排队时被 abort（干净退出）
- 1401：治理门禁拦截

**任意一个漏了置位，就会误报一条 CAT_ERROR。** 所以变量声明处的注释写着 `must be before any early return`（875）。

`wasAbortedWithoutError` 用同一个三元组算出来，再驱动遥测状态和 span 状态：

```ts
const wasAbortedWithoutError = !didWriteAudit && !hadError && !didComplete;
const otelStatus = hadError || wasAbortedWithoutError ? 'error' : 'ok';
```
【源码】3559-3560

**"abort 算 error"** 是个明确选择——注释：`Abort path — generator .return()'d without completion, consistent with audit CAT_ERROR`。审计和遥测口径一致，这样两个数据源对得上。**如果一个算 error 一个算 ok，事后对账时会怀疑人生。**

`finalizeTaskProgress` 里还有一段防降级逻辑值得看：

```ts
// 一旦已经持久化 completed 快照，就不能因为稍后收到 abort 而降级为 interrupted。
// "interrupted" just because the request was aborted after completion
if (finalizedTaskProgressStatus === 'completed' && status === 'interrupted' && !hadError) return;
if (finalizedTaskProgressStatus === 'interrupted' && status === 'completed') return;
if (finalizedTaskProgressStatus === status) return;
```
【源码】962-968

**终态一旦确定就不允许被后来的 abort 改写**（客户端断连发生在完成之后是很常见的）。三条守卫分别防降级、防升级、防重写。这是个小型的**单调状态机**——和 10 章球权状态机是同一个思路，只是规模小到不值得单独建模。

### 3.11 源码执行复盘：把一次调用当成“状态机”逐变量跟踪

**这一节不是新知识，而是把 3.1～3.10 串成一条能复述的故事。** “状态机”在这里不需要理解成复杂理论，只表示：调用在运行过程中会记住几个状态，最后根据这些状态判断它是成功、失败还是半路消失。

第一次复盘只盯六个锚点：创建 `invocationId`、决定 `sessionId`、检查工作目录、调用 `service.invoke()`、收到 `done/error`、进入 `finally`。其余代码都是在这六点之间补充功能或异常处理。

**面试掌握线：**你要能不看书画出这六点，并分别走一遍正常、失败、取消。七个变量的完整表用于第二轮深入，不要求第一次背诵。


前面的 3.1～3.10 已经按代码块讲过流程。这里再换一种更适合初学者和面试的读法：**不要只盯着函数调用，要盯住几个变量何时发生变化。** `invokeSingleCat()` 虽然有三千多行，但一次执行真正决定结局的核心状态可以压缩成下面这张表。

| 状态变量 | 初始含义 | 什么时候改变 | 最终用于什么 |
|---|---|---|---|
| `invocationId` | 本次调用的唯一业务编号 | `registry.create()` 返回后确定 | callback 鉴权、日志、审计、前端关联 |
| `callbackToken` | 本次调用的临时回调凭证 | 与 `invocationId` 一起创建 | 注入 `CAT_CAFE_CALLBACK_TOKEN`，防伪造回调 |
| `sessionId` | 可恢复的 CLI 会话编号 | 从 `sessionManager.get()` 读取，或收到 `session_init` 后更新 | 决定 Provider 是新开会话还是 `resume` |
| `hadError` | 流里是否出现过错误 | 收到 `error` 或进入异常路径时变为真 | 决定审计、OTel 状态、pane 最终状态 |
| `didComplete` | 是否走到了正常终点 | 正常处理终止消息后设为真 | 区分“正常完成”和“生成器被强制 return” |
| `didWriteAudit` | 是否已经写过终态审计 | `CAT_RESPONDED`/`CAT_ERROR` 写入后改变 | 防止 `catch` 和 `finally` 重复写错误审计 |
| `signal` | 合并后的取消信号 | 由调用方 signal 与内部 `invocationAc.signal` 组合 | 中断 preflight、Provider 迭代和超时等待 |

#### 路径 A：Provider 正常返回

**人话版：登记一次执行 -> 准备环境 -> Provider 不断回传事件 -> 收到 done -> 记成功 -> 清理。**

这里最容易说错的是“收到正文就成功”。正文只是中间产物，真正终点是协议里的 `done` 以及随后完成的审计和收尾。即使已经显示了一部分文字，连接仍可能在最后失败。

假设用户让 `codex` 修改一个文件，正常执行可按下面的“断点清单”走：

1. `registry.create()` 先生成 `invocationId + callbackToken`。这一步发生在 Provider 启动前，所以即使 CLI 随后起不来，系统仍有一条可追踪的调用记录。
2. 立即 `yield invocation_created`。前端拿到编号后，才能把后续文本、工具调用、取消按钮和审计记录绑定到同一次调用。
3. 读取旧 `sessionId`，检查工作目录指纹和恢复健康度。**会话存在不代表一定可恢复**；目录不一致、连续恢复失败等情况会让系统选择 fresh start。
4. 执行工作区、共享状态、治理规则等 preflight。warn-only 分支会先输出警告再继续；真正阻断的分支不会进入 Provider。
5. 组装 `callbackEnv`、账号环境和最终 prompt，然后调用 `service.invoke(...)` 获得一个异步消息流。
6. 循环读取消息。`session_init` 更新会话映射；`text` 累积可见输出；`tool_use/tool_result` 更新工具状态；`done` 携带 usage 时还会生成上下文健康信息。
7. 正常终止时写 `CAT_RESPONDED`，并把 `didComplete`、`didWriteAudit` 调整到能让 `finally` 判断“已经善后”的状态。
8. 进入 `finally`：清计时器、释放 session mutex、删临时配置目录、完成任务进度、记录指标、结束 span。

初学者最容易误解第 8 步：`finally` 不是“只在失败时执行”，而是**成功、抛错、取消、消费者提前停止迭代都会执行**。所以资源释放必须放这里。

#### 路径 B：Provider 抛异常或流中返回 `error`

**人话版：失败有两条通道。** 一种是 JavaScript 直接 `throw`，程序跳进 `catch`；另一种是 Provider 正常维持消息流，但送来一条 `{ type: 'error' }`。后者仍可能继续送诊断和 `done`，所以不能一看到 error 事件就把整个迭代器粗暴丢掉。

**面试掌握线：**能解释“异常通道”和“协议错误事件”并存，以及两者最终都需要明确终态。

这两种错误看起来相似，但代码语义不同：

- **抛异常**：例如 spawn 直接失败，控制流进入 `catch`。
- **流内 `error` 消息**：Provider 本身没有 throw，而是遵守 `AgentMessage` 协议返回 `{ type: 'error' }`；外层循环仍能继续决定是否补一个 `done`、是否抑制已知错误、是否 fresh retry。

因此面试时可以说：项目没有把所有错误都建模成 JavaScript 异常，而是同时支持“异常通道”和“消息协议中的错误事件”。这样做的优点是流式接口即使失败，也能尽量给前端一个结构化终态，而不是突然断流。

重试又不是“只要失败就重试”。例如 `invoke-single-cat-timeout-retry.test.js` 明确覆盖：

- 有旧 `sessionId`、发生 timeout、且只有 `system_info`，可以丢弃旧 session 后 fresh retry；
- 已经产生实质正文后超时，不重试，避免重复副作用；
- 本来就没有 session 的 timeout，不做“去掉 session 再试”这种无意义操作。

#### 路径 C：用户取消或消费者提前结束迭代

**人话版：上层不再读取，不代表底层资源自动消失。** 消费者调用 `.return()` 时可能绕过普通 `catch`，所以取消信号负责通知正在等待的步骤停止，而 `finally` 负责释放锁、定时器和临时文件，并补齐审计。

**面试掌握线：**不要只答“用了 AbortController”。至少再补一句：取消意图需要传到 Provider，生成器提前结束还必须由 finally 收尾。

取消最难理解，因为 `async generator` 的消费者可以调用 `.return()`，此时不一定经过普通 `catch`。源码专门用三层措施兜底：

1. `AbortSignal.any(...)` 把外部取消和内部硬超时合并；
2. `abortableNext()` 用 `Promise` 竞争 `iter.next()` 与 abort，解决普通 `for await` 卡在下一条消息时无法及时退出的问题；
3. `finally` 检查 `!didWriteAudit && !hadError && !didComplete`，补写 `generator_returned_without_completion` 的 `CAT_ERROR` 审计。

这就是 `invoke-single-cat-finally-audit.test.js` 中“force-returned mid-stream 仍写 fallback CAT_ERROR”以及“catch 已写错误时不重复写”的来源。

**读图方法：每一行都必须落到 finally。** 区别只在进入 finally 前，哪个状态标志已经被设置、终态审计由谁写。

## 4. 关键算法与判定逻辑

### 4.1 `preflightRace`：给所有前置 IO 加天花板

**这一节解决“还没启动 Agent，读取 Redis 等前置操作就永久卡住”的问题。** `Promise.race` 可以理解为让三个参赛者同时等待：真正的存储请求、30 秒超时、用户取消；谁先有结果就采用谁。

代码中的泛型 `<T>` 只表示“它可以包装任何返回类型的 Promise”；`Promise<never>` 表示超时分支不会返回正常值，只会抛错；`.finally(cleanup)` 保证不论谁获胜都清掉计时器。

两段英文注释的中文是：**这个计时器必须让 Node 进程保持存活，直到前置检查的超时保护真正触发；如果对它调用 `unref()`，当原存储 Promise 永远没有结果时，Node 可能提前退出，保护逻辑反而没有机会执行。** 这与调用级长计时器使用 `unref()` 的目的相反，场景不同，选择也不同。

另一句限制 `The original promise is NOT cancelled` 的中文是：**race 只是不再等待输掉的原 Promise，并没有通用办法把它取消；它可能仍在后台完成。** 所以真正有副作用的 IO 最好自身支持 AbortSignal 或幂等。

**面试掌握线：**讲清“真实 IO、超时、取消三者赛跑”和“race 不等于取消原任务”。泛型语法与 timer 的 unref 对比能看懂即可。


【源码】invoke-helpers.ts:139-184

```ts
export const PREFLIGHT_TIMEOUT_MS = Number(process.env.CAT_CAFE_PREFLIGHT_TIMEOUT_MS) || 30_000;

export async function preflightRace<T>(promise: Promise<T>, label: string, signal?: AbortSignal): Promise<T> {
  if (signal?.aborted) throw signal.reason;
  let timer: ReturnType<typeof setTimeout> | null = null;
  const cleanup = (): void => { if (timer) clearTimeout(timer); };
  const timeoutPromise = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`preflight_timeout: ${label}`)), PREFLIGHT_TIMEOUT_MS);
    // 必须让进程存活到前置检查的超时守卫真正触发。
    // 如果对这个 timer 调用 unref，而被 race 的原 Promise 永不结束，Node 可能提前退出。
  });
  const parts: Promise<T | never>[] = [promise, timeoutPromise];
  if (signal) {
    parts.push(new Promise<never>((_, reject) => {
      signal.addEventListener('abort', () => reject(signal.reason), { once: true });
    }));
  }
  return Promise.race(parts).finally(cleanup);
}
```

存在理由的注释写得极清楚：

> 源码注释中文意：没有这道保护时，一个卡死的 Redis/存储操作会无限阻塞生成器，导致 `finally` 永远不运行、`InvocationTracker` 永远不清理，最终 thread 会一直显示为忙碌。
> 【源码】invoke-helpers.ts:130-133

**"thread 永久 busy"是这个系统里最难受的故障态**：用户看到猫在转圈，但什么都不会发生，也没法取消。根因是 generator 卡在一个不会 settle 的 await 上，`finally` 永远不执行。

两个细节：

1. **`label` 参数**：错误消息是 `preflight_timeout: sessionManager.get`，直接指出卡在哪一步。调用点有四处（`sessionManager.get` / `threadStore.get` / `isRebornSession` / 会话链查询）。
2. **这里的 timer 故意不 unref**（和 §3.2 的调用超时相反！）。注释解释了：`Keep the process alive until the preflight guard actually fires. Unref'ing this timer lets Node exit early when the raced promise never settles.` —— **如果 unref 了，Node 会在"被 race 的 promise 永不 settle"时提前退出，守卫就白设了。** 同一个 API 在两个地方要相反的用法，这种对比是很好的面试素材。

`Promise.race` 的三方参与者：原 promise / 超时 / abort。注意 **原 promise 不会被取消**（注释：`The original promise is NOT cancelled (no way to do so generically)`）——它还在后台跑，只是没人等它了。**这是 JS 里 race 的固有限制，诚实地写在注释里而不是假装解决了。**

### 4.2 错误分类的七个纯函数

**这一节是在把各家 CLI 五花八门的错误文字，归一成系统能采取动作的错误类别。** “纯函数”指只根据输入算结果，不写 Redis、不启动 CLI；因此很适合用大量输入样例做单元测试。

### 4.3 `_needsReinjection` 与 `_staticIdentityRegistryRevision`：两个模块级 Map

**这一节讲两个进程内的小记事本。** 一个记“某个用户/Agent/thread 下次需要补注身份”，另一个记“上次注入身份时 registry 是哪个版本”。`Map` 就是键值表，组合 key 用来隔离不同会话。

### 4.4 workspace fingerprint：防止 resume 到错误的工作区

**这一节防止“模型记忆来自项目 A，本轮却在项目 B 的目录继续执行”。** fingerprint 是把规范化后的工作目录做成稳定标识，恢复 session 前对比旧值和当前值；不一致就放弃 resume，开新会话。

这不是为了防密码碰撞，而是快速、稳定地比较“是不是同一个工作区”。路径规范化还要处理大小写、分隔符和相对路径等表现差异，避免同一目录被误判成不同。

系统放弃 resume 时还会输出结构化诊断，把旧目录、新目录、旧指纹、新指纹和原因都留下。因为“丢弃旧上下文”会影响用户，必须能够解释系统为什么这样决定。

**面试掌握线：**一句话说清“session 与 workspace 绑定，目录不匹配宁可新开，防止跨项目上下文污染”。诊断 JSON 字段无需背。

### 4.5 `getOpenCodeKnownModels`：进程级缓存 + 静默失败

**这一节是在调用 `opencode models` 查询可用模型，并把结果缓存起来。** `null` 表示“还没查”，空 `Set` 表示“已经查过，但失败或没有结果”，二者不能混为一谈，否则失败后每个请求都会重新阻塞查询。

`execFileSync` 会同步阻塞当前 Node 线程，通常不是服务端首选；这里用“进程内只执行一次 + 5 秒超时”限制影响。`stdio: ['ignore', 'pipe', 'ignore']` 分别表示忽略标准输入、捕获标准输出、忽略标准错误。

“静默失败”表示查询失败时不让主调用失败，而是返回空集合。这适用于模型列表这种增强判断；如果查询的是必需凭据，就不能采用同样策略。

**面试掌握线：**这是维护者级旁支。知道缓存区分“未加载”和“加载为空”，以及同步调用通过一次缓存和超时控制风险即可，不建议主动展开。


【源码】116-147

```ts
let _openCodeKnownModels: Set<string> | null = null;

  if (_openCodeKnownModels !== null) return _openCodeKnownModels;
  try {
    const opencodePath = resolveCliCommand('opencode');
    if (!opencodePath) { _openCodeKnownModels = new Set(); return _openCodeKnownModels; }
    const stdout = execFileSync(opencodePath, ['models'], {
      encoding: 'utf-8', timeout: 5000, stdio: ['ignore', 'pipe', 'ignore'],

    _openCodeKnownModels = new Set(stdout.trim().split('\n').map((line) => line.trim()).filter(Boolean));
```

**这是"用子进程当配置源"的最小实现。** 值得注意的是它同步阻塞（`execFileSync`）——在 Node 服务里同步调子进程是要挨骂的，但因为有缓存所以只在进程内第一次调用时发生一次，5 秒上限。**这是"明知不优雅但影响可界定"的实用主义取舍**，比起改成异步要传染一整条调用链，这里选了简单。面试里这样讲比装作没看见强。

### 4.6 Antigravity 运行时会话的重试碎片标记

**这一节处理某个特殊载体内部自动重试时产生的临时 session 记录。** 对业务来说它仍是一次任务；对底层载体来说，容量不足、空响应或断连可能创建多个运行时 session。系统要给这些碎片标明原因，避免把它们误看成用户主动开启了多个会话。

幂等守卫检查“这个记录是否已经用同一原因封存”。如果是，就不重复封存。幂等的意思是同一个动作执行一次和多次，最终效果相同；它是 webhook 重放、重试和并发处理中的常见要求。

**面试掌握线：**这是特定 Provider 的实现细节，当前可以跳过。只保留一个概念：底层自动重试产生的记录要与真正的业务会话切换区分，并保证重复处理安全。

| 场景 | 输入/前置状态 | 必须观察的状态变化 | 关键断言 |
|---|---|---|---|

| resume 后 timeout，未有实质输出 | 有旧 session，仅 system_info | 丢弃/不再使用旧 session，fresh retry | Provider 被调用第二次，第二次不带旧 session |

| 用户提前停止迭代 | consumer 调 generator `.return()` | 普通 catch 可能不执行，finally fallback 生效 | 写一次 `generator_returned_without_completion` |
| task progress 存储失败 | done 正常，但 finalize store throw | 主调用仍正常完成 | 不向用户额外输出存储错误 |

## 6. 可观测性：出问题怎么查

**这一节回答的不是“代码怎样正常运行”，而是“线上坏了以后凭什么定位”。** 可观测性主要有三种证据：日志告诉你某个时刻发生了什么，审计记录业务事件，指标和 trace 告诉你整体数量、耗时及调用链。

### 6.1 日志关键字索引

**先按同一个 `invocationId` 搜索，再看创建、调用前快照、重试、终态。** 不要一上来全库搜中文报错，因为同一句错误可能来自很多调用。日志中的结构化字段比拼接文本更适合过滤。

排障顺序可以固定为：有没有 `Created invocation`；有没有到达 `service.invoke()` 前快照；是否触发 retry/timeout；最后是否出现完成或 fallback audit。这样可以快速判断卡在前置、Provider 还是收尾。

**面试掌握线：**会说“用 invocationId 串联同一次执行，先定位阶段再看具体错误”。关键字表现场查，不背。

| 要查什么 | 关键字 / 字段 |
|---|---|
| 调用创建 | `'Created invocation'` + `{ invocationId, catId, threadId, userId }` |
| 调用前上下文快照 | `'[invocation] service.invoke() — full context before subprocess launch'` |
| session 解析结果 | `{ sessionId, isResume, injectSystemPrompt, forceReinjection }` 在同一行 |
| 自愈重试 | `'cat retrying invoke (session self-heal)'` + `{ reason, retryReason, attempt, hadSessionId }` |
| 瞬时重试 | `'cat retrying invoke (transient CLI exit)'` |
| 调用超时 | `'Invocation hard timeout fired'` + `{ timeoutMs }` |
| malformed 封板 | `'[F215] Sealed malformed session for fresh-context retry'` |
| malformed 兜底 | `'[F215] Malformed tool-call recovery exhausted — emitting 46接力 card (AC-C3)'` |
| 代理不可达 | `'Proxy unreachable, falling back to direct upstream'` |
| reborn 会话 | `'#836: reborn session strategy — forcing new session'` |
| 工作区不匹配 | `type: 'opencode_resume_workspace_guard'` 的 system_info |
| 治理门禁拦截 | `type: 'governance_blocked'` 的 system_info |
| generator 被掐 | `'Finally fallback CAT_ERROR audit write failed'` 或事件日志里 `generator_returned_without_completion` |
| 云猫短路 | `'F247 KD-17: cloud-only cat (Remote MCP) — skipping local dispatch'` |
| 桥没接通参数 | `'F247 AC-B1c-2: bridge wired but mentionContent/mentioningCatId missing (PR-C will plumb)'` |

### 6.2 审计事件三件套

**审计事件是业务账本：开始过、成功响应过、失败过。** 它和普通 debug 日志的区别是事件类型稳定、字段固定，适合事后对账或安全调查。

`promptDigest` 是 prompt 的摘要而不是全文，目的是支持关联和比对，又尽量避免把用户完整指令及敏感内容写进审计。`fire-and-forget` 写审计表示不阻塞主调用，但写失败必须留告警。

**面试掌握线：**知道 `CAT_INVOKED -> CAT_RESPONDED/CAT_ERROR`，并能解释为什么要防重复终态审计。

| 事件 | 触发时机 |
|---|---|
| `CAT_INVOKED` | 函数入口，fire-and-forget，`promptDigest`（不是 prompt 全文）|
| `CAT_RESPONDED` | 流里收到 `done` 且 `!hadStreamError` |
| `CAT_ERROR` | ① catch 块（`hadError=true`）/ ② `done` + `hadStreamError` / ③ finally 兜底 |

**注意 `CAT_ERROR` 有三个来源** —— 事后看事件流时，`didWriteAudit` 防止 ①③ 重复写，但 ②（流里报错但还能走到 done）走的是 processMessage 里的分支，和 ① 路径不重叠。

### 6.3 遥测 Instruments（OTel）

**OTel 是 OpenTelemetry，一套统一记录指标和调用链的标准。** Counter 只累计次数，UpDownCounter 可以加减表示当前并发数，Histogram 收集耗时分布，Span 表示一段操作的起止和父子关系。

最值得理解的是两个耗时：`invocationDuration` 包含 session、目录、凭据等全部前置与收尾；`llmCallDuration` 更接近 Provider/模型实际调用时间。两者差距大，说明慢点可能不在模型，而在 Redis、目录检查或队列等外围步骤。

**面试掌握线：**不用背 instrument 名。能区分“总调用耗时”和“模型耗时”，并知道 active 数必须在 finally 中减回去即可。

| Instrument | 类型 | 触发 |
|---|---|---|
| `catInvocationCount` | Counter | 调用创建时，按 `triggerType`（mention/routing/default）分 |
| `activeInvocations` | UpDownCounter | try 入口 +1，finally -1 |
| `invocationDuration` | Histogram | finally，秒 |
| `invocationCompleted` | Counter | finally，按 `status`（ok/error）|
| `catResponseDuration` | Histogram | finally，秒 |
| `threadDuration` | Histogram | finally，从 `thread.createdAt` 算，有值才记 |
| `llmCallDuration` | Histogram | processMessage 里，从 `done.metadata.durationMs` 读 |
| `tokenUsage` | Counter | processMessage 里，`input_tokens` + `output_tokens` 分开记 |
| `sessionRounds` | Histogram | 每次 `messageCount` 自增时 |
| `geminiContextFallback` | Counter | Gemini 的 context window fallback 路径 |

**`invocationDuration` 和 `llmCallDuration` 的差**：前者含所有 preflight；后者只含"provider 实际跑了多久"（从 provider 的 `done.metadata.durationMs` 读）。两者相减 ≈ 本文讲的这一切"前置工作"的开销。

## 7. 面试追问应对

**下面原答案深度偏高，使用时不要全部倒给面试官。** 你的安全说法是：先给 30 秒主线；对方追问哪个点，再展开那个点；没亲手实现的设计统一说“我读源码后的理解是”。

适合你主动准备的只有四题：一次调用流程、为什么不能盲目重试、取消如何收尾、session 为什么不能无条件 resume。prompt 四层和所有 Provider 特例作为追问材料。

**不要说：**“我设计了这套两层超时/重试机制。”  
**可以说：**“我在源码中重点研究了它的调用生命周期，并用安全测试思路整理了超时、重放和资源释放的风险。”

**Q: 最复杂的一段代码是哪里？怎么理解它？**

A: `invoke-single-cat.ts` 的 `invokeSingleCat`，3599 行，一个 generator 函数。它是全项目所有"跟真实世界打交道的脏活"的汇聚点，按照我的理解分成 12 个阶段：云猫短路、invocationId 注册、两层超时合并、session 四道解析（Redis 读 + 封板检查 + reborn + mutex）、三道 preflight（工作区 / 共享态 / 治理）、账号凭据注入、effectivePrompt 四层 prepend、消息处理管线、两次重试 + 六类错误抑制、catch 审计、finally 八项补偿。每一段都能单独说出"它为什么这么复杂、它防的是哪种真实故障"。

**Q: generator 被 `.return()` 掐断怎么处理？**

A: `finally` 块用三个标志位的组合识别这条路：`!didWriteAudit && !hadError && !didComplete`。正常完成置 `didComplete`，catch 里报错置 `hadError + didWriteAudit`，干净退出（排队时取消）也置 `didComplete`——三个都不置就是被掐了，写兜底审计 `generator_returned_without_completion`。这是全函数里我认为最精妙的一处，因为它把"一个 generator 的三条出口"用三个布尔量完整覆盖了。

**Q: 为什么要用 `abortableNext` 而不是 `for await`？**

A: `for await` 会永久阻塞在 `gen.next()` 上，没有任何办法打断。`abortableNext` 把 `gen.next()` 和 AbortSignal 赛跑，信号先到就 reject，并且在两个分支都 `removeEventListener`——不摘监听器的话长会话会挂几千个回调，内存泄漏。这是 JS 里"如何取消正在等待的 async iterator"的一个完整答案。

**Q: 重试逻辑的核心判断是什么？**

A: 关键门槛是 `attemptHasContentOutput` 和 `attemptHasSubstantiveOutput`——有内容输出时不允许重试，因为重试 = 重放 prompt，会重复副作用。六类错误对这个门槛的依赖各不相同：session 类的三个都要求无内容输出；malformed 也是；只有瞬时 CLI 退出允许有 system_info 存在（不算"内容"）。用两个布尔量区分"真正的内容"和"系统信号"，这个区分是被 F215 hotfix 逼出来的。

**Q: session 解析为什么这么复杂？**

A: 四道处理里面，我认为最有价值的一条判断原则是注释里那句：*"Lost resume is recoverable; sealed-session corruption is not."* 两个失败模式比大小，选可恢复的。Redis 读不到、chain 对不上、reborn 策略——每一道都是在解决"resume 进错会话比不 resume 更糟"这个问题。mutex 那道是解决"两个请求同时 resume 同一个 CLI 会话会写坏 rollout JSONL"——这个不加锁的话是必现的并发 bug，不是概率问题。

**Q: 你说子进程会超时，那超时怎么设计的？**

A: 两层。内层是 CLI 超时（Provider 管，NDJSON 流空闲判定），外层是调用级硬超时 = 内层 × 2。两层分开是为了保证"内层先报错、外层兜底"的顺序是确定的。有三类消息不重置外层超时：`provider_signal`、`liveness_signal`、`status`——不重置的原因是防止"只发心跳不干活"的子进程续命。硬超时用的 `AbortSignal.any([callerSignal, invocationAc.signal])` 合并了用户取消和超时两个信号，两个都能打断，而且 reason 保留，下游能区分。

**Q: effectivePrompt 怎么组装的？**

A: 四层 prepend + 一个尾部 append。每一层都有独立的注入条件，最重要的是要区分"只在新会话注入"（staticIdentity）和"每轮必注入"（staging / contextHint / missionPrefix）——前者在 resume 时跳过，后者不能跳过。两类"每轮必注"还要独立于 `injectSystemPrompt` 判定，因为 `injectSystemPrompt=false`（resume 跳过身份）时它们仍然需要在场。这个区分是被 ADR-038 的"每轮注入生效"契约和 F225 的"压缩后补提示"两个需求共同逼出来的。

**Q: 这里有什么安全隐患？**（我的安全背景）

A: 我看到三处值得关注：①callbackEnv 把 `CAT_CAFE_CALLBACK_TOKEN` 传给子进程——这是设计需要，但 token 的有效期和轮换机制要看 `InvocationRegistry`，如果 token 不过期且可重放就有问题；②账号凭据（API key）通过 `callbackEnv` 传环境变量——子进程可以通过 `/proc/self/environ` 或日志泄露，`maskEnv` 这个函数在 debug 日志里会遮掉值（3024），但只有 debug 级才走，生产 info 日志里呢？③ `workingDirectory` 用了 `validateProjectPathDetailed` 验证，防的是路径遍历，但允许的 root 范围够严格吗？这些是我实际研究后的怀疑，不一定是真洞，需要进一步看。

| `INVOCATION_TIMEOUT_MULTIPLIER` | `2` | 外层超时 = CLI 超时 × 2 |
| `PREFLIGHT_TIMEOUT_MS` | `30_000`（可覆盖） | 每个前置 IO 的上限 |
| `maxAttempts` | `2` | 重试上限（共 2 次） |
| `ANTIGRAVITY_AUTOMATIC_RETRY_FRAGMENT_REASONS` | 5 个 | 哪些原因触发 Antigravity 重试碎片标记 |

### 8.3 六类错误抑制速记

**六类只是在实践中落地同一条规则：先判断是否可恢复，再判断是否已经有副作用。** 你的最低掌握线是 session 失效可在无产出时 fresh retry；认证失败、上下文满或已经执行工具不能无脑重试。

```
1. 会话不存在  → 丢 session，重试
2. prompt 超 token  → 同上（须无内容输出）
3. 上下文溢出 → 同上（须无内容输出）
4. 瞬时 CLI 退出 → 原样重试（须无内容输出）
5. CLI 超时（有 session，无实质输出）→ 丢 session，重试（#774）
6. malformed tool call → 封板 + 丢 session，重试；再失败 → 46 接力卡片
```

`attemptHasContentOutput` = text / tool_use / tool_result 出现过  
`attemptHasSubstantiveOutput` = 同上 + 不含 system_info

### 8.4 finally 八件事

**八项可再压成三类：资源、业务终态、观测终态。** 资源包括 timer、mutex、临时目录和孤儿 span；业务终态包括审计和任务进度；观测终态包括指标、pane 状态和 span。这样比按顺序背八行更容易迁移到其他后端项目。

```
1. toolSpanTracker.endAllOrphans('aborted')
2. clearTimeout(invocationTimer)
3. sessionMutexRelease?.()
4. rm(openCodeRuntimeConfigDir)  [OpenCode only]
5. 兜底 CAT_ERROR 审计  [当 !didWriteAudit && !hadError && !didComplete]
6. finalizeTaskProgress()
7. 遥测（六个 instruments）
8. agentPaneRegistry 状态标记 + invocationSpan.end()
```
