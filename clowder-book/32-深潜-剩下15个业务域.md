# 32 · 深潜：剩下 15 个业务域

> 前面的章节把编排、记忆、纪律讲透了 —— 那是 `domains/` 下的 7 个域。
> **还有 15 个域没碰过。**
>
> 这一篇不是要把它们都讲深，而是解决两个具体问题：
> ① 面试官问"这项目还有什么模块"时不至于哑口；
> ② **更重要的** —— 这 15 个域揭示了一件事：
> 这个项目有一套稳定的内部架构范式，**新功能都是按同一个骨架长出来的**。
> 能说出这套范式，比能背出 22 个域的名字有用得多。

---

## 1. 为什么这一篇值得读

### 场景一：被问到"还有什么"

```
面试官："你讲的路由、记忆这些是核心。这项目还有别的模块吗？"
答不上来 → 显得只读了一条主线
```

### 场景二：被问到"这项目怎么扩展新功能"

**这是更好的问题，也是这一篇真正的价值。**

我读完这 15 个域最强的感受是：**它们长得很像。**

```
纯函数状态机（表驱动）+ 事件日志 → 投影器
Interceptor 两段式（prepare 一次 + per-cat 一次）
可选依赖 fail-open
Port/Adapter 抽象存储
从现有 id 派生 key，不引入新原语
```

**这五个模式在 15 个域里反复出现。** 说明这个项目有"范式"，
新功能不是各自发明轮子。

**面试话术**：

> "我读完之后发现一件事比功能清单更有意思：
> 这个项目有一套很稳定的内部范式，22 个 domain 里的新功能基本都按同一个骨架长 ——
> 纯函数状态机 + 事件投影、interceptor 两段式、可选依赖 fail-open、
> port/adapter 抽存储、key 从现有 id 派生。
>
> **所以'加一个新功能'的成本是可预测的**，
> 而且新人读第三个域的时候就已经认得那个骨架了。
> 我觉得这是大型项目里比任何单个设计都重要的东西。"

## 3. 逐域拆解

### 3.1 community —— 社区事务编排（F168）

**做什么**：把 GitHub 上的 issue / PR 变成可编排的"事务对象"，
自动分诊、路由给合适的 Agent、跟踪到关闭。

**关键文件与设计**：

```
community-state-machine.ts     ★ 表驱动纯函数状态机
community-projector.ts         事件 → 投影
CommunityEventLog.ts           事件日志
CommunityObjectStore.ts        投影存储
TriageOrchestrator.ts          分诊编排
GuardianMatcher.ts             找"守护者"（谁负责）
RoleResolver.ts                角色解析
NarratorDriver.ts              叙事驱动（把事务变成可读的进展叙述）
RedisNarratorDedupStore.ts     叙事去重
GitHubIssueFetcher/Publisher.ts   GitHub 双向
GitHubPrFetcher.ts
CommunityReconciler.ts         对账
community-sla-policy.ts        SLA 策略
community-decision-queue.ts    决策队列
community-closure-checklist.ts 关闭检查表
resolveConsensus.ts            共识解析
```

**最值得讲的是它的状态机不变量**【源码】：

```ts
/**
 * Closure invariant (P1#3 from codex review, Phase A must enforce):
 *   `fixed` → `closed` requires EITHER:
 *     - snapshot.lastPublicCommentAt != null  (case.reported path)
 *     - snapshot.closureWaiver != null         (explicit waiver)
 *   Violation → { ok: false, reason: 'closure_invariant' }
 */
```

**大白话**：一个社区 issue 从"修好了"到"关闭"，
**必须满足两个条件之一**：要么已经公开回复过报告者，要么有显式的豁免记录。

**为什么这条规则重要？**

```
Agent 修好了一个社区报告的 bug
  → 直接关 issue
    → 报告者不知道修了、不知道怎么验证
      → 社区体验极差（"我提的 issue 被默默关了"）
```

**这条不变量把"社区礼貌"变成了状态机的硬约束。**

还有一条防重放的设计【源码】：

```ts
// P1-5 fix: "opened" events (plan: 仅当无既有状态) only valid from 'new'
// This prevents webhook retries from resetting an already-routed/fixed case.
// issue.reopened intentionally uses '*' — it is an explicit user re-open action.
'issue.opened': { from: new Set<CommunityObjectState>(['new']), to: 'new' },
'issue.reopened': { from: '*', to: 'new' },
```

**`issue.opened` 只能从 `new` 状态进，但 `issue.reopened` 可以从任何状态进。**

区别是：`opened` 是 webhook 可能重复投递的**系统事件**（要防重放），
`reopened` 是用户的**显式动作**（该允许）。

**同一个"进入 new 状态"的转移，因为事件来源不同而有不同的 from 约束** ——
这个区分很讲究。

**面试可讲的点**：

> "community 域有个设计我觉得挺有意思。
> 它是个表驱动的纯函数状态机（和球权那个同一个范式，
> 而且球权的注释里明说是'照 community-state-machine 的模式'——
> 所以这个模式在项目里被复用了至少两次）。
>
> 它有一条业务不变量：从'已修复'到'已关闭'，
> **必须要么公开回复过报告者、要么有显式豁免记录**，
> 否则状态机直接拒绝转移。
> 这把'别默默关掉别人提的 issue'这条社区礼貌变成了代码约束。
>
> 还有个细节：`issue.opened` 只允许从 `new` 状态进（防 webhook 重放），
> 但 `issue.reopened` 允许从任何状态进（那是用户显式动作）。
> **同一个目标状态，因为事件来源不同而有不同的准入约束。**"

**这个域也是全项目"运营闭环未上线"的例子** ——
ROADMAP 里 F168 的状态是 `infra-complete / ops-gap`，
【源码】说明基础设施做完了但运营流程没跑起来。

**这和 [17 章](17-如果重新设计.md) §3 说的"机制建好了但没被用"是同一类问题。**

### 3.2 signals —— 情报管线

**做什么**：定时抓取信息源（RSS / API / 网页）→ 去重 → 富化 →
存档 → 生成日报（邮件 + 站内通知）→ 可以被 Agent 检索和讨论。

**架构是很标准的抓取管线**：

```
config/
  sources-tier1-china.ts      ★ 信息源按"层级 + 地域"分文件
  sources-tier1-global.ts
  sources-tier2-community.ts
  sources-papers.ts
  sources-loader.ts / notifications-loader.ts / signal-paths.ts
fetchers/
  rss-fetcher.ts / api-fetcher.ts / webpage-fetcher.ts   ★ 三种抓取策略
  types.ts（Fetcher 接口）
services/
  fetch-scheduler.ts          调度 + 汇总
  source-processor.ts         processSources / selectSources
  deduplication.ts            去重
  enrich-article.ts           富化
  article-store.ts / article-query-service.ts / article-document.ts
  evidence-pack.ts            ★ 打包成证据（接入记忆系统）
  email-service.ts / in-app-notification.ts
  podcast-generator.ts        ★ 生成播客音频
  signal-thread-lookup.ts     关联到讨论帖
  study-meta-service.ts       学习模式元数据
templates/daily-digest.ts
```

**三个设计点值得讲**：

**① 信息源按 tier 分层，而且 tier 影响可信度**

`sources-tier1-china` / `tier1-global` / `tier2-community` / `papers`——
这个分层不只是组织代码，它对应 [09 章](09-模块-记忆与检索.md) 里
`SignalArticle` 的 `tier` 字段，**而 tier 会进 prompt**：

```ts
// InvocationContext（模块 07）
activeSignals?: readonly {
  readonly id: string;
  readonly title: string;
  readonly source: string;
  readonly tier: number;      // ← 这里
  readonly contentSnippet: string;
  // ...
}[];
```

**所以 Agent 看到一篇情报时，知道它的来源可信度等级。**

**② 抓取器是策略模式**

```
Fetcher 接口 → RssFetcher / ApiFetcher / WebpageFetcher
```

**加一个新信息源类型 = 加一个 Fetcher 实现。**

**③ 调度结果是结构化汇总**【源码】：

```ts
export interface SignalFetchSchedulerSummary {
  readonly dryRun: boolean;
  readonly fetchedAt: string;
  readonly processedSources: number;
  readonly skippedSources: number;
  readonly fetchedArticles: number;
  readonly newArticles: number;
  readonly storedArticles: number;
  readonly duplicateArticles: number;
  readonly errors: readonly FetchError[];
  readonly notifications?: { email: EmailSendResult; inApp: InAppNotificationResult } | ...;
}
```

**注意 `dryRun` 是第一个字段** ——
和 [16 章](16-模块-存储与部署.md) 里"恢复默认 dry-run"、
Skills 同步的 dry-run 一致：**这个项目的所有批量写操作都有 dry-run。**

**面试可讲的点**：

> "signals 是个标准的抓取管线，但有两个细节我觉得可以讲。
>
> 一是**信息源分 tier**（tier1 国内 / tier1 全球 / tier2 社区 / 论文），
> 而这个 tier 会跟着文章一路进到 Agent 的 prompt 里 ——
> 所以 Agent 看到一篇情报时知道它的可信度等级。
> **这和记忆系统里'权威度'的思路是一致的：可信度是数据的一部分，不是隐含的。**
>
> 二是调度返回的汇总结构里 `dryRun` 是第一个字段。
> 我注意到这个项目**所有批量写操作都有 dry-run** ——
> Skills 同步、Redis 恢复、配置同步都是。这算是个团队习惯。"

### 3.3 packs —— 第三方能力包（F129 / ADR-021）

**做什么**：让第三方能给 Agent 装"包" —— 人格面具、硬约束、
默认行为、工作流、世界驱动、知识库。**本质是 Mod 生态。**

**这个域是全篇最值得深讲的**，因为它直面一个尖锐的安全问题：
**怎么让第三方修改 Agent 的行为，但不能篡改它的身份和底线？**

**编译而不是注入**【源码】：

```ts
/**
 * F129 PackCompiler — Schema → Canonical Prompt Blocks
 * Compiles validated pack content into prompt blocks for SystemPromptBuilder.
 *
 * AC-A3: compile to canonical prompt blocks (not raw YAML injection)
 * AC-A6: dual-track trust boundary (guardrails = hard; defaults = overridable)
 *
 * Compilation mapping (ADR-021 §5):
 * - masks/      → masksBlock (role overlay)
 * - guardrails  → guardrailBlock (硬约束轨)
 * - defaults    → defaultsBlock (默认行为轨)
 * - workflows/  → workflowsBlock (声明式流程提示)
 * - knowledge/  → skip (RAG, not prompt)
 * - expression/ → skip (assets)
 * - bridges/    → skip (Phase B)
 * - world-driver→ worldDriverSummary (read-only)
 * - capabilities→ already rejected by PackSecurityGuard
 */
```

**三个关键设计：**

**① "compile to canonical prompt blocks (not raw YAML injection)"**

**不是把第三方的 YAML 原样塞进 prompt**，而是经过 schema 校验 + 编译。
这样第三方只能填预定义的槽位，不能注入任意文本结构。

**这和 [07 章](07-模块-身份注入.md) 的 L0 编译是同一个思路** ——
**编译 > 注入**。

**② 双轨信任边界：guardrails 是硬的，defaults 可覆盖**

```
guardrails → 硬约束轨（第三方只能加严，不能放松）
defaults   → 默认行为轨（Agent 可以覆盖）
```

**这个区分很重要**：第三方包想说"在我的场景下要更谨慎"是合理的，
想说"在我的场景下可以不管安全规则"是攻击。

**③ 安全守卫的三道防线**【源码】：

```ts
/** Prompt injection blocklist — patterns that must never appear in pack content */
const INJECTION_PATTERNS: RegExp[] = [
  /ignore\s+(all\s+)?(previous|above|prior)\s+instructions/i,
  /you\s+are\s+now\b/i,
  /from\s+now\s+on\s+you\b/i,
  /forget\s+(everything|all|your)/i,
  /system\s+prompt/i,
  /reveal\s+your/i,
  /show\s+me\s+your\s+instructions/i,
  /override\s+(your|the)\s+(rules|identity|constraints|personality)/i,
  /do\s+not\s+follow/i,
  /disregard\b/i,
  /bypass\b/i,
];

/** Constraint relaxation patterns — guardrails must only add strictness */
const RELAXATION_PATTERNS: RegExp[] = [
  /\b(allow|permit|enable)\s+(any|all|unrestricted)/i,
  /\brelax\b/i,
  /\bremove\s+restriction/i,
  /\bdisable\s+(guardrail|constraint|safety|filter)/i,
  /\bno\s+(limits?|restrictions?|boundaries)\b/i,
];
```

**第二组正则是我在整个项目里见过最有意思的安全设计之一：
它检测"约束放松的方向"。**

普通的 injection 检测是"有没有恶意模式"。
这个是"**你说的话是让约束变严还是变松**"——
guardrails 只允许变严，出现"relax""remove restriction""no limits"就拒绝。

**第三道是身份字段不可变**【源码】：

```ts
/**
 * Identity fields that masks must never set (KD-3 + F093 KD-12 five-layer classification).
 * L1 (routing identity): catId, family, breedId, name→displayName, nickname, mentionPatterns
 * L2 (infrastructure): provider, model, defaultModel, contextBudget, cli, mcpSupport
 * Note: mask's own 'id' and 'name' fields are valid (mask identity, not cat identity).
 */
const IMMUTABLE_FIELDS = new Set([
  // L1: Routing identity — never overridable
  'catId', 'family', 'breedId', 'displayName', 'nickname',
  // ...
]);
```

**五层身份分类**，L1（路由身份）和 L2（基础设施）不可覆盖。

**为什么 `family` 必须不可变？**
因为 [11 章](11-模块-跨模型互审.md) 的跨模型互审靠 `family` 判定 ——
**如果第三方包能改 family，就能绕过"不能自审"的铁律。**

**注意那句注释里的细节**：
`mask's own 'id' and 'name' fields are valid` ——
面具自己的 id 和 name 是合法字段，只是不能设**猫的** displayName。
**同名字段在不同上下文下语义不同，这个区分必须写清楚，否则会误拦。**

**面试可讲的点（这段很有杀伤力）**：

> "packs 这个域直面一个尖锐问题：**怎么让第三方修改 Agent 行为，
> 但不能篡改它的身份和底线？**
>
> 三道防线：
>
> 一，**编译而不是注入**。第三方的 YAML 要过 schema 校验再编译成
> 预定义的 prompt block，不能原样塞进 prompt。
> 注释里写的是 'compile to canonical prompt blocks (not raw YAML injection)'。
>
> 二，**双轨信任边界**。硬约束轨（guardrails）第三方只能加严不能放松，
> 默认行为轨（defaults）可以被 Agent 覆盖。
> 而且有一组正则专门检测'约束放松的方向'——
> 出现 relax、remove restriction、no limits 这类词就拒绝。
> **一般的 injection 检测是找恶意模式，这个是判断你说的话让约束变严还是变松。**
> 我觉得这个思路挺妙。
>
> 三，**身份字段白名单不可变**。做了五层身份分类，
> L1 路由身份（catId、family、displayName、mentionPatterns）
> 和 L2 基础设施（provider、model、cli）都不能被面具覆盖。
>
> 第三道尤其关键：**如果第三方能改 `family` 字段，
> 就能绕过'跨模型互审不能自审'的铁律** ——
> 因为那条规则是靠 family 判定的。安全边界是有连锁的。"

### 3.4 world —— 世界共创引擎（F093）

**做什么**：多 Agent 一起搭一个"世界"（角色、场景、设定），
支持叙述、对话、修改角色定义、提议/裁定"正史"（canon）。

**关键设计：模式 × 动作白名单**【源码】：

```ts
const MODE_ACTION_ALLOWLIST: Record<string, string[]> = {
  build: [
    'narrate', 'perform_dialogue', 'edit_character_definition',
    'update_character_state', 'propose_canon', 'decide_canon',
    'transition_scene', 'care_check_in',
  ],
  perform: [
    'narrate', 'perform_dialogue', 'update_character_state',
    'propose_canon', 'decide_canon', 'transition_scene', 'care_check_in',
  ],
  replay: [],
};
```

**三种模式**：
- `build`（搭建）—— 什么都能做，包括改角色定义
- `perform`（演出）—— **不能改角色定义**（`edit_character_definition` 不在列表里）
- `replay`（回放）—— **什么都不能做**（空数组）

**这是很干净的权限模型**：不是"检查这个动作允不允许"，
而是"这个模式下有哪些动作"—— **白名单而不是黑名单。**

**幂等键的作用域**【源码】：

```ts
async execute(envelope: WorldActionEnvelope): Promise<ExecuteResult> {
  const scopedKey = `${envelope.worldId}:${envelope.sceneId}:${envelope.idempotencyKey}`;
  if (this.processedKeys.has(scopedKey)) {
    return { events: [] };
  }
  this.processedKeys.add(scopedKey);
  // ...
}
```

**幂等键带了 worldId 和 sceneId 前缀** ——
同一个 idempotencyKey 在不同世界/场景里是不同的操作。

**这和 [10 章](10-模块-球权状态机.md) 里
`sourceEventId` 要追加 `toCatId` 是同一类修正**：
**幂等键的作用域必须和"什么算同一次操作"完全对应。**

其他文件：

```
SqliteWorldStore.ts        ★ 又一个 SQLite（不只记忆用 SQLite）
schema.ts                  世界的表结构
action-handlers.ts         动作分派
```

### 3.5 limb —— 远程执行节点（F126）

**做什么**：让 Agent 能调用本机之外的执行能力（手机、另一台电脑、
外部服务）。项目管这叫"四肢"。

**核心是一条带闸门的调用流水线**【源码】：

```ts
/**
 * LimbRegistry — F126 四肢节点注册表
 *
 * 管理四肢节点的注册/注销/查询/调用。内存中的 live registry，
 * 与 capabilities.json（静态配置真相源）职责分离。
 *
 * Phase B: invoke 升级为 pipeline — policy check → lease → action log → execute。
 */
```

**四段流水线**：

```
policy check  → LimbAccessPolicy    这个 Agent 能不能调这个能力
lease         → LimbLeaseManager    拿租约（防并发抢同一个节点）
action log    → LimbActionLog       先记账再执行（审计）
execute       → 真正调用
```

**注意顺序：先记账，再执行。**
【推断】这样即使执行崩了，也有"尝试过"的记录 ——
审计日志的完整性优先于执行成功。

**"live registry 与静态配置真相源职责分离"这句值得讲**：

```
capabilities.json  = 静态真相源（有哪些节点被允许）
LimbRegistry       = 内存 live registry（现在哪些节点在线）
```

**配置说"可以有什么"，registry 说"现在有什么"。**
这个分离和 [12 章](12-模块-Skills分发.md) 的
"配置 ↔ 实际挂载"的三层漂移检测是同一个思路。

其他文件：

```
LimbPresenceManager.ts     在线状态/心跳
LimbPairingStore.ts        配对（设备怎么绑定上来）
RemoteLimbNode.ts          远程节点实现
PluginLimbAdapter.ts       把插件包装成 limb
PluginRestExecutor.ts      REST 方式执行
PluginTokenManager.ts      插件 token
limb-yaml-loader.ts        YAML 配置加载
```

**面试可讲的点**：

> "limb 是远程执行节点，它的调用是条四段流水线：
> 权限检查 → 拿租约 → **记审计日志** → 执行。
>
> 注意顺序是**先记账再执行**。我理解是：
> 即使执行崩了也有'尝试过'的记录 ——
> 审计完整性优先于执行成功。这在有远程副作用的场景下是对的。
>
> 而且它明确区分了两个东西：
> `capabilities.json` 是静态真相源（**可以有**哪些节点），
> `LimbRegistry` 是内存 live registry（现在**在线**哪些节点）。
> 配置说可以有什么，registry 说现在有什么 ——
> 这和 Skills 那边'配置 ↔ 实际挂载'的漂移检测是同一个思路。"

### 3.6 concierge —— 前台接待猫（F229）

**做什么**：一个"前台"角色，负责用户侧的功能发现、记忆检索、分诊。
让不懂系统的用户有个入口。

**它的实现是本篇最值得学的"扩展范式"** ——
**Interceptor 两段式**【源码】：

```ts
/**
 * F229: Concierge Routing Interceptor
 *
 * Decouples concierge context logic from routing core (GuideRoutingInterceptor 同模式).
 *
 * Called once before the per-cat loop:
 *   const conciergeCtx = await prepareConciergeContext(routeThread, userId, ...);
 *   // Inside buildInvocationContext:
 *   ...conciergeCtx,
 */
```

```ts
// 第一段：整个路由前调一次
export async function prepareConciergeContext(
  thread: Thread | null,
  userId: string,
  store: IConciergeConfigStore | undefined,
): Promise<ConciergeInvocationContext | Record<string, never>> {
  if (thread?.threadKind !== 'concierge' || !store) return {};   // ← 双重 fail-open
  const config = await store.get(userId);
  return { threadKind: 'concierge', conciergeConfig: config };
}

// 第二段：每只 Agent 调一次
export function conciergeContextForCat(
  ctx: ConciergeInvocationContext | Record<string, never>,
  catId: string,
): ConciergeInvocationContext | Record<string, never> {
  if (!('conciergeConfig' in ctx)) return {};
  // ...只有 catId === config.dutyCatProfileId 才返回
}
```

**为什么要分两段？**

```
prepare（一次）  → 读配置（有 IO），整条路由只做一次
perCat（每只）   → 纯判断（无 IO），决定这只 Agent 要不要注入
```

**IO 只做一次，per-cat 只做纯判断。**
这在一次路由要调多只 Agent 时省掉了 N-1 次配置读取。

**而且注意 per-cat 那段的门禁**【源码】：

> Returns ConciergeInvocationContext only when catId === config.dutyCatProfileId.
> All other cats on a concierge thread (A2A, user @mentions) get empty context —
> the 岗位 prompt is exclusively for the configured duty cat.

**"岗位 prompt 只给值班猫"** ——
同一个帖子里其他 Agent（通过 A2A 或用户 @ 进来的）不注入前台身份。

**为什么？**【推断】
因为"前台"是个岗位不是身份。如果所有进这个帖子的 Agent 都拿到前台 prompt，
它们会都以为自己是前台，然后互相争着接待用户。

**两处 fail-open 也值得注意**：
`thread?.threadKind !== 'concierge'` 和 `!store` 都返回空对象 ——
**不是 concierge 帖子就完全不影响，store 没配也不影响。**

其他文件：

```
ConciergeThreadService.ts          帖子服务
ConciergeConfigStore.ts            per-user 配置
ConciergeHandleMapStore.ts         短句柄 → 锚点映射（KD-17）
ConciergeTriagePlanStore.ts        分诊计划
ConciergeConfirmationStore.ts      确认
ConciergeRelayStore.ts             转发
ConciergeInvestigationJobStore.ts  调查任务
ConciergeInvestigationWorker.ts    调查执行
ConciergePromptSection.ts          → prompt 注入
concierge-reply-validator.ts       回复校验 + triage plan marker 提取
concierge-search-context.ts        搜索上下文
concierge-target-cats-resolver.ts  目标 Agent 解析
concierge-keys.ts                  Redis key
```

**注意 `concierge-reply-validator.ts`** ——
它从 Agent 的回复里提取结构化标记（triage plan marker）并剥离。
**这和 [04 章](04-模块-mention解析.md) 从文本提取结构是同一类活，
说明"从自由文本里提结构"在这个项目里是个反复出现的模式。**

**面试可讲的点（这是"扩展范式"的最佳例子）**：

> "concierge 这个域我觉得最值得讲的不是功能，是它的**扩展范式**。
>
> 它叫 Routing Interceptor，两段式：
> `prepareXxxContext()` 在整条路由前调一次（有 IO，读配置），
> `xxxContextForCat()` 对每只 Agent 调一次（纯判断，无 IO）。
> 然后把返回的对象 spread 进 `buildInvocationContext`。
>
> 这样做有三个好处：
> **一，IO 只做一次** —— 一次路由调 3 只 Agent 不会读 3 次配置；
> **二，和路由核心解耦** —— 路由层不需要知道 concierge 是什么，
> 只是 spread 一个对象；
> **三，双重 fail-open** —— 不是这类帖子、或者 store 没配，都返回空对象，
> 对普通帖子零影响。
>
> 而且 guides 域用的是**完全一样的范式**（注释里明说'GuideRoutingInterceptor 同模式'）。
> **所以'给路由加一个新的上下文来源'这件事在这个项目里有标准做法** ——
> 这比任何单个功能都重要。
>
> 还有个业务细节我挺喜欢：岗位 prompt **只注入给配置的值班猫**，
> 同帖子里其他 Agent 不给。因为'前台'是岗位不是身份 ——
> 如果都给，它们会争着接待用户。"

### 3.8 approval-hub —— 统一审批中心（F246）

**做什么**：把散落在各处的"Agent 提议 → 人批准"收口成一个统一的审批界面。

**这是很干净的 port/adapter**【源码】：

```ts
/**
 * F246: Approval Hub per-feature adapter port.
 *
 * Each adapter maps a canonical feature store's pending proposals to the
 * unified ApprovalItem DTO. Internal-only (AC-A8) — not exported through
 * shared or used by the frontend directly.
 */
export interface IApprovalAdapter {
  readonly featureId: ApprovalFeatureId;
  listPending(userId: string): ApprovalItem[] | Promise<ApprovalItem[]>;
  listSettled?(userId: string, opts?: ListSettledOpts): SettledApprovalItem[] | Promise<SettledApprovalItem[]>;
}
```

**四个 adapter**：

```
F128ApprovalAdapter   Agent 提议建 thread
F193ApprovalAdapter   跨帖相关
F225ApprovalAdapter   会话交接提议
F231ApprovalAdapter   用户画像更新提议
```

**两个设计点**：

**① 各 feature 的 store 保持自己的真相源，adapter 只做映射**

**不是把所有提议搬到一个新表**，而是各自存各自的，
审批中心通过 adapter 读。

**这避免了"又一个真相源"** ——
和 [15 章](15-模块-Self-Evolution.md) 的
"不发明新沉淀库：路由到现有真相源"是同一个判断。

**② `listSettled` 是可选的**

```ts
/**
 * F246 Phase F: Fetch settled (approved|rejected) proposals for history view.
 * Optional — adapters that don't retain decided data return [].
 */
listSettled?(...)
```

**有些 feature 的 store 不保留已决策的提议**，
所以这个方法是可选的，不支持就返回空。

**接口设计承认了实现的能力差异，而不是强迫所有实现都支持。**
（和 [06 章](06-模块-Provider适配.md) 的 provider 能力差异是同类问题。）

**面试可讲的点**：

> "approval-hub 是把散落各处的'Agent 提议 → 人批准'收口成统一界面。
>
> 我觉得它的设计选择很对：**没有把所有提议搬到一张新表**，
> 而是各 feature 保持自己的 store，审批中心通过 adapter 读。
> 四个 adapter 对应四类提议（建帖、跨帖、会话交接、用户画像更新）。
>
> 这避免了'又一个真相源'——
> 和他们 Self-Evolution 里那条'不发明新沉淀库，路由到现有真相源'是同一个判断。
>
> 而且 `listSettled`（查已决策的历史）是**可选方法**，
> 因为有些 feature 的 store 不保留已决策数据。
> **接口承认实现的能力差异，而不是强迫所有实现都支持** ——
> 这比定义一个大而全的接口然后一半实现抛 NotImplemented 好。"

### 3.9 feat-trajectory —— Feature 轨迹投影（F233 Phase C）

**做什么**：把一个 feature 从立项到关闭的全过程，从三个数据源合流成一条轨迹。

**这个域最值得讲的是它明确"照抄"了球权模块的范式**【源码】：

```ts
/**
 * F233 Phase C C2a — FeatTrajectoryProjector（三源 → feat 维度 trajectory 投影）
 *
 * 照 Phase B `BallCustodyProjector` 模式：
 * - 纯函数 / 零 git/gh IO（store.save 是 projection state 持久化不算外部副作用）
 * - apply(entry) = read projection → upsert / append → save
 * - rebuild = delete all + replay 三源全部 entries → 同结果（INV-2）
 *
 * **砚砚 P2-2 collector/projector 分层**：git/gh IO 在 collector，projector 只消费
 * DTO（`GitRefSnapshot` / `BallCustodyEvent` / stitched payload）。
 */
```

**"照 Phase B BallCustodyProjector 模式"** ——
这是范式复用的直接证据。

**三个数据源**：

```
ball-custody 事件流    → applyBallCustodyEvent()
git ref 快照           → applyGitRefSnapshot()
历史拼接               → applyStitchedEntry()
```

**collector / projector 分层**（review 意见推动的）：

```
collector  → 做 git/gh 的 IO（RealGitRunner / RealGhClient / GitRefSnapshotCollector）
projector  → 只消费 DTO，纯函数
```

**这个分层让 projector 可以单测**（不需要真 git 仓库）。

**保守映射策略**【源码】：

```ts
/**
 * Map ball-custody event → trajectory kind（conservative per 砚砚 step 3 advisory #1）。
 *
 * Strategy: 未明确映射 → return null → projector skip (no entry created)。
 */
```

**没有明确映射规则的事件就跳过，不猜。**

【推断】为什么？因为轨迹是给人看的时间线 ——
猜错一个事件的类型会让整条轨迹产生误导。**宁可少一条，不要错一条。**

**还有 `staleBucketForAge` / `STALE_BUCKET_THRESHOLDS_MS`** ——
把"这个 feature 停滞多久了"分桶。这是"安乐死"机制的输入
（[10 章](10-模块-球权状态机.md) 提到的 `ball.frozen` / `degraded` / `abandoned`）。

| 域 | 文件 | 状态数 |
|---|---|---|
| ball-custody | `ball-custody-state-machine.ts` | 8 状态 × 17 事件 |
| community | `community-state-machine.ts` | 表驱动 + closure invariant |
| guides | `GuideStateMachine.ts` | 5 状态 forward-only DAG |
| cats/routing | `multi-mention-state-machine.ts` | multi-mention |
| cats/invocation | `invocation-state-machine.ts` | 调用状态 |

**共同特征（三条都是明文写在注释里的）**：

```
① 纯函数，零 IO、零 Redis、零副作用
② 表驱动（TRANSITION_TABLE）而不是 if 链
③ 持久化和副作用留给调用方（projector / LifecycleService）
```

**而且 community 和 ball-custody 之间有明确的"照抄"关系**——
球权的注释写"照 community-state-machine 的表驱动模式"。

**面试话术**：

> "我数了下这个项目里有至少五个状态机：球权、社区事务、引导流程、
> 多方询问、调用状态。
>
> **五个都是同一个骨架**：纯函数、零 IO、表驱动而不是 if 链、
> 副作用留给调用方。
> 而且注释里能看到互相引用 ——
> 球权状态机写着'照 community-state-machine 的表驱动模式'。
>
> 这带来两个好处：
> **一，都能穷举测试**（球权是 8×17 全覆盖）；
> **二，新人读第三个状态机时已经认得这个骨架了**。"

### 范式二：事件日志 → 投影器 → 投影存储

**出现次数：至少 3 次**

```
ball-custody      BallCustodyEventLog → BallCustodyProjector → ProjectionStore
community         CommunityEventLog → community-projector → CommunityObjectStore
feat-trajectory   三源 collector → FeatTrajectoryProjector → FeatTrajectoryStore
```

**共同的不变量**：

```
事件永不删除（immutable facts）
rebuild = delete + replay，要求逐字段一致（无漂移）
投影器零外部副作用（否则 rebuild 会重发历史动作）
```

**feat-trajectory 明确写了"照 BallCustodyProjector 模式"** ——
第三次复用。

**这直接支撑我在 [17 章](17-如果重新设计.md) §2 的判断**：
**事件溯源在这个项目里已经被验证三次了，调用生命周期该迁过去。**

### 范式三：Routing Interceptor 两段式

**出现次数：2 次（concierge / guides），且明确互相引用**

```ts
prepareXxxContext(thread, userId, store)   // 整条路由前调一次，有 IO
  ↓ 返回 context 对象或 {}
xxxContextForCat(ctx, catId)               // 每只 Agent 调一次，纯判断
  ↓ spread 进 buildInvocationContext
```

**三个好处**：IO 只做一次 / 与路由核心解耦 / 双重 fail-open。

**这是"给路由加新上下文来源"的标准做法。**

### 范式四：可选依赖 fail-open

**出现次数：几乎每个域**

```ts
readonly conciergeConfigStore?: IConciergeConfigStore;   // optional, fail-open
readonly guideSessionStore?: IGuideSessionStore;
readonly worldContextProvider?: WorldContextProvider;
readonly ballCustody?: IBallCustodyIngest;
// ...十几个
```

**在 `invoke-single-cat.ts` 和 `AgentRouter` 里，
业务域几乎全是可选注入的。**

**收益**：测试环境、早期部署、精简部署都能跑。
**代价**：每个可选依赖都要判空 —— 这是 3599 行的一部分原因。

**面试话术**：

> "业务域接入编排核心的方式几乎全是**可选注入 + fail-open**——
> `AgentRouter` 和 `invoke-single-cat` 里有十几个
> `readonly xxxStore?: IXxx` 加注释 `optional, fail-open`。
>
> 好处是任何一个业务域没配都不影响主链路跑，
> 测试和精简部署都容易。
> **代价是每个可选依赖都要判空** ——
> 这是 `invoke-single-cat.ts` 有 3599 行的原因之一。
>
> 我觉得这是个合理的取舍，但我会做得更结构化 ——
> 把这些可选能力收成一个显式的 `capabilities` 对象，
> 而不是十几个平铺的可选字段。"

### 范式五：key 从现有 id 派生，不引入新原语

**出现次数：至少 4 次**

```
ball-custody     subjectKey = `ball:thread:{threadId}`   （KD-1 明确"不引入球 ID 新原语"）
world            scopedKey = `{worldId}:{sceneId}:{idempotencyKey}`
feat-trajectory  makeFeatSubjectKey / makeGitRefSubjectKey / makeEventStreamEntryId
memory           anchor = `doc:{相对路径}`（权威度也从路径推导）
worktree 端口     从 worktree 名 hash 推导
```

**共同思路**：能从已有信息推导的，就不要新建一个需要分配和维护的原语。

## 5. 这 15 个域暴露的三个问题

【推断】以下是我的判断。

### 问题一：业务域和核心域的边界不够清晰

```
world 域有自己的 SQLite（SqliteWorldStore + schema.ts）
memory 域有自己的 SQLite（evidence.sqlite）
signals 有自己的存储
community 有自己的 Redis key 空间
```

**四套存储，各自的迁移、备份、一致性策略。**

**我会怎么改**：把"业务域的持久化"收成一层统一的
domain store 基础设施（统一的迁移框架、统一的备份、统一的 key 命名规范），
业务域只声明 schema。

**代价**：多一层抽象，而且各域的存储需求确实不同
（world 需要 JSON patch，memory 需要向量）。所以要小心不要过度统一。

### 问题二：几个域处于"基础设施完成但运营缺口"状态

【源码】ROADMAP 里 F168 community 的状态是 `infra-complete / ops-gap`。

**这和 [17 章](17-如果重新设计.md) §3 说的观测闭环缺失是同一类问题**——
机制建好了，但没有"它有没有被用"的反馈。

**面试可讲**：

> "有几个域处于他们自己标注的 'infra-complete / ops-gap' 状态 ——
> 基础设施做完了但运营流程没跑起来。
>
> 我觉得这是**大型项目的一个典型陷阱**：
> 建能力比用能力容易，而且建能力有明确的完成信号（测试通过、PR 合入），
> 用能力没有。
>
> 所以我在重构建议里把'机制健康度面板'排得比较前 ——
> 每个机制声明自己的使用量和有效性指标，
> 零使用的进 review 队列。"

### 问题三：域数量本身是个信号

**22 个域，其中 15 个是业务域。**

【推断】这说明这个项目在**同时探索很多方向**（社区运营、情报、
世界共创、游戏化、远程执行、Mod 生态）。

**好处**：编排内核被多种业务场景验证过，泛化性得到了检验。
**风险**：注意力分散；很多域停在 `spec` / `phase-a-done` 状态。

**面试里怎么说这个（要客观，不要评判）**：

> "22 个 domain 里 15 个是业务域，覆盖社区运营、情报抓取、
> 世界共创、游戏化、远程执行、Mod 生态。
>
> 我的观察是这有两面：
> **好的一面**是编排内核被很多种业务场景验证过 ——
> 一套路由和记忆能同时支撑'写代码'和'共创世界'两类完全不同的场景，
> 说明抽象是对的。
> **风险的一面**是 ROADMAP 里很多 feature 停在 spec 或 phase-a-done，
> 注意力比较分散。
>
> 不过这是个人/小团队的开源项目，探索多方向本身可能就是目的。"

## 6. 面试追问应对

**Q：这项目除了 Agent 编排还有什么？**

> "22 个 domain，但体量极不均衡 —— `cats`（编排内核）和 `memory`（记忆）
> 两个域大概占了一半以上代码，剩下 20 个是业务域。
>
> 业务域里比较大的几个：
> community 是 GitHub 社区事务编排（issue/PR 自动分诊、路由、跟到关闭）、
> signals 是情报抓取管线（RSS/API/网页三种抓取器 + 去重 + 日报）、
> packs 是第三方能力包生态（Mod 系统）、
> world 是世界共创引擎、
> limb 是远程执行节点。
>
> 但我觉得比功能清单更有意思的是**这些域揭示的架构范式**——
> 它们长得很像。"

**Q：他们怎么加一个新功能？**

> "有五个反复出现的范式：
>
> **一，纯函数表驱动状态机 + 副作用留给调用方**——
> 至少五个状态机都是这个骨架，而且注释里互相引用
> （球权的注释写'照 community-state-machine 的模式'）。
>
> **二，事件日志 → 投影器 → 投影存储**——
> 至少三个域用了（球权、社区、feature 轨迹），
> 而且 feature 轨迹明确写了'照 BallCustodyProjector 模式'。
>
> **三，Routing Interceptor 两段式**——
> `prepareXxxContext` 整条路由前调一次（有 IO），
> `xxxContextForCat` 每只 Agent 调一次（纯判断），
> 返回值 spread 进 prompt 上下文。concierge 和 guides 用的完全一样。
>
> **四，可选依赖 fail-open**——业务域接入核心几乎全是可选注入。
>
> **五，key 从现有 id 派生**——不引入新原语。
>
> **所以'加一个新功能'的成本是可预测的。**
> 我觉得这个比任何单个设计都重要 ——
> 它意味着新人读第三个域的时候就已经认得骨架了。"

**Q：packs 那个第三方包不会被用来攻击 Agent 吗？**

见 §3.3 的完整话术。核心是三道防线：
编译而非注入 / 双轨信任边界（含"约束放松方向"检测）/ 身份字段不可变。

**追加一句加分的**：

> "而且这三道防线是有连锁的 ——
> 如果第三方能改 `family` 字段，
> 就能绕过'跨模型互审不能自审'的铁律，因为那条规则靠 family 判定。
> **所以身份字段不可变不是孤立的安全措施，它撑着上层的一条纪律。**"

**Q：这些业务域你都读透了吗？**

**诚实收窄**：

> "没有。我读的是每个域的入口文件、核心状态机、
> 以及它们怎么接入编排核心。
>
> 深度上：packs 的安全守卫、community 的状态机不变量、
> concierge/guides 的 interceptor 范式我读得比较细，
> 因为它们有可讲的设计。
>
> signals 的抓取细节、leaderboard 的统计口径、
> world 的完整动作处理器我只看了骨架。
>
> 我把这一篇的定位就是'范式识别 + 全景'，不是逐域深潜。
> 真正深潜的是编排、会话、记忆那几篇。"

**Q：如果让你重构这 15 个业务域？**

> "三件事，按优先级：
>
> **一，统一业务域的持久化基础设施。**
> 现在 world、memory、signals、community 各有自己的存储
> （两套 SQLite + 各自的 Redis key 空间），
> 各自的迁移、备份、一致性策略。
> 我会做一层统一的 domain store（统一迁移框架 + key 命名规范 + 备份），
> 业务域只声明 schema。
> 但要小心不要过度统一 —— world 需要 JSON patch、memory 需要向量，
> 需求确实不同。
>
> **二，给'infra-complete / ops-gap' 的域补观测。**
> 他们自己标注了几个域是这个状态 —— 能力建好了但没跑起来。
> 我会先加使用量度量，零使用的进 review。
>
> **三，把可选依赖收成显式的 capabilities 对象。**
> 现在编排核心里有十几个平铺的 `readonly xxxStore?`，
> 我会收成一个对象 + 一个能力探测函数，
> 这样'这次调用有哪些业务能力可用'是一个可打印的状态，
> 而不是散在十几个判空里。"
