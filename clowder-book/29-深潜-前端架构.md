### 2.1 `ChatMessage` —— 一切的中心【源码】`packages/web/src/stores/chat-types.ts`


逐字段"为什么存在"（注释里有明确理由的）：

| 字段 | 为什么存在 |
|---|---|
| `origin: 'stream' \| 'callback' \| 'briefing'` | 区分气泡内容来源：`stream` = CLI stdout（心里话/工作日志），`callback` = MCP `post_message`（猫真正"说"的话），`briefing` = F148 context briefing。**整章一半的复杂度来自这两条路会撞在同一个逻辑气泡上。**【源码】 |
| `deliveredAt` | 排队消息的"发送时间"和"投递时间"不同。`ChatMessage.tsx` 的 `formatDualTime()` 在两者差 > `DELIVERED_AT_GAP_THRESHOLD = 5000`ms 时渲染成 `发送 xx:xx · 收到 xx:xx`。【源码】 |
| `thinkingChunks` | thinking 是增量拼的，payload 里可能带视觉分隔符导致重复。`chatStore.appendThinkingChunk()` 用 `THINKING_CHUNK_SEPARATOR = '\n\n---\n\n'` 拼 chunks，并做前缀去重（`next.startsWith(lastChunk)` → 替换最后一块）。【源码】 |
| `cachedFrom: 'idb'` | 标记"这条是从 IndexedDB 快照恢复的"。`mergeReplaceHydrationMessages` 见到就 `continue` —— 服务器历史绝对权威，缓存副本不参与 merge。写回 IDB 前 `stripPersistMarkers` 剥掉。【源码】 |
| `mentionsUser` | 猫 @ 了铲屎官。`chatStore.fireOwnerMentionNotification()` 在 `!document.hasFocus()` 时弹 Web Notification（用 `document.hasFocus()` 而不是 `document.hidden`，注释说切 macOS App 时 hidden 仍是 false）。【源码】 |

### 2.2 `extra` 里的 `stream` —— 双 ID 契约（最重要的一段）【源码】

**双 ID 的存在理由**，`debug/bubbleIdentity.ts` 注释给了具体 bug：
> "same parent A2A chain `opus → codex → opus` 共用 `extra.stream.invocationId=parentId`，
> 如果 bubble identity 用 parent id，第 1 个和第 3 个 opus turn 会被 reducer/merge 视为同一气泡 →
> **cancel 按钮消失 + 第 3 个 opus 失踪**（co-creator catch 2026-05-09 17:32）"【源码】

于是有了 identity 提取函数：

```ts
// debug/bubbleIdentity.ts
export function getBubbleInvocationId(msg: ChatMessage): string | undefined {
  if (msg.extra?.isExplicitPost) return undefined;               // #814
  if (msg.extra?.stream?.turnInvocationId) return msg.extra.stream.turnInvocationId;  // 优先 turn
  if (msg.extra?.stream?.invocationId) return msg.extra.stream.invocationId;          // legacy fallback
  if (msg.id.startsWith('draft-')) return msg.id.slice('draft-'.length);              // 服务端 draft
  return undefined;
}

export function deriveBubbleId(invocationId, catId, fallback): string {
  if (invocationId && catId) return `msg-${invocationId}-${catId}`;   // 确定性 ID
  return fallback();
}
```

> **面试官追问：为什么气泡 ID 要"确定性"？**
> "因为有两条 handler 会为同一个 invocation 造气泡：active path（当前 thread）和 background path（后台 thread）。
> `deriveBubbleId` 的注释说得很直白：'Two handlers (active, background) creating the "same" bubble for the same
> invocation will land on the same ID — so hydration merge dedups by ID, no ghost survives.'
> 换句话说，确定性 ID 是**跨 handler、跨 F5 刷新的去重锚点**。ID 是 `msg-{invocationId}-{catId}`，
> reducer 自己 derive 时还会带 kind 后缀 `msg-{inv}-{cat}-{kind}`（防止 thinking 和 text 撞 ID）。"

### 2.3 `ThreadState` 与 `chatStore` 的"扁平 + 镜像"双表示【源码】

```ts

  activeInvocations: Record<string, { catId; mode; startedAt? }>;   // F108 槽位
  intentMode: 'execute' | 'ideate' | null;
  targetCats: string[];

  workspaceOpenFilePath: string | null; workspaceOpenFileLine: number | null;

export const DEFAULT_THREAD_STATE: ThreadState = { messages: [], ..., hasMore: true, ... };
```

`ChatState` 把 `ThreadState` 的每个字段**同时扁平化到顶层**（`state.messages`、`state.isLoading`…），
再加一个 `threadStates: Record<string, ThreadState>`。这不是冗余，是刻意的迁移中间态：

```ts
/** F173 Phase A — ThreadRuntimeWriter mirror helper.
 *  When a setThreadX writes to the active thread's flat state, this also mirrors
 *  the same patch into threadStates[currentThreadId] so threadStates is always
 *  the source of truth (flat is a compatibility mirror, KD-2). */
function mirrorActiveToThreadStates(state, threadId, patch) { ... }
function mirrorActiveFlat(state, patch) { return mirrorActiveToThreadStates(state, state.currentThreadId, patch); }
```
【源码】KD-2 = "threadStates 是写入真相源，flat 是兼容镜像"。

三个配套纯函数：
- `snapshotActive(s)` —— 扁平 → ThreadState。有个精妙细节：`lastActivity` 在 `hasActiveInvocation` 时用
  `Date.now()`，否则取 `max(旧 lastActivity, 最后一条消息的 deliveredAt ?? timestamp)`，
  注释理由是"**光切 thread 不应该重排侧边栏**"。【源码】
- `flattenThread(ts)` —— ThreadState → 扁平。只在 `ts.workspaceWorktreeId != null` 时恢复 worktreeId，
  "avoids wiping the global selection for threads that never opened workspace"。【源码】
- `stampThreadCompletion(threadStates, threadId, patch?)` —— 集中定义"真实活动刚结束"的语义。【源码】

读侧有配套的 `hooks/useThreadScopedSelectors.ts`：`selectThreadMessages` / `selectThreadLiveness`，
当 `threadId === currentThreadId` 走扁平（保持引用相等），否则走 `threadStates[threadId]`。
`useThreadLiveness` 用 `useShallow` 包，注释说"selector 每次返回新对象，不 shallow 会每次 store 变动都重渲染"。【源码】

> **面试官追问：这个"扁平 + 镜像"不是明显的坏味道吗？**
> "是，而且代码自己承认了 —— 注释写 'flat is a compatibility mirror (KD-2)'，说明这是 F173 重构的中间态，
> 目标是最终统一到 `threadStates`。它带来的真实成本是：每个 setter 都要记得调 `mirrorActiveFlat`，
> 漏一个就出现"当前 thread 状态和 threadStates 不一致"。代码里能看到补丁痕迹：
> `updateThreadMessage()` 的注释写 'F173 KD-2 (PR-C Task 10): mirror message edits to threadStates[active]


### 3.5 客户端接收：coalescer（这是一个真实崩溃的修复）

`useSocket-message-coalescer.ts` 82 行，头部注释是完整的事故复盘：

```
Root cause (original #789): each socket event dispatched synchronously →
multiple chatStore.setState per event → useSyncExternalStore bypasses
React 18 automatic batching → >50 nested update depth → React throws.

Original fix: buffer events from the same macrotask, flush in one microtask.

Recurrence root cause: the single-microtask flush processes ALL buffered
events synchronously. ... When a burst exceeds ~8 events (multi-cat streaming,
reconnect gap detection, epoch change), the total set() count within one flush
exceeds React's 50 nested update limit → crash recurs.

Fix (chunked flush): process at most CHUNK_SIZE events per microtask.
```

实现：
```ts
const CHUNK_SIZE = 6;   // 6 events × 8 set() = 48，安全低于 React 的 50
export function createAgentMessageCoalescer(handler) {
  const queue: unknown[] = [];
  let flushScheduled = false;
  function flush(): void {
    const chunk = queue.splice(0, CHUNK_SIZE);
    if (queue.length > 0) queueMicrotask(flush);   // microtask 链，无 paint 边界
    else flushScheduled = false;
    for (const msg of chunk) handler(msg);
  }
  return { push(msg) { queue.push(msg); if (!flushScheduled) { flushScheduled = true; queueMicrotask(flush); } } };
}
```
设计契约写在注释里：**每条事件都处理、不丢不合并、宏任务内 FIFO 顺序保持**。【源码】

> **面试官追问：为什么是 microtask 而不是 requestAnimationFrame / setTimeout？**
> "注释直接答了：'Microtask chaining adds no paint boundaries (no user-visible delay)'。
> React 在 microtask 之间会重置嵌套更新计数器，所以分块就够了；用 rAF 会引入 16ms 延迟，
> 流式打字会看着一顿一顿。CHUNK_SIZE=6 的来历也写了：每条事件约 4~8 次 zustand `set()`，
> 6×8=48，压在 React 50 的硬限下留了余量。"

## 4. 关键算法与判定逻辑

### 4.1 `processThreadSeq` —— gap 检测状态机【源码】

纯函数（为了脱离 React 单测），输入 `{threadId, seq, seqEpoch}` + store，输出 6 种 action：

```
输入: msg.seq, msg.seqEpoch
lastSeq   = store.lastSeqByThread[tid] ?? 0
lastEpoch = store.lastSeqEpochByThread[tid] ?? ''
pending   = store.pendingCatchUpTargetSeqByThread[tid] ?? 0

1. !threadId                              → 'no-op'
2. seq 非数字 或 seq <= 0                  → 'no-op'（legacy producer，优雅降级）
3. lastSeq>0 且 lastEpoch 且 incomingEpoch 且 两者不等
     → setLastSeqEpoch(incoming); setLastSeq(0); setPending(incomingSeq); requestStreamCatchUp()
     → 'epoch-change'
4. lastSeq === 0:
     4a. pending > 0  → if (seq > pending) setPending(seq); requestStreamCatchUp() → 'gap'
     4b. else         → setLastSeq(seq); setLastSeqEpoch(epoch) → 'seed'
5. seq <= lastSeq                          → 'late'（不丢，交给下游 stable-key 去重）
6. seq > lastSeq + 1
     → setPending(seq); requestStreamCatchUp()   ★ 不推进 lastSeq
     → 'gap'
7. seq === lastSeq + 1                     → setLastSeq(seq) → 'advance'
```

**三个反直觉设计各有事故背景**：
1. **gap 时不推进 `lastSeq`**（cloud P1 2026-05-02）："Optimistically advancing puts the missing range
   'behind the watermark' — if the subsequent HTTP fetchHistory fails or is canceled, future in-order
   events become 'advance' and the gap silently never retriggers catch-up."【源码】
2. **epoch-change 时 `lastSeq` 重置为 0 而不是 incomingSeq**（cloud R2 P1-B）：如果重启后第一个包 seq>1
   且 catch-up 失败，后续事件会走 'advance' 永不重试。所以重置为 0 + 记 pending，
   后续事件走 4a 分支持续重试。【源码】
3. **ack 机制**（砚砚 R5 P1）：`fetchHistory` 成功后调 `acknowledgeCatchUp(threadId, targetAtStart)`。
   `targetAtStart` 是**fetch 开始时**捕获的 pending，不是 ack 时读的 —— 防止飞行中来了新 gap 被误清（砚砚 R6 P1）。

`acknowledgeCatchUp` 的实现：
```ts
const nextLastSeq = Math.max(currentLastSeq, ackedTargetSeq);   // 防御性：ack 乱序不回退
if (typeof pending === 'number' && pending === ackedTargetSeq) { /* 清 pending */ }
// pending 已被刷新成更大值 → 保留 pending，只推进 lastSeq
```
【源码】

### 4.2 catch-up 消费者（`useChatHistory`）—— 防抖 + 退避 + 幂等门【源码】

## 7. 面试追问应对

**Q1：`useAgentMessages.ts` 5938 行，而 `CLAUDE.md` 写着"File size: 200 lines warning / 350 hard limit"。你怎么解释？**

> "这是这个仓库最诚实的一处技术债，而且是被自己的规范明确标红的（`CLAUDE.md` 的 Code Standards
> 写 200 行警告 / 350 行硬限）。为什么它长成这样：它是**唯一的 socket 事件分发入口**（F173 Phase E
> KD-1 "handler unification"），里面同时住着 active 和 background 两条路径、8 种 `msg.type` 的 9 个分支
> （`text` 有 "有 content" / "无 content" 两条）、`system_info` 内层 20+ 种 JSON 类型，每种在两条路径各写一遍。
> 已经做的拆分是把**纯逻辑抽出去**：`thread-runtime-ledger.ts`(601) 管运行时账本、
> `bubble-reducer.ts`(735) 管状态转换、`bubble-projection.ts`(315) 管投影、
> `bubble-event-adapter.ts`(129) 管协议映射、`bubble-invariants.ts`(216) 管校验 —— 这 5 个都是可单测的纯模块。
> 剩下的 5938 行本质是**编排 + 恢复策略**，而恢复策略的每一条都对应一个真实事故（注释里全有出处）。
> 如果让我继续拆，第一刀会砍在 `system_info`：把 20+ 种内层 type 做成一张
> `Record<type, (parsed, ctx) => ConsumeResult>` 表，两条路径共用同一张表 —— 这能一次消掉
> #939 和 F210-H1 两类"漏写一个 handler"的 bug。"

**Q2：气泡身份为什么需要 `(catId, canonicalInvocationId, bubbleKind)` 三元组？两元不行吗？**

> "`bubbleKind` 有 5 种（`assistant_text` / `thinking` / `tool_or_cli` / `rich_block` / `system_status`），
> ADR-033 允许**同一 invocation 下多个 kind 共存**：一次调用可以同时有 thinking 气泡和正文气泡。
> 如果身份只用 (catId, invocationId)，thinking 事件和 text 事件会撞成一个气泡。
> 反过来也有坑：`deriveBubbleKindFromMessage` 是从消息**内容形态反推**的（有 content → assistant_text；
> 无 content 但有 rich blocks → rich_block；有 thinking → thinking；有 toolEvents → tool_or_cli），
> 所以一个气泡的 kind 会随内容变化而漂移。这就产生了 `isUiCompatStreamingAssistantContainer()` 这个
> 白名单：ID 是 `msg-{inv}-{cat}` 或 `msg-{inv}-{cat}-assistant_text` 或 `bg-think-*` 的气泡，
> 即使当前只有 toolEvents/thinking，也**强制归 `assistant_text`** —— 否则 `stream_started → tool_event
> → stream_chunk` 这条链会在第三步 canonical-split，正文内容直接丢（砚砚 复现，F194 Phase Z5 R2）。"

**Q3：`origin='stream'` 和 `origin='callback'` 为什么会撞在同一个逻辑气泡上？**

> "同一次回复有两条数据通道：CLI 的 stdout（stream，工作日志/心里话）和 MCP `post_message` 回调
> （callback，猫真正要说的话）。后端不保证顺序，前端要决定"这两个是同一个气泡还是两个气泡"。
> 演进了三个阶段（都写在 `bubble-projection.ts` 头部）：Z8 让 live 和 hydrate 共用同一个投影函数；
> Z11 修了"post_msg 合并后 stream stdout 消失"；然后运行时证据澄清了正确的 UI 模型 ——
> **post_msg speech 自成一个气泡，CLI 工作日志留在 stream 气泡里**。
> 现在的分组规则是：callback record 用**自己的 message id** 分组（自成一组），
> 只有一种例外 —— exact-key callback（它的 id 恰好等于某个 stream record 的 id），
> 那是 stream 气泡的终态更新，留在 stream 组里；这时会额外产出 `cliStdout` / `speechContent` 两个字段
> 供渲染层分开用。"

**Q4：WebSocket 断线重连之后，你怎么保证不丢消息、也不重复？**

> "四层防御，从便宜到贵：
> ① **seq/epoch gap 检测**（最便宜）：`SocketManager` 给每条 `agent_message` 注入 per-thread 单调 `seq`
> 和 sequencer 的 boot UUID `seqEpoch`。客户端 `processThreadSeq` 发现 `seq > lastSeq+1` 或 epoch 变了就补拉。
> ② **重连主动补拉**：`useSocket` 的 connect handler 在**非首连**时遍历 `joinedRoomsRef` 里所有
> `thread:*` 房间逐个 `requestStreamCatchUp`。注释解释了为什么必须有这层：如果猫在断线窗口里播完了，
> 之后没有新事件，gap 检测永远不会被触发（用户报的"F5 / 切 thread 才出来"）。
> ③ **服务器状态对账**：`reconcileThreadWithServer` 打 `GET /api/threads/{id}/queue`，服务器还有活跃槽位
> 就用 `hydrated-{threadId}-{catId}` 合成槽位重建本地状态，服务器没槽位就清本地 + 补拉。
> ④ **看门狗**：30s 定时 + `visibilitychange` 扫 `threadStates`，找"`hasActiveInvocation` 但静默超 3 分钟"
> 的 thread，60s 冷却内不重复探测。
> 不重复靠的是 **stable-key 去重**：补拉回来的历史和本地实时状态走 `mergeReplaceHydrationMessages`，
> 用 `id` ∪ `catId:invocationId` 两个命名空间做单一索引匹配，命中就 merge 不追加。"

**Q5：`gap` 时为什么不推进 `lastSeq`？看着像 bug。**

> "看着像，其实是 cloud P1 2026-05-02 专门修的。如果 gap 时乐观推进 `lastSeq = incomingSeq`，
> 缺失区间就落到"水位线之后"了 —— 后续按序到达的事件全部判定为 `advance`，gap 再也不会重新触发 catch-up。
> 如果那次 HTTP 补拉失败或被 abort，丢的消息**整个会话都不会回来**。
> 现在的设计是：gap 时只记 `pendingCatchUpTargetSeqByThread[tid] = incomingSeq` + 触发补拉，
> `lastSeq` 停在原水位；只有 `fetchHistory` 真成功了才通过 `acknowledgeCatchUp(tid, targetAtStart)`
> 把 `lastSeq` 推到那次捕获的目标。这也是为什么 `acknowledgeCatchUp` 里要 `pending === ackedTargetSeq`
> 才清 pending —— 飞行途中来了更大的 gap，pending 被刷新了，不能被旧 ack 清掉（砚砚 R6 P1）。"

**Q6：长列表怎么处理？消息几千条会不会卡？**

> "**没有虚拟滚动**，这是我能确认的事实：`package.json` 里没有 react-window / react-virtuoso，
> `grep -ril virtual` 在整个 `src` 只命中 `hooks/useTeleport.ts` 和一个测试文件
> （`lib/story-player/__tests__/bullet-time-trigger.test.ts`），没有任何虚拟列表实现。
> 现在靠这些手段兜着：
> ① **分页**：`HISTORY_PAGE_SIZE = 50`，`handleScroll` 在 `scrollTop < 80` 且未加载中时用
> `${deliveredAt ?? timestamp}:${id}` 游标往上翻。
> ② **hasMore 门**：默认 `true`，服务端返回才置 false。
> ③ **`useShallow`**：`useThreadLiveness` 用 shallow 比较避免每次 store 变动都重渲染。
> ④ **blob 回收**：超过 `MAX_BLOB_MESSAGES = 200` 就 revoke 老的 objectURL（防内存泄漏，不是防渲染卡）。
> ⑤ **IDB 快照只存 50 条**，所以冷启动首屏渲染量有上界。
> **`React.memo` 只在 `story-player/ReplayMessageList.tsx` 用了一处** —— `ChatMessage` 没有 memo。
> 这是我会第一优先补的性能工作：先给 `ChatMessage` 加 memo（它的 props 里 `getCatById` 是函数，
> 需要先 `useCallback` 稳定住），再评估虚拟滚动。虚拟滚动在这里不好做的原因是气泡高度差异极大
> （CLI Output 折叠/展开、rich blocks、mermaid 图），需要动态测量。"

**Q9：Preview Gateway 是什么？为什么不直接在 iframe 里开 localhost:3847？**

> "因为浏览器和被预览的 dev server 都会挡你。`preview-gateway.ts` 的类注释写了模型：
> `GET http://gateway:PORT/path?__preview_port=3847` → 代理到 `http://localhost:3847/path`。
> iframe 永远只连 gateway，不直连业务端口。它干四件事：
> ① **剥 iframe 拦截头**：`delete proxyRes.headers['x-frame-options']`，
> 并从 CSP 里过滤掉 `frame-ancestors` 指令（过滤后为空就整条删掉）。
> ② **注入桥接脚本**：HTML 响应会被 buffer 下来（支持 gzip/deflate 解压，
> 遇到 `br` 等不支持的编码就直接 passthrough 不注入），在 `</head>` 或 `<body>` 后插入
> `buildWsPatchScript(targetPort) + BRIDGE_SCRIPT`。桥接脚本 patch `console.log/warn/error/info`
> 和 `window.onerror`，用 `parent.postMessage({ type:'console', source:'cat-cafe-bridge', ... })` 送出去；
> 还支持截图请求（SVG `foreignObject` 包 `documentElement.outerHTML` → `Image` → canvas → dataURL，
> 上限 1920×1080）。注入后要 `delete content-encoding` + `delete transfer-encoding` + 重算 `content-length`。
> ③ **HMR WebSocket 代理**：`server.on('upgrade')` 转 `proxy.ws`，所以热更新照样工作。
> ④ **端口白名单**：`validatePort` 做 loopback-only + 1024~65535 + 排除 gateway 自身（防递归）
> + 排除 14 个硬编码 Clowder 服务端口 + 8 个环境变量里的运行时端口。"
