# 16 · 模块：存储抽象与部署形态

> 这一章讲**工程面**：存储怎么抽象、Redis 为什么能是可选的、
> 桌面打包要交什么税、多 worktree 并行开发怎么不打架。
>
> 面试里它的价值在于：**大部分候选人只讲功能架构，讲不了部署形态。
> 而部署形态往往反过来决定了功能架构的很多选择。**

---

## 0. 30 秒电梯版

> "存储全接口化 —— `stores/ports/` 下 27 个接口，
> 每个都有 Redis 和内存两套实现。
> 所以 `--memory` 模式能跑（Redis 可选），
> 代价是每个 store 两套实现要维护。
>
> 而且有个 **fail-closed 的存储守卫**：
> Redis 不可用时，除非显式设 `MEMORY_STORE=1`，否则**直接拒绝启动**——
> 不静默降级到内存（因为那会静默丢数据）。
>
> 部署形态是**本地优先的桌面应用**：有 Windows/macOS 安装包，
> 自带 Node 运行时和 Redis。
> 这个形态反过来决定了很多架构选择 ——
> 为什么不用向量数据库、为什么不用 Kafka、为什么不容器化，
> 答案都是同一个：**普通用户双击就要能用。**"

---

## 1. 它解决什么问题

### 问题一：不同用户的部署能力差异极大

```
开发者用户       → 会装 Redis、会跑 pnpm、会看日志
普通用户         → 只会双击安装包
公司内网用户     → 装不了外部服务，也连不了外网
```

**同一套代码要覆盖这三种。**

### 问题二：状态放哪儿

```
thread / message / task / session / memory / 球权 / 队列…

放内存      → 重启丢
放 Redis    → 要装 Redis
放 SQLite   → 并发受限
放文件      → 查询困难
```

**答案是混合**，但混合意味着要有明确的分层规则。

### 问题三：多个 worktree 并行开发怎么不打架

**这是多 Agent 独有的问题**：

```
Agent A 在 worktree/f123 开发
Agent B 在 worktree/f456 开发
Agent C 在主仓库读代码

三个都要跑 dev server → 抢端口
三个都连 Redis → 数据互相污染
```

---

## 2. 不做会怎样

### 场景 A：不做存储抽象

```
代码里到处直接调 redis.hget()
  → 没 Redis 就跑不起来
    → 普通用户装不上
      → 也没法写单元测试（要起 Redis）
```

### 场景 B：Redis 不可用时静默降级到内存

```
用户的 Redis 挂了
  → 系统自动切内存模式，照常运行
    → 用户聊了一整天
      → 重启
        → 所有对话历史消失
          → 而且用户不知道为什么
```

**这就是为什么要 fail-closed。**

### 场景 C：不做端口偏移

```
Agent A 在 worktree/f123 跑 pnpm dev → 占 3003
Agent B 在 worktree/f456 跑 pnpm dev → 3003 被占，启动失败
  → 或者更糟：B 连上了 A 的服务，往 A 的 Redis 里写数据
```

### 场景 D：不隔离 Redis 数据库

```
开发环境和生产环境用同一个 Redis
  → 测试时 flush 了一下
    → 用户的真实数据全没了
```

**这就是第一条铁律"数据存储圣域"的由来，
以及 SOP 里 `impl-redis-6398-only` 那条规则**
（[模块 14](14-模块-SOP门禁.md) §3.8）。

## 3. 怎么设计的

### 3.1 存储接口化：27 个 port

```
packages/api/src/domains/cats/services/stores/ports/
├─ MessageStore.ts              消息
├─ ThreadStore.ts               帖子
├─ TaskStore.ts                 任务
├─ SessionChainStore.ts         会话链
├─ InvocationRecordStore.ts     调用记录
├─ DraftStore.ts                草稿
├─ SummaryStore.ts              摘要
├─ DeliveryCursorStore.ts       投递游标
├─ WorkflowSopStore.ts          SOP 状态
├─ MemoryStore.ts / MemoryGovernanceStore.ts
├─ BacklogStore.ts / GameStore.ts
├─ AuthorizationRuleStore.ts / AuthorizationAuditStore.ts
├─ ProfileUpdateProposalStore.ts / SessionHandoffProposalStore.ts
├─ DossierObservationStore.ts / DossierDistillationProposalStore.ts
├─ CommunityIssueStore.ts / CommunityPrStore.ts / CommunityIssueDraftStore.ts
├─ FrustrationIssueStore.ts / PendingRequestStore.ts
├─ PushSubscriptionStore.ts / ThreadReadStateStore.ts / ProposalStore.ts
└─ invocation-state-machine.ts
```

**每个接口两套实现：Redis 和内存。**

**面试话术**：

> "存储全部接口化，`stores/ports/` 下有 27 个接口，
> 每个都有 Redis 和内存两套实现。
>
> 这带来的能力是：**Redis 可以是可选的**——
> `pnpm start --memory` 就能跑，普通用户不用装 Redis。
> 而且单元测试不需要起 Redis。
>
> 代价是**每个 store 两套实现要维护**，
> 而且要保证两套的语义一致（比如原子自增、TTL、有序集合）——
> 内存实现要手动模拟 Redis 的这些行为。
>
> 我觉得这个代价是值的，因为它换来的是**部署门槛**。
> 这是个有桌面安装包的产品，'必须先装 Redis'会挡掉大部分用户。"

### 3.2 Fail-closed 存储守卫

```ts
/**
 * Fail-closed storage guard.
 * Ensures Redis is available unless memory mode is explicitly opted into.
 *
 * Two-layer defense:
 * 1. start-dev.sh exits on Redis failure (unless --memory flag)
 * 2. This guard catches direct `pnpm dev` without Redis
 */
export function assertStorageReady(redisAvailable: boolean): StorageGuardResult {
  if (redisAvailable) {
    return { mode: 'redis' };
  }

  if (process.env.MEMORY_STORE === '1') {
    return { mode: 'memory' };
  }

  throw new Error(
    '[api] REDIS_URL not set and MEMORY_STORE not enabled. ' +
      'Start Redis or use --memory flag. ' +
      'Set MEMORY_STORE=1 to explicitly allow in-memory storage.',
  );
}
```

**三个设计点值得讲：**

**① 不静默降级**

Redis 不可用 + 没显式 opt-in 内存模式 → **抛异常，拒绝启动**。

**为什么？** 因为内存模式会**静默丢数据**——
用户聊了一整天，重启全没了，而且不知道原因。

**这和 L0 编译的 fail-closed（[模块 07](07-模块-身份注入.md)）是同一个判断：
宁可崩溃，不要静默错误。**

**② 双层防御**

```
第一层：start-dev.sh 检查 Redis，失败就退出（除非 --memory）
第二层：这个守卫捕获"直接跑 pnpm dev 绕过脚本"的情况
```

**"绕过启动脚本"是个真实的使用场景** ——
开发者习惯直接 `pnpm dev`。第二层就是给这种情况兜的。

**③ 错误消息给出三条出路**

```
'Start Redis or use --memory flag. Set MEMORY_STORE=1 to explicitly allow in-memory storage.'
```

**不只说"错了"，还说"你可以怎么做"** ——
三个选项：起 Redis、用 flag、设环境变量。

### 3.3 真相源分层

【ADR】ADR-020 里的分层规则（[模块 09](09-模块-记忆与检索.md) 讲过，
这里从存储角度再看一次）：

```
索引（evidence.sqlite）      = 编译产物，gitignore + rebuild
工作流状态（docs/markers/*.yaml）= git-tracked durable store
知识真相源                    = docs/*.md 文件
运行时状态                    = Redis（可降级到内存）
```

**四层，各有不同的容错策略：**

| 层 | 存哪儿 | 丢了怎么办 |
|---|--------|-----------|
| 知识真相源 | git 里的 Markdown | git 恢复 |
| 工作流状态 | git-tracked YAML | git 恢复 |
| 索引 | SQLite（gitignore） | **重建**（几分钟） |
| 运行时状态 | Redis | 丢了就丢了（但有导出机制） |

**"把可重建的和不可重建的分开"是我认为最实用的一条架构原则。**

**面试话术**：

> "他们的存储分了四层，而且每层的容错策略不同。
>
> 知识真相源是 git 里的 Markdown ——丢了 git 恢复。
> 工作流状态（比如待处理的记忆标记）也是 git-tracked 的 YAML。
> **索引明确定位成'编译产物'**——gitignore 掉，随时能 rebuild。
> 运行时状态在 Redis。
>
> 这个分层的价值在于**它决定了每层的容错成本**。
> SQLite 坏了、schema 要迁移、embedding 模型换了 ——
> 全都'删了重建'，不需要写数据迁移脚本。
>
> **把可重建的东西和不可重建的东西分开** ——
> 我觉得这是最实用的一条架构原则，
> 因为它让'哪些数据需要备份、哪些不需要'变成一个显而易见的问题。"

### 3.4 运行时状态的导出机制

虽然 Redis 的数据"丢了就丢了"，但项目提供了导出/恢复：

```
scripts/export-threads-from-redis.mjs      导出 thread
scripts/restore-chat-md-to-redis.mjs       从 Markdown 恢复
scripts/user-redis.sh backup               备份
scripts/user-redis-autobackup.sh install   自动备份
scripts/find-redis-dumps.sh                找 dump 文件
scripts/thread-exports-autosave.sh         自动导出
```

**注意 `restore-chat-md-to-redis.mjs`** ——
**从 Markdown 恢复到 Redis**。

【推断】这说明他们把对话历史也导出成了 Markdown 文件 ——
**Markdown 成了 Redis 数据的"冷备"**。

这个设计很聪明：Markdown 是人可读的、git 可管的、
而且天然是 [模块 09](09-模块-记忆与检索.md) 的索引源。
**一份数据同时是备份和知识源。**

而且注意有 `--dry-run` 和 `--apply --yes` 两个模式：

```json
"redis:md:restore:dry-run": "node ./scripts/restore-chat-md-to-redis.mjs",
"redis:md:restore:apply": "node ./scripts/restore-chat-md-to-redis.mjs --apply --yes"
```

**默认是 dry-run** —— 恢复是危险操作，默认只预览。

### 3.5 端口隔离：多 worktree 并行

```
scripts/derive-worktree-ports.mjs        从 worktree 名推导端口偏移
scripts/check-worktree-port-offset.mjs   CI 检查
scripts/check-worktree-dirty-ledger.mjs  脏状态账本
```

**为什么需要"从 worktree 名推导端口"？**

```
worktree/f123  → hash("f123") % N → 端口偏移 +10 → API 3013
worktree/f456  → hash("f456") % N → 端口偏移 +20 → API 3023
主仓库          → 偏移 0            → API 3003
```

**推导而不是配置的好处**：
Agent 开新 worktree 时不需要记得分配端口，
**端口是从名字里算出来的，天然不冲突。**

**这和 [模块 09](09-模块-记忆与检索.md) 的"权威度从路径推导"、
[模块 10](10-模块-球权状态机.md) 的"subjectKey 从 threadId 派生"
是同一个思路 —— 能推导就不要新建/不要配置。**

**Redis 数据库也隔离：**

```yaml
# SOP 规则
- id: impl-redis-6398-only
  predicate:
    type: env_check
    key: REDIS_URL
    must_include: ":6398"
    must_not_include: ":6399"
```

**6398 = 开发，6399 = 生产。一个端口号之差，所以专门加了 SOP 门禁。**

**面试话术**：

> "多 worktree 并行有个很实际的问题：抢端口。
>
> 他们的解法是**从 worktree 名字推导端口偏移** ——
> hash 一下取模，算出偏移量。
> 好处是 Agent 开新 worktree 时不需要记得分配端口，
> **端口从名字算出来，天然不冲突**，而且可复现。
> 还有个 CI 检查 `check-worktree-port-offset` 防止有人写死端口。
>
> Redis 也隔离：6398 是开发，6399 是生产。
> 就一个端口号之差，所以他们专门加了一条 SOP 门禁规则 ——
> `env_check` 类型的 predicate，
> 要求 `REDIS_URL` 必须含 `:6398` 且不含 `:6399`。
>
> 这对应他们的第一条铁律'数据存储圣域'——
> 因为 Agent 有 shell 权限，一个 `redis-cli flushall` 就能删掉用户所有数据。"

### 3.6 桌面打包的税

```
desktop/
├─ main.js              Electron 主进程
├─ preload.js
├─ afterPack.js         打包后处理
├─ project-root.js      ★ 定位项目根
├─ project-root.test.js
├─ installer/
└─ assets/
```

README 里的描述：

> 桌面安装包会自带应用运行时、便携 Node.js 和 Redis，
> 普通用户不需要手动执行 `pnpm install` 或 `pnpm build`。

**自带 Node + Redis** —— 这是"双击就能用"的代价。

**桌面分发引出的具体问题（都是【源码】里能看到的）：**

**① Windows NTFS junction 的首次启动问题**

`governance-l0.ts` 里那段：

```ts
} catch (primaryErr) {
  // On Windows desktop installs, the project dir lives in AppData and uses
  // NTFS junctions pointing back to the install directory. On the very first
  // launch after installation the junction can fail with UNKNOWN even though
  // the link entry and target both exist. Fall back to reading directly from
  // the install root (derived from this module's file path) so the API can
  // boot instead of crashing.
  const installRoot = deriveInstallRoot();
  // ...
}
```

以及：

```ts
// ENOENT: file genuinely missing.
// UNKNOWN: Windows NTFS junction not yet usable on first boot after
// installation — treat as absent; the junction resolves on next launch.
if (code === 'ENOENT' || code === 'UNKNOWN') return null;
```

**"first boot after installation" 的 junction 问题** ——
链接和目标都存在，但读取报 UNKNOWN。第二次启动就好了。

**这是纯粹的平台税，逻辑上完全不该存在，但你必须处理。**

**② 从模块路径反推安装根目录**

```ts
/**
 * Derive the install root from this module's file path.
 * governance-l0.ts lives at packages/api/src/domains/cats/services/context/
 * → dist layout: packages/api/dist/domains/cats/services/context/governance-l0.js
 * → 7 levels up from __filename reaches the install root.
 */
function deriveInstallRoot(): string | null {
  try {
    const thisFile = fileURLToPath(import.meta.url);
    return resolve(dirname(thisFile), '..', '..', '..', '..', '..', '..', '..');
  } catch {
    return null;
  }
}
```

**数了 7 层往上。** 而且注释里画出了 src 和 dist 两种布局。

【推断】**这段代码很脆** —— 目录结构改一层它就错。
但在桌面打包场景下，"找到安装根目录"确实没有更好的办法
（`process.cwd()` 不可靠，环境变量可能没设）。

**③ Windows 的 symlink 差异**

```ts
function symlinkTargetFor(linkPath: string, sourcePath: string): string {
  return process.platform === 'win32' ? sourcePath : relative(dirname(linkPath), sourcePath);
}
```

**Windows 用绝对路径，Unix 用相对路径** —— 因为 Windows 对相对符号链接支持很差。

**④ shell 脚本只能用 ASCII**

```
check-scripts-ascii-only.mjs
```

**Agent 写的脚本容易混进中文注释或全角标点**，
在某些 Windows shell / 编码环境下会炸。

**⑤ Windows 需要 Git Bash**

hook README 里：

> **Windows 用户**：需要安装 [Git for Windows](https://gitforwindows.org/)（提供 Git Bash）。
> Hook 命令通过 `bash` 显式调用，确保跨平台执行。
> 如果不装 Git Bash，`.sh` 文件会被 VS Code 等编辑器打开而不是执行。

**"会被编辑器打开而不是执行"** —— 这个失败模式很有画面感。

**面试话术**：

> "桌面打包要交的税比我预想的多，代码里能看到至少五处：
>
> 一，**Windows NTFS junction 的首次启动问题** ——
> 桌面安装后项目目录在 AppData 里，通过 junction 指回安装目录。
> 安装后第一次启动时，链接和目标都存在但读取报 UNKNOWN，第二次就好了。
> 所以他们的代码里把 UNKNOWN 和 ENOENT 一起当"文件不存在"处理，
> 还写了个从模块路径往上数 7 层反推安装根目录的 fallback。
>
> 二，**Windows 的 symlink 要用绝对路径**，Unix 用相对路径。
>
> 三，**shell 脚本禁止非 ASCII**，有 CI 检查 ——
> 因为 Agent 写的脚本容易混进中文注释，
> 在某些 Windows 编码环境下会炸。
>
> 四，**Windows 需要 Git Bash**，而且 hook 命令必须显式用 `bash` 调用 ——
> 否则 `.sh` 文件会被编辑器打开而不是执行。
>
> 五，安装包要**自带 Node 运行时和 Redis**。
>
> 这些都是逻辑上完全不该存在的复杂度，但**'双击就能用'这个目标
> 决定了你必须处理它们**。
>
> 而且反过来说，正是因为选了这个部署形态，
> 才决定了'不用向量数据库、不用 Kafka、不容器化'这些架构选择。"

### 3.7 启动 profile 隔离

```
"start:direct": "node ./scripts/start-entry.mjs start:direct --profile=opensource",
"dev:direct":   "node ./scripts/start-entry.mjs dev:direct --profile=opensource",
```

以及 CI 检查：

```
check:start-profile-isolation
```

【ADR】ADR-016 里有相关决策：

> ### N3: 不分叉 `start-dev.sh` 成两份真相源
>
> **否决理由**：方案 B（clowder-ai 有自己的 start-dev.sh）
> 会创造两份启动链真相源，未来必然漂移，
> 且 sync transform 需要额外维护这个分叉点。
>
> **采纳方案**：Profile 化 `start-dev.sh --profile=dev|opensource`，
> 一份脚本、不同 profile 决定默认值和 sidecar/proxy 策略。
> **`.env` 只做显式 override，不负责定义环境身份。**

**最后一句很重要：`.env` 不定义环境身份，只做覆盖。**

【推断】为什么？因为如果环境身份靠 `.env` 判断，
用户复制了一份别人的 `.env` 就会跑成错误的环境。
**用显式的 `--profile` 参数，身份是命令行里可见的。**

### 3.8 另一条启动脚本的决策

【ADR】ADR-016：

> ### N4: 不在 `start-dev.sh` 默认自动安装可选依赖
>
> **否决理由**：启动脚本必须可预测，
> 不能一边拉服务一边偷偷改环境（pip install）。
> 静默自动安装会引入不可控的网络依赖和环境变化。
>
> **采纳方案**：交互式 setup 脚本负责安装可选依赖；
> `start-dev.sh` 只检查、报错、给下一步命令。
> 可选显式 `--install-missing` 触发，但默认不安装。

**"启动脚本必须可预测，不能一边拉服务一边偷偷改环境"** ——
这句话可以直接抄。

**而且"只检查、报错、给下一步命令"这个模式和 §3.2
存储守卫的错误消息是一致的** —— **报错要给出路。**

```

check:env-registry     环境变量注册表
check:env-example      .env.example 同步
scripts/gen-env-reference.mjs   生成环境变量文档
```

**`.env.example` 有 9279 字节** —— 说明环境变量非常多。

**所以需要：**
```
① 注册表（所有环境变量在一处声明）
② 同步检查（代码里用了新变量但 .env.example 没加 → CI 红）
③ 自动生成文档
```

**这和 [模块 14](14-模块-SOP门禁.md) 的
"YAML 生成 TS 类型 + 过期检查"是同一个模式。**

## 4. 为什么这么设计

### 决策 A：为什么存储要全接口化

**取舍**：两套实现的维护成本 vs 部署门槛 + 可测性。

【推断】判断依据：

```
如果目标用户是开发者    → 要求装 Redis 完全可以接受
如果目标用户包括普通人  → 必须有零依赖模式
```

**这个项目明确要覆盖普通用户（有安装包），所以接口化是必须的。**

### 决策 B：为什么 fail-closed 而不是自动降级

**取舍**：可用性 vs 数据安全。

**内存模式会静默丢数据，而数据丢失是不可逆的。**
所以选择"拒绝启动 + 明确的错误消息"。

**这个判断和 L0 编译的 fail-closed 一致 ——
项目在"静默错误 vs 明确失败"上很一致地选了后者。**

### 决策 C：为什么端口从名字推导

**取舍**：可能哈希冲突 vs 零配置。

【推断】推导的价值是**免维护**：
Agent 开新 worktree 不需要查"哪些端口被占了"，
也不需要有人维护一张端口分配表。

**代价是可能冲突（哈希碰撞），但概率低且有 CI 检查兜。**

## 6. 如果重新设计

【推断】以下全是我的方案。

### 6.1 给两套存储实现加"一致性契约测试"

**现在最大的风险**：27 个接口 × 2 套实现 = 54 个实现，
**怎么保证两套语义一致？**

Redis 有很多特殊语义：

```
原子自增（incrementCompressionCount）
有序集合的 score 语义（thread 消息排序）
TTL
Lua 脚本的原子性
HSCAN 的游标语义
```

**内存实现要手动模拟这些。一旦模拟得不对，
就会出现"Redis 模式好的，内存模式有 bug"（或反过来）。**

**我的方案**：

```
tests/contracts/stores/
├─ MessageStore.contract.ts      一份测试，两套实现都跑
├─ ThreadStore.contract.ts
└─ ...

// 写法
describe.each([
  ['redis', () => new RedisMessageStore(testRedis)],
  ['memory', () => new MemoryMessageStore()],
])('MessageStore (%s)', (name, factory) => {
  // 同一份测试用例
  it('append 后 getByThread 返回时序正确', ...);
  it('并发 append 不丢消息', ...);
  it('markDelivered 改变 score 但不改变时序', ...);   // ★ 这条有真实 bug 痕迹
});
```

**最后那条测试有真实依据** ——
`AgentRouter.ts` 里有段注释提到：

```
// markDelivered 把 score 改成 deliveredAt 但…
```

**这说明"score 语义"曾经出过问题。**

**为什么这是最高优先的改进？**
因为**两套实现不一致是最难查的 bug** ——
它只在特定部署模式下出现，而开发者通常只用一种模式测试。

### 6.2 把"可重建/不可重建"变成显式的元数据

**现在的分层写在架构文档里**，靠人记得。

**我的方案**：让每个 store 声明自己的持久性等级。

```ts
interface StoreMetadata {
  durability:
    | 'source-of-truth'      // git 里的文件，不可重建
    | 'durable-state'        // Redis，丢了有损但可接受
    | 'derived-index'        // SQLite/向量，可完全重建
    | 'ephemeral';           // 进程内，重启即丢（如 processingSlots）
  rebuildCommand?: string;   // derived-index 必填
  exportCommand?: string;    // durable-state 建议有
}
```

**收益**：
- 备份策略自动推导（只备份前两类）
- 启动时能自检"derived-index 类的索引在不在，不在就自动 rebuild"
- 新人一眼知道"这个数据丢了严重吗"

**而且能发现问题**：
现在 `QueueProcessor` 的 `processingSlots` / `pausedSlots` 是
`ephemeral`（进程内 Map），但**它们承载的语义是 `durable-state`**——
重启后队列状态应该恢复。

**显式声明会立刻暴露这个不匹配。**
（这也是 [模块 05](05-模块-调用生命周期.md) §6.2 提的"状态外移"的动机。）

### 6.3 桌面平台适配层收口

**现在的问题**：平台差异散在各处。

```
governance-l0.ts        NTFS junction 的 UNKNOWN 处理 + 7 层反推安装根
skill-mount.ts          Windows 绝对路径 vs Unix 相对路径
cli-spawn-win.ts        Windows 的 spawn 差异
check-scripts-ascii-only  ASCII 检查
hook README             Git Bash 要求
```

**每处都是独立的 workaround，没有统一的地方能回答
"这个项目在 Windows 上有哪些特殊处理"。**

**我的方案**：

```ts
// platform/desktop-fs.ts —— 唯一的平台适配层
export const desktopFs = {
  /** 读文件，处理 Windows junction 首启的 UNKNOWN */
  readTolerant(path: string): Promise<string | null>,

  /** 定位安装根，多策略：env → 已知锚文件向上找 → 模块路径反推 */
  resolveInstallRoot(): string | null,

  /** 建 symlink，自动选相对/绝对 */
  createLink(from: string, to: string): Promise<void>,

  /** 平台能力探测 */
  capabilities: { symlinkRelative: boolean; bashAvailable: boolean; ... },
};
```

**特别是 `resolveInstallRoot` 我会改成多策略**：

```
① 环境变量 CAT_CAFE_INSTALL_ROOT（打包时写入）
② 从当前文件往上找已知锚文件（pnpm-workspace.yaml）  ← 比数层数健壮
③ 数 7 层（最后兜底）
```

**因为"往上数 7 层"这个实现，目录结构改一层就错，而且错了很难发现。**
**用"往上找锚文件"更健壮**（项目里已经有 `findMonorepoRoot` 在用这招，
只是 `governance-l0.ts` 的 fallback 没用）。

### 6.4 给端口推导加冲突检测和显式覆盖

**现在的问题**：端口从 worktree 名 hash 推导。
**哈希会碰撞** —— 两个 worktree 名字碰巧算出同一个偏移。

有 `check-worktree-port-offset.mjs` 但那是 CI 检查（防写死端口），
不是运行时的冲突检测。

**我的方案**：

```
启动时：
① 从 worktree 名推导端口
② 探测端口是否已被占用（tcpProbe 已经有了）
③ 被占用 → 线性探测下一个可用偏移 + 明确日志
   "worktree/f456 的推导端口 3023 被占用（可能哈希碰撞），已改用 3033"
④ 记录到一个本地的端口分配文件（便于查"现在谁占了什么"）
```

**加一个显式覆盖：**

```
CAT_CAFE_PORT_OFFSET=50 pnpm dev    # 手动指定
```

**收益**：从"祈祷不碰撞"变成"碰撞了自动处理且可见"。

### 6.5 我不会改的

| 我原本的想法 | 为什么放弃 |
|------------|-----------|
| 去掉内存实现（只支持 Redis） | 部署门槛是这个产品的核心考量；而且测试也依赖内存实现 |
| Redis 不可用时自动降级到内存 | 会静默丢数据；fail-closed 是对的 |
| 用 Docker Compose 统一部署 | 桌面用户装不了 Docker；这是部署形态决定的 |
| 端口写死在配置里 | 推导 + 免维护的价值 > 碰撞风险；而且碰撞可以运行时处理 |
| 分叉启动脚本给不同环境 | 【ADR】两份真相源必然漂移；profile 化是对的 |

## 8. 面试怎么讲

### 30 秒版

见 §0。

### 3 分钟版

> "这块讲工程面。
>
> **存储全接口化** —— `stores/ports/` 下 27 个接口，
> 每个都有 Redis 和内存两套实现。
> 所以 `--memory` 模式能跑，普通用户不用装 Redis，
> 单元测试也不需要起 Redis。
> 代价是每个 store 两套实现要维护，而且要保证语义一致 ——
> 内存实现得手动模拟 Redis 的原子自增、有序集合 score、TTL 这些。
>
> **有个 fail-closed 的存储守卫**：Redis 不可用时，
> 除非显式设 `MEMORY_STORE=1`，否则直接拒绝启动。
> 因为内存模式会**静默丢数据** ——
> 用户聊一整天，重启全没了还不知道原因。
> 而且它是双层的：启动脚本检查一次，这个守卫再兜一次

> SQLite 索引明确定位成"编译产物"（gitignore，随时 rebuild）、
> Redis 是运行时状态。
> **把可重建的和不可重建的分开** ——
> 我觉得这是最实用的一条架构原则。
>
> **部署形态是本地优先的桌面应用**，
> 而且这个形态反过来决定了很多架构选择 ——
> 不用向量数据库、不用 Kafka、不容器化，
> 答案都是同一个：普通用户双击就要能用。
>
> 桌面打包的税也不少：
> Windows NTFS junction 在安装后首次启动会报 UNKNOWN（链接和目标都存在），
> 所以代码里把 UNKNOWN 和 ENOENT 一起当"文件不存在"处理，
> 还写了个从模块路径往上数 7 层反推安装根目录的 fallback；
> Windows 的 symlink 要用绝对路径；
> shell 脚本禁止非 ASCII（有 CI 检查，因为 Agent 写脚本容易混进中文）；
> Windows 还得装 Git Bash，否则 `.sh` 会被编辑器打开而不是执行。"

> 而是一个不同的产品。"

## 9. 本模块要点

| 要点 | 内容 |
|------|------|
| **27 个存储 port × 2 套实现** | Redis 可选的代价 |
| **fail-closed 存储守卫** | 不静默降级到内存；双层防御；错误消息给三条出路 |
| **四层持久性** | 真相源(git) / 工作流状态(git) / 索引(可重建) / 运行时(Redis) |
| **把可重建的和不可重建的分开** | 最实用的一条架构原则 |
| **Markdown 是 Redis 的冷备** | 一份数据同时是备份和知识源 |
| **恢复默认 dry-run** | 危险操作默认只预览 |
| **端口从 worktree 名推导** | 免维护、可复现；和"能推导就不新建"一致 |
| **6398/6399 隔离** | 一个端口号之差，专门加了 SOP 门禁 |
| **桌面五种税** | junction UNKNOWN / 绝对 symlink / ASCII 脚本 / Git Bash / 自带 Node+Redis |
| **【ADR-016】不分叉启动脚本** | 两份真相源必然漂移 → profile 化 |
| **【ADR-016】`.env` 不定义环境身份** | 只做覆盖；身份用命令行参数（可见） |
| **【ADR-016】启动脚本不自动装依赖** | "必须可预测，不能一边拉服务一边偷偷改环境" |
| **【ADR-016】有损变换不能双向同步** | 22 个逆映射维护不了 |
