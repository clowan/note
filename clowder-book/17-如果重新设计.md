# 17 · 如果重新设计

> 面试里"如果让你重新设计会怎么做"是一道**分水岭题**。
>
> 答不好的表现：说"我会用更好的架构"（空话），
> 或者把项目的每个设计都批一遍（显得没理解取舍）。
>
> 答好的表现：**能说出哪些设计我会保留（并说出为什么），
> 哪些我会改（并说出代价），以及如果需求变了架构会怎么翻。**
>
> 本章是系统级的重构方案。单个模块的改进在各章的 §6。

---

## 0. 30 秒电梯版

> "我会保留三个核心判断：CLI 子进程（订阅额度不可替代）、
> 机械路由 + 模型判断（语境判断该归模型）、
> 本地优先（部署门槛是这个产品的命）。
>
> 我会改三处结构性问题：
> **一，状态表太多** —— 一次调用有六套状态表描述它的不同侧面，
> 靠对账器维护一致性。而他们最新的球权模块已经用事件溯源了，
> 证明这条路可行，老模块该迁过去。
> **二，provider 适配层没抽象** —— 六个大类各写一遍完整流程，
> 但只有两步是真差异，四步是配置差异。
> **三，缺契约测试** —— 上游改输出格式是这个架构唯一的系统性风险，
> 现在完全靠用户报障发现。
>
> 而且我会补一层**观测闭环**：
> 现在很多机制'建好了但不知道有没有被用'——
> Skill 加载、SOP 的 manual_only 规则、30 天 replay 验证，
> 全都缺反馈数据。"

## 1. 先说我会保留什么

**这一节比"改什么"更重要** —— 它证明你理解了取舍。

### 保留一：CLI 子进程作为默认调用路径

**为什么不改**：

```
订阅额度这一条无法替代。
如果用户已经买了 Claude Pro / ChatGPT Plus，
走 API 就是重复付费 —— 而且成本差一个数量级。

而且 CLI 自带的东西是白送的：
文件读写、shell、git、内置 MCP、会话恢复、上下文压缩。
自己实现要几个月，而且做不到那个成熟度。
```

**【ADR】而且他们已经翻过一次案了** ——
初稿选官方 SDK，两天后因"只能用 API key 计费"推翻。
**我没有比这更好的理由去翻回来。**

**唯一的条件变化**：如果哪天官方 SDK 支持 OAuth 订阅授权，
那 SDK 方案的所有优势就都能拿到了 —— 少五千行适配、少启动开销、少格式漂移。
**那时候我会重新评估，但判据还是那一条：能不能用订阅额度。**

### 保留二：机械路由 + 模型判断

**为什么不改**：

```
"请让 @opus 来 review" 到底是现在叫他还是只是提到他 ——
这是语境判断，正则永远做不对。

路由层一旦开始猜，就会陷入无穷的误报修补：
每加一条规则解决一类误报，就引入一类新的漏报。
而每次误报都是真金白银。
```

**而且他们试过更聪明的版本并退回了** ——
早期做过句中"动作提及"检测，因为误报和歧义放弃了。
**这是有实践依据的收紧，不是懒。**

**我唯一想改的是一处不一致**：意图判断（串行还是并行）
现在用的是机械规则（"≥2 只就并行"），
但那明显是语义判断，应该归模型（见 [模块 03](03-模块-路由与编排.md) §6.1）。

### 保留三：本地优先的部署形态

**为什么不改**：

```
它决定了产品能覆盖的用户范围。
"必须先装 Redis / Docker / 向量数据库"会挡掉大部分用户。

而且数据敏感：项目文档、对话历史、用户画像 —— 这些不该出本机。
```

**代价我也认**：单进程、扩不了、桌面平台税。
**但对这个产品的定位来说是对的。**

### 保留四：几个具体设计

| 设计 | 为什么保留 |
|------|-----------|
| **L0 从 Markdown 确定性编译 + fail closed** | 摘要不稳定；宁可崩溃不要静默丢治理规则 |
| **prompt 存成 `.md` 模板** | 能 diff、能不重编译改、能审计、有段号 |
| **权威度从路径推导** | 任何需要人记得做的流程最终都会有人忘 |
| **消费信号只影响导航不影响权威** | 否则系统陷入回音室 |
| **告示牌哲学（不用传送带）** | 传送带在异常情况下会把 Agent 送进沟；而且强制依赖工具级 hook，各 CLI 不一致 |
| **封板协议（LLM reviewer 的机械上限）** | `P1/P2==0` 没有不动点，机械判定无弹性是对的 |
| **最小杠杆排序** | Agent 的本能是改 L0，而 L0 边际收益递减 |
| **双车道（承认有些知识停在 L2/L3）** | 大部分成熟度模型的错误就是假设"都该往上走" |
| **存储 fail-closed（不静默降级到内存）** | 数据丢失不可逆 |
| **符号链接分发 Skills** | 让"一份源"这个约束物理成立，不靠流程保证 |

## 2. 三个结构性问题

### 问题一：状态表太多，靠对账器维护一致性

**现状**：一次调用的状态散在六处。

```
InvocationRecord.status          queued/running/succeeded/failed/canceled
InvocationTracker slot           active/canceled(墓碑)/absent
QueueEntry.status                queued/processing
QueueProcessor.processingSlots   进程内 Map
QueueProcessor.pausedSlots       进程内 Map + pauseEpoch
球权投影                          new/active/blocked/parked/dead/void/zombie/resolved
```

**症状**（都能在代码里看到）：

```
ensureTerminalStatus.ts       确保终态一致
reconcileZombies.ts           回收僵尸
StartupReconciler.ts          启动对账
getThreadLiveInvocations.ts   1122 行 —— 判"到底几个活的"
sweepZombieSlots()            队列侧的僵尸清扫
reconcileStuck / reconcileAllStuck   会话封存的两级收尸
cleanupStreamingOnFailure     流式失败清理
```

**七个对账/清理机制，全都在补同一个问题：多套状态表之间的一致性。**

### 我的方案：统一成事件溯源

**关键论据：球权模块已经是这个模式了，而且它是全项目最新的模块。**

```
BallCustodyEventLog（append-only）
   → BallCustodyProjector（纯函数）
      → BallCustodyProjectionStore
rebuild = delete + replay，要求逐字段一致
```

**所以这不是我凭空提议，是"让老模块学新模块"。**

**目标形态：**

```
invocation_events（append only，唯一真相源）
  ├─ invocation.enqueued
  ├─ invocation.started
  ├─ invocation.heartbeat
  ├─ invocation.output_chunk
  ├─ invocation.tool_called
  ├─ invocation.canceled
  ├─ invocation.failed
  └─ invocation.completed
        │
        ├──→ 投影 1：当前状态（给 UI 和查询）
        ├──→ 投影 2：slot 占用（给判忙）
        ├──→ 投影 3：队列状态
        ├──→ 投影 4：球权（已经是这个模式）
        └──→ 投影 5：审计日志
```

**收益：**

| 现在 | 改后 |
|------|------|
| 六套表互相对账 | 投影是否幂等（单一正确性条件） |
| 七个对账/清理机制 | replay 事件（一个机制） |
| 重启恢复靠专门的 reconciler | 重启 = replay |
| 调试要拼多个状态表 | 看一条事件流 |
| MCP 回调和 stdout 是两条写入路径 | 都写同一个日志 |

**代价（必须说清）：**

```
① 迁移风险高 —— 六套表的读写点遍布全项目
② 事件日志会增长 —— 需要归档策略（快照 + 截断）
③ 投影延迟 —— 最终一致，UI 可能短暂看到旧状态
④ 需要保证投影幂等 —— 这是新的正确性负担
```

**所以我会增量做，分四步：**

```
第一步：新功能只写事件、只读投影（不动旧表）
第二步：把球权之外最独立的一块（比如审计日志）改成投影
第三步：把 QueueProcessor 的三个进程内 Map 改成 Redis 投影
        （顺带解决"重启丢队列状态"和"扩不了"）
第四步：InvocationRecord 和 Tracker slot 变成投影，删掉对账器
```

**面试话术**：

> "我认为最大的结构性问题是**状态表太多**。
> 一次调用的状态散在六处：InvocationRecord、Tracker slot、
> QueueEntry、两个进程内的 Map、球权投影。
> 它们之间的一致性靠代码互相调用维护，
> 所以有七个对账和清理机制 ——
> `ensureTerminalStatus`、`reconcileZombies`、`StartupReconciler`、
> `sweepZombieSlots`、两级收尸……
> 还有个 1122 行的文件专门回答'这个帖子到底有几个活的调用'。
>
> **我会统一成事件溯源。** 而且这不是我凭空提议 ——
> 他们最新的球权模块已经是这个模式了：
> 事件日志 append-only、投影器纯函数、rebuild 是 delete + replay，
> 而且要求 replay 出来的投影逐字段一致。
> **所以是让老模块学新模块。**
>
> 收益是一致性问题从'六套表互相对账'变成'投影是否幂等'，
> 重启恢复从'专门的 reconciler'变成'replay 事件'。
>
> 但代价要说清：迁移面很大、事件日志要归档、投影有延迟。
> 所以我会分四步增量做，先让新功能只写事件，
> 然后从最独立的部分开始迁 ——
> 第三步把队列的三个进程内 Map 改成 Redis 投影，
> 顺带把'重启丢队列状态'和'扩不了'这两个问题一起解决。"

### 问题二：Provider 适配层没抽象

**现状**：六个 provider 各写一遍完整流程，共约 5000 行。

```
GeminiAgentService.ts    1569
CodexAgentService.ts     1335
ClaudeAgentService.ts     957
ClaudeBgCarrierService     709
OpenCodeAgentService.ts    605
ClaudeInteractivePty       450
KimiAgentService.ts        450
+ 各自的 parser / transform / config writer
```

**观察**：六个步骤里只有两步是真差异。

```
① 解析账号凭据       逻辑几乎一样          ← 配置差异
② 决定新开还是 resume 差异只在参数写法     ← 配置差异
③ 写 MCP 配置        差异在路径和格式      ← 配置差异
④ 拼命令行 + spawn   差异在参数拼法        ← 配置差异
⑤ 解析输出           ★ 真差异（五种格式）
⑥ 映射成 AgentMessage ★ 真差异
```

### 我的方案：能力矩阵 + 解析器

```ts
// 配置差异全进这张声明式的表
interface CliCapability {
  command: string;
  outputFormat: 'stream-json' | 'json' | 'ndjson' | 'plain' | 'acp';

  resume: { style: 'flag'; flag: string }
        | { style: 'config'; key: string }
        | { style: 'none' };

  mcp: { kind: 'native-flag'; flag: string }
     | { kind: 'config-file'; path: string; format: 'json' | 'toml' }
     | { kind: 'none' };                   // → 走回调桥

  systemChannel?: { flag: string; compressionImmune: boolean };
  hooks: readonly ('PreCompact' | 'SessionStart' | 'Stop' | 'PostToolUse')[];
  contextWindow: number;
  sealThresholds: { warn: number; action: number };
  carriers?: readonly CarrierTier[];
}

// 只有这个各写一份
interface OutputParser {
  parse(chunk: string, state: ParserState): { messages: AgentMessage[]; state: ParserState };
}
```

**收益**：加一个新 CLI 从"写 1500 行"变成"填配置 + 写 parser"。

**而且能力矩阵能把散落的能力标记统一起来** ——
现在这些标记散在各处：

```
HOOK_CAPABLE_PROVIDERS = new Set(['anthropic'])       // session-strategy.ts
nativeL0Injection?: boolean                            // AgentService 接口
DEFAULT_STRATEGY_BY_PROVIDER                           // session-strategy.ts
needsMcpInjection()                                     // McpPromptInjector
DEGRADATION_CHAIN（只有 Claude 有）                     // carrier-health.ts
```

**五处能力标记，五个地方定义。** 收进一张表之后：

```
上层要判断"这个 provider 支不支持 X" → 查一张表
新增 provider → 填一行
新增能力维度 → 加一个字段 + 补全所有 provider
```

**代价（必须说清）：**

```
抽象一旦不够用，会出现绕过抽象的特例分支，反而更难读。
所以能力矩阵的字段必须从真实差异里长出来，不能提前设计。
```

**这也解释了为什么项目现在是那个形态**：
它是在不知道会接六种 CLI 的时候一个个加起来的。
**先写六遍再抽象，比先抽象再往里塞，是对的顺序。**

**我做这个抽象的前提是：现在已经有六个样本了。**

### 问题三：缺契约测试

**这是我认为投入产出比最高的一个改进。**

**现状**：上游改格式 → 线上才发现 → 紧急修。

**证据链（全是【源码】）：**

```
"Required for claude 2.1.172+ where interactive TUI no longer writes transcripts."
"Codex CLI deprecated OPENAI_BASE_URL env var."
"Google consumer Gemini CLI 在 2026-06-18 停止服务"
"agy 早期把 cascade UUID 写进 log"   ← 靠这个逆向工程内部数据库
```

**而 ADR-001 明确把这条列为已知风险：**

> **NDJSON 格式变化**：CLI 升级可能改变输出格式，需版本锁定 + 容错解析

**已知风险 + 已经兑现多次 + 完全靠用户报障发现 = 该补测试。**

### 我的方案

```
tests/contracts/
├─ fixtures/
│   ├─ claude-2.1.172-stream-json.jsonl      真实抓取的输出
│   ├─ codex-0.x-json.jsonl
│   ├─ agy-print-plain.txt
│   ├─ opencode-ndjson.jsonl
│   └─ META.json                              抓取时间 + CLI 版本
├─ contract.test.ts
│   每个 fixture 必须解析成预期的 AgentMessage 序列
└─ freshness.cron.ts
    每周用真实 CLI 跑一个最小任务 → 抓输出 → 和 fixture diff
```

**关键设计：定期任务告警而不是失败。**

```
上游新增字段 → 合法（向后兼容）→ 只记录，不告警
我们依赖的字段消失 → 问题 → 告警
输出结构大改 → 严重问题 → 告警 + 附 diff
```

**收益**：把"发现延迟"从几周压到几天。

**为什么优先级最高？**
因为格式漂移是这个架构**唯一的系统性风险**——
其他问题都是"某个功能不好用"，这个是"整条通路断了"。

## 3. 一层横切的缺失：观测闭环

**这是我读完全部模块之后最强的一个感受。**

**很多机制"建好了但不知道有没有被用"：**

| 机制 | 缺什么 | 后果 |
|------|--------|------|
| Skill 分发 | 加载遥测没闭环 | symlink 坏了 Agent 静默不加载，一周后才发现代码没测试 |
| SOP 的 `manual_only` 规则 | 没有"已人工检查"的记录 | 不知道这些规则实际守住了没 |
| Self-Evolution 的 30 天 replay | 没自动化 | 改进有没有效果不知道 |
| Scope Guard 灵敏度 | 成功率统计是手工的 | 误报率高的护栏会被忽略 |
| Pitfall 清单 | 没有发生率追踪 | 清单单调增长，没人敢删 |
| CJK 检索权重 1.5 | 没纳入评估设施 | 换 embedding 模型后不知道还合不合适 |
| 跨模型互审有效性 | 没度量 | "跨族优先"是未经验证的先验假设 |

**而且项目自己承认了这个问题**【源码】：

> **F231 adoption 仍是硬问题**
> F231 机制全绿，但历史上出现过"C1 merged 2 天零有机使用"
> 和 8 天 `profile_update.proposed = 0`。

**"机制全绿但零有机使用"** —— 这一句话概括了整个问题。

### 我的方案：统一的机制健康度面板

```
每个"治理机制"必须声明它的健康信号：

interface MechanismHealth {
  id: string;                        // 'skill-load' | 'sop-manual-attest' | ...
  // 使用量
  invocations: { last7d: number; last30d: number; trend: 'up'|'flat'|'down' };
  // 有效性（每个机制自己定义）
  effectiveness?: { metric: string; value: number; target: number };
  // 状态
  status: 'healthy' | 'unused' | 'ineffective' | 'noisy';
}
```

**四种状态的判定和处理：**

```
healthy      → 正常
unused       → 30 天零使用 → 要么机制没接线，要么根本不需要 → 进 review
ineffective  → 有使用但目标指标没改善 → 杠杆找错了 → 重走 Mode B
noisy        → 触发多但被接受率低 → 误报率高 → 收紧阈值
```

**然后关键的一步**（这是项目自己的教训教我的）：

> **把这份面板做成"必须被消费"的东西** ——
> 每周指派一只 Agent 处理它，处理结果写回证据库。
> **不是生成报告放着。**

**因为项目自己的教训是"机制全绿但零有机使用"——
报告不被消费就等于没有。**

**面试话术**：

> "读完所有模块我最强的一个感受是：**缺一层观测闭环。**
>
> 我数了至少七处'机制建好了但不知道有没有被用'：
> Skill 加载没遥测（symlink 坏了 Agent 静默不加载）、
> SOP 的 manual_only 规则没有"已人工检查"的记录、
> Self-Evolution 的 30 天验证没自动化、
> Scope Guard 的灵敏度调节是手工的、
> pitfall 清单没有发生率追踪所以只增不减、
> 中文检索的权重系数没纳入他们自己已有的评估设施、
> 跨模型互审的有效性没度量（"跨族优先"其实是个未经验证的先验假设）。
>
> **而且项目自己承认了这个问题** ——
> 记忆系统的架构文档里写着某个机制'全绿但 merged 2 天零有机使用'。
>
> 我会做一个统一的机制健康度面板：
> 每个治理机制声明自己的使用量和有效性指标，
> 分四种状态 —— healthy / unused（零使用）/
> ineffective（有使用但指标没改善）/ noisy（触发多但接受率低）。
>
> 但最关键的一步是：**把面板做成必须被消费的东西**——
> 每周指派一只 Agent 处理它，处理结果写回证据库。
> 因为他们自己的教训就是'机制全绿但零使用'——
> **报告不被消费就等于没有。**
> 这也和他们 Self-Evolution 里那句
> '沉淀不是目的，可调用才是；写了没人读 = 没写'一致。"

## 4. 如果需求变了，架构会怎么翻

**这是面试的高分区** —— 它显示你理解"架构是需求的函数"。

### 场景一：做云端多租户 SaaS

**核心决策会翻过来：**

| 现在 | 云端版 | 为什么 |
|------|--------|--------|
| CLI 子进程（用户订阅额度） | **API 直连成为主路径** | 云端你没法用用户的 Claude Pro |
| 不容器化 | **必须容器化** | 不同租户的代码不能在同一文件系统 |
| 进程内队列 | Redis Stream + consumer group | 要横向扩展 |
| 本地 SQLite 记忆 | 重新评估专用向量库 | 有租户隔离 + 跨租户规模 |
| Redis 可选 | Redis 必需 | 没有"单机零依赖"的诉求了 |
| 存储 27 个 port × 2 实现 | 可以只留一套 | 内存实现的价值消失（除了测试） |

**最有意思的是第一条** ——
[模块 02](02-决策-为什么选CLI子进程.md) 里那条被否掉又 opt-in 加回来的
"API 直连"通路，在云端版会变成**主路径**。

**所以严格说那不是"同一个产品的云端版"，而是一个不同的产品。**
共享的只有上层的编排、记忆、纪律逻辑。

**面试话术**：

> "如果做云端多租户版，我认为**核心架构决策会翻过来**。
>
> 因为 CLI 子进程这条路的核心理由是'用用户已有的订阅额度'——
> 但云端你没法用用户的 Claude Pro，那个额度绑在他本机的登录态上。
> 所以他们那条 opt-in 的 API 直连通路会变成主路径。
>
> 然后连带一串：必须容器化（不同租户的代码不能在同一文件系统）、
> 队列必须外移到 Redis Stream（要横向扩展）、
> 记忆库要重新评估（有租户隔离和跨租户规模）、
> Redis 从可选变必需（内存实现的价值消失）。
>
> **所以严格说那不是同一个产品的云端版，而是一个不同的产品**——
> 共享的只有上层的编排、记忆、纪律逻辑。
>
> 我觉得这个判断本身挺重要：**很多团队会把'加个云端版'当成部署问题，
> 实际上它可能是架构问题。**"

### 场景二：Agent 数量从 4 只涨到 40 只

**会先崩的三个地方：**

```
① 队友名册（模块 07）
   现在全量注入 prompt，5 行表格
   40 只 → 40 行，几千 token × 每个 session
   → 必须改成按需查询（我在模块 07 §6.4 提过）

② reviewer 匹配（模块 11）
   现在只按 family/role/lead/活跃度排序
   40 只里可能有 15 个符合条件
   → 必须加专长匹配（模块 11 §6.1）

③ @mention 解析（模块 04）
   pattern 表从 ~20 条涨到 ~200 条
   长匹配优先的排序 + 前缀冲突检查成本上升
   而且前缀冲突概率大增
   → 必须收紧 handle 命名空间（模块 04 §6.3）
```

**而不会崩的地方**：路由护栏（扇出 2 × 深度 15 和 Agent 数量无关）、
球权状态机（和 Agent 数量无关）、存储抽象。

**这个分析的价值**：它显示你能判断"哪些设计是 O(1) 的，哪些是 O(n) 的"。

### 场景三：单 Agent 场景（简化版）

**如果只有一只 Agent，能删掉哪些模块？**

```
可以整个删：
  ├─ 模块 04 A2A mention 解析（没有 Agent 之间的路由）
  ├─ 模块 11 跨模型互审（没有第二只 Agent）
  └─ 模块 10 球权状态机（只有一个持球者）

可以大幅简化：
  ├─ 模块 03 路由（只剩"意图 + 单目标"）
  ├─ 模块 06 Provider 适配（只适配一种 CLI）
  ├─ 模块 07 身份注入（不需要队友名册、同族提醒）
  └─ 模块 05 判忙（不需要 slot 级，thread 级就够）

必须保留：
  ├─ 模块 08 会话与抗压缩（单 Agent 也有上下文压缩）
  ├─ 模块 09 记忆（单 Agent 也要跨 session 记忆）
  ├─ 模块 12/14/15 Skills/SOP/进化（单 Agent 也需要方法论和纪律）
  └─ 模块 13 MCP（单 Agent 也要往回写数据）
```

**这个分析很有价值，因为它回答了"多 Agent 到底带来了什么额外复杂度"：**

```
多 Agent 独有的复杂度 = 路由 + 互审 + 球权 + 身份消歧 + slot 判忙 + 公平性
                     ≈ 全项目复杂度的 40%
```

**面试话术**：

> "有个反向的思考我觉得挺有意思：如果只有一只 Agent，
> 哪些模块能删掉？
>
> A2A mention 解析、跨模型互审、球权状态机可以整个删；
> 路由、Provider 适配、身份注入可以大幅简化；
> 但会话抗压缩、记忆、Skills、SOP、MCP 回调必须保留 ——
> 因为那些问题单 Agent 也有。
>
> 我粗估**多 Agent 独有的复杂度大概占全项目的 40%**：
> 路由、互审、球权、身份消歧、slot 级判忙、队列公平性。
>
> 这个比例我觉得挺说明问题的 ——
> **'让多个 Agent 协作'不是在单 Agent 上加个消息总线，
> 而是接近于把复杂度翻倍。**"

## 5. 我会重新排的优先级

如果我接手这个项目，按投入产出比排序：

| 优先级 | 改动 | 为什么这个顺序 |
|--------|------|--------------|
| **P0** | 契约测试 + 定期真机抓样本 | 唯一的系统性风险，现在完全靠用户报障 |
| **P0** | SOP 覆盖率仪表盘 + 门禁 | 极便宜（数据已在 YAML 里），防 `manual_only` 变逃生门 |
| **P1** | 存储两套实现的契约测试 | 不一致的 bug 最难查，只在特定部署模式出现 |
| **P1** | Skill 加载遥测闭环 | 分发做得再好，没被加载也是白搭 |
| **P1** | Self-Evolution 的 30 天 replay 自动化 | Verify 不自动化，整个闭环是开口的 |
| **P2** | 队列状态外移到 Redis | 顺带解决"重启丢队列"和"扩不了" |
| **P2** | Provider 能力矩阵化 | 收益明确，但要动 5000 行，风险中等 |
| **P2** | 机制健康度面板 | 解决"机制全绿但零使用" |
| **P3** | 调用生命周期迁事件溯源 | 收益最大但风险最高，要先有前面的测试铺垫 |
| **P3** | 结构化交接为主路径（F055） | 项目自己的路线图里有，只是没做 |

**排序逻辑（面试可以讲）：**

> "我的排序逻辑是**先补观测，再改结构**。
>
> P0 两条都是'加测试/加度量'——不改任何行为，风险极低，
> 但能立刻让问题可见。
> 契约测试解决唯一的系统性风险；
> SOP 覆盖率仪表盘极便宜（数据已经在 YAML 里了），
> 而且能防 `manual_only` 变成太方便的逃生门。
>
> P1 三条是'把已有机制的反馈闭环补上'——
> 存储两套实现的一致性、Skill 有没有被加载、改进有没有效果。
>
> P2 才开始改结构，而且都是局部的。
>
> **P3 那两条（事件溯源、结构化交接）收益最大但风险最高**，
> 我会放最后 —— 因为它们要动很多地方，
> 必须先有前面的测试和度量铺垫，否则改坏了都不知道。
>
> **这个顺序背后的原则是：在能看见的系统里改，不在黑盒里改。**"

## 6. 三个我原本想改但放弃的

**面试里主动说这个很加分** —— 它显示你会推翻自己。

### 放弃一：上进程池减少 CLI 启动开销

**原本的想法**：每次 spawn 有 0.5~2 秒开销，用进程池复用。

**为什么放弃**：

```
① 会话隔离难做 —— 上一个任务的状态会污染下一个
   （CLI 的 session、cwd、环境变量、打开的文件句柄）
② 健康检查复杂 —— 池里的进程可能是半死状态
③ 复杂度不比现在的适配层小

而且他们已经有更聪明的解法：
  轻量任务走 API 直连（方案 E），重活才付启动开销
```

**【ADR】而且 ADR-001 明确写了"不做边界：本轮不引入进程池"**——
是知道但故意不做，不是遗漏。

### 放弃二：统一成一条回程通路

**原本的想法**：stdout 和 MCP 回调两条路太麻烦，统一成一条。

**为什么放弃**：

```
stdout 是 CLI 的既有行为 —— 改不了
MCP 是标准协议 —— 不该改

所以"两条路"不是设计选择，是外部约束
```

**但我保留了一个更小的改动**：
**两条路都写同一个事件日志**（§2 问题一），
统一的是"状态收敛点"，不是"传输通路"。

### 放弃三：全部走 ACP 协议统一 Provider

**原本的想法**：ACP 是结构化双向协议，比解析纯文本好太多，全走 ACP。

**为什么放弃**：

**【ADR】ADR-001 的 F210 更新注释里有答案：**

> 但 catalog 配了 `acp` section 的Siamese仍优先走 `GeminiAcpAdapter` / `gemini --acp`，
> **直到 `agy` 暴露受支持的 ACP server mode**。

**他们本来就想全走 ACP，是上游不支持。**
**这不是设计问题，是等待上游。**

**我没有比"等上游"更好的办法。**

## 7. 一句话总结这一章

> **我会保留它所有基于"取舍"的决定，改掉所有基于"来不及"的欠账。**

```
基于取舍的（保留）：
  CLI 子进程 / 机械路由 / 本地优先 / fail-closed / 告示牌 / 封板协议

基于来不及的（改）：
  六套状态表 / provider 没抽象 / 缺契约测试 / 观测闭环缺失
```

**怎么区分这两类？看有没有 ADR 或注释说明"为什么这样"：**

```
有明确理由的 → 取舍，尊重它
只有"历史演进"的 → 欠账，可以改
```

**这个判据我觉得挺实用** ——
它让"重新设计"变成一件有依据的事，而不是凭个人偏好推翻。

## 8. 面试怎么讲这一章

### 被问"如果重新设计会怎么做"的标准答法

**结构：先保留，再改动，最后说条件变化。**

> "我会先说我**不会**改什么，因为那些是有明确取舍依据的。
>
> **CLI 子进程**这条我不会翻 —— 订阅额度无法替代，
> 而且他们已经从官方 SDK 方案翻过一次案了，理由是'SDK 只能用 API key 计费'。
> 我没有比这更好的理由翻回去。
>
> **机械路由 + 模型判断**我也不会改 ——
> 语境判断该归模型，而且他们试过更聪明的版本并退回了。
>
> **本地优先的部署形态**不会改 —— 它决定了产品能覆盖的用户范围。
>
> **我会改三个结构性问题。**
>
> 第一，**状态表太多**。一次调用的状态散在六处，
> 靠七个对账机制维护一致性。我会统一成事件溯源 ——
> 而且这不是凭空提议，他们最新的球权模块已经是这个模式了，
> 是让老模块学新模块。但代价是迁移面很大，所以要分四步增量做。
>
> 第二，**Provider 适配层没抽象**。六个大类各写一遍完整流程，
> 但我数了下六个步骤里只有两步是真差异，四步是配置差异。
> 我会做成'能力矩阵 + 解析器'。
> 不过我要说清 —— **先写六遍再抽象是对的顺序**，
> 他们现在的形态是历史演进的结果，不是设计失误。
> 我做这个抽象的前提是现在已经有六个样本了。
>
> 第三，**缺契约测试**。上游改输出格式是这个架构唯一的系统性风险，
> 而且已经兑现好几次了 —— Claude 改了 transcript 行为、
> Codex 废了环境变量、Google 直接停了服务。
> 现在完全靠用户报障发现。
>
> **另外我会补一层横切的观测闭环。**
> 我数了至少七处'机制建好了但不知道有没有被用'——
> 而且项目自己的文档承认了这个问题，写着某个机制
> '全绿但 merged 2 天零有机使用'。
>
> **最后说个判据**：我区分'该改'和'不该改'的方法是 ——
> 看有没有 ADR 或注释说明为什么这样。
> 有明确理由的是取舍，尊重它；只有'历史演进'的是欠账，可以改。
> **我会保留它所有基于取舍的决定，改掉所有基于来不及的欠账。**"

### 追问：你觉得最该先做哪一个？

> "**契约测试。** 三个理由：
>
> 一，它是唯一的**系统性风险** ——
> 其他问题是'某个功能不好用'，这个是'整条通路断了'。
>
> 二，它**不改任何行为**，风险极低。
>
> 三，它是后面所有改动的**前提** ——
> 你要重构 provider 层，得先有测试保证重构没改变行为。
>
> 我的整个优先级排序都是这个逻辑：**先补观测，再改结构。
> 在能看见的系统里改，不在黑盒里改。**"
