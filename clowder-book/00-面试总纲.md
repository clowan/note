## 1. 先搞清楚：这个项目在解决一个什么级别的问题

面试时最容易犯的错，是把项目说小了。

**说小了的版本**（听起来像个玩具）：

> "这是一个可以同时调用 Claude、GPT、Gemini 的聊天工具。"

**说到位的版本**：

> "现在市面上的 Agent 框架，解决的都是'怎么把一次 LLM 调用包成一个 Agent'——
> 核心是 Agent Loop。
> 这个项目解决的是它的下一个问题：**这些 Agent 之间怎么协作**。
>
> 听起来像是加个消息总线就完了，实际不是。
> 一旦 Agent 之间能直接对话，你立刻要回答一堆新问题：
> 一条 `@` 到底算不算路由指令？上下文被压缩了 Agent 怎么知道自己在干什么？
> 让 GPT review Claude 的代码，谁来选这个 reviewer？
> Claude Code 有 Skills 但 Codex 没有，怎么让一套能力四端生效？
>
> 这些问题都没有现成答案，这个项目把它们一个个落成了代码。"

**为什么这个版本更好？** 因为它做了三件事：

1. **定位了问题的层级**（Agent Loop 之上的一层）
2. **说明了为什么难**（列了四个具体的、面试官一听就懂的难点）
3. **暗示了你读得很深**（这些难点不是 README 上的）

## 2. 三层架构：最需要背下来的一张图

```
┌───────────────────────────────────────────────────────────┐
│  L3  纪律层 —— 项目真正想卖的东西                            │
│      跨模型互审 · SOP 门禁 · Self-Evolution · 愿景守护       │
├───────────────────────────────────────────────────────────┤
│  L2  编排与记忆层 —— 项目的主体，90% 的代码在这              │
│      @路由 · 会话封存 · 身份注入 · 证据库 · Skills · MCP 桥   │
├───────────────────────────────────────────────────────────┤
│  L1  Agent CLI 层 —— 别人写的，一行都不改                    │
│      claude / codex / gemini / agy / opencode / kimi       │
└───────────────────────────────────────────────────────────┘
```

**讲这张图的关键是讲清"为什么不碰 L1"。**

因为这是整个项目最大的一个赌注：
它选择了**建在别人的 CLI 上**，而不是自己调模型 API。

这个选择换来三样东西：
- CLI 自带的完整工具链（读写文件、跑 shell、操作 git、内置 MCP）—— 白送的
- CLI 自带的订阅额度（Claude Pro / ChatGPT Plus）—— 省钱
- CLI 自带的会话恢复（`claude --resume`）—— 抗压缩方案直接建在上面

代价是：**上游改一次输出格式，你就得跟一次。**
六种 CLI 五种输出格式，适配层写了 5000 多行。

这段是 [02 章](02-决策-为什么选CLI子进程.md)的内容，也是**最高频的面试题**。

## 3. 电梯稿：三个长度版本

### 30 秒版（自我介绍里带一句）

> "我深度研究过一个开源的多 Agent 协作平台叫 Clowder AI。
> 它不是 Agent 框架，是架在 Claude Code、Codex 这些 Agent CLI 之上的团队协作层 ——
> 让不同厂商的模型能在同一个对话里互相叫醒、互相 review 代码、共享同一份记忆。
> 我把它的编排、会话、记忆、治理四个子系统全拆了一遍，
> 里面有几个设计我觉得挺值得聊的。"

**最后半句是钩子** —— 引导面试官往你熟的地方问。

### 3 分钟版（"你详细讲讲这个项目"）

分四段，每段大约 45 秒：

**第一段 · 问题**

> "起因很实际：如果你同时用 Claude、GPT、Gemini，你自己就变成了人肉路由器 ——
> 在窗口之间复制粘贴上下文，手动记谁说了什么。
> 这个项目要做的第一件事就是把这个人肉路由器换成代码。
>
> 但真正的难点不在'换掉路由器'，而在换掉之后冒出来的问题。"

**第二段 · 架构**

> "它是个 pnpm monorepo，五个包，但主体就一个 `packages/api`，1300 个 TS 文件。
> 里面按 DDD 分了 22 个 domain，核心是 `domains/cats/services`——
> 编排、调用、上下文、会话都在那儿。
>
> 三层结构：最底下是别人的 Agent CLI，它一行不改；
> 中间是它自己的编排和记忆层；最上面是协作纪律。
> 一条消息进来的路径是：路由决定叫醒谁 → 组装 prompt（身份 + 历史）→
> spawn CLI 子进程 → 解析流式输出 → 检测是否 @ 了下一只猫 → 可能再进一轮。"

**第三段 · 挑一个亮点深讲**（这段最重要，建议选抗上下文压缩）

> "我印象最深的是它怎么处理上下文压缩。
>
> 单 Agent 系统里压缩掉的是'你说过什么'。
> 多 Agent 系统里压缩掉的还有'你现在是第几棒、球在谁手里、你开在哪个 worktree'——
> 这些是控制流状态，CLI 自带的摘要不可能保留它们，因为 CLI 根本不知道这些概念。
>
> 它的方案是三道防线：
> 第一道最便宜，每一轮都注入一行 `Identity: 布偶猫 (@opus, model=...)`，
> 大约 15 个 token，保证无论压缩多少次，最近一轮里一定有一句话说了你是谁。
> 第二道叫连续性胶囊，在压缩边界上冻结一份纯控制流的快照 ——
> 模式、第几棒、谁 @ 的我、A2A 深度、球权状态，一个字段都不是对话内容。
> 第三道是主动封存：到阈值就把当前 session 封掉、生成交接摘要、开新 session 注入。
>
> 恢复时那段 prompt 我觉得写得特别好，它是逐条针对具体失败模式的 ——
> 比如有一句是'在存在的 worktree 无法从上下文确定之前，不要新开 worktree'，
> 说明真的发生过'醒来第一件事就新开一个 worktree，然后有两个了'这种事。"

**第四段 · 你的判断**

> "我觉得这个项目最值得学的是一条贯穿的原则：
> **机械层做路由，判断层留给模型**。
>
> 比如 @mention 只认行首，句中的 `@` 一律不路由 ——
> 因为'请让 @opus 来 review'到底是现在叫他还是只是提到他，
> 这是语境判断，正则永远做不对。
> 所以路由层做到近乎迟钝，把'这条该不该我接'完全交给模型自己判断。
>
> 这个取舍的好处是路由层可以被单元测试钉死，坏处是不保证。
> 但在这个场景下我觉得是对的，因为误路由的代价是烧掉真金白银的 token，
> 而模型恰好擅长判断'这事该不该我干'。"

先给一张**依赖关系图**（谁离不开谁）：

```

                        │  02 CLI 子进程选型 │  ← 一切的地基
                        └────────┬─────────┘

          ┌──────────────────┐      ┌──────────────────┐

                   ┌──────────────────┐

                   └────────┬─────────┘
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
     ┌──────────────┐ ┌──────────┐ ┌──────────────┐

     │ 04 mention   │ │    注入  │ │              │

     └──────────┘ └──────────┘ └──────────────┘

                  ┌──────────────────┐
                  │ 16 存储抽象/部署  │  ← 横切所有层
                  └──────────────────┘
```

**这张图的读法**：

- **02 是地基**。选了 CLI 子进程，才有 06（要适配五种输出格式）
  和 13（CLI 不都支持 MCP，得建回调桥）。如果当初选了 SDK，这两个模块都不存在。
- **05 是枢纽**。所有"调一次模型"都过它，所以 token、超时、僵尸回收都在这。
- **09 是公共设施**。路由要读它（找 reviewer 的历史活跃度）、
  身份要读它（always-on 文档）、会话封存要写它（digest）。
- **11/12/14/15 是"纪律"**，它们都不产生新的运行时能力，
  而是在既有能力上加约束。所以它们在最上面。

### 一句话记住每个模块

| # | 模块 | 一句话 |

> 面试官："他们怎么防止 Agent 互相调用失控？"
>

> 超过 4 次直接硬切。先劝后拦。"

## 7. 面试里的三个雷区

### 雷区一：别把我的推断当成项目的事实

这份笔记里凡是标【推断】的，都是我根据代码形态反推的。
面试官如果追问"这个你从哪看到的"，你答不出出处就很难看。

**安全说法**："我的理解是……"、"我猜他们的考虑是……"、"这块文档没写，我反推的逻辑是……"

### 雷区二：别硬讲你没读过的模块

15 个模块不可能都熟。**主动收窄**比硬撑好：

> "记忆检索那块我读得不深，主要看了 schema 设计和排序信号的分层，
> 具体的向量召回参数我没细看。
> 我读得比较透的是编排和会话生命周期这两块，
> 特别是抗上下文压缩的设计。"

这个答法反而加分 —— 它显示你知道自己知道什么。

### 雷区三：别只讲"设计得很好"

面试官想听的是**取舍**，不是赞美。任何一个设计你都要能说出它的代价：

| 设计 | 好处 | 代价（必须一起说） |
|------|------|-----------------|
| CLI 子进程 | 订阅额度 + 完整工具链 | 五套 parser、上游改格式要跟、启动开销 0.5~2 秒 |
| 机械路由 | 可测试、误报不背锅 | 不保证；模型判断错了没有代码兜底 |
| L0 编译 fail-closed | 治理规则不会静默丢 | 有人改了文档标题就启动崩溃 |
| 存储全接口化 | Redis 可选 | 每个 store 两套实现要维护 |
| 三道抗压缩防线 | 控制流不丢 | 每轮多花 token；bootstrap 有 2000 token 预算压力 |

**"任何设计都有代价，说不出代价就是没想清楚"** —— 这是资深候选人的标志。
