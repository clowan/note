### 1.3 三条边界，必须说清楚

**边界一：store 不认识 `dimension` / `collections` / `intent`。**
这三个字段虽然声明在 `SearchOptions` 里，但 `SqliteEvidenceStore.ts` 全文没有一处读它们（grep `dimension` 在该文件命中 0 次，grep `intent` 在整个 `domains/memory/*.ts` 命中 0 次）。`dimension`/`collections` 由 `KnowledgeResolver` 消费，`intent` 由 route 消费。【源码】

**边界二：F163 salience rerank 不在 store 里。**
`applySalienceRerank()` 定义在 `f163-types.ts`，调用点在 `routes/evidence.ts`，在 store 返回之后才跑。所以「14 层」是 store 级的，用户实际看到的顺序还多一层。【源码】

**边界三：写路径和读路径共用一把锁。**
`SqliteEvidenceStore` 内有 `private readonly writeQueue = new EvidenceWriteQueue()`，`upsert` / `deleteByAnchor` / `addEdge` / `createSummary` / `refreshEntityMentions` 全部走 `this.writeQueue.enqueue(...)`；`search` 不走。`EvidenceWriteQueue` 的实现就是一条 promise 链：

```ts
export class EvidenceWriteQueue {
  private tail: Promise<void> = Promise.resolve();
  enqueue<T>(fn: () => T | Promise<T>): Promise<T> {
    return new Promise<T>((resolve, reject) => {
      this.tail = this.tail.then(async () => {
        try { resolve(await fn()); } catch (e) { reject(e); }
      });
    });
  }
}
```
【源码】`evidence-write-queue.ts`，注释写明 "F163: Single-writer scheduler for ALL evidence.sqlite mutations. Design Gate contract 3"。

> **面试官追问：为什么读不加锁？**
> 「SQLite 开了 WAL（`journal_mode = WAL`），读写不互斥，读永远看到一个一致快照。加锁只为了防多个写并发触发 `SQLITE_BUSY`——另外 `busy_timeout` 也设了 5000ms 做二次兜底。这个单写者队列的语义是 FIFO、不交错，注释里明确叫 Design Gate contract 3。」

## 2. 核心数据结构

### 2.1 `SearchOptions`（`interfaces.ts`）——逐字段解释

```ts
export interface SearchOptions {
  kind?: EvidenceKind;
  status?: EvidenceStatus;
  keywords?: string[];
  limit?: number;
  scope?: 'docs' | 'memory' | 'threads' | 'sessions' | 'all';
  mode?: 'lexical' | 'semantic' | 'hybrid';
  depth?: 'summary' | 'raw';
  dateFrom?: string;
  dateTo?: string;
  contextWindow?: number;
  threadId?: string;
  dimension?: SearchDimension;
  collections?: string[];
  provenanceTier?: ProvenanceTier;
  includeBackstop?: boolean;
  worldId?: string;
  sceneId?: string;
  explain?: boolean;
  intent?: 'topk' | 'coverage';
}
```

| 字段 | 默认 | 这个字段为什么存在 / 它到底改变了什么 |
|---|---|---|
| `limit` | `10`（store 内 `options?.limit ?? 10`）；**route 层是 `5`**（`limit ?? 5`）；MCP schema 限制 `1..20` | 三处默认值不同，是很好的追问点 |
| `scope` | 无（=不过滤） | `threads`→`kind='thread'`；`sessions`→`kind='session'`；`docs`/`memory`→`AND kind != 'session' AND kind != 'thread'`；`all`→不加条件 |
| `mode` | `'lexical'`（`options?.mode ?? 'lexical'`） | 决定走 `lexicalResults` 直接返回 / `semanticNNSearch()` / `hybridRRFSearch()`。**只有 `hybrid` 会把 BM25 候选池撑大** |
| `depth` | `'summary'` | `'raw'` 会在 authority boost **之前**跳进 `rawPassageSearch()`，走完全不同的 passage 分支 |
| `kind` | 无 | 优先级高于 `scope`：`options?.kind ?? (scope 推导)` |
| `keywords` | 无 | 拼成 `keywords LIKE ?` + 参数 `%"kw"%`（注意带双引号，因为 keywords 列存的是 JSON 数组字符串） |
| `dateFrom/dateTo` | 无 | 打在 `updated_at`（doc）或 `created_at`（passage）上；`dateTo` 长度 ==10 时自动补 `T23:59:59` |
| `contextWindow` | 无 | 只在 `depth=raw` 生效，取命中 passage 前后 N 条（`position BETWEEN ?-N AND ?+N`） |
| `threadId` | 无 | 转成 `threadAnchor = 'thread-' + threadId`，然后 `AND anchor = ?` |
| `provenanceTier` | 无 | `AND provenance_tier = ?` |
| `includeBackstop` | `false` | 为 false 且 `F163_COMPRESSION !== 'off'` 时 → `suppressBackstop=true` → 所有分支加 `AND activation != 'backstop'` |
| `worldId`/`sceneId` | 无 | F093 世界观隔离，`AND world_id = ?` / `AND scene_id = ?` |
| `explain` | `false` | 让 `annotateMatchReasons()` 额外写 `item.rankingFactors = { bm25Score: index+1 }` |
| `intent` | `'topk'` | **store 不读**；route 里 `intent === 'coverage'` 直接 `return coverageResult`，连 KnowledgeResolver 都不进 |
| `dimension` | route 默认 `'project'`（MCP 侧 `const { dimension = 'project' }`），resolver 内 `options?.dimension ?? 'all'` | `'all'` 会回一条 deprecationWarning |

【源码】全部来自 `interfaces.ts` 的 `SearchOptions`、`SqliteEvidenceStore.searchWithMeta()` 的参数解析段、`routes/evidence.ts` 的 `searchSchema`、`evidence-tools.ts` 的 `searchEvidenceInputSchema`。

> **面试官追问：`limit` 默认值为什么三处不一样？**
> 「store 是库，默认 10 是库的合理默认；REST route 面向 agent，默认 5 是为了省 token；MCP schema 上限 20 是为了防猫一次要 100 条把上下文打爆。这三个值分别在 `searchWithMeta()` 的 `options?.limit ?? 10`、`evidence.ts` 的 `limit ?? 5`、`searchEvidenceInputSchema` 的 `.max(20)`。」

### 2.3 `SearchExecutionMeta`——可观测性的唯一出口

```ts
export type SearchDegradeReason =
  | 'passage_embedding_unavailable'
  | 'passage_vector_search_error'
  | 'evidence_store_error'
  | 'raw_lexical_only';

export interface SearchExecutionMeta {
  degraded: boolean;
  degradeReason?: SearchDegradeReason;
  effectiveMode?: 'lexical' | 'semantic' | 'hybrid';
}
export interface EvidenceSearchExecution { items: EvidenceItem[]; meta: SearchExecutionMeta; }
```

**关键事实**：doc 级的降级（embedding 不可用 → 退 lexical）**不会**写 meta——那三个 `return` 全都写死 `meta: { degraded: false }`。只有 `depth=raw` 的 passage 分支才会填 `degradeReason`。这是一个真实的可观测性缺口，面试时可以主动指出。【源码】`searchWithMeta()` 的 `if (searchMode === 'semantic') { const embeddingAvailable = ...; if (!embeddingAvailable) { return { ..., meta: { degraded: false } }; } }`

`degradeReason` 的优先级在 `KnowledgeResolver.degradeReasonPriority()` 里定死：`evidence_store_error`=4 > `passage_vector_search_error`=3 > `passage_embedding_unavailable`=2 > `raw_lexical_only`=1。多个 collection 同时降级时取优先级最高的那个。【源码】

两个 vec0 表**不在迁移里**，是单独的函数，且返回 boolean 而不抛异常：

```ts
export function ensureVectorTable(db, dim): boolean {
  try {
    db.exec(`CREATE VIRTUAL TABLE IF NOT EXISTS evidence_vectors USING vec0(
      anchor TEXT PRIMARY KEY, embedding float[${dim}])`);
    return true;
  } catch { return false; }   // sqlite-vec not loaded — fail-open
}
// ensurePassageVectorTable 同理，表名 passage_vectors，主键列 passage_key
```
【源码】注释原文就是 `// sqlite-vec not loaded — fail-open`。

**迁移的三个可复述特征**【源码】：
1. `CURRENT_SCHEMA_VERSION = 26` 这个常量**导出了但 `applyMigrations()` 里没用它**——每一步都是硬编码的 `if (currentVersion < N)`。
2. 每个 `ALTER TABLE ... ADD COLUMN` 都单独包 `try { } catch { }`，注释是 "Column may already exist from a partial migration"。因为 SQLite 没有 `ADD COLUMN IF NOT EXISTS`。
3. `applyMigrations()` 第一件事是 `CREATE TABLE IF NOT EXISTS schema_version`，注释写着 "P1 fix (codex review R2): schema_version may not exist on empty DB"。

> **面试官追问：为什么 vec0 表不走迁移？**
> 「因为它依赖运行时 `import('sqlite-vec')` 成功加载扩展。迁移是 `initialize()` 必跑的路径，如果把 vec0 放进去，扩展没装就整个 DB 起不来。把它挪到 `factory.ts` 里 embed 分支下、用 try/catch + 返回 boolean，就实现了『没装扩展 = 没有 vectorStore = 自动只走 lexical』的 fail-open。」

### 3.3 [D] exact-anchor 旁路：为什么需要它

注释原文：

【源码】

### 3.4 [E] FTS5 层：SQL、BM25 权重、progressive relaxation

#### SQL 本体

```sql
SELECT d.*, bm25(evidence_fts, 5.0, 1.0) AS rank
FROM evidence_fts f
JOIN evidence_docs d ON d.rowid = f.rowid
WHERE evidence_fts MATCH ?
  -- ... 各种可选过滤 ...
ORDER BY (d.superseded_by IS NOT NULL),
         (d.source_path LIKE 'archive/%'),
         (CASE WHEN d.provenance_tier = 'authoritative' THEN 0
               WHEN d.provenance_tier IS NOT NULL THEN 1
               ELSE 2 END),
         rank
LIMIT ?
```
【源码】

**BM25 权重 `5.0, 1.0` 对应的是 `evidence_fts` 的两列：`title` 和 `summary`。** 不是「标题 vs 正文」——`evidence_fts` 里根本没有正文列。这是架构文档写得不准确的地方（见本篇 §7 末尾的「文档与代码不一致清单」）。

`bm25()` 在 SQLite FTS5 里返回的是**负数，越小越相关**，所以 `ORDER BY ... rank` 升序是对的。代码里 `PassageResult.rank` 的注释也确认了这点：`/** BM25 relevance score from passage_fts (lower = more relevant) */`。【源码】

ORDER BY 的四列语义（SQLite 里 boolean 表达式产出 0/1，0 排前面）：
1. `superseded_by IS NOT NULL` → 被取代的排最后
2. `source_path LIKE 'archive/%'` → **注意是 `archive/`，不是 `internal-archive/`**（文档写错了）
3. provenance_tier 三档：authoritative(0) < 其它非 null(1) < null(2)
4. BM25 rank

#### `buildProgressiveFtsQueries()` 完整算法（`fts-query-builder.ts`）

```ts
export function buildProgressiveFtsQueries(query: string): string[] {
  const tokens = query.trim().split(/\s+/).filter(Boolean);
  if (tokens.length === 0) return [];
  const escaped = tokens.map(escapeToken);          // `"tok"`，内部 " → ""
  if (tokens.length <= 3) return [escaped.join(' ')];   // ← 关键分支：≤3 词不放松

  const queries: string[] = [];
  queries.push(escaped.join(' '));                  // Level 1: AND-all（空格=隐式AND）

  const strong: string[] = []; const weak: string[] = [];
  for (let i = 0; i < tokens.length; i++) {
    if (isStrongToken(tokens[i])) strong.push(escaped[i]); else weak.push(escaped[i]);
  }
  if (strong.length > 0 && weak.length > 0) {
    const strongPart = strong.join(' AND ');
    const weakPart = weak.length === 1 ? weak[0] : `(${weak.join(' OR ')})`;
    queries.push(`${strongPart} AND ${weakPart}`);  // Level 2
  }
  queries.push(escaped.join(' OR '));               // Level 3: OR-all
  return queries;
}
```

`isStrongToken()` 的四条规则（**按顺序短路**）：
1. `/^(?:F|ADR|LL|KD|TD|AC|HW)-?\d+[a-zA-Z]?$/i` → 实体标识（F042 / ADR-005 / AC-B1 / HW-6）
2. `/^Phase[A-Z]$/i` → PhaseA / PhaseB
3. `/[一-鿿㐀-䶿]/` → 含 CJK 字符（注意这里用的是字符区间字面量，不是 `\p{Script=Han}`，和 `hasCJKCharacters()` 是**两套不同的正则**）
4. `token.length >= 4`
否则弱。【源码】

**三个容易被追问的细节**【源码】：
- **≤3 个 token 只返回 1 条查询，完全不放松。** 所以「短查询 0 结果」不会被 relaxation 救回来。
- Level 2 在 `strong.length === 0` 或 `weak.length === 0` 时**整级被跳过**，数组只有 2 条。
- `strongPart AND weakPart` 里的 `AND` 是显式的，注释写明原因：*"FTS5 requires explicit AND before parenthesized OR groups — implicit AND (space) before `(...OR...)` throws syntax error."*

#### 调用侧的降级循环

```ts
for (const ftsQuery of ftsQueries) {
  try {
    // ... 拼 SQL, 执行 ...
    const rows = this.db?.prepare(sql).all(...params) as RowShape[];
    for (const row of rows) { if (!seenAnchors.has(row.anchor)) { results.push(rowToItem(row)); seenAnchors.add(row.anchor); } }
    if (rows.length > 0) break;   // HW-6: 命中就不再放松
  } catch {}
}
```
【源码】`catch {}` 是空的——FTS5 语法错误（比如 query 里有裸的 `*` 或 `^`）会被静默吞掉，然后自动尝试下一级。这既是防御也是坑（见 §5）。

> **面试官追问：progressive relaxation 具体几级、怎么降？**
> 「三级，但要分情况说：token ≤ 3 时只有一级（AND-all），根本不放松；token ≥ 4 时才是三级——Level 1 AND-all、Level 2『强 token 全 AND + 弱 token 括号 OR』、Level 3 全 OR。降级靠调用侧的 for 循环，每级执行完看 `rows.length > 0` 就 break。强 token 的判定是四条规则：实体正则 `^(F|ADR|LL|KD|TD|AC|HW)-?\d+[a-zA-Z]?$`、`^Phase[A-Z]$`、含 CJK、长度 ≥4。设计动机在注释里：F200 HW-6 发现长查询在 AND-all 语义下 75% 空结果。」

### 3.5 [F] Lexical backfill：匹配规则与排序规则

**触发条件**：`if (lexicalBackfillWords.length > 0)` —— **不是「FTS 没结果时才跑」，是无条件跑**（只要 query 分得出词）。这是架构文档描述错误的第二处。【源码】

分词：
```ts
export function splitLexicalBackfillWords(query: string): string[] {
  return [...new Set(query.trim().toLowerCase().split(/\s+/).filter(Boolean))];
}
```
—— 小写 + 空白切分 + 去重。中文不分词，整段中文会当成一个「词」。【源码】

匹配 SQL（每个 word 生成一个三段 OR，词与词之间也是 OR）：
```sql
SELECT * FROM evidence_docs
WHERE ((LOWER(title) LIKE ? OR LOWER(COALESCE(summary,'')) LIKE ? OR LOWER(COALESCE(keywords,'')) LIKE ?)
    OR (…第二个词…))
  AND …同样一套过滤（kind/status/keywords/anchor/world/scene/date/provenance/backstop）…
```
参数是 `%word%`，每个词灌 3 次。【源码】

排序：`rankLexicalBackfillRows(rows, words)` 返回 `{ rows, signals }`。信号计算（`computeLexicalBackfillSignal`）：

```ts
for (const word of words) {
  const keywordHit = keywords.some(k => k.includes(word));   // keywords 是 JSON.parse 后小写化的数组
  const titleHit   = title.includes(word);
  const summaryHit = summary.includes(word);
  if (keywordHit) keywordHits += 1;
  if (titleHit)   titleHits   += 1;
  if (keywordHit || titleHit || summaryHit) textHits += 1;
}
```

排序比较器是**四级 lexicographic**：
1. `keywordHits` 降序
2. `titleHits` 降序
3. `textHits` 降序
4. `compareLexicalBackfillRowQuality()`：`superseded_by` 有的排后 → `source_path.startsWith('archive/')` 的排后 → `provenanceRank`（authoritative=0 / 非null=1 / null=2）升序 → `b.updated_at.localeCompare(a.updated_at)`（新的在前）

【源码】`lexical-backfill.ts`

然后回到 store，**backfill 会对整个 `results` 数组重排一次**（不只是新加的那些）：

```ts
if (signals.size > 0) {
  results.sort((a, b) => compareEvidenceItemsByLexicalBackfill(a, b, signals, exactRow?.anchor));
}
```
`compareEvidenceItemsByLexicalBackfill` 里第一件事是 exactAnchor 免疫：精确命中恒返回 -1 排最前；其余按三个 hits 比。**没有信号的 item（比如纯 FTS 命中但不含子串的）signals 取不到，退化成 `{0,0,0}`，会被挤到后面。**【源码】

> **面试官追问：backfill 会不会把 BM25 的排序毁掉？**
> 「会，而且是有意的。只要 backfill 匹配到任何行（`signals.size > 0`），整个 results 数组就按 keywordHits/titleHits/textHits 重排一遍，BM25 的 rank 顺序被覆盖。唯一的保护是 exact-anchor 恒排第一。我的理解是：这是把『关键词标签命中』当成比 BM25 更强的信号——因为 keywords 是 scanner 从 frontmatter topics 和 section heading 抽出来的人工语义标签。【推断】」

`rankRawResults()` 的三级排序：**有 passages 的排前 → 按 `passageOrder`（该 anchor 第一条 passage 在合并列表里的下标）→ 按原始顺序**，最后 `slice(0, limit)`。【源码】

`toEvidencePassage()` 顺手做了 ID 反解：`threadId = docAnchor.startsWith('thread-') ? slice(7) : undefined`、`messageId = passageId.startsWith('msg-') ? slice(4) : undefined`。这两个字段直接喂给第 14 层的 drillDown。【源码】

### 3.8 [I] Authority boost

```ts
const AUTHORITY_WEIGHTS: Record<F163Authority, number> = {
  constitutional: 1.3, validated: 1.2, candidate: 1.1, observed: 1.0,
};

function applyAuthorityBoost(results: EvidenceItem[], query = ''): void {
  const flags = freezeFlags();
  if (flags.authorityBoost === 'off' || results.length < 2) return;
  if (findExactLexicalProtectedAnchors(results, query).size > 0) return;   // ← 整体跳过

  const K = 60;
  const scored = results.map((item, i) => ({
    item, score: (1 / (i + K)) * AUTHORITY_WEIGHTS[(item.authority as F163Authority) ?? 'observed'],
  }));
  scored.sort((a, b) => b.score - a.score);
  if (flags.authorityBoost === 'on') { for (let i=0;i<results.length;i++) results[i] = scored[i].item; }
  // shadow: order unchanged, but boost was computed
}
```
【源码】

四个可复述要点：
1. **权重区间 1.0–1.3**，代码注释写着 `(1.0–1.3 range, spec constraint)`。
2. 位置分是 `1/(i + 60)`，**注意是 `i + K` 不是 `K + i` 的另一种写法——数值相同**，注释解释选它的理由：*"RRF-style positional score: 1/(rank+k) keeps adjacent positions close so the 1.0–1.3 authority weight can meaningfully reorder near-tied items."*
3. **shadow 模式什么都不改**，只是白算一遍（注释：`(logging in Task 7)`——日志其实没实现）。
4. 调用侧包了 try/catch，注释 `// Kill-switch: boost failure → continue with original ranking`。

`findExactLexicalProtectedAnchors()` 是 authority boost 和 consumption rerank **共用**的护栏：

```ts
function findExactLexicalProtectedAnchors(results, query): Set<string> {
  const words = splitLexicalBackfillWords(query.trim());
  if (words.length === 0) return new Set();
  if (words.length < 2 && !hasCJKCharacters(trimmed)) return new Set();   // 单个英文词不保护
  for (const item of results) if (isExactLexicalMatch(item, words)) protectedAnchors.add(item.anchor);
}
function isExactLexicalMatch(item, words): boolean {
  const haystack = `${title} ${summary} ${keywords.join(' ')}`.toLowerCase();
  if (!words.every(w => haystack.includes(w))) return false;         // 全部词都要在
  return words.some(w => title.includes(w) || keywords.includes(w)); // 且至少一个在 title/keywords
}
```
【源码】—— 「单个英文词不触发保护，但单个中文词会（因为 `hasCJKCharacters`）」是个很细但真实的分支。

**两处用法不同**：authority boost 是「有任何保护锚 → 整个 boost 不做」；consumption rerank 是「保护锚拎出来置顶，剩下的才参与重排」。【源码】

### 3.10 出口层：`enrichWithDrillDown()`

执行顺序是固定的四步：

```ts
private enrichWithDrillDown(results, targetLimit?, options?, query = ''): EvidenceItem[] {
  try { if (this.db) applyConsumptionRerank(results, this.db, targetLimit, query); }
  catch { /* F200 kill-switch */ }
  if (targetLimit && results.length > targetLimit) results.length = targetLimit;   // ← 截断在 rerank 之后
  annotateMatchReasons(results, query, options?.explain);
  for (const item of results) { /* drillDown 四分支 */ }
  return results;
}
```
【源码】

**drillDown 四分支（按 if-else 顺序，先匹配先赢）**：

| 条件 | tool | params |
|---|---|---|
| `item.passages` 里存在同时有 `threadId` 和 `messageId` 的 passage | `cat_cafe_get_thread_context` | `{ threadId, messageId, before:'3', after:'3' }` |

【源码】注意 params 的值全是**字符串**（`'3'` 不是 `3`），因为 `EvidenceDrillDown.params` 类型是 `Record<string, string>`。

### 4.1 RRF：三处实现，公式一样、权重不一样

#### （a）doc 级 hybrid — `hybridRRFSearch()`

```ts
const scores = new Map<string, number>();
const nnWeight = hasCJKCharacters(query) ? CJK_NN_WEIGHT : 1.0;   // CJK_NN_WEIGHT = 1.5

for (let i = 0; i < lexicalResults.length; i++)
  scores.set(anchor, (scores.get(anchor) ?? 0) + 1 / (RRF_K + i));          // BM25 腿，权重恒 1.0
for (let i = 0; i < nnResults.length; i++)
  scores.set(anchor, (scores.get(anchor) ?? 0) + nnWeight / (RRF_K + i));   // NN 腿，CJK 时 ×1.5

// 缺失的 NN anchor 用一条 IN(...) hydrate（带全套过滤）
return allAnchors.filter(a => lexicalMap.has(a))
                 .sort((a,b) => (scores.get(b) ?? 0) - (scores.get(a) ?? 0))
                 .map(a => lexicalMap.get(a)!).slice(0, limit);
```
【源码】

**可复述的公式**：

```
RRF(d) = Σ_legs  w_leg / (60 + rank_leg(d))

rank 从 0 开始（数组下标）
w_lexical = 1.0（永远）
w_nn      = 1.5 若 query 含 CJK，否则 1.0
```

**手算一遍**（英文 query，某文档 BM25 第 2、NN 第 5，rank 都是 0-based）：
```
1/(60+2) + 1/(60+5) = 0.016129 + 0.015385 = 0.031514
```
另一篇只在 BM25 排第 0：`1/(60+0) = 0.016667`。前者胜。

**同一篇文档换成中文 query**：
```
1/(60+2) + 1.5/(60+5) = 0.016129 + 0.023077 = 0.039206
```

> **面试官追问：k=60 是怎么来的、为什么不用加权求和？**
> 「k=60 是 Cormack 2009 那篇 RRF 论文的经验常数，代码注释写的是 `k=60 (standard constant)`。不用加权求和的原因是量纲：BM25 分是负数、量级跟文档长度和语料相关，vec0 的 distance 是 L2 平方距离，两者没有可比的归一化方式。RRF 只用名次，天然免疫量纲；代价是丢掉了『第一名比第二名好多少』的信息。k 越大越平滑——k=60 时第 0 名 1/60≈0.0167、第 1 名 1/61≈0.0164，差 2%，所以单路的名次差很难压过双路都命中。」

### 4.2 Consumption Prior：完整贝叶斯算法（逐行可复述）

`consumption-prior.ts` 全文核心：

```ts
const ALPHA_0 = 2;
const BETA_0 = 8;
const GRACE_PERIOD_MS = 14 * 86_400_000;          // 14 天

const KIND_HALF_LIVES: Record<string, number | null> = {
  adr: null, lesson: null, canon: null,
  feature: 90, decision: 90,
  plan: 45, research: 45, phase: 45,
  discussion: 21, reflection: 21,
  thread: 14, session: 14,
};

export function computeConsumptionPrior(input, globalMeanCtr): ConsumptionPriorResult {
  // ── 分支 0：冷启动宽限期（最先判，早于 constitutional！）
  if (input.firstIndexedAt > 0 && Date.now() - input.firstIndexedAt < GRACE_PERIOD_MS)
    return { shrunkCtr:0, meanCtrKind:0, recencyFactor:0, rawLift:0, prior:0, branch:'cold-start' };

  // ── 贝叶斯收缩 CTR
  const shrunkCtr = (input.consumedCount30d + ALPHA_0) / (input.exposureCount30d + ALPHA_0 + BETA_0);
  const meanCtrKind = globalMeanCtr[input.docKind] ?? 0.2;
  const halfLife = input.docKind in KIND_HALF_LIVES ? KIND_HALF_LIVES[input.docKind] : 45;
  const recencyFactor =
    input.daysSinceLastConsumed == null ? 0.5
    : halfLife == null ? 1.0
    : halfLife / (halfLife + input.daysSinceLastConsumed);
  const rawLift = (shrunkCtr - meanCtrKind) * recencyFactor;

  const isConstitutional = input.authority === 'constitutional' || ['decision','lesson'].includes(input.docKind);

  if (isConstitutional)            return { ..., prior: Math.max(0, rawLift), branch:'constitutional' };
  if (input.exposureCount30d < 5)  return { ..., prior: 0,                    branch:'cold-start' };
  if (input.exposureCount30d < 20) return { ..., prior: Math.max(0, rawLift), branch:'low-sample' };
  return                                  { ..., prior: rawLift,              branch:'full' };
}
```
【源码】

#### 决策表（面试时可以直接背这张）

| # | 判定顺序 | 条件 | `prior` | `branch` |
|---|---|---|---|---|
| 0 | 最先 | `firstIndexedAt > 0 && now - firstIndexedAt < 14d` | `0`（其余字段也全 0） | `cold-start` |
| 1 | 次之 | `authority === 'constitutional'` **或** `docKind ∈ {decision, lesson}` | `max(0, rawLift)` | `constitutional` |
| 2 | | `exposureCount30d < 5` | `0` | `cold-start` |
| 3 | | `5 ≤ exposureCount30d < 20` | `max(0, rawLift)` | `low-sample` |
| 4 | 兜底 | `exposureCount30d ≥ 20` | `rawLift`（可负） | `full` |

**三个非常容易答错、但代码写死的细节**【源码】：
1. **宽限期判定在 constitutional 之前**。一篇 3 天前入库的 ADR，`branch` 是 `cold-start` 不是 `constitutional`——因此它在 `applyConsumptionRerank` 里**不会被 pin**。
2. `firstIndexedAt > 0` 是必要条件。V21 迁移给这列的默认值是 `0`（`NOT NULL DEFAULT 0`），所以**所有 V21 之前入库、之后没被 upsert 过的老文档 `firstIndexedAt = 0`，永远不走宽限期分支**。
3. `docKind ∈ {decision, lesson}` 就算 constitutional，**跟 authority 无关**。所以一篇 `authority='observed'` 的 lesson 也享受「只升不降」。

#### `recencyFactor` 三分支
```
daysSinceLastConsumed == null → 0.5     （从没被消费过：中性）
halfLife == null              → 1.0     （lesson/adr/canon：不衰减）
其它                          → T/(T+d)
```
注意这里的 `d` 是 **`anchor_recall_metrics.dormancy_days`（距上次被消费的天数）**，不是文档年龄。【源码】

#### 数据从哪来（`RecallMetricsComputer`）
```ts

  cutoff = Date.now() - 30 * 86_400_000
  遍历 recall_events(timestamp >= cutoff)：candidates_json 每出现一次 exposed++，
```

### 4.3 `applyConsumptionRerank()`：合成公式 + pin + MMR

```ts
export function applyConsumptionRerank(results, db, targetLimit?, query = ''): void {
  const f200Flags = freezeF200Flags();
  if (f200Flags.consumptionRerank === 'off' || results.length < 2) return;

  // 1) 精确词法保护分区
  const exactProtectedAnchors = findExactLexicalProtectedAnchors(results, query);
  const protectedResults = ...filter(在集合里);
  const rerankPool       = ...filter(不在集合里);
  if (rerankPool.length < 2) { /* 只把 protected 提前，然后 storeShadowRanking 后 return */ }

  // 2) 快照原始顺序做 shadow baseline（HW-7 + Cloud-P2：必须用原 results，不能用分区后的）
  const preRerankOrder = results.map((item, i) => ({ anchor: item.anchor, shadowRank: i }));

  // 3) 拉指标
  const anchorMetrics  = loadAnchorMetrics(db, rerankPool.map(r => r.anchor));   // 一条 IN(...)
  const globalMeanCtr  = loadGlobalCtrBaseline(db);                              // 全表

  const K = 60, BETA = 0.15, GAMMA = 0.1;

  const scored = rerankPool.map((item, i) => {
    const metrics = anchorMetrics.get(item.anchor);
    const prior = computeConsumptionPrior({
      consumedCount30d:     metrics?.consumed_count_30d ?? 0,
      exposureCount30d:     metrics?.exposure_count_30d ?? 0,
      daysSinceLastConsumed: metrics?.dormancy_days ?? null,
      docKind:   item.kind ?? 'unknown',
      authority: (item.authority as F163Authority) ?? 'observed',
      firstIndexedAt: item.firstIndexedAt ?? 0,
    }, globalMeanCtr);

    const ageDays = item.updatedAt ? (Date.now() - new Date(item.updatedAt).getTime()) / 86_400_000 : 365;
    const decay = computeRecencyDecay(ageDays, item.kind ?? 'unknown');

    const positionalScore = 1 / (i + K);
    const newScore = positionalScore + BETA * prior.prior + GAMMA * (decay.factor - 0.5);
    return { item, newScore, originalIndex: i, isConstitutional: prior.branch === 'constitutional' };
  });

  // 4) pin：constitutional 保持原下标不动
  const pinned = new Map<number, EvidenceItem>();
  let movable = [];
  for (const s of scored) { if (s.isConstitutional) pinned.set(s.originalIndex, s.item); else movable.push(s); }
  movable.sort((a, b) => b.newScore - a.newScore);

  // 5) MMR：只在候选足够多时
  if (targetLimit && movable.length >= 3 * targetLimit) {
    const mmrItems = movable.map(m => ({ item: m.item, score: m.newScore }));
    const mmrResults = applyMMR(mmrItems, targetLimit, 0.7);
    movable = mmrResults.map((item, i) => ({ item, newScore: targetLimit - i }));
  }

  // 6) 回填：pinned 占回原下标，其余按 movable 顺序填空
  const reranked = [];
  let mi = 0;
  for (let i = 0; i < rerankPool.length; i++) {
    if (pinned.has(i)) reranked.push(pinned.get(i)!);
    else if (mi < movable.length) reranked.push(movable[mi++].item);
  }
  const final = protectedResults.length > 0 ? [...protectedResults, ...reranked] : reranked;
  if (f200Flags.consumptionRerank === 'on') { for (...) results[i] = final[i]; results.length = final.length; }

  // 7) shadow 语义按模式反转
  const shadowOrder = f200Flags.consumptionRerank === 'shadow'
    ? final.map((item, i) => ({ anchor: item.anchor, shadowRank: i }))   // shadow：live=BM25, shadow=重排后
    : preRerankOrder;                                                    // on：    live=重排后, shadow=BM25
  storeShadowRanking(keyAnchors, shadowOrder);
}
```
【源码】

**最终合成公式（背这个）**：
```
newScore(d) = 1/(rank_d + 60)  +  0.15 × prior(d)  +  0.10 × (decayFactor(d) − 0.5)

rank_d       : 该文档在 rerankPool 中的 0-based 下标
prior(d)     : computeConsumptionPrior 的四分支输出
decayFactor  : T / (T + ageDays)，ageDays 由 updatedAt 算，无 updatedAt 时取 365
```

**量级直觉**（面试可以直接说）：
- `positionalScore` 第 0 名 = 1/60 ≈ **0.01667**，第 1 名 ≈ 0.01639，相邻差约 **0.00028**
- `GAMMA × (decay−0.5)` 的范围是 `0.1 × (−0.5 … +0.5)` = **±0.05**
- `BETA × prior` 中 prior ≈ `(shrunkCtr − meanCtr) × recencyFactor`，绝对值一般 < 0.5，所以贡献 < **0.075**

→ **行为信号（±0.05~0.075）比位置信号的相邻差（0.00028）大两个数量级**。这意味着 BETA/GAMMA 一旦开启，位置分基本只起「稳定 tiebreak」作用，实际排序由 prior 和 decay 主导。这跟架构文档说的「温和调整」有出入，值得在面试里作为「我读代码发现的量级问题」讲出来。【推断】（公式和常量是【源码】，量级结论是我算的）

### 4.5 MMR

```ts
export function applyMMR(items: ScoredItem[], limit: number, lambda: number = 0.7): EvidenceItem[] {
  if (items.length < 3 * limit) return items.slice(0, limit).map(i => i.item);   // 二次守卫
  const selected: ScoredItem[] = [];
  const remaining = [...items];
  while (selected.length < limit && remaining.length > 0) {
    let bestIdx = 0, bestScore = -Infinity;
    for (let i = 0; i < remaining.length; i++) {
      const relevance = remaining[i].score;
      const maxSim = selected.length === 0 ? 0
        : Math.max(...selected.map(s => keywordSimilarity(remaining[i].item, s.item)));
      const mmrScore = lambda * relevance - (1 - lambda) * maxSim;
      if (mmrScore > bestScore) { bestScore = mmrScore; bestIdx = i; }
    }
    selected.push(remaining.splice(bestIdx, 1)[0]);
  }
  return selected.map(s => s.item);
}

export function keywordSimilarity(a, b): number {   // Jaccard
  const setA = new Set(a.keywords ?? []), setB = new Set(b.keywords ?? []);
  if (setA.size === 0 && setB.size === 0) return 0;
  const intersection = [...setA].filter(k => setB.has(k)).length;
  const union = setA.size + setB.size - intersection;
  return union === 0 ? 0 : intersection / union;
}
```
【源码】

**可复述的四点**：
1. **λ = 0.7 硬编码在调用侧**：`applyMMR(mmrItems, targetLimit, 0.7)`。函数默认值也是 0.7。
2. 公式：`MMR(d) = 0.7 × relevance(d) − 0.3 × max_{s∈selected} sim(d, s)`
3. `relevance` 传的是 `newScore`（consumption rerank 的合成分，量级 ~0.017），`maxSim` 是 Jaccard（量级 0~1）。**两者量纲差 60 倍**——`0.3 × sim` 会彻底压过 `0.7 × relevance`。实际效果接近「纯多样性优先」。【推断】
4. 相似度只看 `keywords` 数组的精确字符串交集。**没有 keywords 的文档之间 sim = 0（永不互相抑制）**；一个有 keywords、一个没有时，`union = size(A) + 0 - 0`，sim 也 = 0。
5. **触发条件写了两遍**：调用侧 `if (targetLimit && movable.length >= 3 * targetLimit)`，函数内 `if (items.length < 3 * limit) return slice`。所以只有 `mode=hybrid` + `movable ≥ 3×limit` 才真跑。
6. 贪心是 **O(limit × |remaining| × |selected|)**，每步全扫剩余候选。

> **面试官追问：MMR 的 λ 和相似度度量是什么？**
> 「λ=0.7，相似度是 keywords 的 Jaccard 指数（`|A∩B| / |A∪B|`），不是向量余弦——虽然 store 里有 embedding，MMR 这一层没用它。触发门槛是候选数 ≥ 3×limit，而且只有 hybrid 模式会传 targetLimit，所以 lexical/semantic/raw 三条路径永远不做 MMR。我读代码时注意到一个量纲问题：relevance 用的是 consumption 合成分，量级只有 0.017，而 Jaccard 是 0~1，`0.3×sim` 会压过 `0.7×relevance`，实际更接近纯多样性选择——这是我根据常量算出来的推断，不是注释里写的。」

### 4.6 图检索：边权重、遍历、孤儿边

#### 边权重（`graph-edge-weight.ts`，全文 32 行）

```ts
const TYPE_BASE: Record<string, number> = {
```

【源码】**一共 8 个 flag，全部默认 `off`，全部从环境变量读，全部 `Object.freeze`。**

| flag | 谁读它 | 三态各做什么 |
|---|---|---|
| `F163_AUTHORITY_BOOST` | `applyAuthorityBoost()` | off=直接 return；shadow=算分排序但**不写回** `results`；on=写回 |
| `F163_RETRIEVAL_RERANK` | `routes/evidence.ts` | off=不算；shadow=算 `applySalienceRerank` 但用户看原序、只写 `f163_logs`；on=用重排序 |
| `F163_ALWAYS_ON_INJECTION` | `routes/evidence.ts` | 非 off 时调 `queryAlwaysOn()` 填 `injectionSources` |
| `F163_COMPRESSION` | `searchWithMeta()` | 非 off 时 `suppressBackstop = true` |
| `F163_CONTRADICTION_DETECTION` | `upsert()` | 非 off 时跑 `ContradictionDetector.check()` |
| `F163_PROMOTION_GATE` / `F163_REVIEW_QUEUE` | 不在检索路径 | — |
| `F200_CONSUMPTION_RERANK` | `applyConsumptionRerank()` + `searchWithMeta()` 算 `f200Pool` | off=return；shadow=算但不写回、**shadow 存重排后顺序**；on=写回、**shadow 存原始顺序** |

**shadow 的三种实现套路（可复述）**【源码】：
1. **算而不写回**（authority boost）：`scored.sort(...)` 照做，但 `if (flags.authorityBoost === 'on')` 才 `results[i] = scored[i].item`。
2. **算 + 落日志 + 不用**（salience rerank）：`salienceResult` 总是算，`reranked` 只在 `=== 'on'` 时取它，日志 `logSalienceRerank` 无论 shadow 还是 on 都写 before/after/scores。
3. **算 + 反转基线**（consumption rerank）：最巧的一个。注释写得很直白：
   > `'on' mode: live = reranked, shadow = original BM25 → compare rerank vs BM25.`
   > `'shadow' mode: live = BM25, shadow = would-be reranked → compare BM25 vs rerank.`
   > `Using the same order for both would make shadow ≡ live → zero signal.`
   
   HW-7 的注释还记录了 bug 本身：*"Previously shadow was stored from `final` (post-rerank), making shadow ≡ live by construction in 'on' mode — shadowConsumedMRR / liveOnShadowSubsetMRR ≈ 1 always."*

**排序后再 hash**，保证键序无关；取 **12 个十六进制字符**。【源码】

## 7. 面试追问应对

### Q1 「RRF 具体怎么算？把公式和 k 值说出来。」

> 「`RRF(d) = Σ_legs w_leg / (60 + rank_leg(d))`，k 硬编码 60，rank 是 0-based 数组下标。代码里有三处实现：doc 级在 `SqliteEvidenceStore.hybridRRFSearch()`，passage 级在 `hybridPassageRRFSearch()`，collection 级在 `KnowledgeResolver.rrfFusionN()`。前两处的 BM25 腿权重恒为 1.0，NN 腿在 `hasCJKCharacters(query)` 为 true 时乘 `CJK_NN_WEIGHT = 1.5`；collection 级完全平权，没有权重项。
> 手算：英文 query 下 BM25 第 2 名 + NN 第 5 名 = `1/62 + 1/65 = 0.0315`；只在 BM25 第 0 名 = `1/60 = 0.0167`，双路命中赢。同一篇换成中文 query = `1/62 + 1.5/65 = 0.0392`。
> 一个实现细节：融合完之后才做 `filter(a => lexicalMap.has(a))`——NN 命中但 hydrate 时被 scope/status 过滤掉的 anchor 已经贡献过分数，但不会出现在结果里。分数是先算后过滤。」

加分点：「不用加权求和是因为量纲——BM25 返回负数、量级跟文档长度相关，vec0 是 L2 距离，没有可比的归一化。RRF 只用名次，代价是丢掉了『第一名比第二名好多少』。k=60 时相邻名次差只有 2%，所以单路名次优势很难压过双路都命中。」

### Q2 「Progressive relaxation 几级？降级的判据是什么？」

> 「名义三级，但 **token ≤ 3 时只有一级**——`buildProgressiveFtsQueries()` 里 `if (tokens.length <= 3) return [escaped.join(' ')];` 直接返回，不做任何放松。
> token ≥ 4 时：Level 1 = 全部 token 用空格连（FTS5 里空格是隐式 AND）；Level 2 = 强 token 全 `AND` + 弱 token 包一层括号 `OR`，两段之间用**显式 `AND`**（注释写明 FTS5 在括号 OR 组前不接受隐式 AND，会抛语法错）；Level 3 = 全部 `OR`。如果强或弱有一边为空，Level 2 整级跳过，数组只有 2 条。
> 降级判据在调用侧：`for (const ftsQuery of ftsQueries) { try { ...执行... ; if (rows.length > 0) break; } catch {} }`——每级执行完看命中行数，>0 就 break；`catch {}` 是空的，语法错误会静默进下一级。
> 强 token 四条规则按顺序短路：实体正则 `^(?:F|ADR|LL|KD|TD|AC|HW)-?\d+[a-zA-Z]?$`、`^Phase[A-Z]$`、含 CJK 字符、长度 ≥ 4。」

加分点：「动机是 F200 HW-6：注释原文写 *'Root cause of 75% empty search results: FTS5 AND-all query semantics'*。另外强 token 的 CJK 判定用的是字符区间 `/[一-鿿㐀-䶿]/`，和 RRF 里 `hasCJKCharacters()` 用的 `\p{Script=Han}` 系列**不是同一套正则**——这是两个 feature 分别加的，没统一。」

### Q3 「consumption prior 的贝叶斯公式完整说一遍，包括分支。」

> 「贝叶斯收缩 CTR：`shrunkCtr = (consumed_30d + α₀) / (exposed_30d + α₀ + β₀)`，`α₀ = 2`、`β₀ = 8`——等价于 Beta(2,8) 先验，即『默认 20% CTR、等效 10 次观测』。
> 提升量：`rawLift = (shrunkCtr − meanCtrKind) × recencyFactor`。`meanCtrKind` 从 `global_ctr_baseline` 表按 doc kind 查，缺失取 `0.2`。`recencyFactor` 三分支：`daysSinceLastConsumed == null → 0.5`（从没被消费，中性）；`halfLife == null → 1.0`（lesson 这类不衰减）；否则 `T/(T + d)`，d 是 `anchor_recall_metrics.dormancy_days`。
> 然后四分支决定 prior，**判定顺序很重要**：
> ① 最先判宽限期 `firstIndexedAt > 0 && now − firstIndexedAt < 14 天` → prior=0、branch='cold-start'，其余字段也全 0；
> ② `authority === 'constitutional'` **或** `docKind ∈ {decision, lesson}` → `max(0, rawLift)`、branch='constitutional'；
> ③ `exposed_30d < 5` → 0、'cold-start'；
> ④ `5 ≤ exposed_30d < 20` → `max(0, rawLift)`、'low-sample'；
> ⑤ 否则 → `rawLift`（可负）、'full'。」

加分点（这是真正拉开差距的地方）：「有两个坑。第一，**宽限期在 constitutional 之前**——一篇 3 天前入库的 ADR，branch 是 cold-start 而不是 constitutional，所以它在 `applyConsumptionRerank` 里**不会被 pin**。第二，`firstIndexedAt > 0` 是必要条件，而 V21 迁移给这列的默认值是 `NOT NULL DEFAULT 0`，所以所有 V21 之前入库、之后没被 upsert 过的老文档永远不走宽限期分支。」

### Q4 「Constitutional immunity 到底在哪一行生效？是几个机制？」

> 「两层，都在 `applyConsumptionRerank()` 这条链上，不是独立的 pass。
> 第一层在 `computeConsumptionPrior()` 里：constitutional 分支返回 `prior: Math.max(0, rawLift)`——**只升不降**，负 lift 被夹到 0。
> 第二层在 `applyConsumptionRerank()` 里：`isConstitutional = prior.branch === 'constitutional'`，然后
> ```ts
> for (const s of scored) { if (s.isConstitutional) pinned.set(s.originalIndex, s.item); else movable.push(s); }
> ```
> pinned 用 `Map<originalIndex, item>` 记原下标，回填时 `for (let i = 0; i < rerankPool.length; i++) { if (pinned.has(i)) reranked.push(pinned.get(i)!); else reranked.push(movable[mi++].item); }`——**pinned 项保持原下标不动，movable 只填空位**。
> 判定条件是 `authority === 'constitutional' || docKind ∈ {decision, lesson}`，所以一篇 `authority='observed'` 的 lesson 也享受 pin。」

加分点：「注意 authority boost（`applyAuthorityBoost`）不是 immunity 的一部分——它是独立的一层，权重表 `constitutional:1.3 / validated:1.2 / candidate:1.1 / observed:1.0`，公式 `1/(i+60) × weight`，而且**只作用于 lexical candidate order**，NN-only 命中的文档不会再单独跑一次 authority sort。」

### Q5 「embedding 挂了会怎样？完整的 fail-open 判定说一遍。」

> 「四层，从外到内。
> **第一层 装配期**（`factory.ts`）：`embedMode === 'off'` 就完全不创建 `EmbeddingService`；创建了也 `try { await embeddingService.load() } catch {}`；`import('sqlite-vec')` 失败或 `ensureVectorTable()` 返回 false → `vectorStore` 是 undefined → `embedDeps` 是 undefined → store 拿不到 embedDeps。
> **第二层 查询期判定**（`isEmbeddingAvailable()`）：
> ```ts
> if (!deps || deps.mode !== 'on') return false;          // shadow 也算不可用！
> try { await deps.embedding.reprobeIfNeeded(); } catch { return false; }
> return deps.embedding.isReady();
> ```
> `reprobeIfNeeded()` 有 30 秒冷却（`REPROBE_COOLDOWN_MS = 30_000`），且 `if (this.ready) return` 提前退出，所以健康时零开销。
> **第三层 调用期**：semantic/hybrid 整段包 `try { ... } catch { return lexicalResults }`。
> **第四层 HTTP**：`/health` 超时 5000ms 硬编码，`/v1/embeddings` 超时用 `embedTimeoutMs`（默认 3000）。
> 结论：embedding 全挂时 hybrid 的行为等于 lexical。**但 `meta` 依然是 `degraded: false`**——doc 级降级完全静默，只有 `depth=raw` 的 passage 分支才会写 `degradeReason: 'passage_embedding_unavailable'` 和 `effectiveMode: 'lexical'`。这是我读代码发现的可观测性缺口。」

### Q6 「`depth=raw` 走的是什么路？和默认路径差在哪？」

> 「`depth=raw` 在 authority boost **之前**就 return 了：
> ```ts
> if (options?.depth === 'raw') {
>   const rawResult = await this.rawPassageSearch(query, results, limit, options, queryEntityMatches, entityMentionDocs.matchesByAnchor);
>   return { items: this.enrichWithDrillDown(rawResult.items, undefined, options, trimmed), meta: rawResult.meta };
> }
> ```
> 差四点：**没有 authority boost**、**没有 mergeEntityResults 配额**、**targetLimit 是 undefined 所以没有 MMR 和截断**、**meta 会真的填 degradeReason**。
> 而且 `rawPassageSearch()` 第一行就有 scope 短路：`if (options.scope && scope !== 'all' && scope !== 'threads') return doc 级结果` —— **`depth=raw` + `scope=docs` 根本不做 passage 检索**，因为 passage 只有 thread 消息。
> passage 的三条路径和 doc 级对称：lexical 走 `searchPassages()`（`bm25(passage_fts)` 无权重参数 + 同样的 progressive relaxation）、semantic 走 `semanticPassageNNSearch()`、hybrid 走 `hybridPassageRRFSearch()`（k=60，CJK 1.5）。」

加分点：「`passage_fts` 的 tokenizer 和 `evidence_fts` **不一样**：`passage_fts` 建表时写了 `tokenize="unicode61 tokenchars '_-'"`，把下划线和连字符当词内字符；`evidence_fts` 用默认配置。所以 `ADR-005` 在 passage 里是一个 token，在 doc 里被切成两个。」

### Q7 「跨帖污染（cross-post contamination）是什么问题，怎么修的？」

> 「问题：passage FTS 和 passage NN 都是**全表搜索、不带 scope 过滤**。如果 thread B 里有人转贴了 thread A 的内容，搜 `scope=threads` 时 thread B 会被 passage 命中拽进结果，导致 teleport 按钮跳到错误的 thread。
> 修法是 `hydratePassageResults()` 里的三重守卫（注释标 BUG-UX-14 R3/R4）：
> ```ts
> const scopeActive = options?.scope && options.scope !== 'all';
> const hasExplicitThreadTarget = !!threadAnchor;
> const hasDocLevelResults = results.length > 0;
> // 对 passage-only 的新 anchor：
> if (scopeActive && !hasExplicitThreadTarget && hasDocLevelResults) {
>   const hasPurelySemanticDiscovery = pList.some(p => p._semanticHit && !p._alsoLexical);
>   if (!hasPurelySemanticDiscovery) continue;
> }
> ```
> 判据很巧：**跨帖转贴会共享字面查询词，所以既被 lexical FTS 命中也被 NN 命中（`_alsoLexical = true`）；纯语义发现只出现在 NN 结果里**。所以『有 `_semanticHit` 但没有 `_alsoLexical`』= 真正的语义发现，放行；否则挡掉。
> `_alsoLexical` 是在 RRF 融合时打的：`if (existing && !existing._semanticHit) passage._alsoLexical = true;`。
> 后面还有 R3 二次校验：即使放行了，也要 `parentDoc.kind` 匹配 scope，防止 session doc 的 passage 混进 `scope=threads`。」

### Q8 「MMR 什么时候触发？λ 和相似度是什么？」

> 「触发条件写了两遍。调用侧：`if (targetLimit && movable.length >= 3 * targetLimit)`；函数内：`if (items.length < 3 * limit) return items.slice(0, limit)`。而 `targetLimit` **只有 `mode=hybrid` 会传**（传的是 `limit`），lexical / semantic / raw 三条路径都传 undefined。所以 MMR 只在 hybrid + 候选数 ≥ 3×limit 时真跑。
> λ = 0.7（调用侧 `applyMMR(mmrItems, targetLimit, 0.7)`，函数默认值也是 0.7），公式 `MMR(d) = 0.7 × relevance(d) − 0.3 × max_{s∈selected} sim(d, s)`。
> 相似度是 **keywords 数组的 Jaccard 指数**：`|A∩B| / (|A| + |B| − |A∩B|)`，不用 embedding。两边都没 keywords 时返回 0，一边有一边没有时 `union = |A|`、`intersection = 0`，也返回 0——**所以没打 keywords 的文档永远不会被互相抑制**。
> 贪心是 O(limit × remaining × selected)，每步全扫。选中后用 `remaining.splice(bestIdx, 1)` 移出。」

加分点：「我算过量纲：relevance 传的是 consumption 合成分，第 0 名约 `1/60 + 0.15×prior + 0.1×(decay−0.5)` ≈ 0.017 量级；Jaccard 是 0~1。`0.3 × sim` 最大 0.3，比 `0.7 × 0.017 ≈ 0.012` 大一个多数量级。所以只要两篇文档有任何 keyword 重叠，多样性项就完全主导——实际行为接近『纯多样性优先』而不是文档里说的『70% 相关性 / 30% 多样性』。这是我根据常量推断的，注释里没写。」

### Q9 「schema 迁移到 V26 了，讲讲迁移是怎么做的、怎么保证幂等。」

> 「`applyMigrations(db)` 就是 26 个 `if (currentVersion < N) { ...; INSERT INTO schema_version }`，`currentVersion = SELECT MAX(version) FROM schema_version`。
> 三个可复述特征：
> ① **第一件事是 `CREATE TABLE IF NOT EXISTS schema_version`**，注释写着 `P1 fix (codex review R2): schema_version may not exist on empty DB`——不然空库查 MAX 就崩了。
> ② **每个 `ALTER TABLE ADD COLUMN` 单独包 try/catch**，注释 `Column may already exist from a partial migration`，因为 SQLite 没有 `ADD COLUMN IF NOT EXISTS`，而且一次 `db.exec` 多条 ALTER 里前面成功后面失败会留下半截状态。
> ③ **`CURRENT_SCHEMA_VERSION = 26` 这个常量导出了但没被 `applyMigrations` 使用**——每一步都硬编码。
> 两个 vec0 表故意不在迁移里：`ensureVectorTable(db, dim)` / `ensurePassageVectorTable(db, dim)` 返回 boolean 不抛异常，注释 `sqlite-vec not loaded — fail-open`。这样扩展没装时 DB 照常能起，只是没有 `vectorStore`。
> V25 还是唯一带数据回填的迁移：加完 `recall_events.thread_id` 后跑一条 `UPDATE ... SET thread_id = (SELECT t.thread_id FROM task_trajectories t WHERE t.invocation_id = recall_events.invocation_id LIMIT 1) WHERE thread_id = '' AND EXISTS (...)`。」

### Q10 「shadow 模式是怎么实现的？为什么 consumption rerank 的 shadow 要反转？」

> 「三种套路。
> ① **算而不写回**（authority boost）：`scored.sort()` 照跑，`if (flags.authorityBoost === 'on')` 才 `results[i] = scored[i].item`。
> ② **算 + 落日志 + 不用**（salience rerank，在 route 层）：`salienceResult` 总是算，`reranked` 只在 `=== 'on'` 时取它；`logSalienceRerank` 无论 shadow 还是 on 都写 before/after/scores 到 `f163_logs`。
> ③ **算 + 反转基线**（consumption rerank）：这个最有意思。注释原文：
> > `'on' mode: live = reranked, shadow = original BM25 → compare rerank vs BM25.`
> > `'shadow' mode: live = BM25, shadow = would-be reranked → compare BM25 vs rerank.`
> > `Using the same order for both would make shadow ≡ live → zero signal.`
>
> 代码：
> ```ts
> const shadowOrder = f200Flags.consumptionRerank === 'shadow'
>   ? final.map((item, i) => ({ anchor: item.anchor, shadowRank: i }))
>   : preRerankOrder;
> ```
> 反转的原因：shadow 的目的是『拿反事实顺序和实际顺序比 MRR』。on 模式下用户看到的是重排后，所以反事实是原 BM25；shadow 模式下用户看到的是 BM25，反事实是重排后。如果两个模式都存同一个顺序，on 模式下 shadow ≡ live，MRR 恒等于 1，指标就废了——HW-7 的注释就记录了这个 bug：*'making shadow ≡ live by construction in on mode — shadowConsumedMRR ≈ 1 always'*。
> 还有一个 Cloud-P2 修复：`preRerankOrder` 必须从**原始 `results` 数组**快照，不能用 `[protectedResults, rerankPool]`，否则把词法保护的偏置烘进 baseline 里了。」

加分点：「shadow ranking 不写 DB，是进程内一个 `Map<string, Array<...>>`，key 是**前 8 个 anchor 拼的字符串**，容量 `MAX_SHADOW_ENTRIES = 32`，满了删最老的。`lookupShadowRanking()` 是破坏性读取（`stack.shift()`），在 `recall-correlation-hook.ts` 里取出来写进 `recall_events.shadow_ranking_json`。所以进程重启会丢未关联的 shadow。」

### Q11 「entity 召回和 BM25 结果怎么合并？会不会互相压制？」

> 「分两处。
> **第一处**在 `searchWithMeta()` 里：entity mention hydrate 出来的 items 用 `if (!seenAnchors.has(item.anchor))` **追加到 results 尾部**，不插队。
> **第二处**是 `mergeEntityResults(entityItems, items, limit)`，有配额保护：
> ```ts
> const entityCap = items.length > 0 ? Math.max(1, Math.ceil(limit / 2)) : limit;
> // 先填 entityItems.slice(0, entityCap)，再填 items，用 seen 去重，最后 slice(0, limit)
> ```
> 主路结果非空时 entity 最多占一半，为空时 entity 可以占满。**注意这个函数只在 semantic 和 hybrid 分支调用，lexical 分支不调**——lexical 模式下 entity 结果只能靠上面那个『追加到尾部』，且会被 `slice(0, limit)` 截掉。
> entity anchor 本身的排序在 `EntityRegistry.selectMentionAnchors()` 的 SQL 里：`ORDER BY has_passage DESC, latest_mention_at DESC, m.doc_anchor`——有段落级提及的优先，然后最近提及，最后 anchor 字典序保证确定性。hydrate 完还要按这个顺序重排（`mentionHits.anchors.map(a => rowMap.get(a))`），不能让 `IN (...)` 的返回顺序覆盖它。」

### Q12 「`intent=coverage` 和默认搜索差在哪？」

> 「差在**它根本不走那条管线**。`routes/evidence.ts` 里 coverage 判定在所有逻辑之前：`if (intent === 'coverage') { ... return coverageResult; }`——不进 KnowledgeResolver、没有 variantId、没有 salience rerank、没有 expansion hints，返回的 JSON 形状也完全不同（`{query, totalHits, bySource, matrix, gaps, degraded?}` 而不是 `{results, degraded, variantId}`）。
> `CoverageSearchService.search()` 五步：并行搜 docs(配额 25) + threads(配额 20)，都是 `mode: 'hybrid'`；union 去重（docs 优先，`matchType: 'direct'`）；frontmatter 扩展（每个 keyword 再搜 docs limit=5，`matchType: 'alias'`，confidence 兜底 0.7）；source-thread 扩展（正则 `/thread-[a-z0-9_-]+/gi` 从 sourceIds 和 summary 抠 thread 引用，再搜 threads limit=3，confidence 兜底 0.6）；convention graph 扩展（配额 10，soft dep，无 adapter 就 push 一条 degraded）。最后 `slice(0, COVERAGE_MAX_TOTAL = 50)`。
> 两个 v1 缺口注释里写明了：convention graph 没有生产 adapter，`onCoverageEvent` 遥测没接线（`catId`/`invocationId` 是空串）。另外 `gaps` 永远返回 `[]`。」

加分点：「coverage 的扩展**没有查询预算上限**——`expandViaFrontmatter` 对命中文档的每一个 keyword 都发一次 hybrid 子查询。F256 Phase B 的 `TopkExpansionService` 是同样逻辑的 topk 版本，那边加了 `MAX_TERMS_PER_TYPE = 5`，注释写着 *'Scanner-generated keywords have no upper bound. Cap internal searchWithMeta calls to avoid amplifying every default topk search into many sub-queries. (砚砚 review P1-2)'*——说明这个问题被发现过，但只在新代码里修了。」

### 8.3 判定规则速查

| 问题 | 规则 |
|---|---|
| 候选池多大 | `mode==='hybrid'` → `clamp(limit*4, 20, 100)`；否则 `limit` |
| FTS 放松几级 | token ≤3 → 1 级；≥4 → 2 或 3 级（强/弱有一边空则跳过 Level 2） |
| 强 token | 实体正则 / `^Phase[A-Z]$` / 含 CJK / 长度 ≥4 |
| backfill 何时跑 | 只要 `splitLexicalBackfillWords()` 非空（**无条件**） |
| backfill 排序 | keywordHits ↓ → titleHits ↓ → textHits ↓ → superseded ↑ → archive ↑ → provenanceRank ↑ → updated_at ↓ |
| MMR 何时跑 | `mode==='hybrid'` 且 `movable.length >= 3*limit` |
| 谁被 pin | `prior.branch === 'constitutional'`，即 `authority==='constitutional'` 或 `kind∈{decision,lesson}`，**且不在 14 天宽限期内** |
| 谁被词法保护 | query 词数 ≥2（或含 CJK）且所有词都在 `title+summary+keywords` 且至少一词在 `title` 或 `keywords` |
| authority boost 何时整体跳过 | flag `off` / `results.length < 2` / 存在词法保护锚 |
| embedding 可用 | `embedDeps` 存在 且 `mode==='on'` 且 `reprobeIfNeeded()` 不抛 且 `isReady()` |
| `depth=raw` 何时不搜 passage | `scope` 存在且既不是 `all` 也不是 `threads` |
| passage-only 新 anchor 何时放行 | `!scopeActive` 或 有显式 threadId 或 doc 级零结果 或 存在 `_semanticHit && !_alsoLexical` 的 passage；且 `parentDoc.kind` 必须匹配 scope |
| 索引跳过 | `sourceHash` 相同 且 不缺 provenance 且 无 force 且 `INDEXING_VERSION` 未变 |
| anchor 归属 | `KIND_PRIORITY` 高者赢；低优先级要覆盖高优先级还需旧文件已从磁盘消失 |
| 向量全量重建 | `checkMetaConsistency()` 发现 `embedding_model_id` 或 `embedding_dim` 变了 |
| confidence 怎么算 | `rankToConfidence(index)`：0/1 → high，2..4 → mid，≥5 → low |
| 图截断 | 单节点边数 ≥15 或总节点 ≥50 |
| coverage 上限 | docs 25 + threads 20 + convention 10，总 slice 50 |
