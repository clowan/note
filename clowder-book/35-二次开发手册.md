# 35 · 二次开发手册：想改什么，从哪下手

> 这一篇回答：**我想加个功能 / 改个东西，从哪开始，会碰到哪些文件，
> 怎么改不破坏现有设计，改完怎么验证。**
>
> 它是一本**查询手册**，不是教程 —— 按你要做的改动类型直接跳到对应小节。
>
> 而且它有一个额外用途：**面试时被问"你会怎么在这个项目上加功能"，
> 这一篇的任何一节都是完整答案。**

---

## 0. 先建立正确的下手姿势

### 三条 Contributor Guardrails（项目自己写的）

【源码】`CONTRIBUTING.md` 里有三条硬约束，**任何改动前先对照**：

> 1. **Cozy Café, not RPG**：成长和进展应该像共享记忆
>    （贴纸墙、猫爬架、共享相册、涌现的知识）。
>    **我们不做硬核 RPG 系统、技能树、原始 XP 数值。**
> 2. **Extend, don't parallel**：新功能应该**扩展已有的域**
>    （比如 Memory Hub F102 或 Expeditions F152），
>    而不是创建孤立的、平行的系统。
> 3. **CatRegistry is the truth**：所有身份必须走中央 `catRegistry`。
>    **不要硬编码假的 `catId` 来代表共创者或系统事件。**

**第 2 条是最容易违反的。**

【推断】新人的本能是"我要加个 X 功能，那就新建一个 `domains/x/`"。
但更多时候正确做法是**扩展已有域** —— 因为孤立的新域意味着新的存储、
新的一致性问题、新的 prompt 注入点。

**面试话术**：

> "这个项目的 CONTRIBUTING 里有三条 contributor guardrail，
> 我觉得第二条最值得学：**'Extend, don't parallel'——
> 新功能要扩展已有的域，不要建平行的孤立系统。**
>
> 因为一个新域意味着新的存储、新的一致性边界、新的 prompt 注入点。
> 我读的时候确实发现它有 22 个域但体量极不均衡 ——
> 说明这条规则是在对抗一个真实的倾向。"

### 贡献流程（比代码更重要的是意图）

【源码】`CONTRIBUTING.md`：

```
1. Intent          你有个想法或发现了问题
      ↓
2. Open an Issue   描述你想要什么、为什么
      ↓
3. Discussion      维护者讨论 → 分配 F 编号 → 创建 Feature Doc
      ↓
4. Execution       对着 Feature Doc 的验收条件实现
      ↓
5. Verification    结果和文档对得上吗？要证据，不要自信
```

**注意第 3 步是维护者做的** —— F 编号不是贡献者自己取的。

而且项目明说了：

> **Step 3 is the most important.** A merged Feature Doc means
> the community agrees on the *what* and *why*.

**"Intent 优先"这个模型对 vibe coding 的人非常友好** ——
你的价值在"想清楚要什么"，实现可以让 AI 干。

### 环境准备（照抄就行）

【源码】`CONTRIBUTING.md` 的 Quick Start：

```bash
# 1. Fork + clone
gh repo fork zts212653/clowder-ai --clone
cd clowder-ai

# 2. 开分支
git checkout -b feat/your-feature-name

# 3. 装 + 构建 + 验证
pnpm install
pnpm build
pnpm check

# 4. 开发模式挂 skills（可选，让本地 CLI 看到这个仓库的 skills）
pnpm sync:skills          # 项目级（推荐）

# 5. 改完跑检查
pnpm check          # Biome lint + 一堆 check:*
pnpm lint           # TypeScript 类型检查
pnpm --filter @cat-cafe/api run test:public   # 公开测试套件

# 6. 提 PR
git push origin feat/your-feature-name
gh pr create --repo zts212653/clowder-ai
```

**注意 `pnpm check` 不只是 lint** ——
它串了十几个一致性检查（见 [14 章](14-模块-SOP门禁.md) §3.12）。
**改完必跑，这是最省事的自检。**

## 1. 改动类型 × 难度速查

| 想做什么 | 难度 | 触点数量 | 跳到 |
|---|---|---|---|
| 加一个新 Agent（新的猫） | ★ 低 | 1~2 个配置文件 | §2 |
| 加一条 SOP 规则 | ★ 低 | 1 个 YAML + 生成 | §3 |
| 加一个新 Skill | ★ 低 | 1 目录 + 1 manifest | §4 |
| 加一个 MCP 工具 | ★★ 中 | 3~5 个文件 | §5 |
| 加一个 prompt 注入段 | ★★ 中 | 2~4 个文件 | §6 |
| 加一个业务域 | ★★★ 中高 | 一个目录 + 若干接线点 | §7 |
| 接一个新的 CLI provider | ★★★★ 高 | 5~10 个文件 | §8 |
| 改存储/加一个 store | ★★★ 中高 | 接口 + 两套实现 | §9 |
| 改前端 | ★★ 中 | 看具体 | §10 |

**建议的第一个 PR**：从 §3 或 §4 开始 —— 触点少、有明确验收、不容易破坏别的东西。

## 2. 加一个新 Agent（新的猫）

**这是最简单的改动，而且不用改代码。**

### 触点

```
.cat-cafe/cat-catalog.json     运行时注册表（真相源）
cat-template.json              模板：roster / roleTemplates / reviewPolicy / breeds
（可选）.env                    per-cat 的模型覆盖 CAT_{CATID}_MODEL
```

### 关键字段

从 [07 章](07-模块-身份注入.md) 和 [11 章](11-模块-跨模型互审.md) 已知，
一个 Agent 的配置至少要有：

```jsonc
{
  "displayName": "布偶猫",          // 显示名
  "variantLabel": "Opus 4.7",       // 同品种不同个体的消歧（重要）
  "isDefaultVariant": true,         // 同名时谁能用短句柄
  "nickname": "宪宪",
  "mentionPatterns": ["@opus", "@布偶猫"],   // ★ 路由靠它
  "clientId": "anthropic",          // 走哪个 CLI
  "defaultModel": "...",
  "roleDescription": "...",
  "personality": "...",
  "restrictions": ["禁止写代码"],    // 会显示在别人的队友名册里
  "caution": "...",
  "teamStrengths": "..."
}
```

roster 那边（`cat-template.json`）：

```jsonc
"opus": {
  "family": "ragdoll",              // ★ 跨模型互审靠它
  "roles": ["architect", "peer-reviewer"],
  "lead": true,
  "available": true,                // ★ 有没有额度
  "evaluation": "..."
}
```

### 五个必须注意的坑

**① `mentionPatterns` 不能有前缀冲突**

```
已有 @opus，你加 @opus-2
  → 长匹配优先能处理（[04 章](04-模块-mention解析.md) §3.6）
  → 但如果你加 @op，它会和 @opus 冲突得更难看
```

**建议**：新 handle 不要是已有 handle 的前缀，反之也不要。

**② `family` 直接影响互审能不能过**

```
如果你把新猫的 family 设成和已有猫一样
  → 它俩之间的 review 会被判成"同族降级"
```

**③ `restrictions` 会出现在所有其他 Agent 的名册里**

【源码】它取代了废弃的 L3 role-gate ——
**写了就是给别的 Agent 看的信息，不是代码强制。**

**④ `available: false` 的猫仍会出现在名册里（标"没额度"）**

这是刻意的（[04 章](04-模块-mention解析.md) §3.7 的"可见的缺席"）。

**⑤ `isDefaultVariant` 同名时只能有一个**

否则短句柄归属不确定。

### 验收

```bash
pnpm check                          # 配置一致性检查
# 启动后在 Console 里 @ 新猫，确认路由到它
# 让它和另一只猫互相 @ 一次，确认 A2A 能通
# 触发一次 review 匹配，确认 family 判定正确
```

### 面试话术

> "加一个新 Agent 不用改代码 —— 改 `cat-catalog.json` 和 `cat-template.json` 就行。
>
> 但有几个字段有连锁影响：
> `mentionPatterns` 决定路由能不能命中，不能和已有 handle 有前缀关系；
> `family` 决定跨模型互审的判定，设错了会让两只猫的 review 被判成同族降级；
> `restrictions` 会出现在所有其他 Agent 的队友名册里，
> 是给模型看的信息不是代码强制 ——
> 因为他们废掉了代码级的角色门禁，改成信息透明 + 模型自己判断。"

## 3. 加一条 SOP 规则

### 触点

```
sop-definitions/development.yaml           ← 唯一要手改的
packages/shared/src/types/sop-definition.generated.ts   ← 生成的，不要手改
```

### 步骤

**① 在对应 stage 下加规则**

```yaml
- id: <stage>-<短横线命名的规则名>
  text: <人类可读的一句话>
  severity: blocker | warn
  predicate:
    type: <七选一>
    # ...判定参数
```

**七种 predicate 类型**（[14 章](14-模块-SOP门禁.md) §3.4）：

| type | 什么时候用 |
|---|---|
| `manual_only` | 判不了，必须配 `reason` + 建议配 `future_candidate` |
| `git_state_predicate` | 要查 git 状态（分支、ahead/behind） |
| `env_check` | 要查环境变量 |
| `command_pattern` | 要求跑过/没跑过某类命令 |
| `command_sequence` | 命令序列 / 反模式（`anti_pattern` + `absent`） |
| `handle_check` | 身份约束（如 `reviewer_not_author`） |
| `sha_dedup` | SHA 去重 |

**② 重新生成 + 检查**

```bash
pnpm gen:sop-definitions
pnpm check:sop-definitions
```

**忘了生成 → CI 红。** 这是刻意的。

### 一个好的第一条规则长什么样

**如果判不了，一定要写清缺什么**：

```yaml
predicate:
  type: manual_only
  reason: <具体缺什么：缺遥测 / 缺结构化事件 / 缺 artifact>
  future_candidate: <将来用哪个 checker 能自动化>
```

**不要写"这条不好自动化"** —— 那是死路。
**要写"缺 post-compact 遥测"** —— 那是下一步。

### 验收

```bash
pnpm gen:sop-definitions && pnpm check:sop-definitions
pnpm check     # 全量
```

## 4. 加一个新 Skill

### 触点

```
cat-cafe-skills/<name>/SKILL.md        新建
cat-cafe-skills/manifest.yaml          加路由条目
cat-cafe-skills/BOOTSTRAP.md           加到路由表（目前手工同步）
```

### SKILL.md 的骨架

```markdown
---
name: <kebab-case>
description: >
  <一句话定位>
  Use when: <触发场景，具体>
  Not for: <排除场景 —— 这段防过度加载，必写>
  Output: <产出契约>
triggers:
  - "<触发词1>"
  - "<触发词2>"
---

# <标题>

<一句话核心主张>

## 核心知识

### 为什么这么做（常见异议的反驳）

| 异议 | 真相 |
|------|------|
| "<模型会自己想到的偷懒理由>" | <反驳> |

## 流程

<编号步骤>

## 关键决策点

- <情况 A>？→ <怎么办>
- <情况 B>？→ <怎么办>

## 和其他 skill 的区别

- `<邻居 skill>`：<什么时候用它，什么时候用我>
```

### 为什么"异议反驳"那张表必须写

【源码】这是 `tdd/SKILL.md` 的做法：

> **模型会自己说服自己跳过步骤。**
> 比如"这个改动很小，直接写实现更高效"——
> 预先写好反驳，它遇到这个念头时能认出来。

**这是给 LLM 写文档的核心技巧，也是这个项目 skill 质量高的原因。**

### manifest 条目

```yaml
<name>:
  category: "<分类>"
  description: >
    Use when: ... / Not for: ... / Output: ...
  triggers: [...]
  not_for: [...]
  output: "..."
  next: ["<下一个 skill>"]      # skill 之间的链
  sop_step: <阶段 id 或 null>
```

### 验收

```bash
pnpm check:skills:manifest
pnpm check:skills:surfaces
pnpm sync:skills               # 挂到本地 CLI
# 然后在实际对话里触发一次，确认 Agent 真的加载了
```

**最后那步很重要** —— [12 章](12-模块-Skills分发.md) §6.1 说过，
**Skill 缺失是静默失败**，光看配置没用。

## 5. 加一个 MCP 工具

### 触点

```
packages/mcp-server/src/tools/<xxx>-tools.ts      工具定义 + handler
packages/mcp-server/src/server-toolsets.ts        注册 + annotation
packages/api/src/routes/callback-<xxx>-routes.ts  服务端路由（如果要回写）
cat-cafe-skills/<相关skill>/SKILL.md              ★ 教 Agent 什么时候用
```

### 关键：注册机制

【源码】`server-toolsets.ts`：

```ts
function registerTools(server: McpServer, tools: readonly ToolDef[]): void {
  // 用 server.registerTool(name, config, cb) —— 显式的 config-object API。
  // server.tool() 的重载解析器会把 JSON Schema 误判成 annotations → 参数错位 → 运行时崩。
  const registerExplicit = server.registerTool.bind(server) as unknown as (...);
  for (const tool of tools) {
    const annotations = inferAnnotations(tool.name);
    // 区分 Zod raw shape（callback tools）和 plain JSON Schema（limb tools）
    const zodSchema =
      typeof schema.type === 'string' && typeof schema.properties === 'object' && schema.properties !== null
        ? jsonSchemaToZod(schema)
        : z.object(schema as z.ZodRawShape);
    registerExplicit(tool.name, { description, inputSchema: zodSchema, annotations }, handler);
  }
}
```

**两个坑写在注释里了**：

**① 必须用 `registerTool` 不能用 `tool`**

因为 `server.tool()` 的重载解析器会把 plain JSON Schema 误判成 annotations，
**参数槽位错位 → 运行时崩溃**。

**② schema 有两种形态**

callback 工具用 Zod raw shape，limb 工具用 plain JSON Schema，
注册时要判别。

### 关键：annotation 的保守默认

```ts
const explicit = EXPLICIT_TOOL_ANNOTATIONS[toolName];
if (explicit) return explicit;
// Fallback for unmapped tools: most conservative write/non-destructive,
// never silently mark unknown as read-only (砚砚 R8 finding).
return A_WRITE_SAFE;
```

**没登记的工具默认按"写操作"处理，绝不默认成只读。**

**为什么？** 因为只读标记会影响过滤（比如某些受限模式只允许只读工具）。
**误标只读 = 安全漏洞。**

**所以你加了新工具，必须在 `EXPLICIT_TOOL_ANNOTATIONS` 里登记**，
否则它会被当成写工具（安全但可能被过滤掉）。

### 别忘了：能力可用 ≠ Agent 会用

**【ADR】ADR-037 定义了四级"认知入口"优先级**：

```
1. MCP tool description        ← 模型总能看到，最重要
2. 相关 skill refs / SOP 文档   ← 场景化指导、参数、副作用、坑
3. Capability wakeup / L0 索引  ← 只给必须扛住压缩的宽泛类别
4. SystemPromptBuilder 的工具清单 ← 只在遗留兼容时用
```

**而且 ADR 明确说了不要默认加到第 4 项**，理由是
"让 prompt 不断膨胀，把遗留 prompt 界面变成过期的目录"。

**Review 时该问的是**：
"哪个认知入口教会了 Agent 用这个工具？"
而不是"加到清单了吗？"

### 降级策略必须显式声明

如果是**写类**工具，[13 章](13-模块-MCP回调桥.md) §3.5 的框架要求：

```ts
withDegradation({
  toolName: 'your_tool',
  primary: () => callbackPost('/api/callbacks/xxx', body),
  policy: { kind: 'none' },   // ← 必填，哪怕是 none
})
```

【源码】`explicitness > silent default` ——
不给默认值，就不会有人"忘了考虑降级"。

### 验收

```bash
pnpm --filter @cat-cafe/mcp-server run test    # 有个 tool-registration.test.js
pnpm check
# 然后在实际对话里让 Agent 调一次
```

**注意那个 `tool-registration.test.js`**，注释写着：

> 早就存在，但 `createServer()` 漏了 `server.tool()` 注册。

**说明"工具定义了但没注册"这个坑真实发生过，所以有专门的测试。**

### 面试话术

> "加一个 MCP 工具的完整改动面比想象的大。
>
> 代码上要改三处：工具定义、注册（而且必须用 `registerTool` 不能用 `tool`——
> 因为重载解析器会把 JSON Schema 误判成 annotations，参数错位会运行时崩）、
> 还有 annotation 登记（没登记的默认按写操作处理，
> **绝不默认成只读，因为误标只读是安全漏洞**）。
>
> 但更重要的是**认知入口**。他们有份 ADR 专门讲这个 ——
> '加了工具'不等于'Agent 会用'。而且明确**否掉**了
> '往 prompt 里塞工具清单'这个做法，理由是那会让 prompt 膨胀、
> 把遗留界面变成过期目录。
>
> 正确做法是四级优先：先改工具自己的 description（模型总能看到）、
> 再改相关 skill 文档、只有必须扛住上下文压缩的宽泛类别才进 L0。
>
> 他们连 review 的提问方式都改了 ——
> 从'加到清单了吗'变成'**哪个认知入口教会了 Agent 用这个工具**'。"

## 6. 加一个 prompt 注入段

### 触点

```
assets/prompt-templates/<dNN>-<name>.md          新模板
packages/api/src/domains/cats/services/context/SystemPromptBuilder.ts
   → InvocationContext 加字段
   → buildInvocationContext 里加渲染分支
（可能）路由层传值：route-serial.ts / route-parallel.ts
（可能）interceptor：如果数据要从 store 读
```

### 模板格式

```markdown
<!-- @segment D21 — <段落名> -->
<!-- Variables: VAR_A, VAR_B -->
<!-- Condition: <什么时候渲染> -->

<正文，用 {{VAR_A}} 占位>
```

### 三个必须遵守的规则

**① 用 interceptor 两段式，不要在路由核心里塞逻辑**

【源码】这是 concierge / guides 的标准做法（[32 章](32-深潜-剩下15个业务域.md) §3.6）：

```ts
// 第一段：整条路由前调一次（有 IO）
export async function prepareXxxContext(thread, userId, store) {
  if (<不适用的条件>) return {};      // fail-open
  const data = await store.get(...);
  return { xxxField: data };
}

// 第二段：每只 Agent 调一次（纯判断，无 IO）
export function xxxContextForCat(ctx, catId) {
  if (!('xxxField' in ctx)) return {};
  // 决定这只 Agent 要不要注入
}
```

然后在路由层：

```ts
const xxxCtx = await prepareXxxContext(routeThread, userId, deps.xxxStore);
// per-cat 循环里
buildInvocationContext({ ...base, ...xxxContextForCat(xxxCtx, catId) })
```

**好处**：IO 只做一次、和路由核心解耦、双重 fail-open。

**② 加 `mark()` 标注**

```ts
mark('D21', '你的段落名');
```

**而且 if/else 两侧都要打** —— 这样 `annotateSegments` 预览时
能分辨"没渲染"和"渲染了但是空的"。

**③ 算 token 预算**

[07 章](07-模块-身份注入.md) 提到的所有预算常量都是硬编码的。
**你加的段落如果每轮注入，要控制在几十 token 以内。**

如果内容可能很长，参考 `compactRosterCell` 那种限长（52/72 字符）。

### 验收

```bash
pnpm --filter @cat-cafe/api run test   # 有 system-prompt-builder.test.js
# 开 annotateSegments 看一眼生成的 prompt
# 确认不该注入的场景真的没注入
```

## 7. 加一个业务域

### 先问三个问题

【源码】对照 contributor guardrail 第 2 条 "Extend, don't parallel"：

```
1. 能不能扩展已有的域？（大多数情况下能）
2. 如果不能，它的持久化用什么？（会不会又造一套存储）
3. 它怎么接入编排核心？（interceptor？MCP 工具？路由钩子？）
```

**只有三个问题都答清楚了才建新域。**

### 骨架（照 [32 章](32-深潜-剩下15个业务域.md) 的五个范式）

```
domains/<yourdomain>/
├─ <Your>StateMachine.ts        纯函数、表驱动、零 IO
│                               （副作用留给下面的 Service/Projector）
├─ <Your>EventLog.ts            如果需要审计/重建 → 事件溯源
├─ <Your>Projector.ts           apply(event) = 读投影 → transition → save
│                               ★ 零外部副作用（否则 rebuild 会重放副作用）
├─ <Your>ProjectionStore.ts     当前状态
├─ <Your>RoutingInterceptor.ts  如果要注入 prompt → 两段式
├─ <Your>PromptSection.ts       prompt 片段生成
├─ <your>-keys.ts               ★ key 从现有 id 派生，不引入新原语
└─ index.ts
```

### 接线点

```
packages/api/src/index.ts            装配（作为可选依赖注入）
route-serial.ts / route-parallel.ts  如果要注入 prompt
routes/callback-<your>-routes.ts     如果 Agent 要通过 MCP 操作它
SystemPromptBuilder.ts               InvocationContext 加字段
```

**注入方式必须是可选 + fail-open**：

```ts
readonly yourStore?: IYourStore;   // optional, fail-open
```

**这样没配它的部署照常跑。**

### 五个范式检查清单

```
[ ] 状态机是纯函数吗？（零 IO、表驱动、副作用留调用方）
[ ] 需要审计/重建吗？→ 用事件日志 + 投影器，投影器零外部副作用
[ ] 要注入 prompt 吗？→ interceptor 两段式（prepare 有 IO / perCat 纯判断）
[ ] 接入核心是可选注入 + fail-open 吗？
[ ] key 是从现有 id 派生的吗？（不要引入新原语）
```

```
└─ session-strategy.ts              ★ DEFAULT_STRATEGY_BY_PROVIDER 加一项

invoke-single-cat.ts                spawn 分支、env 注入
utils/cli-resolve.ts                命令解析
utils/cli-error-patterns.ts         错误模式识别
```

### 六个必答问题

**在写代码之前先答**（这也是能力矩阵该有的字段 —— 见 [17 章](17-如果重新设计.md) §2）：

| 问题 | 影响什么 |
|---|---|
| 输出格式是什么？ | parser 怎么写 |
| session 怎么 resume？（flag / config / 不支持） | 会话恢复能不能用 |
| MCP 怎么接？（原生 / 配置文件 / 不支持） | 要不要走回调桥 |
| 有原生 system 通道吗？ | 身份走哪条路（`nativeL0Injection`） |
| 支持哪些 hook？ | 会话策略的上限（能不能用 `hybrid`） |
| 上下文窗口多大？token 计数准吗？ | 封存阈值定多少 |

**最后一个问题的重要性**：

【源码】Gemini 的阈值是 0.55/0.65，比 Claude 的 0.80/0.90 保守 20 个百分点 ——
**因为它是纯文本输出，token 只能估算**。

**估算不准就要留大安全边际。**

### 别忘了 `DEFAULT_STRATEGY_BY_PROVIDER`

【源码】有个真实的坑注释：

```ts
// clowder#915: opencode was falling through to GLOBAL_DEFAULT_STRATEGY
// because it had no entry here. The fallback values happened to be correct
// but the gap masked an architectural issue: opencode had no first-class
// strategy provenance, and tuning would silently be dropped.
```

**"兜底值恰好是对的，但缺口掩盖了架构问题"** ——
不加这一项的话，任何对这个 provider 的阈值调优会**静默失效**。

### 验收

```bash
pnpm --filter @cat-cafe/api run test
# 手动：配一只用新 provider 的猫，跑通一次完整对话
# 手动：验证 resume 能用
# 手动：验证 MCP 工具能调（或回调桥能通）
# 手动：跑到上下文阈值，验证封存能触发
```

**我的建议：先别做这个。** 它是最难的，而且和你的 vibe coding 目标关系不大。

## 11. 三条"改动前必读"的自检

### 自检一：这个改动会不会破坏已有的不变量

**这个项目有一批"硬不变量"**，改动前扫一眼：

| 不变量 | 在哪 | 破坏后果 |
|---|---|---|
| 同一个体不能自审 | reviewer-matcher + SOP predicate | review 失效 |
| 身份不可冒充 | catRegistry + cat-signature-strip + packs IMMUTABLE_FIELDS | 互审失效、审计失效 |
| 开发/生产数据隔离 | 6398/6399 + SOP env_check | 可能删用户数据 |
| 消息历史不可变 | 编辑做成 fork（ADR-008） | 多 Agent 游标错乱 |
| L0 锚点必须存在 | governance-l0 的 13 条断言 | **API 启动失败** |
| 生成物不能过期 | check:sop-definitions 等 | CI 红 |

**第五条尤其要注意**：如果你重构了 `cat-cafe-skills/refs/shared-rules.md`
的标题结构，**API 会直接起不来**。这是刻意的 fail-closed。

### 自检二：这个改动要不要同步别的地方

**这个项目有多处"一处真相源 + N 处投影"**：

```
sop-definitions/development.yaml → 生成 TS 类型 + docs/SOP.md + SKILL.md
cat-cafe-skills/manifest.yaml    → BOOTSTRAP.md 路由表（手工同步）
shared-rules.md                  → L0 编译
cat-catalog.json                 → prompt 名册 + 路由 pattern
.env.example                     → 环境变量注册表
```

**改真相源要跑对应的生成/检查。忘了 → CI 红（这是好事）。**

### 自检三：改完跑什么

```bash
pnpm check     # 一次跑十几个一致性检查，最省事
pnpm lint      # 类型
pnpm --filter @cat-cafe/api run test:public
```

**如果 `pnpm check` 挂了，先看是哪个 `check:*`** ——
错误信息通常直接告诉你该改哪个文件或跑哪个生成命令。

## 12. 面试怎么讲这一篇

### 被问"你会怎么在这个项目上加功能"

**挑一个具体的讲，不要泛泛。推荐讲 MCP 工具**（触点适中、有 ADR 支撑）：

> "我举加一个 MCP 工具的例子。
>
> 代码上要改三处：工具定义、注册、annotation 登记。
> 注册那里有个坑 —— 必须用 `registerTool` 不能用 `tool`，
> 因为重载解析器会把 plain JSON Schema 误判成 annotations，
> 参数槽位错位会运行时崩。这个坑注释里写着。
> annotation 那里的默认值是'写操作'，**绝不默认只读** ——
> 因为只读标记会影响过滤，误标是安全漏洞。
>
> **但更重要的是认知入口。**
> 他们有份 ADR 专门讲'加了工具不等于 Agent 会用'，
> 而且**否掉**了往 prompt 里塞工具清单这个做法 ——
> 理由是那会让 prompt 膨胀、把遗留界面变成过期目录。
> 正确做法是四级优先：工具 description > skill 文档 > L0 索引 > prompt 清单。
>
> 而且如果是写类工具，还要**显式声明降级策略**，
> 哪怕是 `{ kind: 'none' }`——他们的原则是
> `explicitness > silent default`，不给默认值就不会有人忘了考虑。
>
> 最后跑 `pnpm check`，它串了十几个一致性检查。"

### 被问"改动会不会破坏别的东西"

> "他们有一批硬不变量，我会先扫一遍。
>
> 最狠的一条是 **L0 锚点** —— 家规是从
> `shared-rules.md` 确定性编译出来的，断言了 13 个必须存在的标题。
> **如果你重构了那份文档的标题结构，API 会直接启动失败。**
> 这是刻意的 fail-closed，因为治理规则静默少一条比崩溃难查得多。
>
> 另外有好几处是'一处真相源 + N 处投影'——
> SOP 的 YAML 生成 TS 类型、skills manifest 投影到 BOOTSTRAP 路由表。
> 改了真相源忘了重新生成，`pnpm check` 会红。
> **这个'生成物过期就 CI 红'的模式在项目里用了好几次。**"

### 被问"你提过 PR 吗"

**如实说**。如果还没提，说计划：

> "还没有。我现在在做的是先把架构读透，然后从小的开始 ——
> 他们的 CONTRIBUTING 里写得很清楚：
> **贡献流程是 Intent 优先** —— 先开 issue 说清楚要什么和为什么，
> 维护者讨论后分配 F 编号并创建 Feature Doc，然后对着验收条件实现。
>
> 原话是 'code is cheap, alignment is expensive'。
>
> 我打算从我熟的方向切 —— 我之前主要做安全测试，
> 他们的 SECURITY.md 里 in-scope 有几条正好在我的领域，
> 比如 prompt injection 导致越权、Agent 身份伪造。
> 而且他们 ROADMAP 里 `F156 Security Hardening` 状态还是 spec。"

**详见 [36 章](36-诚实定位与真实参与.md)。**

## 13. 本篇速查

### 改动难度 × 触点

| 改动 | 触点 | 必跑的检查 |
|---|---|---|
| 加 Agent | 2 个配置文件 | `pnpm check` |
| 加 SOP 规则 | 1 YAML + 生成 | `gen:sop-definitions` + `check:sop-definitions` |

| 加业务域 | 目录 + 装配 + 可选接线 | 五个范式检查清单 |

| 加 store | 接口 + 两套实现 | 两套实现行为一致性 |

```
3. CatRegistry is the truth  —— 身份必须走 catRegistry，不硬编码假 catId
```

### 五个范式检查清单（加业务域时）

```
[ ] 状态机纯函数？（零 IO、表驱动、副作用留调用方）

```
