# 05 · 模块：调用生命周期与队列

> 前面两个模块决定了"叫谁"。这个模块管"**叫的过程**"：
> 一次调用是一个有 id、有 token、有状态机、能被排队、
> 能被取消、能被封存、能被回收的**对象** —— 不是一次函数调用。
>
> 这个模块最能体现"多 Agent 系统的工程复杂度"，
> 因为单 Agent 系统里 90% 的内容都不需要。

---

## 0. 30 秒电梯版

> "他们把'调一次模型'从一个 async 函数升级成了一个**有生命周期的对象**：
> `InvocationRecord`，状态机是 `queued → running → succeeded/failed/canceled`。
>
> 【ADR】这是 ADR-008 的核心决策，动因很具体：
> 原来消息写入和 Agent 调用在同一个 async 里，
> 调用失败时没法单独重试；而且没有幂等键，网络重试就产生重复消息。
>
> 配套三个组件：`InvocationTracker` 管'谁在跑'（互斥锁），
> `InvocationQueue` 管'谁在等'（FIFO），`QueueProcessor` 管出队执行。
> 判忙的粒度是 slot 级 —— `(threadId, catId)`，
> 所以 A 忙的时候你可以顺手问 B。"

---

## 1. 它解决什么问题

### 问题一：调用失败了怎么重试

```
用户发消息
  → 写入 messageStore
  → spawn claude
  → ENOENT（claude 命令找不到）
  → 整个 async 抛异常
  → 消息已经写进去了，但没有 Agent 回复
  → 用户重发 → 又写一条消息 → 又失败 → 消息叠了两条
```

【ADR】ADR-008 原文列的三个结构性缺陷：

> | 缺陷 | 现状 | 后果 |
> |------|------|------|
> | 无幂等性 | POST /api/messages 没有去重机制 | 网络重试或用户重发 → 重复消息 |
> | 无执行状态 | 消息写入 + 猫调用在同一 background async 中 | 调用失败时无法单独重试执行 |
> | 消息不可变是全局假设 | cursor 单调递增依赖消息 ID 链不变 | 一旦允许删除，cursor 可能指向"空洞" |

### 问题二：Agent 正忙的时候来了新消息

单 Agent 系统里这个问题很简单：排队就行。
多 Agent 系统里要回答：**"忙"的粒度是什么？**

```
opus 正在跑一个 10 分钟的任务
用户：@codex 顺便问一下这个怎么理解？
  → 如果 thread 级判忙：codex 也被锁，用户要等 10 分钟
  → 如果 slot 级判忙：codex 立刻回答
```

### 问题三：Agent 之间的消息和用户消息谁优先

```
opus 和 codex 正在 A2A 接力，每轮结束又追加下一只
  队列里躺着一条用户消息
    → 如果没有优先级，用户消息永远排不上
```

### 问题四：进程卡死 / 进程崩了 / API 重启了

子进程会：卡住不输出、变僵尸、被父进程重启带走、
留下孤儿 Chrome 进程（Antigravity 场景）。

**这些全部是"选了 CLI 子进程"的代价**（见 [模块 02](02-决策-为什么选CLI子进程.md) §8）。

---

## 2. 不做会怎样

| 不做 | 后果 |
|------|------|
| 没有 InvocationRecord | 失败无法单独重试；消息和执行状态耦合 |
| 没有幂等键 | 网络抖动/用户双击 → 重复消息 → 重复调用 → 重复烧钱 |
| 没有 Tracker | 同一 Agent 同时跑两个调用 → session 状态打架 → CLI 报错 |
| 没有队列 | 忙的时候直接拒绝，用户体验极差；或者直接并发，成本失控 |
| 没有公平性闸门 | A2A 链把用户消息饿死 |
| 没有僵尸回收 | 卡死的 slot 永远占着，那只 Agent 从此不可用 |
| 没有启动对账 | API 重启后遗留一堆 `running` 状态，永远不会变成终态 |

**最后一条尤其真实**：`RedisAuthInvocationBackend.ts` 的注释【源码】：

```
 * Restart-resilient: API process exit / deploy / crash no longer drops active…
```

**"no longer"说明这是个已经填掉的坑。**

## 3. 怎么设计的

### 3.1 三个组件的分工

```
┌──────────────────────────────────────────────────────────┐
│  InvocationTracker — "谁在跑"                              │
│  slot = (threadId, catId)                                 │
│  每个 slot 一个 AbortController                            │
│  同 catId 新调用会 abort 旧调用（单锁语义）                  │
│  不同 catId 可以并发                                       │
├──────────────────────────────────────────────────────────┤
│  InvocationQueue — "谁在等"                                │
│  scopeKey = (threadId, userId)  ← 存储层天然用户隔离        │
│  FIFO + 优先级 + 用户可拖拽排序                             │
├──────────────────────────────────────────────────────────┤
│  QueueProcessor — "怎么出队执行"                            │
│  processingSlots / pausedSlots / 僵尸清扫 / 公平性判定       │
└──────────────────────────────────────────────────────────┘
```

源码注释把前两个的关系说得很清楚【源码】：

```ts
/**
 * InvocationQueue
 * Per-thread, per-user FIFO 队列，用于猫猫在跑时排队用户/connector 消息。
 *
 * 与 InvocationTracker（互斥锁，跟踪活跃调用）互补：
 * - InvocationTracker: "谁在跑"
 * - InvocationQueue: "谁在等"
 *
 * scopeKey = `${threadId}:${userId}` — 存储层天然用户隔离。
 * 系统级出队（invocation 完成后）通过 *AcrossUsers 方法跨用户 FIFO。
 */
```

**`scopeKey` 带 userId 这个设计值得讲**：
队列按用户隔离，所以一个用户塞满队列不会影响另一个用户；
但系统出队时用 `*AcrossUsers` 方法跨用户做 FIFO，保证公平。

### 3.2 判忙的双层设计

**这是本模块最值得在面试里讲的设计。**

```
入队决策层：slot 级  →  宽松
执行层：   thread 级 →  严格
```

【ADR】ADR-018 的原文：

> ### OQ-4: 保持 slot 级判忙 ✅
>
> **决定**：Connector 和用户消息的判忙维持 slot 级（`has(threadId, catId)`），
> 不改为 thread 级。
>
> **效果**：
> - 猫A 在忙时，发给猫B 的消息直接执行（by the way 场景）
> - 用户可以同时和多只猫交互，只要目标猫空闲
> - 前端提示"XX猫正在回复中"，用户知道谁在忙
>
> **放弃的方案**：thread 级判忙（`has(threadId)`）。
> 理由：太粗，猫A忙时猫B也被锁，牺牲并行性。
>
> **安全保障**：`tryStartThread()` 在执行层面仍是 thread 级 busy gate
> （同一 thread 不会并发两个 invocation），slot 级只影响入队决策。

**用大白话解释这两层为什么都需要：**

```
为什么入队要宽松（slot 级）？
  → 用户在等 opus 干活的时候，想顺便问 codex 一句
  → 如果 thread 级判忙，这句话要排队 10 分钟才回
  → 但语义上它们完全无关，没必要等

为什么执行要严格（thread 级）？
  → 同一个 thread 的消息历史、球权状态、参与者列表是共享的
  → 两个调用并发写这些状态会打架
  → 而且两只 Agent 同时往同一个帖子输出，用户看到的是乱码流
```

**面试话术**：

> "他们的判忙做了两层，我觉得这是个很漂亮的拆分。
> 入队决策看 slot 级 —— slot 是 `(threadId, catId)`，
> 所以你可以在 A 忙的时候顺手问 B，不用等。
> 但执行层是 thread 级串行的，因为同一个帖子的消息历史和球权状态是共享的。
>
> 这个拆分让'并行感'和'状态一致性'能同时拿到 ——
> **用户感受到的是并行，实际执行是串行的**。
> 他们的 ADR 里明确写了否掉纯 thread 级判忙的理由：
> '太粗，猫A忙时猫B也被锁，牺牲并行性'。"

### 3.3 Tracker 里的"墓碑"设计

这段我觉得很精妙【源码】：

```ts
/**
 * F-parallel-cancel tombstone: 'active' = running; 'canceled' = single-cat cancelled but the
 * slot is RETAINED so getController() still returns the aborted controller. This is critical for
 * "pre-invoke cancel": a cat cancelled before the route layer grabbed its own signal must still
 * see an aborted signal (not fall back to the batch gate). Tombstones are inactive for has()/
 * busy gates and are purged at the next start-family or complete-family call for the slot.
 */
state: 'active' | 'canceled';
```

**问题场景（用大白话讲）**：

```
时间线：
  T1  路由层决定要调 opus 和 codex（并行）
  T2  用户点了"取消 codex"
  T3  路由层才走到 codex 那一步，去拿它的 abort signal
      → 如果 slot 已经被删掉了
        → 拿不到 codex 自己的 signal
          → 回退到 batch 级的 signal（那个还没被 abort）
            → codex 照样被调用了
```

**解法**：取消不删 slot，而是标记成 `canceled`（墓碑）。
这样 T3 还能拿到那个已经 abort 的 controller。

墓碑的三条规则：

```
① 对 has() / 判忙 是"不存在"     → 不阻塞新调用
② 对 getController() 是"存在"    → 能拿到 aborted signal
③ 下次 start/complete 时清理     → 不会永久堆积
```

**面试怎么用**：

> "并发取消这块有个我很欣赏的设计 —— 墓碑。
>
> 场景是：并行调三只 Agent，用户在路由层还没走到第三只的时候就取消了它。
> 如果取消是直接删 slot，路由层走到第三只时拿不到它的 signal，
> 会回退到批次级的 signal —— 那个还没被 abort，于是它照样跑起来了。
>
> 解法是取消不删 slot，标记成 `canceled` 墓碑。
> 墓碑对判忙来说是'不存在'（不阻塞新调用），
> 对取信号来说是'存在'（能拿到已 abort 的 controller）。
> **同一个数据结构对不同的查询呈现不同的存在性** —— 我觉得这个抽象很干净。"

### 3.4 队列条目：一个字段清单就是一份需求史

`QueueEntry` 的字段【源码】，每个字段背后是一个需求：

```ts
export interface QueueEntry {
  id: string;
  threadId: string;
  userId: string;
  idempotencyKey?: string;          // ADR-008 D2：防重复
  content: string;
  messageId: string | null;
  mergedMessageIds: string[];       // 连续消息合并
  source: 'user' | 'connector' | 'agent';   // ★ 公平性闸门靠它
  targetCats: string[];
  intent: string;
  status: 'queued' | 'processing';
  createdAt: number;
  processingStartedAt?: number;      // stale-processing TTL
  autoExecute: boolean;              // ★ ADR-018：A2A 不需要用户批准
  callerCatId?: string;              // 谁发起的（A2A 显示用）
  senderMeta?: { id: string; name?: string };   // 群聊里的真实发送者
  priority: 'urgent' | 'normal';
  sourceCategory?: 'ci' | 'review' | 'conflict' | 'scheduled'
                 | 'a2a' | 'continuation' | 'issue' | 'freshness';   // 视觉分组
  continuationKey?: string;          // 控制流去重
  position?: number;                 // ★ 用户拖拽排序，覆盖 priority
  suggestedSkill?: string;           // connector 触发时的 skill 提示
  callerTraceContext?: CallerTraceContext;   // 分布式追踪
  a2aTriggerMessageId?: string;      // 回复线程化
}
```

**三个字段特别值得讲：**

**① `source: 'user' | 'connector' | 'agent'`**

公平性闸门就靠它【源码】：

```ts
/** F185 Phase B: non-agent fairness gate for text-scan A2A — user + connector block, agent does not. */
```

大白话：队列里有 **user** 或 **connector**（飞书/企微）的消息在等，
就不许展开新的 A2A 跳转；有 **agent** 的消息在等，不挡。

**为什么 agent 不挡？** 因为如果挡，A2A 链会互相阻塞 ——
A 排队等 B，B 排队等 A，死锁。

**② `autoExecute: boolean`**

【ADR】ADR-018 OQ-1 的产物：

> **决定**：A2A callback 产生的任务入 InvocationQueue，
> 但标记为 `auto-execute`，系统自动执行不需要用户批准。

**这个字段是"既要可见又要自动"的关键。**
A2A 任务进队列是为了让用户看得见、能插队；
标 `autoExecute` 是为了不需要用户点确认。

**③ `position?: number`**

```ts
/** F175: user drag-reorder position — explicit values override priority in dequeue */
```

**用户拖拽的顺序覆盖系统的优先级。**
这是个产品判断：系统的优先级只是建议，人的意图更高。

### 3.5 QueueProcessor 里的四个状态表

```ts
private processingSlots = new Map<string, number>();      // 哪些 slot 正在处理
private pausedSlots = new Map<string, 'canceled' | 'failed'>();   // 哪些暂停了
private pauseEpoch = new Map<string, number>();            // 暂停的世代号
private suppressedAutoResume = new Map<string, number>();   // 抑制自动恢复
private static readonly SUPPRESS_TTL_MS = 60_000;
private continuationWindows = new Map<string, number[]>();  // 续跑限流
private static readonly CONTINUATION_WINDOW_MS = 60 * 60 * 1000;
private static readonly MAX_CONTINUATIONS_PER_WINDOW = 5;
```

**`MAX_CONTINUATIONS_PER_WINDOW = 5` 值得单独说。**

这是"会话续跑"的限流：一小时内同一个 key 最多续跑 5 次。

**为什么需要？**【推断】
会话封存后会自动续跑（见 [模块 08](08-模块-会话与抗压缩.md)）。
如果续跑本身又立刻触发封存（比如 bootstrap 太大，一注入就超阈值），
就会形成"封存 → 续跑 → 封存"的死循环。**限流是最后一道保险。**

**`pauseEpoch` 世代号也是个经典手法**【推断】：
暂停/恢复有并发风险 —— 旧的恢复请求可能在新的暂停之后到达。
带世代号就能判断"这个恢复请求是针对哪次暂停的"，过期的直接丢。

（和 [模块 10](10-模块-球权状态机.md) 里 `ball.hold_expired`
要求 `payload.fireAt` 匹配 `snapshot.heldUntil` 是同一个模式：
**用版本/时间戳区分新旧事件。**）

### 3.6 僵尸清扫

```ts
private sweepZombieSlots(threadId: string): void { ... }
```

以及独立文件：

```
reconcileZombies.ts        运行中的僵尸回收
StartupReconciler.ts       启动时对账
getThreadLiveInvocations.ts  1122 行 —— 判定"这个 thread 到底有几个活的调用"
```

`getThreadLiveInvocations.ts` 有 1122 行，说明**"到底谁还活着"这个问题非常难答**。
里面有一段注释【源码】：

```ts
 *  detectCatSlotReuseZombie used to rely on tracker, but now classifies via fresh drafts only —
```

**"used to rely on tracker, but now…"** 说明判定依据换过 ——
从"tracker 里有没有"改成"有没有新的 draft 产出"。

**为什么改？**【推断】
因为 tracker 里的记录可能是陈旧的（进程已死但记录还在）。
"有没有新内容产出"是**行为证据**，比"状态表里写着什么"可靠。

**这是个通用的分布式系统教训**：
判活要看**行为**（心跳、产出），不要看**声明**（状态表）。

### 3.7 `invokeSingleCat` 的九个阶段

```ts
export async function* invokeSingleCat(
  deps: InvocationDeps,
  params: InvocationParams,
): AsyncIterable<AgentMessage>
```

**是 async generator，不是 Promise** —— 边跑边吐，前端有实时流。

```
① cloud-only 短路      provider === 'openai-chatgpt-pro' → 走桥不 spawn
② 凭据与账号解析        resolveForClient / resolveBoundAccountRefForCat
③ session 解析          新开还是 --resume
④ workingDirectory     项目根 / worktree / bootcamp workspace
⑤ 环境变量注入 ★        CAT_CAFE_INVOCATION_ID / CALLBACK_TOKEN / git identity
⑥ MCP 配置             写配置文件让 CLI 连上 mcp-server
⑦ spawn 子进程
⑧ 事件解析 → yield      provider parser 把原生格式转成 AgentMessage
⑨ 终态 + 审计 + 遥测    CAT_RESPONDED / CAT_ERROR
```

**职责边界写在文件头**【源码】：

```
 * 不处理: system prompt 构建（由调用方负责 prepend）、
 *         消息存储（由调用方在 yield 后累积并存储）。
```

**为什么 prompt 组装不在这里？** 因为 prompt 里有
"你是第 1/2 棒""队友是 codex""前一棒说了什么"——只有路由层知道。

**一个有意思的细节**：`isLastCat` 参数在串行路径里永远传 `false`【源码】：

```ts
// Always pass isLastCat:false — we set isFinal AFTER A2A detection
```

**因为跑之前不知道这只 Agent 会不会 @ 出下一只。**
等回复解析完、A2A 检测跑完，才能回头标记 `isFinal`。

### 3.8 为什么这个文件有 3599 行

四个原因叠加：

| 原因 | 说明 |
|------|------|
| ① 六种 provider 的差异要收敛 | session 恢复语义、MCP 配置写法、超时策略各不同 |

**面试可以这么讲这个文件**：

> "`invoke-single-cat.ts` 有 3599 行，而项目自己的规范写着
> '200 行警告 / 350 行硬限制'—— 超了十倍。
> 他们有个 tech debt feature（F219）在跟这件事。
>
> 但我觉得这个文件的'臃肿'是有信息量的：它诚实地展示了
> **接一个 Agent CLI 到底要处理多少现实**。
> 六种 provider 的差异、十几个可选依赖的 fail-open、
> 十个遥测指标、还有每一次 review 留下的防御分支。
>
> 如果让我拆，我会按'阶段'横切成一条显式 pipeline，
> 而不是按功能纵切 —— 因为九个阶段的顺序是固定的，
> 差异只在每个阶段的具体实现。
> 但我要说清楚风险：这个文件里每个防御分支都对应一个真实事故，
> 重构前必须先把测试补到能覆盖那些 edge case。"

## 4. 为什么这么设计

### 决策 A：为什么要 InvocationRecord 这层抽象

【ADR】ADR-008 的 D1 决策：

> 引入 `InvocationRecord`，将"消息写入"与"猫调用执行"解耦。
>
> ```typescript
> type InvocationStatus = 'queued' | 'running' | 'succeeded' | 'failed' | 'canceled';
> ```

**解耦带来三个能力**：

```
① 失败可以单独重试（消息已经写了，只重跑执行）
② cursor 只在 succeeded 时推进（失败不会让增量投递错位）
③ 有了"调用"这个一等公民，才能挂 token、挂 abort、挂遥测
```

**第③点是我认为最重要的**【推断】：
`invocationId` 后来成了 MCP 回调的鉴权凭据（[模块 13](13-模块-MCP回调桥.md)）、
成了球权状态机的事件主体（[模块 10](10-模块-球权状态机.md)）、
成了连续性胶囊的字段（[模块 08](08-模块-会话与抗压缩.md)）。

**一个抽象引入之后长出了三个下游能力 —— 这是抽象选对了的标志。**

### 决策 B：为什么幂等键的 scope 是 `(threadId, userId)`

【ADR】ADR-008 的图里写了 `IdempotencyKey (D2) 防重复写入 (threadId,userId)`。

【推断】为什么不是全局唯一？
因为幂等的语义是"同一个用户在同一个帖子里的同一次提交"。
全局唯一会让不同用户的相同 key 互相干扰。

### 决策 C：为什么队列按 `(threadId, userId)` 分片，出队却跨用户

```
分片按用户  →  一个用户塞满队列不影响别人（隔离）
出队跨用户  →  整体 FIFO 公平（公平）
```

**这是"隔离"和"公平"的经典组合。**

## 5. 否掉了哪些方案

### 方案一：原地编辑消息（不分支）

**【ADR】ADR-008 否决理由：**

> **备选方案 A**：原地编辑消息（不分支）
> 不选原因：会破坏 cursor 单调假设与多猫 session 一致性，
> 重放和审计链条会断裂。

**用大白话解释这个问题**：

```
每只 Agent 有自己的"读到哪了"游标（增量上下文投递靠它）
  opus 的游标：读到 msg-5
  codex 的游标：读到 msg-3

用户原地编辑了 msg-4
  → opus 已经读过 msg-4 的旧版本，它的记忆里是旧的
  → codex 还没读到，它会读到新版本
  → 两只 Agent 对同一条消息有不同的认知
```

**所以编辑改成了"分叉出一个新 thread"** —— 原 thread 不可变。

**面试可以这么讲**：

> "消息编辑他们做成了 fork 而不是原地改。
> 原因是每只 Agent 有自己的增量投递游标 ——
> 原地编辑会导致'已经读过的 Agent'和'还没读到的 Agent'
> 对同一条消息有不同的认知。
> **在多 Agent 系统里，消息历史的不可变性是一致性的基础。**
> 这个约束在单 Agent 系统里不存在，因为只有一个读者。"

### 方案二：只加幂等键，不引入 InvocationRecord

**【ADR】否决理由：**

> **备选方案 B**：只加幂等键去重，不引入 InvocationRecord
> 不选原因：只能缓解重复消息，无法表达调用生命周期、
> 失败补偿与可重试边界。

**这是个很好的"为什么不用最小改动"的例子**：
幂等键能解决"重复写入"，但解决不了"写入成功了但执行失败了"。
两者是不同的问题。

### 方案三：强一致的级联删除

**【ADR】这是 ADR-007 的内容：**

> **备选方案 A**：强一致删除（全部成功才返回成功）
> 不选原因：会把非关键存储抖动放大成用户可见失败，
> 删除体验脆弱且恢复成本高。
>
> **备选方案 B**：Lua/MULTI 跨存储原子事务
> 不选原因：现有数据跨多 Store/多 key 结构，
> 事务改造复杂且无法覆盖所有实现路径。
>
> **备选方案 C**：删除即触发后台补偿任务（必做）
> 不选原因：会引入新的调度系统和观测面，当前阶段收益低于复杂度成本。
>
> **不做边界**：本轮不承诺强一致与即时零孤儿，
> 仅保证 best-effort 删除 + TTL 兜底收敛。

**"best-effort + TTL 兜底"这个组合值得学**：
不追求立刻零孤儿，靠 TTL 让孤儿自然过期。
**用时间换复杂度。**

### 方案四：thread 级判忙

见 §3.2，【ADR】ADR-018 OQ-4 明确否决。

### 方案五：进程池

【ADR】ADR-001 的"不做边界"：

> **不做边界**：本轮不引入进程池和统一守护进程优化，
> 启动性能优化留到后续独立议题。

**这是"知道但故意不做"** —— 面试里讲这个比讲"他们没考虑"强得多。

## 6. 如果重新设计

【推断】以下全是我的方案。

### 6.1 把调用生命周期做成显式的事件溯源

**现在的问题**：状态散在多处。

```
InvocationRecord.status        queued/running/succeeded/failed/canceled
InvocationTracker slot         active/canceled(墓碑)/absent
QueueEntry.status              queued/processing
QueueProcessor.processingSlots
QueueProcessor.pausedSlots + pauseEpoch
球权状态机                       new/active/blocked/parked/dead/void/zombie/resolved
```

**六套状态表描述同一件事的不同侧面。**
它们之间的一致性靠代码互相调用维护 —— 所以有 `ensureTerminalStatus.ts`、
`reconcileZombies.ts`、`StartupReconciler.ts` 这些对账逻辑。

**我的方案**：一份 append-only 的事件日志作为唯一真相源，
所有状态表都是它的**投影**。

```
invocation_events (append only)
  ├─ invocation.enqueued
  ├─ invocation.started
  ├─ invocation.heartbeat
  ├─ invocation.output_chunk
  ├─ invocation.canceled
  ├─ invocation.failed
  └─ invocation.completed
       │
       ├──→ 投影 1：当前状态（给 UI）
       ├──→ 投影 2：slot 占用（给判忙）
       ├──→ 投影 3：球权状态（模块 10 已经是这个模式了）
       └──→ 投影 4：审计日志
```

**为什么我有信心这个方向对？**
因为**球权状态机已经是这个模式了** ——
它有 `BallCustodyEventLog` + `BallCustodyProjector` + `BallCustodyProjectionStore`。
**项目自己在最新的模块上选了事件溯源，只是老模块还没迁。**

**收益**：
- 一致性问题从"六套表互相对账"变成"投影是否幂等"
- 重启恢复变成"重放事件"，不需要专门的对账器
- 调试变成"看事件流"，不需要拼多个状态表

**代价**（必须说）：
- 事件日志会增长，需要归档策略
- 投影延迟（最终一致），UI 可能短暂看到旧状态
- 迁移风险高（六套状态表的读写点遍布全项目）

### 6.2 队列改成能横向扩展的形态

**现在的问题**：`QueueProcessor` 的状态在进程内存里
（`processingSlots`、`pausedSlots`、`continuationWindows` 都是 `Map`）。
**这意味着单进程，扩不了。**

**我的方案**（如果要做多实例）：

```
状态外移到 Redis：
  processing slot   → Redis SETNX + TTL（天然的分布式锁）
  paused slot       → Redis Hash
  continuation 窗口  → Redis ZSET（按时间戳，天然滑动窗口）

出队改成：
  Redis Stream + consumer group
  → 多个 API 实例竞争消费
  → 天然的 at-least-once + ack
```

**但我要明确说：现在不做是对的。**
因为这是个**本地优先的桌面应用**，Redis 都是可选的（有内存模式）。
为了扩展性上分布式队列，会让单机部署变复杂 —— 那是它的主场景。

**面试里这么说**：

> "现在的队列是单进程状态，横向扩展不了。
> 但我认为现在不做是对的 —— 它是本地优先的桌面应用，
> Redis 都是可选的。为了扩展性上分布式队列会让主场景变复杂。
>
> 如果要做云端多租户版，我会把 processing slot 换成 Redis SETNX + TTL、
> 续跑限流窗口换成 ZSET、出队换成 Redis Stream 的 consumer group。
> 这三个替换刚好对应现在的三个内存 Map，映射很干净。"

### 6.3 给"卡死"加分级超时

**现在的问题**：超时策略是 per-CLI 的固定值（`resolveCliTimeoutMs`）。
但"卡死"有很多种：

```
① 进程起不来（ENOENT）        → 秒级就能判定
② 进程起来了但没任何输出       → 需要等，但不用等满
③ 有输出但停了很久            → 可能在跑长命令，也可能真卡了
④ 一直有输出但不收敛           → 最难判，可能在死循环
```

**我的方案**：分级探测。

```
无任何输出          → 30s 判死（起不来的话早就报错了）
有输出后静默         → 5min 判可疑，发心跳询问，10min 判死
持续输出但超总时长    → 软提醒（往 prompt 注入"你已经跑了 40 分钟"）
                     → 让 Agent 自己收尾，而不是硬杀
```

**为什么最后一条重要？**
硬杀会丢掉 Agent 已经做的工作（可能改了一半的文件）。
让它自己收尾能拿到一个交接摘要。
**这和项目自己的"先劝后拦"原则一致。**

### 6.4 我不会改的

| 我原本的想法 | 为什么放弃 |
|------------|-----------|
| 用外部 MQ（Kafka/RabbitMQ） | 队列语义太特殊（slot 判忙、用户插队、公平性闸门），通用 MQ 表达不清；而且桌面部署装不了 |
| 合并 Tracker 和 Queue | "谁在跑"和"谁在等"是两个不同的生命周期，合并会让判忙逻辑更绕 |
| 去掉墓碑，改成取消时同步等待 | 同步等待会阻塞路由层；墓碑是异步友好的正确解 |
| 上进程池 | 会话隔离 + 状态污染 + 健康检查，复杂度不比现在小；轻活走 API 直连更聪明（见模块 02 §7.2） |

## 7. 和其他模块怎么咬合

### 上游（谁创建调用）

```
routes/messages.ts                用户发消息
routes/callback-a2a-trigger.ts    Agent 交接
routes/callback-multi-mention-*   多方询问
QueueProcessor.executeEntry()     队列出队
infrastructure/connectors/*       外部平台
infrastructure/scheduler/*        定时任务
```

**六个入口，全部汇聚到 `AgentRouter` → `invokeSingleCat`。**
这就是 ADR-018 说的"统一执行通道"。

### 下游（调用产生什么）

```
invokeSingleCat
  ├─ AgentMessage 流 ─────→ 路由层累积 → messageStore → WebSocket
  ├─ invocationId + token ─→ 环境变量 → 子进程 → MCP server → 回调（模块 13）
  ├─ 球权事件 ─────────────→ BallCustodyIngest（模块 10）
  ├─ session 健康度 ───────→ SessionSealer 判断要不要封存（模块 08）
  ├─ 遥测 ─────────────────→ 10 个指标 + OTel span
  └─ 审计 ─────────────────→ EventAuditLog
```

### 一根特别关键的线：环境变量

```
invokeSingleCat 阶段⑤
  CAT_CAFE_INVOCATION_ID = <id>
  CAT_CAFE_CALLBACK_TOKEN = <token>
        │
        ▼ 传给子进程 env
   claude 子进程
        │
        ▼ 子进程拉起 MCP server 时继承 env
   mcp-server 进程
        │
        ▼ process.env 读出来，作为 HTTP 头
   X-Invocation-Id / X-Callback-Token
        │
        ▼
   callback-auth-prehandler 校验
        │
        ▼ 通过后 decorate 到 request
   request.callbackAuth = InvocationRecord
        │
        ▼ 各个 callback 路由用它确定
   "这是哪只 Agent、在哪个帖子、代表哪个用户"
```

**这条链是整个"回程通路"的地基**，而它的起点是
`InvocationRecord` 这个抽象（ADR-008 D1 的产物）。

**面试可以这么串**：

> "ADR-008 引入 `InvocationRecord` 的初衷只是'失败能单独重试'。
> 但这个抽象后来长出了三个下游能力：
> 它的 id 成了 MCP 回调的鉴权凭据、
> 成了球权状态机的事件主体、
> 成了会话连续性胶囊的字段。
>
> **我觉得这是判断抽象选得对不对的一个信号** ——
> 好的抽象会被后来的需求反复复用，而不是只服务当初那个动机。"

### 和会话模块的双向咬合

```
invokeSingleCat 读 session 策略
  → 决定新开还是 --resume
  → 决定阈值多少要封存

调用过程中上报 contextHealth
  → SessionSealer 判断超阈值
  → requestSeal()
  → 封存后 QueueProcessor.enqueueContinuation()
  → 续跑（带连续性胶囊）
  → 回到 invokeSingleCat（新 session）
```

**这是个环。** 所以有 `MAX_CONTINUATIONS_PER_WINDOW = 5` 的限流兜底 ——
防止"封存 → 续跑 → 又封存"的死循环。

## 8. 面试怎么讲

### 30 秒版

见 §0。

### 3 分钟版

> "他们把'调一次模型'做成了一个有生命周期的对象。
> 【ADR】动因很具体：原来消息写入和 Agent 调用在同一个 async 里，
> 调用失败没法单独重试；而且没有幂等键，网络重试就产生重复消息。
> 所以引入了 `InvocationRecord`，状态机是
> queued → running → succeeded/failed/canceled，
> 而且 cursor 只在 succeeded 时推进。
>
> 三个组件分工：`InvocationTracker` 管'谁在跑'，
> `InvocationQueue` 管'谁在等'，`QueueProcessor` 管出队。
>
> **最值得讲的是判忙的双层设计。**
> 入队看 slot 级 —— slot 是 `(threadId, catId)`，
> 所以你可以在 A 忙的时候顺手问 B。
> 但执行层是 thread 级串行的，因为同一个帖子的消息历史和球权状态是共享的。
> 用户感受到的是并行，实际执行是串行。
>
> 还有个我很欣赏的细节叫**墓碑**：
> 取消一只 Agent 时不删它的 slot，而是标记成 canceled。
> 因为并行场景下可能'路由层还没走到它就被取消了'——
> 如果删了 slot，路由层拿不到它的 abort signal，
> 会回退到批次级的信号，那个还没 abort，于是它照样跑起来了。
> 墓碑对判忙是'不存在'，对取信号是'存在'。
>
> 另外消息编辑他们做成了 fork 而不是原地改，
> 因为每只 Agent 有自己的增量投递游标 ——
> 原地编辑会让'读过的'和'没读到的'Agent 对同一条消息有不同认知。
> **多 Agent 系统里，消息历史的不可变性是一致性的基础。**"

### 常见追问

**Q：一个 Agent 卡死了怎么发现？**

> "现在是分层的：`cli-timeout` 算超时、`cli-supervisor` 监督、
> `ProcessLivenessProbe` 探活、`reconcileZombies` 回收。
> 还有个 `getThreadLiveInvocations.ts` 有 1122 行，
> 专门回答'这个帖子到底有几个活的调用'——
> 这个文件的长度本身就说明这个问题很难答。
>
> 里面有个注释我印象很深：
> `detectCatSlotReuseZombie used to rely on tracker, but now classifies via fresh drafts only`——
> 判活依据从'tracker 状态表里有没有'改成了'有没有新的产出'。
> **判活要看行为，不要看声明** —— 因为状态表可能是陈旧的。
>
> 如果让我改，我会加分级超时：
> 完全没输出 30 秒判死；有输出后静默 5 分钟判可疑、10 分钟判死；
> 一直有输出但超总时长的话不硬杀，而是往 prompt 注入
> '你已经跑了 40 分钟'让它自己收尾 ——
> 硬杀会丢掉它改了一半的文件。"

**Q：API 重启，正在跑的调用怎么办？**

> "两部分。
>
> **状态**能恢复：invocation 记录持久化在 Redis
> （`RedisAuthInvocationBackend` 的注释写了
> `Restart-resilient: API process exit / deploy / crash no longer drops active…`），
> 启动时有 `StartupReconciler` 对账，把遗留的 running 清理成终态。
>
> **进程**恢复不了：父进程死了子进程会被回收。
> 所以恢复的是一致性，不是'继续跑'。
> 真要继续得靠会话恢复重新调一次 —— 用 `--resume` + 连续性胶囊。
>
> 队列那边的状态更麻烦：`processingSlots`、`pausedSlots`
> 都是进程内的 `Map`，重启就丢。有个 `sweepZombieSlots` 兜。
> 我会把这些外移到 Redis —— processing slot 用 SETNX + TTL，
> 天然就是分布式锁，重启也不丢。"

**Q：为什么不用 Kafka / RabbitMQ？**

> "三个理由。
>
> 一，**队列语义太特殊**：需要 slot 级判忙、需要用户拖拽插队、
> 需要公平性闸门防 A2A 饿死用户消息、需要 `autoExecute` 区分
> '要不要人批准'。这些用通用 MQ 表达出来会比自己写更绕。
>
> 二，**部署形态不允许**：这是个有 Windows/macOS 安装包的桌面应用，
> 普通用户双击就用。Redis 都是可选的（有 `--memory` 模式），
> 要求装 Kafka 门槛就爆炸了。
>
> 三，**没有跨进程需求**：现在是单进程，MQ 的价值发挥不出来。
>
> 但如果做云端多租户版我认为必须换 —— 那时候的瓶颈完全不同。"

**Q：`invoke-single-cat.ts` 3599 行，怎么看？**

见 §3.8 的面试话术。

## 9. 本模块要点

| 要点 | 内容 |
|------|------|
| **【ADR】三个动因** | 无幂等性 / 无执行状态 / 消息不可变是全局假设 |
| **InvocationRecord** | queued→running→succeeded/failed/canceled；cursor 只在 succeeded 推进 |
| **三组件分工** | Tracker 管跑、Queue 管等、Processor 管出队 |
| **判忙双层** | 入队 slot 级（宽松）+ 执行 thread 级（严格） |
| **墓碑** | 取消不删 slot；对判忙"不存在"，对取信号"存在" |
| **公平性靠 source 字段** | user/connector 挡 A2A，agent 不挡（否则死锁） |
| **autoExecute** | 既要可见（进队列）又要自动（不用批准） |
| **用户拖拽覆盖优先级** | 系统优先级只是建议 |
| **续跑限流 5/小时** | 防"封存→续跑→又封存"死循环 |
| **判活看行为不看声明** | 从 tracker 状态改成 fresh drafts |
| **编辑改成 fork** | 多 Agent 的增量游标要求历史不可变 |
| **【ADR】否掉强一致删除** | best-effort + TTL 兜底，用时间换复杂度 |
| **我的改进** | 事件溯源统一六套状态表 / 状态外移 Redis 以便扩展 / 分级超时 + 软收尾 |
