# 10 · 模块：球权状态机

> 这个模块回答一个很小但很难的问题：**这个任务现在归谁？**
>
> 听起来像加个 `ownerId` 字段就完了。实际上它是一个
> **8 状态 × 17 事件、要求全覆盖、纯函数 + 事件溯源**的状态机。
>
> 而且它是全项目里**架构最现代**的模块 ——
> 事件日志 + 投影器 + 投影存储，标准的 event sourcing。
> 我在 [模块 05](05-模块-调用生命周期.md) 提的重构方向，就是让老模块学它。

---

## 0. 30 秒电梯版

> "多 Agent 协作里最容易出的问题不是'谁做错了'，而是'**没人在做**'——
> A 以为交给 B 了，B 以为 A 还在弄，任务就悬在那儿。
>
> 他们把'球权'做成了一个显式状态机：8 个状态、17 种事件，
> 而且要求 **8×17=136 格每一格行为确定**（转移或显式拒绝），穷举测试钉死。
>
> 架构是标准的事件溯源：事件日志 append-only、
> 投影器纯函数（`apply(event) = 读投影 → transition → 存`）、
> rebuild 就是 delete + replay，而且要求逐字段一致（无漂移）。
>
> 三个状态名很能说明它在防什么：
> `zombie`（进程活着但没心跳）、`dead`（异常终止）、
> `void`（球传给了不存在的接收方 —— 他们叫'虚空传球'）。"

---

## 1. 它解决什么问题

### 核心问题：任务悬空

```
布偶猫："这块我改完了，缅因猫应该可以开始 review 了"
缅因猫：（没有收到 @，不知道该开工）
用户： （以为它们在协作，等着）

结果：任务悬在那儿，谁都没在做。
```

**这个失败模式在人类团队里靠"站会"发现，在 Agent 团队里没人会发现** ——
Agent 不会主动问"这个任务是不是卡住了"。

### 四类具体场景

```
① 球传给了不该传的人      → 传给一个不可用/不存在的 Agent
② 球传出去了但没人接      → 上面那个例子（状态描述不是球权声明）
③ 持球的 Agent 卡死了      → 进程还在但没心跳
④ 球在等外部条件          → 等 CI、等用户回复、等另一个 PR
```

**第 ④ 类最有意思**：任务不是"卡住"了，是"合理地在等"。
需要区分这两种，否则会误报。

## 2. 不做会怎样

### 场景 A：只用一个 `ownerId` 字段

```
task.ownerId = 'codex'
  → 但 codex 到底知不知道这事？
  → 它是"正在做"还是"还没开始"还是"卡住了"？
  → 一个字段答不了
```

### 场景 B：不区分"卡住"和"在等"

```
如果把"等 CI"也算卡住：
  → 每次等 CI 都告警 → 告警疲劳 → 没人看告警了

如果把"卡死"也算在等：
  → 卡死的任务永远不被发现
```

### 场景 C：没有"虚空传球"检测

```
布偶猫："@nonexistent-cat 帮我看下"
  → 路由失败（那只 Agent 不存在/不可用）
  → 但布偶猫已经"交出去"了，它不会继续跟进
  → 球掉在地上
```

**项目专门给这个起了名字叫"虚空传球"（void pass）**，
说明它真实发生过。

### 场景 D：定时器 bug 导致状态翻烧饼

```
T1  设置 hold（等 2 小时），起一个 2 小时后的 reminder
T2  hold 提前解除，重新设置 hold（等 4 小时），起新 reminder
T3  【2 小时后】旧 reminder 触发 → 误以为 hold 到期 → 把新 hold 杀了
```

**这是所有基于定时器的状态机都会踩的坑。**

## 3. 怎么设计的

### 3.1 事件溯源架构

```
┌────────────────────────────────────────────────────────┐
│  BallCustodyEventLog（append-only）                     │
│  事件永不删除；事件是 facts，immutable                    │
└──────────────┬─────────────────────────────────────────┘
               │ 消费
               ▼
┌────────────────────────────────────────────────────────┐
│  BallCustodyProjector                                   │
│  apply(event) = 读 projection → transition() →           │
│                 字段 effect + save                       │
│  rebuild = delete + replay                              │
│  ★ 零外部副作用                                          │
└──────────────┬─────────────────────────────────────────┘
               ▼
┌────────────────────────────────────────────────────────┐
│  BallCustodyProjectionStore（当前状态，给 UI 和查询用）    │
└────────────────────────────────────────────────────────┘

旁路（不在投影路径上）：
  BallCustodyProbeScheduler   定期探测外部条件
  BallCustodyWakeSender       条件满足 → 唤醒持球 Agent
```

**投影器的"零副作用"约束写得很清楚**【源码】：

```
 * **零外部副作用**（plan §E）：projector 只做纯状态投影 + store.save，
 * 绝不做唤醒投递等外部副作用（那些在 ProbeScheduler/WakeSender 的实时 tick 路径，
 * rebuild 不重发）。
```

**为什么这条约束是必须的？**

```
如果投影器会发唤醒消息：
  → rebuild（replay 全部历史事件）时
    → 会把历史上所有的唤醒重发一遍
      → 用户收到几百条"球回到你手上了"
```

**"rebuild 不重发"是事件溯源的一条基本纪律**，
而这个模块把它写成了显式约束。

**面试话术**：

> "投影器有个明确约束：**零外部副作用**。
> 它只做'读投影 → 状态转移 → 存回去'，绝不发唤醒消息。
>
> 因为 rebuild 是 delete + replay 全部历史事件。
> 如果投影器会发消息，rebuild 时会把历史上所有唤醒重发一遍 ——
> 用户收到几百条'球回到你手上了'。
>
> 所以唤醒投递在另一条路径上（ProbeScheduler / WakeSender 的实时 tick），
> 那条路径不参与 replay。
> **这是事件溯源的基本纪律，但很多实现会踩这个坑。**"

### 3.2 四条不变量

```
 * Invariants:
 *  - 事件永不从 log 删除（事件 facts immutable）。
 *  - rejected transition 记 lastRejectedEvent（仅 state-changing），不改 state（INV-5）。
 *  - informational reject（ball.wake_sent 非 blocked）不记 lastRejectedEvent（不污染 observability）。
 *  - rebuild(replay) 得逐字段相同 projection（INV-2，无漂移）。
```

**第二和第三条的区分很讲究：**

```
事件分两类（classification 字段）：
  state-changing   会改状态的（ball.handed、task.done…）
  informational    只是通知的（ball.wake_sent…）

被拒绝时：
  state-changing 的拒绝  → 记 lastRejectedEvent（这是异常，要能观测）
  informational 的拒绝   → 不记（这是正常的，记了会污染观测数据）
```

**例子**：`ball.wake_sent` 事件到了，但球当前不是 `blocked` 状态 ——
这是正常的（可能刚好被别的事件解除阻塞了），不该记成"异常拒绝"。

**"不污染 observability"** —— 这是个很成熟的判断。
**告警/观测数据里混进正常情况，就等于没有观测。**

**第四条"rebuild 得逐字段相同"是事件溯源的核心正确性条件**：
replay 出来的状态必须和增量算出来的完全一致，否则就有漂移。

### 3.3 8 状态 × 17 事件

```ts
export const ALL_BALL_STATES: BallState[] = [
  'new',        // 刚创建
  'active',     // 有人在做
  'blocked',    // 在等外部条件
  'parked',     // 主动搁置
  'dead',       // 异常终止
  'void',       // 虚空传球（传给了不存在的接收方）
  'zombie',     // 进程活着但没心跳
  'resolved',   // 完成
];

export const ALL_BALL_EVENT_KINDS: BallCustodyEvent['kind'][] = [
  // 球权转移
  'ball.handed', 'ball.handed_cvo', 'ball.void_pass', 'ball.held', 'ball.hold_expired',
  // 调用生命周期（来自模块 05）
  'invocation.started', 'invocation.heartbeat', 'invocation.died',
  // 任务状态
  'task.blocked', 'task.unblocked', 'task.idle_long', 'task.done',
  // 唤醒
  'ball.wake_sent', 'ball.wake_condition_met',
  // Phase C 安乐死
  'ball.frozen', 'ball.degraded', 'ball.abandoned',
];
```

**完整性要求写在文件头**【源码】：

```
 * INV-10（完整性）：全 8 state × 17 event 的每格行为确定（转移 or 显式 reject），穷举测试钉死。
```

**136 格，每一格都要有明确行为。**

**面试话术**：

> "他们要求 8 个状态 × 17 个事件 = 136 格**每一格行为确定**——
> 要么是合法转移，要么是显式拒绝，不能有'没考虑到'的格子。
> 而且用穷举测试钉死。
>
> 我觉得这个要求很关键。状态机最容易出的 bug 不是'转移写错了'，
> 而是'某个状态收到某个事件时没人想过会怎样'——
> 于是它可能静默忽略、可能崩溃、可能进入非法状态。
>
> **穷举覆盖把'没想过'变成了编译期/测试期的错误。**"

### 3.4 三个状态名对应三种真实失败

| 状态 | 什么时候进 | 为什么需要单独一个状态 |
|------|-----------|-------------------|
| `zombie` | 进程还活着但没心跳 | 和 `dead` 不同 —— 可能还能救（迟到心跳） |
| `dead` | 调用异常终止 | 明确死了，要重新派 |
| `void` | 球传给了不存在/不可用的接收方 | "虚空传球"—— 球掉在地上，没人知道 |

**`void` 这个状态是我觉得最有洞察的**：

```
一般系统的处理：路由失败 → 报错 → 结束
这个系统的处理：路由失败 → 球进入 void 状态 → 有人要负责把它捡起来
```

**区别在于"失败"和"责任真空"是两回事。**
报个错就完了的话，任务确实还在那儿没人做。

对应的检测代码在 `void-hold-detect.ts`（路由层）。

### 3.5 两个精细的守卫

**守卫一：迟到心跳的宽限期**

```ts
/** 死球迟到心跳 grace（复用 F194/Phase A DEAD_BALL_ZOMBIE_GRACE_MS=600s）。 */
export const DEAD_BALL_ZOMBIE_GRACE_MS = 600_000;   // 10 分钟
```

```
 * - invocation.heartbeat from dead：迟到心跳 grace
 *   （died.at < hb.at ≤ died.at+GRACE，died.at=lastStateChangeAt）
```

**大白话**：判死之后 10 分钟内收到的心跳，算"迟到"不算"复活"。

**为什么？** 网络抖动、进程调度延迟都可能让心跳晚到。
如果一收到心跳就复活，状态机会在 dead ↔ active 之间翻烧饼。

**守卫二：`fireAt` 匹配防旧定时器误杀**

```
 * - ball.hold_expired：需 payload.fireAt 匹配 snapshot.heldUntil，
 *   防旧 reminder 误杀新 hold
```

**这就是 §2 场景 D 那个坑的解法**：

```
事件携带它当初约定的 fireAt
  → 到达时和当前的 heldUntil 对比
    → 对不上就丢弃（说明这是个过期的定时器）
```

**这个模式在 [模块 05](05-模块-调用生命周期.md) 也出现了**——
`QueueProcessor.pauseEpoch`（暂停世代号）是同一个思路：
**用版本/时间戳区分新旧事件。**

**面试话术**：

> "有两个守卫我觉得设计得特别细。
>
> 一个是**迟到心跳的宽限期**：判死之后 10 分钟内收到的心跳算迟到不算复活。
> 因为网络抖动会让心跳晚到，一收到就复活的话状态机会在 dead 和 active 之间翻烧饼。
>
> 另一个是 **`fireAt` 匹配**：hold 到期事件必须携带它当初约定的触发时间，
> 和当前的 `heldUntil` 对比，对不上就丢弃。
> 这防的是'旧定时器误杀新 hold'——
> 你设了个 2 小时的 hold，中途改成 4 小时，
> 旧的 2 小时定时器触发时不该把新的杀掉。
>
> **这是所有基于定时器的状态机都会踩的坑**，
> 解法是让事件携带它自己的身份标识。
> 同一个思路在他们的队列模块里也用了（暂停世代号）。"

### 3.6 复杂守卫拆成独立 resolver

```
 * 复杂守卫拆成独立 resolver：
 *   - ball.handed_cvo：payload.intent 三态（handoff→parked / done_notify→resolved / fyi→不变）
 *   - ball.hold_expired：需 payload.fireAt 匹配 snapshot.heldUntil
 *   - invocation.heartbeat from dead：迟到心跳 grace
```

**`ball.handed_cvo` 的三态很有意思**（cvo = co-creator，也就是人）：

```
Agent 把球传给人，但"传给人"有三种意思：
  handoff      → 我做完我的部分，交给你 → 球变成 parked（等人处理）
  done_notify  → 整件事完了，通知你一下 → 球变成 resolved
  fyi          → 就是告诉你一声 → 球状态不变（我还持球）
```

**这三态区分很重要**：如果不区分，Agent 每次跟人汇报进度
都会被当成"交出球权"，然后它自己就不干了。

**这和 [模块 07](07-模块-身份注入.md) 里跨帖提示的
`effectClass: 'fyi' | 'coordinate' | 'investigate' | 'assign_work'`
是同一个设计思路** —— **消息要声明它期待对方做什么。**

### 3.7 表驱动而不是 if 链

```ts
/**
 * 纯函数 — 零 IO、零 Redis、零副作用。照 community-state-machine 的**表驱动**模式
 * （TRANSITION_TABLE 而非 if-chain，降单函数 cognitive complexity）。
 * 调用方（projector）负责持久化 + 字段 effect（heldUntil/blockedSinceAt/lastWakeAt）。
 */
```

**为什么表驱动？**

```
if 链：
  136 个组合写成嵌套 if → 认知复杂度爆炸 → 漏格子很难发现

转移表：
  TRANSITION_TABLE[state][event] → 一眼能看出哪格是空的
  → 穷举测试可以直接遍历表
```

**而且注意"调用方负责持久化 + 字段 effect"** ——
状态机只算 `next state`，字段更新（`heldUntil`、`blockedSinceAt`、`lastWakeAt`）
留给投影器。

**这和 [模块 03](03-模块-路由与编排.md) 的
"副作用不进决策函数，否则纯函数变上帝函数"是同一条纪律。**

### 3.8 返回类型强制处理拒绝

```ts
export type BallTransitionReject = 'invalid_transition' | 'bad_payload';

export type BallTransitionResult =
  | { ok: true; next: BallState }
  | { ok: false; reason: BallTransitionReject };

const ok = (next: BallState): BallTransitionResult => ({ ok: true, next });
const reject = (reason: BallTransitionReject): BallTransitionResult => ({ ok: false, reason });
```

**不是抛异常，而是返回 `{ ok: false }`** ——
调用方必须显式处理拒绝，TypeScript 会逼它 narrow。

**而且拒绝原因分两类**：
`invalid_transition`（这个状态不接受这个事件）
vs `bad_payload`（事件本身格式不对）。

### 3.9 窄输入好测

```ts
/** transition 守卫只需 projection 的这几字段（窄输入，好测）。 */
export type BallTransitionSnapshot = Pick<BallCustodyProjection, 'heldUntil' | 'lastStateChangeAt'>;
```

**状态机不吃整个 projection，只吃它真正需要的两个字段。**

**为什么值得单独说？** 因为这让测试变成：

```ts
transition('dead', heartbeatEvent, { heldUntil: null, lastStateChangeAt: 1000 })
```

而不是要构造一个完整的 projection 对象（十几个字段）。

**"窄输入"是纯函数可测性的关键。** 面试里提一句能体现测试意识。

### 3.10 幂等键的一个细节

`ball-custody-events.ts` 的文件头有一段很实在的讨论【源码】：

```
 * §F 细化（B2 PR1，请 reviewer 确认）：handed 的 sourceEventId 在 `route:{messageId}` 基础上
 * **追加 `:{toCatId}`**——一条消息可行首 @ 多猫（`@catA @catB`），各产生一条独立 handed 事件；
 * 若只用 `route:{messageId}` 则第二只猫被全局 sourceEventId 去重静默吞掉。
 * void_pass 追加 `:void` 与 handed 区分（同一 messageId 理论互斥——evaluateVoidHold 在有
 * lineStartMention 时不触发——但显式后缀更防御）。
```

```ts
export function buildHandedEvent(input: HandedEventInput): BallCustodyEvent {
  return {
    sourceEventId: `route:${input.messageId}:${input.toCatId}`,   // ← 带上目标
    subjectKey: `ball:thread:${input.threadId}`,
    kind: 'ball.handed',
    classification: 'state-changing',
    payload: { toCatId: input.toCatId, ...(input.fromCatId ? { fromCatId: input.fromCatId } : {}) },
    at: input.at,
  };
}
```

**这个 bug 值得讲**：

```
一条消息 @ 了两只 Agent：@catA @catB
  → 产生两个 ball.handed 事件
    → 如果 sourceEventId 都是 route:{messageId}
      → 幂等去重会把第二个静默吞掉
        → catB 的球权事件丢了
```

**修法**：`sourceEventId` 追加目标 Agent id。

**而且 `void_pass` 也追加 `:void` 后缀**，
注释说"理论互斥但显式后缀更防御"——
**明知理论上不会撞，还是加了区分。这是对的偏执。**

**面试话术**：

> "有个幂等键的 bug 我觉得很典型。
> 球权转移事件的幂等键原来是 `route:{messageId}`。
> 但一条消息可以行首 @ 两只 Agent，产生两个独立的转移事件 ——
> 幂等去重就把第二个静默吞掉了，catB 的球权丢了。
>
> 修法是幂等键追加目标 Agent id。
>
> 更讲究的是：他们给 `void_pass` 事件也追加了 `:void` 后缀，
> 注释里写'理论互斥但显式后缀更防御'——
> 也就是说明知这两种事件理论上不会用同一个 messageId，还是加了区分。
>
> **我觉得这是对的偏执**。幂等键撞了是静默失败，
> 静默失败在事件溯源系统里特别难查 ——
> 因为你看日志会发现事件'确实被记录了'（第一个），
> 但状态就是不对。"

### 3.11 探针和唤醒（旁路）

```
BallCustodyProbeEvaluator     判断外部条件满足了吗
BallCustodyProbeScheduler     定期 tick
BallCustodyProbeTaskSpec      探针任务的定义
BallCustodyWakeSender         条件满足 → 发唤醒消息
```

唤醒消息长这样：

```ts
const content = [
  `${SCHEDULER_TRIGGER_PREFIX} 条件探针已满足，球回到 @${ownerCatId}：${input.task.title}`,
  input.task.why ? '' : undefined,
  input.task.why || undefined,
].filter(...).join('\n');
```

**注意 `@${ownerCatId}` —— 唤醒是通过发一条 @ 消息实现的。**

**这是个很聪明的复用**：不需要新的唤醒机制，
直接用现有的 @ 路由（[模块 04](04-模块-mention解析.md)）就行。

**而且有个 fail-fast**：

```ts
if (!ownerCatId) {
  throw new Error(`F233 PR4: cannot wake blocked task ${input.task.id} without ownerCatId`);
}
```

**没有 owner 就不能唤醒** —— 不猜、不默认给某只 Agent。

## 4. 为什么这么设计

### 决策 A：为什么用事件溯源而不是直接改状态

**取舍**：存储成本 + 复杂度 vs 可审计性 + 可重建。

【推断】理由：

```
球权的问题特点：
  ① 状态转移的"为什么"和"什么时候"都重要（要能审计"球什么时候掉的"）
  ② 多个来源写同一个状态（路由、调用生命周期、任务、定时器）
  ③ 逻辑会演进（Phase C 加了三个"安乐死"事件）

事件溯源的匹配点：
  ① 事件日志天然是审计日志
  ② 多来源写事件比多来源改状态安全（append 不会互相覆盖）
  ③ 加新事件不影响旧事件的语义
```

**第②点是我认为最关键的**：
如果是直接改状态，路由层和调用层可能并发写，谁后写谁赢。
append 事件不会有这个问题。

### 决策 B：为什么状态机是纯函数

**取舍**：多一层调用 vs 可穷举测试。

136 个格子要测，如果状态机要连 Redis，测试成本就爆了。
**纯函数 + 窄输入让 136 个格子可以直接遍历测。**

### 决策 C：为什么区分 `zombie` 和 `dead`

**取舍**：多一个状态的复杂度 vs 精确性。

```
如果合并成一个"失败"状态：
  → 迟到心跳的宽限期就没地方放了
    → 要么误杀（一判死就不接受心跳）
      → 要么误活（一收到心跳就复活，翻烧饼）
```

**`zombie` 是一个"可能还能救"的中间态**，
它的存在让宽限期这个机制有了落点。

## 5. 否掉了哪些方案

### 方案一：if 链而不是转移表

【源码】注释明确说了选表驱动的理由：

```
照 community-state-machine 的**表驱动**模式
（TRANSITION_TABLE 而非 if-chain，降单函数 cognitive complexity）
```

**而且提到了"照 community-state-machine"** ——
说明这是从另一个模块（F168 社区状态机）复用的模式。

【推断】**一个模式在项目里被复用第二次，是它被验证过的信号。**

### 方案二：投影器直接做副作用（发唤醒）

【源码】明确否决：

```
 * **零外部副作用**（plan §E）：projector 只做纯状态投影 + store.save，
 * 绝不做唤醒投递等外部副作用（那些在 ProbeScheduler/WakeSender 的实时 tick 路径，
 * rebuild 不重发）。
```

见 §3.1 的论证。

### 方案三：抛异常而不是返回 `{ ok: false }`

【推断】从类型设计看是刻意的。

**为什么返回值更好？**
拒绝转移是**正常业务情况**（很多格子就是"这个状态不接受这个事件"），
不是异常。用异常表达正常情况会导致：
① 调用方必须 try/catch 才能正确处理
② 拒绝原因难以类型化
③ 性能（异常栈）

### 方案四：引入独立的"球 ID"原语

【源码】注释里有痕迹：

```
 * subjectKey 遵 KD-1（从现有痕迹派生 ball:thread:{threadId}，不引入球 ID 新原语）
```

**"不引入球 ID 新原语"是个明确的决策。**

**大白话**：球权的主体标识不是新造一个 `ballId`，
而是从现有的 `threadId` 派生出 `ball:thread:{threadId}`。

【推断】为什么？因为新原语意味着：
① 要有地方创建/分配它
② 要维护它和 thread/task 的映射
③ 所有引用点都要传它

**从现有 id 派生是零成本的。**
这个决策和 [模块 09](09-模块-记忆与检索.md) 的
"权威度从路径推导"是同一个思路 —— **能推导就不要新建。**

## 6. 如果重新设计

【推断】以下全是我的方案。

### 6.1 把这个模块的架构推广到调用生命周期

**这不是改这个模块，是让别的模块学它。**

[模块 05](05-模块-调用生命周期.md) §6.1 我提过：
现在有六套状态表描述"一次调用"的不同侧面
（InvocationRecord / Tracker slot / QueueEntry / processingSlots /
pausedSlots / 球权投影），它们之间靠代码互相调用维护一致性。

**球权模块已经证明了事件溯源在这个场景下可行。**
所以我会：

```
统一成一个 invocation_events 日志
  ├──→ 投影 1：InvocationRecord（当前状态，给 UI）
  ├──→ 投影 2：slot 占用（给判忙）
  ├──→ 投影 3：球权（已经是这个模式了）
  └──→ 投影 4：审计日志
```

**收益**：一致性问题从"六套表互相对账"变成"投影是否幂等"。
`ensureTerminalStatus`、`reconcileZombies`、`StartupReconciler`
这些对账器可以简化成"replay 事件"。

**代价**：迁移风险高（六套表的读写点遍布全项目）。
所以我会**增量做**：先让新功能只读投影不读旧表，逐步把旧表变成投影。

### 6.2 状态机可视化 + 转移表导出

**现在的问题**：136 格的完整性靠穷举测试保证，
但**人看不到全貌**。新人要理解球权，得读代码。

**我的方案**：

```
① 从 TRANSITION_TABLE 自动生成 Mermaid 状态图（进文档）
② 生成一张 8×17 的覆盖矩阵（哪格是转移、哪格是拒绝、拒绝原因是什么）
③ CI 检查：矩阵有变化时必须同时更新文档（和他们 SOP 生成物过期就红是同一招）
```

**收益**：
- 新人 30 秒看懂全貌
- review 状态机改动时能直接看 diff 前后的矩阵差异
- 文档不会过期（自动生成 + CI 检查）

**这个改动很便宜但收益很实在** ——
项目已经有"生成物过期则 CI 红"的模式（`check:sop-definitions`），
直接复用。

### 6.3 给"球掉了"加一个显式的兜底责任人

**现在的问题**：`void` 状态表示球传给了不存在的接收方。
但**谁负责把它捡起来**？

从代码看有探针和唤醒机制，但那是给 `blocked` 用的（等外部条件）。
`void` 和 `dead` 的球，看不到明确的兜底逻辑。

**我的方案**：

```
球进入 void / dead / zombie 超过 N 分钟
  → 自动把球交给一个"兜底责任人"
     优先级：① 上一个持球者
             ② thread 的 lead Agent
             ③ 用户（作为最后兜底）
  → 并且发一条明确的消息：
    "任务 X 的球掉了（原因：目标 Agent 不可用），现在交给你处理"
```

**为什么需要？**
因为多 Agent 系统最糟的失败是**责任真空**——
不是"做错了"，而是"没人在做，而且没人知道没人在做"。

**状态机能识别 void，但识别之后要有人接。**

**代价**：可能打扰用户（如果兜底到人）。
缓解：先兜底给 Agent，只有 Agent 也搞不定才升级到人。
**这和项目自己的"决策漏斗"（细节 Agent 自治，宏观人拍板）是一致的。**

### 6.4 探针条件从代码改成声明式

**现在的问题**：`BallCustodyProbeEvaluator` 判断外部条件是否满足，
但条件类型是代码里定义的。

**我的方案**：让 Agent 在设置 hold 时声明条件（结构化）：

```ts
hold_ball({
  reason: '等 CI 通过',
  until: {
    kind: 'github_check',       // 或 'pr_merged' / 'file_exists' / 'time' / 'user_reply'
    repo: 'owner/repo',
    ref: 'abc123',
    check: 'ci/test',
  },
  fallbackAfterMs: 3600_000,   // 兜底：一小时还没满足就唤醒问一下
})
```

**收益**：
- 探针可以精确判断（而不是定期问 Agent"好了吗"）
- 条件类型可枚举 → 可以做 UI 展示"在等什么"
- `fallbackAfterMs` 保证不会永久等待

**这个方案的思路和我在 [模块 04](04-模块-mention解析.md) §6.1
提的"结构化交接优先"一致** ——
**能让 Agent 给结构化数据，就不要从文本里猜。**

### 6.5 我不会改的

| 我原本的想法 | 为什么放弃 |
|------------|-----------|
| 合并 `zombie` 和 `dead` | `zombie` 是"可能还能救"的中间态，宽限期需要它 |
| 状态机改成类（有内部状态） | 纯函数才能穷举测 136 格；有状态就要构造 fixture |
| 引入独立的 ballId | 从 threadId 派生是零成本的；新原语要维护映射 |
| 投影器顺手发唤醒（省一层） | rebuild 会重发历史唤醒，这是事件溯源的基本纪律 |
| 用异常表达拒绝转移 | 拒绝是正常业务情况，不是异常 |

## 7. 和其他模块怎么咬合

### 谁产生球权事件

```
模块 03/04 路由层
  ├─ 行首 @ 路由成功        → ball.handed
  ├─ 虚空传球检测命中        → ball.void_pass
  └─ hold_ball 回调          → ball.held

模块 05 调用生命周期
  ├─ 调用开始                → invocation.started
  ├─ 心跳                    → invocation.heartbeat
  └─ 调用死亡                → invocation.died

任务系统
  ├─ 阻塞/解除               → task.blocked / task.unblocked
  ├─ 长时间空闲              → task.idle_long
  └─ 完成                    → task.done

探针调度器
  ├─ 发唤醒                  → ball.wake_sent
  └─ 条件满足                → ball.wake_condition_met

安乐死（Phase C）
  └─ ball.frozen / degraded / abandoned
```

**四个来源写同一个日志** —— 这正是选事件溯源的理由（append 不会互相覆盖）。

### 球权状态被谁读

```
① 前端 UI                   显示"这个任务归谁、什么状态"
② 模块 08 的连续性胶囊        ballState 字段
③ 探针调度器                 决定要不要探测
④ 唤醒发送器                 决定要不要发 @
```

### 一根很关键的线：胶囊里的 ballState

```ts
// 模块 08 的胶囊
ballState: 'in_progress' | 'completed' | 'needs_handoff' | 'needs_owner';
```

**注意这四个值和状态机的 8 个状态不是一一对应的** ——
它是一个**给恢复用的简化投影**：

```
状态机的 8 个状态（内部精确）
   │  投影
   ▼
胶囊的 4 个值（给 Agent 看的语义）
   in_progress    → 继续干
   completed      → 报告完成，别重做
   needs_handoff  → 交接给别人
   needs_owner    → 找人接手
```

**为什么要简化？**【推断】
因为 Agent 不需要知道 `zombie` 和 `dead` 的区别 ——
它只需要知道"我该干什么"。**内部状态精确，对外语义简化。**

**这个"内部精确 / 对外简化"的分层，
和 [模块 06](06-模块-Provider适配.md) 的
"五种输出格式 → 一种 AgentMessage"是同一个模式。**

### 和路由层的双向咬合

```
路由层 → 球权：@ 路由成功就发 ball.handed
球权 → 路由层：唤醒时通过发一条 @ 消息实现
                （复用 @ 路由，不新建唤醒机制）
```

**这是个环，但不会死循环**，因为唤醒消息带 `SCHEDULER_TRIGGER_PREFIX` 前缀，
且 `ball.wake_sent` 是 informational 事件（不改状态）。

### 和 L0 家规的咬合

L0 里那两条【源码】：

```
- @ 是路由指令；收到 @ 后三选一：接 / 退 / 升。状态描述不是球权声明。
- 球权只有第一人称；唯一凭据是 @ 或 hold_ball 动作本身。
```

**"球权只有第一人称"这条是给状态机兜底的**：

```
状态机能记录"球传给了谁"
但它不能阻止 Agent 说"我觉得 B 应该接手了"
  → 所以 prompt 层要说清楚：那不算传球
    → 传球的唯一凭据是 @ 或 hold_ball 动作
```

**代码定义机制，prompt 定义语义。两层配合。**

## 8. 面试怎么讲

### 30 秒版

见 §0。

### 3 分钟版

> "这个模块回答'任务现在归谁'。听起来加个 ownerId 就完了，
> 实际上它是个 8 状态 × 17 事件的状态机，
> 而且要求 136 格**每一格行为确定**，穷举测试钉死。
>
> **为什么需要这么重？** 因为多 Agent 协作里最糟的失败不是'做错了'，
> 而是'**没人在做，而且没人知道没人在做**'。
> A 说'我改完了，B 应该可以 review 了'，B 没收到 @ 不知道该开工，
> 任务就悬在那儿。
>
> 三个状态名很能说明它在防什么：
> `zombie`（进程活着但没心跳）、`dead`（异常终止）、
> `void`——他们叫'虚空传球'，就是球传给了不存在或不可用的接收方。
> 我觉得 `void` 这个状态最有洞察：
> 一般系统的处理是'路由失败 → 报错 → 结束'，
> 但报错完了任务还在那儿没人做。**失败和责任真空是两回事。**
>
> **架构上它是全项目最现代的模块** —— 标准事件溯源：
> 事件日志 append-only、投影器纯函数、rebuild 就是 delete + replay，
> 而且要求 replay 出来的投影**逐字段一致**（无漂移）。
>
> 投影器有个明确约束：**零外部副作用**。
> 因为 rebuild 会 replay 全部历史事件 ——
> 如果投影器会发唤醒消息，用户会收到几百条'球回到你手上了'。
>
> 还有两个守卫我觉得特别细：
> 迟到心跳有 10 分钟宽限（网络抖动不该让状态机翻烧饼）；
> hold 到期事件必须携带它当初约定的触发时间，
> 和当前值对比，对不上就丢 —— 防旧定时器误杀新 hold。"

## 9. 本模块要点

| 要点 | 内容 |
|------|------|
| **要解决的核心失败** | 责任真空：没人在做，而且没人知道 |
| **8 状态 × 17 事件** | 136 格全覆盖（转移或显式拒绝），穷举测试钉死 |
| **`void` = 虚空传球** | 失败 ≠ 责任真空；报个错任务还在那儿 |
| **`zombie` vs `dead`** | zombie 是"可能还能救"，宽限期需要它 |
| **事件溯源** | 日志 append-only + 投影器纯函数 + rebuild 逐字段一致 |
| **投影器零副作用** | 否则 rebuild 会重发历史唤醒 |
| **state-changing vs informational** | 只有前者的拒绝记入观测（不污染 observability） |
| **迟到心跳 10 分钟宽限** | 网络抖动不该让状态机翻烧饼 |
| **`fireAt` 匹配** | 防旧定时器误杀新 hold；同思路见队列的 pauseEpoch |
| **表驱动而非 if 链** | 一眼看出空格；穷举测试可遍历 |
| **返回 `{ok:false}` 而非抛异常** | 拒绝是正常业务情况 |
| **窄输入** | 只吃两个字段，测试不用构造完整 projection |
| **幂等键要带目标 id** | 一条消息 @ 两只会被去重吞掉第二个 |
| **【源码】不引入球 ID 新原语** | 从 threadId 派生，能推导就不新建 |
| **唤醒复用 @ 路由** | 不新建机制 |
| **内部精确 / 对外简化** | 8 状态 → 胶囊里的 4 个语义值 |
| **我的改进** | 推广事件溯源到调用层 / 状态机可视化 + CI / void 兜底责任人 / 探针条件声明式 |
