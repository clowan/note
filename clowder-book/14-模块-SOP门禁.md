# 14 · 模块：SOP 门禁

> 流程规则写在 Markdown 里，模型读了会照做吗？**有时会，有时不会**——
> 而"有时不会"在多 Agent 系统里意味着流程静默失效。
>
> 这个模块的答案不是"强制执行"，而是**分级**：
> 能机器判定的就判定，判定不了的**必须显式标注"这条只能人工看"并写明缺什么**。
>
> 我认为这是全项目**最值得抄进任何团队**的一个设计 ——
> 它让"文档里的规范"和"CI 里的检查"合成了同一个集合。

---

## 0. 30 秒电梯版

> "SOP 有七个阶段（立项 → 实现 → 自检 → 可选预审 → Review → 合入 → 完成），
> 定义在一份 YAML 里，这份 YAML 是**机器真相源**——
> 它生成 TypeScript 类型，生成物过期 CI 就红。
>
> 最值得学的是 **predicate 机制**：
> 每条规则都必须声明"它能不能被机器判定，以及怎么判"。
> 有七种判定类型（git 状态、环境变量、命令模式、命令序列、身份检查、SHA 去重），
> **判不了的必须显式写 `manual_only` + 理由 + `future_candidate`**——
> 也就是"将来用哪个 checker 能自动化"。
>
> 这样就得到了一张完整的自动化覆盖率地图，
> 而且'提升覆盖率'变成了一个可执行的 backlog：搜一遍 `future_candidate` 就是待做清单。
>
> 至于执行方式，他们叫**告示牌哲学**——
> 注入'当前阶段 + 建议 skill'让 Agent 自己决定，不用传送带推它走。"

---

## 1. 它解决什么问题

### 核心矛盾

```
规则写得越死 → Agent 越容易被规则困住（紧急 hotfix 也要走完整流程）
规则写得越松 → Agent 越容易跳过步骤（"这个改动很小，直接写实现更高效"）
```

**而且更麻烦的是**：你不知道它有没有照做。

```
SOP 说"改代码必须先开 worktree"
  → Agent 在 main 上改了
    → 没有任何报错
      → 直到你 review 时才发现
```

### 三个具体问题

```
① 规则在哪儿？           散在 CLAUDE.md、SOP.md、各个 SKILL.md 里 → 多真相源
② 怎么知道守住了？       大部分规则没有机器检查
③ 怎么让 Agent 照做？    强制 vs 提示，怎么选
```

## 2. 不做会怎样

### 场景 A：规则散在多处

```
CLAUDE.md 说"必须开 worktree"
docs/SOP.md 说"main 同步后开 worktree"
tdd/SKILL.md 说"worktree 里跑测试"

某天规则改了 → 改了两处，漏了一处 → 三份文档不一致
  → Agent 读到哪份就按哪份做
```

### 场景 B：规则和检查是两个集合

```
文档里有 30 条规则
CI 里有 12 个检查

哪 18 条没检查？没人知道
某条规则实际上从来没被守住过？也没人知道
```

**这是最常见的状态** —— 规范和检查各自演化，中间是一片模糊地带。

### 场景 C：全靠强制

```
系统检测到 Agent 在 impl 阶段 → 强制加载 tdd skill → 强制走 TDD

但如果 Agent 正在处理一个紧急 hotfix：
  → 它得花力气对抗系统，而不是解决问题
    → 或者它会找绕过系统的办法（这更糟）
```

## 3. 怎么设计的

### 3.1 告示牌哲学

**先记住这句话**（它在 [模块 07](07-模块-身份注入.md) 里埋过伏笔）：

```ts
/**
 * F073 P4: SOP stage hint from Mission Hub workflow-sop.
 * Injected per-invocation so all cats (Claude/Codex/Gemini) see current stage.
 * 告示牌哲学：猫看了自己决定行动，不被系统推着走。
 */
sopStageHint?: {
  readonly stage: string;
  readonly suggestedSkill: string;
  readonly featureId: string;
};
```

**"告示牌"是个精准的比喻：**

```
❌ 传送带模式
   系统检测到你在 impl 阶段 → 自动加载 tdd skill → 强制走 TDD

✅ 告示牌模式
   系统在路边立个牌子"当前：impl 阶段，建议 skill: writing-plans"
   → Agent 自己看，自己决定
```

**为什么选告示牌？**
因为**传送带会在异常情况下把 Agent 送进沟里**。

而告示牌保留了 L0 里 Rule 0 的空间：

> **Rule 0: 规则是边界不是全部。边界之内保留判断力；认为不适用时用证据说话。**

**但同时 L0 里也有反向约束，防止"判断力"变成"推诿"：**

> **SOP 流程推进不是决策，是执行。SOP 写了下一步就照做，不问。**

**两句话合起来才完整** ——
流程该走就走别问，但流程明显不适用时可以带证据顶回来（Push Back 协议）。

**面试话术**：

> "他们的执行哲学叫'告示牌哲学'——
> 注释里写着'猫看了自己决定行动，不被系统推着走'。
>
> 也就是：系统在 prompt 里注入'当前 impl 阶段，建议用 writing-plans skill'，
> 但不强制加载、不强制执行。
>
> **为什么不用传送带？** 因为传送带在异常情况下会把 Agent 送进沟里 ——
> 比如它正在处理紧急 hotfix，系统硬推它走完整的立项→实现→review 流程，
> 它就得花力气对抗系统而不是解决问题。更糟的是它可能会找绕过系统的办法。
>
> 而且他们的家规里有两条配套的话：
> 一条是 'Rule 0: 规则是边界不是全部，边界之内保留判断力'，
> 另一条是 'SOP 流程推进不是决策，是执行。SOP 写了下一步就照做，不问'。
>
> **这两条合起来才完整** —— 前者防规则奴隶，后者防过度请示。
> 单独看任何一条都会跑偏。"

### 3.2 真相源和代码生成

```
sop-definitions/README.md：

`development.yaml` is the machine truth source for Workflow SOP stage ids, labels,
suggested skills, hard rules, pitfalls, owners, severity, and predicate metadata.

Runtime code only consumes top-level `*.yaml` files in this directory. Files under
`stubs/` are schema fixtures for future SOP domains.

After editing YAML, run:
  pnpm gen:sop-definitions
  pnpm check:sop-definitions
```

**生成链：**

```
sop-definitions/development.yaml
        │  pnpm gen:sop-definitions
        ▼
packages/shared/src/types/sop-definition.generated.ts
```

```ts
/**
 * Auto-generated by scripts/sop-definitions.mjs.
 * Do not edit by hand. Run: pnpm gen:sop-definitions
 */

export const SOP_DEFINITION_IDS = ['development'] as const;
export const DEVELOPMENT_SOP_STAGE_IDS = [
  'kickoff', 'impl', 'quality_gate', 'fresh_context', 'review', 'merge', 'completion',
] as const;
export type DevelopmentSopStageId = (typeof DEVELOPMENT_SOP_STAGE_IDS)[number];
```

**YAML 里的 stage id 变成了 TypeScript 的字面量联合类型** ——
代码里写错阶段名，编译不过。

**而且 `pnpm check` 会验证生成文件是否过期：**

> `pnpm check` runs `check:sop-definitions` and fails when that generated file is stale.

**改了 YAML 忘了重新生成 → CI 红。**
这就堵死了"真相源和代码不一致"。

**这个"生成 + 过期检查"的模式在项目里被复用了多次**
（见 [模块 12](12-模块-Skills分发.md) 的 `check:skills:manifest`）。

### 3.3 七个阶段

```yaml
id: development
domain: engineering
label: Development SOP
stages:
  - id: kickoff        label: 立项      suggested_skill: feat-lifecycle
  - id: impl           label: 实现      suggested_skill: writing-plans
  - id: quality_gate   label: 自检      suggested_skill: quality-gate
  - id: fresh_context  label: Fresh-Context Pre-Review   optional: true
  - id: review         label: Review    suggested_skill: request-review
  - id: merge          label: 合入      suggested_skill: merge-gate
  - id: completion     label: 完成      suggested_skill: feat-lifecycle
```

每个 stage 下两类条目：

```
hard_rules  → 必须满足的
pitfalls    → 常见踩坑
```

两者都有 `severity`（`blocker` / `warn`）和 **`predicate`**。

### 3.4 Predicate：本模块的核心

**每条规则都要声明它能不能被机器判定，以及怎么判。**

**七种类型：**

| type | 判定方式 | 例子 |
|------|---------|------|
| `manual_only` | **判不了，只能人看** | "Feature spec 必须有 AC + 需求点 checklist" |
| `git_state_predicate` | 查 git 状态 | worktree 前 main 必须 ahead=0 behind=0 |
| `env_check` | 查环境变量 | `REDIS_URL` 必须含 `:6398` 不含 `:6399` |
| `command_pattern` | 命令行是否匹配正则 | 必须跑过 `pnpm gate\|pnpm test\|…` |
| `command_sequence` | 命令序列 / 反模式 | 有 `git push` + `gh pr close` 但没有 `gh pr merge` |
| `handle_check` | 身份约束 | `reviewer_not_author` |
| `sha_dedup` | SHA 去重 | 同一 SHA 不重复触发云端 review |

### 3.5 `manual_only` 必须写理由 —— 这是最聪明的一处

```yaml
- id: kickoff-ac-checklist
  text: Feature spec 必须有 AC + 需求点 checklist
  severity: blocker
  predicate:
    type: manual_only
    reason: Feature spec completeness is reviewed from docs and operator context;
            no stable machine artifact yet.
```

**为什么这个设计聪明？对比一下常规做法：**

```
常规做法：
  能自动检查的 → 写检查
  不能的       → 就……不写
     ↓
  规则集和检查集是两个割裂的集合
  没人知道"这条规则到底有没有被守住"

Clowder 的做法：
  每条规则都进 YAML，都必须声明 predicate
  判不了的显式写 manual_only + 理由
     ↓
  规则集 == 检查集（只是有些检查是"人工"的）
```

**这样就得到了一张完整的自动化覆盖率地图：**

```
所有规则
  ├─ 有机器 predicate  → 能自动守
  └─ manual_only       → 只能人工守，且知道为什么
```

**面试话术（这是本模块的最高分点）：**

> "我觉得这个项目最值得抄的一个设计是它的 predicate 机制。
>
> **每条 SOP 规则都必须声明'它能不能被机器判定'。**
> 有七种判定类型 —— git 状态、环境变量、命令模式、命令序列、
> 身份检查、SHA 去重。
> **判不了的必须显式写 `manual_only`，而且必须写理由。**
>
> 一般的做法是：能自动检查的写检查，不能的就不写。
> 结果规则集和检查集是两个割裂的集合 ——
> 你有 30 条规则、12 个检查，但不知道哪 18 条没检查，
> 更不知道某条规则是不是从来没被守住过。
>
> 强制声明 predicate 之后，**规则集和检查集变成了同一个集合**，
> 只是有些检查标记为'人工'。
> 你随时能算出自动化覆盖率，而且知道每条没自动化的原因。"

### 3.6 `future_candidate`：把提升覆盖率变成 backlog

```yaml
- id: impl-design-gate-before-code
  text: 跳过 Design Gate（含 User Journey 落盘）直接写代码
  severity: blocker
  predicate:
    type: manual_only
    reason: Design Gate evidence and User Journey section are feature-doc fields;
            upgrade to feature_doc_readiness_check when checker script is available.
    future_candidate: feature_doc_readiness_check
```

**更多例子，注意每条 reason 都指出了具体缺什么：**

```yaml
reason: Current runtime has no stable post-compact recall-failure telemetry.
future_candidate: trace_pattern_post_compact_recall
                                        # ↑ 缺遥测

reason: Convention graph CLI usage is not yet emitted as structured telemetry.
future_candidate: convention_graph_usage_event
                                        # ↑ 缺结构化事件

reason: Vision coverage has no machine-checkable report artifact yet.
future_candidate: quality_gate_report_artifact
                                        # ↑ 缺 artifact

reason: Guardian identity and signoff are still conversational/thread-state artifacts.
future_candidate: guardian_signoff_event
                                        # ↑ 缺显式事件
```

**"缺遥测""缺结构化事件""缺 artifact"** ——
不是笼统的"暂时做不了"，而是**明确指出补什么就能自动化**。

**搜一遍 `future_candidate` 就是自动化 backlog。**

### 3.7 一条已经升级过的规则（完整闭环）

```yaml
- id: impl-user-journey-missing
  text: 用户可感知 Feature 缺 User Journey 段（或 user_journey_exempt）
  severity: blocker
  predicate:
    type: command_pattern
    must_match: pnpm check:features|node scripts/check-feature-truth
    reason: "check-feature-truth.mjs now checks changed feature docs for ## User Journey
             presence. F252 root cause — session vs thread scope mismatch went undetected
             because journey was never written down."
```

**注意 `reason` 里那句事故复盘：**

> F252 的根因 —— session 和 thread 的 scope 不匹配没被发现，
> 因为用户旅程从来没写下来。

**这是一次完整的闭环，面试里讲这个特别有说服力：**

```
① 事故      F252：session 和 thread 的 scope 不匹配
② 根因      用户旅程从来没写下来，所以没人发现口径不一致
③ 规则      加一条 impl 阶段的 hard rule
④ Checker   写 check-feature-truth.mjs
⑤ 升级      predicate 从 manual_only 升级成 command_pattern
⑥ 门禁      进 pnpm check，CI 强制
```

**从"人工守"升级到"机器守"的完整路径，而且有记录。**

### 3.8 具体规则赏析

**impl 阶段：**

```yaml
- id: impl-main-sync-before-worktree
  text: worktree 开之前必须 main 双向同步 (ahead=0 behind=0)
  severity: blocker
  predicate:
    type: git_state_predicate
    repository: cat-cafe
    branch: main
    checks: [ahead_zero, behind_zero]
    before_command: git worktree add
```

**为什么这条重要？**
多只 Agent 共用一个仓库时，从落后的 main 开 worktree = 后面必然要处理冲突。

**`before_command` 字段指明了检查时机** ——
不是"任何时候"，而是"执行这个命令之前"。

```yaml
- id: impl-redis-6398-only
  text: Redis 只用 6398，禁碰 6399
  severity: blocker
  predicate:
    type: env_check
    key: REDIS_URL
    must_include: ":6398"
    must_not_include: ":6399"
```

**6399 是生产数据，6398 是开发数据。一个端口号之差。**
这对应第一条铁律"数据存储圣域"。

**review 阶段：**

```yaml
- id: review-no-self-review
  text: 同一个体不能 review 自己的代码
  severity: blocker
  predicate:
    type: handle_check
    constraint: reviewer_not_author
```

**这是 [模块 11](11-模块-跨模型互审.md) 那条铁律的机器形态。**

```yaml
- id: review-retrigger-after-p1
  text: 收到 P1 修完后没 re-trigger review
  severity: blocker
  predicate:
    type: command_sequence
    must_include: [git push, gh pr comment]
    absent: ["@codex review"]
```

**`command_sequence` 的表达力："做了 A 和 B，但没做 C = 违规"。**

修完 P1 推了代码、评论了 PR，却没重新触发 review ——
**这是个很隐蔽的漏步**，因为前两步做了会让人以为流程走完了。

**merge 阶段（两条最有代表性）：**

```yaml
- id: merge-github-squash-only
  text: 必须用 gh pr merge --squash（禁止本地 squash）
  severity: blocker
  predicate:
    type: command_pattern
    must_match: gh pr merge .*--squash
    must_not_match: git merge --squash|git reset --soft
```

```yaml
- id: merge-local-squash-close
  text: 本地 squash + push + gh pr close（PR 显示 closed 不是 merged）
  severity: blocker
  predicate:
    type: command_sequence
    anti_pattern: [git push, gh pr close]
    absent: [gh pr merge]
```

**`anti_pattern` —— 反模式检测。这个坑很真实：**

```
Agent 在本地 squash 好了，push 上去，然后 gh pr close
  → 代码确实进了 main
    → 但 GitHub 上这个 PR 显示的是 closed 而不是 merged
      → PR 的关联关系、review 记录、变更归属全乱了
```

```yaml
- id: merge-runtime-update-after-merge
  text: 合入后擅自更新 runtime
  severity: blocker
  predicate:
    type: command_sequence
    cwd_contains: cat-cafe-runtime
    anti_pattern: [git pull, "pnpm start|runtime:start|restart"]
```

**`cwd_contains` 限定了作用域** —— 只在 runtime 目录下才算违规。

对应第二条铁律"进程自我保护"：
**Agent 自己就跑在这个 runtime 上，重启它等于自杀。**

**completion 阶段：**

```yaml
- id: completion-vision-guardian
  text: feat close 前必须跨猫愿景守护
  severity: blocker
  predicate:
    type: manual_only
    reason: Guardian identity and signoff are still conversational/thread-state artifacts.
    future_candidate: guardian_signoff_event
```

**"愿景守护"是这个项目最独特的一环：**
功能做完了、测试全绿了、PR 合了 ——
**还要另一只 Agent 来确认"这真的实现了当初那个愿景吗"。**

对应 `docs/SOP.md` 里的核心原则【源码】：

> **没达成愿景 = 没完成**，必须继续做，不能半路停下来问"要不要继续"

### 3.9 fresh_context 的定位声明

```yaml
- id: fresh_context
  label: Fresh-Context Pre-Review
  optional: true
  hard_rules: []
  pitfalls:
    - id: fresh-context-not-approval
      text: Fresh-context 是 finding generator，不是 approval authority
            ——不产出 verdict，不记入 Review Provenance Matrix
      severity: warn
      predicate:
        type: manual_only
        reason: Fresh-context output is free-form finding list, not a structured verdict event.
```

**"finding generator, not approval authority"** ——
和 [模块 11](11-模块-跨模型互审.md) 封板协议里对云端 reviewer 的定性**完全一致**。

**同一个原则在项目里出现两次，说明它被反复验证过：**

```
作者自己开个新上下文扫一遍代码 → 能发现问题
但不能给自己发放行
所以它不进 Review Provenance Matrix
```

### 3.10 三份文档，一个真相源

```
sop-definitions/development.yaml      机器真相源（predicate / severity / owner）
        │
        ├──→ docs/SOP.md              人类可读叙事
        ├──→ cat-cafe-skills/*/SKILL.md   每步的执行细节
        └──→ sop-definition.generated.ts  代码用的类型
```

`docs/SOP.md` 开头就声明从属关系【源码】：

```markdown
> 三猫开发全流程的导航图。每步的详细操作在对应 skill 内。
> Stage id / suggested skill / hard rules / pitfalls 的机器真相源是
> `sop-definitions/development.yaml`；本文件保留人类可读叙事。
> 冲突时先修 SopDefinition 单一源，再同步本文件和相关 skill。
```

每个 SKILL.md 也声明：

```markdown
> **SOP 位置**: 本 skill 是 `sop-definitions/development.yaml` stage `review` 的执行细节。
> **上一步**: `quality-gate` | **下一步**: `receive-review`
```

**"冲突时先修单一源"这条元规则是所有多副本文档的必需品。**
没有它，三份文档会各自演化，最后谁都不敢信。

### 3.11 SOP 状态存哪儿

```ts
export class VersionConflictError extends Error {
  readonly currentState: WorkflowSop;
  constructor(current: WorkflowSop) {
    super(`Version conflict: expected ${current.version - 1}, actual ${current.version}`);
    this.name = 'VersionConflictError';
    this.currentState = current;
  }
}

export interface IWorkflowSopStore {
  get(backlogItemId: string): Promise<WorkflowSop | null>;
  upsert(backlogItemId, featureId, input: UpdateWorkflowSopInput, updatedBy: string): Promise<WorkflowSop>;
  delete(backlogItemId: string): Promise<boolean>;
}
```

**乐观并发控制**，而且冲突时**把当前状态带回去**（`currentState`）——
调用方可以直接看到"别人推到哪儿了"，不用再查一次。

**这个细节很实用**：
一般的 `VersionConflictError` 只说"冲突了"，
调用方还得再发一次请求查当前状态。带回去省一次往返。

### 3.12 门禁脚本群

`pnpm check` 是一串检查的组合：

```
pnpm biome check .
  && check:biome-review-worktrees && check:features && check:capability-tips
  && check:sop-definitions && check:skills:manifest && check:skills:surfaces
  && check:env-ports && check:env-registry && check:env-example
  && check:start-profile-isolation && check:pre-merge-gate
  && check:guides && check:followup-tails && check:scripts-ascii-only
```

**几个有意思的：**

```
check-scripts-ascii-only.mjs      shell 脚本禁止非 ASCII
check-worktree-port-offset.mjs    多 worktree 的端口偏移
check-worktree-dirty-ledger.mjs   worktree 脏状态账本
check-feature-truth.mjs           feature 文档是否说真话
check-capability-tips-stale.mjs   能力提示是否过期
```

**`check-scripts-ascii-only`**：Agent 写的脚本很容易混进中文注释或全角标点，
在某些 shell / 编码环境下会炸。

**`check-worktree-port-offset`**：多个 worktree 同时跑 dev server，
端口必须按 worktree 偏移，否则互相抢端口。
**这是多 Agent 并行开发独有的问题。**

## 4. 为什么这么设计

### 决策 A：为什么是告示牌不是传送带

**取舍**：不保证执行 vs 保留 Agent 的判断力。

见 §3.1。**核心论证是"传送带在异常情况下会把 Agent 送进沟里"。**

【推断】还有一个更实际的理由：
**传送带需要能拦住 Agent 的动作，而拦动作依赖工具级 hook** ——
而 ADR-019 已经判定工具级 hook 在各 CLI 上支持不一致
（见 [模块 08](08-模块-会话与抗压缩.md) §3.12）。

**所以告示牌不只是哲学选择，也是能力约束下的现实选择。**

### 决策 B：为什么 YAML 而不是代码

**取舍**：多一层生成 vs 规则可读可审计。

```
写在代码里：
  ✅ 类型安全，不需要生成步骤
  ❌ 非工程师改不了；规则和实现混在一起；难以整体审视

写在 YAML 里：
  ✅ 规则集能一眼看全；可以 diff；能生成多种投影
  ❌ 需要生成步骤和过期检查
```

**他们用"生成 + CI 检查过期"补掉了 YAML 的缺点。**

### 决策 C：为什么 `manual_only` 必须写 reason

**取舍**：多写一行 vs 知道缺什么。

【推断】这个选择的关键价值是**把"做不了"变成"缺什么"**。

```
"这条不好自动化"        → 死路，没人知道下一步
"缺 post-compact 遥测"  → 明确的下一步
```

**而且 `future_candidate` 让它变成可搜索的 backlog。**

## 5. 否掉了哪些方案

### 方案一：传送带式强制执行

见 §3.1 和 §4 决策 A。

### 方案二：状态字段多点写入

**【ADR】ADR-011 的否决理由：**

> 否决理由：
> - 661 个文件每次状态变化都要同步 → **蜘蛛网 2.0**
> - 单点真相源原则违背
> - 4.6 原话："**状态字段多点写入会复发蜘蛛网**"

**"蜘蛛网"是他们对"多处同步"的形象叫法。**
这条 ADR 讲的是文档 frontmatter 契约，但原则通用。

### 方案三：用 tag 代替结构化字段

**【ADR】ADR-011：**

> ### 2. 用 tag 代替 feature_ids（否决）
>
> 方案：`tags: [F040, memory, backlog]` 不区分 ID 和松散标签
>
> 否决理由：
> - 语义模糊：`F040` 是强引用还是松散标签？
> - 机器解析困难
> - 无法区分"关于这个 Feature"和"提到了这个 Feature"

**"无法区分'关于'和'提到'"** —— 这个区分对检索质量很关键
（对应 [模块 09](09-模块-记忆与检索.md) 的图谱边）。

### 方案四：单一 `related_ids` 字段

**【ADR】ADR-011：**

> ### 3. 单一 `related_ids` 字段（否决）
>
> 方案：`related_ids: [F040, TD086]` 不区分 Feature 和 Tech Debt
>
> 否决理由：
> - Bug report 绑定 Tech Debt 的场景很常见
> - 分开字段语义更清晰
> - 查询时可以分别过滤

### 方案五：工具级 hook 做全 Agent 强制

**【ADR】ADR-019**（见 [模块 08](08-模块-会话与抗压缩.md) §3.12）：

> **行为一致性 > 自动化程度**

**这条直接支撑了"告示牌"的选择** ——
如果不能在所有 Agent 上一致地强制，就不要部分强制。

### 方案六：五件套只在 review 时要求

**【ADR】ADR-002**（见 [模块 11](11-模块-跨模型互审.md) §5 方案三）：

> 会形成"**双轨写作标准**"，跨猫同步时上下文质量不一致。

**"双轨标准"这个概念和 SOP 直接相关** ——
如果只在某些阶段要求高标准，实际是两套标准共存，最终退化到低标准。

## 6. 如果重新设计

【推断】以下全是我的方案。

### 6.1 加"覆盖率仪表盘"和覆盖率门禁

**现在有了 predicate 声明，但没看到有人统计它。**

**我的方案**：

```
pnpm check:sop-coverage 输出：

  阶段         规则数   自动化   人工   覆盖率
  kickoff        2        0        2      0%
  impl           4        3        1     75%
  quality_gate   2        1        1     50%
  review         3        1        2     33%
  merge          5        4        1     80%
  completion     3        1        2     33%
  ────────────────────────────────────────────
  总计          19       10        9     53%

  待自动化（有 future_candidate）：
    feature_doc_readiness_check      → 2 条规则
    guardian_signoff_event           → 2 条规则
    quality_gate_report_artifact     → 1 条规则
    trace_pattern_post_compact_recall → 1 条规则
```

**再加一条门禁**：**新增 hard_rule 时，
覆盖率不能下降**（除非显式豁免）。

**为什么？** 因为不加门禁的话，
`manual_only` 会变成一个太方便的逃生门 ——
每加规则都写 `manual_only`，覆盖率单调下降。

**这个改动很便宜** —— YAML 已经有全部数据，写个脚本统计就行。
**投入产出比在我列的所有改进里最高。**

### 6.2 让 `manual_only` 的规则也留下"已检查"的痕迹

**现在的问题**：`manual_only` 意味着"人工检查"。
**但没有记录说明这次人工检查做了没有。**

```
"Feature spec 必须有 AC + 需求点 checklist"
  → 谁在什么时候确认了这个？
    → 没有记录
```

**我的方案**：给 `manual_only` 规则加一个轻量的确认机制。

```yaml
- id: kickoff-ac-checklist
  predicate:
    type: manual_only
    reason: ...
    # 新增
    attestation:
      required_at: stage_exit          # 阶段退出时必须确认
      by: 'agent' | 'operator'         # 谁能确认
      evidence_hint: 'AC 章节的行号或摘录'
```

Agent 在推进 SOP 阶段时，必须通过 MCP 提交确认：

```
attest_sop_rule({
  ruleId: 'kickoff-ac-checklist',
  verdict: 'satisfied',
  evidence: 'docs/features/F123.md#L20-L35 有 5 条 AC',
})
```

**收益**：
- `manual_only` 从"不检查"变成"人工检查且有记录"
- 事后能审计"这条规则实际的满足率是多少"
- 如果某条规则的确认总是走过场（evidence 都很空洞）→ 说明规则本身有问题

**代价**：增加 Agent 的负担（每阶段多几次确认调用）。
**缓解**：只对 `severity: blocker` 的 `manual_only` 要求确认，
`warn` 级别不强制。

**这个改动的价值**：它填上了 predicate 机制的最后一块 ——
现在能回答"哪些规则没自动化"，
改完能回答"**没自动化的那些，实际守住了吗**"。

### 6.3 predicate 从"声明"变成"可执行"

**现在的问题**：predicate 是**元数据**，描述了怎么判定，
但**判定逻辑在别处实现**（checker 脚本、routing guard 等）。

```yaml
predicate:
  type: git_state_predicate
  repository: cat-cafe
  branch: main
  checks: [ahead_zero, behind_zero]
  before_command: git worktree add
```

**这段描述得很清楚，但谁来执行它？** 从代码看是散在各处的。

**我的方案**：写一个 predicate 求值器。

```ts
interface PredicateEvaluator {
  evaluate(predicate: Predicate, context: EvaluationContext): Promise<{
    satisfied: boolean | 'unknown';    // unknown = manual_only
    evidence?: string;
    reason?: string;
  }>;
}

interface EvaluationContext {
  gitState?: { ahead: number; behind: number; branch: string; cwd: string };
  env: Record<string, string>;
  recentCommands: string[];            // 从工具调用记录来
  reviewerCatId?: string;
  authorCatId?: string;
  prShas?: { local: string; cloud: string; head: string };
}
```

**收益**：
- 六种机器 predicate 的判定逻辑集中在一处（现在散着）
- 可以在**运行时**求值（不只是 CI）→ Agent 违规时能立刻知道
- 可以在 prompt 里注入"当前有 2 条 blocker 未满足"

**这个改动能让告示牌变得更有信息量**：

```
现在的告示牌：  "当前 impl 阶段，建议 skill: writing-plans"
改进后：        "当前 impl 阶段，建议 skill: writing-plans
                ⚠ 未满足：main 落后 origin 3 个 commit（开 worktree 前需同步）"
```

**注意这仍然是告示牌，不是传送带** ——
它只是把牌子上的信息写得更具体，不强制拦。

### 6.4 pitfall 应该记录"实际发生率"

**现在的问题**：`pitfalls` 是一份"常见坑"清单，
但**不知道哪些坑还在发生、哪些已经绝迹**。

```yaml
pitfalls:
  - id: impl-post-compact-recall-loss
    text: 压缩后忘了当前在做什么
    severity: warn
```

**这条还在发生吗？** 如果 [模块 08](08-模块-会话与抗压缩.md)
的三道防线有效，它应该已经很少了。

**我的方案**：给 pitfall 加发生率追踪。

```yaml
pitfalls:
  - id: impl-post-compact-recall-loss
    text: 压缩后忘了当前在做什么
    severity: warn
    # 新增（自动维护，不手写）
    occurrences:
      last_30d: 2
      last_90d: 11
      trend: 'decreasing'
      last_seen: '2026-07-01'
```

```
发生率降到 0 且超过 90 天 → 标记为 'dormant'，从 prompt 注入里移除（省 token）
发生率上升 → 告警，可能是某个防线退化了
```

**为什么值得？**
因为 pitfall 清单会单调增长 —— 每次事故加一条，从来不删。
最后变成一份没人读的长清单，而且占 prompt 预算。

**有发生率数据才能做"退役"决策。**

**这也和 [模块 15](15-模块-Self-Evolution.md) 的
"30 天 replay check"一致** —— 那边验证改进有没有效果，
这边验证坑有没有消失。**是同一件事的两个方向。**

### 6.5 我不会改的

| 我原本的想法 | 为什么放弃 |
|------------|-----------|
| 改成传送带（强制加载 skill） | 异常情况会把 Agent 送进沟；而且强制依赖工具级 hook，各 CLI 支持不一致 |
| 规则写在代码里（省生成步骤） | YAML 能一眼看全规则集、能 diff、能生成多种投影；生成过期有 CI 兜 |
| 去掉 `manual_only`（只留能自动化的） | 那就退回"规则集 ≠ 检查集"的老问题；显式声明"判不了"本身就是价值 |
| 把 pitfalls 和 hard_rules 合并 | severity 已经区分了 blocker/warn，但 pitfall 的语义是"容易踩"不是"必须满足"，不该混 |

## 8. 面试怎么讲

### 30 秒版

见 §0。

### 3 分钟版

> "SOP 有七个阶段，定义在一份 YAML 里，
> 这份 YAML 是**机器真相源**—— 它生成 TypeScript 类型，
> 生成物过期 CI 就红，所以真相源和代码不会不一致。
> 而且 `docs/SOP.md` 和各个 SKILL.md 都声明了自己是它的投影，
> 有一条元规则：'冲突时先修单一源'。
>
> **最值得学的是 predicate 机制。**
> 每条规则都必须声明'它能不能被机器判定，以及怎么判'。
> 有七种类型 —— git 状态、环境变量、命令模式、命令序列、
> 身份检查、SHA 去重。
> **判不了的必须显式写 `manual_only`，而且必须写理由。**
>
> 一般做法是：能自动检查的写检查，不能的就不写 ——
> 结果规则集和检查集是两个割裂的集合，
> 你不知道哪些规则从来没被守住过。
>
> 强制声明 predicate 之后，规则集和检查集变成同一个集合。
> 而且他们还有个 `future_candidate` 字段，写"将来用哪个 checker 能自动化"。
> 那些 reason 写得很具体 ——'缺 post-compact 遥测'、
> '缺结构化事件'、'缺 machine-checkable artifact'。
> **搜一遍 `future_candidate` 就是自动化 backlog。**
>
> 有一条规则展示了完整闭环：
> 一次事故（F252：session 和 thread 的 scope 不匹配）→
> 根因（用户旅程从来没写下来）→ 加一条 SOP 规则 →
> 写 checker 脚本 → predicate 从 `manual_only` 升级成 `command_pattern` →
> 进 CI 强制。**从人工守到机器守的完整路径，而且有记录。**
>
> 执行方式他们叫**告示牌哲学** ——
> 注入'当前阶段 + 建议 skill'让 Agent 自己决定，不强制。
> 因为传送带在异常情况下会把 Agent 送进沟（比如紧急 hotfix）。
> 而且他们的家规里有配套的两条：
> 'Rule 0: 规则是边界不是全部' + 'SOP 流程推进不是决策，是执行，写了就照做不问'——
> 前者防规则奴隶，后者防过度请示。"

### 常见追问

**Q：这些规则怎么保证 Agent 真的遵守？**

> "**不保证。这是明确的设计取舍。**
>
> 他们选了告示牌而不是传送带 —— 注入信息让 Agent 自己决定。
> 理由是传送带在异常情况下会把 Agent 送进沟，
> 而且更糟的是它可能会找绕过系统的办法。
>
> 但有三层兜底：
> 一，`severity: blocker` 的规则在 CI 有对应检查（能自动化的那些）；
> 二，`merge-gate` 那一环有五个硬条件，PR 过不了就合不进去；
> 三，跨模型互审 —— 另一只 Agent 会审你有没有守流程。
>
> 而且我发现一个更根本的原因：**强制需要能拦住 Agent 的动作，
> 而拦动作依赖工具级 hook** ——
> 他们的 ADR-019 已经判定工具级 hook 在各 CLI 上支持不一致
> （Claude 完整、Codex 完全没有），原话是'行为一致性 > 自动化程度'。
>
> **所以告示牌不只是哲学选择，也是能力约束下的现实选择。**"

**Q：`manual_only` 的规则会不会变成摆设？**

> "**会，而且我认为这是现在最大的缺口。**
>
> `manual_only` 意味着"人工检查"，
> 但**没有任何记录说明这次人工检查做了没有**。
> "Feature spec 必须有 AC"—— 谁在什么时候确认了？没记录。
>
> 而且 `manual_only` 是个太方便的逃生门 ——
> 每加规则都写 manual_only，覆盖率会单调下降。
>
> 我会做两件事：
>
> 一，**覆盖率仪表盘 + 门禁**。
> 统计每个阶段的自动化率，加一条'新增 hard_rule 时覆盖率不能下降'。
> 这个很便宜，YAML 里已经有全部数据。
>
> 二，**给 `manual_only` 加轻量确认机制**。
> Agent 推进阶段时必须通过 MCP 提交
> `attest_sop_rule({ ruleId, verdict, evidence })`，
> evidence 要给出具体的行号或摘录。
> 只对 blocker 级别要求，warn 不强制。
>
> 这样 `manual_only` 从'不检查'变成'人工检查且有记录'，
> 而且能审计'某条规则的确认是不是总在走过场'。
>
> **这填上了 predicate 机制的最后一块** ——
> 现在能回答'哪些没自动化'，改完能回答'没自动化的那些实际守住了吗'。"

**Q：这套设计能用在别的团队吗？**

> "我认为**这是这个项目最可迁移的一个设计**，而且不限于 AI 团队。
>
> 骨架是：
>
> ```yaml
> stages:
>   - id: <阶段>
>     suggested_skill: <该阶段的方法论>
>     hard_rules:
>       - id: <规则 id>
>         text: <人类可读描述>
>         severity: blocker | warn
>         predicate:
>           type: <判定方式> | manual_only
>           reason: <为什么判不了>
>           future_candidate: <将来用什么判>
> ```
>
> 三个可迁移的要点：
>
> 一，**每条规则都必须声明 predicate**，包括'判不了'——
> 这样规则集和检查集永远是同一个集合。
>
> 二，**`manual_only` 要写 reason**，而且要说清缺什么
> （缺遥测/缺事件/缺 artifact），不是笼统的'不好自动化'。
>
> 三，**`future_candidate` 是自动化 backlog**，让覆盖率提升有迹可循。
>
> 任何有 SOP 的团队都能用这套结构，
> 把'文档里的规范'和'CI 里的检查'合成一件事。
> 我觉得大部分团队的痛点恰恰在这个割裂上。"

## 9. 本模块要点

| 要点 | 内容 |
|------|------|
| **告示牌哲学** | 注入阶段提示让 Agent 自己决定，不用传送带推 |
| **两句话合起来才完整** | "Rule 0 规则是边界" + "SOP 推进不是决策，写了就照做" |
| **YAML 是机器真相源** | 生成 TS 类型，过期则 CI 红；三份投影声明从属 |
| **每条规则必须有 predicate** | 判不了就显式 `manual_only` |
| **七种 predicate 类型** | manual_only / git_state / env_check / command_pattern / command_sequence / handle_check / sha_dedup |
| **`manual_only` 要写 reason** | 说清缺什么（遥测/事件/artifact），不是"不好做" |
| **`future_candidate`** | 自动化 backlog，可搜索 |
| **完整升级闭环** | 事故 F252 → 根因 → 规则 → checker → predicate 升级 → CI |
| **`anti_pattern`** | 反模式检测，如"push + close 但没 merge" |
| **`cwd_contains`** | 限定作用域，只在 runtime 目录下才算违规 |
| **`before_command`** | 指明检查时机 |
| **finding generator ≠ approval authority** | 同原则在云端 review 和 fresh-context 上各出现一次 |
| **"冲突时先修单一源"** | 多副本文档的必需元规则 |
| **乐观并发 + 带回当前状态** | 冲突时省一次往返 |
| **【ADR-011】三个否决** | 状态多点写入（蜘蛛网）/ tag 代替结构化字段 / 单一 related_ids |
| **【ADR-019】支撑告示牌** | 行为一致性 > 自动化程度 |
| **我的改进** | **覆盖率仪表盘 + 门禁** / `manual_only` 确认机制 / predicate 求值器 / pitfall 发生率追踪 |
