# 11 · 模块：跨模型互审

> "让 GPT review Claude 写的代码"这句话很好听。
> 但要落地，你得回答：**谁来选这个 reviewer？凭什么？**
>
> 这个模块的代码只有 223 行，但它是**这个项目最想卖的东西**。
> 而且它有一段我认为全项目最好的工程判断：
> **封板协议 —— 当 LLM reviewer 永远不说"通过"的时候怎么办。**

---

## 0. 30 秒电梯版

> "核心是一条铁律：**同一个个体不能 review 自己的代码**。
> 落地成七条规则：排除自己 → 必须有 peer-reviewer 角色 →
> **必须有额度**（注释写着'40 美刀教训'）→ 优先跨模型家族 →
> 优先 lead → 优先帖内活跃 → 都不行就降级到同族不同个体。
>
> 而且降级是**显式**的：返回值带 `isDegraded` 和 `degradeReason`，
> 不静默降级。
>
> 但最值钱的是**封板协议**。他们发现 LLM reviewer 是
> '无状态抽样信号源'—— 每轮重放全部历史 comment、
> 分不清已修和未修、不读你的反驳。
> 所以'零 P1/P2'这个终止条件**在数学上没有不动点**。
> 实测一个 PR 跑了 21 轮，其中一轮 22 个 finding 里 21 个是假阳性。
> 于是加了机械闸门：5 轮，或单轮假阳性率超 50%，强制封板。"

---

## 1. 它解决什么问题

### 为什么单模型自审不行

```
Claude 写代码时的思维模式
       ↓
Claude 审代码时的思维模式（几乎一样）
       ↓
它写的时候没想到的，审的时候也想不到
```

**同一个模型的训练数据、归纳偏好、常见错误模式都是一致的。**
让它审自己，等于让近视眼检查自己的视力表。

项目的 roster 里对每只 Agent 的评价直接写着差异：

```json
"opus": {
  "family": "ragdoll",
  "roles": ["architect", "peer-reviewer"],
  "lead": true,
  "available": true,
  "evaluation": "主架构师，全栈开发，深度思考强，bug定位弱"
}
```

**"深度思考强，bug 定位弱"** —— 这就是需要另一个模型的理由。

### 落地要回答的四个问题

```
① 谁能审？        角色、额度、家族关系
② 如果只有一只 Agent 在线怎么办？
③ review 完代码又变了，之前的签字还算数吗？
④ 如果 reviewer 永远不说"通过"怎么办？
```

**第③④两个问题是这个模块最有深度的部分。**

## 2. 不做会怎样

### 场景 A：随便挑一个 reviewer

```
挑到没额度的 Agent
  → 调用失败
    → 但 prompt 已经发出去了，token 已经烧了
```

**这就是"40 美刀教训"的由来。**

### 场景 B：允许同模型自审

```
Claude 4.7 写的代码，Claude 4.8 来审
  → 如果它们互相以为是"自己的另一个版本"
    → 审阅退化成自审
      → 盲区一样，什么都发现不了
```

**所以 [模块 07](07-模块-身份注入.md) 的 D3 同族提醒是这个模块的前置条件。**

### 场景 C：不做 review continuity

```
reviewer 审了 SHA-abc，说 LGTM
你跑 pnpm gate，biome 自动格式化，HEAD 变成 SHA-def
  → 这个 LGTM 还算数吗？
    → 如果算：可能签的是没审过的代码
      → 如果不算：每次格式化都要重审，没人受得了
```

### 场景 D：等 LLM reviewer 说"零问题"

```
第 1 轮  云端 reviewer 报 8 个 finding
        → 修了
第 2 轮  报 6 个，其中 4 个是上轮已修的（它不记得）
        → 修 2 个新的，对 4 个假阳性写了反驳
第 3 轮  报 7 个，包括那 4 个（它不读反驳）
        → ...
第 21 轮 报 22 个，其中 21 个是假阳性
```

**实测数据（F168 PR #2214）**。这不是假设。

## 3. 怎么设计的

### 3.1 配置层：roster + policy

```json
"reviewPolicy": {
  "requireDifferentFamily": true,
  "preferActiveInThread":   true,
  "preferLead":             true,
  "excludeUnavailable":     true
}
```

roster 里每只 Agent 有：

| 字段 | 作用 |
|------|------|
| `family` | 模型家族（`ragdoll`/`mainecoon`/`siamese`…）—— 跨族判定的依据 |
| `roles` | 含 `peer-reviewer` 才有资格 |
| `lead` | 是否首席 |
| `available` | **有没有额度** |
| `evaluation` | 人写的能力评价 |

**`family` 这个字段是整条铁律的地基** ——
它把"模型品牌"变成了可判定的数据。

### 3.2 七条规则

```ts
/**
 * Reviewer Matcher
 * F032: Dynamic reviewer selection based on roster, availability, and thread activity.
 *
 * Rules (co-creator confirmed):
 * 1. Must be different from author
 * 2. Must have 'peer-reviewer' role
 * 3. Must be available (有猫粮！40 美刀教训)
 * 4. Prefer different family
 * 5. Prefer lead
 * 6. Prefer active in current thread
 * 7. Degrade to same-family lead if no cross-family reviewer available
 */
```

**排序键的优先级值得单独讲：**

```ts
const sortCandidates = (candidates) => [...candidates].sort((a, b) => {
  // First by activity (higher = better)
  const activityDiff = (activity[b[0]] ?? 0) - (activity[a[0]] ?? 0);
  if (activityDiff !== 0) return activityDiff;

  // Then by lead status (lead first)
  if (policy.preferLead) {
    if (b[1].lead && !a[1].lead) return 1;
    if (a[1].lead && !b[1].lead) return -1;
  }
  return 0;
});
```

**帖内活跃度 > lead 身份。**

**为什么活跃度优先？**

```
一只已经在这个帖子里聊过的 Agent
  → 它已经知道这个 feature 在讨论什么
    → 上下文成本低得多

lead 虽然权威，但如果它没参与过
  → 得从头读一遍历史
    → 而且更可能误解需求
```

**这是个很实际的取舍：上下文成本 > 名义权威。**

### 3.3 三级降级链

```ts
// 5. 优先跨族
if (policy.requireDifferentFamily || differentFamily.length > 0) {
  const sorted = sortCandidates(differentFamily);
  if (sorted.length > 0) {
    return { reviewer: createCatId(sorted[0]?.[0]), isDegraded: false, candidates: allCandidateIds };
  }
}

// 6. 降级到同族（只考虑 lead）
if (sameFamily.length > 0) {
  const sameFamilyLeads = sameFamily.filter(([_, entry]) => entry.lead);
  const sorted = sortCandidates(sameFamilyLeads.length > 0 ? sameFamilyLeads : sameFamily);
  if (sorted.length > 0) {
    const degradeReason = differentFamily.length === 0
      ? 'No different-family reviewers available (all unavailable or no peer-reviewer role)'
      : 'Different-family reviewers filtered out by policy';
    log.warn({ authorId, degradeReason }, `[resolveReviewer] Degraded to same-family`);
    return { reviewer: ..., isDegraded: true, degradeReason, candidates: allCandidateIds };
  }
}

// 7. 兜底
return { reviewer: getDefaultCatId(), isDegraded: true,
         degradeReason: 'No reviewers available at all', candidates: allCandidateIds };
```

**降级到同族时只挑 lead：**

```ts
const sameFamilyLeads = sameFamily.filter(([_, entry]) => entry.lead);
```

**同族已经是妥协了 —— 至少让最强的那个来。**
连 lead 都没有才退到任意同族。

### 3.4 降级必须可见

```ts
export interface ReviewerMatchResult {
  reviewer: CatId;
  isDegraded: boolean;              // ← 明确标记
  degradeReason?: string;           // ← 说清楚为什么
  candidates: readonly CatId[];     // ← 所有候选，便于调试
}
```

**对比一下：如果只返回 `reviewer: CatId`，出问题时你完全不知道
是"跨族没人"还是"policy 过滤掉了"。**

**这是项目里出现至少五次的原则**（见
[模块 06](06-模块-Provider适配.md) 载体降级、
[模块 13](13-模块-MCP回调桥.md) 工具降级、
[模块 09](09-模块-记忆与检索.md) 检索 fail-open）。

### 3.5 拒绝要带理由

```ts
export function canReview(reviewer: CatId, author: CatId): { canReview: boolean; reason: string } {
  if (reviewerId === authorId) {
    return { canReview: false, reason: 'Cannot review own code' };
  }
  if (!reviewerEntry) {
    return { canReview: false, reason: `Reviewer "${reviewerId}" not in roster` };
  }
  if (!reviewerEntry.roles.includes('peer-reviewer')) {
    return { canReview: false, reason: `"${reviewerId}" does not have peer-reviewer role` };
  }
  if (policy.excludeUnavailable && reviewerEntry.available === false) {
    return { canReview: false, reason: `"${reviewerId}" is not available (没猫粮！)` };
  }
  if (policy.requireDifferentFamily && authorEntry) {
    if (reviewerEntry.family === authorEntry.family) {
      return { canReview: false, reason: `Same family (${reviewerEntry.family}) — different family required` };
    }
  }
  return { canReview: true, reason: 'OK' };
}
```

**每个 false 都带 reason 字符串。**
这些 reason 是**给 Agent 看的** ——
它被拒绝时能知道为什么，进而做正确的下一步（换个 reviewer？等额度？）。

### 3.6 注入 prompt：让 Agent 知道有谁可选

`buildReviewerSection` 生成：

```markdown
## 你当前的 Reviewers

根据 roster 配置，你当前可以找以下猫 review：
- @codex (mainecoon, lead)
- @gemini (siamese)

[注意] 以下猫当前不可用：
- @kimi (Kimi, 没猫粮)
```

**三个细节：**

**① 不可用的也列出来**

```ts
unavailable.push(`- ${mention} (${displayName}, 没猫粮)`);
```

**告诉 Agent"这只存在但没额度"，而不是假装它不存在。**
否则 Agent 会疑惑"明明有五只，为什么名单只有两只"，
或者反复 @ 一只永远不回应的 Agent。

**和 [模块 04](04-模块-mention解析.md) §3.7 是同一个原则：
可见的缺席胜过静默的消失。**

**② 降级时明确提示**

```ts
} else if (sameFamily.length > 0) {
  // Cloud Codex R5 P2 fix: No cross-family, but same-family available as fallback
  available = sameFamily;
  fallbackNote = '[注意] 没有跨家族 reviewer 可用，以下同家族猫可作为 fallback：';
}
```

Agent 看到这句就知道这次 review 的质量保证等级降了一档，
可能需要更谨慎、或者向用户说明。

**③ policy 开关必须被尊重**

```ts
// Cloud Codex R6 P2 fix: Respect excludeUnavailable policy
// When excludeUnavailable=false, treat all cats as "effectively available"
const isEffectivelyAvailable = !policy.excludeUnavailable || isCatAvailable(id);
```

**注意 `R5 P2` / `R6 P2` 这两个注释** ——
说明这两处都是 review 发现的问题。**审阅系统本身也是被审阅出来的。**

### 3.7 SOP 侧：六个硬前置

代码只解决"选谁"。"什么时候能发 review 请求"是 SOP 的事。

`request-review/SKILL.md` 列了六个硬前置：

| 条件 | 未满足 |
|------|--------|
| `quality-gate` 通过（有本轮 gate report） | BLOCKED |
| 测试全绿（附测试命令输出） | BLOCKED |
| 原始需求可引用（Discussion 路径 + ≤5 行摘录） | BLOCKED — **reviewer 有权拒绝审查** |
| Architecture ownership 已声明 | BLOCKED |
| 前端改动已浏览器实测（截图证据） | BLOCKED |
| 根目录工件闸门通过 | BLOCKED |

**第三条附了一段教训**【源码】：

> **教训（F041）**：review 信只附了 spec，没附原始 Discussion。
> 结果 multiple remote review rounds 全在抓 edge case，
> 没有一轮说"UI 不可用"。Reviewer 没有上下文，无法做**愿景验证**。

**这是多 Agent review 特有的失效模式，面试里一定要讲：**

> "有个教训我觉得特别值得说。
>
> 有一次 review 信只附了 spec，没附原始的需求讨论。
> 结果好几轮 review 全在抓边界条件，**没有一轮说'这个 UI 根本不能用'**。
>
> **人类 reviewer 缺上下文时会喊停** ——'这需求是什么，我看不懂'。
> **LLM reviewer 缺上下文时不会喊停** ——
> 它会认真地审它能看到的部分，把 edge case 抓得很漂亮，
> 然后放行一个根本不能用的东西。
>
> 所以'原始需求可引用'被列成了**硬前置**，
> 而且写明'reviewer 有权拒绝审查'。
>
> 我觉得这是 LLM 做 reviewer 最容易被忽略的一个特性：
> **它不会说'我信息不够'，它会在信息不够的情况下给你一个看起来很专业的答案。**"

### 3.8 Review Continuity：代码变了签字还算数吗

这是 `merge-gate/SKILL.md` 里最精彩的一段。

**基本规则：**

> `pnpm gate`、rebase、fixup、biome 格式化刷新等都可能让 HEAD 变化。
> **只要 HEAD 变了，旧 review 默认不自动继承。**

**但它没停在这条简单规则上：**

> 但 continuity 不是一个布尔 `reviewer`。
> 进入 merge-gate 后必须维护 **Review Provenance Matrix**，
> 先判当前 HEAD 变化由谁产生，再决定下一步 gate owner，
> **避免把 cloud / CI / PR check 的外部 gate 投射成本地旧 reviewer**。

**Review Provenance Matrix：**

| 字段 | 记录内容 |
|------|----------|
| `localPeerReviewSha` | 本地同伴 review 覆盖的 SHA |
| `cloudReviewSha` | 最新云端 review 覆盖的 SHA |
| `currentHead` | PR 当前 `headRefOid` |
| `headChangeCause` | `local-gate` / `cloud-finding` / `ci-fix` / `rebase` / `pr-meta` |
| `nextGateOwner` | `local-peer` / `cloud` / `ci` / `author` / `guardian` |

**判定规则：**

| HEAD 变化原因 | 下一个 gate owner |
|--------------|-----------------|
| `cloud-finding`（修云端 finding 后 push） | **cloud** —— 禁止为此 @ 本地旧 reviewer |
| `ci-fix`/`local-gate` 且**非行为性** delta（纯 rebase、import order、formatter） | local peer 做一次 **scoped continuity approval** |
| `ci-fix`/`local-gate` 且**行为性** delta（代码、测试、配置、接口） | local peer **delta review**；超出原 scope 则完整 review |
| `pr-meta`（只改 PR body） | 不影响任何 coverage |

**核心洞察是"gate 的所有权"：**

> **谁提的 finding，谁负责确认修好了。**

**这防的是一种很自然但很坏的行为：**

```
作者修完云端 reviewer 的 finding
  → 顺手 @ 本地 reviewer 说"帮我再看一眼"
    → 本地 reviewer 根本不知道云端提了什么
      → 只能凭空签字
        → 签字变成走过场
```

**面试话术**：

> "review 完代码又变了这个问题，他们没有用简单的
> '变了就重审'或'变了也算'——而是引入了一个 **Review Provenance Matrix**。
>
> 记五个字段：本地 review 覆盖的 SHA、云端 review 覆盖的 SHA、
> 当前 HEAD、**HEAD 变化的原因**、下一个 gate 的所有者。
>
> 然后按原因分流：
> 如果是修云端 finding 导致的变化 → 下一个 gate owner 是云端，
> **明确禁止为此 @ 本地旧 reviewer**；
> 如果是纯格式化/rebase → 本地做一次 scoped 的续签；
> 如果是行为性改动 → 本地做 delta review，超出原 scope 就完整重审。
>
> 核心洞察是**'谁提的 finding 谁负责确认修好了'**。
> 这防的是：作者修完云端的问题，顺手 @ 本地 reviewer 签字 ——
> 而本地 reviewer 根本不知道云端提了什么，只能凭空签字。
> **签字变成走过场比不签字更危险。**"

### 3.9 封板协议：本模块最值钱的部分

**完整引用**【源码】：

> **封板协议（LL-072，cloud re-review 循环的硬上限）**：
>
> "cloud-finding 修复 → 重新触发 cloud review" 没有自然终点 ——
> cloud reviewer 是**无状态抽样信号源**（每轮重放全部历史 inline comments、
> 不能分辨 stale/fresh、不读 pushback），在多 commit 累积 diff 上
> "0 P1/P2"这个条件**没有不动点**，等它说零等于无限循环
> （F168 PR #2214 实测 21 轮，R19 单轮 22 findings 中 21 个假阳性）。
> 因此：
>
> 1. **循环检测阈值（机械判定，无弹性）**：
>    同一 PR cloud review 达到 **5 轮**，
>    或单轮假阳性（stale 重放/已修重报）比例 **>50%**
>    → 当轮处理完**强制进入封板**，不是继续修-触发循环。
>
> 2. **封板动作**：处理完当前轮全部 finding
>    （真 P1/P2 修复 + 红绿测试；假阳性在 PR comment 有据 pushback）
>    → **不再 re-trigger cloud review，无论结果**。
>    终局确权交给**本地有状态 reviewer** 对最终 SHA 做 final review
>    （核 pushback 成立性 + 全 diff continuity），放行即 merge。
>    cloud 的角色定位：**有贡献预算的辅助信号源，不是终局确权者**。

**三个词说清了病根：**

| 特性 | 后果 |
|------|------|
| **无状态** | 每轮从头看，不记得上轮说过什么 |
| **抽样** | 每轮采样不同，随机报不同的问题 |
| **重放历史 comment** | 已经修掉的问题会被再报一遍 |
| **不读 pushback** | 你解释过"这不是 bug"，它下轮照样报 |

**结论：`P1/P2 == 0` 这个终止条件在数学上没有不动点。**

**这段为什么是全项目最好的工程判断（面试重点）：**

> "我认为这段是全项目最好的工程判断，因为它做了三件事：
>
> **一，它给出了 LLM reviewer 的正确心智模型。**
> 不是'更便宜的人类 reviewer'，而是'高召回低精度的信号源'。
> 一旦你期待它收敛、期待它记得、期待它认账，就会陷入无限循环。
>
> **二，它把一个模糊的挫败感量化成了可执行的闸门。**
> 5 轮，或单轮假阳性率超 50%。而且明确写了'机械判定，无弹性'——
> 如果阈值是'觉得差不多了就封板'，那实际上没有阈值，
> 因为每一轮都会有'这轮的 finding 好像挺重要的'这种感觉。
>
> **三，它有实测数据支撑。** 21 轮，其中一轮 22 个 finding 里 21 个假阳性。
> 而且这个数据被写进了教训库（LL-072），不是口头传说。
>
> 最后那句定性我觉得也很准：
> **'cloud 的角色定位：有贡献预算的辅助信号源，不是终局确权者。'**
> 终局判断必须由**有状态**的主体做 —— 因为只有有状态的主体
> 才能核对'你上轮说的这个我已经解释过了'。"

## 4. 为什么这么设计

### 决策 A：为什么活跃度优先于 lead

**取舍**：名义权威 vs 上下文成本。

见 §3.2。**上下文成本在 LLM 系统里是真实的钱**——
一个没参与过讨论的 Agent 要读几十条历史才能开始 review。

### 决策 B：为什么"有额度"是硬规则而不是软偏好

**"40 美刀教训"** —— 派给没额度的 Agent，
调用失败但 token 已经烧了。

【推断】这条从软偏好升级成硬规则，说明它真实发生过而且不止一次。

### 决策 C：为什么降级只到"同族不同个体"，不到"自审"

**取舍**：可用性 vs 底线。

```
如果允许自审：
  → 只有一只 Agent 在线时流程能走通
    → 但 review 完全失去意义
      → 而且会形成"反正能自审"的习惯

现在的做法：
  → 降到同族不同个体（至少盲区不完全一样）
    → 连这个都没有 → 兜底到默认 Agent + 标 isDegraded
      → 让人看到"这次没有真正的 review"
```

**底线是"不能是同一个个体"，这条不降级。**

## 5. 否掉了哪些方案

### 方案一：写死 reviewer 是某只 Agent

**【源码】BOOTSTRAP.md 里明确禁止：**

> **Reviewer 选择是动态匹配**（`docs/SOP.md` 配对规则），
> **禁止写死"reviewer 是Ragdoll"**。

**这条规则本身很有意思** —— 它防的不是代码写死，
而是**模型形成刻板印象**。

【推断】为什么需要这条？因为 Agent 见过很多次"Ragdoll 做 reviewer"，
就会开始把它当成规则，然后在 reviewer 不可用时也去 @ 它。

### 方案二：只记录 What，Why 让接手方自己推断

**【ADR】ADR-002 的否决理由：**

> **备选方案 A**：仅要求记录 `What`，由接手方自行推断 `Why`
> 不选原因：历史实践已证明会导致决策不可审计，
> 接手猫无法判断"bug 还是 feature"。

**"接手猫无法判断 bug 还是 feature"** ——
这是交接文档缺 Why 的最典型后果。

### 方案三：只在 review 请求里要五件套，日常交接不强制

**【ADR】ADR-002：**

> **备选方案 B**：仅在 review 请求中要求五件套，日常交接不强制
> 不选原因：会形成**"双轨写作标准"**，
> 跨猫同步时上下文质量不一致，问题回流概率高。

**"双轨写作标准"这个词很好用。**
如果只在某些场合要求高标准，实际上是两套标准共存，
最终会退化到低标准。

### 方案四：完成后批量补 commit 和 Why

**【ADR】ADR-002：**

> **备选方案 C**：允许"完成后批量补 commit 和 Why"
> 不选原因：**补写信息容易失真**，
> 无法保证每个可验证子任务和证据一一对应。

**"补写信息容易失真"** —— 事后回忆写的 Why 不是当时的 Why。

### 方案五：等云端 reviewer 说零问题

见 §3.9 的封板协议。**这是"否掉一个终止条件"的罕见案例。**

### 方案六：让 fresh-context review 有放行权

**【源码】`sop-definitions/development.yaml`：**

```yaml
- id: fresh-context-not-approval
  text: Fresh-context 是 finding generator，不是 approval authority
        ——不产出 verdict，不记入 Review Provenance Matrix
  severity: warn
```

**"finding generator, not approval authority"**——
和封板协议里对云端 reviewer 的定性**完全一致**。

**同一个原则在项目里出现了两次，说明它被反复验证过：**

```
作者自己开个新上下文扫一遍代码 → 能发现问题
但不能给自己发放行
所以它不进 Review Provenance Matrix
```

## 6. 如果重新设计

【推断】以下全是我的方案。

### 6.1 reviewer 匹配加"专长匹配"维度

**现在的问题**：匹配只看 family / role / lead / 活跃度，
**不看"这次改的是什么"**。

但 roster 里明明有能力评价：

```json
"evaluation": "主架构师，全栈开发，深度思考强，bug定位弱"
```

**这个字段现在只是给人看的，没进匹配逻辑。**

**我的方案**：

```ts
interface ReviewerMatchOptions {
  author: CatId;
  threadId?: string;
  // 新增：这次改动的特征
  changeProfile?: {
    domains: ('frontend' | 'backend' | 'infra' | 'prompt' | 'schema')[];
    riskLevel: 'low' | 'medium' | 'high';
    touchesSecurityBoundary: boolean;
  };
}

// roster 里加结构化专长
interface RosterEntry {
  // ...
  strengths: ('architecture' | 'bug-hunting' | 'frontend' | 'security' | 'perf')[];
  weaknesses: string[];
}
```

**匹配时**：`changeProfile.domains` 和 `strengths` 求交集，
交集大的排前面。

**收益**：改前端的 PR 优先给擅长前端的 Agent 审，
高风险改动优先给擅长 security 的。

**代价**：
- `changeProfile` 要能自动推导（可以从 diff 的文件路径推，
  和 [模块 09](09-模块-记忆与检索.md) 的"权威度从路径推导"同一招）
- 专长标签会过期（模型升级了能力就变了）→ 需要定期校准

**为什么我认为这个改动有价值？**
因为**跨模型互审的价值来自"盲区互补"**，
而现在只用 family 这一个维度近似"盲区不同"。
family 只保证了"训练数据不同"，不保证"这次改动的盲区互补"。

### 6.2 假阳性率自动统计，不靠人判断

**现在的问题**：封板协议的第二个阈值是
"单轮假阳性比例 >50%"——但**谁来判断哪个 finding 是假阳性？**

现在是靠作者判断 + 在 PR comment 里 pushback。
这有两个问题：
① 作者有动机把真问题也判成假阳性
② 没有累积统计（这个 reviewer 的历史假阳性率是多少？）

**我的方案**：

```
每个 finding 结构化跟踪：
  {
    id, round, file, line, claim,
    disposition: 'fixed' | 'pushed-back' | 'duplicate-of-previous',
    pushbackReason?: string,
    // 关键：第三方确认
    confirmedBy?: { catId, verdict: 'agree-false-positive' | 'disagree' }
  }

统计：
  ├─ 单轮假阳性率 = duplicate-of-previous + agreed-false-positive / total
  ├─ 累积：这个 reviewer 在这个仓库的历史假阳性率
  └─ 累积：这个作者的 pushback 被驳回率（防作者滥用 pushback）
```

**关键是 `confirmedBy`** —— 假阳性判定要有第三方确认，
不能作者一个人说了算。

**收益**：
- 封板阈值从"作者感觉"变成"可审计的数据"
- 能发现"某个 reviewer 在某类文件上假阳性率特别高"→ 针对性调整
- 能发现"某个作者滥用 pushback"→ 反向约束

**这个改动符合项目自己的原则** ——
它到处强调"完成附证据"，那么"这是假阳性"也该附证据。

### 6.3 把"reviewer 不可用"变成可预测的

**现在的问题**：`available` 是个布尔字段，
但额度是**会恢复的**（按小时/天重置）。

现在 Agent 看到"@kimi 没猫粮"，不知道**什么时候会有**。

**我的方案**：

```ts
interface RosterEntry {
  // 替代布尔 available
  availability:
    | { state: 'available' }
    | { state: 'quota-exhausted'; estimatedResetAt: number }   // 从 provider 的 rate limit header 推
    | { state: 'disabled'; reason: string };                    // 人为停用
}
```

prompt 里就能说：

```
[注意] @kimi 额度用尽，预计 2 小时后恢复。
       如果不急，可以 hold_ball 等它；急的话用 @gemini。
```

**收益**：Agent 能做"等还是换人"的判断，而不是只能换人。

**和 [模块 10](10-模块-球权状态机.md) 的 hold 机制天然衔接** ——
"等额度恢复"就是一个典型的 `blocked` 状态 + 探针条件。

**代价**：要从 provider 的响应头里解析 rate limit 信息，
各家格式不同（又是 [模块 06](06-模块-Provider适配.md) 的活）。

### 6.4 给"同族不同个体"加一个真实性校验

**现在的问题**：降级到同族不同个体时，
**假设它们的盲区不完全一样** —— 但这个假设没被验证。

`opus-47` 和 `opus-48` 是不同版本，盲区大概率相似。

**我的方案**：加一个"互审有效性"的事后度量。

```
统计每一对 (author family, reviewer family) 的：
  ├─ 平均发现的 P1/P2 数量
  ├─ merge 后仍然出 bug 的比例
  └─ reviewer 提的 finding 被作者接受的比例

→ 如果发现"同族互审"的这三个指标明显差于跨族
   → 用数据支撑"是否该允许同族降级"这个决策
→ 如果发现某两个 family 的互审效果特别好
   → 优先级里加权
```

**为什么值得？**
因为"跨族优先"现在是一个**未经验证的先验假设**。
它听起来很对（不同模型盲区不同），但**没有数据说明它有多对**、
以及同族降级的损失有多大。

**项目自己有 harness eval 的基础设施（F192）**，
把互审有效性纳进去是自然的延伸。

### 6.5 我不会改的

| 我原本的想法 | 为什么放弃 |
|------------|-----------|
| 允许同一个体自审（只有一只 Agent 时） | 底线不能降；宁可标 isDegraded 让人看到"这次没有真 review" |
| 封板阈值改成动态（按 PR 大小调整） | "机械判定，无弹性"是对的 —— 有弹性就等于没阈值 |
| 让云端 reviewer 变成有状态的（喂它历史） | 那是上游的能力，我控制不了；封板是正确的应对 |
| 去掉"原始需求可引用"这个硬前置 | LLM reviewer 缺上下文不会喊停，这条是必须的 |

## 7. 和其他模块怎么咬合

### 三层落地

```
┌──────────────────────────────────────────────────────┐
│  L0 / prompt 层（模块 07）                             │
│  "跨猫 review 铁律：hotfix PR 必须跨族或同族不同个体    │
│   review，不允许 self-merge"                          │
│  buildReviewerSection → 我当前有哪些 reviewer          │
│  D3 同族分身提醒 → 认清对方是独立个体                   │
├──────────────────────────────────────────────────────┤
│  代码层（本模块）                                       │
│  resolveReviewer  → 帮我选一个（含降级链）             │
│  canReview        → 这只能不能审（含拒绝理由）         │
├──────────────────────────────────────────────────────┤
│  SOP / Skill 层（模块 14）                             │
│  request-review   → 六个硬前置                        │
│  receive-review   → Red→Green 处理                    │
│  merge-gate       → Provenance Matrix + 封板协议       │
│  predicate: handle_check / reviewer_not_author         │
└──────────────────────────────────────────────────────┘
```

### 一根很关键的依赖链

**L0 铁律的措辞是"必须跨族**或同族不同个体**"。**

这就是 [模块 07](07-模块-身份注入.md) D3 段存在的理由：

```
如果 Opus 4.7 和 Opus 4.8 互相以为是"自己的另一个版本"
  → "同族不同个体的 review"就退化成了自审
    → 铁律的第二半失去意义
```

**所以三个东西必须咬合：**

```
roster 的 family + variantLabel 字段（数据）
   ↓
D3 同族提醒（认知）
   ↓
铁律的措辞（规范）
   ↓
predicate reviewer_not_author（机器判定）
```

**四层缺一层，这条纪律就有漏洞。**

### 依赖的共享数据

```
cat-template.json
  ├─ roster（family / roles / lead / available / evaluation）
  │    ├──→ 本模块的匹配
  │    └──→ 模块 07 的队友名册
  └─ reviewPolicy
       ├──→ 本模块的 policy
       └──→ 模块 07 的 buildReviewerSection
```

**一份配置，两个消费者。** 所以它们的判定必须一致 ——
`buildReviewerSection` 里那个 `isEffectivelyAvailable` 的修复
（R6 P2）就是在修这个不一致。

### 和记忆系统的咬合

```
review 请求要求"原始需求可引用"
  → Agent 要能找到原始 Discussion 文档
    → 靠模块 09 的 search_evidence
      → 而 Discussion 的权威度是 candidate（从路径推导）
        → 所以能搜到但不会当成结论
```

### 和 SOP 的咬合

```yaml
- id: review-no-self-review
  text: 同一个体不能 review 自己的代码
  severity: blocker
  predicate:
    type: handle_check
    constraint: reviewer_not_author
```

**这是铁律的机器形态**（[模块 14](14-模块-SOP门禁.md)）。

以及：

```yaml
- id: review-retrigger-after-p1
  text: 收到 P1 修完后没 re-trigger review
  severity: blocker
  predicate:
    type: command_sequence
    must_include: [git push, gh pr comment]
    absent: ["@codex review"]
```

**"做了 A 和 B 但没做 C = 违规"** ——
修完 P1 推了代码、评论了 PR，却没重新触发 review。

## 8. 面试怎么讲

### 30 秒版

见 §0。

### 3 分钟版

> "核心是一条铁律：同一个个体不能 review 自己的代码。
> 因为**同一个模型的盲区是相关的** ——
> 它写的时候没想到的，审的时候也想不到。
>
> 落地成七条规则：排除自己、必须有 peer-reviewer 角色、
> **必须有额度**（注释里写着'40 美刀教训'，
> 因为派给没额度的 Agent 会失败但 token 已经烧了）、
> 优先跨模型家族、优先 lead、优先帖内活跃、
> 都不行才降级到同族不同个体。
>
> 有个排序细节我觉得挺实际：**帖内活跃度优先于 lead 身份**。
> 因为已经在帖子里聊过的 Agent 上下文成本低得多，
> lead 虽然权威但没参与过就得从头读历史。
>
> **降级是显式的**：返回值带 `isDegraded` 和 `degradeReason` 和候选列表。
> 而且 prompt 里连不可用的 reviewer 也列出来，标'没额度'——
> 因为静默降级会让 Agent 反复 @ 一只永远不回应的 Agent。
>
> **但最值钱的是封板协议。**
> 他们发现云端 LLM reviewer 是'无状态抽样信号源'——
> 每轮重放全部历史 comment、分不清已修和未修、不读你的反驳。
> 所以'零 P1/P2'这个终止条件**在数学上没有不动点**，
> 等它说零等于无限循环。
> 实测一个 PR 跑了 21 轮，其中一轮 22 个 finding 里 21 个假阳性。
>
> 于是加了机械闸门：同一 PR 达到 5 轮，
> 或单轮假阳性率超 50%，强制封板 ——
> 处理完当轮 finding 就不再触发云端 review，无论结果，
> 终局确权交给本地**有状态**的 reviewer。
>
> 而且明确写了'机械判定，无弹性'。我觉得这五个字是关键 ——
> 如果阈值是'觉得差不多了',那实际上没有阈值，
> 因为每轮都会有'这轮好像挺重要的'这种感觉。"

### 常见追问

**Q：只有一只 Agent 在线怎么办？**

> "三级降级：跨族 → 同族 lead → 兜底到默认 Agent。
> 但**最后一级会标 `isDegraded: true` 和
> `degradeReason: 'No reviewers available at all'`**。
>
> 底线是'不能是同一个个体'，这条不降级。
> 因为如果允许自审，只有一只 Agent 时流程能走通 ——
> 但 review 完全失去意义，而且会形成'反正能自审'的习惯。
>
> 宁可标记'这次没有真正的 review'让人看到，也不假装审过了。"

**Q：LLM 做 code reviewer 有什么坑？**

> "两个大坑，都在这个项目里有真实记录。
>
> **第一个：它不会说'我信息不够'。**
> 有次 review 信只附了 spec 没附原始需求讨论，
> 结果好几轮 review 全在抓边界条件，
> 没有一轮说'这个 UI 根本不能用'。
> 人类 reviewer 缺上下文会喊停，LLM 会在信息不够的情况下
> 给你一个看起来很专业的答案。
> 所以'原始需求可引用'被列成了硬前置，reviewer 有权拒绝审查。
>
> **第二个：它没有终止条件。**
> 无状态 + 抽样 + 重放历史 comment + 不读反驳 ——
> 这四个特性叠起来，'零问题'这个条件没有不动点。
> 实测 21 轮，单轮 22 个 finding 里 21 个假阳性。
>
> 正确的心智模型是：**LLM reviewer 是高召回低精度的信号源，
> 不是终局确权者**。它负责找可疑点，不负责下结论。
> 终局判断必须由有状态的主体做 ——
> 因为只有有状态的主体才能核对'你上轮说的我已经解释过了'。"

**Q：review 完代码变了怎么办？**

见 §3.8 的话术。

**Q：这套匹配逻辑你觉得缺什么？**

> "缺**专长匹配**。
>
> 现在只看 family、role、lead、活跃度 ——
> 不看'这次改的是什么'。但 roster 里明明有能力评价字段，
> 比如'主架构师，全栈开发，深度思考强，bug 定位弱'——
> **这个字段现在只是给人看的，没进匹配逻辑。**
>
> 我会加一个 `changeProfile`（从 diff 的文件路径自动推导 domain 和风险等级，
> 和他们'权威度从路径推导'是同一招），
> 然后把 roster 的能力评价结构化成 `strengths` 标签，求交集排序。
>
> 更根本地说：**跨模型互审的价值来自盲区互补**，
> 但现在只用 family 这一个维度近似"盲区不同"。
> family 只保证了训练数据不同，不保证这次改动的盲区互补。
>
> 而且我会加一个事后度量：统计每一对
> (author family, reviewer family) 的平均发现 P1/P2 数、
> merge 后仍出 bug 的比例、finding 被接受率 ——
> 用数据验证'跨族优先'这个先验假设到底有多对。
> 他们已经有 harness eval 的设施（F192），纳进去是自然延伸。"

## 9. 本模块要点

| 要点 | 内容 |
|------|------|
| **为什么需要** | 同模型盲区相关；自审等于近视眼查自己视力 |
| **七条规则** | 排除自己 → 有角色 → **有额度** → 跨族 → lead → 帖内活跃 → 降级 |
| **活跃度优先于 lead** | 上下文成本 > 名义权威 |
| **"40 美刀教训"** | 额度检查从软偏好升级成硬规则 |
| **降级显式化** | `isDegraded` + `degradeReason` + `candidates` |
| **不可用的也要列** | 可见的缺席胜过静默的消失 |
| **拒绝带 reason** | Agent 才知道下一步干什么 |
| **LLM reviewer 不会喊停** | 缺上下文会给"专业但错"的答案 → 原始需求是硬前置 |
| **Review Provenance Matrix** | 按 HEAD 变化原因决定 gate owner |
| **谁提的 finding 谁确认** | 别把云端问题丢给本地 reviewer 签字 |
| **封板协议** | 无不动点；5 轮或 50% 假阳性率，机械判定无弹性 |
| **【源码】21 轮 / 22 中 21 假阳性** | 实测数据支撑，写进教训库 LL-072 |
| **信号源 ≠ 确权者** | 同一原则也用在 fresh-context review 上 |
| **【ADR-002】三个否决** | 只记 What / 双轨标准 / 事后补写 |
| **禁止写死 reviewer** | 防模型形成刻板印象 |
| **四层咬合** | roster 数据 → D3 认知 → 铁律规范 → predicate 判定 |
