> **追问：为什么 SQLite 和 Redis 混用？**
> "分工是按数据形态切的：Redis 存**当前状态和事件流**——thread/message/task/session/球权，读写都是点查和有序集合扫描；SQLite 存**要做全文检索和向量检索的知识**——evidence_docs + FTS5 + vec0，这些用 Redis 做不了。两边不共享数据，只有一个方向的投影：消息从 Redis 被 IndexBuilder 编译进 evidence.sqlite 的 passage 表。ADR-020 里把这个叫'真相源在 Redis，索引是编译产物'。"

### 2.2 游标 CAS 的 Lua 脚本

三个游标（delivery / mentionAck / seen）共用一个脚本 `SET_IF_GREATER_LUA`【源码】：

```lua
local cur = redis.call('GET', KEYS[1])
if cur and ARGV[1] <= cur then
  return 0
end
redis.call('SET', KEYS[1], ARGV[1], 'EX', tonumber(ARGV[2]))
return 1
```

**为什么能用字典序比较**：messageId 由 `generateSortableId()` 生成【源码 `ports/MessageStore.ts`】：
```ts
export function generateSortableId(timestamp: number): string {
  const ts = String(timestamp).padStart(16, '0');
  const seq = String(_seq++).padStart(6, '0');
  const suffix = randomUUID().slice(0, 8);
  return `${ts}-${seq}-${suffix}`;
}
```
16 位零填充的时间戳 + 6 位进程内自增序号 + 8 位 UUID 片段 → 字典序 == 时间序。所以 Lua 里一个 `<=` 字符串比较就完成了单调推进保护。

> **追问：为什么时间戳要 padStart(16)？**
> "因为 `Date.now()` 现在是 13 位，如果不补齐，等到 2286 年变 14 位时字典序就断了。padStart(16) 一次买断到很远的未来。中间那 6 位 seq 是进程内自增，解决同毫秒多条消息的顺序问题；最后 8 位 UUID 片段是防多进程同毫秒同 seq 撞车。"

```ts
export function serializeExtra(extra: NonNullable<StoredMessage['extra']>): string {
  const { tracing, ...rest } = extra;
  if (!tracing) return JSON.stringify(extra);
  const compact: Record<string, string> = { t: tracing.traceId, s: tracing.spanId };
  if (tracing.parentSpanId) compact.p = tracing.parentSpanId;
  return JSON.stringify({ ...rest, tracing: compact });
}
```
读侧同时接受两种键名：`const t = tr.t ?? tr.traceId;`——注释写明目的是「stay within AC-F6 100-byte budget per pointer」。

```ts
// Cloud R12 P2: require strictly all-digit suffix so "123abc" is rejected.
// parseInt("123abc") === 123 (not NaN), but the projector regex requires /^\d+$/;
// accepting partially-numeric keys leaves unprojectable events in the event log.
```

> **追问：这个校验解决的是什么真实故障？**
> "解析器宽松、投影器严格 → 事件被 append 进 log 但永远投不出来，变成幽灵事件。修法是把解析器收紧到和投影器同样严格，宁可在入口拒绝。"

## 3. 主流程逐段拆解

这一节按「一条消息落盘」和「一次调用鉴权落盘」两条主线拆。

### 3.1 消息落盘：`RedisMessageStore.append()`

**第一段：幂等 claim**【源码】

```ts
const id = generateSortableId(msg.timestamp);
const idempotencyIndexKey = msg.idempotencyKey
  ? MessageKeys.idempotency(msg.userId, threadId, msg.idempotencyKey)
  : null;

if (idempotencyIndexKey) {
  const existingId = await this.redis.get(idempotencyIndexKey);
  if (existingId) {
    const existingMessage = await this.getById(existingId);
    if (existingMessage) return existingMessage;      // 命中 → 直接返回旧消息
    await this.redis.del(idempotencyIndexKey);        // 索引指向已消失的消息 → 清掉
  }
  const claimed =
    this.ttlSeconds === null
      ? await this.redis.set(idempotencyIndexKey, id, 'NX')
      : await this.redis.set(idempotencyIndexKey, id, 'EX', this.ttlSeconds, 'NX');
  if (claimed !== 'OK') {
    // 并发竞争：别人抢到了，读他写的
    const claimedId = await this.redis.get(idempotencyIndexKey);
    if (claimedId) { /* ... */ }
    throw new Error('message idempotency key contention');
  }
}
```

为什么这么写：**先读后 claim 是快路径，claim 失败再读一次是慢路径**。两次读之间用 `SET NX` 卡死并发。坑在于：如果 claim 失败且 `claimedId` 对应的消息还没写完（另一个进程正在 pipeline 中间），这里会抛 `message idempotency key contention`——这是一个**明确抛出而不是静默重试**的选择。

**第二段：Hash 写入**【源码】

```ts
pipeline.hset(hashKey, {
  id, threadId,
  userId: msg.userId,
  catId: msg.catId ?? '',                                    // null → 空串
  content: msg.content,
  contentBlocks: msg.contentBlocks ? JSON.stringify(msg.contentBlocks) : '',
  toolEvents: msg.toolEvents ? JSON.stringify(msg.toolEvents) : '',
  metadata: msg.metadata ? JSON.stringify(msg.metadata) : '',
  extra: msg.extra ? serializeExtra(msg.extra) : '',
  mentions: JSON.stringify(msg.mentions),
  timestamp: String(msg.timestamp),
  ...(msg.thinking ? { thinking: msg.thinking } : {}),
  ...(msg.origin ? { origin: msg.origin } : {}),
  // ... 其余可选字段都是 spread 条件写入
});
```

**坑**：可选字段用 `...(cond ? {k:v} : {})` 而不是写空串，是因为 Hash 字段一旦写了空串，`HGETALL` 会返回 `''`，解析器要额外判空。但前 8 个必填字段又用了空串占位——不一致的原因是那 8 个字段的解析器（`safeParseXxx`）都以 `if (!raw) return undefined` 开头，空串等价于缺失。

**第三段：四个索引 ZSet**（`msg:timeline` / `msg:user:{u}` / `msg:thread:{t}` / `msg:mentions:{cat}`）——score 都是 `msg.timestamp`。

**第四段：TTL 决策**【源码】
```ts
const DEFAULT_TTL_SECONDS = 0; // persistent — set >0 via env to enable expiry
// ...
const raw = options?.ttlSeconds ?? DEFAULT_TTL_SECONDS;
if (!Number.isFinite(raw) || raw <= 0) {
  this.ttlSeconds = null;      // null = 永不过期
} else {
  this.ttlSeconds = Math.floor(raw);
}
```
注意：**`ttlSeconds` 内部用 `null` 表示"不过期"，不是 0**。这是为了让 `this.ttlSeconds === null` 这种判断在类型上干净。

> **追问：这个 DEFAULT_TTL_SECONDS = 0 是怎么来的？**
> "是一次事故的产物。`assets/prompt-templates/l4-iron-laws.md` 第 5 条铁律写着：'用户状态默认持久化——用户可见、可追溯、可恢复预期的数据（thread / message / task / memory 等）默认持久化（TTL=0）。TTL 只能由用户主动 opt-in。违反 = P0 bug（来源 LL-048）'。在这之前 `DEFAULT_TTL_SECONDS` 是 `7 * 24 * 60 * 60`，F102 的文档里 KD-46 明确记了这次修正：'KD-32 假设真相源在 Redis（TTL=0 永久），实际 DEFAULT_TTL_SECONDS = 604800（7 天），.env 未覆盖'——也就是说记忆索引曾经依赖一个 7 天就消失的层。"

### 3.2 调用鉴权落盘：`RedisAuthInvocationBackend`

这是全项目 Lua 用得最重的地方。Schema 头注释【源码】：
```
- auth:inv:{invocationId}                 → Hash (record fields, expiresAt)
- auth:inv:{invocationId}:msgs            → Set (clientMessageIds)
- auth:latest:{threadId}:{catId}          → String (latest invocationId)
All keys carry PEXPIREAT(expiresAt) so Redis natively reaps expired records.
```

**create：一次 Lua 写两个 key**【源码 `CREATE_LUA`】
```lua
local n = #ARGV
local hashFields = {}
for i = 1, n - 2 do hashFields[i] = ARGV[i] end
redis.call('HSET', KEYS[1], unpack(hashFields))
-- Grace: 60s past logical expiry so Lua can return 'expired' before reaper hits.
local graceMs = tonumber(ARGV[n]) + 60000
redis.call('PEXPIREAT', KEYS[1], graceMs)
redis.call('SET', KEYS[2], ARGV[n - 1])
redis.call('PEXPIREAT', KEYS[2], graceMs)
return 1
```

**60 秒宽限期是整个设计的关键**：如果 key 在逻辑过期那一刻就被 Redis 删掉，验证时只能返回 `unknown_invocation`（"这个调用不存在"）；多留 60 秒，Lua 就能读到 `expiresAt` 已过期的记录，返回精确的 `expired`（"过期了，去 refresh"）。前端提示词完全不同。

**verify：验证 + 滑动 TTL 一次原子完成**【源码 `VERIFY_LUA`】
```lua
local exists = redis.call('EXISTS', KEYS[1])
if exists == 0 then return {'fail', 'unknown_invocation'} end
local stored = redis.call('HGET', KEYS[1], 'callbackToken')
if stored ~= ARGV[1] then return {'fail', 'invalid_token'} end
local expiresAt = tonumber(redis.call('HGET', KEYS[1], 'expiresAt'))
if not expiresAt or tonumber(ARGV[2]) > expiresAt then
  redis.call('DEL', KEYS[1])
  return {'fail', 'expired'}
end
redis.call('HSET', KEYS[1], 'expiresAt', ARGV[3])
redis.call('PEXPIREAT', KEYS[1], tonumber(ARGV[3]) + 60000)
return {'ok', redis.call('HGETALL', KEYS[1])}
```

**verifyLatest：多加一个 stale 检查**【源码 `VERIFY_LATEST_LUA`】，比 `VERIFY_LUA` 多两段：
```lua
local latest = redis.call('GET', KEYS[2])
if latest ~= ARGV[4] then return {'fail', 'stale_invocation'} end
-- ...
redis.call('PEXPIREAT', KEYS[2], tonumber(ARGV[3]) + 60000)   -- latest 指针也滑
```
注释写明动机：
> `Closes race window between preValidation isLatest check and preHandler verify slide (cloud Codex P2 #1368, 05de7c98b). All checks + slide happen in one Redis round-trip — concurrent create() can't sneak in.`

**verify() 里的三个"不做"决策**【源码注释】：
1. **不加载 msgs Set**：`F174-B P2 (cloud Codex review #1363): don't load idempotency set on every verify(). It's hot path` → 返回空 Set。
2. **但仍滑 msgs 的 TTL**：`await this.redis.pexpireat(KEY_MSGS(invocationId), newExpiresAt + 60_000)` —— 注释说 `PEXPIREAT on a non-existent msgs key is a no-op so this is safe`。
3. **latest 指针只在还指向自己时才滑**：
```ts
if (fields.threadId && fields.catId) {
  const latestKey = KEY_LATEST(fields.threadId, fields.catId);
  const currentLatest = await this.redis.get(latestKey);
  if (currentLatest === invocationId) {
    await this.redis.pexpireat(latestKey, newExpiresAt + 60_000);
  }
}
```
理由【源码注释】：`We only slide if the pointer still references THIS invocationId — otherwise a newer create() already overwrote it and we shouldn't extend that newer pointer's life on behalf of an old verify.`

**claimClientMessageId 的有界 Set**【源码】：
```ts
const MAX_CLIENT_MESSAGE_IDS = 1000;
// ...
const count = await this.redis.scard(KEY_MSGS(invocationId));
if (count > MAX_CLIENT_MESSAGE_IDS) {
  await this.redis.spop(KEY_MSGS(invocationId));   // 随机淘汰
}
```
注释坦白：`random eviction — acceptable since dedup window is best-effort, not a security boundary`。

> **追问：为什么 verify 有三个变体（peek / verify / verifyLatest）？**
> "`peek()` 是纯读，不滑 TTL——用在 refresh-token 的 onRequest 钩子里，注释写明是 'gpt52 P1 #2 — bad-auth 请求 not allowed to burn cooldown slot'，即坏 token 不能消耗冷却名额。`verify()` 验证 + 滑窗。`verifyLatest()` 额外验证'你是不是这个 thread+cat 上最新的调用'，用来挡住旧调用的迟到回调。还有个 `peekRecord()` 是'忽略过期、绝不删除'的纯读，注释说是给 401 通知器用的——verify 刚把记录删了，通知器还需要元数据。"

### 3.3 RuntimeSessionStore 的 Lua 前缀陷阱

`RedisRuntimeSessionStore.ts` 头注释【源码】：

### 3.4 SCAN 的前缀往返

`RedisSessionChainStore.scanKeys()`【源码】——这是全项目 SCAN 的参考实现，被 `session-strategy-overrides.ts` 显式引用：
```ts
private async scanKeys(pattern: string): Promise<string[]> {
  const prefix = (this.redis.options as { keyPrefix?: string }).keyPrefix ?? '';
  const prefixedPattern = `${prefix}${pattern}`;
  return new Promise((resolve, reject) => {
    const keys: string[] = [];
    const stream = this.redis.scanStream({ match: prefixedPattern, count: 100 });
    stream.on('data', (batch: string[]) => {
      for (const k of batch) {
        // Strip prefix so subsequent auto-prefixing commands work
        const stripped = prefix && k.startsWith(prefix) ? k.slice(prefix.length) : k;
        keys.push(stripped);
      }
    });
    stream.on('end', () => resolve(keys));
    stream.on('error', reject);
  });
}
```

**规律（背下来）**：
```
命令类型                       ioredis 自动加前缀？
────────────────────────────────────────────────
GET/SET/HSET/ZADD/... 普通命令      ✅ 是
EVAL 的 KEYS[] 参数                 ✅ 是
EVAL 的 ARGV[] 里拼出来的 key        ❌ 否（脚本内必须手拼）
SCAN / scanStream 的 MATCH 模式      ❌ 否（必须手拼）
SCAN 返回的 key                     ❌ 带真实前缀（必须手剥）
```

`session-strategy-overrides.ts` 的 `hydrateFromRedis()` 还多做了一件事——**临时 Map 全量成功后才 swap**【源码】：
```ts
// Build into a temporary map — only swap to _cache on full success.
// If SCAN fails mid-way, _cache stays empty (clean fallback) rather than
// holding a partial subset that silently drops some overrides.
const tempCache = new Map<string, Partial<SessionStrategyConfig>>();
// ... scan loop ...
// Atomic swap: replace cache contents (not append) so deleted Redis keys
// don't linger in memory after re-hydration.
_cache.clear();
for (const [catId, override] of tempCache) _cache.set(catId, override);
```

### 3.5 SQLite 迁移主流程

`applyMigrations(db)`【源码 `memory/schema.ts`】的骨架：
```ts
db.exec(`CREATE TABLE IF NOT EXISTS schema_version (
  version INTEGER PRIMARY KEY, applied_at TEXT NOT NULL)`);   // P1 fix (codex review R2)

const currentVersion =
  (db.prepare('SELECT MAX(version) as v FROM schema_version').get() as { v: number | null })?.v ?? 0;

if (currentVersion < 1) { db.exec(SCHEMA_V1); /* + FTS 触发器 */ ; stamp(1); }
if (currentVersion < 2) { ... }
// ... 一直到 26
```

三个必须记住的实现细节：

1. **ALTER TABLE 一律包 try/catch**【源码】
```ts
try { db.exec('ALTER TABLE evidence_docs ADD COLUMN pack_id TEXT'); }
catch { /* Column may already exist from a partial migration */ }
```
理由：SQLite 没有 `ADD COLUMN IF NOT EXISTS`；半途失败的迁移会留下已加的列。

2. **FTS5 触发器必须逐条 exec**【源码注释】：`FTS5 external-content sync triggers — must be executed one statement at a time`，所以定义成 `FTS_TRIGGER_STATEMENTS: string[]` 而不是一个大字符串。

3. **vec0 表不进迁移，单独 fail-open**【源码】
```ts
export function ensureVectorTable(db: Database.Database, dim: number): boolean {
  try {
    db.exec(`CREATE VIRTUAL TABLE IF NOT EXISTS evidence_vectors USING vec0(
      anchor TEXT PRIMARY KEY, embedding float[${dim}])`);
    return true;
  } catch {
    return false; // sqlite-vec not loaded — fail-open
  }
}
```
因为 `sqlite-vec` 是可选扩展，装不上时整个记忆系统要退化成纯词法检索，而不是启动失败。

**PRAGMA 设置**【源码 `PRAGMA_SETUP`】：
```sql

PRAGMA journal_size_limit = 67108864;   -- 64 MB
PRAGMA foreign_keys = ON;
```

#### event-memory.sqlite（F227）

单表 `event_memory`：`eventId`(PK), `type`, `trigger_type`, `cat`, `threadId`, `messageId`, `timestamp`, `summary`, `cognitiveTransition`, `relatedHarness`, `confidence`, `ownerUserId DEFAULT ''`。

索引 6 个：`idx_event_threadId`、`idx_event_coord(threadId,messageId)`、`idx_event_trigger`、`idx_event_timestamp`、`idx_event_confidence`、`idx_event_owner`，外加 **`UNIQUE INDEX idx_event_owner_coord_type ON event_memory(ownerUserId, threadId, messageId, type)`**。

它没有 `schema_version` 表，升级靠**列探测 + 去重再建唯一索引**【源码】：
```ts
const hasOwner = (db.prepare(`PRAGMA table_info(event_memory)`).all() as Array<{name:string}>)
  .some((c) => c.name === 'ownerUserId');
if (!hasOwner) db.exec(`ALTER TABLE event_memory ADD COLUMN ownerUserId TEXT NOT NULL DEFAULT ''`);
db.exec(`
  DROP INDEX IF EXISTS idx_event_coord_type;
  DELETE FROM event_memory WHERE rowid NOT IN (
    SELECT MIN(rowid) FROM event_memory GROUP BY ownerUserId, threadId, messageId, type
  );
  CREATE UNIQUE INDEX IF NOT EXISTS idx_event_owner_coord_type
    ON event_memory(ownerUserId, threadId, messageId, type);
`);
```
> **追问：为什么要先 DELETE 再建唯一索引？**
> "因为老库（加 owner 列之前）可能已经有重复行，直接建 UNIQUE 索引会失败，`initialize()` 就永远起不来。先按 `MIN(rowid)` 保留每组最早那条，再建索引——注释写的就是 `so initialize() never fails on a DB with duplicates`。另外 owner 回填用空串而不是 'default-user'，注释说 `Existing un-owned rows get '' and stay unreachable to any real authenticated owner (safe-by-default, no cross-user leak)`——宁可让老数据不可见也不误归属。"

> `catId uses z.string().refine() (via catIdSchema) instead of z.enum() because route modules are imported before the registry is populated. z.string().refine() defers validation to request time.`

## 7. 面试追问应对

**Q1：为什么 Redis key 用冒号分层而不是一个大 JSON？**
> "三个原因。一是索引要用 ZSet 的 score 排序——`msg:thread:{tid}` 用 timestamp 当 score，取最近 50 条就是一次 `ZREVRANGE`，塞大 JSON 里就得全量读出来在应用层排。二是字段级更新——`RedisThreadStore` 的 CAS 只 HSET 一个字段，大 JSON 每次读-改-写，并发就完了。三是 TTL 粒度——`auth:inv:{id}` 和 `auth:inv:{id}:msgs` 分开，前者到期后者自然成孤儿被 TTL 收走，而不是一个对象里半个过期。代价是一次业务读多次往返，项目用 pipeline 和 Lua 把它压回一次。"

**Q2：`cat-cafe:` 前缀怎么工作的，有什么坑？**
> "前缀由 ioredis 的 `keyPrefix` 统一加，所以业务代码里所有 key 都是裸的。坑是 ioredis 只对普通命令和 EVAL 的 KEYS[] 自动加前缀，对 SCAN 的 MATCH 模式**不加**、对 Lua 脚本内 ARGV 拼出来的 key 也**不加**。项目踩过这个坑，现在有两套固定写法：SCAN 走 `scanKeys()`——手动加前缀匹配、手动剥前缀返回；Lua 走『keyPrefix 当 ARGV 传进去，脚本内手拼』。两处注释都标着 LL-016，说明有正式的 lesson learned 编号。"

**Q3：TTL 默认 0，不怕 Redis 撑爆？**
> "这是铁律 #5 的直接后果——`assets/prompt-templates/l4-iron-laws.md` 第 5 条：『用户状态默认持久化（TTL=0），TTL 只能由用户主动 opt-in，违反 = P0 bug』，来源 LL-048。之前 message 默认 TTL 是 7 天，导致 F102 的记忆索引依赖了一个会消失的层，文档 KD-46 明确记了这次修正。撑爆问题靠**区分数据类别**解决：用户可见数据 TTL=0；运行态有 TTL——`freshness:state` 30 分钟、`idemp:*` 5 分钟、`dedup:propose` 10 分钟、`tool-event-log` 7 天、`grounding:samples` 8 天。判据是『用户会不会期望重启后它还在』。"

**Q4：那个 8 天的 grounding TTL 为什么不是 7 天？**
> "注释写得很直白：`operator directive: TTL must exceed weekly eval cron period to avoid TTL-vs-cron race (sample expires before eval reads it)`。周评测 cron 是 7 天周期，样本 TTL 也 7 天就会出现 cron 还没跑样本先过期。这是『TTL 必须大于消费周期』的标准例子，多留一天缓冲。"

**Q5：SQLite 26 个迁移版本怎么保证不出事？**
> "四条纪律。一，版本号存在 `schema_version` 表，`applyMigrations` 按 `if (currentVersion < N)` 逐级往上跑，天然幂等。二，所有 `ALTER TABLE ADD COLUMN` 单独 try/catch，因为 SQLite 没有 `IF NOT EXISTS`，半途失败的迁移会留下已加的列。三，新增列一律可空或带 DEFAULT，从不加 NOT NULL 无默认的列。四，需要回填的迁移（V25 加 `thread_id`）在同一个版本块里跑 UPDATE，从 `task_trajectories` 反查 `invocation_id → thread_id`。已知风险是这些迁移不在一个事务里，`db.exec` 逐条执行，中途崩会停在半路——所以每条都必须幂等。"

**Q6：`evidence_docs` 从 11 列涨到 26 列，算表设计失败吗？**
> "不算。加的都是**同一个实体的正交属性**：`pack_id` 是归属、`provenance_*` 是来源、`authority`/`activation` 是可信度和激活方式、`world_id`/`scene_id` 是叙事域、`collection_id` 是集合。它们都描述『这条知识本身』，没有引入一对多。真正该拆的部分已经拆了——passage 拆到 `evidence_passages`、向量拆到 `evidence_vectors`（注释明说 `decoupled`）、指标拆到 `anchor_recall_metrics`。如果重来，我会把 F163 那三组实验性字段（authority 组、compression 组、contradiction 组）收进一个 JSON 列或者 EAV 表，因为它们可能整组下线。"

**Q7：`.cat-cafe/` 全部 gitignore，新机器怎么起来？**
> "分三类。一、**可从 git 内容 bootstrap**：`cat-catalog.json` 从仓库根的 `cat-template.json` 生成（还会 `pruneRosterToRuntimeBreeds` 修剪 roster），`capabilities.json` 从发现结果 bootstrap（扫 `.claude/mcp.json` 这类外部配置导入）。二、**必须用户填**：`accounts.json` / `credentials.json`。三、**可以丢**：venv 目录、`proxy-upstreams.json`（每次调用重写）、`user-preferences.json`（丢了回落模板顺序）。`.gitignore` 那行注释很直白：`Runtime state (bootstrapped per-machine from cat-template.json)`。"

**Q8：消息 id 为什么不用 UUID 或雪花？**
> "需要**字典序 == 时间序**且**不依赖外部服务**。`generateSortableId()` = 16 位零填充毫秒 + 6 位进程内序号 + 8 位 UUID 片段。UUIDv4 完全无序，做不了游标 CAS；雪花要分配 workerId，本地单机应用引入太重。代价是 id 长 30 字符且泄露时间，换来的是游标推进只需 Lua 里一个字符串 `<=`、ZSet member 天然有序、跨进程无需协调。UUIDv7 现在能达到同样效果，重做我会直接用 UUIDv7。"

**Q9：Redis 挂了会怎样？**
> "分启动时和运行中。启动时 `assertStorageReady()` 检查：`REDIS_URL` 没配且 `MEMORY_STORE !== '1'` 直接抛异常拒绝启动——注释叫『fail-closed storage guard』，刻意如此，防止静默降级成内存模式让用户以为数据存住了。运行中：ioredis `retryStrategy` 重试 3 次（200/400/600ms），超了返回 null 放弃重连，`maxRetriesPerRequest: 3`，之后所有操作抛错。项目里**没有**全局熔断降级——各 Store 的 catch 只保护 JSON 解析失败，不保护连接失败。这是个已知缺口，我会补一层 Redis 健康探针 + 前端只读横幅。"

**Q10：多个 API 实例同时跑会怎样？**
> "有 `runtime:api-instance-lease:v1` 租约 key，配三个 Lua：`RENEW`（GET 等于自己的 token 才 PEXPIRE）、`RELEASE`（比对后 DEL）、`STEAL`（比对后换新 token）。租约持有者是 `{version, token, instanceId, pid, hostname, apiPort, cwd, startedAt, acquiredAt}`，失效原因分 `renew_failed` 和 `lease_lost`。所以设计上是**单活**。仍有一处没被租约覆盖：`session-strategy-overrides.ts` 的内存 cache 只在启动时 hydrate 一次，别的实例改了 Redis 它不知道【推断】——单活假设下不是问题，真要多活就得加 pub/sub 失效通知。"

**Q11：球权和社区两套事件流长得一模一样，为什么不抽象？**
> "`ball-custody-keys.ts` 的注释直接写『照 community-keys』，两边都是 `{ns}:events:log:{subjectKey}` List + `{ns}:events:seen` Set + `{ns}:events:subjects` Set + 投影 String + index Set 这五件套。我认为是**克制的重复**：两个域的事件 kind 完全不同（球权 17 种）、状态机不同、投影字段不同，真正能共用的只有『append-only + sourceEventId 去重 + 纯投影』这三条**模式**，抽成基类会得到一堆泛型参数。项目选了复制五个 key 模板 + 注释互相引用。代价是改一处要记得改另一处；出现第三个域时我会抽一个 `createEventLogKeys(namespace)` 工厂。"

**Q12：`blockedCats` 为什么用黑名单不用白名单？**
> "注释定义了完整语义：`undefined/absent = all cats can use it. Empty array = all cats can use it. Contains all cat IDs = fully disabled.`——默认全开，符合『新加的 MCP 应该所有猫都能用』的直觉。白名单的话每加一只新猫就要改所有 MCP 的白名单，运维负担线性增长。它替代的老字段 `overrides: [{catId, enabled}]` 已标 `@deprecated` 且注释说『运行时忽略，只为反序列化老配置保留』——从『每猫一条记录』改成黑名单本身就是这个考虑的结果。"

**Q13：类型 8966 行、75 个文件，怎么不失控？**
> "三条约束。一、`types/` **只放类型**，零运行时逻辑（例外是 `ids.ts` 的 11 个工厂函数和几个类型守卫）。二、按 feature 切文件不按层——`ball-custody.ts` / `concierge.ts` / `feat-trajectory.ts` 都对应一个 F 编号，删 feature 就删整个文件。三、`index.ts` 866 行全是 re-export，唯一对外门面，按 feature 分段注释。失控信号已经有了：`capability.ts` 505 行 31 个类型，混了持久化 schema（`CapabilitiesConfig`）、API 响应（`CapabilityBoardResponse`）、请求体（`McpInstallRequest`）三种关注点，该拆成 `capability.ts` / `capability-api.ts`。"

**Q14：为什么 Zod 用 `z.string().refine()` 而不是 `z.enum()` 校验 catId？**
> "`message.schema.ts` 的注释解释了：`route modules are imported before the registry is populated. z.string().refine() defers validation to request time.` 猫的 id 集合是运行时才知道的——从 `.cat-cafe/cat-catalog.json` 加载进 `catRegistry`，而路由模块在那之前就 import 完了。`z.enum` 在定义时就要拿到值，只能用延迟到请求时的 `refine`。副作用是在 `z.discriminatedUnion('type', ...)` 里，catId 的校验发生在字段层不是判别层——注释也写明了这个后果。"

**Q15：`sop-definition.generated.ts` 是生成的，源在哪？**
> "文件名带 `.generated`，370 行，导出 5 类型 + 5 常量 + 4 函数；仓库根有 `sop-definitions/` 目录。所以是从 SOP 定义文件生成 TS 常量和联合类型。【推断】价值在于把 SOP 阶段 id（`DevelopmentSopStageId` / `RuntimeSopStageId`）变成编译期可穷举的联合类型，写 switch 时靠 TS 检查漏分支。"

**Q16：为什么每个 Store 都有内存和 Redis 两套实现？**
> "工厂模式统一：`createXxxStore(redis?)`，有 redis 返回 Redis 实现，没有返回内存实现。接口和内存实现同住在 `ports/*.ts`，Redis 实现在 `redis/*.ts`。好处有三：`pnpm start --memory` 能零依赖跑起来给新用户试；单测不需要起 Redis；接口被两个独立实现验证过，不会长出 Redis 特有的方法。代价是行为要对齐——比如内存版 `MessageStore` 也实现了 idempotencyIndex 和 contentDedupIndex（带过期时间戳的 Map），不然两套语义会漂。"

### 8.4 判定规则速记

```
─── 是否给数据设 TTL？──────────────────────────────
  用户可见 / 可追溯 / 期望重启后还在？
    ├─ 是 → TTL = 0（铁律 #5 / LL-048，违反 = P0）
    └─ 否 → 运行态，按消费周期设，且 TTL > 消费周期
             （grounding 8 天 > 周 cron 7 天）

─── ioredis 会不会自动加前缀？───────────────────────
  普通命令 / EVAL 的 KEYS[]      → 会
  EVAL 内 ARGV 拼的 key          → 不会（脚本内手拼）
  SCAN 的 MATCH / SCAN 返回值    → 不会（手拼 + 手剥）

─── index 用什么结构？──────────────────────────────
  按时间/序号取 topN → ZSet（score = timestamp 或 seq）
  只要存在性判断      → Set（events:seen、running invocations）
  要 field 级读写     → Hash（read-state、thread activity、task-progress）
  1:1 映射            → String（tasks:subject、session-active、auth:latest）
  有序追加            → List（ballcustody / community events:log）

─── detail 和 index 分开吗？────────────────────────
  分。统一模式：detail Hash/String + 一到多个索引 ZSet/Set
  理由：索引可 rebuild，detail 不动

─── 新增 process.env.XXX？──────────────────────────
  必须在 env-registry.ts 的 ENV_VARS 注册
  标 exampleRecommended:true 的还要进 .env.example（CI 卡）

─── 事件流的幂等键怎么定？──────────────────────────
  从上游已有痕迹派生，不新建 ID：
  route:{messageId} / inv:{invocationId}:started / task:{taskId}:done
  / comment:{repo}#{n}:{commentId} / euthanasia:{subject}:{kind}:{at}

─── SQLite 加字段的规矩？───────────────────────────
  1. 单独 ALTER，包 try/catch（没有 IF NOT EXISTS）
  2. 可空或带 DEFAULT，不加 NOT NULL 无默认列
  3. 需要回填就在同一版本块里跑 UPDATE
  4. 加完 stamp schema_version
```

### 8.6 一分钟口述版

> "存储分三层。Redis 是**运行态和事件流的真相源**——ioredis 统一加 `cat-cafe:` 前缀，约 130 个 key 模板集中在 27 个 `redis-keys/*.ts` 文件里，全部是纯字符串模板零 IO；模式是 detail Hash + 索引 ZSet/Set 分离；用户可见数据 TTL 一律 0，这是写进铁律的（LL-048），运行态数据才有 TTL。并发安全靠 13 个 Lua 脚本——游标单调用字典序 CAS、鉴权记录留 60 秒宽限窗好区分『过期』和『不存在』、终态和索引在一个脚本里提交消除崩溃窗口。
>
> SQLite 是**知识检索层**——`evidence.sqlite` 走到第 26 版迁移，主表 `evidence_docs` 加 FTS5 全文和 vec0 向量两个虚表；vec0 和 embedding 都是 fail-open，装不上就退化成纯词法。另外三个小库分管世界引擎、事件记忆、任务结局。
>
> 文件系统是**配置和交接层**——`cat-template.json` 在 git 里做基线，`.cat-cafe/` 全部 gitignore 做每机器运行态，两者是 base + delta overlay 关系；`docs/markers/*.yaml` 是 marker 的真相源而 SQLite 只是镜像；`~/.cat-cafe/callback-outbox/` 是回调至少一次投递的落盘队列。
>
> 最值得讲的一致性风险是 MCP 配置——全局配置、每项目 capabilities.json、三份生成的 CLI 配置，靠 `mcpSync.sourceConfigHash` 这个 SHA-256 对账。"
