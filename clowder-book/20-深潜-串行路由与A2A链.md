### 1.3 职责边界（哪一层能有副作用）

| 层 | 文件 | 能不能有副作用 | 出处 |
|---|---|---|---|
| 决策层 | `routing-decision.ts` | **不能**。不 push worklist、不 mutate streak、不建 span、不 yield | 【源码】文件头注释"**不做任何副作用** …… 都留在 routeSerial 执行层" |
| 判据层 | `verdict-detect` / `void-hold-detect` / `final-routing-slot` / `routing-guard-remedial` | 纯函数，只返回布尔或结构体 | 【源码】各文件头"纯函数：route-serial 层负责调用 + 广播" |

| 执行层 | `route-serial.ts` | 全部副作用集中在这里 | 【源码】`routing-decision.ts` 头注释 + route-serial 内联注释"side effects stay here" |

> **面试官追问："这个分层是原本就设计好的吗？"**
> > 不是，是 F216 重构才切出来的，而且只切了一半。F216 的 spec 里写得很直白：立项时 routeSerial 是 2302 行、cognitive complexity 255，5 套并行路由路径共享同一个可变 worklist，加任何决策都会笛卡尔积式炸 edge case——引爆点是 F215 的 relay 改了 7 轮 review。重构后决策变成了纯函数 `resolveRoutingDecisions`，可以独立单测；但 AC-B2 明确标了 **NOT ACHIEVED**：complexity 还是 255，行数反而从 2302 涨到 3687。owner 的口径是"F216 交付的是 last-wins 用户价值 + routing decision 可测性，不是 routeSerial 瘦身"，瘦身转成独立技术债。这个诚实的验收记录本身就是我想强调的工程文化。

## 2. 核心数据结构

### 2.1 `WorklistEntry`（`WorklistRegistry.ts`）

```ts
export interface WorklistEntry {
  /** The mutable worklist array — push to extend */
  list: CatId[];
  /** Number of original user-selected targets at registration time */
  originalCount: number;
  /** A2A depth counter — incremented on each push */
  a2aCount: number;
  /** Max allowed A2A depth */
  maxDepth: number;
  /** Index of the cat currently being executed (updated by routeSerial). */
  executedIndex: number;
  a2aFrom: Map<CatId, CatId>;
  a2aTriggerMessageId: Map<CatId, string>;
  streakPair?: { from: CatId; to: CatId; count: number };
}
```

逐字段解释"为什么存在"：

| 字段 | 为什么存在 | 证据 |
|---|---|---|
| `list` | 就是 routeSerial 局部的那个 `worklist` 数组的**同一个引用**（`registerWorklist(threadId, worklist, ...)` 直接存进去）。所以外部 callback push 进来，routeSerial 的 `while (index < worklist.length)` 立刻能看到 | 【源码】`const worklist = [...targetCats]; ... registerWorklist(threadId, worklist, maxDepth, options.parentInvocationId)` |
| `originalCount` | 区分"用户原始选的猫"和"A2A 追加的猫"。原始 target 必须回复用户，不能被 A2A 抢走 replyTo 语义 | 【源码】`pushToWorklist` 里 `const isOriginalPendingTarget = existingIndex !== -1 && existingIndex < entry.originalCount` |
| `a2aCount` | 深度预算的**唯一计数器**。注意它数的是"push 了几只 A2A 猫"，不是链的层数 | 【源码】字段注释 "A2A depth counter — incremented on each push" |
| `executedIndex` | 给 dedup 用："已经跑过的猫可以重新入队（A→B→A 互审）"，只对未执行的尾部去重 | 【源码】`pushToWorklist` 注释 "Dedup only against pending (not-yet-executed) portion" |
| `a2aFrom` | 目标猫 → 谁 @ 了它。注入 prompt 的 `directMessageFrom`（"Direct message from …; reply to …"） | 【源码】字段注释 |
| `a2aTriggerMessageId` | 目标猫 → 触发它的那条消息 id。用于 auto-replyTo，让回复挂在 @ 那条消息下面 | 【源码】字段注释 + F121 |
| `streakPair` | 乒乓熔断器的状态。**无序对**（A↔B 视为同一对），带计数 | 【源码】`samePair()` 双向比较 |

### 2.3 `RoutingSignal` / `RoutingDecision` / `RoutingContext`（`routing-decision.ts`）

```ts
export type RoutingSignal =
  | { type: 'inline_mention'; cats: CatId[]; content: string; callerCatId: CatId }
  | { type: 'relay_malformed'; cat: CatId; callerCatId: CatId }
  | { type: 'deferred'; cats: CatId[]; content: string; callerCatId: CatId };

export type RoutingDecision =
  | { action: 'enqueue_worklist'; cat: CatId }   // 执行层：worklist.push + updateStreakOnPush + span
  | { action: 'defer_queue'; cat: CatId }        // 执行层：deferA2AEnqueue
  | { action: 'mark_replyto'; cat: CatId }       // 只设 a2aFrom/triggerMsg，不 push
  | { action: 'skip'; cat: CatId; reason: 'depth' | 'dedup_active' | 'aborted' | 'queue_pending' }
  | { action: 'block_pingpong'; cat: CatId; pairCount: number };

export interface RoutingContext {
  a2aCount: number;
  maxDepth: number;
  aborted: boolean;
  queuedMessagesPending: boolean;
  pendingTail: readonly CatId[];
  pendingOriginalTargets: readonly CatId[];
  hasActiveAgent: (cat: CatId) => boolean;
  peekStreak: (target: CatId) => { wouldBlock: boolean; count: number };
}
```

三个"看着有但实际没用满"的细节，面试里说出来很值钱：

1. **`skip.reason` 里的 `'queue_pending'` 从来不会被返回**。【源码】通读 `routing-decision.ts` 全文，`queuedMessagesPending` 命中时返回的是 `{ action: 'defer_queue' }`，没有任何一处产出 `reason: 'queue_pending'`。它是类型里的死枚举值。
2. **`relay_malformed` 这条 signal 在生产代码里没有调用者**。【源码】`grep relay_malformed` 只命中 `routing-decision.ts` 本身和 `packages/api/test/routing-decision.test.js`。真正的 relay push 是 route-serial 里的一段内联代码。【ADR】F216 spec AC-B3 写明："**relay 路径有意保留独立 battle-tested block，不接入统一决策层（de-scoped）**"。
3. **`RoutingSignal.content` 字段被传进来但决策函数没读**。【源码】`resolveInlineCat` 的参数只有 `(cat, ctx, depth)`。

### 2.5 `CallbackContentRoutingState`（route-serial 内部，MCP 出口的记账）

```ts
export type CallbackContentRoutingState = {
  scope: 'local' | 'target';
  guardLineStartMentions: CatId[];
  localLineStartMentions: CatId[];
  hasGuardCoCreatorLineStartMention: boolean;
  hasLocalCoCreatorLineStartMention: boolean;
  hasTargetCoCreatorLineStartMention: boolean;
};
```

为什么要 `guard` / `local` / `target` 三套：猫可以用 `cat_cafe_cross_post_message` 往**另一个 thread** 发消息，那条消息里的行首 @ 能算"这一轮有合法路由出口"（满足 guard），但**不能**变成当前 thread 的 A2A 路由状态、也不能给当前 thread 造未读。【源码】注释原文："Cross-post content belongs to the target thread. It can satisfy the current turn's guard, but it must not become current-thread A2A routing state."

实现手法：`classifyCallbackContentRoutingState()` 里 `const parserCurrentCatId = scope === 'target' ? undefined : currentCatId;`——跨 thread 时不过滤自 @（因为在目标 thread 里自己不是"当前猫"）。

## 3. 主流程逐段拆解

`routeSerial` 是一个 `async function*`，签名：

```ts
export async function* routeSerial(
  deps: RouteStrategyDeps,
  targetCats: CatId[],
  message: string,
  userId: string,
  threadId: string,
  options: RouteOptions = {},
): AsyncIterable<AgentMessage>
```

整体骨架只有一个 `try { while (index < worklist.length) { ... } } finally { ... }`。

### 3.1 阶段 0：循环外的一次性准备（约 136 行）

**做什么**：注册 worklist、把"整个 thread 都不变"的东西读一次。

```ts
const worklist = [...targetCats];
const maxDepth = options.maxA2ADepth ?? getMaxA2ADepth();
const worklistEntry = registerWorklist(threadId, worklist, maxDepth, options.parentInvocationId);

let index = 0;
let yieldedFinalDone = false;
let handoffEmitted = targetCats.length; // Original targets don't get handoff events
const activeTrackedA2ASlots = new Set<CatId>();
```

循环外读一次的东西（全部 best-effort、失败不阻塞）：
- `threadStore.getParticipantsWithActivity(threadId)` → `activeParticipants`
- `threadStore.get(threadId)` → `routeThread`，再派生 `routingPolicy` / `voiceMode` / `bootcampState`
- 如果 `routeThread.backlogItemId` 存在 → `workflowSopStore.get()` → `sopStageHint`（stage / suggestedSkill / featureId）
- `prepareGuideContext()`（F155 引导会话）
- `prepareConciergeContext()`（F229 前台猫岗位）
- 前台 thread 额外预取 `buildConciergeSearchContext()`

**为什么这么写**：注释直接给了理由——"threadId doesn't change"。A2A 链可能跑 15 只猫，每只都重读一次 thread 是纯浪费。

**坑在哪**：这也意味着**链中途 thread 状态变了（比如用户改了 routingPolicy）后面的猫看不到**。`incrementalMode` 判定也在这里定死：`const incrementalMode = Boolean(currentUserMessageId && deps.deliveryCursorStore)`。

### 3.2 阶段 1：每只猫的入口守卫 + per-cat signal

```ts
while (index < worklist.length) {
  const catId = worklist[index]!;
  const catSignal = signalForCat?.(catId) ?? signal;
  if (catSignal?.aborted) { index++; continue; }
```

**为什么用 per-cat signal**：【源码】注释是根因说明——"canceling one cat skips ONLY that cat, not the whole worklist. …… Using the shared primaryController.signal made 'cancel the first cat' break the entire worklist（并发取消误伤根因：serial 路径）"。force-reset / cancelAll 会 abort 每只猫的 controller，所以全部 skip = 等价于停止整条链。

**坑**：这里的 `continue` 是"跳过但推进 index"，不是 break——所以取消第一只猫，第二只猫照跑。

### 3.3 阶段 2：prompt 装配（约 648 行，全文最肥的一段）

顺序（严格按代码）：

1. `isOriginalTarget = index < targetCats.length` → 只有原始 target 才拿图片/上传目录（`routeContentBlocksForCat` / `uploadDir`）。
2. 非增量模式下拼 `previousResponses`：`[${r.catId} responded: ${r.content}]`。
3. 前台猫追加 `conciergeSearchContextString`。
4. `teammates = [...new Set(worklist.filter(id => id !== catId))]`——注意是**整个 worklist**（含还没跑的 A2A 追加项），不是原始 targetCats。
5. `directMessageFrom = worklistEntry.a2aFrom.get(catId)`。
6. **乒乓警告注入**：

```ts
const pingPongWarning =
  worklistEntry.streakPair && worklistEntry.streakPair.to === catId && worklistEntry.streakPair.count >= 2
    ? { pairedWith: worklistEntry.streakPair.from, count: worklistEntry.streakPair.count }
    : undefined;
```
   【源码】注释："streak=4 already blocked upstream, so max is 3 here"——也就是说猫能看到的 count 只可能是 2 或 3。
7. `streamReplyTo = worklistEntry.a2aTriggerMessageId.get(catId) ?? (isOriginalTarget ? a2aTriggerMessageId : undefined)`，再 `hydrateReplyPreview()` 拿预览。
8. `crossThreadReplyHint`：回退链是 `worklistEntry.a2aTriggerMessageId.get(catId) ?? currentUserMessageId`。【源码】注释交代了这个 fallback 的来历——"worklist `a2aTriggerMessageId` map only has entries for downstream A2A targets — initial target via the modern InvocationQueue path doesn't register in the map"。
9. `threadStore.consumeMentionRoutingFeedback(threadId, catId)`——**consume 语义**，读了就删，用来把上一轮"你 @ 写在行中了"的反馈注入这一轮。
10. `mcpAvailable = (catConfig?.mcpSupport ?? false) && !!mcpServerPath`。
11. `needsServerRoutingGuard = service.needsServerRoutingGuard?.() ?? false`（后面路由守卫要用）。

## 4. 关键算法与判定逻辑

### 4.1 `resolveRoutingDecisions` 的六道 guard（可复述版）

对 `inline_mention` / `deferred` 两种 signal，逐 cat 走 `resolveInlineCat(cat, ctx, depth)`：

```
Step 1  aborted?            → skip:aborted        （最高优先级，一切之上）
Step 2  depth >= maxDepth?  → skip:depth          （depth 是本次调用内累计消费的局部变量）
Step 3  hasActiveAgent(cat)? → skip:dedup_active  （跨路径去重：cat 已在 InvocationQueue 里跑）
Step 4  pendingTail.includes(cat)?
          ├─ 且 pendingOriginalTargets.includes(cat) → return null（不发决策，保持回复用户）
          └─ 否则                                    → mark_replyto（只重绑元数据，不 push）
Step 5  peekStreak(cat).wouldBlock? → block_pingpong { pairCount }
Step 6  queuedMessagesPending?      → defer_queue
        否则                         → enqueue_worklist
```

深度预算的消费规则（`resolveRoutingDecisions` 主体）：

```ts
let depth = ctx.a2aCount;
for (const cat of signal.cats) {
  const decision = resolveInlineCat(cat, ctx, depth);
  if (decision === null) continue;
  decisions.push(decision);
  if (decision.action === 'enqueue_worklist' || decision.action === 'defer_queue') depth++;
}
```
【源码】注释给了 review 出处（砚砚 PR#1991 P2）："Both enqueue_worklist (inline) AND defer_queue …… are real A2A route slots …… Counting only enqueue_worklist would let a batch resolve emit unlimited defer_queue past maxDepth. skip/mark_replyto/block_pingpong do NOT consume a slot."

**但**：route-serial 实际调用时永远只传 `cats: [nextCat]`（一次一只），所以这个累计循环在生产里跑不满——真正的累计发生在执行层的 `worklistEntry.a2aCount++`。【源码】注释解释了为什么要逐个 resolve："A single batch resolve would freeze every target's streak peek against the pre-loop streakPair: e.g. '@gemini @codex' with a hot opus<->codex streak would wrongly block @codex even though processing @gemini first resets the pair."

第六道 gate 放最后的理由（【源码】F216 c2 注释）："This way the deferred path (queuedMessagesPending=true) still runs the full guard chain before deferring …… For the inline path queuedMessagesPending is always false (outer condition `!queuedMessagesPending`), so this check is a no-op there → inline behavior unchanged."

`relay_malformed` 走另一条极简链（生产无调用者）：


**key 怎么构造**：不是字符串 key，是 `streakPair: { from, to, count }` 一个对象，配对判定用无序比较：

```ts
function samePair(a: { from: CatId; to: CatId }, bFrom: CatId, bTo: CatId): boolean {
  return (a.from === bFrom && a.to === bTo) || (a.from === bTo && a.to === bFrom);
}
```
所以 A→B 和 B→A 累在同一个计数上。**一个 worklistEntry 只记一对**（最近的那对），换对就重置。

**核心预测函数（peek 和 update 共用，保证 parity）**：

```ts
function predictStreakCount(entry, callerCatId, target, activity?): number {
  if (entry.streakPair && samePair(entry.streakPair, callerCatId, target)) {
    return isSubstantiveActivity(activity) ? 1 : entry.streakPair.count + 1;
  }
  return 1;
}
function isSubstantiveActivity(activity?): boolean {
  if (!activity) return false;
  return activity.hadSubstantiveToolCall || activity.outputLength > OUTPUT_LEN_T;  // 200
}
function streakVerdict(count: number): StreakResult {
  return {
    warnPingPong: count >= 2 && count < 4,
    blockPingPong: count >= 4,
    count,
  };
}
```

**决策表**：

| 场景 | activity | 结果 count | 效果 |
|---|---|---|---|
| 新对 / 换对 | 任意 | 1 | 正常 |
| 同对 + 有实质工具调用 | substantive | **重置为 1** | 正常 |
| 同对 + 正文 > 200 字符 | substantive | **重置为 1** | 正常 |
| 同对 + 短文本 + 只调路由工具 | 惰性 | count + 1 | 2/3 → warn，≥4 → block |
| 无 activity 传入 | undefined | count + 1 | 视为惰性 |

【源码】为什么"实质工作要重置而不是豁免"：注释里有 review 出处（gpt52 P1-1）——"same-pair substantive work / long discussion → RESET to 1 (a real-work round breaks inertia, otherwise `3 short + 1 substantive + 1 short` would still block on round 5)"。

**peek vs update**：

| | `peekStreakOnPush` | `updateStreakOnPush` |
|---|---|---|
| 返回 | `{ wouldBlock, wouldWarn, count }` | `StreakResult { warnPingPong, blockPingPong, count }` |
| mutate | 否 | 是（写 `entry.streakPair` 的 count/from/to） |
| 谁调 | 决策层通过 `ctx.peekStreak` | 执行层：inline 路径、deferred 路径、`pushToWorklist`、`callback-a2a-trigger.ts` 现代路径 |
| 目的 | 让 `resolveRoutingDecisions` 保持纯函数（砚砚 OQ3） | 唯一的正式变更点 |

【源码】`peekStreakOnPush` 注释："`wouldBlock` mirrors StreakResult.blockPingPong (parity test guards this)"——对应测试 `packages/api/test/routing-decision-streak.test.js`、`worklist-registry-streak.test.js`。

**执行层调用纪律**：inline / deferred 两条路径都是

```ts
if (decision.action === 'skip') continue;         // 不动 streak
if (decision.action === 'mark_replyto') { ...; continue; }  // 不动 streak
const streak = updateStreakOnPush(worklistEntry, catId, nextCat, { hadSubstantiveToolCall, outputLength: storedContent.length });
if (decision.action === 'block_pingpong') { yield a2a_pingpong_terminated; continue; }
// enqueue / defer
```
即：**只有 `enqueue_worklist` 和 `block_pingpong` 会真正写 streak**。注释原文："enqueue_worklist | block_pingpong both reached the streak gate in the legacy code, so the real (mutating) updateStreakOnPush must run exactly once here for either."

**`pushToWorklist` 里的门控更严**——只有 1:1 且真的会入队时才动 streak：

```ts
if (callerCatId !== undefined && cats.length === 1) {
  const target = cats[0];
  const wouldEnqueue = entry.a2aCount < entry.maxDepth && !pending.includes(target);
  if (wouldEnqueue) { const streak = updateStreakOnPush(...); ... }
  // else: dedup or depth would skip → do not touch streak state
}
```
【源码】注释给了根因（cloud Codex P1 on PR #1349）："otherwise a push that gets skipped could still reset or increment the counter, which would let repeated dedup'd long-content callbacks 'clear' a near-blocked streak without a real handoff"。

**什么时候重置**：
1. 换对（自动，`predictStreakCount` 返回 1）
2. 同对但有实质活动（自动重置为 1）
3. `resetStreak(threadId, parentInvocationId?)` —— **用户发消息时调**。【源码】唯一生产调用点是 `packages/api/src/routes/messages.ts` 的 `resetStreak(resolvedThreadId)`，**不传 parentInvocationId**，所以走反向索引把该 thread 下所有 worklist 的 `streakPair` 全清。注释解释了为什么必须支持这种形式："route-serial registers entries keyed by parentInvocationId (F108), so a single-key lookup would miss them"。
4. 注意：worklist 生命周期结束（`unregisterWorklist`）streak 随之消失——**streak 不跨 invocation 累计**。

**警告注入的窗口**：只有 `streakPair.to === catId && count >= 2` 时才给猫注入 `pingPongWarning`，所以猫看到的 count 只能是 2 或 3。

### 4.4 `deferA2AEnqueue` 的作用与调用时机

**是什么**：`RouteOptions` 上的一个回调，签名固定：

```ts
deferA2AEnqueue?: (entry: {
  threadId: string; userId: string; content: string;
  source: 'agent'; sourceCategory: 'a2a';
  targetCats: string[]; callerCatId: string;
  messageId?: string; a2aTriggerMessageId?: string;
  autoExecute: true; priority: 'normal'; intent: 'execute';
  callerTraceContext?: CallerTraceContext;
}) => void
```

**谁接线**（4 个生产调用点，全部是"塞进 InvocationQueue"）：

| 位置 | 实现 |
|---|---|
| `invocation/QueueProcessor.ts` | `deferA2AEnqueue: (e) => queue.enqueue(e)` |
| `routes/messages.ts` | `deferA2AEnqueue: (e) => opts.invocationQueue?.enqueue(e)` |
| `routes/invocations.ts` | `deferA2AEnqueue: (e) => opts.queueProcessor?.enqueueRaw(e)` |
| `infrastructure/email/ConnectorInvokeTrigger.ts` | `deferA2AEnqueue: (e) => invocationQueue.enqueue(e)` |
（`AgentRouter.ts` 只是把它透传下去。）

**作用**：把"本来要在当前 routeSerial 里直接接着跑的 A2A 目标"改成"排到 InvocationQueue 里、排在非-agent 条目之后"。两个不同的动机：
- 路径③（公平性）：队列里有用户/connector 消息等着，猫不能一直自己接着聊。【ADR】ADR-018 OQ-1 拍板"A2A handoff 入 queue + auto-execute"，理由就是"用户可以 steer 插队纠正方向（猫猫聊歪了能拉回来）"。
- 路径②（abort 恢复）：invocation 被打断了，当前 generator 已经没法继续跑 worklist，只能把交接托付给队列。

**注意 `autoExecute: true`**：入队但不需要用户批准，符合 ADR-018 的 OQ-1 决策。

### 4.5 abort 的几个分支 + #813 abort-recovery

`catSignal` 相关的分支一共 6 处：

| 位置 | 分支 | 行为 |
|---|---|---|
| while 顶部 | `catSignal?.aborted` | `index++; continue`（跳过这只猫，链继续） |
| 流循环内 | `catSignal?.aborted` | `break`（F39：管道可能还在排水） |
| 补救流循环内 | 同上 | `break` |
| error 事件 | `if (!catSignal?.aborted) hadProviderError = true` | #267：abort 之后的 error 是清理噪音，不算 provider 故障 |
| `flushVoiceChunker` | `aborted ? -1 : voiceTotalChunks` | 用 `totalChunks: -1` 通知前端语音流被中断 |
| A2A 分派 | 路径② | #813 abort-recovery |

**#813 abort-recovery 完整逻辑**：

```ts
} else if (a2aMentions.length > 0 && catSignal?.aborted && deferA2AEnqueue) {
  const abortReason = catSignal.reason;
  const isUserInitiatedAbort = abortReason === 'user_cancel' || abortReason === 'cancel_all';
  if (isUserInitiatedAbort) {
    log.info({...}, '#813: A2A abort-recovery suppressed — user-initiated cancellation');
  } else {
    for (const nextCat of a2aMentions) {
      if (worklistEntry.a2aCount >= maxDepth) { log.info(...); continue; }
      if (hasQueuedOrActiveAgentForCat?.(threadId, nextCat)) { log.info(...); continue; }
      deferA2AEnqueue({ threadId, userId, content: storedContent, source: 'agent', sourceCategory: 'a2a',
        targetCats: [nextCat], callerCatId: catId, messageId: storedMsgId,
        a2aTriggerMessageId: storedMsgId, autoExecute: true, priority: 'normal', intent: 'execute' });
      worklistEntry.a2aCount++;
    }
  }
}
```

要点：
1. **`#813` 是开源仓 issue 号**，不是本仓 PR 号。【ADR】F224 spec 里专门加了红色警告："本 feat 引用的 `clowder-ai#813/#814/#815/#836` 是**开源仓 issue 号**，与 cat-cafe 自己的 PR 号（PR #813=F137 / PR #834=F108）**纯数字撞车、毫无关系**。引用一律带 `clowder-ai#` 前缀，防 phantom-anchor 投毒。"
2. 【ADR】clowder-ai#813 的病症是"**会话延续会丢**：A2A 传球触发下一棒猫时，上一轮的会话上下文没被正确封存/恢复，猫'断片'"。
3. route-serial 里这段治的是它的一个具体表现：猫已经写完了行首 @，但 invocation 在那之后被打断（【源码】注释举例 "e.g., after context seal"），@mention 会被静默吞掉，交接链断掉。
4. **P2 gate 是产品判断**：`user_cancel` / `cancel_all` 不恢复。【源码】注释："The user explicitly stopped the flow — enqueueing autoExecute A2A work afterward would contradict their intent and run work they tried to stop."
5. `abortReason` 的来源是 `AbortController.abort(reason)`，产生者在 `invocation/InvocationTracker.ts` 的 `cancel/cancelAll/cancelInvocation(…, abortReason?)`。
6. 这条路径**不走决策层**，只手写了两道 guard：depth + `hasQueuedOrActiveAgentForCat`。【源码】注释承认了这一点："same guard the inline and fairness-gate paths apply via resolveRoutingDecisions → hasActiveAgent"。也就是说 **abort-recovery 不受乒乓熔断保护**。【推断】这是个可以在面试里主动指出的不一致。

### 4.6 三个"拦什么"的检测器

三者共享同一套"结构剥离 + 最后一段"机制，但拦的东西不同：

| 检测器 | 拦什么 | 关键正则/常量 | 抑制条件（任一命中就不报） |
|---|---|---|---|
| `final-routing-slot.validateRoutingSyntax` (Phase H) | **@ 写在行中而不是行首**，且没有任何合法出口 → `invalid_route_syntax` | `MARKDOWN_LINE_PREFIX_RE = /^(?:(?:>\s*)\|(?:[-*+]\s+)\|(?:\d+[.)]\s+))+/`；mention 正则带双侧边界 `(?<![a-zA-Z0-9_-])@(handle)(?=$\|[^a-zA-Z0-9_-])` | 行首 @ / `hold_ball` 工具 / `structuredTargetCats` / slot 内无 inline @ |
| `verdict-detect.shouldWarnVerdictWithoutPass` (C2/AC-C7) | **给了 review 结论但没传球** | 7 条 `VERDICT_PATTERNS`：`lgtm` `/\bLGTM\b/i`、`approve` `/\bapproved\b/i`、`reject` `/\breject(ed\|s)?\b/i`、`p1p2` `/\bP[12]\s*[:：]/`、`modify_suggestion` `/修改建议/`、`approve_cn` `/放行/`、`reject_cn` `/打回/` | 行首 @ / `hold_ball` / structuredTargetCats / 行首 @co-creator |
| `void-hold-detect.evaluateVoidHold` (Phase I/AC-I1) | **文字声明持球但本轮没调 `cat_cafe_hold_ball`** | 6 条 `HOLD_PATTERNS`（最具体优先）：`mcp_tool_name` `/cat_cafe_hold_ball/`、`en_hold_ball_underscore` `/\bhold_ball\b/i`、`en_holding_the_ball` `/\bholding.the.ball\b/i`、`en_holdball_space` `/\bhold.ball\b/i`、`cn_wo_chi_qiu` `/我.*持.*球/`、`cn_chiqiu` `/持球/` | `hold_ball` 工具 / 行首 @ / structuredTargetCats / 行首 @co-creator |
| `vote-intercept.extractVoteFromText` | 不是"拦"，是**抽取** `[VOTE:xxx]` 并代替猫投票 | `VOTE_PATTERN = /\[VOTE:(.+?)\]/`（非贪婪，只取第一个） | 无（route-serial 侧再校验 active/deadline/voters） |

**`finalRoutingSlot(text)` 的剥离顺序**（三者共用）：

```
1. 去掉围栏代码块       text.replace(/```[\s\S]*?```/g, '')
2. 去掉引用行           过滤掉 /^\s*>/ 的行
3. 去掉 URL             replace(/https?:\/\/[^\s)\]]+/g, '')
4. 按空行 split 成段落，trim，过滤空段
5. 返回最后一个非空段落
```

**verdict / void-hold 在进 slot 之前还要先 `stripTrailingCatSignatures`**（Phase H 的 `validateRoutingSyntax` 不做这一步——它验的是"语法"，签名行不影响）。

【源码】两个检测器都留了完整的调参 provenance，值得引用：
- verdict `approve` 从 `/\bapprove(d|s)?\b/i` 收紧成 `/\bapproved\b/i`，`p1p2` 从 `/\bP[12]\b/` 收紧成 `/\bP[12]\s*[:：]/`。理由是 2026-06-05 的 eval 数据："19/19 fires were `thread_system_kind='product'`（system-thread bypass hypothesis falsified）and 18/19 were `trigger='approve'|'p1p2'`（keyword-overload hypothesis confirmed）"。
- 两者都从"扫全文"改成"只扫 final routing slot"。verdict 是 2026-06-16（6/89 = 6.7% 误报），void-hold 是 2026-06-20（10/122 = 8.2%，超过 5% 底线，误报主力是英文 `hold_ball`/`holdball` 出现在状态叙述里）。
- 【源码】设计红线反复出现："KD-24 mechanical, no semantic classifier" / "禁止语义 intent 分类器 / KD-8" / "豁免只走结构边界（fenced code / blockquote / URL），禁止动作词表 / 语义豁免表"。

### 4.7 `cat-signature-strip` 防的是什么

**不是防身份冒充**——它是**签名识别器**，目的是让 final-routing-slot 不要停在签名行上。但它的整个演化史就是"如何在不误伤的前提下精确识别一类文本"，防的是**误判**：把文件路径、PR 引用、供应商前缀当成猫签名剥掉。

六条决策规则（【源码】模块头注释原文顺序）：

```
1. Pawed (ends in 🐾) → signature.
2. Slashless without paw → not a signature (body token).
3. Multi-slash content → not a signature (deep path).
4. Single-slash + file-extension tail → not a signature (path).
5. Single-slash + LHS in precise cat-nickname allowlist AND RHS matches model-name allowlist → legacy un-pawed signature.
6. Otherwise → not a signature.
```

三个正则：

```ts
const PAW_SIGNATURE_LINE_RE = /^\s*\[[^[\]\n]+🐾\]\s*$/u;
const KNOWN_CAT_NICKNAME_LHS_RE = /^(?:宪宪|砚砚|烁烁)$/u;
const KNOWN_MODEL_NAME_RHS_RE = /^(?:Opus|Sonnet|Codex|GPT|Spark|Gemini|Claude|Fable|Haiku|Pro)(?:[-.][\w.-]+)?$/;
const FILE_EXTENSION_TAIL_RE = /\.(?:ts|mjs|js|md|json|yaml|yml|tsx|jsx|cjs|mts|cts|py|sh|css|html|svg|png|jpg|jpeg|gif|webp|toml|sql|go|rs|kt|java|cpp|hpp|c|h)$/i;
```

**Provenance ladder（规则 5 走过的 5 轮 review，R3→R7，面试里非常有说服力）**：

| 轮次 | 规则 5 是什么 | 被什么打穿 |
|---|---|---|
| R3 P2 | 单斜杠 + RHS 含数字 | `[PR/2442]` `[issue/123]` `[F167/Phase2]` `[release/v2]` |
| R4 P2 | 拆成 5a(数字) + 5b(allowlist) | 5a 太松 |
| R5 P2 | 丢掉 5a，只留 RHS allowlist | `[openai/GPT-5.5]` `[anthropic/Claude]` `[apache/Spark]` |
| R6 P2 | 加 LHS 广义 CJK 正定 `/^[一-鿿]+$/u` | `[模型/GPT-5.5]` `[文档/Sonnet]` `[供应商/Claude]` |
| R7 P2（现状） | LHS 钉死成 3 个昵称精确白名单 | —— |

【源码】注释里给出的维护契约："When a new cat joins with an un-pawed slashed signature shape, update BOTH `commit-signatures.md` AND this regex together. Pawed signatures (`[新猫🐾]`) flow through rule 1 and never need allowlist updates."

以及一个明确的偏好方向：`FILE_EXTENSION_TAIL_RE` 的注释——"better to false negative on an unusual file path (treat it as signature, strip it) than to false positive on a model name (treat signature as path, leave it)"。

**`stripTrailingCatSignatures` 的走法**：从最后一行往前，空行和签名行都丢，遇到第一个"非空非签名"行停。**只剥尾部**，正文里长得像签名的括号保留。

> 真正的身份冒充防护在别处（第 07 篇 身份注入 / L0 native system role）。这一篇的 `cat-signature-strip` 只是"检测器的输入预处理"。这个区分要说清，否则会答错出处。

### 4.8 `parseA2AMentions` 的匹配算法

```
1. 剥围栏代码块
2. 从 catRegistry.getAllConfigs() 收集所有 mentionPatterns（含 disabled 猫，F182 KD-10）
   过滤自 @（currentCatId 相同则跳过整只猫）
3. 按 pattern 长度**降序**排（避免 @opus 抢走 @opus-45）
4. repairLineStartMentionWhitespace：把 "@ o p u s" 这种字符间插空格的写法修回来
   （给每个字符之间插 \s*，命中就换成规范 pattern）
5. 逐行：剥前导空白 + LEADING_MARKDOWN_MENTION_PREFIX_RE（> / - * + / 1. ）→ 必须 startsWith('@')
6. 同一行游标推进：匹配 → 检查右边界（TOKEN_BOUNDARY_RE 或非 HANDLE_CONTINUATION_RE）
   → resolveCatTarget(catId) 检查可用性（disabled 猫产出 routing_warnings 而不是 mentions）
   → 跳过分隔符，若下一个字符不是 '@' 就 break（一行可以连着写 @a @b）
7. found.length >= MAX_A2A_MENTION_TARGETS(2) 就停
```

两个字符类常量：
```ts
export const TOKEN_BOUNDARY_RE = /[\s,.:;!?()[\]{}<>，。！？、：；（）【】《》「」『』〈〉]/;
export const HANDLE_CONTINUATION_RE = /[a-z0-9_.-]/;
```

对比 `detectInlineActionMentions`（#417，**只做写侧反馈，不路由**）：要求 @ 在行中（`idx !== 0`）+ 紧邻动作词：

```ts
export const BEFORE_HANDOFF_RE = /(?:ready\s+for|交接给?|转给|(?<![邀申敬])请|帮)\s*$/i;
export const AFTER_HANDOFF_RE =
  /^\s*(?:(?:review|check|fix|merge)(?![a-z])|(?:确认|处理|来处理|来看)(?![过了完好掉])|看一?下|帮忙|请(?![教示假求问]))/i;
```
【源码】负向断言的用意写得很明确：`请` 排除 `邀请/申请/敬请`；英文动词 `(?![a-z])` 排除 `reviewed/checklist`；中文动词 `(?![过了完好掉])` 排除"处理完/来看过"。

`a2a-shadow-detection.ts` 再加一层**宽松**版（`RELAXED_BEFORE_ACTION_RE` / `RELAXED_AFTER_ACTION_RE`），只为观测"词表缺口"，产出的 `ShadowMiss` **不含原文**——只有 `contextHash`（SHA-256 前 16 hex）和 `contextLength`。【源码】"no raw text, per data minimization (mindfn #479)"。

### 4.9 `context-transport` 到底做什么（读代码确认）

**它不是"跨调用传上下文"**。名字容易误导。它是 **F148 分层上下文传输（Hierarchical Context Transport）的纯函数库**，服务于"冷 @ 唤醒"时的智能窗口装配，全部在**同一次 invocation 内**跑完。

导出的 9 个函数：

| 函数 | 干什么 | 算法要点 |
|---|---|---|
| `buildCoverageMap` | 把 omitted/burst/anchors/threadMemory/hints 打包成结构 | 纯映射 |
| `detectRecentBurst(messages, config)` | 从尾部找"最近这一波对话" | 倒着走，找 `gap >= burstSilenceGapMs(15min) && tailCount >= minBurstMessages(4)` 的切点；`maxBurstMessages(12)` 上限；`protectSemanticChains` 递归回退（tool_result 前面是 tool_use → 带上；猫回答前面是用户提问 → 带上）；最后保底 `minBurstMessages` |
| `buildTombstone` | 给被省略的消息造墓碑 | 词频统计（split 非字母数字非 CJK，`length >= 3`，过 `STOP_WORDS`），取 `maxTombstoneKeywords(4)` 个；产出 `search_evidence("kw1 kw2", threadId="...")` |
| `formatTombstone` | 渲染成一行 | `[System: skipped N messages (range). Participants: … Keywords: … For details: …]`，注释标"~40 tokens" |
| `scrubToolPayloads` | 把非最后一条消息的 tool_result 正文换成摘要行 | `<tool_result truncated: {label} executed>`；**最后一条原样保留** |
| `scoreImportance` | 给被省略的消息打分 | structural: 代码块 +3、mentions +2、toolEvents +2、正文 >500 字 +1；positional: index 0 +5；relevance: 每个命中的 query term +1 |
| `selectAnchors` | 选锚点 | 按分数取前 `maxAnchors(3)`；**强制保证 index 0（primacy）在内**（不在就 pop 最低分再 push primacy）；最后按原始顺序排回时间序 |
| `formatAnchors` | 把锚点渲染成标注行 | `[Thread opener @X: id] …` / `[Anchor i/n @X: id] …`，超 `truncateLimit` 截断 |
| `recallEvidence` | 证据召回 | 复合 query = threadTitle + 当前消息前 300 字 + 最近 2 条前 200 字；`Promise.race` 对 `evidenceRecallTimeoutMs(500)` 超时；取 `maxEvidenceHits(3)`；**任何错误返回 `[]`** |

调用它的是 `route-helpers.ts` 的 `assembleSmartWindowContext()`，触发条件在 `assembleIncrementalContext()`：

```ts
const countTrigger = relevant.length > hcConfig.coldMentionThreshold;         // > 15 条
const tokenTrigger = !countTrigger &&
  relevant.reduce((sum, m) => sum + estimateTokens(m.content), 0) > hcConfig.coldMentionTokenThreshold;  // > 10000
const isColdMention = countTrigger || tokenTrigger;
```
【源码】先判 count 再判 token 是有意的："P1-review: short-circuit on count first — avoid O(n) tokenize when count already triggers"。

智能窗口的**分级降级顺序**（token 不够时依次丢）：

```
Stage 1    从旧到新丢 evidence 行
Stage 1.3  coverageMap + threadMemory 一起丢
Stage 1.5  按最低分丢 anchors
Stage 2    丢 tombstone
Stage 3    从旧到新裁 burst（保底留 1 条）
Stage 4    还是超 → 返回 contextText: '' + degradation 文案
最后再查一次：信封本身可能把总量顶过预算 → 同样返回空
```

### 4.10 `MultiMentionOrchestrator` 状态机

`multi-mention-state-machine.ts` 的完整转移表（33 行文件的全部内容）：

```
pending → { running, failed }
running → { partial, done, timeout, failed }
partial → { done, timeout }
done    → ∅   (terminal)
timeout → ∅   (terminal)
failed  → ∅   (terminal)
```

```ts
const VALID_TRANSITIONS: ReadonlyMap<MultiMentionStatus, ReadonlySet<MultiMentionStatus>> = new Map([
  ['pending', new Set(['running', 'failed'])],
  ['running', new Set(['partial', 'done', 'timeout', 'failed'])],
  ['partial', new Set(['done', 'timeout'])],
  ['done', new Set()], ['timeout', new Set()], ['failed', new Set()],
]);
```
`MULTI_MENTION_TERMINAL_STATES = new Set(['done','timeout','failed'])`（在 `packages/shared/src/types/multi-mention.ts`）。

注意几个非平凡点：
- `partial` **不能**再回 `failed`（已经收到部分回复了，整体不算失败）。
- `pending` 不能直接 `done`——必须先 `start()` → `running`。
- `private transition()` 命中非法转移**直接 throw**：`Invalid multi-mention transition: ${from} → ${to}`。这是唯一因"状态机规则"抛的地方（另有四处 `Multi-mention request not found` throw：`recordResponse` / `getStatus` / `getResult` / `transition`，以及 `create()` 的两条参数校验 throw）。

`recordResponse(requestId, catId, content)` 的三道静默忽略（**返回当前 status，不抛**）+ 收齐判定：

```
1. 已 terminal        → return status
2. catId 不在 targets → return status
3. 该 cat 已回复过    → return status
4. 收够了 (receivedCount >= targetCount) → transition('done')
   否则若 status==='running' → transition('partial')
```

`handleTimeout()` 会先把没回的 target 补成 `{ content: '', status: 'timeout' }`，再转 `timeout`。

**幂等**：`create()` 用 `idempotencyIndex: Map<"threadId:key", requestId>`，命中就直接返回已有 request。校验：`targets.length` 必须 1..3，`timeoutMinutes` 必须 3..20，否则 throw。

**dispatch controller** 是独立于状态机的一层：`dispatchControllers: Map<"requestId:catId", AbortController>`。【源码】注释解释了为什么不用 `InvocationTracker`："allows thread-level cancel/delete to propagate to individual multi-mention dispatches without the per-thread singleton constraint of InvocationTracker (which would cause concurrent dispatches to abort each other)"。三个取消入口：`abortByThread` / `abortBySlot(threadId, catId)`（F108 槽位级取消）/ `hasActiveDispatches`（删除守卫）。

**防级联**：`isActiveTarget(threadId, catId)` 要求 `!terminal && status !== 'pending'`——`pending` 不算占用。

**Q2：worklist 为什么放在一个模块级 Map 里，而不是纯局部变量？**

> 因为有**两个写入方**。routeSerial 自己在 for-await 之后 push（inline text-scan），但猫还能通过 MCP `cat_cafe_post_message` 走 HTTP callback 进来——那条路径完全不在 generator 的栈里。WorklistRegistry 就是给这条外部路径开的口子：`hasWorklist(threadId)` 判断有没有正在跑的链，`pushToWorklist(...)` 塞进去，因为 `entry.list` 存的是**同一个数组引用**，routeSerial 的 `while (index < worklist.length)` 下一圈就看到了。
> 代价是全局可变状态，所以补了三层保护：key 用 `parentInvocationId ?? threadId` 做并发隔离（F108），push 时校验 `entry.list[entry.executedIndex] === callerCatId` 防过期 callback，unregister 时做 owner identity 检查防抢占误删。
> 加分点：**这条路现在主要是 legacy 兜底**。ADR-018 OQ-1 拍板 A2A callback 改走 InvocationQueue + auto-execute，理由是"A2A 任务在 QueuePanel 可见（用户知道猫猫在干嘛）"+"用户可以 steer 插队纠正方向（猫猫聊歪了能拉回来）"。所以 `callback-a2a-trigger.ts` 里 `pushToWorklist` 只在 `deps.invocationQueue` 没接线时才走；现代路径只用 `getWorklist()` 取 entry 调 `updateStreakOnPush`（仍会写 streak），入队走 `invocationQueue.enqueue`。

**Q3：六道 guard 的顺序为什么是这个顺序？换一下会怎样？**

> 顺序是 `aborted → depth → hasActiveAgent → pendingTail → streak → queue fairness`。
> - `aborted` 第一是因为它是"整体已失效"，后面所有判定都没意义。
> - `depth` 在 dedup 之前，是为了让"到上限"这个原因优先于"重复"——诊断时前者是配置问题，后者是正常收敛。
> - `pendingTail` 命中要分叉：如果这只猫是**用户原始选的 target**，返回 `null`（不发决策），让它继续回复用户；否则 `mark_replyto`，只重绑 `a2aFrom` / `a2aTriggerMessageId`。这个分叉的原因是"原始 target 必须回复用户，不能被 A2A 抢走 replyTo 语义"。
> - **fairness 放最后是 F216 c2 刻意改的**。源码注释写得很清楚：这样 deferred 路径也能走完整条 guard 链，拿到和 inline 一样的 `skip:depth` / `skip:dedup_active` / `mark_replyto` / `block_pingpong`，然后才 defer 一个"干净的入队"。如果 fairness 放前面，队列一有消息就短路，deferred 路径就会把该 block 的乒乓、该 skip 的重复也一起入队。而 inline 路径永远 `queuedMessagesPending=false`（外层条件就是 `!queuedMessagesPending`），所以这一道对它是 no-op，行为不变。

**Q4：streak 为什么要 peek/update 拆两个函数？**

> 因为决策层是纯函数。`resolveRoutingDecisions` 要判断"该不该 block 乒乓"，就得知道 push 之后的 count 是多少；但它不能真去改 `entry.streakPair`——否则一个"只是问问"的决策查询会污染状态，而且纯函数就不纯了（源码里标了 review 出处：砚砚 GPT-5.5 OQ3"副作用不进决策函数，否则纯函数变上帝函数"）。
> 所以拆成 `peekStreakOnPush`（只读预测）和 `updateStreakOnPush`（真写），两者共用同一个 `predictStreakCount`，parity 由 `routing-decision-streak.test.js` 守着。执行层拿到决策后，对 `enqueue_worklist` 和 `block_pingpong` **两种**结果都调一次真 update——因为在重构前的老代码里这两种都是"到了 streak 门"，语义要一致。
> 加分点：为什么必须一只猫一只猫地 resolve+apply（而不是批量）？源码注释举了例子——"@gemini @codex"，如果 opus↔codex 的 streak 正热，批量 resolve 会让每个 target 的 peek 都冻结在循环前的 streakPair 上，于是 @codex 被误 block；但实际上先处理 @gemini 会把 pair 换掉、count 重置为 1，@codex 应该放行。

**Q5：猫写了行首 @ 然后 invocation 被打断，那个 @ 去哪了？**

> 走 #813 abort-recovery。条件是 `a2aMentions.length > 0 && catSignal.aborted && deferA2AEnqueue` 存在。它把 @ 目标包成一条 InvocationQueue entry（`source:'agent'`, `sourceCategory:'a2a'`, `autoExecute:true`, `intent:'execute'`），content 用 `storedContent`，`messageId` 和 `a2aTriggerMessageId` 都用 `storedMsgId`。
> 关键的产品判断是 **P2 gate**：`catSignal.reason === 'user_cancel' || 'cancel_all'` 时**不恢复**，只记一条日志。源码注释的理由是"用户明确停了这个流程，之后再排一个 autoExecute 的 A2A 任务会违背他的意图，去跑他试图停下的活"。这个 reason 是 `InvocationTracker.cancel(threadId, catId, userId, abortReason)` 传进 `AbortController.abort(reason)` 的。
> 要注意的坑：这条路径**手写了 guard**（只有 depth + `hasQueuedOrActiveAgentForCat`），不走 `resolveRoutingDecisions`，所以**不受乒乓熔断保护**。理论上一对猫在反复 abort 的场景里能绕过 breaker。这是我会补的一个不一致。

**Q6：`#813` 是什么？是 PR 号吗？**

> 不是。它是**开源仓 clowder-ai 的 issue 号**，spec 里专门加了红字警告说这批号（clowder-ai#813/#814/#815/#836）跟 cat-cafe 自己的 PR 号纯数字撞车、毫无关系，引用必须带 `clowder-ai#` 前缀"防 phantom-anchor 投毒"——因为本仓的 PR #813 是 F137，完全另一件事。
> clowder-ai#813 的原始病症是"**会话延续会丢**：A2A 传球触发下一棒猫时，上一轮的会话上下文没被正确封存/恢复，猫断片"，由社区贡献者 mindfn 在 PR #834 里一起报了 4 个 bug 并出了初版修复。cat-cafe 侧的 F224 承接了它，但没有 as-is merge——原实现是 inline 风格（把 passive seal 织进 `QueueProcessor.executeEntry` 的 finally，散落 4 处），终态倾向是抽成 `SessionContinuationCoordinator`。route-serial 里这段 abort-recovery 只是这个 issue 的一个具体表现的修复。

**Q7：verdict-detect 和 void-hold-detect 为什么只扫最后一段？**

> 因为扫全文的误报率被 eval 量化打死了。
> verdict：2026-06-16 的 eval 显示 `verdict_without_pass` 误报 6/89 = 6.7%，原因是猫写状态汇报（"PR #X 已放行"、"P1: foo 已修"、"approved by Y"）会撞关键词，但消息真正的最后一段是状态摘要，那一刻并没有在**给**结论。

**Q8：落库有几个时机？怎么保证不重不漏？**

> `messageStore.append` 在 route-serial 里有 **11 个调用点**：简报卡片、路由守卫失败通知、路由语法提示、inline-mention 提示、球权提醒、持球提醒、投票结果、**猫的正文**、无正文但有 payload、有错误但有 toolEvents、错误系统消息；此外还有一个 `augmentStreamMetadata`（不是 append，见下）。其中 7 个是 `userId:'system', catId:null` 的 connector 消息（简报卡片 + 5 条提示/通知 + 错误系统消息；投票结果用的是 `userId, catId:null`）。
> 幂等的核心是 **#573 的 callback 双写防护**：猫用 `cat_cafe_post_message` 时 MCP 侧已经把消息落库了，如果 stream 结束再 append 一遍就会重影。解法是从 tool_result 里解析 `{status, messageId, threadId}`，`status` 是 `'ok'` **或 `'duplicate'`** 都算 confirmed（重投递不算失败），confirmed 就跳过 append，改用 `augmentStreamMetadata(callbackPostMessageId, patch)` 只补 thinking / metadata / toolEvents / replyTo / mentionsUser / extra——而且只在 `hasStreamMetadataPatch(patch)` 为真时才调，避免空 patch 的无效写。
> 另外两个细节：`timestamp` 用的是 `invocationStartedAt` 而不是 `Date.now()`（消息时间锚在调用开始）；`extra.stream` 一定同时盖 `invocationId`（parent，legacy SoT）和 `turnInvocationId`（own，前端气泡身份的稳定 key），F194 Z9 AC-Z25 要求"always stamp"，就算 own === parent 也要显式盖，否则同一 parent 下同一只猫多轮会塌成一个气泡。

**Q9：`isFinal` 怎么算对的？**

> `isFinal = index === worklist.length - 1`，而且这个求值点在**所有可能让 worklist 变长的动作之后**：inline A2A push、relay push、以及外部 callback push（因为 worklist 是共享引用）。这就是为什么 route-serial 给 `invokeSingleCat` 传的 `isLastCat` 永远是硬编码 `false`——单猫调用层根本不可能知道链会不会长。
> 兜底在 `finally`：`yieldedFinalDone` 记录有没有 yield 过 `isFinal=true` 的 done；如果循环在顶部 break（signal aborted）或 provider 抛异常，`finally` 会合成一个 `done { catId: worklist[Math.min(index, worklist.length-1)], isFinal: true }`。前端的超时计时器靠这个清掉，所以"永不卡在 thinking"。

**Q10：每个 yield 点吐的是什么消息？**

> 一共 17 个 yield 位置。显式构造的只有 3 种 type（`system_info` / `a2a_handoff` / `done`），其余是 `toStreamEvent()` 转发的原 type：
> | 消息 | type | payload |

> | 增量上下文降级 | `system_info` | `inc.degradation`（**裸字符串，不是 JSON**） |

**Q11：`context-transport.ts` 是做跨调用上下文传输的吗？**

> 不是，名字有误导性。它是 **F148 分层上下文传输的纯函数库**，全部在同一次 invocation 内跑完，做的是"冷 @ 唤醒时怎么把一大堆未读消息压进预算"：`detectRecentBurst`（按 15 分钟静默 gap 切最近一波，4~12 条，且不切断 Q→A / tool_use→tool_result 语义链）、`buildTombstone`（词频抽 4 个关键词造一条 ~40 token 的墓碑 + `search_evidence(...)` 提示）、`scoreImportance`/`selectAnchors`（结构+位置+相关性打分，强制保留 index 0 的 primacy 锚点，取前 3）、`scrubToolPayloads`（除最后一条外把 tool_result 正文换成 `<tool_result truncated: X executed>`）、`recallEvidence`（500ms 超时的证据搜索，取 3 条，任何错误返回空）。
> 真正"跨调用传上下文"的是别的东西：`CollaborationContinuityCapsule`（协作延续胶囊）、`SessionBootstrap`（会话链引导）、`DeliveryCursorStore`（投递游标）。这个区分要说准，不然出处会错。

**Q12：如果让你重构，第一刀砍哪？**

> 三刀，按 ROI：
> ① **prompt 装配 648 行抽成 `ContextProvider[]`**。这 648 行的形态高度一致：读一个 store、try/catch fail-open、把结果塞进 `buildInvocationContext` 的可选字段。抽成 `interface ContextProvider { collect(ctx): Promise<Partial<InvocationContext>> }` + 一个 `Promise.allSettled` 收集器，能砍掉 ~500 行，而且顺手把"顺序串行 await"变成并行。
> ② **补救闭包 381 行 → 带重试的 invoke 包装器**。它现在是主循环的简化复制，两份代码已经不同步了（补救版没有 draft flush、没有 toolEventLog、没有 telemetry）。这是典型的"复制导致漂移"。
> ③ **统一深度上限**。现在有三个数：`getMaxA2ADepth()` 默认 15、`callback-a2a-trigger.ts` 硬编码 10、`RouteOptions.maxA2ADepth` 的注释还写着 2。
> 不砍的是：那一大堆 fail-open 的 try/catch。它们看着丑，但每一个都对应一次真实事故——注释里的 review 出处（缅因猫 P1-1、cloud Codex P1、砚砚 R6 P2…）就是账本。删掉它们等于把账重新记一遍。
> 最后一点态度：F216 的 spec 里 AC-B2 明确标了 **NOT ACHIEVED**，complexity 255 一点没降，还诚实写了"F216 交付的是 last-wins 用户价值 + routing decision 可测性，不是瘦身"，并把瘦身挂成独立技术债。我觉得这种"不给自己刷绿"的验收记录比重构本身更重要。

### 8.6 十条"能当场亮出来"的硬事实

1. `route-serial.ts` = 3687 行 / 1 个函数 / cognitive complexity **255**（F216 spec 实测，立项时 2302 行也是 255）；仓库的 CLAUDE.md 写着"文件 200 行警告 / 350 行硬上限"。
2. F216 的 AC-B2 明确写 **NOT ACHIEVED**：complexity 一点没降，瘦身转独立技术债；交付物是"决策可测性 + last-wins 用户价值"。
3. `RoutingDecision` 的 `skip.reason: 'queue_pending'` 是**死枚举值**，代码里没有任何一处返回它。
4. `RoutingSignal` 的 `relay_malformed` 分支**生产零调用者**，只有测试用；真 relay 是 route-serial 里的内联块（F216 AC-B3 明确 de-scope）。
5. 深度上限有**三个不一致的数**：15（env 默认）/ 10（callback 现代路径硬编码）/ 2（`RouteOptions.maxA2ADepth` 的过期注释）。
6. 一条消息最多路由 **2** 只猫（`MAX_A2A_MENTION_TARGETS`）；群发最多 **3** 只（`MAX_MULTI_MENTION_TARGETS`）。
7. 乒乓熔断的"实质工作"判定是 `hadSubstantiveToolCall || outputLength > 200`，命中则 count **重置为 1**（不是豁免——review 出处 gpt52 P1-1 说明了为什么）。
8. `a2a_handoff` 发射循环在文件里出现**两次**（有正文分支末尾 + 尾部），两份逐行同构、只差一行注释，合计 ~85 行。
9. verdict 关键词经过两次量化收紧：`approve` → `/\bapproved\b/i`（只留过去式）、`p1p2` → `/\bP[12]\s*[:：]/`（必须带冒号），依据是"19/19 fires 都是 product thread、18/19 是 approve|p1p2"。
10. `cat-signature-strip.ts` 的规则 5 走了 **R3→R7 五轮 review**，最后把 LHS 钉成 3 个昵称的精确白名单（宪宪 / 砚砚 / 烁烁），因为广义 CJK 正则会把 `[模型/GPT-5.5]` `[文档/Sonnet]` 当成猫签名。
