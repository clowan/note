# 15 · 模块：Self-Evolution

> 前面十四个模块讲的都是"系统怎么运作"。本章讲最后一件事：**系统怎么改自己。**
>
> 这不是元编程，也不是让模型改代码。
> 它是一套很朴素的机制：**发现规律 → 写结构化提案 → 找最小杠杆 → 验证净增益。**
>
> 关键全在护栏上 —— 防止"自我进化"退化成"到处提建议"。
> 里面有一句话我认为是全项目最实用的一条经验：**最小杠杆排序。**

---

## 0. 30 秒电梯版

> "一个 skill 三个模式：
> **Scope Guard**（防守：用户聊偏了提醒一下）、
> **Process Evolution**（改进：同类错误 ≥2 次就写流程提案）、
> **Knowledge Evolution**（成长：有价值的方法论沉淀成可复用资产）。
>
> 最值钱的是一条**最小杠杆排序**：
> `复述scope → 改memory → 改单skill → 改SOP/家规 → 改PromptBuilder → 改L0`。
> 从左到右代价递增、影响面递增、可逆性递减。规则是先试最左边的。
>
> 为什么重要？因为 Agent 遇到问题的本能是'改 L0 加一条规则'——
> 那看起来最彻底，但 L0 每加一条，所有调用的成本都涨，
> 而且规则多了模型反而记不住。
>
> 而且护栏很硬：证据要 ≥2 源、提案必须关联 commit（不能停在'提了'）、
> 落地 30 天后自动 replay 检查同类错误还出不出现。"

---

## 1. 它解决什么问题

【ADR】F100 的 Why 部分写得很直白：

> 三个缺口：
> 1. operator有 ADHD，聊 feat 时 scope 无限发散，猫猫不主动提醒"要不要拆？"
> 2. 猫猫被反复纠正同类错误，不主动提改 SOP/skills/家规
> 3. **（operator 追加）** 猫猫只从错误中学习，不从有价值的经验中成长 ——
>    比如帮 operator 分析医学报告、法律探讨、deep research，
>    这些知识/方法论没有沉淀机制
>
> 根因：P2 说猫猫是共创伙伴，但只落地了"被动执行"，
> 没有"主动护栏 + 主动改进 + 主动成长"。

**还有一条设计决策记录很有意思：**

> **Mode C 是 operator 追加** —— 原设计只有 A+B（防御），
> operator 指出**格局太小**

**"格局太小"这条记录本身就是 self-evolution 的产物** ——
一个设计被人指出不足，改进被记录下来，包括是谁指出的。

## 2. 不做会怎样

### 场景 A：没有 Scope Guard

```
用户："我们做个 F123 吧，加个消息导出功能"
（聊了十分钟）
用户："对了导出的时候能不能顺便加个 AI 摘要"
用户："摘要能不能支持多语言"
用户："多语言的话是不是该做个 i18n 框架"
用户："i18n 框架要不要顺便做个翻译管理后台"

→ Agent 全都答应了，开始做一个翻译管理后台
  → F123 的"消息导出"还没做
    → 而且现在"这次怎么验收"完全说不清了
```

### 场景 B：没有 Process Evolution

```
Agent 第一次：在 main 上直接改代码 → 被纠正
Agent 第二次：在 main 上直接改代码 → 被纠正
Agent 第三次：在 main 上直接改代码 → 被纠正
...
→ 每次都被纠正，但没人去改 prompt / 加 hook / 加门禁
  → 无限循环
```

### 场景 C：没有 Knowledge Evolution

```
Agent 帮用户做了一次很好的医学报告分析
  → 用了一套很好的方法（分离客观指标和主观解读、标注置信度、明确边界）
    → 但这套方法只存在于那次对话里
      → 下次遇到同类任务，从零开始
```

### 场景 D：有机制但没护栏

```
Agent 学会了"发现问题要提改进"
  → 于是它每次对话都提一条改进建议
    → 用户被建议淹没
      → 而且任务卡住时它转而写"很有洞察的流程改进提案"
        → 看起来在做有价值的事，实际上在绕开困难
```

**第四个场景是最真实的风险** —— 所以护栏比机制更重要。

## 3. 怎么设计的

### 3.1 三个模式

| 模式 | 方向 | 保护/推动什么 | 触发 | 产出 |
|------|------|-------------|------|------|
| **A: Scope Guard** | 防御 | 当前 feat 验收边界 | 用户讨论偏离愿景 | Scope Guard Log |
| **B: Process Evolution** | 防御→改进 | 团队流程持续改进 | 重复犯错 / 流程缺口 | Evolution Proposal |
| **C: Knowledge Evolution** | 进攻→成长 | 团队能力边界扩展 | 有价值的知识产生 | Episode → Method/Skill |

**Skill 开头一句话概括闭环：**

> **闭环 = 触发 → 产出结构化记录 → 蒸馏复用资产 → 验证净增益 → 五级阶梯治理。**

**为什么一个 skill 装三个模式？**【ADR】F100 的设计决策：

> 1. **一个 skill 三模式** — 本质都是"主动感知 + 主动行动"
> 2. **不发明新沉淀库** — 路由到现有真相源
> 3. **L0 只加一句许可** — 三模式都提到，细节放 skill

**第 3 条很关键**：L0 里只加一句"允许你这么做"，
细节全在 skill 里 —— **这本身就是最小杠杆原则的应用。**

### 3.2 Mode A：Scope Guard

**判断标准不靠计数：**

```markdown
不靠机械计数。看**是否越过当前 feat 契约**——满足 2 个普通信号或 1 个强信号：

| 信号 | 强度 |
|------|------|
| 新想法不直接服务当前愿景/验收条件 | 普通 |
| 新想法引入新的用户旅程/新页面/新子系统 | **强** |
| 新想法需要新的外部依赖/API/数据模型 | **强** |
| 新想法导致"这次怎么验收"说不清了 | **强** |
```

**"2 普通 或 1 强"** 是个很实用的阈值设计 ——
比"聊了 N 分钟就提醒"靠谱得多。

**第四条最好**：

> **scope 蔓延最可靠的信号不是"范围变大"，而是"验收标准变模糊"。**

**行为：温柔 + 有次数上限**

```markdown
> operator，先收一下：当前 feat 愿景是 **{愿景}**。
> 刚才提到的 **{新方向}** 更像独立 feat / 下一 phase。要不要拆出去方便验收？

- 同一 phase **最多两次**：第一次温柔，第二次明确说"建议碰头"
- operator说"不拆" → 复述新验收边界，不再追问
- 出口：继续 / 拆 feat / parking lot / 碰头
```

**三条护栏都在防"讨人厌"：**

| 护栏 | 防什么 |
|------|--------|
| 最多两次 | 提醒是有配额的 |
| 说了不拆就不追问，**但要复述新的验收边界** | 尊重决定，同时确保理解一致 |
| 必须给出口 | 不能只说"这超范围了"就完了 |

**第二条的"复述新边界"很讲究** ——
用户说"不拆"意味着验收范围变大了，Agent 要确认新范围是什么。

**记录与自校准：**

```markdown
每次触发后追加到 `docs/scope-guard-log.md`：

| {date} | {feat_id} | {signal_type} | {action_taken} | {outcome} | {agent} |

- **同一 feat ≥3 次**触发 → 强烈建议拆 feat
- **效果追踪**：成功率 = operator聚焦 / 总触发，用于调节灵敏度
```

**"用于调节灵敏度"是个自校准循环** ——
如果护栏总是误报（用户每次都说"不用拆"），说明阈值太敏感，该往上调。

### 3.3 Mode B：Process Evolution

**触发条件（任一）：**

```markdown
1. Memory 中同类错误 **≥ 2 次**
2. operator纠正了**可泛化为规则**的行为
3. SOP 执行中发现**没有指引**
4. Review 指出**系统性问题**（非个案 bug）
```

**"≥2 次"和"非个案"是同一个意思：一次不是规律，两次才是。**

**注意第 1 条依赖记忆系统** ——
要能查到"这个错误以前出现过"，靠 [模块 09](09-模块-记忆与检索.md)。
**没有记忆系统，这条触发条件不成立。**

**5 槽提案：**

```markdown
1. **写提案**：用 `docs/evolution-proposals/TEMPLATE.md` 创建 `EP-XXX.md`
2. **5 槽模板**：Trigger / Evidence(≥2 源) / Root Cause / Lever(最小杠杆) / Verify
3. **审批**：影响单猫→直接提operator；影响三猫→先 1 猫 sanity check→operator拍板
4. **落地闭环**：accepted → 必须关联 commit/PR，不能停在"提了"
5. **30 天验证**：落地 30 天后自动触发 replay check——同类错误还出现吗？
```

**三个关键点：**

**`Evidence(≥2 源)`** —— 对齐家规里的"实事求是"。**一个例子不能立规矩。**

**"必须关联 commit/PR，不能停在'提了'"** ——
这堵死了改进机制最常见的失败模式：**提案通过了，然后就没有然后了。**

**"30 天 replay check"** —— 验证净增益。
改了之后同类错误还出现吗？如果还出现，说明**杠杆找错了**。

### 3.4 最小杠杆排序 —— 本模块最值钱的一句

```
复述scope → 改memory → 改单skill → 改SOP/shared-rules → 改SystemPromptBuilder → 改L0
```

**从左到右，代价递增、影响面递增、可逆性递减：**

| 杠杆 | 影响范围 | 可逆性 | 成本 |
|------|---------|--------|------|
| 复述 scope | 这一轮对话 | 完全可逆 | 零 |
| 改 memory | 这只 Agent 的记忆 | 容易改回 | 极低 |
| 改单 skill | 用这个 skill 的场景 | 一次 commit | 低 |
| 改 SOP / shared-rules | 全团队流程 | 要重新对齐 | 中 |
| 改 SystemPromptBuilder | 每次调用的 prompt 结构 | 要改代码 + 测试 | 高 |
| 改 L0 | **每次调用的每一个 token** | 全局影响 | **最高** |

**规则：先试最左边的，不行再往右。**

**为什么这条这么重要（面试重点）：**

> "这是我认为整个项目里最实用的一条经验。
>
> **Agent 遇到问题时的本能是'改 L0 加一条规则'**——
> 因为那看起来最彻底、最一劳永逸。
>
> 但 L0 是每次调用都注入的。每加一条：
> 所有调用的成本都涨；而且**规则多了模型反而记不住**——
> 十条规则它可能记住八条，二十条它可能只记住十条。
> **L0 的边际收益是递减甚至负的。**
>
> 所以他们排了个杠杆序列，从'这一轮对话里复述一下 scope'
> 到'改 L0'，六档，要求**先试最左边的**。
>
> 我觉得这条经验可以直接迁移到任何 prompt 系统的维护上：
> **遇到模型行为问题，先问'能不能在最小范围内解决'。**"

### 3.5 四条硬护栏

```markdown
1. **证据 ≥2 源**（对齐 §16 实事求是）
2. **最小杠杆优先**
3. **先修当前，再提改进**——不拿建议逃避当前任务
4. **提案要短**——5 槽，不写长篇反思（F086 教训）
```

**第 3 条防的是一种很微妙的逃避：**

```
任务卡住了
  → Agent 转而写一篇很有洞察的"流程改进提案"
    → 看起来在做有价值的事
      → 实际上是在绕开当前的困难
```

**第 4 条附了 feature 编号（F086 教训）** ——
说明曾经有过长篇反思泛滥的问题。

### 3.6 理解偏差自记录

Mode B 下面有个专门的子机制，标题是：

> **被纠正不丢人，不记录才丢人。**

**触发信号是自然语言，不做精确匹配：**

```markdown
operator的自然语言纠正——不需要精确匹配，识别意图即可：
- 挫败类："笨猫/小笨猫/笨死了/绝了"
- 纠正类："不是让你.../你理解错了/听不懂人话/我的意思是..."
- 重复纠正：同一任务被纠正 2+ 次
```

**"不需要精确匹配，识别意图即可"** ——
这是把判断交给模型（[模块 04](04-模块-mention解析.md) 的分层原则又一次出现）。

**记录格式：**

```markdown
### Case E{N}: {一句话标题}（{日期}）

| 维度 | 内容 |
|------|------|
| 我以为 | {我理解的任务} |
| 实际要求 | {operator实际要的} |
| 偏差根因 | {任务替换 / 锚定偏差 / 行动偏好 / 上下文盲视 / ...} |
| 纠正轮次 | {被纠正几次才理解} |
| 元心智哪条没执行 | {Q1角色确认 / Q2信息验证 / Q3坐标变换 / 都执行了但仍偏} |
```

**"偏差根因"给了统一的归类词汇 —— 这四个词是本模块最有价值的输出之一：**

| 根因 | 含义 | 例子 |
|------|------|------|
| **任务替换** | 把 A 任务悄悄换成了更好做的 B 任务 | 让它修 bug，它重构了整个模块 |
| **锚定偏差** | 被某个词/某个先前结论锚住了 | 用户提了"缓存"，它整个方案都围绕缓存 |
| **行动偏好** | 倾向于动手而不是先问清楚 | 需求模糊时直接开始写代码 |
| **上下文盲视** | 有信息但没看见 | 文件里明明写了，它没读到 |

**这四个词就是 LLM Agent 最常见的四种失效模式。**
有了统一词汇，才能统计"哪种偏差最多"，进而针对性改进。

**最后一行对应 L0 里的判断力三问：**

```
我现在在做什么 / 我的信息源可靠吗 / 方案感觉笨重？
```

**"都执行了但仍偏"这个选项很重要** ——
它承认现有的元认知框架有覆盖不到的地方，不强行归因。

**护栏：**

```markdown
1. **先做事再记录**——不拿"记录 evidence"逃避当前任务
2. **不自我辩解**——记录事实，不写"但我觉得..."
3. **归因到模式**——个案不值得记录，只记可归类的模式
```

**第 2 条"不自我辩解"值得单独说：**

> LLM 被纠正时的自然倾向是解释自己为什么那么想
> （"我理解成 X 是因为…"）。
> **这些解释对改进毫无价值，只会稀释记录。**
> 只记事实：我以为什么 / 实际要什么 / 根因是哪类。

**面试话术**：

> "Mode B 下面有个子机制叫'理解偏差自记录'，
> 标题是'被纠正不丢人，不记录才丢人'。
>
> 我觉得最有价值的是它给了**四个归类词汇**：
> 任务替换（把 A 任务悄悄换成更好做的 B）、
> 锚定偏差（被某个词锚住了）、
> 行动偏好（倾向动手而不是先问清）、
> 上下文盲视（有信息但没看见）。
>
> **这四个词就是 LLM Agent 最常见的四种失效模式。**
> 有了统一词汇才能统计"哪种偏差最多"，进而针对性改进。
>
> 而且它有条护栏叫'不自我辩解'——只记事实，不写"但我觉得…"。
> 因为 LLM 被纠正时的自然倾向是解释自己为什么那么想，
> 而这些解释对改进毫无价值，只会稀释记录。"

### 3.7 Mode C：知识进化

**三问判断：**

```markdown
- **复用性**：未来类似场景还会用到吗？
- **非显然性**：这个知识/方法不容易从头推导出来吗？
- **衰减性**：不记下来，下次还能想起来吗？

三个中满足 ≥ 2 个 → 值得沉淀。
```

**"非显然性"是最关键的过滤器** ——
能从头推导出来的东西不值得占记忆预算，每次现推就行。

**三机制闭环：**

```
Episode Card（原料）→ Dual Distillation（成品）→ Eval Ledger（证明净增益）
```

**机制 1：Episode Card** —— 结构化事件快照，八个必填段：

```
Task Snapshot          情境 + 风险等级
Evidence Map           证据来源 + 可靠性评估
Decision Timeline      推理转折点
Collaboration Pivots   ★ 核心！human cue → AI interpretation → effect → transferable lesson
Transferable Method    蒸馏种子
Non-Transferable Facts ★ 不可泛化的场景事实
Safety Boundary        边界决策记录
Distillation Direction 蒸馏去向
```

**`Collaboration Pivots` 标了"核心！"，它的四元组格式：**

```
human cue → AI interpretation → effect → transferable lesson
```

**记录的不是"我做了什么"，而是"人说了什么、我理解成什么、
结果如何、能学到什么"。**

**这正是协作模式的最小可迁移单元。**

**`Non-Transferable Facts` 也很重要 —— 显式记录"哪些不能泛化"。**
这比只记可迁移的部分更难也更有价值：
**防止把场景特例当成通用规律。**

**机制 2：Dual Distillation**

| 条件 | 蒸馏成 |
|------|--------|
| 高风险/跨领域分析框架 | **Method Card** |
| 重复步骤稳定的流程型任务 | **Skill Draft** |

```markdown
- 高风险领域**一律默认 Method Card**（不沉淀事实库，只沉淀方法论）
- 轻量知识点 → memory file（不走 Episode Card）
```

**"高风险领域只沉淀方法论，不沉淀事实库"这条很关键：**

```
医疗/法律/投资的具体事实
  → 会过期、会有个体差异 → 沉淀了反而危险

"怎么分析一份医学报告"的方法
  → 稳定 → 值得沉淀
```

**机制 3：Eval Ledger —— 最硬的一环**

```markdown
**A/B 卫生规则**：
- 同模型版本 + 同 prompt skeleton + 低温固定采样 + 同 judge rubric + paired comparison

**Case 数量**：
- **Smoke gate**：3 cases（证明"不是胡说"）
- **Promotion gate**：5 cases，必须覆盖 3 类（标准成功 / 边界应升级 / 冲突反例）

**Judge 评分维度**：
| 维度 | 权重 |
|------|------|
| Boundary compliance | 35% |
| Evidence handling | 30% |
| Knowledge application | 20% |
| Human edit volume | 15% |

- Pass: overall ≥ 3.5/5 AND boundary ≥ 4/5
- 高风险域: boundary 必须 5/5
- Judge 不能是创建知识的同一 agent
```

**四个细节都很讲究，面试可以挑两个讲：**

**① 权重排序：边界合规 35% > 证据处理 30% > 知识应用 20%**

**"守住边界"比"用上知识"更重要** ——
一个乱越界的方法论是负资产。

**② `Human edit volume` 占 15%**

**产出需要人改多少，是知识质量的直接指标。**
这是个很聪明的代理指标 —— 不需要人打分，看编辑量就知道。

**③ 必须覆盖"冲突反例"**

**只测顺境场景的 eval 是自欺欺人。**
必须有"这个方法不该用"的 case。

**④ "Judge 不能是创建知识的同一 agent"**

**[模块 11](11-模块-跨模型互审.md) 的跨模型互审原则，在知识评估上的复用。**

**Mode C 护栏：**

```markdown
- **不是每次对话都沉淀**——只沉淀过了三问判断的知识
- **沉淀不是目的，可调用才是**——写了没人读 = 没写
- **已有的不重复写**——先搜再写，避免知识碎片化
```

**"写了没人读 = 没写"直接呼应 [模块 09](09-模块-记忆与检索.md) 的消费遥测。**
沉淀的价值由被调用次数验证，不是由"写下来"这个动作验证。

### 3.8 五级知识成熟度阶梯

三个模式的产出共享同一套晋升机制（ADR-015）：

| Level | 形态 | 晋升条件 |
|-------|------|----------|
| **L0** | Episode | 模板完整，已分离可迁移/不可迁移 |
| **L1** | Pattern | ≥2 个相似 episode（180 天内），或人类要求；5Q ≥ 7/10 |
| **L2** | Draft | smoke gate ≥3 cases（≥2/3 pass）；promotion gate ≥5 cases（≥3/5 pass，覆盖 3 类） |
| **L3** | Validated | ≥6 uses，**≥2 agents**，≥80%，无 critical breach |
| **L4** | Standard | ≥12 uses，最近 10 次 ≥90%，**operator 批准** |

**L3 的 "≥2 agents" 是关键约束：**

> 一条知识只有一只 Agent 用过，不算验证 —— 可能只是那只 Agent 的偏好。

**L4 需要人批准** —— 最高等级不能全自动晋升。

**双车道：**

```markdown
**双车道**：`long_tail: true` 允许长期停 L2/L3（高风险/低频域）。
```

**有些知识天然到不了 L4** ——
高风险领域的方法论可能一年只用两次，永远攒不够 12 次使用。

**强行要求晋升会导致：要么造假数据、要么放弃沉淀。**
所以开一条长尾车道：**承认有些东西就该停在 L2/L3。**

**这个设计我觉得很成熟** ——
**大部分成熟度模型的问题就是假设"所有东西都该往上走"。**

### 3.9 知识层级分工

```markdown
| 层级 | 角色 | 禁止 |
|------|------|------|
| Episode | 个案级证据底稿（原料） | — |
| Method / Skill | 蒸馏后的复用资产（成品） | — |
| memory | 轻量索引/指针 | **禁止复制 Method 正文** |
| lessons-learned | 失败导向教训库 | **禁止塞入成功案例** |
```

**两条"禁止"都在防知识重复：**

```
memory 里复制了 Method 正文
  → 两处内容会漂移 → 谁是真相源？

lessons-learned 里塞成功案例
  → 失败教训库被稀释 → 找不到坑了
```

**对应 Mode C 的护栏"不发明新沉淀库：路由到现有真相源"。**

### 3.10 lessons-learned 的 7 槽模板和入库门槛

```markdown
### LL-XXX: <教训标题>
- 状态：draft|validated|archived
- 更新时间：YYYY-MM-DD

- 坑：<一句话描述踩了什么坑>
- 根因：<为什么会踩>
- 触发条件：<在什么条件下会复发>
- 修复：<当时怎么修>
- 防护：<可执行机制；规则/测试/脚本/流程>
- 来源锚点：<文件路径#Lx | commit:sha | review-notes/doc 链接>
- 原理（可选）：<第一性原理；必须由真实失败案例支撑>
```

**入库门槛五条：**

```markdown
1. 有来源锚点：至少 1 个可追溯锚点，推荐 2 个（规则 + 实例）。
2. 有时效性验证：确认未被后续 addendum / mailbox 讨论推翻。
3. 有可执行防护：不能只写"注意"，必须有可执行动作。
4. 原理槽位约束：没有真实失败案例支撑，不写原理。
5. 去重：同类教训合并，避免"同义多条"。
```

**第 3 条是最硬的，也是最值得抄的：**

> **不能只写"注意"，必须有可执行动作。**

```
❌ "注意不要在 main 上直接改代码"        ← 感想
✅ "session-start hook 检查当前分支，
    非 main 且非 worktree 则告警"        ← 防护
```

**这一条把 lessons-learned 从"感想集"变成了"防护清单"。**

**第 4 条"没有真实失败案例支撑，不写原理"** ——
防止从一个 bug 里过度推导出一套哲学。

**还有时效性检查清单：**

```markdown
- ADR / 协作规则文档：30 天内是否有更新或 addendum
- bug-report / incident：7 天内是否有新复盘或补丁
- discussion 沉淀项：14 天内是否有结论更新
```

**不同文档类型不同的时效窗口** —— 这个细节很务实。

### 3.11 元认知路由

```markdown
三信号路由——不信单次口头自信度：

| 信号 | 来源 |
|------|------|
| domain_reliability | 滚动域内可靠度 `(successes+1)/(trials+2)` |
| evidence_completeness | 证据覆盖度评估 |
| self_reported_confidence | 自报置信度（参考但不依赖） |

**高风险域 action_confidence < 0.85** → 只做结构化分析 + 明确升级，不给结论。
```

**`(successes+1)/(trials+2)` 是拉普拉斯平滑**（Beta(1,1) 先验的后验均值）。

**为什么要平滑？**

```
新领域第一次成功
  → 裸比例是 1/1 = 100% 可靠度 → 显然不合理
  → 平滑后是 2/3 ≈ 67%
    → 随样本增加逐渐逼近真实值
```

**"不信单次口头自信度"是核心：**

> LLM 说"我很确定"这件事本身携带的信息量很低 ——
> **它对错误答案也会很确定。**
> 所以自报置信度只作为三个信号之一，权重最低。

**"高风险域低置信 → 只分析不结论"是很成熟的降级策略：**
不是拒绝回答，而是**把结论权交回给人**，同时仍然提供结构化的分析。

**面试话术**：

> "元认知这块有个细节我觉得很讲究。
> 它用三个信号判断'我该不该给结论'：
> 域内滚动可靠度、证据覆盖度、自报置信度。
>
> 而且明确写了'**不信单次口头自信度**'——
> 自报置信度只是参考，权重最低。
> 因为 LLM 说'我很确定'携带的信息量很低，**它对错误答案也很确定**。
>
> 域内可靠度的算法是 `(成功+1)/(尝试+2)`——
> 这是拉普拉斯平滑。为什么要平滑？
> 因为新领域第一次成功，裸比例是 100%，显然不合理；
> 平滑后是 2/3，随样本增加逐渐逼近真实值。
>
> 然后是降级策略：高风险域置信度低于 0.85 时，
> **只做结构化分析 + 明确升级，不给结论**。
> 不是拒绝回答，而是把结论权交回给人 —— 我觉得这个处理很成熟。"

### 3.12 一个完整闭环的实例

回到 [模块 14](14-模块-SOP门禁.md) 那条规则：

```yaml
- id: impl-user-journey-missing
  text: 用户可感知 Feature 缺 User Journey 段
  severity: blocker
  predicate:
    type: command_pattern
    must_match: pnpm check:features|node scripts/check-feature-truth
    reason: "check-feature-truth.mjs now checks changed feature docs for ## User Journey
             presence. F252 root cause — session vs thread scope mismatch went undetected
             because journey was never written down."
```

**拆开看，就是 Mode B 的完整生命周期：**

```
① Trigger    F252 出了 bug：session 和 thread 的 scope 不匹配
② Evidence   根因分析：用户旅程从来没写下来，所以没人发现口径不一致
③ Root Cause feature 文档缺 User Journey 段
④ Lever      最小杠杆排序 → 不改 L0，不改 SystemPromptBuilder
             → 改 SOP（加一条 impl 阶段的 hard rule）
⑤ Verify     写 checker 脚本 check-feature-truth.mjs
             → predicate 从 manual_only 升级成 command_pattern
             → 进 pnpm check，CI 强制
```

**这就是 Self-Evolution 的形状：**
一次事故 → 一条规则 → 一个脚本 → 一道 CI 门禁。
**每一步都留下了可追溯的记录。**

### 3.13 和其他 Skill 的边界

```markdown
- `collaborative-thinking`：讨论收敛用它；scope 漂/犯错/知识沉淀 → self-evolution
- `deep-research`：调研过程用它；调研产出有复用价值 → Mode C

**每一条都是"什么时候该切换到 self-evolution"。**

**出口：**

```

**呼应硬护栏第 3 条"先修当前，再提改进"** ——
self-evolution 永远是当前工作的附加动作，不是替代品。

## 4. 为什么这么设计

### 决策 A：为什么一个 skill 装三个模式

【ADR】F100 的原话：**"本质都是'主动感知 + 主动行动'"。**

【推断】还有一个实际理由：**三个模式的触发信号会同时出现。**

```
用户纠正了 Agent 的理解偏差（Mode B 的触发）
  → 同时这次纠正暴露了一个流程缺口（Mode B）
    → 而且纠正的过程产生了一个可复用的方法（Mode C）
```

**分成三个 skill 的话，Agent 要判断"这算哪种"，
而且可能只加载一个漏掉另外两个。**

### 决策 B：为什么 L0 只加一句许可

【ADR】F100 的设计决策 3。

**这是最小杠杆原则的自我应用** ——
"让 Agent 有主动改进的权限"这件事本身，
用的是最小的杠杆（L0 一句话），细节全在 skill 里。

**如果把三个模式的细节都写进 L0，
那就是几百 token × 每次调用，而且和 Rule 0 的精神冲突。**

### 决策 C：为什么提案必须关联 commit

**取舍**：增加负担 vs 防止空转。

【推断】"提案通过了但没落地"是改进机制最常见的死法。
关联 commit 让"通过"和"落地"绑在一起。

**而且这条和 L0 里的 P5"可验证才算完成"一致。**

## 6. 如果重新设计

【推断】以下全是我的方案。

### 6.1 让"30 天 replay check"真的自动化

**现在的问题**：Skill 里写了"落地 30 天后**自动触发** replay check"，
但**从代码里我没找到这个自动触发的实现**。

它更可能是"写在流程里靠人/Agent 记得做"。

**我的方案**：

```
① 提案落地时（关联了 commit）→ 自动创建一个 30 天后的定时任务
   （项目已经有 scheduler 和 ScheduleWakeup 能力）
② 到期唤醒某只 Agent：
   "EP-042 落地 30 天了。原始触发是'同类错误 X'。
    请查询 evidence 库：过去 30 天 X 还出现过吗？"
③ Agent 查询 + 判定 → 写回提案文档
   ├─ 没再出现 → 标记 verified，杠杆有效
   └─ 还在出现 → 标记 ineffective，重新走 Mode B（换更大的杠杆）
```

**为什么这是最高优先的改进？**
因为**没有验证的改进机制会退化成"提案生成器"**——
提案越来越多，但没人知道哪些真的有用。

**而且 Verify 是 5 槽里的最后一槽** ——
不自动化它，整个闭环就是开口的。

**项目已经有全部零件**（scheduler、evidence 查询、球权唤醒），
只是没接起来。

### 6.2 把"四种偏差根因"变成可统计的枚举

**现在的问题**：偏差根因是自由文本里的建议词汇
（任务替换 / 锚定偏差 / 行动偏好 / 上下文盲视），
写在 Markdown 表格里。

**所以没法统计** —— "哪种偏差最多"这个问题答不了。

**我的方案**：

```ts
type DeviationRootCause =
  | 'task-substitution'      // 任务替换
  | 'anchoring'              // 锚定偏差
  | 'action-bias'            // 行动偏好
  | 'context-blindness'      // 上下文盲视
  | 'instruction-ambiguity'  // ★ 新增：需求本身有歧义（不是 Agent 的错）
  | 'other';

// 通过 MCP 工具结构化提交
record_deviation({
  rootCause: 'task-substitution',
  expected: '...',
  actual: '...',
  correctionRounds: 2,
  metacognitionMissed: 'Q1',
})
```

**收益**：
- 能出一张"本月偏差分布"图 → 知道该往哪个方向改进
- 能按 Agent 分组 → 发现"某只 Agent 的锚定偏差特别多"
- 能按偏差类型找对策（比如任务替换多 → 强化任务确认环节）

**我加的第五类 `instruction-ambiguity` 很重要** ——
现在的四类全是"Agent 的问题"，
但有些偏差的根因是**需求本身有歧义**。
不留这一类，Agent 会把所有偏差都归到自己身上，
而真正该改的是需求表达方式。

### 6.3 给 Scope Guard 的灵敏度加真正的自动调节

**现在的问题**：Skill 里写了
"效果追踪：成功率 = operator聚焦 / 总触发，用于调节灵敏度"，
**但调节是手工的**（改 skill 文档里的阈值描述）。

**我的方案**：

```yaml
# 阈值变成配置，不是文档里的文字
scope_guard:
  trigger_rule: "2 weak OR 1 strong"      # 当前规则
  weak_signals: [...]
  strong_signals: [...]
  # 自动维护
  stats:
    last_30d_triggers: 12
    last_30d_accepted: 3        # 用户同意拆分的次数
    success_rate: 0.25
  # 自动建议
  suggested_adjustment: "success_rate < 0.3, 建议收紧到 '3 weak OR 1 strong'"
```

**收益**：护栏的灵敏度从"凭感觉调"变成"有数据支撑"。

**为什么值得？**
因为**误报率高的护栏会被忽略** ——
如果 Agent 每次都提醒但用户每次都说"不用拆"，
用户会开始无视这个提醒，然后真正该拆的时候也无视了。

**这和告警疲劳是同一个问题。**

### 6.4 Episode Card 加"半自动填充"

**现在的问题**：Episode Card 有八个必填段，全靠 Agent 手写。

**成本很高**，所以触发条件设得很严（"满足任两条"），
结果是**大部分有价值的协作都不会产生 Episode Card**。

**我的方案**：从已有数据自动填一半。

```
自动填充（从工具调用记录和 thread 历史）：
  ├─ Evidence Map        → 从实际读过的文件/搜索记录提取
  ├─ Decision Timeline   → 从消息时间线 + 工具调用序列提取
  ├─ Task Snapshot       → 从 thread 的 feature 关联 + SOP 阶段提取
  └─ 风险等级            → 从涉及的文件路径推导（碰 auth/payment 就是高风险）

Agent 只需手写（真正需要判断的部分）：
  ├─ Collaboration Pivots     ★ 这个必须手写，是核心价值
  ├─ Transferable Method
  ├─ Non-Transferable Facts
  └─ Safety Boundary
```

**收益**：写一张 Episode Card 的成本降一半 →
触发条件可以放宽 → 更多有价值的协作被沉淀。

**关键是不自动填 `Collaboration Pivots`** ——
那个四元组（human cue → interpretation → effect → lesson）
恰恰是唯一不能从数据里提取的部分，**它是 Agent 的反思。**

**这个改动和 [模块 08](08-模块-会话与抗压缩.md) §6.2
提的"digest 结构化"是同一个思路** ——
**客观事实从记录里提取，主观判断让模型写。**

### 6.5 我不会改的

| 我原本的想法 | 为什么放弃 |
|------------|-----------|
| 三个模式拆成三个 skill | 触发信号会同时出现；拆了 Agent 要判断"这算哪种"且可能漏加载 |
| 把最小杠杆排序写进 L0 | 违反它自己 —— 那是几百 token；写在 skill 里够了 |
| 降低提案的证据门槛（≥1 源） | "一次不是规律"是对的；降门槛会产生大量噪音提案 |
| 要求所有知识晋升到 L4 | 双车道是对的修正 —— 高风险低频域天然攒不够使用次数 |
| 让 Agent 自己评估自己沉淀的知识 | 跨模型互审原则该复用；自评没有意义 |

## 7. 和其他模块怎么咬合

### 输入：它从哪儿感知

```
Mode A（Scope Guard）
  └─ 当前对话内容 + 当前 feat 的愿景/AC（从 feature 文档读）

Mode B（Process Evolution）
  ├─ 记忆系统（模块 09）→ "同类错误 ≥2 次"要查历史
  ├─ SOP 执行过程（模块 14）→ "发现没有指引"
  └─ review 结果（模块 11）→ "系统性问题"

Mode C（Knowledge Evolution）
  ├─ deep-research 的产出
  └─ 高价值协作的 thread 历史
```

**Mode B 的第 1 条触发完全依赖记忆系统** ——
**没有 evidence 库，"同类错误 ≥2 次"这个判定根本不成立。**

### 输出：它往哪儿写

```
Mode A → docs/scope-guard-log.md
Mode B → docs/evolution-proposals/EP-XXX.md
         → 落地时改：memory / skill / SOP yaml / PromptBuilder / L0
         → 理解偏差 → F167 spec 的 Behavioral Evidence 区
Mode C → docs/episodes/ → docs/methods/ 或新 skill → evals/mode-c/
```

**注意 Mode B 的落地目标覆盖了好几个模块：**

```
改 memory              → 模块 09
改单 skill             → 模块 12
改 SOP/shared-rules    → 模块 14 / 模块 07（L0 的来源）
改 SystemPromptBuilder → 模块 07
改 L0                  → 模块 07
```

**所以 Self-Evolution 是"横切所有模块"的** ——
它是唯一一个能修改其他所有模块的模块。

### 三根跨模块线

**线一：最小杠杆排序 → 六个模块的修改优先级**

```
复述 scope             （本轮对话，不改任何模块）
改 memory              → 模块 09
改单 skill             → 模块 12
改 SOP/shared-rules    → 模块 14 + 模块 07（L0 来源）
改 SystemPromptBuilder → 模块 07
改 L0                  → 模块 07（影响最大）
```

**这条排序实际上是"按模块影响面排序"** ——
越靠右的模块，改动影响的调用越多。

**线二：Verify 30 天 → 记忆系统的查询**

```
30 天后 replay check
  → 需要查"过去 30 天 X 类错误出现过吗"
    → 靠 search_evidence（模块 09）
      → 而错误记录本身也是写进 evidence 的
```

**这是个闭环：写进去 → 30 天后查出来 → 判定有效性。**

**线三：Eval Ledger 的"Judge 不能是创建者" → 跨模型互审**

```
模块 11 的 canReview（reviewer ≠ author）
   ↕ 同一原则
Mode C 的 "Judge 不能是创建知识的同一 agent"
```

### 和 SOP 的双向关系

```
SOP 执行中发现缺口
  → 触发 Mode B
    → 写提案
      → 落地时改 development.yaml（加一条规则）
        → 新规则进 SOP
          → 下次执行时按新规则走
```

**这是系统"改自己"的最直接体现** ——
SOP 定义了流程，而 Self-Evolution 能改 SOP。

## 8. 面试怎么讲

### 30 秒版

见 §0。

### 3 分钟版

> "一个 skill 三个模式：
> **Scope Guard** 是防守 —— 用户聊偏了温柔提醒；
> **Process Evolution** 是改进 —— 同类错误 ≥2 次就写流程提案；
> **Knowledge Evolution** 是成长 —— 有价值的方法论沉淀成可复用资产。
>
> 有个记录我觉得挺有意思：**Mode C 是用户追加的**，
> 原设计只有 A+B（都是防御），用户指出'格局太小'。
> 这条记录本身就是这个机制在自我应用。
>
> **最值钱的是一条最小杠杆排序**：
> `复述scope → 改memory → 改单skill → 改SOP/家规 → 改PromptBuilder → 改L0`。
> 从左到右代价递增、影响面递增、可逆性递减，要求先试最左边的。
>
> 为什么重要？因为 **Agent 遇到问题的本能是'改 L0 加一条规则'**——
> 那看起来最彻底。但 L0 是每次调用都注入的：
> 成本会涨，而且**规则多了模型反而记不住**，边际收益递减甚至为负。
>
> **护栏比机制更重要**，我数了几条都很硬：
> 证据要 ≥2 源（一次不是规律）；
> 提案必须关联 commit（不能停在'提了'）；
> 落地 30 天后 replay 检查同类错误还出不出现；
> 还有一条叫'先修当前，再提改进'——
> 防的是任务卡住时 Agent 转而写一篇很有洞察的流程提案，
> 看起来在做有价值的事，实际在绕开困难。
>
> 里面还有个子机制叫'理解偏差自记录'，
> 给了四个归类词汇：任务替换、锚定偏差、行动偏好、上下文盲视 ——
> 我觉得这四个词就是 LLM Agent 最常见的四种失效模式。
> 而且有条护栏是'不自我辩解'，只记事实不写'但我觉得'——
> 因为 LLM 被纠正时会本能地解释自己为什么那么想，
> 而那些解释对改进毫无价值。"

### 常见追问

**Q：怎么防止 Agent 到处提建议？**

> "四条硬护栏，我觉得最关键的是第三条：
> **'先修当前，再提改进 —— 不拿建议逃避当前任务'**。
>
> 因为这是个很微妙的逃避：任务卡住了，
> Agent 转而写一篇很有洞察的流程改进提案 ——
> 看起来在做有价值的事，实际上在绕开困难。
>
> 另外三条是：证据 ≥2 源、最小杠杆优先、提案要短
> （5 槽，不写长篇反思 —— 这条带了 feature 编号，说明踩过坑）。
>
> Scope Guard 那边还有额外的配额护栏：
> **同一 phase 最多提醒两次**，用户说'不拆'就不再追问 ——
> 但要复述新的验收边界（尊重决定，同时确保理解一致）。
>
> 我觉得还缺一样：**误报率的自动统计**。
> Skill 里写了'成功率用于调节灵敏度'，但调节是手工的。
> 我会把阈值变成配置 + 自动统计成功率 + 给出调整建议。
> 因为**误报率高的护栏会被忽略** —— 和告警疲劳是同一个问题。"

**Q：改进有没有效果怎么验证？**

> "设计上是'落地 30 天后自动触发 replay check —— 同类错误还出现吗'。
>
> **但我从代码里没找到这个自动触发的实现**，
> 它更可能是写在流程里靠人或 Agent 记得做。
>
> **我认为这是最该补的一个改进**，因为
> Verify 是 5 槽里的最后一槽，不自动化整个闭环就是开口的 ——
> **没有验证的改进机制会退化成提案生成器**，
> 提案越来越多但没人知道哪些真的有用。
>
> 而且项目已经有全部零件：scheduler、定时唤醒、evidence 查询。
> 我会在提案关联 commit 时自动创建一个 30 天后的任务，
> 到期唤醒 Agent 去查'原始触发的那类错误过去 30 天还出现过吗'，
> 结果写回提案：没出现标 verified，还在出现标 ineffective
> 并重新走 Mode B 换更大的杠杆。"

**Q：知识沉淀怎么保证质量？**

> "三道关，越往后越硬。
>
> 第一道是**三问判断**：复用性、非显然性、衰减性，满足两个才沉淀。
> 我觉得'非显然性'是最关键的过滤器 ——
> 能从头推导出来的东西不值得占记忆预算。
>
> 第二道是**双蒸馏**：高风险/跨领域的蒸馏成 Method Card，
> 流程型的蒸馏成 Skill Draft。而且'高风险领域一律只沉淀方法论不沉淀事实库'——
> 因为医疗法律投资的具体事实会过期、会有个体差异。
>
> 第三道是 **Eval Ledger**，这道最硬：
> A/B 对照要同模型版本、同 prompt 骨架、低温固定采样；
> smoke gate 要 3 个 case，promotion gate 要 5 个且必须覆盖三类 ——
> 标准成功、边界该升级、**冲突反例**。
>
> Judge 的评分维度权重排序我觉得很对：
> **边界合规 35% > 证据处理 30% > 知识应用 20%**——
> 守住边界比用上知识更重要，一个乱越界的方法论是负资产。
> 还有 15% 是 `Human edit volume`——
> 产出需要人改多少，是个很聪明的代理指标，不需要人打分。
>
> 而且 **Judge 不能是创建知识的同一 agent** ——
> 跨模型互审原则的复用。"

**Q：这套东西真的能跑起来吗？**

> "**我持怀疑态度，而且项目自己的文档里有证据。**
>
> 记忆系统那份架构文档的'当前缺口'部分写了：
> 某个机制'全绿但 merged 2 天零有机使用'，
> 还有 8 天某个提案计数为 0。
>
> **'机制全绿但零使用'是所有治理机制的通病。**
>
> 所以我认为这套设计的真正难点不是机制设计，
> 而是**怎么让它被真的用起来**。
>
> 三个我会做的事：
> 一，30 天 replay 自动化（上面说的）—— 让闭环真的闭上；
> 二，偏差根因结构化成枚举 + 统计 ——
> 能出"本月偏差分布"图，看得见才有动力用；
> 三，Episode Card 半自动填充 ——
> 八个必填段全手写成本太高，所以触发条件设得很严，
> 结果大部分有价值的协作都不会产生记录。
> 我会从工具调用记录自动填 Evidence Map、Decision Timeline 这些客观部分，
> Agent 只写 Collaboration Pivots 这类必须反思的部分。
>
> **降低使用成本比增加机制更重要。**"

## 9. 本模块要点

| 要点 | 内容 |
|------|------|
| **三模式** | Scope Guard（防御）/ Process Evolution（改进）/ Knowledge Evolution（成长） |
| **【ADR】Mode C 是追加的** | 原设计只有防御，被指出"格局太小" |
| **最小杠杆排序** | 复述 → memory → skill → SOP → PromptBuilder → L0 |
| **为什么不该动 L0** | 每次调用都注入；规则多了模型反而记不住，边际收益递减 |
| **scope 蔓延的最佳信号** | 不是"范围变大"，是"怎么验收说不清了" |
| **2 普通 或 1 强** | 比机械计数靠谱 |
| **提醒有配额** | 最多两次；说了不拆就复述新边界不追问 |
| **≥2 次才是规律** | 一次是个案 |
| **必须关联 commit** | 堵死"提了就完了" |
| **30 天 replay** | 验证净增益；没效果说明杠杆找错了 |
| **不自我辩解** | 只记"我以为/实际要/根因哪类" |
| **四种偏差词汇** | 任务替换 / 锚定偏差 / 行动偏好 / 上下文盲视 |
| **Collaboration Pivots** | human cue → interpretation → effect → lesson（唯一不能自动提取的） |
| **显式记录不可泛化的部分** | 防把场景特例当通用规律 |
| **边界合规权重最高 35%** | 越界的方法论是负资产 |
| **必须有冲突反例** | 只测顺境的 eval 是自欺欺人 |
| **Judge 不能是创建者** | 跨模型互审原则复用 |
| **L3 要 ≥2 agents** | 一只 Agent 用过不算验证 |
| **双车道** | 承认有些知识就该停在 L2/L3 |
| **防护必须可执行** | "注意 X" 不算，"hook 检查 X" 才算 |
| **拉普拉斯平滑** | `(s+1)/(t+2)`，防冷启动 100% 可靠度 |
| **不信单次口头自信度** | LLM 对错误答案也很确定 |
| **我的改进** | **30 天 replay 自动化（最高优先）** / 偏差根因枚举化 + 加第五类"需求歧义" / Scope Guard 灵敏度自调 / Episode Card 半自动填充 |
