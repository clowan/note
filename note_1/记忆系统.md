# 一、先给出模块的合理边界

这个目标模块不是一个单独的 `Memory` 类，而是一个**本地证据索引与检索系统**：

```text
真实来源
├── docs/*.md                         项目文档、决策、计划、教训
├── Redis MessageStore                线程消息
├── JSONL transcript                  Redis 消息过期后的历史回填来源
├── docs/markers/*.yaml               候选记忆 / 物化工作流
└── 可选的全局知识、外部 collection

        │ IndexBuilder / Scanner
        ▼

本地持久化读模型
├── evidence_docs                    文档摘要与元数据
├── evidence_fts                     文档级 FTS5
├── evidence_passages                消息级 passage
├── passage_fts                      消息级 FTS5
├── evidence_vectors                 文档级向量
├── passage_vectors                  消息级向量
├── edges                            知识图边
└── summary_state / summary_segments  摘要生命周期状态

        │
        ├── MCP search_evidence
        ├── Agent 路由中的直接 recall
        ├── SessionBootstrap 自动召回
        ├── API evidence route
        └── graph / recent / session 等邻近导航能力
```

## 1. 它真正解决的业务问题

实现层面的目标不是“替模型记住所有内容”，而是：

1. 把项目文档、线程摘要、消息 passage 编译成本地可检索读模型；
2. 对查询进行词法、语义或混合召回；
3. 返回**候选证据的摘要、anchor、来源和下钻方式**；
4. 让 Agent 再调用文件读取、线程上下文或 session 工具，获取原文；
5. 在 embedding 不可用、索引部分缺失、某个 collection 失败时尽量降级，而不是让整个 Agent 请求失败。

所以需要牢记一句话：

> **search_evidence 负责“找到候选证据”，不负责直接替你读完所有原文。**

这几个边界不能混在一起：

```text

```

它不是先走 MCP，也不是先走 `/api/evidence/search`。

## 4.5 Progressive Relaxation：长查询不是只试一次

虽然本次固定请求只有一个 token，但为了理解真实算法，假设查询是：

```text
F102 memory and the
```

`buildProgressiveFtsQueries()` 会按顺序构造：

```text
第 1 层：
"F102" "memory" "and" "the"

第 2 层：
"F102" AND "memory" AND ("and" OR "the")

第 3 层：
"F102" OR "memory" OR "and" OR "the"
```

实现中的 token 强弱规则：

- `F102`：强 token；
- 包含 CJK 的 token：强 token；
- 长度大于等于 4：强 token；
- 其他短 token：弱 token。

调用者找到第一层有结果后就停止：

```ts
if (rows.length > 0) break;
```

因此它不是把三层结果合并，而是：

```text
严格 AND 命中 → 立即停止
严格失败 → 尝试强词 AND 弱词 OR
仍失败 → OR-all
```

### 算法代价

设：

- `N` = evidence document 总数；
- `K` = 候选池大小，通常 20 到 100；
- `W` = 查询 token 数。

则：

- FTS 最多执行 3 个查询；
- 每个查询限制结果数为 `K`；
- 但后面的 `LIKE` backfill 没有直接用 `LIMIT` 截断，可能扫描很多 `evidence_docs` 行；
- `seenAnchors` 去重的空间成本约为 `O(R)`，其中 `R` 是召回候选数。

## 5.4 RRF 具体怎么算

文档级 hybrid 实现位于：

[`D:\AI\clower-1\clowder-ai\packages\api\src\domains\memory\SqliteEvidenceStore.ts#L1226-L1328`](file:///D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/SqliteEvidenceStore.ts#L1226-L1328)

核心逻辑：

```ts
const RRF_K = 60;
const nnWeight = hasCJKCharacters(query) ? CJK_NN_WEIGHT : 1.0;

for (let i = 0; i < lexicalResults.length; i++) {
  const anchor = lexicalResults[i].anchor;
  scores.set(
    anchor,
    (scores.get(anchor) ?? 0) + 1 / (RRF_K + i),
  );
}

for (let i = 0; i < nnResults.length; i++) {
  const anchor = nnResults[i].anchor;
  scores.set(
    anchor,
    (scores.get(anchor) ?? 0) +
      nnWeight / (RRF_K + i),
  );
}
```

按当前代码的 **0-based rank**，公式是：

\[
score(a)
=
\sum_{\text{lexical rank }i}
\frac{1}{60+i}
+
\sum_{\text{NN rank }j}
\frac{w_{NN}}{60+j}
\]

其中：

- `i/j`：数组下标，从 0 开始；
- `60`：RRF 的平滑常数；
- `wNN`：普通查询为 `1.0`，CJK 查询为 `1.5`。

### 静态示意数据

下面不是实际数据库输出，而是根据源码做的算法复演。

假设：

```text
lexical candidates:
rank 0: F102
rank 1: F209
rank 2: ADR-020

vector NN:
rank 0: F209
rank 1: ADR-020
rank 2: F148
```

因为查询是 `F102`，不含 CJK，所以：

```text
wNN = 1.0
```

计算：

| anchor | lexical 部分 | vector 部分 | 总分 |
|---|---:|---:|---:|
| F102 | 1/60 = 0.016667 | 0 | 0.016667 |
| F209 | 1/61 = 0.016393 | 1/60 = 0.016667 | 0.033060 |
| ADR-020 | 1/62 = 0.016129 | 1/61 = 0.016393 | 0.032522 |
| F148 | 0 | 1/62 = 0.016129 | 0.016129 |

排序：

```text
F209
ADR-020
F102
F148
```

最终 `limit=3` 时可能返回：

```text
[F209, ADR-020, F102]
```

这解释了一个关键取舍：

> exact anchor 会优先进入 lexical 候选，但当前代码没有保证它在 hybrid 最终结果中永远排第一。

如果查询包含中文，例如：

```text

```

则 `wNN=1.5`，向量路径的贡献会被放大，用来弥补 BM25/FTS5 对中文召回较弱的问题。

## 5.5 Vector anchor 为什么还要回 SQLite hydrate

`VectorStore.search()` 返回的主要是：

```ts
{ anchor, distance }
```

它不直接带完整 `EvidenceItem`。

因此 hybrid 会：

1. 收集 lexical 和 vector 的所有 anchor；
2. 找出 lexical 没有、但 vector 找到的 anchor；
3. 对这些 anchor 执行一次：

```sql
SELECT * FROM evidence_docs
WHERE anchor IN (?, ?, ...)
```

4. 重新应用：
   - kind；
   - scope；
   - status；
   - keywords；
   - threadId；
   - world/scene；
   - provenance；
   - backstop；
5. 过滤掉 hydrate 不成功的 anchor；
6. 按 RRF 分数排序。

这是为了避免 N+1：

```text
不是每个向量命中再查一次数据库，
而是一次 IN(...) hydrate。
```

但是它不是一个覆盖 lexical 与 vector 的全链路事务。后面会讲并发边界。

## 10.3 hybrid 检索不是一个全链路事务

hybrid 路径有多个 `await`：

```text

  ↓ await isEmbeddingAvailable()
Embedding health probe
  ↓ await embedding.embed()
外部 Embedding HTTP
  ↓ vector search / hydrate

```

因此可能发生：

1. lexical 查询拿到 `F102`；
2. embedding 请求等待期间，IndexBuilder 删除或更新了某条 evidence；
3. vector 返回旧 anchor；
4. hydrate 时找不到该 anchor，于是被过滤；
5. 新增的文档不会自动出现在已经完成的 lexical candidate pool 中。

源码没有一个包住：


# 十二、本篇面试闭环

## 面试官第一问：你们的本地记忆系统入口在哪里？

### 可直接表达的回答

> 入口有两层。Agent 侧通常通过 `cat_cafe_search_evidence` 进入 MCP，MCP 工具只负责参数校验和 HTTP 转发；真正的检索服务在 API 进程，由 `KnowledgeResolver` 和 `SqliteEvidenceStore` 完成。底层以 SQLite 的 `evidence_docs + FTS5` 为词法主索引，向量是可选加速器。搜索返回的是摘要、anchor、sourcePath 和 drillDown，不直接返回完整原文，原文由后续的文件或线程读取工具下钻。

### 面试官追问：那 MCP 是不是直接访问 SQLite？

### 源码级回答

不是。`packages/mcp-server/src/tools/evidence-tools.ts` 里使用的是：

```ts
fetch(`${API_URL}/api/evidence/search?...`)
```

SQLite 初始化和查询都在：

```text
packages/api/src/domains/memory/SqliteEvidenceStore.ts
```

所以通信边界是：

```text
MCP stdio → HTTP → API → 进程内 Memory domain → SQLite
```

---

## 面试官第二问：你说支持 hybrid，默认就是 hybrid 吗？

### 准确回答

不一定。

- MCP handler 默认只设置 `dimension='project'`；
- `mode` 如果没有传，就不会写入 URL；
- Store 内部 `options.mode ?? 'lexical'`；
- 因此未显式传 `mode=hybrid` 时，默认是 lexical；
- 即使显式传 hybrid，embedding mode 不是 `on` 或 sidecar 不可用时，summary 路径仍会回退 lexical；
- 当前 summary fallback 的 `meta.degraded` 还是 `false`，这点与 raw path 不一致。

---

## 面试官第三问：RRF 具体怎么做？

### 可直接表达的回答

> 代码不是把 BM25 分数和向量距离直接相加，而是先保留 lexical 和 vector 两个有序候选列表，再按名次做 Reciprocal Rank Fusion。实现中 rank 是 0-based，常数 `K=60`，每个列表贡献 `1/(60+rank)`。如果查询包含中日韩字符，向量分支权重变成 1.5，用来弥补 FTS5 对 CJK 词法召回较弱的问题。之后用 anchor 去重，并对向量命中的缺失文档做一次带过滤条件的 SQLite hydrate。

---

## 面试官第四问：为什么不在 search_evidence 里直接返回完整文件？

### 源码级回答

因为搜索和证据核实是两个阶段：

1. `evidence_docs` 中保存的是 title、summary、keywords、sourcePath 等候选信息；
2. `drillDown` 只返回下一步工具和有限窗口；
3. `read_file_slice` 默认最多 120 行，硬上限 400 行；
4. thread 结果则交给 `get_thread_context`；
5. 这样可以控制 prompt token，也避免 Agent 只凭一个长摘要下结论。

这体现的是：

```text
索引负责找路
原文读取负责证据确认
```

---

## 面试官第五问：超时以后底层搜索会停止吗？

### 准确回答

不能一概而论。

- `SessionBootstrap` 使用 `AbortController` 取消 HTTP fetch 的等待；
- `context-transport.recallEvidence` 使用 `Promise.race`，超时后返回空数组；
- 但后者没有把 AbortSignal 传给 `evidenceStore.search()`，因此只能保证调用者不再等待，不能证明底层检索已经停止；
- Embedding HTTP 请求本身使用 `AbortSignal.timeout()`，能终止客户端 fetch，但源码没有证明远端模型推理一定被取消。

---

## 面试官第六问：这个系统是严格一致的吗？

### 准确回答

不是全链路强一致。

- SQLite 常规写入通过进程内 FIFO queue；
- WAL 和 busy timeout 提供 SQLite 层面的并发处理；
- 但 lexical、embedding、vector hydrate 之间有多个 await，不在一个事务中；
- passage vector 是 lexical passage 的加速器，可能滞后；
- 某些实验 cohort/log 直接写 DB，没有走 Store queue；
- 因此它更接近“本地持久化 + 可降级 + 最终补齐”的检索系统，而不是严格快照式搜索系统。

```ts
export function extractFrontmatter(
  content: string,

  const match = content.match(/^---\n([\s\S]*?)\n---/);
  if (!match?.[1]) return null;

  for (const line of match[1].split('\n')) {
    const kv = line.match(/^(\w+):\s*(.+)$/);
    if (!kv) continue;

    const arrMatch = kv[2].match(/^\[(.+)]$/);

}
```

## 5.1 `sourceHash` 是什么，不是什么

源码：

```ts
const sourceHash = createHash('sha256')
  .update(scanned.rawContent)
  .digest('hex')
  .slice(0, 16);
```

它是：

```text
源文件内容变化指纹
```

它不是：

- primary key；
- 幂等键；
- 文件身份；
- 乐观锁版本号；
- 绝对无碰撞保证。

`anchor` 才是 `evidence_docs` 的主键。

`sourceHash` 被截断为 16 个十六进制字符，即 64 bit。碰撞概率很低，但不是数学上不可能。

原始文件不变时：

```text
sourceHash 不变
```

但 scanner 代码可能变化，例如新增加：

```text

```

因此源码还有：

```ts
export const INDEXING_VERSION = 5;
```

如果数据库中的 `indexing_version` 不等于 5，就自动 force rebuild。

这解决的是：

```text
原文没变
但派生字段算法变了
```

不过前提是开发者修改派生算法时记得提高 `INDEXING_VERSION`。

## 7.1 进入进程内 single-writer queue

[`D:\AI\clower-1\clowder-ai\packages\api\src\domains\memory\evidence-write-queue.ts#L6-L20`](file:///D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/evidence-write-queue.ts#L6-L20)

```ts
private tail: Promise<void> = Promise.resolve();

enqueue<T>(fn: () => T | Promise<T>): Promise<T> {
  return new Promise<T>((resolve, reject) => {
    this.tail = this.tail.then(async () => {
      try {
        resolve(await fn());
      } catch (e) {
        reject(e);
      }
    });
  });
}
```

本次安全最小验证得到：

```text
提交顺序：
A（内部等待 30ms）
B
C（抛错）
D

实际执行顺序：
A:start
A:end
B
C:throw
D
```

返回：

```text
A
B
ERR:boom
D
```

说明当前实现：

- 同一个 queue 内 FIFO；
- 前一个异步操作完成前，后一个不会开始；
- 某个任务失败不会毒死整个 tail；
- 后续任务仍然继续；
- 如果某个任务永久不返回，后面的写入也会永久等待；
- queue 只属于一个 `SqliteEvidenceStore` 实例，不是跨进程锁。

```sql
AFTER UPDATE:
  先删除旧 FTS 内容
  再插入新 FTS 内容
```

因此普通 INSERT/UPDATE/DELETE 的文档行与 FTS 更新位于同一个 SQLite statement/transaction 范围内。

但要注意当前 Store 使用的是：

```sql
INSERT OR REPLACE
```

不是：

```sql
INSERT ... ON CONFLICT(anchor) DO UPDATE
```

## 8.1 `INSERT OR REPLACE` 的最小隔离验证

我没有连接项目真实数据库，而是用 Python SQLite **3.50.4** 建立了完全隔离的内存表、FTS5 表和同结构 trigger。

验证步骤：

```text
1. INSERT anchor=F102, title="old title"
2. INSERT OR REPLACE anchor=F102, title="new title"
3. 查询 MATCH old / MATCH new
4. 比较 recursive_triggers=off 和 on
```

结果：

### `recursive_triggers=off`

```text
evidence_docs:
rowid=2, title=new title

FTS MATCH old:
仍返回旧 rowid=1

FTS MATCH new:
返回 rowid=2
```

但生产搜索 SQL会：

```sql
JOIN evidence_docs d ON d.rowid = f.rowid
```

所以旧 rowid=1 无法 join 到当前文档，通常不会产生错误搜索结果。

### `recursive_triggers=on`

```text
MATCH old:
无结果

MATCH new:
rowid=2
```

当前源码初始化设置了：

```text
journal_mode
foreign_keys
busy_timeout
```

没有设置 `recursive_triggers`。

因此可以得出：

- **已验证于隔离 SQLite 3.50.4**：默认关闭 recursive triggers 时，REPLACE 可能留下旧 FTS posting；
- 搜索 join 会过滤掉无对应 content row 的旧 posting；
- 但可能产生索引膨胀或多余扫描；
- 当前 `checkConsistency()` 只比较 count，可能发现不了这种情况；
- 尚未使用本项目 `better-sqlite3 12.6.2` 的实际二进制复现，因此不能宣称生产环境一定如此。

# 十二、增量更新与 full rebuild 的职责并不相同

增量逻辑：

[`D:\AI\clower-1\clowder-ai\packages\api\src\domains\memory\IndexBuilder.ts#L606-L685`](file:///D:/AI/clower-1/clowder-ai/packages/api/src/domains/memory/IndexBuilder.ts#L606-L685)

## 12.1 两遍处理

```text

Pass 2：upsert
```

这样设计是为了：

```text

→ 先删掉它
→ 同一批中的低优先级候选才能接管 anchor
```

删除后还会：

1. 全仓库重新扫描；
2. 找所有声明同 anchor 的候选；
3. 按 kind priority 排序；
4. 选择最高者回填。

```text

vector 更新
edges 仍可能是旧的
```

要全局重建这些 edge，需要 full rebuild。

# 十三、时间、空间与 I/O 成本

设：

- `F`：发现的文件数量；
- `B`：所有文件总字符数；
- `N`：数据库 evidence 数量；
- `E`：抽取出来的 edge 数量；
- `C`：需要生成文档向量的数量；
- `A`：entity alias 数量。

## Scanner

```text
目录遍历：O(目录项数量)
读取原文：O(B)
frontmatter/title/summary/headings：O(B)
sourceHash：O(B)
```

每份文档会被多次线性扫描，虽然渐进复杂度仍是 `O(B)`，常数并不小。

## 内存

`discover()` 不是 streaming：

```ts
ScannedEvidence {
  rawContent: 完整文件文本
}
```

所有 `ScannedEvidence` 被一次性放入数组，用于后续 edge 重建。

因此峰值内存近似：

```text
O(B + F + E)
```

而不是只保留一份当前文件。

## 数据库

对于每个非 force 文档：

- 至少一次 `getByAnchor`；
- hash 相同则可能 skip；
- 未 skip 时又一次 `getByAnchor` 做 kind priority；
- 一个 singleton transaction upsert；
- 一次 entity mention refresh。

## Edges

即使文档全部 unchanged：

```text
删除全部 frontmatter edges
重新扫描全部 rawContent
逐条 addEdge

删除全部 content edges
重新扫描全部 rawContent
逐条 addEdge
```

所以“0 个 docsIndexed”不代表“0 个 SQLite write”。

## Embedding

文档向量：

```text
ceil(C / 64) 个 embedding batch
```

如果模型 metadata 不一致：

```text
C = evidence_docs 全量
```

具体时延依赖外部 embedding 服务，本次没有测量。

# 十四、事务、并发、重试与一致性总结

## 14.1 已确认的保证

### 单 Store 实例内常规 evidence 写入 FIFO

由 `EvidenceWriteQueue` 保证。

### 单次 evidence_docs upsert 有 SQLite transaction

但 `IndexBuilder` 通常一文档一个 transaction。

### FTS trigger 与文档 SQL 同一数据库事务执行

普通 trigger 失败会使该 SQL/transaction 失败。

### `firstIndexedAt` 在同 anchor 替换时显式保留

这保护了 F200 cold-start 逻辑不会因普通重建每次重置。

### Edge 通过主键和 `INSERT OR IGNORE` 去重

主键维度是：

```text
from_anchor + to_anchor + relation
```

---

## 14.2 不保证的部分

### full rebuild 不是全局原子操作

搜索可能看到部分新文档、部分旧文档。

启动 rebuild 在 listen 前执行，降低了这个问题；但手动或服务 ready rebuild 可能在服务运行时发生。

### docs、edges、entity mentions、vectors 不是一个事务

可能出现：

```text
文档成功
FTS 成功
entity mentions 失败
edge 尚未重建
vector 尚未生成
```

### queue 不是跨进程锁

API、CLI、另一个 API 进程各有自己的 queue。

### RebuildJobTracker 不是全局 rebuild mutex

只保护同一 tracker 发起的手工任务。

### 没有 per-document 自动 retry

写入失败会让 rebuild 抛错；启动路径只记录 warning。

### embedding fail-open

embedding 出错不会回滚 lexical index，但文档 vector 可能缺失或部分更新。

# 十六、连续面试追问

## 第一问：IndexBuilder 到底是什么？

### 可直接回答

> 它更像一个本地索引编译器。输入是 Markdown、thread、session 和 message 等真实来源；Scanner 先把原文解析成带 provenance 和 rawContent 的 `ScannedEvidence`，IndexBuilder 再补 sourceHash、做 anchor 冲突保护，最后写入 `evidence_docs`，由 trigger 同步 FTS，并异步派生 edge、entity mention 和 vector。它准备搜索读模型，本身不是搜索算法。

---

## 追问：`sourceHash` 是幂等键吗？

### 源码级回答

不是。

- 主键是 `anchor`；
- `sourceHash` 只是 raw content 的变化指纹；
- rebuild 非 force 时用它跳过 unchanged 文档；
- 只保留 SHA-256 前 16 个 hex；
- CRLF 和 LF 会产生不同 hash；
- scanner 逻辑变化由单独的 `INDEXING_VERSION` 处理。

---

## 追问：文档没变，是不是 rebuild 基本不做事？

### 准确回答

不是。

即使最终 `skipped++`，仍然会：

- 目录扫描；
- 完整文件读取；
- frontmatter/title/summary/heading 解析；
- sourceHash；
- DB 查询。

full rebuild 还会全局删除并重建 frontmatter/content edges。

所以“没写 evidence_docs”不等于“没有 I/O 或计算”。

---

## 追问：文档行、FTS、vector 是一次原子写吗？

### 准确回答

不是全链路原子。

- evidence_docs 与其 trigger 驱动的 FTS 更新处于文档 SQL 事务范围；
- entity mention refresh 在事务之后；
- edges 在另一个阶段全局重建；
- embedding 要等待外部 HTTP；
- vector 再单独写入；
- IndexBuilder 还按单文档提交，而不是整个项目一个事务。

因此可以出现 lexical 已可用、semantic 尚未补齐的中间状态。

---

## 追问：为什么有 full rebuild 和 incrementalUpdate 两条路径？

### 准确回答

因为两者掌握的信息不同。

full rebuild 知道：

```text
当前整个 corpus 有哪些 anchor
```

所以能：

- 删除 stale anchor；
- 全局重建 edge；
- 检查 indexing version；
- 批量 embedding。

incrementalUpdate 只知道：

```text
这几十个 path 发生了变化
```

因此更快，但当前不能完整处理：

- 未上报路径的删除；
- anchor 变化后的旧 row；
- 全局 edge 更新；
- indexing version。
